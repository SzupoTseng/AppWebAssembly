# 付録J　フロント／バックの境界決定表と、堀のチェックリスト

> これは第 9〜12 章を操作可能な形にしたものだ。**具体的な機能を前にして、それをどちら側へ置くべきか分からないときは、ここに従って進めばよい。**

---

## 1. 三つの問いによる決定の流れ

```
それぞれの機能モジュールについて、順に三つの問いを立てる：

┌─────────────────────────────────────────────────────────┐
│ 問い一：このロジックが一字一句ブログで公開されたら、商売は傷むか？ │
└─────────────────────────────────────────────────────────┘
        │
        ├─ 傷まない ──→ 【フロントの Wasm へ】費用も帯域も節約、privacy も上がり、並行数は無限
        │
        └─ 傷む ──→ 問い二へ進む
                  │
┌─────────────────────────────────────────────────────────┐
│ 問い二：それが要する計算量は、サーバを一台養うに値するか？        │
└─────────────────────────────────────────────────────────┘
        │
        ├─ 値する ──→ 【標準的なバックエンドのサービス】
        │
        └─ 値しない ──→ 問い三へ進む
                      │
┌─────────────────────────────────────────────────────────┐
│ 問い三：「フロントで計算し、バックで検証する」に割れないか？      │
│（検証はたいてい計算より数桁安い：整列は高いが、整列済みかの検査は安い）│
└─────────────────────────────────────────────────────────┘
        │
        ├─ 割れる ──→ 【混成：Wasm が計算 + 軽量なバックエンドが検証】★ 最良解
        │
        └─ 割れない ──→ 【バックエンドに置くしかない】その費用を受け入れる
```

## 2. 分類の対照表

### ✅ フロントの Wasm へ（計算が重く、アルゴリズムは公開で、機密がない）

| 種類 | 例 |
|---|---|
| メディア処理 | 変換、フィルタ、背景除去、サムネイル、形式変換、波形解析 |
| 幾何と描画 | 3D 行列、ブーリアン演算、メッシュ化、経路計画、物理シミュレーション |
| データ処理 | ローカルの SQL 問い合わせ、集約、整列、全文検索、圧縮と展開 |
| 解析と変換 | 構文解析、AST、コードのトランスパイル、形式変換、Markdown |
| 標準的なアルゴリズム | FFT、畳み込み、有限要素、モンテカルロ、ニュートン法、A* |
| 暗号の演算 | 暗号化と復号、署名、ハッシュ、ZKP の証明生成（**アルゴリズムは公開で、鍵はバイナリに入らない**） |
| エッジの AI 推論 | 画像分類、OCR、物体検出、軽量な LLM |

### ❌ バックエンドに置かねばならない（漏れれば災厄、あるいは単一の権威が要る）

| 種類 | なぜか |
|---|---|
| **鍵、パスワード、署名の秘密鍵** | `strings` が一秒で掴み出す（第 9 章の禁域その一） |
| **認証と認可の判定** | クライアントは信頼できず、いかなる自己証明もローカルで書き換えられる |
| **課金、与信、計量** | 金銭が絡む。単一の真実の源が要る |
| **監査ログ** | 改竄されえないものでなければならない |
| **多人数協働の衝突解決** | 権威ある仲裁と単一の状態が要る（Figma の CRDT エンジン） |
| **データの所有権とアクセス制御** | 権限の取り消しはサーバ側で効かねばならない |
| **中核の商業機密のアルゴリズム** | 判定基準：対手が明日それを手に入れたら、私に何が残るのか |
| **法令がデータの所在を求める処理** | 監査が問うのは「データがどこにあり、誰が触れるか」である |

### ⚖️「フロントで計算し、バックで検証する」に割れるもの（最も価値のある一類）

| 場面 | フロントがすること | バックがすること |
|---|---|---|
| ファイルのアップロード | ローカルでの圧縮、分割、ハッシュ計算 | ハッシュの検証、割当と権限の確認 |
| フォーム | 即時の検証、整形 | **もう一度検証する**（フロントの検証は体験であって、安全ではない） |
| 大きなファイルの処理 | 丸ごと処理し、結果の要約だけを送る | 要約の妥当性を検証する |
| ZKP | 証明の生成（高い） | 証明の検証（数桁安い） |
| 画像処理 | フィルタ、切り抜き、圧縮 | 出力の形式と大きさを検証する |
| スケジューリング／最適化 | 求解（NP 困難、高い） | 解の実行可能性を検証する（安い） |
| 検索 | ローカルの索引による検索 | 利用者をまたぐデータが要るときだけ介入する |

## 3. 混成アーキテクチャの、境界の設計原則

```
┌──────────── クライアント（丸ごとダウンロードされうる）─────┐
│  Wasm の計算カーネル                            │
│  · 標準の Web API のみに依存（Canvas/WebGL/OPFS）  │
│  · いかなる鍵も平文の機密も含まない                │
│  · strip/lto でコンパイルする                     │
└───────────────────┬───────────────────────────┘
                    │ ★ この線の四つの設計原則：
                    │
                    │ 1. 境界は狭く：要約で済むなら全量を送らない
                    │ 2. 境界は粗く：一度の要求で一束の結果を得る。細かい往復をしない
                    │ 3. 境界には schema を：Protobuf/FlatBuffers を使い、裸の JSON にしない
                    │ 4. 境界の向こうは敵だと仮定する：あらゆる入力を悪意あるものとして扱う
                    │
┌───────────────────┴───────────────────────────┐
│  バックエンドの API（あなたが完全に統べる）        │
│  · 短命で範囲を限った token（長期の鍵は決して配らない）│
│  · 認可の判定はすべてこちら側。クライアントの主張を信じない│
│  · 極めて軽量でよい（Lambda / Workers で足りる）    │
└───────────────────────────────────────────────┘
```

**四つのアンチパターン**（見かけたら警戒すべきもの）：

| アンチパターン | なぜ誤りか |
|---|---|
| フロントで「権限があるか」の真偽値を計算し、バックへ送る | クライアントはそれを直に `true` に書き換えられる |
| バックがフロントの送ってきた価格／割引／数量を信じる | 同上 |
| フロントの Wasm のハッシュで完全性を検証する | クライアントの自己検証はつねに迂回されうる |
| 「短命な token」の有効期間を半年にする | それはもう長期の鍵である |

## 4. 堀の自己評価表

> あなたの製品に一行ずつ点をつける（0 = まったくない、3 = 極めて強い）。

| # | 堀の種類 | 検証の問い | 時定数 | 点 |
|---|---|---|---|---|
| 1 | **技術的な先行** | オープンソースの共同体が等価なものを作るのに、どれだけかかるか？ | **1〜3 年** | ☐ |
| 2 | **データの引力** | 利用者が積み上げたデータは、乗り換えでどれだけ失われるか？ | 5〜15 年 | ☐ |
| 3 | **ワークフローの固着** | 私を外すのに、顧客は何人を再訓練し、いくつの流れを直すのか？ | 5〜15 年 | ☐ |
| 4 | **ネットワーク効果** | 利用者が増えるほど、一人ひとりにとっての価値が上がるか？ | 5〜15 年 | ☐ |
| 5 | **エコシステム** | いくつの第三者が、私のために沈んだ専用の投資をしたか？ | 5〜15 年 | ☐ |
| 6 | **物理的な資源** | ソフトウェアでは出せないものを、私は何か握っているか（計算力、帯域、生産能力、契約）？ | 長い | ☐ |
| 7 | **法令と責任の引き受け** | 私は SLA に署名し、事故のときに賠償できるか？ 競争相手はできるか？ | **10 年以上** | ☐ |
| 8 | **標準とプロトコル** | 他者は相互運用のために、私の形式へ取り込まねばならないか？ | 長い | ☐ |
| 9 | **AI エージェントのエコシステム** | AI エージェントが仕事をこなすとき、既定で私の API へつなぐか？ | 新興 | ☐ |

**読み方**：

- **第 1 項だけが高い** → **危うい**。三年のうちに追いつかれ、しかもあなたはまだ他の何も築いていないかもしれない。**正しい動き：技術的な先行で時間を買い、その間に 2〜5 を築く。**
- **2〜5 に高い項がある** → 堅固。多くの成功した SaaS が立っている位置である。
- **6〜8 に高い項がある** → 極めて堅固であり、**しかも AI に侵食されない**。
- **第 9 項** → 新しい競争の次元。2026 年になってようやく形をとりはじめた。

## 5. 購買する側の、鏡像のチェックリスト（同じ表を、裏から読む）

> 供給側が固着を築くのは当然であり、顧客が固着を見積もるのも当然である。**これは道徳の問題ではなく、対称な商売の判断である。**

```
□ 私のデータは丸ごと書き出せるか？ 書き出しの形式は開かれているか、専有か？
□ 書き出したあと、それを取り込める第二の場所はあるか？（本当に試したことがあるか？）
□ 版の履歴、コメント、権限の設定といった「周辺のデータ」も一緒に持ち出せるか？
□ 私の自動化の流れは、どれだけ専有の API に縛られているか？
□ この会社が明日、値を三倍にしたら、私の最悪の場合は何か？
□ この会社が明日倒れたら、私のデータはまだあるのか？
□ 私は「書き出して他所で復元する」を定期的に演習したことがあるか？
□ 私の払う金のうち、どれだけが機能を買う分で、どれだけが「事故のとき賠償してくれること」を買う分か？
```

**最後の一つがいちばん重い**：払っている金が**主に機能を買う分**なら、AI の時代にはあなたが自前で建てる目がある。**主に責任の外部委託を買う分**なら、自前で建てることは危険を自分の肩に戻すことになる（第 12 章の時間の罠）。

## 6. 三年後の自己点検

> 第 12 章の中核の問いは、単独で挙げるに値する。すべてのアーキテクチャ審査の議題に書き込むとよい。

```
□ これが三年後の真夜中に壊れたとき、誰が直すのか？ その人はまだ会社にいるか？
□ このコードの下層の構造を読み解いたことのある第二の人間はいるか？
□ 私の依存する標準の API のうち、どれが標準委員会でまだ動いているか？
□ 私の依存するブラウザの振る舞いが明日締められたら（たとえば OPFS の割当、
   クロスオリジン隔離の規則、ある Wasm 提案の意味論）、私の退路は何か？
□ 私の「消耗品の層」と「資産の層」は分かれているか？
   腐りは、私が捨ててよいと思っている層の内側に閉じ込められるか？
□ 私の schema は安定しているか？ それは未来のあらゆる変更を律する、最も有効な道具であるか？
```

**最初の問いに澄んだ答えがないなら、あなたが造っているのは車輪ではなく、負債である。**
