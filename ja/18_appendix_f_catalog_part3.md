## VI. 産業と工学のシミュレーション

### 71.（元 90）Kinematics-Wasm — 六軸ロボットの逆運動学の求解　🟡

**痛点**：自動化工学とスマート製造では、エンジニアがウェブ側（デジタルツインのダッシュボード、産業用ロボットのオンラインプログラミングのプラットフォーム）から多関節のロボットアームを制御せねばならない。ユーザがマウスで末端のツールをある三次元座標へドラッグすると、システムは全関節の回転角をリアルタイムに計算せねばならない——これを**逆運動学（IK）**と呼び、きわめて密な非線形の三角方程式系の求解、ヤコビ行列の逆演算、ニュートン・ラフソンの反復を伴う。純粋な JS で高頻度の行列の反復を扱うと、演算子の多重定義とキャッシュの最適化を欠くために求解が遅く、浮動小数点の精度の喪失でロボットアームに不自然な「関節の飛び」やデッドロックが生じやすい。

**原理**：産業級のロボット運動学の中核（C++/Rust の Orocos KDL の類）を Wasm へコンパイルする。**DH パラメータ行列のメモリ**：ロボットアームのデナビット・ハーテンバーグの幾何パラメータと目標の六自由度の姿勢行列を、厳密に連続した `f64` として線形メモリに整列させて並べる。**GC ゼロの微分反復器**：Wasm 内部の代数のオプティマイザがバイナリのレベルでヤコビ行列の特異値分解（SVD）と擬似逆の演算を高速に実行し、各反復は閉じたメモリ内で完結する。

**性能**：七自由度（冗長）の産業用ロボットアームの高精度な IK の収束の求解一回に、フロントエンドで **0.1〜0.3 ミリ秒**しかかからず（毎秒数千回解ける）、純粋な JS より **35 倍以上速く**、マウスのドラッグへのリアルタイムで滑らかな追従を実現すると主張されている。

**長所**：静的な産業デジタルツインのプラットフォームに産業制御級の高精度の運動学の求解をもたらす。Three.js と組み合わせればリアルタイムの 3D ロボットアームのシミュレーションができる。バックエンドコストはゼロ。
**短所**：IK は多解と特異点（singularities）の判定を伴い、Wasm 内部の C++ の例外の捕捉には仮想機械のクラッシュを防ぐ厚いグルーの設計が要る。

**競合**：純粋な JS の数学ライブラリ（高自由度の非線形の幾何方程式系の反復と疎なヤコビ行列の求解では、計算力も数値の精度も産業級のリアルタイム制御にまったく対処できない）。

### 72.（元 91）BioClust-Wasm — 単一細胞 RNA の遺伝子発現行列の階層クラスタリング　🔴

**痛点**：がん研究と現代の生物医学では、科学者が単一細胞 RNA シーケンス（scRNA-seq）が生む膨大な遺伝子発現行列（数万の細胞 × 数万の遺伝子の特徴）を分析せねばならない。中核の段階は**階層クラスタリング**とピアソン相関係数の距離行列の計算である。以前はバックエンドの HPC クラスタに頼るしかなかった。静的な医療のダッシュボードで対話的なヒートマップとクラスタリングの推論を直接提供しようとすると、純粋な JS は数百万の浮動小数点の要素に対して大量の動的なメモリの確保とキャッシュの最適化の欠如により、メインスレッドを永久に固めるか OOM で落ちる。

**原理**：C++ の産業級の行列クラスタリングの中核（C Clustering Library の中核の演算子など）を Wasm へコンパイルする。**キャッシュに整列した平坦な行列の配置**：遺伝子の発現データを連続した `f32` として厳密に整列させて線形メモリに並べる。距離行列の計算で JS のオブジェクトを一切確保せず、L1/L2 のキャッシュヒット率を限界まで高める。**SIMD のベクトル化と並列の分割統治**：一命令で 4 組の遺伝子発現量のユークリッド距離か相関係数を並列に計算し、同時に Web Worker で巨大な行列の木の分割を多コアの CPU へ配る。

**性能**：5,000 細胞、20,000 の遺伝子の特徴を含む医学の行列の全量のピアソン階層クラスタリングに、フロントエンドで **400〜650 ミリ秒**しかかからず、純粋な JS より **45 倍以上速い**と主張されている。

**長所**：静的な遺伝子医学のドキュメントサイトにインストール不要の科学級の演算能力をもたらす。**患者の遺伝子のプライバシーのデータが 100% ローカルのサンドボックスに留まり**、国際的な医療プライバシー（HIPAA）規範の最も厳しい要求に適合する。
**短所**：クラスタリングが生むバイナリの木構造は極度に低水準であり、フロントエンドがそれを高頻度で対話的な DOM ノードへ変換する必要があるなら、境界越えの逆直列化がオーバーヘッドを生むので、`TypedArray` の共有バッファで最適化する必要がある。

**競合**：純粋な JS の数学行列ライブラリ（軽量なグラフの統計には向くが、医学級の膨大な遺伝子の特徴、高次元の行列の反復、階層の木の連結のアルゴリズムでは次元を落として打ちのめされる）。

### 73.（元 92）Kyber-WebPlatform — 耐量子暗号（PQC）の鍵交換　🟡

**痛点**：量子計算の進展に伴い、RSA や ECC に基づく従来の非対称暗号は将来 Shor のアルゴリズムに破られる危険がある。世界のセキュリティの領域はポスト量子暗号（PQC）へ移りつつあり、NIST は **CRYSTALS-Kyber** を耐量子の鍵カプセル化（KEM）の標準に定めた。しかし Kyber の下層は極度に複雑な「格子ベース」の数論変換（NTT）と多項式環の代数演算を伴う。ウェブで純粋な JS にこれらの密なビット演算を実行させると性能が極めて低く、しかも **JS は定数時間（constant-time）の実行の保証を欠き、サイドチャネル攻撃で鍵を漏らしやすい。**

**原理**：Rust か最適化された C で書かれた公式の CRYSTALS-Kyber の中核を Wasm へコンパイルする。**定数時間の NTT エンジン**：Wasm が `i32`/`i64` の命令で線形メモリ上の厳密なバタフライ演算と剰余乗算を実行する。コードはコンパイルのレベルで**秘密鍵のデータに依存する動的な分岐を一切含まない**ことを保証し、タイミングのサイドチャネル攻撃を防ぐ。**メモリ安全な乱数の注入**：Wasm 内部に乱数生成器を内蔵せず、アーキテクチャ上は JS のグルーからブラウザ標準の `crypto.getRandomValues()` を安全に呼び、環境のエントロピーを耐量子暗号の行列へ注入する。

**性能**：標準的な Kyber-512/768/1024 の鍵のカプセル化と復号のカプセル化一回に、フロントエンドの計算時間が **0.2〜0.5 ミリ秒**しかかからず（毎秒数千回処理できる）、ネイティブ C の **85%** に達すると主張されている。

**長所**：静的ページに耐量子のエンドツーエンドの暗号通信の能力をもたらす。暗号の秘密鍵は永久にユーザのブラウザ内に留まる。バックエンドコストはゼロ。
**短所**：PQC の公開鍵と暗号文のサイズ（通常数 KB）は従来の ECC の曲線より顕著に大きく、フロントエンドにはこの大きめの暗号のバイトブロックを運ぶより堅牢なネットワーク転送のグルーが要る。

> ⚠️ **必要な技術的訂正**：元の記述は「Wasm が定数時間の実行を保証できる」と述べていたが——**より正確な表現が要る**。Wasm の仕様自体は定数時間を**保証しない**。保証するのは「JS エンジンのようにデータの型で内部表現を動的に切り替える（V8 の Smi → HeapNumber など）挙動がないこと」である。しかし**コンパイラは依然として分岐を導入しうるし、CPU にはデータ依存のキャッシュの挙動がありうる**。定数時間は**ソースの書き方**（秘密鍵に依存する分岐を避け、秘密鍵で索引を引くことを避ける）が保証するのであり、Wasm は JS よりも制御しやすい実行の基盤を提供しているにすぎない。**「Wasm を使ったから定数時間である」は危険な誤読である。**

**競合**：純粋な JS の暗号の模倣ライブラリ（JS エンジンは密なビットシフトと多倍長の剰余除算の実行時に自動の型変換を行うので、**定数時間をまったく保証できず**、セキュリティの防御に致命的な欠陥がある）。

### 74.（元 93）Hologram3D-Wasm — 3D 光学顕微のホログラフィック断層再構成　🔴

**痛点**：生物物理学と細胞のイメージングでは、デジタルホログラフィック顕微法（DHT）により、科学者が染色せずに（非破壊で）多角度のホログラムから細胞内部の 3D の屈折率の分布を再構成できる。中核は巨大な 3D の逆散乱の求解のアルゴリズムであり、数百枚の高解像度の 2D 干渉図に対する FFT、三次元のフィルタ逆投影（FBP）、非線形の多重散乱の反復を伴う。この重い計算は以前ワークステーションの GPU にしか頼れなかった。

**原理**：C++ の 3D 光学ホログラフィック再構成のアルゴリズムの中核を Wasm へコンパイルする。**複素数の 3D フーリエ空間のメモリ**：線形メモリ内に数百 MB に達する連続した平坦な空間を確保し、厳密に倍精度の複素数（振幅と位相を表す二つの `f64`）として 3D の周波数領域の行列を保存し、メモリのアドレス指定のオーバーヘッドを大きく削る。**SIMD で加速した逆投影**：一つの CPU 命令で複数のピクセルの光路差（OPD）と位相のアンラップの反復を並列に計算し、サンドボックス内で多角度の 2D の干渉縞を 3D の屈折率のボリュームデータへ復元する。

**性能**：1024×1024 の 2D ホログラムを 100 枚読み込み 512×512×512 の 3D の細胞の屈折率のモデルを再構成するのに、フロントエンドで **1.8〜3.2 秒**しかかからず、純粋な JS より **40 倍以上速い**と主張されている。

**長所**：静的な研究のプラットフォームにインストール不要のデスクトップ級の 3D 断層イメージングの求解能力をもたらす。生物試料のデータは完全にローカルで解析される。
**短所**：3D のホログラフィックの再構成は極度にメモリを食う。**2D のホログラムの枚数が多すぎるか解像度が高すぎると、容易に 4 GB の上限に触れるので、精密な「分割して取り寄せる」アーキテクチャの設計が要る**（第 8 章の突破アーキテクチャ一が必要になる場面）。

**競合**：純粋な JS の 3D の行列処理（効率的なポインタ操作とキャッシュに優しい多次元の配置を欠き、膨大な浮動小数点の 3D の周波数領域の変換でそのまま OOM を起こす）。

### 75.（元 94）Nesting2D-Wasm — 不規則多角形のネスティング最適化　🔴

**痛点**：機械加工、板金製造、革の裁断、衣料の紡織において、一枚の板材の上に何千もの任意の形状の 2D の部品を回転させて緊密に並べ、材料の利用率を最大化することを**ネスティング最適化**と呼ぶ。これは NP 困難な問題であり、中核は不規則多角形の臨界の非重なり境界（NFP, No-Fit Polygon）の求解、ミンコフスキー和、幾何の衝突検出、そして遺伝的アルゴリズムか焼きなまし法に基づく高度なヒューリスティック探索を伴う。フロントエンドで純粋な JS に不規則な幾何体の頂点の交差を頻繁に反復させると、求解が遅く、浮動小数点の精度の喪失で部品が重なりやすい。

**原理**：産業級の CAD/CAM のネスティングシステムの C++ の中核のアルゴリズムライブラリ（オープンソースの幾何ライブラリ GEOS に基づく最適化された演算子など）を Wasm へコンパイルする。**平坦な多角形の幾何のメモリ（NFP の配置）**：すべての部品の多角形の頂点の座標と回転角の行列を厳密に連続した `f64` として線形メモリに整列させ、バイナリのレベルで多角形の包絡線の切削の計算を高速に実行する。**マルチコアのヒューリスティックな並列探索**：Web Workers + `SharedArrayBuffer` を使い、異なる回転角とネスティングの順序の遺伝的アルゴリズムの集団を複数の CPU コアへ並列に配る。

**性能**：200 枚の高度に不規則な衣料の裁断片への深いネスティング最適化（500 世代の集団の反復）に、フロントエンドで **1.2〜2.5 秒**しかかからず、利用率 85% 以上のネスティングの配置（G-code/DXF 形式）を出せ、純粋な JS より **35 倍以上速い**と主張されている。

**長所**：静的な産業の CAD/CAM のクラウドの作業台に産業制御級の幾何のネスティング最適化をもたらす。SVG/Canvas と組み合わせればネスティングの軌跡のリアルタイムのアニメーション表示ができる。
**短所**：NFP の計算は極度に複雑であり、幾何の部品に高頻度のノイズの頂点（スキャンで生成された粗い多角形など）が含まれるなら、フロントエンドで先に幾何の簡略化の前処理をせねばならない。

**競合**：純粋な JS の幾何ライブラリ（Poly2Tri の類。高密度の不規則体のミンコフスキー和の求解と高度なヒューリスティックの反復では、計算力も幾何の精度も産業の生産にまったく対処できない）。

### 76.（元 95）HydroSolver-Wasm (EPANET) — 管網の水力学と過渡流体のシミュレーション　🟡

**痛点**：都市工学、水利計画、原子力の冷却系の設計では、エンジニアが数万の管、ポンプ、バルブを含む巨大な管網の水力学の動的シミュレーションを行う必要がある。とくにバルブの急閉が引き起こす「**水撃現象**」は、複雑な非線形の双曲型の偏微分方程式系の求解を要する。この技術はたいてい C 言語の権威ある中核 **EPANET**（有限要素法と特性曲線法 MOC を採る）に頼る。以前はウェブで管網のリアルタイムの圧力波の伝播を見せるには、位相をバックエンドの有限要素のワークステーションへ上げるしかなく、高並行時のコストは天文学的だった。

**原理**：数十万行の厳密な C のコードを積み上げた EPANET の水力学の中核を丸ごと Wasm へコンパイルする。**正確な疎な線形方程式系のソルバ**：管網の位相を Wasm のメモリ内で連続したバイナリの圧縮疎行列へ変え、効率的な疎行列の不完全コレスキー分解と共役勾配法（CG）の反復器を内部に統合する。**GC ゼロの過渡の推進の状態機械**：あらゆる時間刻みの動的な過渡の推進、管の摩擦の非線形項（Hazen-Williams か Darcy-Weisbach）の求解を、すべて連続したメモリ内で完結させる。

**性能**：10,000 の管のノードを含み 24 時間（刻み 0.1 秒の細かな過渡のシミュレーション）動的に発展する巨大な都市の管網の全量の有限要素の求解に、フロントエンドで **80〜130 ミリ秒**しかかからず、精度は国家級の水利工学の標準に適合し、純粋な JS より **35 倍以上速い**と主張されている。

**長所**：静的な産業のデジタルツインの水道のプラットフォームに産業級の流体力学の求解をもたらす。WebGL と組み合わせれば全市の管網の圧力波の振動をリアルタイムの色のコンター図で可視化できる。
**短所**：有限要素法は大量の境界条件と位相の行列の初期化を伴う。入力の管網のデータに行き止まりや非物理的な位相の誤りがあると、Wasm 内部の C のアサーションが仮想機械を落としやすいので、フロントエンドに極めて強い位相の事前検証のグルーの設計が要る。

**競合**：純粋な JS の数学ライブラリ（大きな疎な線形方程式系の求解と非線形の流体の偏微分方程式の時間刻みの反復では、計算力も数値の安定性もリアルタイムの産業制御の場面にまったく対処できない）。

### 77.（元 96）QuantMCMC-Wasm — 金融デリバティブの価格付けと MCMC のシミュレーション　🔴

**痛点**：クオンツ金融とリスク管理では、複雑なバリアオプション、アジアンオプション、多資産の経路依存のデリバティブを正確に評価するのに、高次元の確率微分方程式の求解が要る。最も権威ある手段は**マルコフ連鎖モンテカルロ（MCMC）** の経路シミュレーションと確率ボラティリティのモデル（Heston モデルなど）の反復であり、数百万の資産価格の軌跡に高頻度の乱数の標本抽出と偏微分方程式の発展を行う必要がある。以前この演算は完全にバックエンドの HPC の金融クラスタで実行された。

### 90.（元 109）MicroPhase-Wasm — 材料科学の金属の結晶粒のフェーズフィールド法の発展のシミュレーション　🔴

**痛点**：材料科学、冶金、航空宇宙の合金の製造では、金属の凝固や熱処理の過程における「結晶粒の組織」の発展の法則が、材料の機械的な強度と疲労寿命を直接決める。結晶粒の結晶化、粒界の偏析、デンドライトの成長を精確にシミュレートするには、科学者が複雑な**フェーズフィールド法の非線形の偏微分方程式系（Allen-Cahn か Cahn-Hilliard の方程式）**を解く必要がある——三次元か二次元の微視的な空間のグリッドに数十万回のラプラス作用素の離散化、界面の曲率の計算、密な時間刻みの発展を実行するのだ。以前これは国家の材料の実験室の GPU のスーパーコンピュータのクラスタに頼るしかなかった。

**原理**：材料物理学のオープンソースの C++ の高性能なフェーズフィールドのシミュレーションの中核を Wasm へコンパイルする。**結晶粒の秩序変数の平坦なメモリ**：空間の各グリッド点のフェーズフィールドの秩序変数、溶質の濃度、弾性のひずみエネルギーを厳密に連続した `f32` として整列させ、プロセッサのキャッシュヒット率を最大化する。**SIMD の空間差分の加速器**：一つの CPU 命令で 4 つか 8 つの空間対称の点の高次の有限差分のラプラス作用素の求解を並列に実行する。あらゆる時間刻みの非線形の動的な推進は Wasm のサンドボックス内で完結する。

**性能**：512×512 のグリッド規模の多元合金の微視的なフェーズフィールドの組織に 5,000 ステップの高精度の結晶化、デンドライトの成長、粒界の発展の反復を行うのに、フロントエンドで **350〜550 ミリ秒**しかかからず、精度は国際的な材料物理学の標準に適合し、純粋な JS より **50 倍以上速い**と主張されている。

**長所**：静的な材料工学のページに研究実験室級の微視的な組織の物理の発展の能力をもたらす。**合金材料の中核の配合と結晶化の発展の特徴のデータが 100% ローカルに留まり**、特許の機密の防護を備える。
**短所**：Cahn-Hilliard の方程式は四階の非線形の偏微分方程式であり、時間刻みの安定性への要求が極度に厳しい。ユーザが非物理的な初期の溶質の揺らぎを入力した場合、Wasm 内部に精密な**適応的な時間刻みの制御の状態機械**を自作する必要がある。

**競合**：純粋な JS の数学と画像のライブラリ（高密度の微視的な空間の偏微分方程式の有限差分の求解と多元の秩序変数の時間刻みの反復では数桁遅れる）。

### 91.（元 110）CSTRFlow-Wasm — 化学反応器の硬い微分方程式系の求解　🔴

**痛点**：化学工学、精密製薬、現代の化学工場では、連続撹拌槽型反応器（CSTR）が医薬品と化学原料を合成する中核の設備である。反応の収率を精確に制御し**熱暴走**による爆発を防ぐため、エンジニアが反応器内部の非線形の多相流の化学動力学をシミュレートせねばならない——きわめて硬派な「**硬い常微分方程式系（Stiff ODEs）**」を解き、数十の化学成分の異なる温度、圧力、撹拌速度における Arrhenius の反応速度の行列と物質移動の平衡を計算するのだ。フロントエンドで純粋な JS にこの種の強い硬さを持つ方程式（反応速度定数が数桁異なる）を解かせると、通常のルンゲ・クッタ法は完全に破綻する。陰的な方法（Gear や Radau5）は巨大な非線形のヤコビの逆行列を高頻度に解く必要があり、JS は正確なメモリ配置の最適化を欠くために求解が遅く、浮動小数点の精度の喪失で結果が歪みやすい。

**原理**：化学工学の世界の権威ある C++ の硬い微分方程式と熱力学の平衡の求解の中核を Wasm へコンパイルする。**化学成分の熱力学のメモリ**：反応に関わるすべての化学成分のエンタルピー、エントロピー、反応速度定数、動的な濃度の行列を厳密に連続した `f64` として整列させ、バイナリのレベルで陰的オイラーと準ニュートンの反復を高速に実行する。**GC ゼロの硬い微分の反復器**：Wasm 内部の代数のオプティマイザが閉じたメモリ内で反応系の疎なヤコビ行列を動的に再構成して高速に解き、各ステップの時間の推進で JS のゴミオブジェクトを一切生成しない。

**性能**：32 種の化学成分を含み、複雑な並行競合反応と非等温の熱平衡の制約を持つ産業級の CSTR の反応器に 24 時間の動的な発展と過渡の熱暴走の境界の予測を行うのに、フロントエンドで **45〜80 ミリ秒**しかかからず、正確な濃度と温度の時間変化の報告（求解の精度 10⁻⁸）を出せ、純粋な JS より **55 倍以上速い**と主張されている。

**長所**：静的な化学工学のデジタルツインのツールに産業級の化学動力学の求解をもたらす。HTML5 のグラフと組み合わせれば反応器の温度の振動をリアルタイムに可視化できる。
**短所**：硬い微分方程式系の陰的な求解は非線形の反復の収束性に強く依存し、ユーザが非物理的な極端な負の濃度や初期温度を入力した場合、Wasm 内部の C++ の例外の捕捉に厚いグルーの設計が要る。

**競合**：純粋な JS の常微分方程式のライブラリ（強い硬さの化学動力学の系と巨大なヤコビ行列の高頻度の陰的な求解では、計算力も数値の安定性も産業制御とデジタルツインの場面にまったく対処できない）。

## VII. 五つの基盤エンジン

> この節の五つの類別（ソフトウェアエンジン、物理エンジン、世界エンジン、LLM エンジン、グラフィックエンジン）は、元の対話の 111 件目でユーザが自ら指定した新しい分類の次元である——**これこそ第 6 章が挙げたあの有効な解法である：探索空間を制約するほうが、記憶を求めるより有効である。**

### 92.（元 111）OpenLISP-Wasm　[ソフトウェアエンジン] — 記号計算と関数型の LISP の中核　🟡

**痛点**：記号 AI、エキスパートシステム、メタプログラミングにおいて、LISP の **S 式**と「コードはデータである（homoiconicity）」という特性は代替不能な価値を持つ。ウェブのフロントエンドで安全な記号計算の Playground やオンラインの規則のコンパイルのエンジンを提供しようとして、LISP のコードを JS のオブジェクトへ直接変換すれば、LISP がきわめて頻繁に末尾再帰し、動的スコープを束縛し、リストのノード（cons cells）を生成するために、JavaScript が壊滅的な GC の固まりを起こす。

**原理**：産業級の C 言語の極小の LISP の中核のインタプリタを Wasm へコンパイルする。**平坦なポインタのメモリプール**：線形メモリ内で、LISP の環境の束縛の木と cons のノードはもはや JS のオブジェクトとして離散して保存されず、連続したバイナリの配列へ圧縮される。Wasm 内部は極めて速い**マーク・アンド・スイープの自作のメモリ回収エンジン**を保持し、ブラウザの JS のヒープの調整を完全に迂回する。**末尾呼び出し最適化の対応**：Wasm の **`return_call`（末尾呼び出し。Wasm 3.0 の核心仕様入り）** の命令を使い、バイナリのレベルで LISP の深い再帰を平坦なレジスタ級のジャンプへ直接変え、スタックの溢れを根絶する。

**性能**：1,000,000 回の記号の置換と深い再帰の照合を含む代数の定理証明のスクリプトの実行に、フロントエンドで **35〜55 ミリ秒**しかかからず、ネイティブ C の **82%** に達し、純粋な JS の LISP のインタプリタより **30 倍以上速い**と主張されている。

**長所**：静的なオンラインの教育と記号計算のプラットフォームにバックエンドコストゼロの安全な実行環境をもたらす。企業の中核の業務規則のスクリプトが完全にローカルに留まる。
**短所**：LISP の記号の木は Wasm のメモリ内で高度に緊密なので、フロントエンドの JS がそれを頻繁に JSON へ直列化したい場合、境界越えの変換がオーバーヘッドを生むため、`TypedArray` の共有バッファで最適化する必要がある。

> 💡 **これは本書で唯一、Wasm の末尾呼び出しの命令を直接使う事例である。** これは第 1 章のあの一文——「末尾呼び出しがなければ、関数型言語の深い再帰は必ずスタックを溢れさせる」——がなぜ返済せねばならない技術的負債だったのかも説明している。

**競合**：純粋な JS の LISP の模倣ライブラリ（効率的なバイナリのポインタ操作とネイティブの末尾呼び出しの最適化を欠き、大規模な記号のリストの処理で頻繁な GC の引っかかりとクラッシュを招く）。

### 93.（元 112）OpenVDB-Wasm　[物理エンジン] — 疎な 3D ボリュームの流体と煙のシミュレーション　🟡

**痛点**：映像の視覚効果と高度な産業の物理シミュレーションでは、煙、炎、液体、複雑な 3D の剛体の「表面の裂けと動的な衝突」のために、膨大な三次元の空間のグリッドのデータを保存し処理せねばならない。この技術の黄金標準は DreamWorks がオープンソース化した **OpenVDB**（革命的な階層的な疎な B+ 木の構造 VDB-Tree を採る）である。フロントエンドで純粋な JS の通常の 3D 配列に 1024³ の巨大な動的な流体のボリュームをシミュレートさせると、メモリのオーバーヘッドが数 GB に達し、高頻度のレベルセットの曲率の変換と粒子の衝突検出でそのまま OOM で落ちる。

**原理**：数十万行の C++ を積み上げた OpenVDB のボリュームの物理エンジンの中核を Emscripten で Wasm へコンパイルする。**高度に緊密な疎な 3D の空間木**：物理の空間を 3D の疎な位相の木へ離散化し、Wasm 内部が極度に最適化された連続したバイナリのキャッシュに優しい配列を保持し、**流体や煙の密度を含む有効なノードだけを保存して**、L1/L2 のヒット率を限界まで高める。**SIMD の演算子のベクトル化の加速**：一命令で 4 つか 8 つのボリュームのグリッド点の Navier-Stokes の圧力の偏微分方程式を並列に計算し、サンドボックス内でマルチスレッドにより物理の刻みを並列に進める。

**性能**：複雑で不規則な 3D のモデルを含む場面で 500,000 の高度に疎な煙のボリュームの粒子の拡散と剛体の表面の衝突をシミュレートし、物理シミュレーションの各ステップが **8〜12 ミリ秒**を超えず、60 FPS を固定すると主張されている。

**長所**：静的な 3D の視覚効果のダッシュボードにインストール不要の映像級の物理シミュレーションをもたらす。**WebGPU のシェーダと完璧に組み合わさる——Wasm が計算した疎なボリュームの行列を GPU 内で直接リアルタイムのボリュームレイキャスティングで描画できる。**
**短所**：OpenVDB のコード量は極度に巨大であり、コンパイルされた Wasm はたいてい **4〜6 MB** あり、ページへの初回の進入時のロードの負担が明らかである。

**競合**：純粋な JS の 3D の物理ライブラリ（小規模で低精度の民生の視覚効果にしか向かず、高次元の産業級の疎な 3D のボリュームのレベルセットの発展と多体の衝突の求解では次元を落として打ちのめされる）。

### 94.（元 113）ProcPlanet-Wasm　[世界エンジン] — 無限のプロシージャルな仮想惑星の地形の生成　🔴

**痛点**：宇宙のシミュレーション、デジタルツインの地球、超大型のサンドボックスゲームでは、正確な地形、河川の位相、植生の分布、大気の光学の散乱を含む「1:1 の等比の仮想惑星の世界」をリアルタイムに生成することが極度に硬派な技術である。中核は**プロシージャル生成の世界エンジン**であり、密な 64 ビットの高次のフラクタルノイズ（シンプレックスノイズ、FBM）、プレートテクトニクスの侵食のアルゴリズム、レイリーとミー（Rayleigh & Mie）の大気の非線形の光散乱の方程式の求解を伴う。フロントエンドで純粋な JS にマウスの移動に応じて数百万の地形のメッシュの頂点を動的に計算させると、多次元の配列のキャッシュのアドレス指定の最適化を欠くために深刻な「地形の読み込みの引っかかり（pop-in）」を招く。

**原理**：Rust で書かれた高精度のプロシージャルな仮想世界の生成エンジンの中核を Wasm へコンパイルする。**八分木の動的な連続の詳細度（LOD Octree）**：仮想惑星を線形メモリ内で平坦な八分木の構造として管理し、カメラの視点の遠近に応じて Wasm 内部のオプティマイザがバイナリのレベルでメッシュの分割と簡略化を高速に実行する。**SIMD の演算子のベクトル化のフラクタル**：一つの CPU 命令で 4 つか 8 つの地表の座標の高次のノイズの振動関数を並列に計算し、全過程で JS のゴミオブジェクトの確保がない。

**性能**：ユーザが超音速で仮想惑星の表面を飛ぶとき、高精度の法線ベクトルと侵食の特徴を含む 3D の地形の頂点を毎秒**最大 2,000,000 個**動的に生成でき、ネイティブの中核の **80%** に達し、60 FPS のフルフレームの描画を保つと主張されている。

**長所**：静的なプラットフォームに「宇宙級」の無限の世界のプロシージャル生成をもたらす。**バックエンドのディスクの保存コストがゼロ——世界は完全にシード値からリアルタイムに計算され、地形のデータを一切保存しなくてよい。**
**短所**：プロシージャルな世界エンジンは複雑な熱力学の大気の散乱の積分を伴い、よい GPU の対応がない低性能な端末では、Wasm の純粋な CPU の縮退の計算で大気の拡散反射を扱うときに性能のピークが生じる。

**競合**：純粋な JS の地形の生成器（低水準のメモリの整列とビット演算の最適化を欠き、大規模なフラクタルの行列の計算で CPU のピークが高すぎ、地形の読み込みが深刻に遅れる）。

### 95.（元 114）RWKV-Core-Wasm　[LLM エンジン] — 線形注意の大規模モデルの超低メモリ推論　🟢

**痛点**：ブラウザ側で大規模言語モデルの推論を実行するとき、主流の Transformer のアーキテクチャは致命的なボトルネックに直面する：**KV キャッシュのサイズが文脈の長さに対して線形か二次で爆発し**、数万字の対話を扱うときにブラウザがメモリの上限を超えてクラッシュしやすい。そこでオープンソースの世界は次世代のアーキテクチャ **RWKV**（線形の回帰的なニューラルネットワークに基づく Transformer）を出した。これは KV キャッシュを「**一定サイズの Time-Mix / Channel-Mix の状態ベクトル**」へ圧縮する。しかしウェブのフロントエンドで RWKV の重みの行列積を滑らかに実行しようとしても、純粋な JS は数十億回の浮動小数点の演算に対してトークンの出力速度が一秒一文字の亀の歩みまで落ちる。

**原理**：RWKV 公式のオープンソースの C/Rust の推論エンジンの中核を Wasm へコンパイルし、非中央集権のプライバシー LLM のエッジ計算のエンジンとする。**平坦な重みの行列のメモリ配置**：モデルの量子化された重み（INT4/INT8）をバイナリのバイト列として直接線形メモリへ書き、Wasm がポインタの直接制御による高速な表引きで線形注意の行列の積和（GEMM）を実行する。**SIMD の演算子のベクトル化の逆量子化**：一つの CPU 命令で 4 つか 8 つの INT4 の重みの浮動小数点への変換を並列に展開して計算し、同時に Web Worker でモデルの行列をブロックに切って多コアの CPU へ配り同期して推論する。

**性能**：1.5B パラメータの軽量化された RWKV のモデルを読み込み、SIMD とマルチスレッドを有効にすると、フロントエンドのトークンの生成速度が **毎秒 15〜25 トークン**に達し、ネイティブの中核の **75%** に達すると主張されている。

**長所**：静的ページに「文脈が無限に長く、メモリが爆発しない」エッジ AI の推論の能力をもたらす。**ユーザのあらゆるプライベートな対話と商業機密のコードが 100% ローカルに留まる。** バックエンドの GPU コストはゼロ。
**短所**：RWKV はメモリを極めて節約するが、1.5B パラメータのモデルファイルは圧縮後でも数百 MB あり、ページへの初回の進入時に長い読み込みの待ちが要るので、**PWA として設定しローカルの永続キャッシュにするのが向く**（まさに第 7 章の OPFS の応用の場面である）。

**競合**：純粋な JS のニューラルネットワークのライブラリ（厳格な型の最適化、効率的なバイナリのビットシフトの解析、レジスタ級の行列演算を欠き、大規模モデルの推論でそのまま固まる）。

### 96.（元 115）Pagmo-Wasm　[最適化エンジン] — 多目的の大域最適化と進化計算　🟡

**痛点**：航空宇宙の軌道の設計（ESA の惑星間探査の経路計画）、物流のサプライチェーンのスケジューリング、高度な工学の構造の設計では、エンジニアが「**多目的の大域最適化**」に直面する——互いに衝突する数百の極限の指標を同時に解き、膨大な局所最適の罠を越えるのだ。世界最高峰の非線形の進化計算の中核は ESA がオープンソース化した **pagmo**（一般化された島モデルに基づく）である。フロントエンドで純粋な JS に粒子群最適化（PSO）、差分進化（DE）、NSGA-II などのアルゴリズムの並列の集団の進化を実行させると、JS のエンジンは高頻度の位相の移住と突然変異の交叉でメモリと CPU のピークが指数的に爆発し、ブラウザを完全に固まらせる。

**原理**：ESA 公式のオープンソースの C++ の多目的最適化エンジン pagmo を丸ごと Wasm へコンパイルする。**異種の島のメモリ配置**：すべての最適化の島の集団の遺伝子の行列、適応度のスコアの表、制約の境界を厳密に連続した `f64` として整列させ、バイナリのレベルでパレート最適解（Pareto Front）の選別を高速に実行する。**多島の異種の並列進化の状態機械**：Web Workers + `SharedArrayBuffer` で高速な移住のキューを構築する——**各 Worker のスレッドが独立に進化する生態の島を一つシミュレートし、各島が定期的にバイナリのポインタで遺伝子を交換する**。全過程で JS のゴミオブジェクトの確保がない。

**性能**：50 次元、3 つの衝突する目的、10,000 個体の集団を持つ産業級の極端な非線形の関数に全量の大域最適化の進化の求解を行うのに、フロントエンドで **450〜700 ミリ秒**しかかからず、正確なパレート最適解の集合を出せ、純粋な JS より **40 倍以上速い**と主張されている。

**長所**：静的な産業の CAD/CAM の作業台と研究のダッシュボードに航空宇宙級の多目的の大域最適化をもたらす。HTML5 のグラフと組み合わせればパレートフロントの進化の過程をリアルタイムのアニメーションで見せられる。
**短所**：進化計算は大量の乱数の突然変異を伴い、目的関数の内部に高度に非線形の特異点があれば、Wasm 内部の C++ の例外の捕捉に厚いグルーの設計が要る。

**競合**：純粋な JS の遺伝的アルゴリズムのライブラリ（高次元の多目的の最適化、大規模な異種の島の並列進化、高頻度の位相の移住では、計算力も数値の安定性も数桁遅れる）。

### 97.（元 116）AMReX-Core-Wasm　[ソフトウェアエンジン] — 適応的メッシュ細分化（AMR）の巨大な PDE のシミュレーション　🟡

**痛点**：天体物理の爆発のシミュレーション、燃焼の流体力学、気候の予測では、空間の偏微分方程式を解くとき、特定の領域（衝撃波の前縁、炎の中心）の物理量の変化が極度に激しく、非常に高い解像度のメッシュが要る。その他の緩やかな領域は粗いメッシュで足りる。この技術の産業の黄金標準はローレンス・バークレー国立研究所がオープンソース化した **AMReX** のフレームワークのエンジンである。ウェブで動的なメッシュの分割と再構成を提供しようとしても、純粋な JS は数百万の多階層の入れ子のメッシュのポインタの飛び回りと再整列に対して頻繁なメモリの断片を招き、メインスレッドを永久に固める。

**原理**：数十万行の C++ の中核を積み上げた AMReX のソフトウェアエンジンを Emscripten で Wasm へコンパイルする。**平坦な多階層のポインタのメモリプール**：多階層の入れ子のメッシュの空間の位相の構造と境界条件はもはや JS のオブジェクトとして離散して保存されず、連続したバイナリのキャッシュに優しい配列へ圧縮される。特定の物理量の勾配が閾値を超えたとき、Wasm 内部がバイナリのポインタのオフセットを直接実行し、動的に子メッシュを分割する。**SIMD の演算子のベクトル化の差分**：一つの CPU 命令で 4 つか 8 つの空間のグリッド点の高次の有限差分のフラックスの求解を並列に計算し、全過程でブラウザの JS のヒープの確保を迂回する。

**性能**：衝撃波の振動を含む非線形の流体の流れ場のシミュレーションで、5 階層の入れ子のメッシュを動的に管理し高精度の偏微分の時間刻みの推進を実行するのに、フロントエンドで一フレームの求解に **180〜290 ミリ秒**しかかからず、ネイティブ C++ の **80%** に達し、純粋な JS より **35 倍以上速い**と主張されている。

**長所**：静的なオンラインの教育と研究のプラットフォームに国立研究所級で、バックエンドコストゼロの巨大な代数とメッシュの分割のエンジンをもたらす。研究者の機微な中核のパラメータが完全にローカルに留まる。
**短所**：AMR が生むデータ構造は極度に低水準であり、フロントエンドの JS がそれを頻繁に JSON へ直列化したい場合、境界越えの変換がオーバーヘッドを生むので、`TypedArray` の共有バッファを使い WebGL でハードウェアのコンター図の描画をせねばならない。

**競合**：純粋な JS の偏微分の計算ライブラリ（効率的なバイナリのポインタ操作と緊密なメモリの整列を欠き、高密度の適応的な動的メッシュの細分化の分割でメモリと CPU のピークが指数的に爆発する）。

### 98.（元 117）ChronoEngine-Wasm　[物理エンジン] — 多相の粒子流と流体構造連成（FSI）　🟡

**痛点**：機械工学、不整地車両の地形の動力学、製薬の混合の工程では、数十万の離散した粒子（砂、錠剤）と複雑な 3D の機械の剛体のあいだの「**流体構造連成（FSI）**」の相互作用と非線形の摩擦の衝突をシミュレートせねばならない。この技術の黄金標準はオープンソースの産業級の多体物理エンジン **Project Chrono** である。フロントエンドで純粋な JS の通常の 3D 剛体のライブラリ（Matter.js）に 10 万の砂の粒子と履帯車両の衝突を含む巨大な系をシミュレートさせると、メモリのオーバーヘッドと衝突検出の複雑さが指数的に爆発し、タブを OOM で落とす。

**原理**：数十万行の一流の C++ のコードを積み上げた Chrono の物理エンジンの中核を Emscripten で Wasm へコンパイルする。**圧縮された疎な非線形の拘束の配置**：すべての離散した粒子の質量、三次元の座標、速度、そして **DVI（Differential Variational Inequalities）** に基づく摩擦の接触の拘束を、厳密に連続したバイナリの構造体配列として線形メモリに並べる。**SIMD のベクトル化の錐計画のソルバ**：一つの CPU 命令で複数の粒子の接触面の二次錐計画（SOCP）の凸最適化の反復を並列に計算し、Web Workers + `SharedArrayBuffer` で膨大な粒子の空間の分割を並列に配る。

**性能**：不整地のロボットアームを含む 3D の場面で **100,000 の離散した粒子流**の動的な衝突、堆積、非線形の摩擦の抵抗の求解を同時にシミュレートし、物理シミュレーションの各ステップが **6〜10 ミリ秒**を超えず、60 FPS を固定すると主張されている。

**長所**：機械と土質力学の産業級の高精度の物理のフィードバックを提供し、純粋な JS の物理エンジンが「膨大な粒子流と多体の流体構造連成」を扱えないという欠陥を根絶する。Wasm のモジュールは高度に自律的で、バックエンドのシミュレーションのサーバをまったく必要としない。
**短所**：Chrono は極度に複雑な硬い微分方程式と時間積分の求解を伴い、ユーザが非物理的な極端な衝撃力を入力した場合、Wasm の仮想機械が落ちるのを防がねばならない。

**競合**：Ammo.js / Cannon.js（軽量なウェブの 3D ゲームの剛体の衝突には向くが、数十万次を超え膨大な離散した粒子流を含む産業級の流体構造連成と非線形の滑り摩擦の求解ではまったく実用にならない）。

### 99.（元 118）CivEvo-Core-Wasm　[世界エンジン] — マルチエージェントの地政学と気候経済学のシミュレーション　🔴

**痛点**：気候変動の経済学、マクロの歴史動態学（クリオダイナミクス）、大型の戦略のサンドボックスゲームでは、数万の仮想の国家／派閥、百万を超えるマルチエージェントの自律的な意思決定、動的な資源の消費と全球の気候のフィードバックを伴う「多階層の仮想世界のモデル」をリアルタイムに生成し推論することが、技術的な偉業である。中核は密な確率的なゲームの行列の求解、非線形の人口動態（マルサスのモデル）、巨大な需給のネットワークのワルラス均衡の非線形の反復を伴う。フロントエンドで純粋な JS に時間刻みに応じて百万のエージェントの経済の取引と資源のゲームを動的に計算させると、動的型付けと頻繁なオブジェクトの生成が深刻な GC の停止を招き、世界の推論に画面の裂けを生じさせる。

**長所**：静的なプラットフォームに「国家級」の全球の気候経済学と地政学の多階層の世界のシミュレーションをもたらす。**世界は完全にシード値からリアルタイムに計算され、バックエンドの膨大なセーブのサーバのディスクのコストを省く。**
**短所**：世界エンジンは高度に複雑な非線形の多変数のフィードバックを伴い、シミュレーションの系のある部分市場のパラメータの設定が崩れると経済学の方程式が収束しなくなりやすいので、Wasm 内部に精密な**適応的な減衰（adaptive damping）の状態機械**を自作する必要がある。

**競合**：純粋な JS のシミュレータ（低水準のメモリの整列と密なバイナリのビットシフトの解析を欠き、大規模なマルチエージェントの関係網の表引きと代数の反復で CPU のピークが高すぎ、世界の推論が深刻に遅れる）。

### 100.（元 119）DeepSpeed-MoE-Wasm　[LLM エンジン] — 混合エキスパートのアーキテクチャの動的ゲーティング推論　🟡

**痛点**：エッジで LLM の推論を実行するとき、最新の黄金のアーキテクチャは**混合エキスパート（MoE, Mixture of Experts）**（Mixtral など）である——総パラメータは数百億に達するが、推論ごとにその一部のエキスパートのネットワークしか活性化しないので計算力を節約できる。しかし MoE はフロントエンドにもう一つの致命的な罰をもたらす：**巨大なモデルのサイズ（通常数十 GB）はクライアントのメモリにまったく収まらない。** ウェブのフロントエンドで MoE の動的な「ゲーティングネットワーク」のルーティングと重みの逆量子化の乗算を滑らかに実行しようとしても、純粋な JS は数十億回の浮動小数点の演算に対してトークンの出力を完全に固まらせる。

**原理**：産業級の大規模モデルの並列最適化のツール（Microsoft の DeepSpeed の推論の演算子の中核など）を Wasm へコンパイルし、非中央集権のプライバシー MoE のモデルのエッジの求解のエンジンとする。**動的な疎な重みのメモリ**：Wasm がポインタの直接制御による高速な表引きでゲーティングネットワークの Top-K のエキスパートのルーティングの計算を実行する。**内部では線形メモリに現在活性化されたエキスパートのネットワークの重みだけを常駐させ、OPFS でディスクとメモリのあいだのバイナリのブロックのストリーミングのスワップを実行する。** **SIMD の演算子のベクトル化の逆量子化**：一つの CPU 命令で 4 つか 8 つの INT4/INT8 の重みの行列の積和を並列に展開して計算し、同時に Web Worker でエキスパートの行列を多コアの CPU へ配る。

**性能**：8×7B だが推論ごとに 2 つのエキスパートしか活性化しない軽量化された MoE のモデルを読み込み、SIMD とマルチスレッドを有効にすると、フロントエンドのトークンの生成速度が **毎秒 12〜18 トークン**に達し、ネイティブの中核の **75%** に達すると主張されている。

**長所**：静的ページに「大規模モデルのアーキテクチャ、小さなメモリの占有」のエッジ AI の推論の能力をもたらす。ユーザのプライベートな対話と機微なコードが 100% ローカルに留まる。バックエンドの GPU コストはゼロ。
**短所**：OPFS で重みのストリーミングのスワップを行うとはいえ、**ローカルのディスクのランダム読み取りの速度（SSD の性能）への要求が高く**、従来の遅いハードディスクでは明らかな最初のトークンまでの遅延（TTFT）が生じる。

> 💡 **これは図鑑全体で第 7 章と第 8 章を最も徹底的に結びつけた事例である**：OPFS のランダム読み取り（第 7 章）とスライディングウィンドウのストリーミング（第 8 章の突破アーキテクチャ一）を同時に使って 4 GB の上限を迂回している——**そしてそのボトルネックは最終的にユーザの SSD に落ちる。これこそ「サーバコストゼロ」という一文の後半への最良の脚注である：コストは消えていない。誰かのハードウェアになったのだ。**

**競合**：純粋な JS のニューラルネットワークのライブラリ（厳格な型の最適化とレジスタ級の行列演算を欠き、MoE の複雑なゲーティングネットワークの調整で性能がそのまま固まる）。

### 101.（元 120）Mitsuba-Spectral-Wasm　[グラフィックエンジン] — 多スペクトルのラジオメトリと逆レイトレーシング　🟡

**痛点**：航空宇宙のリモートセンシング、塗料の光学の設計、高度な逆レンダリングでは、通常の RGB の三チャネルのグラフィックの描画エンジンでは物理の正確さをまったく満たせない。科学者は数十の連続した波長（380 nm〜780 nm、間隔 5 nm）を含む**多スペクトルのラジオメトリのレイトレーシングのエンジン**を使い、厳密な物理光学のマクスウェル方程式の幾何の近似と双方向反射率分布関数（BRDF）を解く必要がある。世界で最も権威ある研究級の中核は **Mitsuba** のレンダリングエンジン（C++）である。フロントエンドで純粋な JS の通常のベクトルで多スペクトルのレイの空間のグリッドとの交差と表面の偏光の状態の行列の反復を行うと、高次元の空間の波長の積分に対して深刻な CPU のピークを招き、ページを固まらせる。

**長所**：静的な航空宇宙のリモートセンシングと光学設計のダッシュボードに研究実験室級の多スペクトルのグラフィックエンジンをもたらす。バックエンドコストはゼロで、光学の中核の配合のデータをローカルで安全に解析することを保証する。
**短所**：多スペクトルの描画は大量の乱数の波長の標本抽出を伴い、材料の幾何の境界が極度に複雑なら、Wasm 内部の C++ の例外の捕捉に厚いグルーの設計が要る。

**競合**：Three.js（商業向けのウェブの 3D の展示には向くが、硬派な物理の多スペクトルの光子のエネルギーの発展、複素屈折率の偏光の行列の求解、高精度の光学の波長の積分では数桁遅れる）。

## 図鑑全体のまとめ：101 の事例が教える五つのこと

**一、Wasm はブラウザと高度な低水準のシステムの演算のあいだの物理の高い壁を打ち破ることに成功した。** 第 1 案のウェブの映像音声のトランスコードから第 101 案の航空宇宙級の多スペクトルのレイトレーシングまで、「ゼロ知識のプライバシー証明、量子の状態のシミュレーション、P2P ネットワークの多重化、産業制御の潮流の反復、大規模データの多次元の集計」といった硬派な技術を、完全に無料で、非中央集権で、エンドツーエンドにプライバシーが安全な静的ウェブの資産へ変えた。

**二、101 の事例すべての下層の技術の本質はきわめて一致している。** メモリのキャッシュに優しい平坦な配置 + SIMD のベクトル化が、JavaScript の柔軟だが断片的なオブジェクトの確保を次元を落として打ちのめした。**この五つのアーキテクチャ（平坦メモリのゼロコピー、Worker の隔離、SIMD、ストリーミングの分割、AudioWorklet の隔離）は第 6 章で完全に解体してある。**

**三、四つの動機が投資対効果を決める。** 計算コストの転嫁（ほぼ全件）、データ主権（約七割）、能力の欠落（約三割）、資産の復活（約二割）。**当たる数が多いほど Wasm の投資対効果は高い。一つも当たらないなら Wasm を使うな。**

**四、どの事例も同じいくつかの壁にぶつかる。** 4 GB の線形メモリの上限（事例 22 の辞書、52 の zk-EVM、53 の 24 量子ビット、74 のホログラフィックの再構成、81 のメッシュの解像度）、モジュールのサイズ（事例 7 の 30〜50 MB、13 の 10〜15 MB、28 の 10〜15 MB）、`SharedArrayBuffer` とクロスオリジン隔離（事例 1、32、62、68、75、81 などすべてのマルチスレッドの事例）。**これらの壁は第 3、5、8 章で完全に解体してある——実装の欠陥ではなく、仕様からの直接の帰結である。**

**五、そして最も重要なこと：この 101 件のうち相当数は示唆的である。** これはその価値を損なわず、むしろこの図鑑の本当の使い方を示している——**それは「この道は通っているか」という実現可能性の地図であり、「git clone できる」一覧ではない。** 🔴 の項目が記述する技術経路はほぼすべて成立する。ただまだ誰もやっていないか、やっているがその名ではないだけだ（事例 66 に対する DuckDB-Wasm、事例 70 に対する OpenCV.js が最良の例である）。

> **この図鑑から一文だけ持ち帰るなら、この一文を**：
> **Wasm は「領域全体の参入障壁をゼロまで打ち下げる」ことを個人にもできることに変えた——必要なのは資源ではなく、どの道がすでに通っているかを知ることである。**

**最後に道標を一つ**：この図鑑は「この道は通っているか」の地図であり、**付録 L は道の果てにある、本当に人が住んでいる場所である**——FluffOS が LPMud のドライバまるごとをブラウザへコンパイルし、`fluffos/mudlibs` が一九九〇年代の中国語圏の MUD のソース二百件を修復して静的なバンドルへ固めた。それは本巻の事例 58（Minestom-Wasm）と事例 60（Micro-Apache-Wasm）という二つの 🔴 の構想の本物の版であり、同時に本書の中心命題の最も清潔な生きた標本でもある。**事例を一つだけ底まで解体したものを見たいなら、あの一篇を読んでほしい。**
