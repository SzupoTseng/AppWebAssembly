# 第4章：競合の全景——JavaScript、Docker、V8 Isolates、EVM、WebGPU、そしてネイティブ

> 「Wasm の競争相手は誰か」——この問いに単一の答えはない。**Wasm は六つのまったく異なる戦場で、六つのまったく異なる相手と向き合っている**からだ。ブラウザでは JavaScript と分業し、クラウドネイティブでは隔離境界をコンテナと奪い合い、エッジではコールドスタートを V8 Isolates と競い、ブロックチェーンでは仮想機械の主導権を EVM と争い、密な計算では **WebGPU** と分業する。そしてそのすべての外側に、最も根本的な相手がいる——**そもそもウェブでやらない**。**勝ち方が違えば、負け方も違う。**

## シナリオ 1　ブラウザ戦場：Wasm vs. 純粋な JavaScript

**背景**：これは最も誤解される対比である。そもそも対立関係ではないからだ。

**分業の物理的な基礎**：

| 観点 | JavaScript | WebAssembly |
|---|---|---|
| 型 | 動的。実行時に推論 | 静的。ロード時に検証 |
| メモリ | ガベージコレクトされるオブジェクトヒープ | 手動管理の線形メモリ |
| 起動 | 解析 → 解釈 → JIT ウォームアップ（性能は実行回数とともに登る） | 解析 → 直接コンパイル（性能は最初の呼び出しから安定） |
| 性能の予測可能性 | 悪い（脱最適化、GC 停止、隠しクラスの遷移がスパイクを生む） | **良い**（GC 停止なし、脱最適化なし。リアルタイム用途に向く） |
| DOM / ブラウザ API | ネイティブでゼロコスト | JS の橋渡しが必須 |
| 文字列とオブジェクト | 非常に強い | 非常に弱い（手動で符号化・復号が要る） |
| 向いている仕事 | UI 対話、イベント処理、業務ロジック、データの組み立て | 3D レンダリング、音声・映像の符号復号、暗号処理、大きな行列演算、パーサ |

**「性能の予測可能性」は「平均性能」より価値がある**：この点はゲーム、音声、リアルタイム対話の場面で決定的である。JavaScript の平均性能は実のところ非常に良いが、**ときおり** GC 停止や脱最適化で 30 ミリ秒詰まる——毎フレーム 16.6 ミリ秒を求めるゲームループにとって、それは目に見える一回のコマ落ちである。Wasm の性能曲線は平らだ。**AudioWorklet の中で Wasm を走らせるのがほぼ業界の慣例になったのは、音声スレッドが予測不能な停止を一度も許容できないからである。**

**「純粋な JS のほうが速い」のはどんなときか**：

- ワークロードが境界越えのオーバーヘッドより小さいとき（毎回ピクセル一つだけ計算する、文字列一つだけ比較する、など）。
- 大量の文字列処理——V8 の文字列実装（rope、インターン化、slice の共有）は極度に最適化されており、Wasm は符号化の税を払う。
- 大量の DOM 操作——毎回 JS を経由するので、Wasm は純損である。
- コールドスタートに極度に敏感で、計算量が大きくない場面——あの 500 KB のモジュールのダウンロードとコンパイルは永遠に取り返せない。

> ⚠️ 真偽の注意
> 「Wasm は JavaScript より 10〜30 倍速い」という主張をよく見る。この種の倍率は**特定の形のベンチマークでのみ成立する**（GC 圧のない密な数値ループで、対照群が最適化されていない JS 実装）。V8 が十分ウォームアップし、コードが型の安定した単相のホットループであるとき、**JavaScript は Wasm の性能に迫り、差はしばしば 1〜2 倍以内に収まる**。付録 D–F の百一の事例に現れる「N 倍速い」という数字はすべてこの基準で読むべきである：**方向は信じ、倍率は疑え。**

> 💡 座右の一言
> **工学において、「平均がより良い」はしばしば「最悪ケースがより良い」に負ける。** JavaScript の平均性能は Wasm にさほど劣らないが、その P99 は GC に貫かれる。Wasm の平均性能は圧倒的とは限らないが、その P99 は平らだ。ユーザが感じるのは平均値ではない——**彼らが感じるのは、あの一回の引っかかり、あの一回のポップノイズ、あの一回のコマ落ちである。** この原理はシステム設計で「テールレイテンシ（tail latency）」と呼ばれ、一見不合理に見える技術選択の山を説明する。取引システムがなぜ GC のない言語を選ぶのか、データベースがなぜスループットを犠牲にして P99 を買うのか、リアルタイム音声がなぜ十分速い JS ではなく Wasm を選ぶのか。**選定のときは、まずこのシステムが平均値で評価されるのか、最悪ケースで評価されるのかをはっきりさせること——この二つが求める技術はまったく違う。**

## シナリオ 2　クラウドネイティブ戦場：Wasm + WASI vs. Docker / コンテナ

**背景**：この対比は「Wasm が Docker を置き換える」と最も誇張されやすいが、真相はもっと面白い——**両者が隔離しているのは、そもそも同じ層のものではない。**

**隔離境界の層の違い**（あらゆる差異を理解する鍵である）：

```
コンテナ（OCI / Docker）：
  ┌───────────────────────────────────────────┐
  │ あなたのプログラム + 完全なユーザ空間         │  ← 隔離するのは「OS ディストリビューション一式」
  │ (glibc, coreutils, /etc, パッケージ管理…)   │
  ├───────────────────────────────────────────┤
  │ namespace + cgroup + seccomp + capabilities │  ← Linux カーネルが隔離を提供
  ├───────────────────────────────────────────┤
  │           共有されたホストカーネル           │  ← 攻撃面：syscall インタフェース全体
  └───────────────────────────────────────────┘

Wasm + WASI：
  ┌───────────────────────────────────────────┐
  │ あなたのプログラム（Wasm へコンパイル済み）   │  ← 隔離するのは「単一のアプリケーション」
  ├───────────────────────────────────────────┤
  │ Wasm 実行環境（メモリ安全な仮想機械）         │  ← 型システムと検証器が隔離を提供
  ├───────────────────────────────────────────┤
  │ WASI 能力インタフェース（ホストが明示的に与えた数点）│  ← 攻撃面：あなたが import した数個の関数
  └───────────────────────────────────────────┘
```

**項目ごとの対照**：

| 観点 | コンテナ | Wasm + WASI | どちらが勝つか |
|---|---|---|---|
| コールドスタート | 数十ミリ秒〜数秒 | マイクロ秒〜数ミリ秒 | **Wasm、しかも桁違い** |
| イメージ／モジュールのサイズ | 数十〜数百 MB | 数十 KB〜数 MB | **Wasm** |
| メモリフットプリント | インスタンスあたり数十 MB から | インスタンスあたり数百 KB〜数 MB | **Wasm** |
| CPU アーキテクチャ横断 | アーキテクチャごとに一版 | 単一の `.wasm` で通す | **Wasm** |
| 攻撃面 | syscall インタフェース全体 | 明示的に import した数個の関数 | **Wasm**（ただし実行環境自体にも穴はありうる） |
| 既存ソフトを動かせるか | **任意の Linux バイナリ** | 再コンパイルしたものだけ | **コンテナ。しかも決定的に** |
| エコシステムの成熟度 | 十年以上。ツールチェーン完備 | いまも進化中（WASI 0.2 へ移行中） | **コンテナ** |
| マルチスレッド／ネットワーク | 完全 | 順次補完中 | **コンテナ** |
| 可観測性 | 完全（strace、perf、eBPF…） | 相対的に乏しい | **コンテナ** |

**「100 倍速い」という一文をどう読むか**：それが**コールドスタート**を指すなら、この桁は信じられる（マイクロ秒 vs. 数十ミリ秒）。**実行性能**を指すならそれは誤りである——**Wasm の実行性能はコンテナ内のネイティブコードより低い**。コンテナの中で走るのは本物のネイティブバイナリであり、Wasm はコンパイル済みの中間表現だからだ。

> ⚠️ 真偽の注意
> 「Wasm は Docker より 100 倍速く、しかも極めて軽い」といった言い方はマーケティング資料でよく見る。**正確に言えば：Wasm のコールドスタートとメモリフットプリントはコンテナより一〜数桁良いが、定常状態の実行性能はたいていコンテナ内のネイティブコードに劣る。** この差が適用範囲を決める：**Wasm は「大量・短命・突発」の関数（サーバレス、エッジ、マルチテナントのプラグイン）で勝ち、コンテナは「長時間稼働し、既存エコシステムに依存する」サービスで勝つ。** 両者を二者択一の代替関係とみなすのは、この技術に対する最もよくある誤用である。

**Wasm がバックエンドで本当にキラーとなる場面**は、コンテナに**できない**ことである。

1. **マルチテナントのプラグインシステム**：顧客が自分のコードをあなたのサービス内で走らせられるようにする。コンテナなら顧客ごとに一つ立ち上げる（重く、遅く、高い）。Wasm なら同一プロセス内で互いに信頼しない数千のモジュールを走らせられ、それぞれが独立した線形メモリと能力境界を持つ。Envoy、Istio、Shopify Functions、Redpanda のデータ変換はこの道を行っている。
2. **エッジコンピューティングの極端なコールドスタート要求**：エッジノードにはローカルなトラフィックがなく、ほぼ毎リクエストがコールドスタートである。コンテナの数十ミリ秒はここでは受け入れられない。
3. **一度コンパイルしてどこへでも配備**：同じ `.wasm` が x86 サーバ、ARM のエッジ機器、そしてブラウザで動く。

> 🔍 踏み込んだ論評──「既存バイナリを動かせない」の一条こそ、勝負を決める
> 表では Wasm が七項勝ち、四項負けている。優位に見える。しかしその四項のうち一つの重みが、他のすべてを圧倒する：**Wasm は再コンパイルしたものしか動かせない。** この一文の実際の意味はこうだ——**あなたの会社が過去十年に積み上げた Python スクリプト、Java サービス、Node.js アプリ、そして誰も触れたがらない先祖伝来の PHP は、誰かが書き直すか少なくとも再コンパイルしない限り、一つも移せない。** コンテナの歴史的勝利は、技術が優雅だったから（cgroup + namespace を優雅とは言えない）ではなく、**書き直しゼロの移行経路**を提供したからである：`FROM ubuntu:22.04`、あなたの散らかった現状をそのまま詰め込めば、明日には Kubernetes に載る。だからこそ「Wasm が Docker を置き換える」という物語は 2019 年から 2026 年まで叫ばれ続け、シェアはいまも懸絶している。**技術の採用曲線は移行コストが決めるのであって、技術的優越性が決めるのではない。** そしてこれは Wasm のバックエンドにおける本当の成長経路も予告している。既存サービスからシェアを奪うのではなく、**コンテナが生まれつき不向きな新しい場面**（マルチテナントのプラグイン、極限のコールドスタート、アーキテクチャ横断のエッジ）に自分の地盤を育て、そこから中央へ広げていくのだ。**インフラ技術の未来を見るときは、それが現職に勝てるかではなく、現職が構造上入れない場所があるかを見よ。**

## シナリオ 3　エッジ戦場：Wasm vs. V8 Isolates

**背景**：六つの競争のうち最も肉薄しているのがこれである。相手が同じエンジンを使っているからだ。

**V8 Isolate とは何か**：Cloudflare Workers の中核となる発想——テナントごとにプロセスやコンテナを立てるのではなく、**同一の V8 プロセス内**に `Isolate`（V8 の隔離実行環境。それぞれ独立したヒープとグローバルオブジェクトを持つ）を一つずつ開く。コールドスタートは 5 ミリ秒以下まで落とせ、メモリフットプリントは数 MB にすぎない。

**両者の対比**：

| 観点 | V8 Isolates | Wasm モジュール |
|---|---|---|
| コールドスタート | 極めて速い（〜5 ms 以下） | 極めて速い（マイクロ秒〜ミリ秒級） |
| 対応言語 | **JS / TypeScript のみ** | Wasm へコンパイルできる数十の言語 |
| メモリフットプリント | 低め（V8 の組み込みオブジェクトとコードを共有） | インスタンスごとに自分の線形メモリが要る |
| 隔離の強度 | V8 自身の安全性に依存（歴史的に V8 には多数の CVE がある） | 仕様レベルの型とメモリの隔離が一層追加される |
| エコシステム | npm。極めて巨大 | 各言語それぞれのエコシステム。言語横断の統合は発展途上 |

**現実には両者はすでに合流している**：Cloudflare Workers は Isolate の中で Wasm モジュールを実行することも**同時にサポートしている**。Fastly の Compute@Edge は Wasm（Lucet/Wasmtime 系）を直接中核に据えている。**だから正しい問いは「どちらを選ぶか」ではなく、「あなたのロジックを何の言語で書くか」である**——JS/TS なら Isolate、Rust/Go/C++ なら Wasm へコンパイルして中に入れる。

> 💡 座右の一言
> **二つの技術が長く並存し、しかも互いに入れ子になっているなら、それらが解いている問題は同じではない——市場が最初に同じ棚へ並べただけである。** Isolate が解くのは「同一の JS エンジン内でいかに安全にマルチテナントを実現するか」であり、Wasm が解くのは「JS でない言語をいかに安全にどこでも走らせるか」である。競合して見えるのは、「エッジのサーバレス」という具体的な製品形態でたまたまぶつかったからにすぎない。**二つの技術が比較されているのを見たら、まずそれぞれが最も得意で、相手には到底できないことを探すこと——それこそが本当の定義である。** 定義の異なる二つを同じ指標で比較することは、技術評価で最もよくある論理の誤りである。

## シナリオ 4　ブロックチェーン戦場：eWasm vs. EVM

**背景**：六つのうち最も「政治的」なのがこれである。技術だけでなく、すでにチェーン上にロックされた数千億ドルの資産が絡むからだ。

**EVM（Ethereum Virtual Machine）の問題**：

- **256 ビットのワード長**。EVM のネイティブなワード長は 256 ビットである。暗号ハッシュのために設計されたからだ。しかしこれは、**加算のたびに 64 ビットの物理 CPU 上で複数回の演算へ模倣される**ことを意味し、暗号以外の一般的な計算には巨大な浪費である。
- **ツールチェーンが閉じている**。基本的に Solidity か Vyper しか使えず、コンパイラもデバッガも解析器もゼロから作らねばならない。
- **実行性能が低い**。速度ではなく「検証可能な決定性」のために設計されているからだ。

**スマートコントラクト仮想機械としての Wasm の優位**：

- **成熟した多言語ツールチェーン**：Rust、C++、AssemblyScript でコントラクトを書け、既存のコンパイラ最適化、デバッガ、ファジングツールをそのまま再利用できる。
- **実行効率が一〜数桁高い**（暗号以外の計算について）。
- **仕様が四大ブラウザの実装で検証済み**であり、仮想機械の仕様を自分で維持しなくてよい。

**チェーン上での Wasm の致命的な難題**（マーケティング資料がたいてい語らない部分である）：

1. **決定性（determinism）**。ブロックチェーンはすべてのノードが同一のトランザクションに対して**完全に同一の**結果を出すことを要求する。ところが Wasm 仕様にはいくつか**非決定的**な隅がある。浮動小数点の NaN のビットパターンは実装によって異なりうるし、SIMD の一部の操作もそうであり、`memory.grow` の失敗の時機はホストのリソースに依存する。**チェーン上の Wasm はまず「決定的な部分集合」を定義しなければならず**（通常は浮動小数点を丸ごと禁止する）、これがあらゆる Wasm チェーンの最初の工程になる。
2. **計量（metering / gas）**。EVM は命令ごとに gas コストが明示されている。Wasm にはこの概念がなく、**命令へのインストルメンテーション**——コンパイル後のモジュールへ計数コードを自動挿入する——で実現するほかない。これは 10〜50% の性能低下をもたらし、速度優位の一部を直接食う。
3. **エコシステムの慣性**。Ethereum メインネット上にロックされた資産、配備されたコントラクト、監査済みのライブラリ——すべて EVM バイトコードである。**移行の調整コストは天文学的である。**

**現実の趨勢**：eWasm は Ethereum 1.x の実行層の代替案としては実質的に棚上げされた（Ethereum のロードマップは EOF などの方向へ転じた）。しかし Wasm は**他のチェーン**で大成功している——Polkadot の runtime 自体が Wasm であり（ホットアップグレード可能）、NEAR、Cosmos の CosmWasm、Internet Computer はいずれも Wasm を実行環境としている。

> 🔍 踏み込んだ論評──「計量」という一件は、汎用仮想機械を特化用途に使うことの根本的な緊張を露呈する
> gas 計量の実装の難しさは工学的な些事ではない。それはパラダイムの衝突の徴候であり、単独で解体する価値がある。**EVM は初日から「命令ごとにいくら課金するか」を仕様に書き込んだ**。信頼できない環境で信頼できないコードを実行し、止めて課金できることが存在目的だったからだ。**Wasm は初日から計量を仕様の外へ置いた**。「検証済みで安全なコードをできるだけ速く実行する」ことが存在目的であり、あらゆる計量は純粋なオーバーヘッドだからだ。そこで Wasm をコントラクト仮想機械に使う者は、コンパイル後のモジュールへインストルメンテーションを施さねばならない——これには三つの連鎖的な帰結がある。**第一**、インストルメント後のモジュールは元のモジュールと別物であり、あなたの最適化器がインストルメント命令を最適化して消してしまいうる。計量と最適化が互いに殴り合うのだ。**第二**、インストルメンテーションの粒度が計量の精度とオーバーヘッドのトレードオフを決める（命令ごとに数えれば高すぎ、基本ブロックごとに一度なら無限ループに突かれうる）。**第三**、チェーンごとにインストルメンテーション戦略が異なるため、「同じ Wasm がチェーンによって gas 消費が違う」ことになり、可搬性の約束が割引かれる。**この事例の一般的な教訓はこうだ：「速度」のために設計された汎用の基盤を、「計量可能・中断可能・監査可能」を要する問題へ持ち込むと、あなたが足すその一層が、そもそもそれを選んだ理由を食い尽くしてしまうことが多い。** 選定のときに問うべきは「この基盤は十分速いか」ではなく——**私が足そうとしているものは、これを凡庸な選択肢へ引き戻さないか**、である。

## シナリオ 5　密な計算の戦場：Wasm vs. WebGPU

**背景**：六つの相手のうち最も新しく、最も誤判されやすいのがこれである——2026 年になってようやく「誰もが使える」選択肢になったからだ。

**WebGPU の状況は変わった**：**2026 年 1 月に主要ブラウザ全面出荷を達成した**（Chrome は 113 から、Firefox は 141 から Windows で、145 で Apple Silicon の macOS へ拡大、Safari 26.0 が macOS/iOS/iPadOS/visionOS を網羅）。**これは「ブラウザ内の密な計算」に、初めて真剣に検討できる選択肢が一つではなく二つできたことを意味する。**

**両者の本質的な違いは速い遅いではなく、並列の粒の形にある**：

| | **Wasm（+SIMD +threads）** | **WebGPU（compute shader）** |
|---|---|---|
| ハードウェア | CPU | **GPU** |
| 並列モデル | 少数の粗粒度スレッド（≒ コア数） | **数千の細粒度スレッド**（SIMT） |
| ベクトル幅 | **固定 128 ビット** | ハードウェア依存。はるかに広い |
| 分岐の発散 | 安い | **高い**（同一 warp が別の分岐へ進む = 直列化） |
| ランダムなメモリアクセス | 安い（大きなキャッシュがある） | **高い**（coalesced アクセスでなければ速くない） |
| 再帰／複雑な制御フロー | 自然 | **WGSL は再帰を非対応**。動的制御フローに制限がある |
| 精度 | `f32`/`f64` 完全 | `f32` が主。`f64` の対応は限定的かなし |
| 起動レイテンシ | ミリ秒級 | **adapter/device の取得、シェーダのコンパイル、パイプライン構築が要る** |
| データの読み戻し | ゼロコピー（同じメモリ） | **`mapAsync` での読み戻しが必須で、無視できないレイテンシがある** |
| 利用可能性 | **ほぼ 100%** | 〜70%（しかもモバイルとドライバの差が大きい） |
| デバッグ | 難しい | **さらに難しい** |

**したがって分業の判断基準は明快である**：

```
あなたの計算は「同じ演算を数百万の独立した要素へ適用する」ものか？
├─ そうであり、しかもデータを GPU 上に留めて数段連続で処理できる
│    → WebGPU（行列積、畳み込み、画像フィルタ、パーティクル、レイトレーシング）
│
├─ そうだが、計算後すぐに結果を CPU へ持ち帰って別のことをする
│    → ⚠️ まず読み戻しのレイテンシを測ること——GPU が節約した時間を食うことが多い
│
└─ いいえ：複雑な分岐、再帰、ランダムアクセス、あるいは f64 精度が要る
     → Wasm（パーサ、圧縮、データベース、エミュレータ、幾何ソルバ）
```

**現実世界の答えはたいてい「両方要る」である**——付録 D の事例 4（ONNX Runtime Web）が最良の例だ：**WebGPU バックエンドと Wasm バックエンドを同時に維持している**。前者は速く、後者は「どんな端末でも動く」。**ここでの Wasm の役割は競争者ではなく、最後の砦（fallback）である。**

> ⚠️ 真偽の注意
> 「WebGPU は Wasm より 10〜100 倍速い」という主張をよく見る。**適したワークロードではこの桁は信じられる**（大きな行列積、畳み込み）。**しかし三つの勘定が省かれている**：**（一）** 起動コスト——device の取得、WGSL のコンパイル、パイプラインの構築は、短いタスクでは大半を占めうる。**（二）** 読み戻しコスト——`mapAsync` で結果を CPU へ戻すレイテンシ。**（三）** 利用可能性のコスト——WebGPU のない端末のために Wasm の経路を用意せねばならず、結果として実装を二つ維持することになる。**「N 倍速い」が語るのは定常状態のスループットであり、ユーザが体験するのは端から端までの時間である。**

> 💡 座右の一言
> **二つの技術が同じ比較表に並べられたら、まず並列の「粒」が同じ種類かを確かめること。** CPU の並列は「数人の賢い職人がそれぞれ別のことをする」であり、GPU の並列は「数千人が同時にまったく同じ動作をする」である——**前者は判断が得意で、後者は反復が得意である。** 判断を要する仕事を GPU へ投げれば分岐の発散を得る。純粋な反復を CPU に留めれば数千倍の計算力を捨てる。この原理は Wasm と WebGPU に留まらない。スレッドプール vs. SIMD、バッチ処理 vs. ストリーミング、マイクロサービス vs. モノリス——**どの対比でも本当の違いは「仕事の切り分け方」にあり、「どちらが速いか」にはない。** 選び間違えた代価は少し遅いことではなく、仕事の形と道具の形が噛み合わず、どう最適化しても外れることである。

## シナリオ 6　最も根本的な相手：そもそもウェブでやらない

**背景**：この節は、本書全体が答えを前提にしながら一度も口に出さなかった問いを投げる——**これは本当にブラウザの中でやるべきなのか？**

**ブラウザを使わなければ、これまでの十数の壁の半分がそのまま消えるからだ**：4 GiB 上限なし、COOP/COEP なし、境界の料金所なし、ダウンロードサイズの不安なし、スレッドを立てられ、ファイルシステムとハードウェアに直接触れ、性能は 60〜90% ではなく 100% である。

**「ウェブでやらない」の三つの具体的な形**：

| 形 | 何か | Wasm に対する取捨 |
|---|---|---|
| **ネイティブバイナリを直接配る** | ふつうのデスクトッププログラム | 最も速く、制約なし。**しかしインストール不要という利点が完全に消える**。プラットフォームごとに一版出し、署名し、更新を扱わねばならない |
| **Electron** | Chromium + Node.js を丸ごと同梱 | 完全な Node の能力とファイルシステムが手に入る。**代価はアプリ一つあたり百数十 MB と無視できないメモリフットプリント** |
| **Tauri** | **システム内蔵の WebView** でフロントを表示し、バックエンドはネイティブ Rust | 成果物はわずか数 MB。フロントは依然として Web 技術だが、**重い計算はネイティブ Rust が走らせる——Wasm へコンパイルする必要がないので、4 GiB 上限も境界の税もなく、スレッドも立てられる** |

**Tauri のこの行は立ち止まって見る価値がある**。それが一つのことを露わにするからだ：**多くの人が Wasm を使うのは、実は「Web 技術で UI を書く」ためであって、「ブラウザの中で走らせる」ためではない。** ユーザがどのみちアプリをインストールするのなら、重い計算を Wasm へコンパイルするのは**純損**である——Wasm の代価をすべて払いながら、その唯一の利点（インストール不要、更新不要、クロスプラットフォームの単一成果物）を手に入れていない。

**したがって判断基準は一つだけである**：

> **「インストール不要」はこの製品にとっていくらの価値があるか、と問え。**
>
> - **とても価値がある**（使い捨てのツール、リンクを共有すれば使える、企業がソフトのインストールを禁じている、検索エンジンに索引されたい、他人のサイトの中で動かしたい）→ **ブラウザ + Wasm。これまでのすべての壁は必要悪である。**
> - **さほど価値がない**（ユーザはどのみちインストールする、長時間使う、ローカルの大量のファイルを触る、バックグラウンド実行が要る）→ **Tauri かネイティブ。本書第二部の四章分の面倒がまるごと省ける。**

**よくある二つの誤判**：

1. **「どうせ Rust を書くのだから、Wasm へコンパイルして両方いっぺんに済ませよう。」** 美しく聞こえるが、実際には Wasm 版は 4 GiB、境界の税、スレッドの欠如に足を引かれ、ネイティブ版は一つも引かれない。**中核ロジックを共有するのは正しいが、両側の能力境界が違うことは受け入れねばならない。**
2. **「Electron は太りすぎだから Wasm を使う。」** この二つは対応していない——Electron の代替は Tauri であって Wasm ではない。**比べているのが「アプリのサイズ」なら、答えは Tauri である。**

> 🔍 踏み込んだ論評──六つの相手を並べると、明快な一本の位置づけの線が浮かぶ
> この章の六つの競争を並べると、Wasm の位置は実に明確であり、しかも多くの人の直感とは違う。**Wasm は「より速い実行方式」ではない。「他人の地面の上で、あなたのコードを安全に実行する」ことの汎用解である。** どの競争の勝敗もこれを裏づけている。**JavaScript に対して**は「既存の C++ 資産を連れて入れる」ことで勝っており、速さで勝っているのではない。**コンテナに対して**は「一つのプロセスで互いに信頼しない数千のテナントを走らせる」ことで勝っており、性能で勝っているのではない。**V8 Isolates に対して**は「JS に限られない」ことで勝つ。**EVM に対して**は「ツールチェーンが出来合いである」ことで勝つ。**WebGPU に対して**はそもそも競争しておらず、「どんな端末でも動く」最後の砦である。**ネイティブに対して**は「インストール不要」で勝ち、それ以外のすべてで負ける。
> **六つを繋げば、Wasm の定義が浮かび上がる：それは「可搬な信頼境界」である。** その優位はすべて「ホストが安心して実行できる」ことから来ており、その制約もすべて同じ理由から来ている。だから選定のときに本当に問うべきは「Wasm は速いか」ではなく——**このコードは誰の地面の上で走るのか。その地主は何を根拠に私を信じるのか**、である。答えが「自分のマシンの上で走る」なら、Wasm はたぶん要らない。答えが「数百万の見知らぬ人のブラウザで走る」「同じプロセス内の他のテナントの隣で走る」「すべてのノードが同じ結果を出さねばならないチェーンの上で走る」なら——**第二の選択肢はない。**

## 本章のまとめ

- **六つの戦場、六つの勝ち方**：ブラウザでは JS と**分業**（Wasm が計算し、JS が描く）。クラウドネイティブではコンテナと**ずれた競争**（コールドスタートとマルチテナントで勝ち、既存エコシステムで負ける）。エッジでは V8 Isolates と**すでに合流**（Isolate が JS を、Wasm が他の言語を走らせる）。ブロックチェーンでは**性能で勝ち、決定性とエコシステムの慣性で詰まる**。密な計算では **WebGPU と競争ではなく分業**。そして**ネイティブ**に対しては、勝てるのは一つだけ——**インストール不要**である。
- JS に対して：**「性能の予測可能性」は「平均性能」より価値がある**——Wasm の曲線は平らであり、これは音声とゲームループにおいて決定的である。しかし小さなワークロード、文字列が密な場面、DOM が密な場面では、**純粋な JS のほうが速い**。
- コンテナに対して：**Wasm のコールドスタートとフットプリントは一〜数桁勝つが、定常状態の実行性能はコンテナ内のネイティブコードに劣る**。そして「既存バイナリを動かせない」の一条の重みが他のすべての優位を圧倒する——**技術の採用曲線は移行コストが決めるのであって、技術的優越性が決めるのではない**（シナリオ 2 の 🔍 参照）。
- EVM に対して：Wasm の速度とツールチェーンの優位は本物だが、**gas 計量はインストルメンテーションで補うほかなく、それが速度優位の一部を食う**——これは「汎用の基盤を特化用途に使う」ことの根本的な緊張である（シナリオ 4 の 🔍 参照）。
- WebGPU に対して：**並列の「粒」が違う**——CPU は「数人の賢い職人がそれぞれ別のことをする」、GPU は「数千人がまったく同じ動作をする」。**ブラウザ AI 推論における Wasm の役割は競争者ではなく最後の砦である**（ONNX Runtime Web が二つのバックエンドを同時に維持していることが証拠だ）。「10〜100 倍速い」が起動・読み戻し・利用可能性の三つの勘定を省いている点に注意（シナリオ 5 の ⚠️ 参照）。
- ネイティブに対して：**判断基準は一つだけ——「インストール不要」はこの製品にとっていくらの価値があるか。** さほどでないなら、Tauri かネイティブが第二部の四章分の面倒を省いてくれる。**Electron の代替は Tauri であって Wasm ではない点に注意。**
- 「N 倍速い」というあらゆる主張は、**対照群の形**に照らして読むべきである。本書付録の百一の事例も含めて（シナリオ 1 の ⚠️ 参照）。
- **六つを繋げば、Wasm の定義が浮かび上がる：それは「可搬な信頼境界」である。** あらゆる優位が「ホストが安心して実行できる」ことから来ており、あらゆる制約も同じ理由から来ている。選定で問うべきは「Wasm は速いか」ではなく——**このコードは誰の地面の上で走るのか。その地主は何を根拠に私を信じるのか**、である（シナリオ 6 の 🔍 参照）。

第一部はここで終わる——機械の来歴、物理法則、能力の境界、そして相手をすべて棚卸しした。**次の部では、紙の上では不可能に見えることをやる：この機械を、HTTP ヘッダを設定させず、ポートを開かせず、バックエンドのコードを一行も動かせない場所へ移すのだ。** 第 5 章へ。
