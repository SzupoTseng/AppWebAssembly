# 付録K　論争と、真偽の較正のための問答

> 本書は、確かめられる仕様上の事実と、確かめられていない共同体の言い分の両方をまたいでいる。この付録は全篇の「⚠️ 真偽の注意」を一箇所に集め、加えて、よくあるが本文には現れなかった論争をいくつか補っている。
> **形式**：問い → 流布している言い分 → 較正した答え → 本書のどの章に出典があるか。

## 1. 歴史と位置づけについて

### Q1. WebAssembly は JavaScript を置き換えるためのものか？

**流布している言い分**：「W3C が定めた第四の言語であり、JavaScript を置き換えるだろう。」

**較正**：**違う。** 仕様文書は Wasm を JS の代替物として位置づけたことは一度もなく、はっきりと**補完（complement）**として位置づけている。技術的にも、Wasm は今なお単独で DOM を操作できず、自分で自分を読み込むこともできない——**その起動のたびに、JavaScript（あるいはホスト環境）が最初の鍵を手渡さねばならない。** 正しい分業は「Wasm が計算し、JS が描く」である。

「2019 年に W3C が勧告標準と定め、HTML/CSS/JS と並ぶ第四の中核言語となった」という事実そのものは**本当である**。盛られているのは「置き換える」の三文字だ。 → 第 1 章、第 4 章

### Q2.「もし 2008 年に WASI があったなら、Docker を発明する必要はなかった」——では、コンテナは死ぬのか？

**較正**：この言葉は**確かに存在する**（Docker の創業者 Solomon Hykes、2019）が、しばしば文脈を切り取られている。もとの投稿の次の一文は「Wasm はサーバ計算の未来である」であって、コンテナの陳腐化を宣言したものではない。本人も後に、これは「軽量・可搬・クロスプラットフォーム」という性質の組への賛辞だと明かしている。

**現実**：両者は**補い合う**。コンテナはオペレーティングシステムのユーザ空間まるごとを隔離し、**既存のいかなるバイナリも走らせられる**。Wasm は単一のアプリケーションだけを隔離し、その代わりにコールドスタートと体積で桁の優位を得るが、**再コンパイルしたものしか走らせられない**。実務で最もよく見る配備の形は、**コンテナ化された実行環境の中で Wasm モジュールが走る**という姿である。 → 第 1 章、第 4 章

### Q3. NaCl は技術が駄目だったから失敗したのか？

**較正**：**違う。** NaCl は技術的には成功していた（x86 の機械語を静的に検証し、セグメントでサンドボックス化する方式は、確かに安全で速かった）。それが敗れたのは**政治**においてである。Chrome だけが支え、それは「ウェブページの中に寄生する native のプログラム」であってページの一部ではなく、しかも他のベンダに「CPU アーキテクチャごとに機械語の検証器を一式ずつ書く」ことを求めた（セキュリティ工学として極めて高くつく約束だ）。 → 第 1 章

## 2. 性能について

### Q4.「Wasm は native の 60〜80% の性能」という言葉は正しいか？

**較正**：**この言葉にはほとんど情報がない。** ワークロードの形に強く依存するからだ：

| ワークロード | native 比 | 理由 |
|---|---|---|
| 純粋な数値密集のループで、データがキャッシュに収まる | **90% 以上** | TurboFan の出す符号は Clang -O2 に近い |
| 手書きの AVX2 で最適化されたコードの移植 | **40〜50%** | **Wasm SIMD は 128 ビットしかなく、ベクトル幅がそのまま半分になる** |
| 細かい境界越えの呼び出しが大量にある | **純粋な JS より遅くなりうる** | 境界越えの固定費が大半を占める |
| 文字列とオブジェクトの操作が大量にある | 純粋な JS が圧倒する | Wasm は符号化・復号の税を払う |
| メモリ律速（キャッシュミスが支配的） | ほぼ 100% | どちらも DRAM を待っている |

**どんな性能の主張を読むときも、最初の問いはつねに：このベンチマークの形は、私が走らせたいものと似ているか？** → 第 2 章

### Q5.「Wasm は JavaScript より 10〜30 倍速い」？

**較正**：特定のベンチマークでのみ成り立つ（GC 圧のない密集した数値ループで、対照が最適化されていない JS の場合）。**V8 が十分にウォームアップし、型の安定した monomorphic な熱いループでは、JavaScript は Wasm に迫り、その差はしばしば 1〜2 倍の内に収まる。**

だが Wasm が確実に勝つことが一つあり、それは平均性能より値打ちがある——**性能の予測可能性**である。JS は GC や脱最適化で時おり 30 ミリ秒詰まる。Wasm の曲線は平らだ。**これは音声（2.9 ミリ秒の硬い期限）とゲームループ（16.6 ミリ秒の予算）では決定的である。** → 第 4 章

### Q6.「Wasm は Docker より 100 倍速い」？

**較正**：**コールドスタートを指すなら信じられる**（マイクロ秒 対 数十ミリ秒〜数秒）。**定常状態の実行性能を指すなら誤りである**——コンテナの中で走るのは本物の native のバイナリであり、Wasm はコンパイルされた中間表現だ。**実行性能はコンテナ内の native のコードより低い。** → 第 4 章

### Q7. 付録 D〜F にある「N 倍速い」という数字は信じられるか？

**較正**：**方向を信じ、倍率を疑え。** これらはすべて元の対話が主張した値であり、本書は独立に検証していない。方向（Wasm が密集した計算で純粋な JS に勝つこと）は信じられる。具体的な倍数（15 倍、40 倍、55 倍）は、測定の結果ではなく桁の目安と見るべきである。 → 付録 D・E・F の冒頭の説明

## 3. セキュリティについて

### Q8.「Wasm はメモリ安全である」——では、私の C のプログラムはその中で安全なのか？

**較正**：**これは本書で最も重要な訂正である。**「Wasm はメモリ安全」は**サンドボックスの境界**という意味においてのみ成り立つ——それが保証するのは「Wasm モジュールがホストを害せない」ことであって、**あなたが C で書いたプログラムにその中でメモリエラーがないことを保証しはしない**。

しかも事情はもっと微妙だ。線形メモリはひと続きの平坦な `ArrayBuffer` であるため、**従来の native のプラットフォームにある緩和策（ASLR、NX、stack canary）は Wasm の中ではおおむね存在しない**。x86 なら ASLR に阻まれるはずのバッファオーバーフローが、Wasm では安定して悪用可能でありうる——ただし壊せる範囲は、そのモジュールの線形メモリの内側に限られる。学術の側にも明確な議論がある（"Everything Old is New Again: Binary Security of WebAssembly", USENIX Security 2020）。

**サンドボックスの安全 ≠ アプリケーションの安全。** 実務上の対策：`-fsanitize=address` / `-fsanitize=undefined` で試験用のビルドを作ること。 → 第 2 章、第 3 章

### Q9.「Wasm は不可逆なバイナリへの変換である」？

**較正**：**誤り。** Wasm のバイナリ形式は**完全に公開され、構造化されている**。WAT への逆アセンブルは無損で、機械的で、既製の道具がある（`wasm2wat`、`wasm-objdump -d`、`wasm-decompile`、Ghidra の Wasm ローダ）——これは x86 の機械語を逆解析するより**はるかに容易である**（x86 には可変長命令、データとコードの混在、間接ジャンプ表があるが、Wasm にはどれもない）。

正確な言い方はこうだ：**Wasm が隠すのは「ソースコードの意味の層」（型、命名、抽象）であって、「プログラムの振る舞いの層」ではない。難読化が押し上げるのはコストであって、可能性ではない。**

**もう一つ、しばしば見落とされる点**：Export セクションは**仕様で強制**されており、剥がすことはできない——攻撃者は、あなたがどの関数を輸出し、その署名が何かを必ず見ることができる。 → 第 9 章

### Q10. 暗号化／符号化／分割は、ハードコードされた鍵を守れるか？

**較正**：**すべて無効である。**

| 手口 | なぜ役に立たないか |
|---|---|
| Base64 で符号化する | `strings` には掛からないが、`base64 -d` が一秒で戻す。復号の関数もすぐ隣にある |
| いくつかに割って連結する | 連結のコードがバイナリの中にある。一度動かせば吐き出す |
| XOR で暗号化する | 鍵の鍵もバイナリの中にある（ホワイトボックス暗号の根本的な困難） |
| 「私の小さなプロジェクトを逆解析する者などいない」 | 自動の走査器が毎日、公開のホスティングを這い回っている。相手を選ばない |

**唯一の正解：鍵はクライアントへ決して入れない。** フロントは自分のバックエンドに、短命で範囲を限った token を求める。**Wasm は、もともと誤った設計を正しくはしない。** → 第 9 章

### Q11.「Wasm を使っているから定数時間（constant-time）であり、サイドチャネルを防げる」？

**較正**：**誤り。** Wasm の仕様そのものは定数時間を**保証しない**。それが保証するのは「JS エンジンのように、データの型に応じて内部表現を動的に切り替える振る舞い（V8 の Smi → HeapNumber）がないこと」であって、**コンパイラは依然として分岐を導入しうるし、CPU にはデータ依存のキャッシュの振る舞いがありうる**。

定数時間は**ソースコードの書き方**が保証するものであり（秘密鍵で分岐しない、秘密鍵で表を索かない）、Wasm は JS より制御しやすい実行の基盤を提供しているにすぎない。 → 付録 F 事例 73

### Q12. 静的ホスティング + Git の署名 = 高い安全性か？

**較正**：方向は正しいが、三つの但し書きがある：

1. **本当の境界はアカウントの安全である**——攻撃者があなたの GitHub アカウントや PAT を得れば、同じように commit を押せる。二要素認証とブランチ保護を有効にすること。
2. **サプライチェーンの危険は依然としてある**——ビルドの流れに毒を入れられたパッケージが混じれば、出てくる `.wasm` そのものが悪意あるものになる。しかもそれには同じように美しい commit の記録が付いている。
3. **「利用者が Wasm の一行一行を検証できる」は、実務ではほとんど誰もやらない**——**透明性が与えるのは「監査されうる」であって、「監査された」ではない。** この二つの隔たりこそ、大半のセキュリティ事故が起きる場所である。 → 第 9 章

### Q13. クライアント側でメモリのハッシュを検証すれば、破られるのを防げるか？

**較正**：**技術的に成り立たない。** クライアントのいかなる自己検証も、ローカルの改変で迂回されうる——これは「クライアントは信頼できない」というセキュリティの鉄則からの直接の帰結である。本当に効くのは**サーバ側の認可の判定**（この token はどのアカウントのものか、支払いはあるか、このファイルへの権限はあるか）であって、クライアントの身の潔白の自己証明ではない。 → 第 10 章

## 3b. 仕様の版について（本書の改訂時に追加）

### Q13b. Wasm 3.0 のあと、どのよくある言い分が古びたか？

**較正**：**2025 年 9 月、WebAssembly 3.0 の完成が宣言され、現行の標準となった。** 一度に九つの機能が核心の仕様へ収まった：**WasmGC、Memory64、例外処理、末尾呼び出し、128 ビット SIMD、複数メモリ、型付き関数参照、拡張された定数式、分岐ヒント**。

**そこで、次の言い分はどれも古びた**：

| 古びた言い分 | 現況 |
|---|---|
| 「Wasm GC はまだ提案／実験的だ」 | **すでに核心の仕様である**（Wasm 3.0） |
| 「memory64 の提案はまだ固まっていない」 | **すでに核心の仕様である**。ただし**性能の代価は依然として存在する**（ガードページの無料の境界検査を失う） |
| 「C++ の例外は JS のトランポリンに頼るしかない」 | **native の例外処理がある**：Tag セクション（id 13）+ `try_table` / `exnref` |
| 「関数型言語は Wasm の上では必ずスタックを溢れさせる」 | **`return_call` の末尾呼び出しがある** |
| 「一つのモジュールは線形メモリを一つしか持てない」 | **複数メモリが標準化された**——これは 4 GiB を回る第四の道であり、しかも**ガードページの無料の境界検査を保っている**（付録 M §8） |

**だが二つのことを分けねばならない**：**仕様の標準化 ≠ 今日あなたが使えること。** エンジンの対応はおおむね追いついたが、**ツールチェーンはしばしば遅れている**——多くの C/C++/Rust のツールチェーンは、既定でなお「メモリは一つだけ」を仮定している。**「仕様の状態」と「私は今日それを使えるか」は、分けて問わねばならない。** → 付録 A、付録 M

### Q13c. 同期の C のコードは、本当に Promise を待てるようになったのか？

**較正**：**待てる。それが JSPI（JavaScript Promise Integration）である。** これは **2025 年 4 月に Phase 4（標準化）へ入り**、**Chrome 137、Firefox 139** で出荷された。仕組みは、**エンジンが Wasm の実行スタックを丸ごと中断させ**、Promise が解決したら中断した場所から再開するというもので——Wasm の側から見れば、ただの同期の呼び出し一回に見える。

**だが三つの代価を知っておかねばならない**：**（一）** 中断と再開の費用はスタックの深さに関わるので、**熱いループには入れられない**。**（二）** **それが解くのは「待つこと」であって「並行」ではない**——あなたには依然としてスレッドが一本しかない。**（三）** **再入の問題**：中断のあいだに JS が同じインスタンスの輸出関数をもう一度呼びうる。ところが大半の C のコードは「同時に走っている呼び出しは一つだけ」を仮定しており、これが状態の破壊を招く。自分で再入のロックを足す必要がある。

**これが取って代わるのは Asyncify** である（Binaryen がモジュール全体をバイナリのレベルで書き換えて中断を模す手法。体積の膨張が著しく、巻き戻す関数を手で注釈せねばならなかった）。**移行の戦略：`typeof WebAssembly.Suspending === "function"` を検出し、あれば JSPI を、なければ Asyncify のビルドへ退く。** → 第 3 章の壁七、付録 M §5

### Q13d. GitHub Pages の上で永続化する SQLite を走らせるには、必ず COOP/COEP を扱わねばならないか？

**較正**：**必ずしもそうではない。そしてこれは、本書の改訂で最も実務的な価値のあった訂正である。**

公式の SQLite-Wasm は **二種類**の OPFS VFS を提供している：

- **`opfs`（第一世代）**：メインスレッドと OPFS のあいだを非同期のプロキシでつなぎ、`Atomics.wait` で非同期を同期に変える → **`SharedArrayBuffer` が要る。ゆえにクロスオリジン隔離が要る**。
- **`opfs-sahpool`**：あらかじめ開いておいた一組の sync access handle を直に持ち、Worker の中で同期に読み書きする → **COOP/COEP は要らず、しかも公式の文書で最も速い選択肢とされている**。代価は**同時に複数の接続を支えないこと**。主要なブラウザでは 2023 年 3 月ごろからおおむね使える。

**公式の推奨もまさにそうである**：並行性より性能を重んじる場合、あるいは COOP/COEP を設定できないクライアントは、`opfs-sahpool` を使うべきだ、と。

> **一般化した教訓**：あるプラットフォームの制約のために高いアーキテクチャの代価を払おうとしているとき、**まず、依存しているライブラリにその制約を要らない道が用意されていないか確かめよ。** 多くのチームが `SharedArrayBuffer` と隔離を相手に二週間格闘したが、彼らの欲しかったものには、実は第二のバックエンドがあった。 → 第 5 章、第 7 章

## 4. 制約について

### Q14. wasm64 が出れば、4GB の問題はなくなるのか？

**較正**：**代価を払わねばならない。** wasm32 の境界検査が熱い経路で零命令なのは、「エンジンが 8 GiB の仮想アドレス空間 + ガードページを予約し、検査を MMU が無料でこなす」からである。**アドレスが 64 ビットになった途端、メモリ一つずつに 2⁶⁴ の仮想空間を予約することなどできない**。ガードページの技は効かなくなり、明示的な比較と分岐へ退くしかなく、実質的な性能の後退を伴う。

**正しい心のモデル**：4 GiB 以下で享受しているのはハードウェアが補助してくれる無料の安全であり、その線を越えたところから、安全は課金され始める。**分割してストリームすれば 4 GiB の内で片づくものなら、慌てて wasm64 へ跳ぶな。** → 第 2 章、第 8 章

### Q15.「Wasm GC を有効にすればファイルの体積が 80% 削れる」？

**較正**：**方向は正しいが、「もともと言語の実行環境をまるごと同梱していた」言語にしか成り立たない**（Java、Kotlin、Dart など）。**Rust、C、C++ にとって、Wasm GC を有効にしても体積の利得はほとんどない**——それらのオブジェクトはもともと線形メモリの中に配置されており、そもそも省ける GC がない。この助言をすべての言語へ無差別に当てはめるのは、実によくある誤読である。 → 第 8 章

### Q16. `coi-serviceworker` は、セキュリティの穴を突いているのか？

**較正**：**違う。** それは仕様の**正しい使い方**である——Service Worker は同一オリジンのページが自分で登録するプロキシの層であり、自分の scope の内側の要求しか横取りできない。それはブラウザのセキュリティモデルを迂回してはおらず、**ページ自身の権限の範囲の内で「私は自ら隔離の状態へ入る」と宣言している**のであって、隔離の代価（クロスオリジンの資源を失うこと）もそのページ自身が負う。

**だが二点、長く警戒するに値する**：（一）仕様は「Service Worker が合成した COOP/COEP はサーバの出したものと等価でなければならない」と明文で約束してはいない——これは各社の実装が仕様から自然に導いた帰結であり、「複数の仕様の交わりにある推論された振る舞い」に依存することには、締められる危険がある。（二）それは構造的な事実を照らし出している：**無料のホスティングがあなたに与えないものは、たいてい今あなたが要るものではなく、二年後にあなたが要ることになるその制御権である。** → 第 5 章

### Q17. WebContainers は、本当にブラウザの中でサーバを一台走らせているのか？

**較正**：**技術的には本当だが、境界をはっきりさせねばならない。** それは Node.js の C++ のソースをそのまま Wasm へコンパイルしたものではなく、**Wasm の上で走り、Node.js の API と互換な実行環境を一式、作り直したもの**であって、Service Worker でネットワークの要求を横取りしてサーバの振る舞いを模している。

**正確な版**：「ブラウザの中に、このページにとっては振る舞いの一致するサーバを模し出している」。**外部のインターネットにいる他人が、その『サーバ』へ URL で入ってくることはできない**——P2P の穴あけを重ねない限りは。 → 第 5 章、付録 E 事例 60

## 5. あの「120 の事例」について

### Q18. あの 120 の事例は、どれも本物のプロジェクトなのか？

**較正**：**違う。しかも三つの層に分けて見ねばならない。**

- **まず、120 のうち 19 は重複である**（26〜30 は 21〜25 の言い換え、32〜35 は 21〜24、61〜65 は 46〜50、66〜70 は 36〜40）。**重複しないものは実際には 101 である。**
- **次に、その 101 は真偽の三つの等級に分かれる**：🟢 確かめられる（およそ四割）、🟡 上流は本物だが Wasm への移植は要確認（およそ四割）、🔴 例示のために構成したもの（およそ二割）。
- **最後に、正しい読み方はそれを「プロジェクトの索引」ではなく「実現可能性の地図」として扱うことである。** 🔴 の項目が描く技術の道筋はほとんどが成り立つ。まだ誰もやっていないか、やられているが別の名で呼ばれているだけだ（事例 66 に対する DuckDB-Wasm、事例 70 に対する OpenCV.js が、その最良の例である）。 → 第 6 章、付録 D〜F

### Q19. なぜ重複が起きたのか？ それは何を示しているのか？

**較正**：これは長い対話における生成の、具体的な失敗の様式である——**生成する側に外部で管理された「すでに出したものの一覧」がないとき、重複の除去は対話の文脈だけに頼るしかなく、その文脈がひとたび有効な注意の範囲を超えれば、重複の除去は効かなくなる。**

面白いのは、もとの対話における利用者の対処の変化である。まず「前と重複しないものをください」（効かない）→「あなたは重複しました」（効かない）→ 最後に新しい分類の軸を指定するやり方へ変えた（「応用の分類：ネットワーク、ゲーム、ERP、server、オープンソースの移植」「ソフトウェアエンジン、物理エンジン、世界エンジン、LLM エンジン、グラフィックエンジン」）**——この一手が効いた。**

**教訓：探索の空間を縛るほうが、記憶を求めるより有効である。** → 第 6 章

### Q19b. FluffOS は本当に、MUD のサーバをまるごとブラウザへ入れたのか？

**較正**：**そうであり、これは本書で逐一確かめられる、数少ない重量級の事例である。** FluffOS の公式 README は WebAssembly をビルドの目標の一つとして明記しており、`src/wasm/README.md` にはアーキテクチャが余さず記されている（ホストが駆動する `fluffos_tick()` のイベントループ、Transport の抽象と JS の橋渡し、七つの輸出の入口、MEMFS + `file_packager` による同梱）。公式の言葉はこうだ——「ドライバ全体が一つのブラウザのタブの中で走る：コンパイラ、仮想機械、efun、telnet」。

**だが三つの境界を正確に理解せねばならない**：**（一）** それは**単体で完結**している——BSD socket がなく、DNS はスタブで `127.0.0.1` を返す。**他人がネットワーク越しに、あなたのブラウザの中のそのサーバへ入ることはできない**（Q17 の WebContainers と同じことである）。**（二）** **いまのところ書き込みはタブのセッションの内でしか有効でない**（MEMFS は揮発する）。IDBFS/OPFS の被せ層はなお roadmap にある。**（三）** eval limit がないので、**無限の LPC のループはタブ全体を固まらせる**。

**収録の数は動く**：リポジトリの README は 200 の mudlib／158 の codebase／79 が WASM で遊べると検証済み、と記しているが、当時のオンラインの典蔵サイトが挙げていた数字はこれと完全には一致しない。**この種の統計は修復が進むたびに変わる。あなたが訪れたその時点の状態を基準にせよ。** → 付録 L

### Q20. Penpot は Wasm に基づいているのか？

**較正**：**Penpot は確かに存在し、本物のオープンソースの設計協働の道具である。** 「オープンソースの代替が成熟しつつある」証拠として挙げるのは筋が通る。だがそれを「Wasm に基づく」と述べるのは**正確ではない**——その技術の積み重ねは ClojureScript/SVG が主である。

**この種の細部での滑りは技術の語りではよくあることで、しかもそれはアーキテクチャの決定を誤らせる。** 正確な言い方はこうだ：オープンソースの代替は確かに存在し成熟しつつあるが、その技術の道筋は商業の製品と同じとは限らない。 → 第 11 章

## 6. 商売と堀について

### Q21. Figma のアーキテクチャの記述は、どれほど信じられるか？

**較正**：**一部は Figma が公開した工学のブログに基づく**（Wasm への移行、多人数の協働、描画のパイプラインといった主題には確かに公式の記事がある）。**一部は技術の論理からの妥当な推論に属する**（たとえば「すべての UI の文字が動的にストリームされる」「バックエンドがバイナリの特徴の照合をする」といった具体の実装の細部は、Figma が公に認めてはいない）。

「ベクターネットワーク（Vector Networks）」は確かに Figma が公に打ち出している中核の技術の特色だが、その具体のアルゴリズムは公開されていない。

**第 10 章は、アーキテクチャの様式の一例として読んでほしい。Figma の内部設計の権威ある記述としてではなく。** → 第 10 章

### Q22.「データの引力」は自然に生まれるものか？

**較正**：**その大部分は設計の選択の結果であって、データ量の自然な結果ではない。** データの引力の強さは**データの可搬性に反比例する**：

- 形式が開かれ、完全な書き出しの API があり、取り込める第三者がいる → 引力は弱い。
- 専有の形式で、書き出しに欠落があり、第二の行き先がない → 引力は強い。

**ゆえに「データの引力」は実務上、その多くが「形式と API の設計の選択」の産物である。** この点は築く側にも購う側にも等しく重い——築く側はどう造るかを知り、購う側はどう嵌まらないかを知る。 → 第 12 章

### Q23. P2P は本当に、協働を「サーバなし」にできるか？

**較正**：**「たいていの場合はサーバなし」である。** 四つの工学上の現実がしばしば飛ばされる：

1. **NAT の穴あけの成功率は 100% ではない**——対称型の NAT では **TURN の中継**へ退くしかなく、TURN のサーバには金も帯域も運用も要る。
2. **オフラインと非同期の協働**——「私は金曜に直し終え、あなたは月曜に開く」には、つねに線上にいる節点が要る。それはサーバである。名を変えただけだ。
3. **誰が真実の源か**——企業が欲しいのは権威ある版、監査の記録、アクセス制御、離職した従業員の権限の取り消しである。**P2P は生まれつき権限の取り消しに弱い**（データはもう相手の機械の上にある）。
4. **法令の遵守**——「データが従業員一人ひとりのブラウザに散らばっている」は、監査を通れる答えではない。 → 第 11 章

### Q24.「token が安くなったのだから、自分で車輪を造るのは時間の問題にすぎない」——この推論は正しいか？

**較正**：**推論そのものは正しいが、二つの勘定が抜けている。**

- **時間の罠**：ソフトウェア工学の法則は「コードを書くのが 20%、デバッグと境界条件が 80%」であり、**AI が零にしたのは前者だけである。** あなたが省いたのはその 20% だ。
- **保守のエントロピー**：二年後、W3C があなたの依存する API を廃止する。そして**その十万行を本当に読み解いた者は誰もいない。** あなたはその「古い車輪」の山を、もう一度 AI に理解させねばならず、下手をすれば作り直しになる。

**より精確に、その変形を述べるとこうなる**：AI は「コードを生む速さが、コードを理解する速さをはるかに超える」状況を作った。ゆえに**「誰も本当には読み解いていないコード」が、かつてない速さで積み上がっていく**——そしてシステムの保守可能性を決めるのは後者であって、前者ではない。 → 第 12 章

### Q25. で、結局、自分で造るべきなのか？

**較正**：二種類の人に分けられる。**独立した個人と小さなチーム**が微小な車輪を造るのは割に合う（規模が小さく、要求が安定していて、壊れたら自分で直せる）。**現代の産業と大きな企業**が供給者に金を払うのは割に合う（技術のエントロピーを外へ出し、時間を中核の事業に使う）。

**その中間の層——凡庸で、機能が一つきりの軽量な SaaS——は消される。**

そして自分が造るべきかどうかの判断には、検証が一つあれば足りる：**「三年後にこれが真夜中に壊れたとき、誰が直すのか、その人はまだ会社にいるのか？」** この問いに澄んだ答えが出るまで、**あなたが造っているのは車輪ではなく、負債である。** → 第 12 章
