# 第7章：状態を持たない機械の記憶——MEMFS、IDBFS、OPFS、WASI

> WebAssembly はそれ自体、**状態を持たない（stateless）**サンドボックス仮想機械である。ハードディスクもなければ、ネイティブのデータベースもない。既定ではホストが割り当てた一枚の平坦なメモリしか持たず、**タブを一度リロードすれば、その中のデータは泡のように一瞬で蒸発する。**
> それを解決するやり方は、本質的にはただ一語である：**権限の外注。**

## シナリオ 1　第一層：MEMFS、メモリの中に生きる偽の Linux

**背景**：C/C++ プロジェクト（FFmpeg、SQLite、GNU tar）を Wasm へコンパイルすると、コードの至るところにこういうものがある。

```c
FILE *f = fopen("input.mp4", "rb");
fread(buf, 1, size, f);
fclose(f);
```

Wasm に `fopen` はない。システムコールという概念すらない。ではこの行はどうやって動いているのか。

**答え：Emscripten が線形メモリの中に POSIX ファイルシステム一式を偽造している。** この仕組みは **MEMFS**（In-Memory File System）と呼ばれ、型付き配列で Wasm の線形メモリ内に標準的な Linux のディレクトリ構造（`/tmp`、`/home`、`/dev`）を模倣し、libc のファイル関数をすべてそこへ振り向ける。

```
C のコード:   fopen("/work/input.mp4", "rb")
                    ↓ Emscripten の libc 実装
JS グルー:    FS.open("/work/input.mp4", "r")
                    ↓
MEMFS:        線形メモリ内で JS オブジェクトが構築したディレクトリツリーを引き、
              ある Uint8Array を指すファイルディスクリプタを返す
```

**典型的なデータフロー**（FFmpeg.wasm を例に）：

```javascript
// 1. ユーザがドラッグしてきたファイルを Wasm の仮想ファイルシステムへ書く
ffmpeg.FS('writeFile', 'input.mp4', await fetchFile(file));
// 2. コマンドラインを実行する——Wasm の内側は本気で CLI を走らせているつもりでいる
await ffmpeg.run('-i', 'input.mp4', '-c:v', 'libx264', 'output.mp4');
// 3. 仮想ファイルシステムから結果を読み戻す
const data = ffmpeg.FS('readFile', 'output.mp4');
// 4. Blob URL へ変えてユーザにダウンロードさせる
const url = URL.createObjectURL(new Blob([data.buffer], {type: 'video/mp4'}));
```

**MEMFS の二つの致命的な痛点**：

1. **一時的である**。タブを閉じる、リロードする、あるいはメモリを使い切る（OOM）と、ファイルは消える。
2. **線形メモリの枠を食う**。500 MB の動画を MEMFS へ書けば、あの 4 GB 上限のうち 500 MB を占める——そして FFmpeg はトランスコードの過程でさらに使う。**これこそ FFmpeg.wasm が大きなファイルを扱えない理由であり、FFmpeg 自体の能力とは無関係である。**

**MEMFS にはあまり語られない前向きな用途もある：一括配布である。** Emscripten の `file_packager` ツールは、何千何万のファイルを**単一の `.data` イメージ + 一つの `.js` ローダ**へ固め、実行時の起動前に指定のパスへマウントできる。FluffOS の Wasm ビルドはこうして mudlib 全体を配っている——**ゲーム世界の数万の LPC ファイルが、一つの静的な blob になる**。代価は公式ドキュメントに正直に書かれている：**「現状の書き込みはタブのセッション内でのみ有効」**。そしてそのロードマップの次の一歩こそ、本節がこれから語る二つの層である——**書き込み経路に IDBFS か OPFS のオーバーレイを重ねること**（付録 L 参照）。

> **これは本書が見つけられた最良の現場検証である**：実在し、複雑で、いまも維持されているプロジェクトが、この四層の階段の第一段でいま立ち止まっており、しかも自分が第二段・第三段へ行かねばならないことを明確に知っている。

> 💡 座右の一言
> **互換性の本質は、新しい環境の中で古い環境の嘘を忠実に再建することである。** Emscripten は C プログラムを「ブラウザへ適応させた」のではない。やったのは逆だ——**ブラウザに自分が Linux のふりをさせた**のであり、`fopen`、`ioctl`、`pthread_create`、`SDL_CreateWindow` のすべてを騙し通せるほど巧みに、である。だからこそ二十年前の C++ ゲームが、核心ロジックをほぼ一行も変えずにウェブで動く。この原理はシステム移行においてより一般的な形を持つ：**大量の既存資産を新しいプラットフォームへ移すとき、「資産をプラットフォームに合わせて改造する」コストは O(資産の数)であり、「プラットフォーム上で古い環境を模倣する」コストは O(1) である。** WSL、Rosetta、Wine、Docker、JVM——すべてこの一手だ。代価も同じである：**移していくのは古い世界の前提一式であり、新しい環境では本来避けられたはずの非効率も一緒に来る。**

## シナリオ 2　第二層：IDBFS、メモリをブラウザのデータベースへ巻き戻す

**背景**：MEMFS の一時性を解決するため、Emscripten は **IDBFS** を提供する——仮想ファイルシステムをブラウザの **IndexedDB** データベースへ繋ぐものである。

**動作原理**：

```javascript
// マウント：/save という仮想ディレクトリを IndexedDB へ結びつける
FS.mkdir('/save');
FS.mount(IDBFS, {}, '/save');

// IndexedDB からメモリへ読み込む（起動時）
FS.syncfs(true, err => { /* true = IDB から MEMFS へ読む */ });

// C プログラムはいつもどおりファイルを書く
// ... fopen("/save/game.sav", "wb") ...

// メモリを IndexedDB へ同期する（セーブ時）
FS.syncfs(false, err => { /* false = MEMFS から IDB へ書き戻す */ });
```

**肝心なのは、これが「一括の巻き戻し」であって、ランダムな読み書きではないことである**。`syncfs` はマウントポイントの内容を**全量**シリアライズして IndexedDB へ入れる（あるいはその逆をする）。これが適用範囲を決める。

- ✅ **向く**：ゲームのセーブデータ（数百 KB）、設定ファイル、小さな JSON、ユーザの好み。**ウェブ版レトロゲームエミュレータのセーブはこうしている。**
- ❌ **向かない**：データベースファイル、大きなメディア、ランダムな読み書きを要するあらゆるもの。500 MB の SQLite ファイルは `syncfs` のたびに丸ごと運ばれる。

**IndexedDB 自体の問題も一緒に受け継ぐ**：非同期のイベント駆動 API、平凡な書き込みスループット、ブラウザの容量制限、そして一部のブラウザのプライベートモードでは縮小されたり消されたりすること。

## シナリオ 3　第三層：OPFS、これこそが本当の答えである

**背景**：**Origin Private File System** は近年の Wasm フロントエンドストレージの黄金標準であり、DuckDB-Wasm と公式 SQLite-Wasm がブラウザ内で数 GB のデータベースを扱い ACID を保証できる理由でもある。

**それは何か**：ブラウザがオリジンごとに開く**高度に隔離され、極度に最適化された私有ディスク空間**である。ユーザのファイルエクスプローラには現れず、許可ダイアログも要らず、他のサイトからは見えない。そして——**性能のために設計された低水準 API を一組持っている。**

**二つのアクセスモードがあり、その差は天と地ほど違う**：

```javascript
// ── モード A：非同期の書き込みストリーム（メインスレッドで使える）────────
const root = await navigator.storage.getDirectory();
const fh = await root.getFileHandle('data.bin', { create: true });
const writable = await fh.createWritable();
await writable.write(uint8array);
await writable.close();        // 各段が Promise であり、マイクロタスクのスケジューリング負荷がある

// ── モード B：同期アクセスハンドル（★ Web Worker の中でしか使えない）──
// ここが性能の分水嶺である
const root = await navigator.storage.getDirectory();
const fh = await root.getFileHandle('db.sqlite', { create: true });
const handle = await fh.createSyncAccessHandle();

handle.write(buffer, { at: offset });   // ← 完全に同期。Promise なし
handle.read(buffer,  { at: offset });   // ← ランダムアクセス。ローカルの pread/pwrite のよう
handle.flush();
handle.truncate(newSize);
handle.getSize();
handle.close();
```

**`createSyncAccessHandle()` がなぜ鍵なのか**：C で書かれたデータベース（SQLite、DuckDB）のストレージ層は**同期**である——`pread(fd, buf, len, offset)` を呼んだら、データが即座に buffer にあることを期待する。Promise を返す API でそれを実装することは**できない**。プログラム全体を非同期へ書き換えないかぎり（それは不可能だ。数十万行の C なのだから）。

**`createSyncAccessHandle` は Wasm に、本物の、同期の、ランダムに位置づけできるファイルハンドルを与えた**——だから SQLite の VFS（Virtual File System。SQLite が移植性のために設計したストレージ抽象層）は関数をいくつか実装するだけで、データベース一式が動き出す。

```
SQLite の中核（無改変の C コード）
        ↓ VFS インタフェースを呼ぶ：xOpen / xRead / xWrite / xTruncate / xSync / xLock
Emscripten グルー層の OPFS VFS 実装
        ↓
FileSystemSyncAccessHandle.read/write/flush
        ↓
ブラウザの私有ディスク空間（本当に着地する）
```

**代価と制約**（これらは仕様レベルのものであって、実装の欠陥ではない）：

1. **`createSyncAccessHandle` は Web Worker の中でしか呼べない**。メインスレッドでは禁止である——同期 I/O は UI をブロックするからだ。これは**あなたの Wasm データベースエンジン全体を Worker へ移さねばならない**ことを意味し、メインスレッドは `postMessage` でのみそれと会話できる。
2. **既定では排他ロックである**。同一ファイルに同時に一つの sync access handle しか持てない。複数タブで同じアプリを開けばロックを奪い合う——調整の仕組みを自分で設計する必要がある（Web Locks API や `BroadcastChannel` など）。
   **ただしこの一条はのちに緩んだ**：新しめのブラウザは `createSyncAccessHandle({ mode: "readwrite-unsafe" })` をサポートし、**同一ファイルに同時に複数のハンドルを開ける**。名前の `unsafe` は正直である——**並行制御の責任をまるごとあなたへ返す**のであり、ブラウザはもう排他してくれない。使う前にはっきりさせること：あなたのエンジンは自前のロックを持っているか。
3. **容量制限**。ブラウザはオリジンごとにストレージの割当を持ち（通常はディスクの空き容量に連動し、`navigator.storage.estimate()` で問い合わせられる）、ディスク圧のもとで persistent と印されていないデータを**追い出す**ことがある。消されないようにするには `navigator.storage.persist()` が要る。
4. **ユーザには見えない**。これは利点でもあり（ユーザを煩わせない）欠点でもある（ユーザが直接バックアップできないので、エクスポート機能を自分で用意せねばならない）。

**四層ストレージの完全な対照**：

| | MEMFS | IDBFS | OPFS（async） | OPFS（sync handle） |
|---|---|---|---|---|
| 永続 | ❌ | ✅ | ✅ | ✅ |
| ランダムアクセス | ✅（メモリ内で） | ❌（一括の巻き戻し） | 限定的 | **✅ 本物の pread/pwrite** |
| 線形メモリを食う | **✅（致命的）** | 同期時に食う | ❌ | ❌ |
| メインスレッドで可 | ✅ | ✅ | ✅ | **❌ Worker のみ** |
| 性能 | メモリ速度 | 悪い | 中 | **ローカルディスクに近い** |
| 適用 | 一時的な中間ファイル | ゲームのセーブ、設定 | 一般のファイル | **データベース、大きなファイル、ストリーミング** |

### ★ 配備の判断を変える分岐：SQLite-Wasm の二つの OPFS VFS

**これは本章で最も実務価値のある一節であり、どの入門記事にもほぼ現れない。** 公式 SQLite-Wasm が提供する OPFS バックエンドは一種類ではなく**二種類**であり、その配備の代価は天と地ほど違う。

| | **`opfs` VFS**（第一世代） | **`opfs-sahpool` VFS**（SAH = SyncAccessHandle） |
|---|---|---|
| 機構 | メインスレッドと OPFS のあいだに非同期プロキシを置き、`Atomics.wait` で非同期を同期へ変える | **あらかじめ開いた sync access handle の一組（「プール」）を直接保持し**、Worker 内で同期に読み書きする |
| **`SharedArrayBuffer` が要るか** | **✅ 要る** | **❌ 要らない** |
| **COOP/COEP のクロスオリジン隔離が要るか** | **✅ 要る** | **❌ 要らない** |
| 性能 | 使える | **公式ドキュメントが全 OPFS 選択肢中で最高と明記** |
| 複数接続 | 対応 | **同時複数接続に非対応** |
| 利用可能性 | 早くから | 主要ブラウザで 2023 年 3 月以降おおむね使える |

**この表の意味を、一文に翻訳すると**：

> **GitHub Pages のような HTTP ヘッダを設定できない場所で永続化 SQLite を走らせたいなら、`opfs-sahpool` を選べ——クロスオリジン隔離が要らず、しかも最速である。**
> 公式の推奨もまさにこうだ：**性能を並行性より重視するクライアント、あるいは COOP/COEP レスポンスヘッダを設定できないクライアントは、`opfs-sahpool` を使うべきである。**

**これは第 5 章のあの「筆頭の障害」をまるごと迂回する**。代価は「複数接続に非対応」だけであり——大多数のシングルユーザのフロントエンドアプリケーションにとって、それはそもそも代価ではない。

> 💡 **ここにはより一般的な教訓がある**：あるプラットフォームの制約のために高い architectural な代価を払おうとしていることに気づいたら（ここでは COOP/COEP がもたらすサードパーティリソースの全面的な破損）、**まず、依存しているライブラリがその制約を必要としない経路を提供していないか確認すること。** 多くのチームが `SharedArrayBuffer` と隔離のために二週間格闘したが、彼らが欲しかったものには、それを必要としないバックエンドがあった。

> ⚠️ 真偽の注意
> 「SQLite-Wasm の読み書きスループットは IndexedDB より 2〜4 倍速い」「OPFS は Wasm にローカルディスクに近い速度の読み書きをさせる」といった言い方は方向としては正しいが、**具体的な倍率はワークロードとブラウザのバージョンに強く依存する**。信頼できる定性的な結論は三つだけである：**（一）** `createSyncAccessHandle` は非同期のスケジューリング負荷を消し去り、「大量の小さなランダム I/O」（まさにデータベースのアクセスパターンである）に対する改善が最も顕著である。**（二）** 「一度に大きな塊を書く」場面では、async と sync の差は大きくない。**（三）** OPFS の性能はブラウザの実装と強く結びついており、Safari、Firefox、Chrome の挙動には顕著な差があった時期がある。**選定するときは対象ブラウザで実測すること。どんな倍率も鵜呑みにしないこと。**

> 🔍 踏み込んだ論評──OPFS の登場こそ、Wasm を「ライブラリ」から「アプリケーションプラットフォーム」へ変えた
> この節は単独で語る価値がある。分水嶺を刻むからだ。**OPFS 以前、ブラウザ内の Wasm は本質的に「純粋関数の加速器」だった**：入力を与え、出力を吐かせ、そして忘れられるべきものだった。状態を要するもの——ユーザのプロジェクトファイル、データベース、キャッシュ——はすべて JavaScript へ戻り、IndexedDB のあの非同期 API で保存せねばならなかった。この隙間が「デスクトップアプリをブラウザへ移す」ことを永遠に最後の一マイルだけ届かせなかった：**SQLite をコンパイルして持ち込むことはできても、それに使わせるファイルシステムがなかった**のである。OPFS の `createSyncAccessHandle` が埋めたのはまさにその一マイルであり、しかも埋め方が興味深い——**Wasm に新しい能力を与えたのではなく、Wasm に「C 言語の世界が期待するインタフェースの形」を与えた**のである。同期で、位置づけでき、ロックがあり、flush がある。この四つの性質は、それが最良だからではなく、**過去五十年のあらゆるストレージソフトウェアがこの形に沿って書かれてきた**からそうなっている。だから本当の洞察はこうだ：**新しいプラットフォームが既存のソフトウェア資産を受け入れる鍵は、どれだけ強い能力を提供するかではなく、相手が期待するインタフェースの形を提供することにある。** これは、OPFS がなぜ「十分に現代的でない」（同期、ブロッキング）ように見える API 設計を選んだのかを説明する——現代的な非同期設計は、C/C++ エコシステム全体を門前払いしてしまうからだ。**プラットフォームの API を設計するとき、最も重要な問いは「どの設計が最も優雅か」ではなく、「私が受け入れたい資産は、どんな形に沿って書かれているか」である。**

## シナリオ 4　第四層：バックエンドの WASI と、能力外注の完全な形

**背景**：Wasm が殻を破ってバックエンドへ向かうと（Wasmtime、WasmEdge）、もはやブラウザのサンドボックスに縛られず、「OS レベルのディスクアクセス」という問題に直面する。そしてその答えは、フロントエンドと本質的に同じである。

**ケイパビリティベース・セキュリティの完全な意味**：

- 従来の Linux では、破られた Node.js プロセスは `/etc/passwd` を直接読める——そのユーザの**全**権限を持っているからだ。
- Wasm の実行環境は既定で「**完全に手ぶら**」である：`open()` システムコールの権限がない。`open()` という import がそもそも提供されていないからである。

```bash
# 起動時に、ホストの ./my_storage を Wasm から見た /sandbox として明示的に認可する
wasmtime run --dir=./my_storage::/sandbox my_server.wasm
```

モジュールの内部が `/sandbox/../etc/passwd` へアクセスしようとすれば、実行環境が能力の境界で直接遮断し終了させる——**これはファイルシステムの権限任せの運任せではなく、「あなたが手にしているディレクトリハンドルはそもそも上へ行けない」という構造的な保証である**（技術的には POSIX の `openat` の意味論とパス解決の制限に対応する）。

**WASI の二つの世代**（技術選定では必ず区別すること）：

| | `wasi_snapshot_preview1` | WASI 0.2 (Preview 2) |
|---|---|---|
| モデル | POSIX 風のファイルディスクリプタ | **Component Model** + WIT のインタフェース定義 |
| インタフェース | 一つの大きな平坦な関数群 | `wasi:filesystem`、`wasi:io`、`wasi:sockets`、`wasi:http`、`wasi:clocks` などへ分割 |
| エコシステム | **成熟**。Rust の `wasm32-wasip1`、TinyGo、多くのツールチェーンが対応 | 進化中。ツールチェーンが順次追いついている |
| 組み合わせ可能性 | 悪い（単体のインタフェース） | **良い**（あるコンポーネントに `wasi:clocks` だけを与え、ファイルは与えないことができる） |

**Component Model はこの道の終点である**：Wasm モジュール同士が `i32` ポインタだけでなく**高水準の型**（文字列、レコード、バリアント、ストリーム）で会話できるようにする——言い換えれば、第 2 章のあの「境界の料金所」の問題を一挙に解こうとしている。**WIT（Wasm Interface Type）** はそのインタフェース記述言語である。

```wit
// WIT のインタフェース定義：IDL のようだが、コンパイル時に各言語のバインディングを生成できる
package example:storage@0.1.0;

interface kv {
  record entry { key: string, value: list<u8> }
  get: func(key: string) -> option<list<u8>>;
  put: func(key: string, value: list<u8>) -> result<_, string>;
  list-all: func() -> list<entry>;
}
```

**技術的思考のまとめ**：Wasm がデータ保存を解決する本質は、**メモリマッピング（Memory Mapping）+ 能力の委譲（Capability Delegation）** である。

- **フロントエンド**では、ディスク操作をブラウザの IndexedDB や OPFS API へ外注する。
- **バックエンド**では、ディスク操作を WASI 実行環境の事前認可されたチャネルへ外注する。

このアーキテクチャは Wasm 仮想機械のサンドボックス隔離の特性を完全に保ちながら、ネイティブの C プログラムに迫る I/O スループットを与えている。

> 💡 座右の一言
> **システムの最も正直な場所は、自分が何を必要とするかを列挙したあの一覧である。** WASI の import セクション、ブラウザ拡張の `permissions` フィールド、Android の manifest、Kubernetes の ServiceAccount——これらの一覧の価値は「悪人を制限した」ことにはない（本物の悪意あるプログラムは必要なものをすべて堂々と要求する）。価値は、**「これは何ができるのか」を、リバースエンジニアリングしなければ答えられない問いから、五秒で読み終わる事実へ変えること**にある。セキュリティ監査のコストは、そのために「悪事を働かないことの証明」から「何を要求したかを見ること」へ下がる。この原理の帰結は実用的だ：**サードパーティのコンポーネントを評価するとき、最初にすべきはコードを見ることではなく、権限一覧を見ることである——その一覧が存在しないか、読み切れないほど長いなら、答えはすでに出ている。**

## 本章のまとめ

- Wasm 自体は**状態を持たない**：線形メモリが一枚あるだけで、タブをリロードすれば蒸発する。その解法はただ一語——**権限の外注**である。
- **MEMFS**：Emscripten が線形メモリの中に偽造した POSIX ファイルシステム一式であり、`fopen()` に行き先を与える。**一時的で、しかもあなたの 4 GB の枠を食う**——これこそ FFmpeg.wasm が大きなファイルを扱えない本当の理由である。
- **IDBFS**：`FS.syncfs()` でマウントポイント全体を**一括で巻き戻して** IndexedDB へ入れる。ゲームのセーブと設定（数百 KB）に向き、**データベースやランダムな読み書きを要するものには向かない**。
- **OPFS こそが本当の答えであり**、その分水嶺は **`createSyncAccessHandle()`** である——Wasm に同期で、ランダムに位置づけでき、ロックと flush を持つファイルハンドルを与え、SQLite の VFS が関数をいくつか実装するだけで一式動くようにした。代価は：**Worker の中でしか使えない、既定で排他ロック（`{mode:"readwrite-unsafe"}` で緩められるが責任はあなたに移る）、容量制限がある、ユーザには見えない**。
- **★ 最も実務価値のある一条**：SQLite-Wasm には **二種類**の OPFS VFS がある。第一世代の `opfs` は `SharedArrayBuffer` を要し、したがって**クロスオリジン隔離が要る**。一方 **`opfs-sahpool` は COOP/COEP を必要とせず、しかも公式ドキュメントで最速の選択肢である**。代価は複数接続に非対応であることだけ。**GitHub Pages で SQLite を永続化したいなら後者を選べ。第 5 章のあの筆頭の障害がまるごと迂回できる。**
- 一般的な教訓：**あるプラットフォームの制約のために高い architectural な代価を払おうとしているときは、まず依存するライブラリにその制約を必要としない経路がないか確認すること。**
- OPFS の設計が示すのは：**新しいプラットフォームが既存のソフトウェア資産を受け入れる鍵は、どれだけ強い能力を提供するかではなく、相手が期待するインタフェースの形を提供することである**——たとえその形（同期、ブロッキング）が十分に現代的に見えなくとも（シナリオ 3 の 🔍 参照）。
- バックエンドの **WASI** は同じ哲学のもう一面である：**ケイパビリティベース・セキュリティ**。モジュールは既定で手ぶらであり、能力の一覧は起動引数に書かれている。**preview1 と 0.2 は二つの世代である**点に注意。今日書くものは一度移行させられる覚悟が要る。
- フロントは OPFS/IndexedDB へ外注し、バックエンドは WASI へ外注する——**同じ心得、二つのホスト。**

記憶の問題は解けた。しかしまだ越えていない硬い壁がある：**データが 4 GB を超えたら、モジュールが 30 MB を超えたら、何が起きるのか。** 第 8 章へ。
