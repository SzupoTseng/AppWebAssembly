# 第3章：長所、短所、そして口に出されない制約

> 技術評価資料の中で最も役に立たないのは、「長所五つ、短所三つ」というあの表である。短所はつねに長所より遠慮がちに書かれ、プロジェクトを本当に殺すのは、書かれなかった四つ目であることが多いからだ。この章では三つの次元の制約を並べる——**ブラウザ側、システムとアーキテクチャ、開発とエコシステム**——そして一条ずつ「なぜそうなっているのか」を追う。

## シナリオ 1　四つの長所と、それぞれの隠れた但し書き

**背景**：Wasm の長所はどの入門記事にも書いてある。しかしどの長所の下にも小さな字の一行があり、工学的判断が見るべきなのはその一行のほうである。

**長所その一：ネイティブに近い性能。**

- **なぜ速いのか**：バイナリ形式の解析コストが極めて低く、静的型付けによりコンパイラが型検査を挿入せずに済み、背後でランダムに停止するガベージコレクタがなく、線形メモリのレイアウトが緊密なので CPU キャッシュのヒット率が高い。
- **隠れた但し書き**：この四つの優位は**すべて「密な計算」という形の下でしか成立しない**。コードの大半の時間がネットワーク待ち、DOM の書き換え、文字列の連結に費やされているなら、Wasm は一つも助けにならず、そのうえモジュールのダウンロードと境界越えのオーバーヘッドを余分に払うことになる。**Wasm の性能優位には閾値がある。計算量が足りなければ、それは負の収益である。**

**長所その二：サンドボックスの安全性。**

- **なぜ安全なのか**：既定でメモリ安全な隔離環境の中で実行され、ホストのリソースへアクセスできず、あらゆる能力を明示的に import しなければならない。
- **隠れた但し書き**：**「サンドボックスの安全」が守るのはホストであって、あなたのプログラムではない。** さらにバックエンドの場面では、そのサンドボックスが本当に隙間なく閉じているかは実行環境の実装品質に依存する——Wasm の実行環境は JIT、シグナルハンドラ、メモリマッピング管理を含む巨大で複雑なソフトウェアであり、**そこは歴史的に脆弱性が最も密集する場所である**。**「Wasm だから安全」はセキュリティ評価報告書に書ける一文ではない**（三層の攻撃面の完全な解体と対策は付録 O §7）。

**長所その三：言語非依存。**

- **なぜ可能なのか**：LLVM へコンパイルできる（あるいは独自の Wasm バックエンドを持つ）言語なら、どれも `.wasm` を出力できる。Rust、C/C++、Go、Zig、AssemblyScript、C#（Blazor）、Kotlin、Swift、Dart いずれも使える。
- **隠れた但し書き**：**「コンパイルできる」と「コンパイルしたものが使える」は別の話である。** 分水嶺は、その言語に一緒に同梱しなければならない実行環境があるかどうかだ。

| 言語 | 実行環境の負担 | 典型的な `.wasm` サイズ（Hello World 級） | 現実的な評価 |
|---|---|---|---|
| Rust / C / C++ / Zig | ほぼゼロ（GC なし、runtime なし） | 数 KB〜数十 KB | **Wasm とは生まれつきの相性** |
| AssemblyScript | 極小の runtime + 簡易 GC | 数 KB | フロントエンド開発者の滑らかな入口 |
| Go | **完全な runtime + GC + scheduler** | 従来の `GOOS=js` では 1.5 MB+ から | サイズが主な痛点（TinyGo で大幅に縮むが対応は部分集合） |
| C# / Blazor | .NET runtime（または AOT トリミング） | 数 MB 級 | エコシステムは強力。サイズとコールドスタートが代価 |
| Java / Kotlin | 従来は JVM の意味論層を同梱する必要があった | 極大 | **Wasm GC（3.0 で核心仕様入り）が着地して初めて実用になった** |
| Python | CPython インタプリタまるごと | Pyodide 一式で 30〜50 MB | 「科学計算エコシステム全体が必要」なときだけ割に合う |

**長所その四：極めて軽量で、起動が非常に速い。**

- **なぜ可能なのか**：Docker イメージが容易に数百 MB になり、起動にイメージ取得と namespace の立ち上げを要するのに対し、`.wasm` はたいてい数 KB から数 MB で、インスタンス化はマイクロ秒級である。
- **隠れた但し書き**：**この比較はバックエンドでしか成立しない。** ブラウザ側では、あなたの競争相手は Docker ではなく「何もダウンロードしない純粋な JavaScript」である。8 MB の Wasm モジュールは 200 KB の JS バンドルに対して**四十倍**の重さだ。「軽量」とは誰に対してかの問題であり、対照群を替えれば結論は反転する。

> 💡 座右の一言
> **あらゆる技術的優位は比であり、比の分母は差し替え可能である。** 「Wasm は極めて軽量だ」は Docker と比べれば真であり、`<script>` と比べれば偽である。「Wasm はネイティブに近い性能だ」は JavaScript と比べれば真であり、ネイティブバイナリと比べれば割引される。これは誰かが嘘をついているのではなく、**性能の主張はどれも対照群を前提としており、その対照群がしばしば省略されている**のである。だから技術を評価するときに最初にすべき動作は、省略された分母を補い、こう問うことだ：**私の場面において、本当の代替案は誰か。** 失敗した技術選定の多くは、技術を間違えたのではなく、比べる相手を間違えたのだ。

## シナリオ 2　ブラウザ側の三つの壁

**背景**：この三つの壁は、あらゆるフロントエンド Wasm プロジェクトがぶつかるものであり、順序もほぼ決まっている。

**壁その一：DOM を直接操作できない。**

Wasm はいまも HTML、CSS、DOM 要素へ直接アクセスできない。JavaScript を仲介役（グルーコード）としてデータを渡すしかない。

- **技術的になぜか**：DOM は JavaScript のオブジェクトモデルの上に築かれた高水準 API であり、ガベージコレクション対象のオブジェクトグラフ、文字列、プロトタイプチェーンが関わる——そして核心の Wasm 仕様には**それらの型が一つもない**。Wasm に DOM を直接触らせることは、JS のオブジェクトモデル全体を Wasm の型システムへ持ち込むことに等しい。
- **現在の解法**：`wasm-bindgen` / `web-sys` がバインディングを生成し、Rust から `document.createElement()` を呼べるように見せてくれる——しかし内側では呼び出しのたびに**やはり JavaScript を一往復している**。
- **将来の解法**：**Reference Types**（Wasm が不透明なホスト参照を保持できるようにする。Wasm 2.0）と **Wasm GC**（Wasm がホストのオブジェクトを理解できるようにする。Wasm 3.0）はこの隙間をかなり縮めた。**JS String Builtins** もさらに前進している。しかし「橋渡しのオーバーヘッドなしに DOM を直接操作する」は予見しうる将来も非現実的である。
- **実務上の結論**：**Wasm で UI を書くな。** Wasm で計算し、JS で描け。Figma はまさにそうしている——Wasm が幾何と組版を計算し、WebGL がピクセルを描き、DOM はメニューとパネルだけを担当する。

**壁その二：JavaScript とのデータ転送コストが高い。**

Wasm の内部が知っているのは数値だけである。文字列、オブジェクト、配列はすべて線形メモリへ直列化し、処理後に逆直列化しなければならない（機構の詳細は第 2 章シナリオ 4）。

- **実測に基づく心的モデル**：境界越え呼び出しそのものの固定オーバーヘッドはナノ秒級だが、**文字列一往復の符号化・復号は容易にマイクロ秒級へ達する**。毎秒十万回の細粒度呼び出しをすれば、この勘定はフレームグラフの真ん中に現れる。
- **よくある災難のパターン**：Wasm を「より速いライブラリ」とみなして関数単位で JS を置き換えていく——結果、どの関数も速くなったのに全体は遅くなる。境界越えの回数が爆発するからだ。

**壁その三：ファイルサイズが大きくなりやすい。**

- **主因**：巨大な実行環境を伴う言語（Go、C#、Java）は GC と標準ライブラリを丸ごと同梱しなければならない。
- **副因**：静的リンク。Wasm には従来、動的リンクがない。`libpng` を使うなら `libpng` を丸ごとコンパイルして入れることになり、十個のモジュールが同じライブラリを使えば十部できる。
- **使える武器**：

```bash
# 1. Binaryen の wasm-opt：最も重要な一歩。サイズと速度の双方に効く
wasm-opt -Oz --strip-debug --strip-producers input.wasm -o output.wasm

# 2. Rust 側：最適化とストリップを Cargo.toml に書く
#    [profile.release]
#    opt-level = "z"      # あるいは 3（速度優先）/ "s"（バランス）
#    lto = true           # クレート横断のインライン展開と死コード削除
#    codegen-units = 1    # LTO により完全な視野を与える
#    panic = "abort"      # unwinding テーブルを削る（Rust 固有。相当なサイズが浮く）
#    strip = true         # シンボルを剥がす

# 3. 診断：twiggy がどのシンボルがサイズを食っているかを教える
twiggy top -n 20 output.wasm

# 4. 転送層：Brotli は必ず有効にする（Wasm の圧縮率はたいてい良好で、3.5〜5 倍が普通）
```

> **これは入口にすぎない。** サイズ最適化の完全な武器庫——セクションレベルの解剖法、`wasm-opt` の各パスが実際に何をしているか、Rust の `panic!` に潜む書式化機構（小さなモジュールでは 30% 以上を占めうる）、単相化爆発への「ジェネリックの薄い殻」という解法、`no_std`、データの切り詰め、そして**圧縮辞書転送**（改版時に数十 KB だけを送る）——**付録 N 第一部を参照。**

> ⚠️ 真偽の注意
> ネット上で流布する「Wasm ファイルはたいてい数 KB から数 MB」は**「純粋な計算カーネル」についての話である**。完全な言語実行環境や大型 C++ ライブラリが絡んだ瞬間、実際のサイズは別の桁になる。OpenCV.js は約 6〜9 MB、Solidity コンパイラ `soljson.wasm` は約 10〜15 MB、Pyodide 一式は 30〜50 MB。**サイズの数字を引用するときは、それがどの層の話なのかを必ず確認すること。**

> 🔍 踏み込んだ論評──「DOM を操作できない」は実は祝福である。ただ誰もそう言いたがらないだけだ
> これは本章で最も直感に反する一節である。どの入門記事も「DOM に触れない」を短所として挙げるが、もし Wasm が本当に DOM を直接操作できたら何が起きるのか。**まず、遅くなる。** DOM 操作のボトルネックはこれまで一度も「呼び出す言語が何か」にあったことはなく、スタイルの再計算（recalculate style）、レイアウトの再配置（reflow）、描画（paint）にある——これらはブラウザのレンダリングパイプラインの中で起き、どの言語から起動したかとは無関係だ。`appendChild` を直接呼べる Wasm は、**JS より速くなるのではなく、毎フレーム千回の再配置を引き起こすコードを書きやすくするだけである**。**次に、エコシステムを引き裂く。** Wasm が DOM を直接触れるようになれば、「Wasm 版 React」「Wasm 版 Vue」が一式現れ、JS エコシステムとの相互運用が永続的な痛みになる。**第三に、そして最も肝心なこと：あの明快なアーキテクチャの分界線を破壊する。** いまこの線は誰にも健全な決定を強いている——**重い計算は Wasm へ、対話と画面は JS へ**。これこそ Figma、Photoshop Web、AutoCAD Web が示し合わせたように採った形であり、しかも彼らは**強いられて**採ったのだ。だから真相はこうだ：**Wasm の DOM に対する無能は、アーキテクトを自らの誘惑から救い出すガードレールである。** この原理は一般化する価値がある——**プラットフォームの最も価値ある制約は、しばしば「便利そうに見えて長期的に腐る」ことをあなたにさせない制約である。** gRPC が先にスキーマを定義させ、Rust が所有権を考え抜かせ、Wasm が計算と表示の境界を引かせる——この三つの本質は同じである。

## シナリオ 3　システムとアーキテクチャの四つの壁

**壁その四：厳格なサンドボックス——ネイティブなシステムアクセス権がない。**

Wasm には既定でオペレーティングシステムという概念がない。ファイルを読めず、ソケットを作れず、ハードウェアへアクセスできない。ブラウザでは JS がデータを手渡し、バックエンドでは WASI が能力を渡す。そして **WASI の仕様はいまも進化の途上にある**。

- **`wasi_snapshot_preview1`**：事実上の第一世代。POSIX 風のファイルディスクリプタをモデルとする。エコシステムが最も広くツール対応も最良だが、意味論が POSIX と強く結びつきすぎている。
- **WASI 0.2（Preview 2）**：**Component Model** の上に建て直され、**WIT**（Wasm Interface Types）でインタフェースを記述し、世界を `wasi:io`、`wasi:filesystem`、`wasi:sockets`、`wasi:http` といった組み合わせ可能なインタフェース群へ分解した。方向は正しいが、エコシステムの移行はまだ進行中の世代である。
- **実務上の結論**：**今日書いているバックエンド Wasm は、一度移行させられる覚悟をしておくこと。** これは採用コストの一部であり、無視してよいものではない。

**壁その五：メモリ管理が制限されている。**

一続きの線形メモリは拡大しかできず縮小できない。コードの内部でメモリリークが起きても、Wasm は回収してくれない（第 2 章シナリオ 2 参照）。実務上の帰結は二つある。

- **長時間動くタブは単調に太っていく**。解法は「使い終わったらインスタンスごと捨てて再 instantiate する」——Wasm ではこれが日常的な操作として使えるほど安い（マイクロ秒級）。
- **`ArrayBuffer` detach の罠**は、いちばん忙しいときに噛みつく（大量割り当て → grow の発火 → すべてのビューが無効化）。

**壁その六：マルチスレッド対応が完全ではない。**

Wasm 自身にスレッドを生成する能力はない。ブラウザでは **Web Workers + `SharedArrayBuffer`** に頼るしかない（threads 機能は `memory` の `shared` フラグと一組のアトミック命令 `i32.atomic.*`、`memory.atomic.wait/notify` を提供する。詳しくは付録 M §6）。

**そして `SharedArrayBuffer` には血なまぐさい経緯がある**：2018 年に **Spectre / Meltdown** のような投機的実行のサイドチャネル脆弱性が噴出したあと、`SharedArrayBuffer` は高精度タイマを提供できるがゆえに攻撃道具の一部となり、**主要ブラウザすべてで緊急に既定無効化された**。のちに戻されたが、厳しい条件が付いた——**クロスオリジン隔離（cross-origin isolation）**である。

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

この二つの HTTP ヘッダを**サーバ**が返して初めてページは隔離状態に入り、`self.crossOriginIsolated` が `true` になり、`SharedArrayBuffer` が存在するようになる。

**この一条は第 5 章で、本書全体の最も重要な関門になる**——**GitHub Pages は独自の HTTP ヘッダを設定させてくれない**からだ。

**壁その七：同期のコードが、非同期の世界にぶつかる。**

これは四つのシステムの壁のうち最も語られず、しかし移植の途中で最も人を転ばせる一つである。

**問題の形**：移植したい C/C++/Rust のコードは**同期**で書かれている——`read(fd, buf, n)` を呼べば、データが戻るときには `buf` の中にあると期待している。ところが**ブラウザの世界はほぼすべて非同期である**：`fetch()` は Promise を返し、IndexedDB はイベントを返し、OPFS の非同期 API は Promise を返す。**そして Wasm には Promise を「待つ」手段がない**——ブロックできないからだ。ブロックした瞬間、タブ全体が凍る。

**歴史上の三つの解法。後になるほど良い**：

| 解法 | 機構 | 代価 |
|---|---|---|
| **非同期へ書き換える** | 呼び出し連鎖全体をコールバック／状態機械へ書き換える | 数十万行の既存 C コードに対しては**実行不可能** |
| **Asyncify**（Emscripten のバイナリ変換） | Binaryen がモジュール全体を書き換え、呼び出しスタックを手動で線形メモリへ保存し復元する | **使えるが高い**：コードサイズが大きく膨らみ、実行が遅くなり、どの関数が unwind するかの注釈に注意が要る |
| **★ JSPI（JavaScript Promise Integration）** | **エンジンが Wasm のスタックのレベルで中断と再開を行う** | **ネイティブで、書き換えがほぼ不要**——これが正解である |

**JSPI の状態は単独で覚える価値がある**：**2025 年 4 月に Phase 4（標準化）へ入り**、**Chrome 137 と Firefox 139** で出荷済みである。動作はこうだ：**Wasm が Promise を返すインポート関数を呼ぶと、エンジンは Wasm の実行スタック全体を中断する。Promise が解決したら中断地点から再開し、結果を返す**——Wasm 側から見れば、ただの同期呼び出し一回にすぎない。

```javascript
// 概念図：Promise を返す JS 関数を、Wasm から見た同期インポートへ包む
const asyncImport = new WebAssembly.Suspending(async (url) => {
  const res = await fetch(url);           // 非同期の世界
  return new Uint8Array(await res.arrayBuffer());
});
// エクスポートした入口は Promising で包み、JS に対して async として見せる
const run = WebAssembly.promising(instance.exports.main);
await run();
```

**これは第 5 章、第 7 章、付録 L に共通する袋小路に穴を開けた**：OPFS の非同期 API、`fetch`、IndexedDB は、**もはや「Worker へ移して同期ハンドルを使う」か「Asyncify で書き換える」かをしなければ同期の C コードから使えない、ということはなくなった。**

**ただし万能薬とみなしてはいけない。但し書きが三つある**：**（一）** 中断と再開は無料ではなく、高頻度の呼び出しではオーバーヘッドが無視できない——**「たまに一度 I/O を待つ」には向くが、ホットループに置くべきではない**。**（二）** 対応状況の検出と縮退経路はいまも必要である。**（三）** **それが解決するのは「待つこと」であって「並列」ではない**——スレッドは依然として一本しかない。

> 💡 座右の一言
> **セキュリティ脆弱性の本当のコストは、修正の工数であることはめったになく、エコシステム全体に残す恒久的な税である。** Spectre の修正は CPU マイクロコードとコンパイラのレベルではとうに完了した。しかしそれが残した税——**マルチスレッドを使いたいすべてのウェブページが「クロスオリジン隔離」という重い配備コストを払わねばならず、隔離は連鎖的にサードパーティ iframe、広告、埋め込み動画、CDN リソースを壊す**——は、Web エコシステム全体が十数年にわたって納め続ける。この法則にはセキュリティ分野の残酷な帰結がある：**脆弱性の深刻度を評価するとき、問うべきは「どれだけの損害を与えうるか」ではなく、「それを防ぐために、世界はこれから十年でどれだけの不便を払うのか」である。** 前者は一度きりで、後者は複利で効く。

## シナリオ 4　開発とエコシステムの二つの壁

**壁その八：デバッグが極度に難しい。**

Wasm がクラッシュしたとき、ブラウザのコンソールがくれるのはたいてい `RuntimeError: memory access out of bounds` と、`wasm-function[1234]` の羅列だけである。

- **なぜ難しいのか**：コンパイルが型も変数名もソースの構造もすべて消し去っている。スタックには関数の添字しかなく、名前がない。
- **できること**（多くの人が思うより多い）：
  - **`name` カスタムセクションを残す**：これは関数名を置くために Wasm 仕様が用意したカスタムセクションである。コンパイル時に何も考えず `--strip-all` せず、これを残せばスタックトレースが人の言葉になる。
  - **DWARF デバッグ情報**：Emscripten も Rust も Wasm 内に DWARF を埋め込める。Chrome DevTools の **C/C++ DevTools Support (DWARF)** 拡張と組み合わせれば、ブラウザの中で **C++ のソースを見て、ブレークポイントを張り、変数の値を見る**ことができる。ここ数年で最も過小評価された体験改善である。
  - **`wasm2wat` / `wasm-objdump`**（WABT ツール群）：バイナリを読めるテキスト形式へ戻し、命令を一条ずつ確かめる。
  - **Emscripten の Sanitizer**：`-fsanitize=address`、`-fsanitize=undefined` は Wasm 上で使え、線形メモリ内部の境界外アクセスと未定義動作を捕まえられる——**これは「Wasm のサンドボックス内に ASLR/canary がない」ことを補う最も実際的な手段である**。
  - **`console.log` 派**：Emscripten の `EM_ASM` と Rust の `web_sys::console::log_1` は、いつでも使え、いつでも効く。
- **しかし本番は別の話である**：リリース時には `strip = true`（第 9 章参照）を付けるが、それはまさにデバッグ情報を全部取り去る。**シンボル付きのビルド成果物を一部保管し、ソースマップかシンボルサーバで対応づけねばならない**——このことは Wasm エコシステムでは、ネイティブの世界ほど成熟していない。

**壁その九：どの言語でもコンパイルすれば割に合う、とは限らない。**

- **GC を持たない言語（Rust、C/C++、Zig）**：Wasm とは完璧な組み合わせである。
- **重い実行環境を持つ言語（Java、Python、Wasm 上の JavaScript）**：Wasm へコンパイルしたあとの実行性能は**期待を下回ることが多く、ネイティブ環境で直接実行するより遅いことさえある**。理由は直截だ。仮想機械の中でもう一つの仮想機械を走らせる（インタプリタのインタプリタ）ことになり、抽象が二層重なる。QuickJS を Wasm へコンパイルして JS を実行すると、ブラウザ native の V8 より 10〜20 倍遅い。これは予見できる物理的帰結であって、実装の欠陥ではない。
- **Wasm GC が変えたもの**：Kotlin、Dart、Java、Scheme のような言語が、自前の GC を同梱せずに**ホストエンジン既存の、極限まで最適化されたガベージコレクタを直接使える**ようになった。これはサイズに対して桁違いの改善であり、性能にも実質的な効果がある——ただしエンジンの対応が要り、すでに大量の `i32` ポインタ式コードを抱える既存プロジェクトへの恩恵は限られる。

> 💡 座右の一言
> **技術の成熟度を測る最も正確な指標は、それがどれだけ速く走るかではなく、壊れたときにどれだけ調べやすいかである。** 技術の性能はベンチマークで測ってスライドに書ける。しかし「午前三時に本番が落ちたとき、その一行にどれだけ速くたどり着けるか」という指標は、どの技術選定比較表にも現れないのに、三年後にチームがうまくやっているかを決める変数である。Wasm の性能の物語は十年語られてきたが、可観測性の物語は語られはじめたばかりだ——**これこそ、それが今日「一つのチームが所有する、境界の明快な計算カーネル」に向き、「アプリケーション全体の本体」に向かない本当の理由である。** 選定のときに一言多く問うてほしい：**これが事故を起こしたとき、私の手には何が残るのか。**

## 本章のまとめ

- 四つの長所にはそれぞれ隠れた但し書きがある：**性能優位には計算量の閾値がある**、**サンドボックスが守るのはホストであってあなたのプログラムではない**、**言語非依存の分水嶺は実行環境の負担である**、**「軽量」の結論は対照群で反転する**（Docker と比べれば軽く、`<script>` と比べれば重い）。
- ブラウザ側の三つの壁（一〜三）：**DOM に触れない**（核心仕様にオブジェクト／文字列型がないため）、**境界越えのデータコストが高い**（文字列一往復 = 符号化・復号二回 + コピー二回）、**サイズが暴れやすい**（重い実行環境の言語 + 静的リンク）。
- **「DOM に触れない」は実質的にガードレールである**。それが Figma/Photoshop Web の「Wasm が計算し、JS が描く」という健全なアーキテクチャを引き出した（シナリオ 2 の 🔍 参照）。
- システム側の四つの壁：**WASI はいまも preview1 → 0.2 の移行中**（今日書くバックエンド Wasm は一度移行させられる覚悟が要る）、**線形メモリは伸びるだけで縮まない**、**マルチスレッドは `SharedArrayBuffer` に頼るしかなく、それは Spectre の余波でクロスオリジン隔離という枷に繋がれた**、**同期のコードが非同期の世界にぶつかる**。
- 四つ目の壁の正解は **JSPI**（2025-04 標準化、Chrome 137 / Firefox 139 で出荷）である：**エンジンがスタックのレベルで Wasm を中断・再開し**、同期の C コードが Promise を返す Web API を直接使えるようにする。高価な Asyncify のバイナリ変換に取って代わる。ただし**解決するのは「待つこと」であって「並列」ではなく**、ホットループに置くべきではない。
- 開発側の二つの壁（八、九）：**デバッグが難しい**（ただし `name` セクション、DWARF + Chrome 拡張、`wasm2wat`、Sanitizer は実際に使える解法であり、「console.log しかない」という印象よりずっと良い）、**重い実行環境の言語を Wasm へコンパイルするのはしばしば割に合わない**（仮想機械の中で仮想機械を走らせる）。
- あのクロスオリジン隔離の制約は、次の部で本書最大の関門になる——**無料の静的ホスティングこそ、HTTP ヘッダを設定させてくれないからだ。**

制約の棚卸しは終わった。しかし自分の制約を知るだけでは足りない。次の問いはこうだ：**同じ場面において、私の本当の代替案は誰か。それは何を武器に私に勝ち、どこで負けるのか。** 第 4 章へ。
