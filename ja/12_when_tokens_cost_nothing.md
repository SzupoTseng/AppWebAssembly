# 第12章：トークンがほぼゼロになったとき——車輪を自作する時間の罠と、終局のアーキテクチャ

> **「あらゆるアプリが LLM で自作・模倣できるなら、濠はどう持続するのか？」**
> **「誰も金を払いたがらず、みんな自分で車輪を作り直す。しかしトークンの費用が十分に安ければ、自作にかかるのは時間だけだ。」**
> この二つの問いは、ソフトウェア工学界とベンチャーキャピタル界の最も中核的な集団的不安を直撃している：**「コードを書く」限界費用がゼロになれば、あらゆるソフトウェアの機能は LLM の前で希少でなくなる。**
> そして第二の文の推論は正しい——**ただ、「時間」という語に隠れた二つの勘定を落としているだけである。**

## シナリオ 1　「コードが無料」になったあとも立っていられる五つの防衛線

**背景**：従来の「技術の濠」と「製品機能の濠」が完全に崩れるとすれば、「全自動のソフトウェア複製」の時代に、企業はどう新しい濠を築くのか。いま見えている答えは以下の五つである。

### 一、データの引力と状態の独占（Data Gravity & State Monopoly）

**LLM はコードを瞬時に複製できる。しかしユーザの蓄積したデータと関係の鎖は複製できない。**

- **コードは流れ、データは粘る**：AI は Figma もどきのレンダリングエンジンを一万個作れるが、あなたの会社が過去五年に積み上げた数百万の UI コンポーネント、デザインシステム、修正のたびのバージョン履歴、部門をまたぐ承認コメントは、**すべてオリジナルのクラウドデータベースの中にある。**
- **最終の防衛線**：企業が買っているのはあの Wasm の描画の計算力ではなく、「**データの連続性と単一の真実の源（single source of truth）**」である。データが多いほど周辺のアプリケーションを引きつける引力が強くなる——**AI がコードを一片複製したくらいで持ち去れるものでは断じてない。**

**技術的に正直な一言を足しておく**：データの引力の強さは**データの可搬性に反比例する**。データ形式が開かれ、完全なエクスポート API があり、第三者がインポートできるなら、引力は弱い。専有形式で、エクスポートに劣化があり、第二の行き先がないなら、引力は強い。**だから実務における「データの引力」は、その大部分が「形式と API の設計選択」の結果であって、データ量そのものの自然な帰結ではない。** この点は作る側にも買う側にも等しく重要である。

### 二、ワークフローの固着と組織の協働ネットワーク

現代の企業においてソフトウェアが担う役割は、本質的に「**組織内部のコミュニケーションのプロトコル**」である。

- **機能は複製しやすく、習慣は移しにくい**：一万人規模の会社では、PM からデザイナー、フロントエンドエンジニア、QA まで、全員があるソフトを軸に密で直感的な部門横断のワークフローを築いている。
- **信頼と協働の境界**：ソフトの入れ替えは URL を変えるほど簡単ではない。会社全体の管理コストを動員し、従業員を再教育し、情報セキュリティの審査を通り直さねばならない。

> **LLM はより完璧なギターを一本作れる。しかし息の合ったオーケストラを無から生み出すことはできない。**

### 三、物理世界のハードウェアへの錨と帯域のコスト

LLM があらゆるソフトを自作できる世界では、計算力や帯域といった「物理的な実在資源」はより高価になる。

- AI が超強力な非中央集権 P2P 協調システムを書いてくれたとしても、**百万規模の並行、国をまたぐデータセンター間の低遅延同期、巨大ファイルの保存、DDoS 防御**を処理するには、背後に実在するクラウドのハードウェア基盤と莫大な電気代・帯域コストが要る。
- **これらの実在資源の濠は、純粋なソフトウェアの AI がコードで無から生み出せるものではない。**

**この一条は AI の時代に重みが下がるどころか上がっている**——ソフトが安くなれば、残る希少性はすべて「ソフトでは複製できないもの」へ集まるからだ：電力、土地、光ファイバ、GPU の生産能力、そしてそれらを確保する長期契約。

### 四、企業級のコンプライアンス、責任の裏書き、信頼のプレミアム

これは B2B 市場における絶対的な物理法則である。大企業（金融、医療、多国籍テクノロジー企業）がソフトを調達するとき、第一の要素は「機能がどれだけ安いか」であったことは一度もなく、「**コンプライアンスと誰がリスクを負うか**」である。

- **誰が責任を負うのか（accountability）**：LLM が自動生成した模倣版アプリが、境界条件のバグでデータを流出させたら、あるいは真夜中に大規模障害を起こして企業に百万ドルの損失を出したら、**誰が責任を負うのか。**
- **産業級の障壁**：SOC 2 Type II のセキュリティ認証、ISO 27001、99.99% の SLA 保証、そして呼べば来る専門のカスタマーサクセスのエンジニアチーム——**これこそ企業が高額の購読料を払う本当の理由である。企業が買っているのは「何かあったとき、責任を負って賠償できる誰かがいる」という信頼のプレミアムである。**

### 五、プラグインと AI エージェントの双方向エコシステム

コードが見られ、自由に複製されるとき、濠は「ソフトウェアそのもの」から「**ソフトウェアの周りに築かれた動的なエコシステム**」へ移る。

- **App Store の論理の再演**：AI が本体を複製しても、プラグイン市場は空である。
- **エージェント的な固着（agentic lock-in）**：これからの時代、さまざまな自律 AI エージェントがプラットフォームを横断してタスクを実行するために送り出される。**もしあるプラットフォームが業界全体の AI エージェントが既定で接続する「標準 API とデータ形式」になったなら、LLM が模倣した他のソフトは、その AI エコシステムの上流と下流に繋がっていないがゆえに、誰も訪れないデジタルの孤島に落ちる。**

**第五は最も新しく、最も注目に値する一条である**：AI の時代には「**あなたの API は AI エージェントの既定の選択肢か**」がまったく新しい競争の軸になる——2010 年代に「あなたのアプリは App Store に入っているか」がそうだったように。

### すでに三十年走っている対照実験

**この五つの防衛線はどれももっともらしく聞こえるが、どれにも欠けているものがある：時間による検証である。** 「コードが無料になれば価値はデータとコミュニティへ移る」が慰めの言葉でないと、どうして分かるのか。

**それに答えられる標本があり、しかもすでに三十年走り続けている。**

一九九〇年代の中国語圏の MUD——LPC で書かれたテキストの武侠世界——**その全ソースコードは初日から完全にダウンロード可能だった。** 世界地図、NPC の対話、武術のシステム、経済の規則、部屋一つひとつの描写。すべてが mudlib というディレクトリの中にある。当時は圧縮ファイルを配って回り、今日は `git clone` で、そしていまや**ドライバまるごとが WebAssembly へコンパイルされ、ブラウザで直接開ける**（付録 L 参照）。

**秘匿はゼロ、複製コストはゼロ、改変の障壁は極めて低い。** 「コードは資産である」という古い論理に従えば、この種のものはとうによりよい複製品に飲み込まれていたはずである。

**しかしそうならなかった。** それらは三十年生き、原作者が去ったあとも繰り返し分岐し、改変され、再び開かれた。そして今日もなお、誰かが二百件の壊れたアーカイブを修復し、一つずつ文字コードを変換し、バグを直し、変更を一箇所ずつ記録するために膨大な労力を注いでいる——**ただ、それらがもう一度開けるようにするためだけに。**

**これこそ、あの五つの防衛線の実測結果である**：ユーザが求めていたのは「動くコードの一部」であったことは一度もなく、**あの世界と、その世界にいる人々**である。そしてその二つは `git clone` では持ち去れず、LLM にも生み出せない。

> 💡 座右の一言
> **ある資源の生産コストがゼロになるとき、価値は消えない。「その資源と補完的な希少品」へ移る。** 印刷術が文字の複製コストをゼロにし、価値は「本を所有すること」から「著者の評判」と「編集者の選別」へ移った。ストリーミングが音楽の複製コストをゼロにし、価値は「レコード」から「ライブ」と「アーティストその人」へ移った。いま LLM がコードの生産コストをゼロにし、価値は「ソフトウェア」から**データ、関係、責任、エコシステム**へ移りつつある——この四つの共通点は、**どれも複製できないことである。そもそも情報ではなく、関係だからだ。** だから、ある技術が「X を無料にする」と謳うたび、最も価値のある問いは「では X の商売はどうなるのか」ではなく——**X と補完的で、しかも一緒に安くならなかったものは何か**、である。その答えのある場所が、新しい価値の中心である。

## シナリオ 2　時間の罠：必要なのは「作る時間」ではなく「デバッグの機会費用」である

**背景**：あの追撃は的確だった——「トークンの費用が十分に安ければ、自作にかかるのは時間だけだ」。**この推論は AI 時代のソフトウェアのコモディティ化の中核的な物理的本質を、完全に射抜いている。**

**LLM が十万行の高性能コード（複雑な Wasm の行列演算とデータベースを含む）を書くのに、五分とトークン一ドル分しかかからないかもしれない。**

**しかしソフトウェア工学の最も硬派な法則はこうだ：コードを書くのは時間の 20%、デバッグと境界条件（edge cases）が 80% である。**

**この道は二つの高い壁にぶつかる**：

### 第一の壁：あの 5% の極端な場面

- **車輪が回っているとき**：AI があなたのために形づくった専用のデザインソフトや ERP は、95% の通常の場面で完璧に走る。
- **物理の壁にぶつかるとき**：96% 目の極端な場面——**たとえばブラウザが OS の更新によって OPFS のストレージ割当を突然変更したり、多人数接続時にきわめて稀な分散状態の衝突が発生したり**——であなたの専用の車輪が突然固まる。
- **見えない代価**：このときあなたは自分で、あるいは AI に命じて、その十万行を洗い直さねばならない。この過程が消費する**集中力、気力、そして時間の機会費用**（本来なら商談に、家族との時間に、中核事業の開発に使えたはずの時間）は、即座に、原メーカーへ毎月数十ドル払って「買って悩みを消す」購読料をはるかに超える。

**ここには、より精確な分析を一段足す価値がある。本章で最も実用的な部分だからだ**：

**AI が車輪を作るとき、コスト構造に決定的な変形が起きる**——

```
従来の開発：
  コードを書くコスト  ████████░░  高い（エンジニアが要る）
  デバッグのコスト    ████████░░  高い（エンジニアが要る）
  → 同じ桁なので、チームは自然に「書く」と「直す」のあいだで釣り合いを取る

AI 支援の開発：
  コードを書くコスト  ░░░░░░░░░░  ほぼゼロ
  デバッグのコスト    ████████░░  高い（システムを理解する人が依然として要る）
  → 差が数桁に達する
  → 結果：コードが産出される速度が「コードが理解される」速度をはるかに超える
  → そこで「誰も本当には読み解いていないコード」が前例のない速さで積み上がる
```

**この変形の帰結は「開発が速くなった」ではなく、「理解されていないコードベースの増加率が速くなった」である。** そしてシステムの保守性は、前者ではなく後者に依存する。

### 第二の壁：システムの保守エントロピー増大

**ソフトウェアは石ではない。生きた有機体である。** オペレーティングシステムは更新され、ブラウザは API の仕様を変える（WebGPU や Wasm のマルチスレッドに対する安全性の制約は、いまも絶えず動いている）。

- **車輪を作った翌日**：あなたは極めて安いトークンで完璧な ERP を作り上げた。
- **二年後の災難**：W3C が、あなたの車輪が強く依存していた低水準 API を廃止した。あなたの車輪が顧客の目の前で崩れる。
- **エントロピーの爆発**：あなたはあのとき LLM で一発生成した。**あなたも従業員も、この十万行の基盤アーキテクチャを本当には誰一人読み解いていない。** あなたは LLM に「二年前の古い車輪」を理解し直させねばならず、あるいは全部を打ち壊して作り直すはめになる。

**この長期の保守の技術的負債とライフサイクルのコストこそ、自作派が最も見落としやすい巨大な盲点である。**

**第 5〜8 章の具体的な技術を例にすると、より生々しくなる**：

| あなたの車輪が依存しているもの | 二年でどう変わりうるか |
|---|---|
| `SharedArrayBuffer` + COOP/COEP | 隔離の要求が厳しくなりうる。`coi-serviceworker` が依拠する挙動の推論が仕様で明確化されたり狭められたりしうる（第 5 章の 🔍 参照） |
| OPFS の `createSyncAccessHandle` | 割当のポリシー、追い出しの戦略、タブ横断のロックの意味論、どれも変わりうる |
| `wasi_snapshot_preview1` | **すでに WASI 0.2 に置き換えられつつある**——これは仮定ではなく、いま起きていることである |
| Emscripten の MEMFS/IDBFS | 公式の方向はすでに WasmFS へ移っている |
| 特定の Wasm 提案（GC、EH、tail call） | 標準化の過程で意味論が何度も調整された |

**誰も読み解いていない十万行のシステムが、この五つのどれか一つにぶつかれば、「AI にプロジェクト全体を理解し直させる」重量級の作業になる。** しかも毎回あなたは、AI が今回も前回と同じくらいよく理解してくれることに賭けている。

> 🔍 踏み込んだ論評──「車輪作りが安くなる」が本当に変えるのは、総量ではなく規模の分布である
> この節はもう一歩先へ進める価値がある。これからの十年のソフトウェア産業の形を予測するからだ。**車輪を作るコストが「エンジニア三人で半年」から「一人で一日の午後」へ落ちるとき、変わるのは「車輪を作る人がいるかどうか」ではなく、「どの大きさの車輪が作る価値を持つか」である。** かつては、自分しか使わないツール（個人の家計簿、私用の CRM、五人のチームのシフト表）は開発する価値がなかった——固定費が見返りを上回っていたからだ。いまはある。**そこで市場は二つに裂ける：一方は「小さすぎて買う価値はないが、いまや自作する価値がある」ロングテール、もう一方は「大きすぎて自作できず、買うしかない」中核システムである。そして中間の層——凡庸で、単機能で、軽量な SaaS のツール——は完全に消滅する。** 実務家への含意は具体的である：**あなたの製品が、一人が一日の午後に AI で九割を再現できるものなら、あなたは消滅する層にいる。** そして唯一の出口は製品をより複雑にすること（複雑さも複製できる）ではなく、両端のどちらかへ動くことである——**ロングテールへ降りて「他人が車輪を作るのを助ける道具」を作るか、規模とデータと責任とエコシステムがなければ動かない中核システムへ昇るか。** 中間地帯は消えつつあり、その速さはトークン価格の下がる速さが決めている。

## シナリオ 3　終局の時代における二つの濠の形態

**背景**：「自分で車輪を作る」ことがこれほど安くなれば、ビジネスモデルは必然的に二つの究極の形態へ向かう。

### 形態その一：保険と裏書きを買う（The Insurance Model）

**これは、ソフトを自作する能力に事欠かないテクノロジーの巨人たちが、それでも外部の SaaS を大量に調達する理由でもある。**

企業はソフトに金を払いたくないが、**「壊れたら誰かが賠償し、誰かが十五分以内に徹夜で直す」というサービスレベル合意（SLA）には、極めて喜んで金を払う。**

**商業の世界で Figma や大手 ERP ベンダに払うことは、本質的に機能を買うことではなく、「リスクの外注」という保険を買うことである。**

**この一条は AI の時代にむしろ強まる。理由は直截だ**：AI が生成したシステムが増えるほど、「これが壊れたとき誰が責任を負うのか」は答えのない問いになる。**そして答えのない問いは、答えを持つベンダをより価値あるものにする。**

### 形態その二：標準プロトコルと相互運用性（The Protocol Standard）

各社が LLM で自社専用の ERP やデザインソフトを仕立てるなら、二社が協業し、注文を連携し、同じ製品を共同で設計する必要が生じたとき、データ形式も API も完全に異なる「自作の車輪」同士は、深刻な「**デジタルのバベルの塔**」の危機に直面する。

**このとき、世界共通の「標準データプロトコルとエコシステムのバス」を定義できた者が、AI に複製できない究極の濠を握る。**

**この一条には強い歴史的な類比がある**：デスクトップパブリッシングのツールが百花繚乱だったとき、真の勝者は最も使いやすい組版ソフトではなく **PDF** だった。インスタントメッセージのアプリが至るところにあったとき、企業間の相互運用を支えたのは **SMTP/email** だった。**プロトコルの価値は「全員が同意していること」から来る。そして「全員が同意していること」は AI が生成できないものである——時間が要り、調整が要り、多方面の既得権益の絡み合いが要る。**

### 未来は二種類の人へ分化する

| | 個人と小さなチーム | 現代の産業と大企業 |
|---|---|---|
| 行動 | 極めて安いトークンを全面的に使い、完全に自分のものである高度にカスタマイズされた「極小の車輪」を狂ったように作る（オーダーメイドの家計簿、極小の CRM、専用ツール） | 依然としてトップベンダに金を払う |
| 理由 | カスタマイズの価値 > 保守コスト（規模が小さく、要求が安定し、壊れたら自分で直す） | **時間を自社の中核の印刷機である事業へ注ぎ、車輪を作り直す技術的エントロピーを外注することが、全体の投資対効果（ROI）で最も高い黄金の判断である** |
| 帰結 | **凡庸で単機能な軽量ソフトウェア企業を完全に消滅させる** | トップベンダへの集中度が上がる |

> 💡 座右の一言
> **「自分でできる」と「自分でやるべきだ」のあいだには、ライフサイクル一つ分のコストが横たわっている。** この一文は AI の時代に前例のないほど重要になった。AI は「できる」までの距離を極端に縮めたのに、「やるべきだ」までの距離をほとんど縮めていないからだ——**保守、更新、デバッグ、結果を負うこと。この四つのコストは、トークンと一緒には下がらなかった。** そこで危険な認識のずれが生じる：**車輪を作る障壁は崩れ、車輪を養う障壁は崩れていない。そして大半の人は、最初の障壁が崩れた瞬間に決定を下す。** 自分が作るべきかどうかには、単純な検査が一つある：**「三年後、これが真夜中に壊れたとき、誰が直すのか。その人はまだ会社にいるのか」と問え。** この問いに明快な答えがないなら、あなたが作ったのは車輪ではなく、負債である。

## シナリオ 4　終局のアーキテクチャ：「保守不要、サーバコストゼロ、極限の性能」の専用エンジン

**背景**：結論が「小さなチームは自分の車輪を作る」なら、その車輪を設計してしまおう——**トークンの限界費用がゼロになった時代に、最も戦えて、最も技術的負債を生みにくい次世代の極小高性能 Wasm 専用アプリケーションの設計図である。**

**中核の思想**：**「保守コストの高い」下層の部品を完全にコモディティ化・標準化し、「計算力が高く、プライバシーが高く、高度にカスタマイズされた」業務の中核を、Wasm でフロントエンドへがっちり溶接すること。**

### 三つの防御的アーキテクチャ原則

自作の車輪が二年後にブラウザの更新や技術的エントロピーで崩れないよう、守るべき三つの鉄則がある。

**原則その一：ホスト環境への依存ゼロ（Host-Agnostic Isolation）**

Wasm のコードを特定の JavaScript フロントエンドフレームワーク（React や Vue の特定バージョン）へ深く縛りつけないこと。Wasm の内部は標準的な ANSI C++ か純粋な Rust のロジックを保ち、**標準のバイナリ Web API（Canvas 2D/WebGL、OPFS）だけを通じてハードウェアと接すること。**

> **こうすれば、将来 JavaScript のフレームワークがどう変わろうと、あなたの Wasm の中核の車輪は決して壊れない。**

**この原則の技術的根拠**：Web プラットフォームの**標準 API はきわめて強い後方互換の約束を持つ**（「Web を壊すな」はブラウザベンダの第一の工学原則である）が、**フレームワークは持たない**。React 18 → 19 の破壊的変更は、Canvas API の十年間の変化より多い。**中核を標準に縛り、外殻をフレームワークに縛り、外殻を安く書き直せるようにせよ。**

**原則その二：型付きデータプロトコル（Structured Protocol Buffers）**

Wasm と外部との通信には、柔軟だが形式が崩れやすい JSON を一切使わないこと。**Protocol Buffers か FlatBuffers** をデータ直列化のプロトコルとして全面採用すること。

**これにより、あとで LLM にフロントやバックエンドの部品をどう改変させても、データ通信の「デジタルのバベルの塔」のプロトコルは永久に固定され、決して衝突しない。**

**技術的な理由を二つ補う**（安定性以外に）：

- **FlatBuffers はゼロコピー読み取りに対応している**——逆直列化なしでフィールドを直接読める。これは第 2 章の「境界は料金所」という最適化の方向にちょうど対応する。
- **スキーマは機械可読な契約である**——これは AI の時代に新しい価値を持つ：**LLM に片側の改変を命じるとき、スキーマは彼が自由に振る舞えない唯一の場所であり**、つまりあなたの手にある最も有効な制約の道具である。

**原則その三：状態を持たない計算の窓（Stateless Compute Window）**

Wasm 仮想機械を純粋な「ブラックボックスのプロセッサ」として扱うこと。データを OPFS から読み込み、Wasm のメモリ内で高速に計算・描画し、終わったら即座に状態をディスクへ書き戻してメモリを空にする。

**これは wasm32 が生まれつき抱える 4 GB のメモリ溢れ（OOM）という致命的な盲点を完璧に防ぐ**（第 8 章参照）。しかも Wasm のインスタンス化は極めて安い（マイクロ秒級）ので、**「終わったらインスタンスごと捨てる」は Wasm では日常的に使える手段であり**、最後の救済策ではない。

### 四層の中核トポロジー

```
┌─ 第 1 層：インタフェースとイベントの調停（純粋な HTML5 / JS）──────────┐
│  職責：マウスのクリック、キーボードの入力、そして基本的な DOM の配置だけ  │
│  鉄則：この層に中核の計算アルゴリズムを含めてはならない                  │
│        これはただの「表示パネル（Display Panel）」である                 │
│  → この層は消耗品であり、三年ごとに LLM が流行のフレームワークで         │
│    書き直すことを許す                                                  │
└──────────────────────────┬─────────────────────────────────────────────┘
                           │ postMessage + Transferable Objects
                           │ （メモリの所有権の移転。ゼロコピー）
┌─ 第 2 層：独立スレッドの非同期バス（Web Worker）────────────────────┐
│  職責：専用の Worker を起動し、Wasm のストレージと計算の中核一式を       │
│        その中へ読み込み、UI のメインスレッドと徹底的に隔離する           │
│  中核の最適化：postMessage(buffer, [buffer]) で transfer を明示的に有効化 │
│              → OS レベルのメモリ所有権の移転。オーバーヘッドはほぼゼロ   │
│  付随する利得：createSyncAccessHandle はそもそも Worker 内でしか使えない  │
└──────────────────────────┬─────────────────────────────────────────────┘
                           │
┌─ 第 3 層：業務中核の Wasm エンジン（Rust / C++）────────────────────┐
│  職責：専用の車輪の硬派な機能を実行する                                 │
│        （財務 ERP の集計行列、3D 幾何の軌道計画、全文検索……）           │
│  防御：opt-level = 3, lto = true, strip = true                          │
│       ダウンロードされても、逆解析する商業的価値がまったくない           │
│  → この層は資産であり、設計目標は十年不動である                         │
└──────────────────────────┬─────────────────────────────────────────────┘
                           │ FileSystemSyncAccessHandle
┌─ 第 4 層：高性能な永続化ストレージ（OPFS Sync API）─────────────────┐
│  職責：Worker 専用の createSyncAccessHandle() を使う                    │
│  最適化：Wasm がローカルの C プログラムと同じように、完全に同期で        │
│         Promise のオーバーヘッドがゼロの高速ディスク I/O を行い、        │
│         分割スライディングウィンドウのランダムな読み書きをする           │
│         → 4 GB のメモリ限界を完全に打ち抜く                             │
└────────────────────────────────────────────────────────────────────────┘
```

**このアーキテクチャの最も重要な性質は、図には表れない**：それはシステムを**「消耗品」と「資産」の二層**に分けている。

- 第 1 層は消耗品である：流行のフレームワークへがっちり溶接され、**設計目標そのものが「安く捨てて書き直せること」である。**
- 第 3・4 層は資産である：標準 API とバイナリのプロトコルだけに依存し、**設計目標は十年不動である。**
- 第 2 層は防火壁である：`postMessage` と型付きプロトコルで両者を隔て、**消耗品の腐敗が資産へ広がらないことを保証する。**

**これこそ「保守エントロピーの増大」に対抗する唯一有効な構造である**——すべてを腐らせないのではなく（不可能である）、**腐敗を、あなたが捨ててよい層の中に閉じ込めるのだ。**

**AI エージェント向けの完全な仕様書テンプレート**（そのまま使える。**付録 H** 参照）：本章のアーキテクチャの設計図は、Claude Code や他のコーディングエージェントへそのまま貼れるシステム仕様書としてまとめてある。依存関係の設定、中核の実装、Worker の隔離、ベンチマークの四段階の完全な指示と、三種類のストレージ機構（OPFS / IndexedDB / WASI）専用の調整指示を含む。

> 💡 座右の一言
> **腐敗に対抗する正しい方法は、すべての部分を堅固にすることではなく、どの部分が「腐ってよいか」を決めることである。** すべての部品を十年不変に設計したシステムは、変化に適応できず三年目に丸ごと償却される。すべての部品が流行に付き従うシステムは、二年目に終わりのない移行へ沈む。長く生きるシステムには例外なく明快な分界線がある：**中核は最も保守的で、最も標準的で、最も退屈な技術で書き、外殻は最も便利で、最も流行していて、最も人を集めやすい技術で書き、そのあいだに、間違えようがないほど狭いインタフェースを置く。** Unix のファイルディスクリプタ、ブラウザの DOM、データベースの SQL、ネットワークの IP——三十年以上生きてきたものはどれも、この形をしている。**長く生きるものを設計するときは、コードを書き始める前に、まずその線を引け。**

## 本章のまとめ

- **「コードが無料」になったあとも立っていられる五つの防衛線**：データの引力と状態の独占、ワークフローの固着と組織の協働、物理的なハードウェアと帯域への錨、コンプライアンスと責任の裏書き、プラグインと AI エージェントのエコシステム。
- 正直な補足：**データの引力の強さはデータの可搬性に反比例する**——それは大部分が「形式と API の設計選択」の結果であり、データ量の自然な帰結ではない。
- **「車輪作りにかかるのは時間だけ」という推論は正しいが、二つの勘定を落としている**：**時間の罠**（書くのが 20%、デバッグが 80% であり、AI は前者だけをゼロにした）と**保守エントロピーの増大**（W3C が API を一つ廃止し、しかも誰もあの十万行を本当には読み解いていない）。
- AI 支援の開発が起こす本当の変形は「開発が速くなった」ではなく——**コードが産出される速度が理解される速度をはるかに超え、そこで「誰も本当には読み解いていないコード」が前例のない速さで積み上がること**である。
- **市場は二つに裂ける**：ロングテール（小さすぎて買う価値はないが、いまや自作する価値がある）と中核（大きすぎて自作できず、買うしかない）。そして**中間の凡庸な軽量 SaaS の層は消滅する**。出口は両端のどちらかへ動くことである（シナリオ 2 の 🔍 参照）。
- 終局の二つの濠の形態：**保険を買うこと（SLA と責任追及）** と **標準プロトコル（PDF や SMTP の位置）**——後者の価値は「全員が同意していること」から来ており、それは AI が生成できない。
- **終局アーキテクチャの三つの鉄則**：ホスト環境への依存ゼロ（標準に縛り、フレームワークに縛らない）、型付きデータプロトコル（Protobuf/FlatBuffers。スキーマは LLM を制約する最も有効な道具である）、状態を持たない計算の窓（終わったらインスタンスごと捨てる）。
- 四層トポロジーの最も重要な性質は図に表れない：**システムを「消耗品」と「資産」の二層に分け、狭いインタフェースで隔てていること**である。腐敗に対抗する方法はすべてを堅固にすることではなく、**腐敗を、あなたが捨ててよい層の中に閉じ込めることである。**

## 全書の終章：あの午後三時四十分へ戻る

あの対話は「WebAssembly の発展史を詳しく」から始まり、一時間あまりのあとに「計画してほしい」の二語で止まった。そのあいだに百二十の事例があり、四層のストレージアーキテクチャがあり、4 GB の天井があり、「全部見られているのでは」という追撃があり、AI 時代の濠についての思考があった。

**この旅全体を一文へ圧縮するなら、その一文はこうだ**：

> **ダウンロードできるものは、いずれ複製される。持ち去れないものだけが、濠になる。**

そしてこの一文の最良の証拠はシリコンバレーにではなく、一九九〇年代の中国語圏のテキストゲームの中にある——**そのソースは三十年間まるごと複製され続け、それでもいまだにそこにある**（付録 L 参照）。

Wasm はきわめて優れた技術である——計算を安全に、安価に、際限なく、世界中のあらゆるコンピュータの端へ押し出した。**そしてあまりにも成功したがゆえに、それは同時に、半世紀続いた「コードは資産である」という前提を破壊した。**

だからこの本の本当の結論は技術のリストではなく、三つの問いである。**何かを作り始める前に、自分に問うてほしい**：

1. **この計算は「重く、公開されていて、機密がない」ものか？** そうなら Wasm へコンパイルしてクライアントへ押し出せ。浮いた金はそのまま利益である。
2. **これが一字一句公開されたあと、私には何が残るのか？** 何も残らないなら、それはクライアントに置くべきではない。データ、関係、責任、エコシステムが残るなら、クライアントは好きなだけ見ればよい。
3. **三年後、これが真夜中に壊れたとき、誰が直すのか？** この問いに明快な答えが出るまで、あなたが作ったのは車輪ではなく、負債である。

**第二の問いのもっと厳しい版が欲しいなら**、あの mudlib たちがすでに答えた形へ置き換えればいい。

> **もし私のソースコードが明日すべて公開されたら、三十年後もまだ誰かがそれを使っているだろうか？**

ガレージの灯りはもう消してよい。**あなたはいま知っている。あの機械がどう回り、どこで走れ、そして走り出したあと、価値がいったい誰の手に残ったのかを。**
