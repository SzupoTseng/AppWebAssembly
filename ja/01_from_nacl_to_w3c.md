# 第一部：起源と物理

# 第1章：NaCl から W3C へ——失敗したプラグインは、いかにして Web の第四の言語になったか

> 二〇一一年、Google は Chrome に **Native Client** というものを押し込み、ブラウザ内でネイティブの C/C++ を走らせられると謳った。技術的には成功であり、商業的には完全な失敗だった——Chrome 以外、どのブラウザもそれを実装しようとしなかったからである。十四年後、同じことが成し遂げられた。違いはただ一つ：**今回は、誰も自分から先に手を動かさなかった。**

## シナリオ 1　技術的には成功し、政治的に失敗したプロジェクト

**背景**：Web の性能の天井は新しい問題ではない。JavaScript は動的型付け、ガベージコレクション付き、シングルスレッドの言語である。UI ロジックにおいては代替不能だが、ひとたび「密な計算」——動画のトランスコード、3D レンダリング、画像フィルタ、大きな行列演算——にぶつかると壁に当たる。二〇一〇年前後、この天井の下で二つの路線が競合していた。

**第一の路線：Google の NaCl / PNaCl（Native Client / Portable Native Client）**。その発想は乱暴なほど直截だった。速くしたいのなら、**ネイティブの機械語をそのまま走らせればよい**。NaCl は静的検証器（validator）で x86 機械語を走査し、命令を 32 バイト境界へ整列させ、安全でないジャンプとシステムコールを禁じ、そのコード全体をセグメントレジスタで囲ったサンドボックスへ閉じ込めた。のちの PNaCl はさらに踏み込む——x86 機械語ではなく **LLVM bitcode** を配布し、最後の一マイルの翻訳をブラウザ側で行うことで、CPU アーキテクチャへの縛りを外した。

**なぜ失敗したのか**：遅かったからではない——まったく遅くなかった。失敗の理由は三つある。

- **それは Web ではなかった**。NaCl モジュールは `<embed>` というプラグインコンテナの中で生き、DOM とも JavaScript とも、あいだにメッセージパッシングの層を挟んでいた。それは**ページに寄生したネイティブプログラム**であって、ページの一部ではなかった。
- **それは一社の仕様だった**。Mozilla は公然と反対し、Apple と Microsoft は実装の意思を一度も示さなかった。Chrome だけが対応する「Web 標準」は、開発者にとってただの負債である。
- **検証器の複雑さが高すぎた**。CPU アーキテクチャごとに、正しさを証明できる機械語検証器を書く——それはセキュリティ工学において極めて高価な約束だった。

**第二の路線：Mozilla の asm.js**。その発想は正反対で、いくらか狡猾でさえあった——**新しいものを何一つ持ち込まない**。asm.js は JavaScript の**極度に厳格な部分集合**である。数値演算はすべてビット演算で型を注釈し（`x|0` は 32 ビット整数、`+x` は倍精度浮動小数点）、メモリアクセスはすべて巨大な `ArrayBuffer` の型付き配列を経由し、オブジェクトもクロージャもガベージコレクションも禁じる。

```javascript
// asm.js の典型的な姿：コメントでモジュールを標し、ビット演算で型を構文に焼き付ける
function AsmModule(stdlib, foreign, heap) {
  "use asm";                          // ← エンジンはこの行を見て AOT コンパイル経路へ切り替える
  var HEAP32 = new stdlib.Int32Array(heap);
  function add(x, y) {
    x = x|0;                          // ← 宣言：x は 32 ビット整数
    y = y|0;
    return (x + y)|0;                 // ← 宣言：戻り値も 32 ビット整数
  }
  return { add: add };
}
```

**この一手の妙は、それが合法な JavaScript であることにある。** asm.js を知らないブラウザでも、このコードは正しく実行される（ただ遅いだけだ）。知っているブラウザでは、エンジンが `"use asm"` を見た瞬間に JIT のウォームアップ一式を飛ばし、静的型付け言語として AOT（事前コンパイル）する。**Emscripten** は C/C++ を LLVM 経由でこの種の JavaScript へコンパイルし、「Unreal Engine をまるごとブラウザへ持ち込む」ことを、会場でデモできる事実に変えた。

**二つの路線はそれぞれ一つのことを証明した**：NaCl は**ブラウザのサンドボックスがネイティブに近いコードを安全に実行できること**を証明し、asm.js は**プラグインなしで、エンジンの最適化だけでネイティブの 2 倍以内の性能が得られ、しかも四社すべてが実装できること**を証明した。

> 💡 座右の一言
> **ある技術案が生き延びられるかどうかは、それが何人に「同意しなくてよい」と言えるかで決まる。** NaCl は他の三社に、巨大な新実行環境と機械語検証器を丸ごと受け入れることを求めた——それは相手にあなたの判断へ大金を賭けろと言うに等しい。asm.js が求めたのは「あなたは何もしなくていい。どうせ合法な JS なのだから。私が最適化しただけだ」——それは**採用コストをゼロまで下げ、最適化の見返りを追随する意思のある者に残す**やり方だった。前者は政治的提案であり、後者は技術的事実である。組織をまたぐ標準争いでは、この法則がつねに成り立つ。**相手のコストがゼロのまま先に走り出せる案が最後に勝ち、相手が先に代価を払わなければ始まらない案は、たいてい議論の機会すら得られない。** これが、Wasm の選んだ道が asm.js の政治的知恵と NaCl の技術的野心の合成である理由でもある。

> 🔍 踏み込んだ論評──asm.js の三つの致命的ボトルネックこそ、Wasm の設計一条一条の答えである
> asm.js は政治に勝ち、物理に負けた。そして負けた三箇所は、そのまま Wasm の設計動機に一対一で対応する。**第一に、解析コスト。** asm.js をどれだけ最適化しても、それは結局**テキスト**である。40 MB の asm.js ファイルに対し、ブラウザはまず JavaScript の字句解析と構文解析を完了させて初めて「ああ、これは asm.js だ」と気づける。純粋な解析だけで数百ミリ秒から数秒を食い、しかもこの代金はコールドスタートのたびに払わされる。Wasm のバイナリ形式はこの一段をほぼゼロまで圧縮した——**ダウンロードしながらコンパイル**（streaming compilation）でき、最初のバイトが届いた時点でコンパイラが働き始める。**第二に、型が仕様ではなく慣例で保証されていたこと。** `x|0` は「エンジンよ、信じてくれ」という約束にすぎない。コードがわずかに逸れれば、エンジンは黙って通常の JS 経路へ戻り、性能は崖のように落ち、開発者は警告一つ受け取らないことが多い。Wasm の型はバイナリに書き込まれ、ロード時に検証器が強制的に検査する——**検証を通るか、ロードを拒否されるか。中間状態は存在しない。** 第三に、**JS にないものは永遠に手に入らない**。64 ビット整数（`i64`）は JavaScript にネイティブ型がなく、asm.js は 32 ビット二つで模倣するほかない。SIMD ベクトル命令、アトミック操作、マルチスレッドの共有メモリは、どれも JS の構文では表現できない。Wasm は最初から `i32/i64/f32/f64` の四つの数値型を仕様に書き込んだ。だから正しい歴史の語りは「Wasm が asm.js を置き換えた」ではなく——**asm.js は成功した市場検証実験であり、需要が実在することと、四社のエンジンが静的型付けの最適化経路を飲み込めることを証明し、そして自らを Wasm の燃料として燃やした**、である。「置き換えられる運命の案を使って、次の案が投資に値することを証明する」というこの戦略は、インフラの進化のなかで繰り返し現れる。

## シナリオ 2　二〇一五年：四社はなぜ突然、同じテーブルに着いたのか

**背景**：二〇一五年六月、Google、Mozilla、Microsoft、Apple が新しいバイナリ形式の標準——**WebAssembly**——を共同開発すると発表した。ブラウザ戦争の歴史において、これは異常なほど珍しい。ほぼあらゆる論点で互いの足を引っ張ってきた四社が、この件では一発で揃ったのである。

**なぜ今回はまとまったのか**。鍵は**三つの「誰も損をしない」**にある。

| ベンダ | すでに投じた資産 | Wasm が守ったもの |
|---|---|---|
| Google | NaCl/PNaCl のサンドボックスと検証器の経験、V8 の TurboFan バックエンド | サンドボックス技術に標準化された出口ができ、誰も追随しない仕様を単独で維持し続けずに済む |
| Mozilla | asm.js、Emscripten ツールチェーン、SpiderMonkey の OdinMonkey AOT 経路 | 既存の Emscripten エコシステムがバックエンドを無痛で差し替えられる。asm.js への最適化投資が無駄にならない |
| Microsoft | Edge は性能の物語で急いで追いつく必要があった | 仕様が明確で実装の境界がはっきりした目標を手に入れ、他社の JS エンジン最適化を逆解析せずに済む |
| Apple | JavaScriptCore の FTL JIT | 「小さく閉じた」仕様は、「任意の LLVM bitcode をサポートする」よりもセキュリティ審査がはるかに安い |

**設計上の決定的な取捨——意図的に小さく作った**。Wasm MVP（実用最小限の製品、2017 年に着地）は多くのことを**意図的にやらなかった**。ガベージコレクションなし、例外処理なし、マルチスレッドなし、DOM に触れず、システムコールなし、文字列型すらない。あるのは四つの数値型、一続きのメモリ、一組のスタック命令、そしてロード時に線形時間で完了できる検証アルゴリズムだけである。

**この「意図的に小さく」は政治的な必要条件だった**。仕様が小さいほど、四つの独立実装が挙動で食い違う確率は下がる。検証器が単純なほど、セキュリティ審査のコストは下がる。能力が少ないほど、悪用される攻撃面は狭くなる。**Wasm の MVP はほとんど「あなたを驚かせないと保証します」という契約書である。**

**タイムライン**（検証可能な仕様上のマイルストーン）：

- **2015 年 6 月**：四社が共同で WebAssembly を発表。
- **2017 年 3 月以降**：Chrome、Firefox、Safari、Edge が順次 Wasm エンジンを内蔵し、MVP が四大ブラウザの共通能力となる。
- **2019 年 12 月**：W3C が WebAssembly Core Specification 1.0 を勧告（Recommendation）に定め、Wasm は HTML、CSS、JavaScript と並ぶ Web の第四の中核言語となる。
- **2019 年以降**：**WASI**（WebAssembly System Interface）提案が登場し、Wasm はブラウザを離れてサーバサイド、クラウドネイティブ、エッジコンピューティングへ進出しはじめる。

> ⚠️ 真偽の注意
> 「四巨頭が 2015 年に手を組んだ」「2017 年に四ブラウザが全面対応した」「2019 年に W3C が標準に定めた」——この三つはいずれも検証可能な公開事実である。しかし巷でよく見る盛られた版——たとえば Wasm を「W3C が任じた第四のプログラミング言語であり、JavaScript を置き換える」と語るもの——は誇張である。**仕様文書は Wasm を JavaScript の代替と位置づけたことは一度もなく、明確に補完（complement）と位置づけている**。Wasm はいまも DOM を単独で操作できず、自分自身を単独でロードできない。その起動のたびに、JavaScript（あるいはホスト環境）が最初の鍵を手渡す必要がある。

> 🔍 踏み込んだ論評──「意図的に小さく」の複利と、いま払っている利息
> MVP のミニマリズムは 2017 年には勝利の鍵だった。しかし 2026 年、その請求書はすべて期日を迎えた。**請求書その一：GC がないことは、Java/Kotlin/Dart/C# のエコシステム全体を門前払いすることに等しい。** これらの言語は自前のガベージコレクタをまるごと `.wasm` へコンパイルせざるをえず、出力は容易に数 MB から始まる——これこそのちの **Wasm GC**（Wasm がホストエンジン既存の GC を直接再利用できるようにするもの。**Wasm 3.0 で核心仕様に入った**）の直接の動機であり、Wasm GC が着地したあと、Kotlin/Wasm や Dart（Flutter Web）といった言語の出力サイズは大きく縮んだ。**請求書その二：例外処理がないことは、C++ の `try/catch` を JavaScript のトランポリンで模倣するしかないことを意味する**。境界を越えるたびに相当なオーバーヘッドがかかる——これが**ネイティブ例外処理**（Wasm 3.0）の動機である。**請求書その三：末尾呼び出しがないことは、関数型言語（Scheme、OCaml、Haskell）の深い再帰が必ずスタックを溢れさせることを意味する**——これが**末尾呼び出し**（`return_call`、Wasm 3.0）の動機である。**請求書その四：数値型しかないことは、文字列のやり取りのたびに手動でエンコード・デコードすることを意味する**——これが **Reference Types**、**JS String Builtins** と続く進化の動機である。だから Wasm の提案一覧（SIMD、threads、bulk memory、multi-value、reference types、GC、exception handling、tail call、memory64、multiple memories、relaxed SIMD、branch hinting……）を眺める正しい仕方は「機能が増えていく」ではなく——**どの提案も、2015 年に四社を交渉のテーブルへ着かせるために意図的に負った一筆の債務を返済している**、である。
> **そしてその債務は、2025 年 9 月におおむね返し終えた。** その月 **WebAssembly 3.0 の完成が宣言され**、**GC、Memory64、例外処理、末尾呼び出し、複数メモリ、型付き関数参照、拡張定数式、分岐ヒント、128 ビット SIMD** が一挙に核心仕様へ収められた。**十年前に合意のために削ぎ落としたものを、十年かけて一条ずつ戻し、しかも核心モデルは一度も崩れなかった。**
>
> この法則は、プラットフォームを作るすべての人が覚えておく価値がある。**合意を得るために行った引き算は、あなたが成功したあと、一条ずつ足し戻さねばならない技術的負債になる。そしてその負債を返せるかどうかは、当初削ったものが核心モデルの一貫性を壊していたかどうかで決まる。** Wasm が返せたのは、削ったのが「能力」であって、「型安全」と「線形メモリ」という二本の柱を削らなかったからだ。**もし 2015 年に性能のために型システムで譲歩していたら、この十年は返済ではなく書き直しになっていた。**

## シナリオ 3　殻を破る：WASI と、繰り返し引用されるあの一文

**背景**：二〇一九年、Wasm はブラウザの外へ出た。核心仕様における Wasm モジュールは**もともとシステム能力を一切持たない**——ファイルを開けず、接続を張れず、時計を読めない。あらゆる能力はホスト環境（host）が **import** の形で明示的に手渡す必要がある。この設計はもともとブラウザのサンドボックスのためのものだったが、思いがけずサーバサイドが最も欲しがっていたものになった。

**WASI が行ったこと**：それは**オペレーティングシステムに依存しない標準インタフェース**——ファイル、時計、乱数、環境変数、ネットワーク（後続版で）——を定義し、同一の `.wasm` が Linux、Windows、macOS 上で同じ意味論で実行されるようにした。さらに決定的なのはそのセキュリティモデルである。

- **ケイパビリティベース・セキュリティ**：Wasm モジュールは既定で「手ぶら」である。`open()` の権限はなく、あるのはホストが**あらかじめ開いて手渡した**ディレクトリハンドル（pre-opened directories）だけだ。
- **パスの脱出は実行時に阻まれる**：モジュールが `/sandbox/../etc/passwd` へアクセスしようとすれば、ファイルシステムの権限任せではなく、実行環境が能力の境界で直接止める。

```bash
# Wasmtime：ホストの ./my_storage を Wasm から見た /sandbox へ写像し、このディレクトリだけを与える
wasmtime run --dir=./my_storage::/sandbox my_server.wasm
```

**これは従来のサーバプロセスとの質的な違いであって、量的な違いではない**。破られた Node.js プロセスが手に入れるのは**それを実行しているユーザの全権限**である。破られた Wasm モジュールが手に入れるのは**ホストが明示的に手渡したその数点だけで、一つも余分にはない**。これは「既定で拒否」と「既定で許可」の差である。

**繰り返し引用されるあの一文**：Docker 創業者 Solomon Hykes は 2019 年、広く拡散したツイートでこう述べた——**「2008 年に WASM+WASI があったなら、Docker を作る必要などなかった。」**

> ⚠️ 真偽の注意
> この発言は実在し、頻繁に引用される。しかししばしば「Wasm が Docker を置き換える」と切り取られる。**原ツイートの次の一文は「Wasm はサーバサイド計算の未来だ」であって「コンテナは死んだ」ではない**。Hykes 本人も後続の議論で、これは「軽量・可搬・クロスプラットフォーム」という性質の組に対する称賛であり、コンテナの陳腐化の宣言ではないと明言している。現実には両者は**補完的**である。Docker/OCI が隔離するのはオペレーティングシステムのユーザ空間全体であり、既存のどんなバイナリでも走らせられる。Wasm が隔離するのは単一のアプリケーションだけで、起動時間とサイズで桁違いの優位を得る代わりに、**「再コンパイルされたもの」しか走らせられない**。実務で最も多い配備形態は、二者択一ではなく **コンテナ化された実行環境の中で Wasm モジュールが動く**（Kubernetes 上の runwasi / Krustlet のような方式）ことである。

**Wasm がバックエンドで持つ三つの具体的優位**（定量可能・検証可能）：

| 観点 | コンテナ（OCI / Docker） | Wasm + WASI |
|---|---|---|
| コールドスタート | 数十ミリ秒〜数秒（イメージ取得、namespace 起動、init プロセス） | マイクロ秒〜数ミリ秒（モジュールのインスタンス化。コンパイル済みを事前キャッシュ可能） |
| 成果物サイズ | 数十 MB〜数百 MB（ベースイメージと OS 層を含む） | 数十 KB〜数 MB（自分のコードと必要な runtime のみ） |
| 隔離境界 | Linux namespace + cgroup + seccomp（OS 層） | メモリ安全な仮想機械（言語層）＋ ケイパビリティ式 API 認可 |
| アーキテクチャ横断 | CPU アーキテクチャごとにイメージを出す必要がある | 単一の `.wasm` がどこでも動く（最後の一マイルのコンパイルは実行環境が行う） |
| 何を走らせられるか | 既存の任意の Linux バイナリ | **再コンパイルされたものだけ**（これが最大の現実的制約） |

**主要な実行環境**：**Wasmtime**（Bytecode Alliance 主導、WASI の参照実装であり仕様推進者）、**WasmEdge**（CNCF サンドボックスプロジェクト。クラウドネイティブ、マイクロサービス、AI 推論に最適化され、Wasm 内からの GPU 呼び出しに対応）、**Wasmer**（可搬性と多言語埋め込みを重視）、**Spin**（Fermyon 製。Wasm マイクロサービスを構築・実行するフレームワークで、慣れた言語でサーバレス関数を書ける）。

> 💡 座右の一言
> **ケイパビリティベース・セキュリティの真の価値は、それがより安全であることではなく、「安全」を配備スクリプトの中で読み取れるものに変えることにある。** 従来のサンドボックスの安全は**否定形**だった——seccomp のホワイトリスト、AppArmor のルール、capability drop で権限を一条ずつ剥ぎ取っていくが、漏れがないかは永遠に確信できない。ケイパビリティベースの安全は**肯定形**である——あの一行の `--dir=./my_storage::/sandbox` が、このサービスの持つ能力の**完全な一覧**であり、一字たりとも余分はない。セキュリティ審査は「脆弱性がないことの証明」から「引数一行を読むこと」へ変わる。これは監査コストの桁違いの低下である。この原理を拡大すれば、データベース権限、クラウドの IAM、OAuth のスコープ、ブラウザ拡張の権限のあちこちで同じもがきが見える。**既定で全部与えて後から差し引く権限モデルは、最後にはすべて、既定で何も与えず一項ずつ付与する形へ進化する。そしてその移行のたびに、人が十年先延ばしにするほど高くつく。**

## シナリオ 4　それが本当に着地した場所：反論しがたい四つの商業事例

**背景**：技術の物語がどれだけ美しくても、「毎日使っている」製品四つには敵わない。以下の四つは Wasm で最も引用され、かつ公開された技術記事の裏づけがある重量級の着地である。

- **Figma**：中核のレンダリングエンジンは C++ で書かれ、Wasm へコンパイルされている。これがウェブ上で数万のベクタレイヤを滑らかに編集できる鍵である。Figma が公開した技術記事には、asm.js から Wasm へ移行したあと**ロード時間が顕著に短縮された**実測が記録されている。
- **Adobe Photoshop Web**：Adobe は数百万行の C++ 資産を Wasm（Emscripten と、のちのマルチスレッド・SIMD 対応を伴って）でブラウザへ移植し、インストールなしでプロ級のレイヤ編集を可能にした。
- **Google Earth**：初期の 3D 地球は専用プラグイン（NPAPI 時代の産物）を必要とした。いまは Wasm でブラウザ内から全球の 3D 地形を直接レンダリングしている。
- **AutoCAD Web**：数十年積み上げた C++ の CAD 中核をブラウザへ持ち込み、図面ファイルがデスクトップソフトを迂回する必要をなくした。

**この四例の共通点は、その差異よりも重要である**：いずれも**「すでに数百万行の成熟した C/C++ 資産を持つ」企業**だという点だ。Wasm がそれらにもたらした価値は「速く走る」ことではなく、**「書き直さなくていい」**ことである——二十年分の幾何カーネル、画像アルゴリズム、フォント組版エンジンを、一本のコンパイルパイプラインでまったく新しい配布経路へ移す。三百人のエンジニアに TypeScript で書き直させるのではなく。

**裏を返せば、これは Wasm が割に合わない境界も引いている**：作ろうとしているのがフォームの CRUD、ブログ、EC のフロントなら、**Wasm はあなたにとって無価値であり**、むしろ純粋な負債である（コンパイル層が一つ増え、サイズが増え、デバッグの難しさが一式増える）。この点は第 3 章で制約一覧を使ってもっと容赦なく述べる。

> 💡 座右の一言
> **新技術の本当の商業価値は、しばしば「何が新しくできるか」ではなく、「どれだけの既存資産を廃棄から救うか」にある。** Figma、Adobe、Autodesk が Wasm を採ったのは、性能表の数パーセントのためでは決してなく、**数十年分の C++ 資産の残存価値が一度に生き返る**ためだった——帳簿には現れないが、一社が新しいプラットフォームへ賭けるかどうかを決めるほど大きな数字である。だからこそ「破壊的イノベーション」の物語はしばしば人を誤らせる。**大きな組織に新技術を採らせるのは、たいてい保守的な動機（既存投資を守る）であって、急進的な動機（未来を抱擁する）ではない。** 組織にある技術の採用を説くとき、「これまでできなかったことができる」と語っても決裁者はたいてい動かない。「すでに払った金が、新しい経路でもう一度稼げる」と語れば動く。

## 本章のまとめ

- Wasm の前史は二つの路線の合流である。**NaCl はブラウザのサンドボックスがネイティブに近いコードを安全に走らせられることを証明し、asm.js はプラグインなしでネイティブに近い性能が得られ、しかも四社すべてが実装できることを証明した**——前者が技術的野心を、後者が政治的知恵を提供した。
- **2015 年の四者合意、2017 年の四ブラウザ着地、2019 年の W3C 標準化**（いずれも検証可能）。まとまった鍵は「意図的に小さく」だった。GC なし、例外なし、スレッドなし、DOM に触れない——**仕様が小さいほど、四つの独立実装が食い違う確率は下がる。**
- 今日の Wasm の特性一つひとつ（SIMD、threads、GC、exception handling、tail call、memory64、multiple memories……）は、本質的には**2015 年に合意のため意図的に負った債務の返済**である——そしてその債務は **2025 年 9 月の WebAssembly 3.0** でおおむね返し終えた。
- **WASI が Wasm の殻を破った**。その核心は「ファイルを開けるようになった」ことではなく、**ケイパビリティベース・セキュリティ**である。モジュールは既定で手ぶらであり、あらゆる能力はホストが明示的に手渡す必要があり、しかもその完全な一覧は起動引数に書かれている。
- 「2008 年に WASI があれば Docker を作る必要はなかった」は実在する発言だが、**コンテナが死んだことにはならない**——実務で最も多いのは、コンテナ化された実行環境の中で Wasm が動く形である（真偽の要検討はシナリオ 3 の ⚠️ を参照）。
- Figma、Photoshop Web、Google Earth、AutoCAD Web の共通点は、いずれも数百万行の成熟した C++ 資産を握っていることである。**Wasm がそれらにもたらす価値は「書き直さなくていい」ことであって、「速く走る」ことではない。**

歴史は語り終えた。機械そのものを見る番だ。次の問いはとても具体的である：**ブラウザが `\0asm` で始まるあのバイト列を受け取ったとき、いったい何をしているのか。なぜそのバイト列は安全だと証明できるのか。** 第 2 章へ。
