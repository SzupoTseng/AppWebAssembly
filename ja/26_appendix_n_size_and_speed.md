# 付録N　体積と速度：Wasm の圧縮と加速の全解

> 本書で最も技術の密度が高い付録である。二つの問いに答える：**「私の `.wasm` はなぜこんなに大きいのか、どう小さくするのか？」** と **「なぜ思ったほど速くないのか、どう速くするのか？」**
>
> **全篇を貫く一つの規律**：**まず測り、それから最適化し、そしてもう一度測れ。** 以下の技法にはそれぞれ適する形がある。無差別に全部かぶせれば、たいてい遅くて保守しにくいビルドの流れが出来上がる。

---

# 前編：体積

## 1. まず解剖する：あなたのバイトは、どこへ消えているのか

**どの旗をいじるより前に、この一歩を踏め。** これを踏まない最適化はすべて当て推量である。

```bash
# 1. セクション単位の予算：どのセクションがいちばん肥えているか
wasm-objdump -h app.wasm
#   Type       start=0x0000000b end=0x000001a4 (size=0x00000199) count: 52
#   Function   ...
#   Code       start=0x00012f4a end=0x0031b2c1 (size=0x00308377) ← たいていはこれ
#   Data       start=0x0031b2c3 end=0x004a9f10 (size=0x0018ec4d) ← だがこれも見落とすな

# 2. 記号の単位：誰が Code セクションを食っているか
twiggy top -n 30 app.wasm

# 3. 保持の連なり：誰が誰を道連れにしているか（最も役に立つ一つ）
twiggy dominators app.wasm

# 4. なぜその関数がまだ居るのか？（「使っていないはずだ」への答え）
twiggy paths app.wasm -- 'core::fmt::write'
```

**四つのセクションの典型的な占有と、対応する武器**：

| セクション | 典型的な占有 | それは何か | 対応する武器 |
|---|---|---|---|
| **Code** | 50〜80% | すべての関数の本体 | コンパイルの旗、LTO、死んだコードの除去、`wasm-opt` |
| **Data** | 10〜45% | 静的なデータ、文字列の定数、参照表 | **データ自体を削る**（§6 参照）、実行時の展開 |
| **Custom (`name`/DWARF)** | 0〜30% | デバッグの記号 | `--strip-debug`（公開版では必須） |
| **Element / Table** | 5% 未満 | 関数テーブルの初期の中身 | 間接呼び出しの対象の数を減らす |

> **よくある第一の誤診**：ファイルが大きいのを見て、すぐ `opt-level` を触りに行く。**だが Data セクションが 45% を占めているなら、Code をさらに 10% 縮めても、総体では 5% しか変わらない。** まず `wasm-objdump -h` を見よ。

## 2. コンパイル時の旗：それらが本当に削っているもの

### 2-1　Rust

```toml
[profile.release]
opt-level = "z"      # 体積を優先（"s" は均衡、3 は速度優先）
lto = "fat"          # 全プログラム最適化：crate をまたぐインライン化 + 大域的な死んだコードの除去
codegen-units = 1    # ★ LTO に全体を見せる。並列のコンパイルは遅くなるが、産物は目に見えて小さくなる
panic = "abort"      # 巻き戻しの表と landing pad を削る
strip = true         # name セクションを剥ぐ
overflow-checks = false
debug = false
incremental = false  # 増分コンパイルは単位をまたぐ最適化を妨げる
```

**それぞれが本当に削るもの**：

| 旗 | 何を削るか | 代価 |
|---|---|---|
| `opt-level = "z"` | ループの展開と**自動ベクトル化**を止める | **⚠️ これは SIMD の自動ベクトル化を切る**——それに頼るなら `"s"` か `3` へ |
| `lto = "fat"` | crate をまたぐインライン化のあとの死んだコード、重複した総称の実体 | コンパイル時間が目に見えて増える |
| `codegen-units = 1` | LTO に全体を見せる——**これ単独で 5〜15% になることがよくある** | コンパイルを並列にできない |
| `panic = "abort"` | 巻き戻しの表、landing pad、`Drop` の展開の経路 | panic を catch できない（Wasm ではもともとあまり使わない） |
| `strip = true` | `name` の独自セクション | **読めるスタックトレースを失う**（§12 の引き換えを見よ） |

### 2-2　Rust で最大の、隠れた体積の犯人：panic の整形の仕組み

**これは大半の Rust/Wasm のプロジェクトで、最も気づかれていない脂身である。**

`panic!("index {} out of range", i)` の一行が、**`core::fmt` の整形の仕組みを一式**バイナリへ引き込む——trait オブジェクトの振り分け、幅と精度の処理、浮動小数の整形を含む小さな機械であり、**軽く数十 KB から数百 KB を占める**。しかも悪いことに：**`unwrap()` の一つひとつ、配列の索引づけのたび、整数の溢れの検査のたびに、失敗の経路からそれが参照されうる。**

```bash
# それが犯人かを確かめる
twiggy paths app.wasm -- 'core::fmt::write' | head -20
```

**根治の手（nightly が要る）**：

```bash
cargo +nightly build --release --target wasm32-unknown-unknown \
  -Z build-std=std,panic_abort \
  -Z build-std-features=panic_immediate_abort
```

`panic_immediate_abort` は、すべての panic を `unreachable` の命令へ変える。**整形の仕組みも panic の文言の文字列も、まるごと消える。** 小さなモジュールでは、この一手の効きが他のすべての旗の合計を超えることがよくある。

**代価は正直である**：**panic のあと、何の情報も得られない**。あるのは `RuntimeError: unreachable` だけだ。**これは「公開版は体積を取り、デバッグ版は情報を残す」という二本立てのビルドの決断であって、全体に一律で下す決断ではない。**

**もう少し保守的なやり方**（nightly が要らない）：

```rust
// 整形を伴う panic を避ける
let v = arr.get(i).ok_or(MyError::OutOfRange)?;   // arr[i] ではなく
// Display / format! を避ける
// format!("...{}", x) ではなく静的な文字列を使う
```

### 2-3　Rust の第二の犯人：単相化の爆発

Rust の総称は**単相化（monomorphization）** される——`Vec<u8>` と `Vec<u32>` はまったく独立した二つのコードを生む。十の型で実体化される複雑な総称の関数は、そのまま十本になる。

```rust
// ❌ 関数の本体まるごとが N 本に複製される
pub fn process<P: AsRef<Path>>(path: P, data: &[u8]) { /* 二百行 */ }

// ✅ 外側の薄い殻が変換を受け持ち、内側の単一の実体が重い仕事をする
pub fn process<P: AsRef<Path>>(path: P, data: &[u8]) {
    process_inner(path.as_ref(), data)      // 薄い殻。複製されても構わない
}
fn process_inner(path: &Path, data: &[u8]) { /* 二百行。一本だけ */ }
```

**この「総称の薄い殻 + 具体的な実装」の型は、Rust のエコシステムで最も有効な体積の技の一つである**。そして `twiggy top` は重複した実体をそのまま並べて見せてくれる。

### 2-4　C / C++

```bash
emcc app.cpp \
  -Oz \
  -flto \
  -fno-exceptions \                  # C++ の例外の巻き戻しの表はたいてい大きい
  -fno-rtti \                        # typeid / dynamic_cast のメタデータ
  -ffunction-sections -fdata-sections \
  -Wl,--gc-sections \                # 使われない section を丸ごと捨てる
  -sASSERTIONS=0 \                   # 実行時の表明と文言の文字列を除く
  -sFILESYSTEM=0 \                   # ★ MEMFS が要らないなら、ファイルシステムを一式同梱するな
  -sENVIRONMENT=web \                # node/worker/shell の分岐を除く
  -sMALLOC=emmalloc \                # dlmalloc よりずっと小さい確保器
  -sMINIMAL_RUNTIME=1 \              # 極小の JS の糊（制約は多い）
  --closure 1 \                      # Closure Compiler で JS の糊を圧縮する
  -sEXPORTED_FUNCTIONS='["_main","_process"]' \
  -o app.js
```

**とりわけ注目に値するもの**：

- **`-sFILESYSTEM=0`**：コードが本当に `fopen` を呼んでいなくても、Emscripten は既定で MEMFS を一式つなぎうる。**この一項だけで、数十 KB の JS の糊が消えることがよくある。**
- **`-sMALLOC=emmalloc`**：`emmalloc` は既定の `dlmalloc` よりずっと小さい。代価は、ある種の確保の型では遅くなること。**動的な確保をほとんどしない（たとえばすべて arena で済ませる）コードなら、これは純粋な得である。**
- **`--closure 1`**：これが圧縮するのは **JS の糊**であって `.wasm` ではないことに注意。Emscripten のプロジェクトでは、糊そのものが数十 KB になりうる。

### 2-5　確保器の選び方

| 確保器 | 体積 | 速度 | 備考 |
|---|---|---|---|
| Rust の既定（dlmalloc） | 中 | 良い | 大半の場合の正しい選択 |
| `emmalloc`（Emscripten） | **小** | 中 | 確保の型が単純なときの良い選択 |
| **自前の bump/arena** | **極小** | **極めて速い** | **§11 参照**——「まとめて確保し、一度に全部手放す」型なら、これは両取りである |
| `wee_alloc` | 極小 | 悪い | ⚠️ **すでに保守されておらず、メモリの回収に既知の問題がある。新しいプロジェクトでは勧めない** |

## 3. `wasm-opt`：ただの `-Oz` ではない

**Binaryen の `wasm-opt` は、この鎖の上で投資対効果が最も高い単一の道具である**が、多くの人は旗を一つしか使わない。

```bash
wasm-opt -Oz \
  --strip-debug --strip-producers --strip-target-features \
  --low-memory-unused \
  --zero-filled-memory \
  --converge \
  app.wasm -o app.opt.wasm
```

**その内側で本当にしていること**（`-Oz` は pass の組み合わせである）：

| pass の類 | 代表的な pass | 何をするか |
|---|---|---|
| 死んだコードと掃除 | `--dce`、`--vacuum`、`--remove-unused-module-elements` | 到達できないコード、使われない import／大域／関数を除く |
| 重複の除去 | `--duplicate-function-elimination` | **バイナリとして完全に同一の関数を統合する**——単相化の爆発への解毒剤の一つ |
| インライン化 | `--inlining-optimizing` | 小さな関数を展開し、その結果をもう一度最適化する |
| 命令の層 | `--optimize-instructions` | 覗き穴の最適化：`x*2` → `x<<1` の類 |
| 局所変数 | `--simplify-locals`、`--coalesce-locals`、`--reorder-locals` | 局所変数の数と索引の大きさを減らす（**LEB128 では小さい索引のほうがバイトを食わない**） |
| 配置 | `--reorder-functions` | **呼ばれる頻度で関数の索引を並べ替え**、よく呼ばれる関数に小さい索引を与える → LEB128 の符号化が短くなる |

**しばしば見落とされる三つの旗**：

- **`--converge`**：小さくならなくなるまで最適化を繰り返す。**たいてい 1〜3% を絞り出せる**。代価はビルド時間が倍になること。
- **`--low-memory-unused`**：「低位のアドレスの領域は使われていない」と最適化器に告げ、アドレス計算についてより大胆な仮定を許す。**Emscripten のプロジェクトではおおむね安全だが、メモリの配置を手で書いているプロジェクトでは注意が要る。**
- **`--zero-filled-memory`**：メモリの初期値が零だと宣言し、余分な零詰めのコードを最適化器に除かせる。

> ⚠️ **順序の罠**：`wasm-opt` は **`wasm-bindgen` のあと**で走らせねばならない。`wasm-pack` は既定でそうしてくれるが、ツールチェーンを手で繋いでいる場合、**`wasm-bindgen` より前に `wasm-opt` を走らせると、bindgen がまだ要るものを削ってしまう**。症状は実行時の訳の分からない `LinkError` である。

## 4. `no_std` と、標準ライブラリを削ること

**モジュールが純粋な計算のカーネルであるとき**、`std` 全体が負担になりうる：

```rust
#![no_std]
extern crate alloc;                  // ヒープの確保だけが要る。std の他の部分は要らない

use alloc::vec::Vec;

#[panic_handler]
fn panic(_: &core::panic::PanicInfo) -> ! { core::arch::wasm32::unreachable() }
```

**得られるもの**：`std` の実行時の初期化、I/O の抽象、スレッドと同期の原始的な部品、そして（最も重要な）それが引き込む整形の仕組みが省ける。
**代価**：`String` が使えない（`alloc::string::String` を使う）、`std::collections::HashMap` が使えない（`hashbrown` へ替える）、エコシステムの半ば以上の crate が対応していない。

**判断の基準**：**モジュールが輸出するのが「バイト列を食わせ、バイト列を受け取る」純粋な関数なら、`no_std` はほとんどつねに割に合う。** ファイル、時刻、乱数が要るなら、`std` の与える便利さはたいていそのバイトに値する。

## 5. 言語をまたぐ重複を消す：`wasm-bindgen` の体積の費用

```rust
// ❌ #[wasm_bindgen] の一つひとつが JS の糊と Wasm 側の shim を生む
#[wasm_bindgen]
pub fn process_pixel(r: u8, g: u8, b: u8) -> u32 { /* ... */ }

// ✅ 粗い境界を一つ。ループは内側で回す
#[wasm_bindgen]
pub fn process_image(ptr: *mut u8, len: usize) { /* ... */ }
```

**これは体積の最適化であると同時に、性能の最適化でもある**（§13 参照）——**細かい粒の輸出の境界は、太くて、しかも遅い。**

**他の具体的な手**：

- `Vec<u8>` を返すと bindgen の確保／解放の定型を通る。**`(ptr, len)` を返して JS に線形メモリを直に読ませるほうが省ける。**
- `js_sys` / `web_sys` は**使う feature だけを開く**——その feature の一覧は極めて長く、全部開けば大量の束縛を引き込む。
- `#[wasm_bindgen(js_name = "...")]` は体積に響かないが、`catch` / `getter` / `setter` などの属性は余分な定型を生む。

## 6. 大半はデータである：FluffOS のあの一課を一般化する

**付録 L はある数字を記録した：FluffOS の Wasm のビルドは、ICU のデータをおよそ 30 MB から約 780 KB へ削り（−97%）、一方でドライバのコードの本体は 3.6 MB しかない。**

**それを一般化して、一つの規則にする**：

> **大きな C/C++ のプロジェクトの Wasm の産物では、しばしば半ば以上がそれの引き込んだデータの表であり、そしてその表のたいてい 90% は、あなたには要らない。**

**よくあるデータの脂身と、対応する手術**：

| データ | よくある大きさ | 手術 |
|---|---|---|
| ICU / Unicode の表 | 数 MB 〜 30 MB | 要る規則だけを残す（分かち書き／照合／翻字はそれぞれ削れる） |
| フォント | 数 MB | 部分集合化する（使う文字だけ残す） |
| 言語モデル／訓練のデータ | 数十 MB | **`.wasm` へ同梱するな**。実行時に取りに行く（キャッシュできる） |
| 時間帯のデータベース | 数百 KB | 対象の地域だけを残す |
| 組み込みの試験データ／見本 | よく忘れられる | コンパイルの条件で除く |
| 参照表（三角関数、CRC…） | KB 〜 MB | **実行時の計算を考えよ**——CPU はたいていメモリより安い |

**もう一手：データを圧縮して埋め込み、実行時に展開する。**

```
2 MB のデータの表を zstd で 400 KB へ圧縮して Data セクションへ埋め、
起動時に 15 KB の展開器で線形メモリへ広げる。
→ 転送で正味 1.6 MB を省く。代価は起動が数ミリ秒延びること。
⚠️ だが先に確かめよ：外側の Brotli の転送圧縮が、すでにそれを圧縮していないか？
   そうなら、この一手は圧縮を転送の層から応用の層へ移しただけで、かえって悪くなりうる。
```

## 7. 転送の層：Brotli と、遊びの規則を変える新しいもの

### 7-1　なぜ Wasm がとりわけ Brotli に向くのか

**経験上、Wasm の圧縮率はしばしば 3.5〜5 倍になる**（付録 L の実例は 3.6 MB → 0.8 MB、およそ 4.5 倍）。理由は三つある：

1. **LEB128 のおかげで小さい数が 1 バイトで済み**、しかも分布が強く偏る → エントロピーが低い。
2. **命令の符号の反復性が極めて高い**：`20 xx 20 yy 6A`（load/load/add）のような型が、モジュール全体で千万回も現れる。
3. **Data セクションにはたいてい大量の零と重複する文字列が含まれる。**

```nginx
# 静的な事前圧縮は即時の圧縮に勝る（CPU が省け、最高の等級も使える）
brotli_static on;
# 産物：app.wasm + app.wasm.br（brotli -q 11）
```

### 7-2　★ 圧縮辞書転送（Compression Dictionary Transport）

**これは Wasm の更新の配り方において、この数年で最も重要な変化であり、しかも Wasm の議論にはほとんど現れていない。**

**問題**：あなたの `app.wasm` は 8 MB（Brotli 後 1.8 MB）だ。三行直して新しい版を出す——**利用者は 1.8 MB を丸ごと再ダウンロードせねばならない。** バイトの 99% は、その人のキャッシュにある古い版とまったく同じであるにもかかわらず。

**解き方**：**利用者がすでにキャッシュしている古い版を、新しい版を圧縮するための辞書として使う。**

```http
# 最初の応答：「このファイルは将来の辞書に使える」と宣言する
HTTP/2 200
Content-Type: application/wasm
Use-As-Dictionary: match="/app-*.wasm"

# のちに利用者が新しい版を要るとき、ブラウザが自動で付ける：
Available-Dictionary: :pZGm1Av0IEBKARczz7exkNYsZb8LzaMrV7J32a2fFG4=:
Accept-Encoding: br, dcb, dcz

# サーバは古い版を辞書にして新しい版を圧縮する：
HTTP/2 200
Content-Encoding: dcb        # Dictionary-Compressed Brotli（dcz は Zstandard の版）
→ 実際の転送は数十 KB で済みうる
```

**状況**：**RFC 9842**。**Chrome 130+、Edge 130+ が対応し、Firefox は進行中。** CDN の側では、**Cloudflare が 2026 年 4 月に辺縁での対応を出した**（その実装そのものが Wasm へコンパイルされた Zstandard である）。

**Wasm にとってその意味はとりわけ大きい。** Wasm のアプリケーションには二つの特徴があるからだ：**（一）** 単一の大きなファイルであること。**（二）** 改版のときバイトの大半が変わらないこと。**これはまさに差分圧縮が最もよく効く形である。**

> 💡 **一つの帰結**：この道が広まれば、**「モジュールを小さく切るべきか」という決断の重みは下がる**——小さく切る主な動機の一つ（更新のとき一部だけ再ダウンロードさせる）が差分圧縮に取って代わられ、一方で小さく切る代価（往復が増える、モジュールをまたぐ呼び出し）は残るからだ。

## 8. 分割と遅延読み込み

| 手 | 仕組み | 向くもの |
|---|---|---|
| **`wasm-split`**（Binaryen） | プロファイルの結果に従ってモジュールを primary + secondary へ切り、初めて呼ばれたときに取りに行く | 起動の経路が明確で、機能の多くを利用者が永遠に押さないかもしれないもの |
| **手で複数モジュール + メモリの共有** | `memory` を一方から export し、他方で import する | 機能の境界がはっきりしているもの（PDF の書き出し、OCR の言語パックなど） |
| **実行時に資産を取る** | データを `.wasm` へ入れず、`fetch` + Cache API で | モデルの重み、フォント、言語パック |

```javascript
// 手で分ける：二つのモジュールが同じ線形メモリを共有し、データを複製しなくてよい
const core = await WebAssembly.instantiateStreaming(fetch("core.wasm"), imports);
const pdf  = await WebAssembly.instantiateStreaming(fetch("pdf.wasm"), {
  env: { memory: core.instance.exports.memory },   // ★ ここが要
});
```

# 後編：速度

## 10. 起動の経路を四段に分解する

**「Wasm は遅い」という不満の八割は、定常状態ではなく起動の話をしている。** そして起動は独立した四段の費用であり、それぞれに武器がある：

```
① ネットワークの転送 ── 圧縮後の体積と RTT に支配される ──→ 前編のすべて
② コンパイル        ── バイト数に線形に比例       ──→ §10-1
③ 実体化           ── メモリの確保、Data セクションの初期化、start の実行 ──→ §10-2
④ 実行時の初期化    ── 大域の構築子、言語の実行環境の自立ち上げ、データ構造の構築 ──→ §10-3 ★最も過小評価される
```

### 10-1　コンパイルの段階の四つの武器

```javascript
// ① ストリーミングコンパイル：最初のバイトが届いた時点で始める（サーバが application/wasm を返すこと）
const { instance } = await WebAssembly.instantiateStreaming(fetch("app.wasm"), imports);

// ② 一度コンパイルし、N 個の Worker で共有する（WebAssembly.Module は構造化複製できる）
const mod = await WebAssembly.compileStreaming(fetch("app.wasm"));
workers.forEach(w => w.postMessage({ mod }));      // ★ N−1 回のフルコンパイルを省く

// ③ ディスク上のコードキャッシュ：.wasm に安定した URL を与える（内容ハッシュのファイル名が最良）
//    エンジンは最適化後の機械語を HTTP のキャッシュへ書き、再訪ではコンパイルの段階を丸ごと飛ばせる
//    → 大きなモジュールの二度目の読み込みは、しばしば桁で速くなる
```

**④ 段階的なコンパイルは自動だが、理解しておくことはできる**：Liftoff がまず実行できる符号を出し（速いが粗い）、TurboFan が背後で良い符号を出して熱いうちに差し替える。**つまり「起動してからの最初の数百ミリ秒、あなたの Wasm は最適化されていない版を走らせている」**——起動の直後にベンチマークを一度回せば、測っているのは Liftoff の数字であって、定常状態の性能ではない。

### 10-2　★ Wizer：「初期化」をビルド時へ移す

**これはサーバ側と CLI の場面で最も過小評価されている技術である。**

多くのモジュールは起動時に大量の一度きりの仕事をする：設定の解析、参照表の構築、データ構造の読み込み、インタプリタの初期化。**Wizer（Bytecode Alliance）の発想はこうだ：それらをビルド時に済ませ、「初期化のあとのメモリの状態」を新しい `.wasm` へ写し取る。**

```bash
# ビルド時：モジュールを実体化し、初期化の関数を走らせ、その結果を新しいモジュールへ写す
wizer app.wasm -o app.initialized.wasm --allow-wasi
```

```rust
// モジュールの側：どの関数が「初期化」かを印づける
#[export_name = "wizer.initialize"]
pub extern "C" fn init() {
    LOOKUP_TABLE.set(build_expensive_table());   // これはビルド時に走り終わっている
}
```

**実行時に手にするモジュールは、Data セクションの中身がすでに初期化の済んだメモリの映像である**——起動時に何もしなくてよい。公式のベンチマークは**実体化と初期化が 1.35 倍から 6.00 倍速くなる**と主張しており、実際の効きは、もともとどれだけの初期化をしていたかによる。

**代価と制約**：**（一）** 写し取りは Data セクションを大きくする（**体積で起動の速さを買う**。前編と正面から衝突するので、測って引き換えを決めること）。**（二）** 初期化の途中で、実行時にしか無いもの（時刻、乱数、ネットワーク）に頼れない。**（三）** 主にサーバ側／CLI 向けであり、ブラウザの場面では体積の代価を天秤にかけねばならない。

**同じ発想の別の形**：

| 技術 | 場面 |
|---|---|
| **Wizer** | 汎用の事前初期化の写し取り |
| `wasmtime compile` → `.cwasm` | **バックエンドの AOT**：コンパイルを配備の前へ完全に移し、実行時は零コンパイル |
| エンジンの pooling allocator | インスタンスのプールをあらかじめ確保し、実体化のたびのメモリの確保を省く |

### 10-3　最も過小評価される第四段

**Pyodide は 30 MB を落とし終えたあと、なお CPython を自立ち上げする時間を要する。** Emscripten のプロジェクトは C++ の大域の構築子をすべて走らせねばならない。これらは**コンパイルが終わったあと**に起きるので、「モジュールの読み込み時間」という指標には現れない。

```javascript
// 分けて測れ。さもないと違う場所を最適化することになる
const t0 = performance.now();
const mod = await WebAssembly.compileStreaming(fetch("app.wasm"));
const t1 = performance.now();                       // ← コンパイル
const inst = await WebAssembly.instantiate(mod, imports);
const t2 = performance.now();                       // ← 実体化
inst.exports.app_init();
const t3 = performance.now();                       // ← 実行時の初期化 ★
console.log(`コンパイル ${(t1-t0)|0}ms / 実体化 ${(t2-t1)|0}ms / 初期化 ${(t3-t2)|0}ms`);
```

## 11. 定常状態の性能その一：コンパイラにより良い符号を出させる

### 11-1　SIMD：有効にしたことは、使われたことではない

```bash
# Rust
RUSTFLAGS="-C target-feature=+simd128" cargo build --release --target wasm32-unknown-unknown
# Emscripten
emcc -msimd128 -O3 ...
```

**知っておかねばならない三つの現実**：

1. **`opt-level = "z"` は自動ベクトル化を切る。** 最小の体積と自動 SIMD を同時に求めることはできない——**これは必ず選ばねばならない選択である。**
2. **自動ベクトル化は気難しい**：ループの境界がコンパイル時に分かるか推定できること、データの依存がないこと、ポインタの別名の疑いがないこと。**ベクトル化されなくてもコンパイラは警告してくれない**。逆アセンブルを見るか、測るしかない。
3. **手書きの intrinsics は最後の砦である**：

```rust
use core::arch::wasm32::*;

pub fn add_f32x4(a: &[f32], b: &[f32], out: &mut [f32]) {
    for i in (0..a.len()).step_by(4) {
        unsafe {
            let va = v128_load(a.as_ptr().add(i) as *const v128);
            let vb = v128_load(b.as_ptr().add(i) as *const v128);
            v128_store(out.as_mut_ptr().add(i) as *mut v128, f32x4_add(va, vb));
        }
    }
}
```

**第 3 章の天井を忘れるな**：**Wasm の SIMD は 128 ビットに固定である。** AVX2（256）向けに手で最適化されたコードを移せば、ベクトルの幅はそのまま半分になる。**典型的な加速比は 2〜4 倍であって、8〜16 倍ではない。**

### 11-2　Bulk memory：しばしば見落とされる、大きな無料の昼食

```c
// ❌ バイトごとのループ：1 バイトにつき load 一つ + store 一つ
for (size_t i = 0; i < n; i++) dst[i] = src[i];

// ✅ memory.copy 一命令にコンパイルされる → エンジンがホストの memcpy（SIMD 化・整列の最適化済み）へ写す
memcpy(dst, src, n);
```

**`memory.copy` / `memory.fill` は Wasm 2.0 からの核心の命令であり**、エンジンはそれらを高度に最適化された native の `memcpy`／`memset` へ直に写す。**大きな塊の移動では、差が桁になりうる。** ツールチェーンで bulk memory が有効かを確かめよ（現代のツールチェーンは既定で有効である）。

### 11-3　codegen の層の、その他の梃子

| 機能 | 効き | 備考 |
|---|---|---|
| **分岐ヒント**（Wasm 3.0） | 熱い経路を fall-through に置かせる | PGO か `likely()` の注釈が駆動する |
| **末尾呼び出し** `return_call` | 深い再帰でスタックが溢れず、スタックフレームも省ける | インタプリタ、状態機械が最も得をする |
| **Multi-value** | 複数の戻り値がメモリを経由しなくてよい | load/store の往復が減る |
| **Relaxed SIMD** の `relaxed_madd` | ハードウェアの FMA へ写る | ⚠️ **決定性を犠牲にする**（付録 M §7） |
| **型付き関数参照**（Wasm 3.0） | 間接呼び出しで実行時の署名の検査が省ける | 仮想関数の密集した C++/OOP が得をする |

## 12. 定常状態の性能その二：メモリとキャッシュ

**第 6 章はあの要となる事実を述べた：L1 に当たればおよそ 4 周期、DRAM へのアクセスはおよそ 200 周期。** ゆえにメモリの配置の影響は、しばしば命令の層の最適化を上回る。

### 12-1　AoS ではなく SoA

```rust
// ❌ AoS：x の平均を出すだけで y、z までキャッシュへ引きずり込む
struct Particle { x: f32, y: f32, z: f32, vx: f32, vy: f32, vz: f32 }
let particles: Vec<Particle>;

// ✅ SoA：xs だけを走査する。完璧なキャッシュの局所性であり、自動ベクトル化の前提でもある
struct Particles { xs: Vec<f32>, ys: Vec<f32>, zs: Vec<f32>, /* ... */ }
```

### 12-2　Arena / bump の確保器

**Wasm では `malloc` が相対的に高くつく**（それはコンパイルされて入ってきた利用者空間の実装であり、オペレーティングシステムの助けがない）。**確保の型が「一フレーム／一要求を処理するあいだにたくさん確保し、終わったら全部捨てる」なら、bump の確保器が圧倒的に勝つ**：

```rust
struct Bump { buf: Vec<u8>, top: usize }
impl Bump {
    #[inline] fn alloc(&mut self, n: usize, align: usize) -> *mut u8 {
        let p = (self.top + align - 1) & !(align - 1);
        self.top = p + n;                       // 確保 = 足し算一回
        unsafe { self.buf.as_mut_ptr().add(p) }
    }
    #[inline] fn reset(&mut self) { self.top = 0; }   // 全部の解放 = 代入一回
}
```

**それは体積の最適化でもあり**（`-sMALLOC=none` や極小の確保器と組み合わせられる）**性能の最適化でもある。**

### 12-3　三つの具体的な罠

| 罠 | 説明 |
|---|---|
| **熱い経路の `memory.grow`** | 既存のすべての `TypedArray` の視野を無効にし、大きなメモリの写し直しを引き起こしうる。**上限をあらかじめ確保し、ループの中で伸ばさせるな。** |
| **整列のヒント** | `i32.load align=2` は**ヒント**であって保証ではない——誤って宣言しても trap しないが、エンジンがそのせいで遅い符号を出しうる。**コンパイラに埋めさせよ。** |
| **ページをまたぐ無作為なアクセス** | 線形メモリが大きいと、無作為なアクセスは TLB のミスを頻発させる。**整列できるなら整列し、分割できるなら分割せよ。** |

## 13. 定常状態の性能その三：境界

**第 2 章は「境界は料金所である」と言った。ここでは実際に料金を下げる手を挙げる。**

```javascript
// ❌ 毎回、新しい Uint8Array を確保して文字列を符号化する
const bytes = new TextEncoder().encode(str);
const ptr = wasm.alloc(bytes.length);
new Uint8Array(wasm.memory.buffer, ptr, bytes.length).set(bytes);

// ✅ encodeInto で Wasm のメモリへ直に書く。中間の確保は零
const view = new Uint8Array(wasm.memory.buffer, ptr, cap);
const { written } = new TextEncoder().encodeInto(str, view);
```

**五つの規則**：

1. **まとめて渡す**：`process_pixel()` を百万回ではなく、`process_image(ptr, w, h)` を一回。
2. **`encodeInto` / `decode` は視野を再利用し**、毎回の確保を避ける。
3. **結果は環状のバッファで返す**。事象ごとに呼び戻しを一つ、ではなく（物理エンジンとゲームループの定石である）。
4. **JS のオブジェクトは `externref` で持つ**。「JS のオブジェクト ↔ 整数の handle」の脇の表を自作しない（その表の保守の費用と漏れの危険はどちらも小さくない）。
5. **境界を越えた回数そのものを測る**：糊に計数器を一つ足せば、それが思っていたより一桁多いことにしばしば気づく。

## 14. 定常状態の性能その四：並行

```javascript
// Worker のプール + SharedArrayBuffer（クロスオリジン隔離が要る。第 5 章参照）
const mem = new WebAssembly.Memory({ initial: 256, maximum: 4096, shared: true });
// どの Worker も同じ Module と同じ共有メモリで実体化する
```

**実務の三つの要点**：

1. **Worker の数は `navigator.hardwareConcurrency` を使うが、余裕を残せ**（メインスレッドは描画もする）。実務ではよく `max(1, hc - 1)` を使う。
2. **メインスレッドで `Atomics.wait` はできない**（仕様が禁じている）。**`Atomics.waitAsync`** を使うこと。
3. **仕事を切る粒度**は、同期の費用を上回るほど大きくせねばならない——**細かすぎる並行は単一スレッドより遅い**。これは native より Wasm のほうが顕著である。Worker をまたぐ調整が JS を経由するからだ。

**データが切り分けられるなら、第 8 章のシナリオ 3 へ戻れ**：**複数インスタンスの隔離にはクロスオリジン隔離が要らず**、しばしばより割に合う並行の道である。

## 15. 測ること：あなたに誤らせる罠が一つある

**⚠️ クロスオリジン隔離がないとき、`performance.now()` の分解能は落とされる。**

これは Spectre の余波のもう一つの帰結である（第 3 章）：**隔離されていないページではタイマの分解能が粗くされ**（実装によって違うが、よくある桁は数十から数百マイクロ秒）、**隔離してはじめてマイクロ秒級へ戻る**。

**つまり**：

- マイクロ秒級の操作（一度の境界越えの呼び出し、小さな関数）を測るのは、**隔離されていないページではそもそも不可能である。**
- **一度の `performance.now()` の差で小さな操作を測るな**——一万回走らせて総時間を取り、割ること。
- 二つのビルドを比べるときは、**双方の隔離の状態が同じかを確かめよ**。さもないと比べているのはコードではなく、タイマの精度である。

```javascript
// 正しいマイクロベンチマークの形
function bench(fn, iters = 100_000) {
  fn(); fn(); fn();                       // 暖機（TurboFan の tier-up を終わらせる）
  const t0 = performance.now();
  for (let i = 0; i < iters; i++) fn();
  return (performance.now() - t0) / iters; // 一回あたりの平均
}
```

**プロファイルの作業の流れ**（付録 M §10 で述べた。ここでは三つ補う）：

- **`name` セクションを残せ**。さもないとフレイムグラフは `wasm-function[1234]` だけになる（`wasm-opt --strip-debug` は name を残し、DWARF だけを剥ぐ）。
- **バックエンドでは `perf` を使え**：Wasmtime は perf/jitdump の対応情報を出せるので、Wasm の関数名が見える。
- **「境界を越えた回数」と「確保の回数」を測れ**。時間だけを測るな——そちらこそ、そのまま行動に移せる指標である。

## 17. アンチパターンの一覧

| アンチパターン | なぜ誤りか |
|---|---|
| 測らずに旗をいじりはじめる | 八割は違う場所をいじっている（Data セクションが半分なら、Code を圧しても効かない） |
| `opt-level="z"` と SIMD の自動ベクトル化を同時に求める | **`-Oz` はベクトル化を切る**。両立しない |
| Wasm を「より速いライブラリ」と見て、関数ごとに JS を置き換える | 個々の関数は速くなるが、全体は遅くなる——**境界越えの回数が爆発する** |
| 熱いループの中で JS を呼ぶ | 毎回が料金所である。ループごと Wasm へ移せ |
| 体積のために `wee_alloc` を使う | **すでに保守されておらず、既知の問題がある** |
| 隔離されていないページでマイクロ秒級の操作を測る | **タイマの精度が落とされている**。測っているのは雑音である |
| 起動の直後にベンチマークを回す | 測っているのは Liftoff の最適化されていない符号である |
| 30 MB のモデルの重みを `.wasm` へ同梱する | それはキャッシュできる資産であって、コードではない |
| 更新の体積のためにモジュールを切りすぎる | **圧縮辞書転送**（§7-2）がすでに解いているかもしれない。一方で分割の代価は残る |
| 公開版で何も考えず記号を全部 `strip` する | 本番で落ちたとき何も追えない——**記号つきのビルドを一本残せ** |
