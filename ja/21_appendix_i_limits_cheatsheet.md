# 付録I：制約と限界のクイックリファレンス

> ぶつかるすべての壁を一ページで見る。**各項目に「これは仕様の制約か、エンジンの制約か、実務上の推奨か」を明記してある**——回避のしやすさがまったく違うからだ。

---

## 1. サイズとメモリ

| 項目 | 数値 | 性質 | 回避の仕方 |
|---|---|---|---|
| 線形メモリのページサイズ | **64 KiB** | 仕様 | — |
| wasm32 のアドレス上限 | **4 GiB**（2³²） | **仕様。回避不能** | ストリーミングの分割、複数インスタンスの隔離、**複数メモリ**、Memory64 |
| ブラウザの実際のメモリ上限 | しばしば **2〜3 GiB** で OOM | エンジン（バージョン／プラットフォームで変動） | 初期メモリを下げる、分割して処理する |
| wasm64 のアドレス上限 | 2⁶⁴（理論） | 仕様 | **代価：ガードページの無料の境界検査を失う** |
| `.wasm` のファイルサイズ（ブラウザ） | 硬い限界は 1〜2 GB 級 | エンジン | — |
| `.wasm` のファイルサイズ（実務上の推奨） | **10〜30 MB 以内** | **実務上の推奨** | **先にデータを削る**、`wasm-opt -Oz`、モジュール分割、Brotli |
| 実際の参照値（FluffOS のドライバ） | **3.6 MB 生 / 0.8 MB Brotli**。ICU データ 30 MB→780 KB | 実測 | 付録 L 参照 |
| `.wasm` のファイルサイズ（バックエンド） | 明確な上限なし | — | 物理メモリに支配される |
| `memory.grow` の方向 | **増やすだけ。縮められない** | 仕様 | 使い終わったらインスタンスごと捨てる（マイクロ秒級） |
| アドレス 0 | **合法で読み書きできる**（ヌルポインタの保護なし） | 仕様 | Emscripten は低位アドレスをトラップ領域として予約できる |

## 2. スレッドと並行

| 項目 | 制約 | 性質 |
|---|---|---|
| Wasm がネイティブにスレッドを作ること | **できない**。ホスト（Web Worker / OS スレッド）に頼るしかない | 仕様 |
| 共有メモリ | `SharedArrayBuffer` + マルチスレッドの機能が要る | 仕様 |
| `SharedArrayBuffer` の前提 | **クロスオリジン隔離**（COOP と COEP の二つの HTTP ヘッダ） | ブラウザのセキュリティポリシー |
| GitHub Pages でのヘッダの設定 | **許されない** | プラットフォームの制約 |
| 回避の仕方 | `coi-serviceworker`（フロントでヘッダを合成する）、あるいは複数インスタンスの隔離へ切り替える | — |
| 複数インスタンス隔離のメモリ | **4 GiB × N**（それぞれ独立） | — |
| 複数インスタンス隔離に隔離は要るか | **❌ 要らない** | — |

## 3. SIMD

| 項目 | 数値 | 対照 |
|---|---|---|
| Wasm SIMD のベクトル幅 | **固定 128 ビット（`v128`）** | x86 の AVX2 = 256、AVX-512 = 512。ARM の SVE は可変 |
| 典型的な加速比 | **2〜4 倍**（4〜16 倍ではない） | メモリ帯域とデータの並べ替えが一部を食う |
| 検出は要るか | **要る**。古いブラウザにはない | 非 SIMD の予備ビルドを用意する必要がある |
| Relaxed SIMD | 意味論を緩めて性能を買う。**結果がプラットフォームによって異なりうる** | チェーン上／決定性を要する場面では禁止せねばならない |

## 4. 境界（JS ↔ Wasm）

| 項目 | コスト |
|---|---|
| `i32` を一つ渡す | ほぼ無料（ナノ秒級） |
| 文字列を一つ渡す（往復） | **符号化・復号二回 + コピー二回 + 境界越えの呼び出し三回**（マイクロ秒級に達しうる） |
| `postMessage` の構造化複製 | O(n) |
| `postMessage` + Transferable | **O(1)**（所有権の移転。元の側は即座に無効になる） |
| `SharedArrayBuffer` | O(1)（双方から同時に見える。隔離が要る） |
| DOM の直接操作 | **できない**。JS を経由せねばならない |
| **黄金律** | **境界を粗く、往復を少なく** |
| 同期のコードが非同期の API を待つ | **JSPI**（Chrome 137+／FF 139+）が Wasm のスタック全体を中断する。退路は Asyncify（高い） |

## 5. ストレージ

| 機構 | 永続 | ランダムアクセス | 線形メモリを食う | メインスレッドで可 | 適用 |
|---|---|---|---|---|---|
| **MEMFS** | ❌ | ✅（メモリ内で） | **✅ 致命的** | ✅ | 一時的な中間ファイル |
| **IDBFS** | ✅ | ❌（一括の巻き戻し） | 同期時に食う | ✅ | ゲームのセーブ、設定（< 数 MB） |
| **OPFS（async）** | ✅ | 限定的 | ❌ | ✅ | 一般のファイル |
| **OPFS（sync handle）** | ✅ | **✅ 本物の pread/pwrite** | ❌ | **❌ Worker のみ** | データベース、大きなファイル、ストリーミング |
| **WASI（バックエンド）** | ✅ | ✅ | ❌ | — | サーバサイド |

**追加の制約**：OPFS は同一ファイルに既定で **一つ**の sync access handle しか持てない（排他ロック。`{mode:"readwrite-unsafe"}` で複数開けるが、並行制御の責任はあなたに移る）。`persist()` していないデータはディスク圧で追い出されうる。ユーザには OPFS が見えないので、書き出しの機能を自前で用意せねばならない。

## 6. 言語と実行環境の負担

| 言語 | 典型的な Hello World のサイズ | 向くかどうか |
|---|---|---|
| Rust / C / C++ / Zig | 数 KB〜数十 KB | **★ 生まれつきの相性** |
| AssemblyScript | 数 KB | ★ フロントエンドの滑らかな入口 |
| Go（標準ツールチェーン） | 〜1.5 MB+ | ⚠️ サイズが主な痛点（TinyGo で大幅に縮む） |
| C# / Blazor | 数 MB 級 | ⚠️ エコシステムは強い。コールドスタートとサイズが代価 |
| Java / Kotlin | 従来は極大 | **Wasm GC が着地して初めて実用になった** |
| Python (Pyodide) | 30〜50 MB の一式 | 「科学計算のエコシステム全体が要る」ときだけ割に合う |

**実行性能の二層の現実**（Pyodide を例に）：純粋な Python のループはネイティブの約 **1/3〜1/5**。NumPy の C カーネルの呼び出しは約 **70%**。**仮想機械の中でインタプリタを走らせる、抽象の二層の重なりである。**

## 7. 仕様のレベルで「存在しない」もの

| 存在しないもの | 帰結 | 対応する提案 |
|---|---|---|
| `goto` / 任意ジャンプ | コンパイラが CFG を構造化せねばならない（Relooper/Stackify）。少数の非簡約ループが遅くなる | multi-loop（未着地） |
| 文字列型 | 往復のたびに符号化・復号が要る | JS String Builtins |
| オブジェクト / ガベージコレクション（MVP にはなかった） | 高水準言語が自前の GC を持ち込む → サイズが爆発 | **✅ Wasm 3.0 に入った** |
| 例外処理（MVP にはなかった） | C++ の try/catch が JS のトランポリンに頼る | **✅ Wasm 3.0 に入った**（Tag セクション + `try_table`/`exnref`） |
| 末尾呼び出し（MVP にはなかった） | 関数型言語の深い再帰がスタックを溢れさせる | **✅ Wasm 3.0 に入った**（`return_call`） |
| ブロッキング／非同期の待機 | 同期の C のコードが Promise を待てない | **JSPI**（2025-04 標準化、Chrome 137+／FF 139+） |
| システムコール | あらゆる能力をホストが import せねばならない | **WASI** |
| ASLR / NX / stack canary | **線形メモリ内部の C のメモリエラーがむしろ安定して悪用可能でありうる** | なし（ASan/UBSan で補う） |
| 実行時のリフレクション / 動的読み込み（核心） | 静的リンクにより重複した同梱が起きる | dynamic linking（Emscripten は独自の方式を持つ） |

## 7b. 配備層の必須チェック

| 項目 | 要求 |
|---|---|
| MIME | `Content-Type: application/wasm`（さもないと `instantiateStreaming` が端的に拒否する） |
| 差分更新 | 圧縮辞書転送（RFC 9842、`dcb`/`dcz`）：改版時に差分だけを送る（付録 N §7-2） |
| ⚠️ タイマの精度 | **クロスオリジン隔離がないと `performance.now()` の精度が落とされる**——マイクロ秒級の操作は正確に測れない（付録 N §15） |
| CSP | `script-src 'wasm-unsafe-eval'`（Chrome 97+／FF 102+／Safari 16+） |
| 圧縮 | `Content-Encoding: br`（Wasm の圧縮率はたいてい良好で、4 倍以上がよくある） |
| 完全性 | **`fetch()` で読み込む `.wasm` に SRI は内蔵されていない**。自前でハッシュを検証するとストリーミングコンパイルを犠牲にする |
| コードキャッシュ | `.wasm` に安定した URL を与える（内容ハッシュのファイル名が最良）。再訪でコンパイルを飛ばせる |
| 複数の Worker | `WebAssembly.Module` は構造化複製できる——**一度コンパイルして N 個の Worker へ postMessage する** |

## 8. セキュリティの赤線

| 赤線 | なぜか | 検査の仕方 |
|---|---|---|
| **ハードコードされた鍵** | 文字列は Data セクションにあり、**剥がせない** | `strings app.wasm \| grep -Ei 'sk-\|AKIA\|password\|secret'` |
| **中核の商業機密のアルゴリズム** | 逆解析が押し上げるのはコストであって可能性ではない | 問え：相手が明日それを手に入れたら、私に何が残るのか |
| Export セクション | **仕様で強制され、つねに見える** | `wasm-objdump -x app.wasm` |
| 「クライアントの自己完全性検証」 | クライアントは信頼できず、いかなる自己証明もローカルで書き換えられる | 認可の判定をサーバ側へ置く |

**逆解析の難度の六つの層**（第 9 章参照）：文字列を読む（秒）→ Export を見る（秒）→ WAT へ逆アセンブル（分）→ 疑似コードの復元（時間）→ アルゴリズムの理解（日〜週）→ 保守可能なソースへの復元（月以上。たいてい割に合わない）。

## 9. 性能の主張を読むための規律

| よくある主張 | 実際 |
|---|---|
| 「Wasm はネイティブの 60〜80% の性能」 | **ワークロードの形による**：純粋な数値ループは 90%+ に達しうる。手書き AVX2 を移植すると 40〜50% しかないこともある。細かい境界越えの呼び出しは JS より遅いこともある |
| 「JS より 10〜30 倍速い」 | 特定のベンチマークでのみ成立する。V8 が十分ウォームアップし型が安定していれば、**JS は Wasm に迫り、差はしばしば 1〜2 倍以内である** |
| 「Docker より 100 倍速い」 | **コールドスタートを指すなら信じられる**。定常状態の実行性能はコンテナ内のネイティブバイナリ**より低い** |
| 「ファイルは数 KB から数 MB しかない」 | 純粋な計算カーネルの話である。OpenCV.js は 6〜9 MB、solc は 10〜15 MB、Pyodide は 30〜50 MB |
| 「Wasm はメモリ安全」 | **サンドボックスの境界**の安全（ホストを害せない）を指すのであり、**あなたの C プログラムにメモリエラーがないことを意味しない** |
| 「Wasm は不可逆」 | **誤り。** 形式は公開され構造化されており、逆アセンブルは x86 の逆解析よりはるかに容易である |
| 「Wasm GC を有効にすればサイズが 80% 減る」 | 「もともと言語の実行環境を同梱していた」言語（Java/Kotlin/Dart）にしか成り立たない。**Rust/C/C++ にはほぼ無効である** |
| 「GC／memory64／末尾呼び出しは提案である」 | **すでに古い。** これらは **2025-09 の Wasm 3.0** で核心仕様へ入った（付録 A 参照） |
| 「Wasm を使ったから定数時間である」 | **誤り。** 定数時間はソースの書き方が保証するのであり、Wasm はより制御しやすい基盤を提供しているにすぎない |
