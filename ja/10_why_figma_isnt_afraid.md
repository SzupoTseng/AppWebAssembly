# 第10章：Figma がなぜ恐れないのか——ローカル私設サーバから、クラウドの中核へ

> **「Figma が Wasm なら、あれも全部見られているのでは？」**
> そのとおり。`figma.wasm` のバイナリはすべてのユーザのブラウザへ完全にダウンロードされ、理論上は完全に「見られている」。
> **では、なぜ今日まで世界のどの企業も、どのハッカー集団も、そっくり同じ Figma を模倣できていないのか。**
> Figma がアーキテクチャ設計において、「低水準機械語の難読化」と「バックエンドのリアルタイム協調ネットワークスタック」を極限まで結びつけ、**物理級の商業的な濠**を築いたからである。

## シナリオ 1　第一の防衛線：数百万行の C++ という「バイナリの天書」

**背景**：Figma の中核バイナリは圧縮後で数十 MB に達し、その中には極度に最適化された数百万行の C++ が入っている。

**構造は完全に平坦化されている**：Figma はコンパイル時に最高等級の **Link-Time Optimization (LTO)** を有効にしており、C++ のクラス、継承関係、変数名、関数名はすべて消され（strip）、数百万条の平坦な `i32.add`、`local.get` という仮想機械の低水準命令へコンパイルされている。

**リバースエンジニアリングの修羅場**：ハッカーが逆解析ツール（Ghidra など）で `figma.wasm` に噛みつけば、目にするのは巨大で意味を欠いた低水準の状態機械である。この数百万条の命令から Figma 独自の「**ベクターネットワーク（Vector Networks）**」アルゴリズムのロジックを逆算する作業量とコストは、**ゼロから新しいソフトを一式書くよりはるかに大きい。**

**ここには技術的な補足を一段入れる価値がある。「規模」そのものがどう防御になるかを説明するからだ**：

| 逆解析の難度の源 | なぜ規模がそれを指数的に難しくするのか |
|---|---|
| **LTO が関数境界を掻き乱す** | コンパイル単位を越えたインライン展開により、「一つの関数 = 一つの論理単位」という前提が失効する。目にする一つの Wasm 関数は、元は五つの C++ 関数が融合した産物かもしれない |
| **テンプレートの実体化爆発** | C++ のテンプレートは型ごとに特殊化コードを生む。逆解析者が目にするのは、ほぼ同じに見えて微妙に違う二十個の関数だが、ソースにはテンプレートが一つあるだけである |
| **型もなく、構造もない** | `struct Node { id, parent, children, transform, style }` は Wasm では `i32.load offset=24` にしか残らない。すべてのアクセス箇所からこの構造のフィールド配置を逆算せねばならない |
| **制御フローが構造化のために書き換えられている** | コンパイラは Wasm の構造化制御フロー（第 2 章）に合わせるため、状態変数と `br_table` を導入し、元は明快だったループとジャンプを変形させる |
| **規模そのもの** | 1,000 行の逆解析は週末のプロジェクトである。100 万行の逆解析はチーム数年の工事であり、しかも**領域一つを丸ごと理解せねばならない**（ベジェ曲線のブール演算、フォント組版、差分レンダリング） |

**この防衛線の本質は「不可能」ではなく「割に合わない」である**——三年かけて、完全には理解できず保守もできないコードを逆算するくらいなら、同じ時間で自分で一式書いたほうがよい。**そしてそれこそが防御成功の定義である。**

## シナリオ 2　第二の防衛線：中核の商業的障壁はバックエンドにある

**背景**：これこそ Figma の最も致命的な濠である——**Figma はスタンドアロンの描画ソフトではなく、多人数リアルタイム協調システムである。**

**フロントの Wasm の職責**：密な計算だけを担う。マウスで四角をドラッグすれば、Wasm が幾何行列を極限の速度で計算し、フォント組版を処理し、WebGL で滑らかな 60 FPS の画面を描く。

**バックエンドサーバの職責**：多人数が同じキャンバスの同じレイヤーを同時に編集するとき、データは絶対に衝突してはならない。Figma のバックエンドは **CRDT（Conflict-free Replicated Data Type、競合のない複製データ型）** に基づく分散ネットワークエンジンを一式持っている。

**CRDT がなぜ本物の濠なのか**（「バックエンドにサーバがある」よりずっと深い話である）：

```
問題：A と B が同じレイヤーを別方向へ同時にドラッグし、しかもネットワークに遅延がある。
      最終的に両者の画面は一致せねばならず、どちらの操作も「消えて」はならない。

素朴な解法：最後に書いた者が勝つ（last-write-wins）
        → 誰かの操作が消え失せ、ユーザは激怒する

Figma の解法：文書モデルに「操作が可換な」データ構造を設計する
        → 操作がどんな順序で届いても、同じ状態へ収束する
        → レイヤーツリーの親子関係、属性、並び順——どれもマージの意味論を個別に設計せねばならない
        → しかもオフライン編集、履歴の遡行、権限の交錯、大きな文書の差分同期を扱わねばならない
```

**この代物の難しさはアルゴリズムの論文にではなく、無数の境界事例の中にある**：二人が同時に A を B へ、B を A へドラッグしたら循環が生じないか。一人が三時間オフラインで編集して戻ってきたらどうマージするか。バージョン履歴を CRDT の上でどう表現するか。**これらは数年と数十人のエンジニアの製品経験がなければ磨けないものであり、しかもそのすべてがサーバ上にあり、一行もあなたのブラウザへダウンロードされていない。**

**防御の境界**：ハッカーがフロントの `figma.wasm` を盗んでも、手に入るのは「**魂のない空のレンダラ**」だけである。バックエンドの強力で秘匿された分散協調ホストの支援がなければ、この Wasm はそもそも動かない。

## シナリオ 3　第三・第四の防衛線：平文データの不在と、法律

**第三：Wasm のコード内に「平文データを一切含まない」**

前述のとおり、Wasm の中で最も底が割れやすいのは平文文字列である（第 9 章の禁域その一）。Figma はこの点で極めて厳格な情報セキュリティの隔離を行っている。

- Figma の Wasm 内には **API キーもパスワードもハードコードされた文字列も一切書かれていない。**
- ユーザのデータ、レイヤーの構造、さらには UI のテキストラベルまで、すべて**実行時に**、暗号化された WebSocket チャネルを通じて Figma のサーバから動的にストリーミングされ Wasm の線形メモリへ注ぎ込まれる。
- **ハッカーが `.wasm` だけを取っても、その中にはユーザデータのアルファベット一文字すら見つからない。**

**この設計にはもう一つ注目すべき副作用がある**：UI のテキストも動的に注入されるので、`.wasm` の中には「このボタンは何という名前か」さえない——**逆解析者は最も基本的な意味の錨（逆解析実務が最も頼るのが文字列定数である）すら手に入らない。** リバースエンジニアリングの実務において、文字列は最も重要な道標である。それを抜き去れば、難度は倍どころではない。

**第四：商業と法律という物理的防衛線**

- **ブラックボックス資産の認定**：もしどこかの会社が本当に模倣版を出したら、Figma の法務とセキュリティのチームは相手のネットワークパケットを解析するか、**バイナリの特徴照合（binary signature matching）**を使えば、相手が Figma のコンパイルした特定の Wasm コード片を盗用したかどうかを判定できる。
- **高価な訴訟**：バイナリコードの盗用が発覚すれば、知的財産権の訴訟と関連する法的責任に直面する。**まともなテクノロジー企業でこの危険を冒す者はいない。**

> ⚠️ 真偽の注意
> 本章の Figma のアーキテクチャに関する記述は、**一部は Figma が公開した工学ブログに基づき（Wasm への移行、多人数協調、レンダリングパイプラインといった主題には確かに公式記事がある）、一部は技術的な筋道からの合理的な推論である**（「UI のテキストがすべて動的にストリーミングされる」「バックエンドがバイナリの特徴照合を行う」といった具体的な実装の細部を Figma は公に認めていない）。**これはアーキテクチャパターンの一例として読んでほしく、Figma 内部設計の権威的な記述としてではない。** また「ベクターネットワーク（Vector Networks）」は確かに Figma が公に宣伝する中核技術の特色だが、その具体的なアルゴリズムは公開されていない。

> 💡 座右の一言
> **何かを大らかに送り出すとき、それがあなたの手を離れたあと「不完全」であることを保証せねばならない。** Figma は毎日、最も中核的なコンパイルエンジンを世界中の数億台のコンピュータへ送り出しながら、なお枕を高くしていられる。頼っているのは隠すことではなく、**それを二つに割って、使えないほうの半分だけを送り出すこと**である。これは自然界のいたるところで見られる戦略だ。種は風に乗って散ってよい。発芽には土壌が要るからだ。蜂の巣の蝋は一片ずつ公開されているが、価値は蜂の群れの組織にある。この原理は、オープンソースにしたい人、API を公開したい人、クライアントを配布したい人のすべてに成り立つ：**すべてを隠す必要はない。持ち去られる部分が、あなたのもう半分なしでは死んでいることを保証すればよい。** そして「どちらの半分が生きているか」を設計することこそ、アーキテクトの最も重要な仕事である。

## シナリオ 4　最も鋭い追撃：逆コンパイルせず、ただローカルで動かしたら？

**背景**：この調査全体で最良の問いである。ソフトウェア工学で最も古典的な「ローカルでの解除とオフラインライセンス」の穴を突いているからだ。

> **「ダウンロードできるのなら、完全な逆コンパイルなど要らない。ダウンロードしてローカルで動かせば、Figma は元のビジネスモデルを完全には続けられなくなるのでは？」**

**フロントエンドのコードだけを見るなら、この推論は正しい**：ハッカーは完全な逆コンパイルなど要らず、ローカルで簡単な Node.js サーバを書いて Wasm を動かせば（俗に local splicing と呼ばれる）、ソフトは動くように見える。

**それでも Figma が恐れないのは、設計の当初から「ネットワークの位相構造」と「中核のビジネスモデル」をクラウドへがっちり縛りつけたからである。** ハッカーが `figma.wasm` をダウンロードしてローカル（`localhost`）で無理やり実行しても、以下の四つの物理級の防御が、破解版を商業的に無価値にする。

### 防御その一：ファイルがそもそもローカルに保存されていない

**従来のスタンドアロンソフト（Photoshop、AutoCAD）が完璧に破られてオフラインで使えるのは、ファイル（`.psd`、`.dwg`）がユーザ自身のディスクにあるからである。**

**Figma の設計は正反対である**：Figma のキャンバスとプロジェクトファイルは、あなたのコンピュータのディスクに**まったく存在しない**。あなたが見ている画面は、バックエンドのデータベースがレイヤーを巨大なバイナリのノードストリームへ変え、Wasm の線形メモリへ動的に転送して描画したものである。

**物理的な断層**：ハッカーがローカルの `localhost` で `figma.wasm` を実行するとき、この仮想機械のメモリは**絶対的に空っぽ**である。ローカルの私設サーバには Figma クラウドのあの巨大なデータベースと分散ファイルストレージのクラスタがなく、**開くべきプロジェクトファイルも読むべきものも何一つない。**

**この一文は三秒立ち止まって考える価値がある**：ファイルのない描画ソフトとは、何一つ開けない永遠の白紙である。**破解者が手に入れるのは無料の Figma ではなく、空白のキャンバスプログラムである。**

### 防御その二：中核の計算力はクラウドに残る

Figma はソフトの機能の 100% を Wasm へコンパイルしてはおらず、厳格な**計算力の分割**を行っている。

| ローカルの Wasm が担う | クラウドのバックエンドが担う |
|---|---|
| UI の対話とリアルタイム描画（マウスのドラッグ、ベジェ曲線の制御、WebGL の描画） | チームの権限検証 |
| 幾何行列の演算、フォント組版 | フォントライブラリの動的読み込み |
| | 複数ファイルのバージョン管理と履歴の遡行 |
| | **CRDT の多人数リアルタイム同期エンジン** |
| | アセットライブラリ、コンポーネントライブラリ、デザインシステムの配布 |

**破解版の代価**：ハッカーがローカルでこの Wasm を動かして手に入れるのは、「**チームを招待して協働できず、ファイルを保存できず、自動更新もなく、バージョン記録もなく、カスタムフォントも読み込めない**」不具合だらけのスタンドアロン描画板である。Figma の最も中核的な有償顧客（企業のデザインチーム、プロダクトマネージャ、フロントエンドエンジニア）にとって、こんな破解版は**本当の産業的生産にはまったく投入できない。**

### 防御その三：買っているのはソフトではなく「協働の効率」である

Figma のビジネスモデルは **B2B SaaS** であり、課金対象は個人のフリーランスデザイナーではなく「テクノロジー企業の製品開発チーム全体」である。

- **企業の痛点**：企業が従業員一人あたり毎月の購読料を払う気になるのは、「四角と丸を描く機能」を買うためではなく、「デザイナーが描き終えたら、プロダクトマネージャがすぐオンラインでコメントでき、フロントエンドエンジニアがワンクリックで CSS をコピーできる」という**協働の効率と信頼の境界**を買うためである。
- **私設サーバの致命傷**：購読料を浮かせるために、ハッカー製の「ローカル破解版 Figma」を従業員にダウンロードさせるまともなテクノロジー企業は一つもない。多人数リアルタイム協働という魂を完全に失うだけでなく、企業は深刻な情報セキュリティの穴、知的財産権の訴訟、データ流出の危険に晒される。

### 防御その四：バックエンドによるクライアントの動的検証

現代のクラウドアプリケーションのバックエンドは、たいていこの防衛線を敷いている。

- **動的なハンドシェイク（handshake tokens）**：フロントの Wasm が起動してバックエンドと WebSocket 接続を確立するとき、バックエンドはクライアントの指紋と完全性を動的に検証する。
- **秒単位の遮断**：ハッカーがログインを迂回しようとフロントのコードを改変したり、認可されていないドメイン（`localhost` など）から接続を張ろうとすれば、バックエンドのセキュリティゲートウェイはそれを「偽造されたクライアント」と識別し、キャンバスデータのストリーミングを即座に拒否し、ローカルの Wasm をロード画面で固まらせる。

> ⚠️ 真偽の注意
> 防御その四が述べているのは業界でよくある手法（Origin の検査、トークンの結びつけ、クライアントの完全性証明）だが、**「Wasm のメモリのハッシュ値で動的に指紋検証する」といった具体的な手法は技術的に脆弱である**——クライアント側のいかなる自己検証もローカルの改変で迂回できる（これは「クライアントは信頼できない」という情報セキュリティの鉄則からの直接の帰結である）。本当に有効なのは**サーバ側の認可判定**（このトークンはどのアカウントのものか、支払っているか、このファイルの権限を持っているか）であって、クライアントの潔白の自己申告ではない。**防御の重心をクライアントの完全性検証に置くのは、よくあるが根本的に成り立たない設計である。**

> 🔍 踏み込んだ論評──「複製の防止」から「無用化」へ、ソフトウェア防護史上最大のパラダイム転換
> この章全体は、すでに完了しているのに多くの人がまだ気づいていない一つのパラダイム転換について語っている。**スタンドアロン時代の防護の目標は「複製させないこと」だった**——シリアル番号、ドングル、パッキング、オンライン認証、DRM。この戦いで守る側は三十年負け続けた。数学的に必敗だからだ：**完全で独立して動くものを相手の手に渡しておきながら、それを使うなと要求している。** これは自己矛盾した要求であり、破られるのは時間の問題である。**クラウド時代の防護の目標は「複製品を無用にすること」へ変わった**——クライアントを持ち去らせないのではなく、クライアントがサーバを離れたあと空の殻であることを保証するのだ。この戦いは守る側が勝つ。もはや矛盾したことを要求しないからである：**好きに持っていけ。もの自体は価値ではないのだから。価値はデータに、協働の関係に、あなたが繋げないあの線の中にある。** そしてこの転換は、すべてのプロダクトの人にとって重要な帰結をもたらす：**「複製の防止」は技術の問題であり、技術の問題はいつか破られる日が来る。「無用化」はアーキテクチャの問題であり、アーキテクチャの問題は一度正しく設計すれば、もう守る必要がなくなる。** だから「どうやってコードを守るか」に大量の労力を注いでいる自分に気づいたら、それはたいてい信号である——**価値がまだ間違った場所に置かれている、という信号だ。** 正しい動作は防御を強めることではなく、価値を引っ越させることである。
>
> しかしここにはまだ答えていないより深い問いがある：**Figma の濠がもはや技術ではなくデータ・協働・エコシステムであるなら、オープンソースコミュニティが技術部分を完全にコモディティ化したあと、この川はあとどれだけ守れるのか。** それこそ次章が扱うことである。

## 本章のまとめ

- Figma の第一の防衛線は**規模がもたらす逆解析コスト**である：LTO が関数境界を掻き乱し、テンプレートの実体化が爆発し、構造と型がすべて失われ、制御フローが書き換えられ、そこへ百万行の体量と領域の障壁が加わる——**逆解析の作業量はゼロから書き直すよりはるかに大きく、それこそが防御成功の定義である。**
- 第二の防衛線は**中核の商業的障壁がバックエンドにあること**である：CRDT のリアルタイム協調エンジンの難しさは論文にではなく無数の境界事例にあり、しかもそれは一行もブラウザへダウンロードされていない。**`figma.wasm` を盗んでも、手に入るのは魂のない空のレンダラだけである。**
- 第三は**バイナリの中に平文データが一切ないこと**（UI のテキストさえ実行時にストリーミング注入される）——これは逆解析が最も頼る意味の道標を同時に抜き去っている。第四は**法律とバイナリの特徴照合**である。
- 最も鋭い追撃「逆コンパイルせずローカルで動かす」は四つのことで塞がれる：**ファイルがそもそもローカルにない**（空白のキャンバス）、**中核の計算力がクラウドにある**（不具合だらけのスタンドアロン版）、**企業が買っているのは機能ではなく協働である**、**バックエンドによるクライアントの認可判定**（ただし注意：クライアントの自己検証は技術的に成り立たない。シナリオ 4 の ⚠️ 参照）。
- これは**すでに完了したパラダイム転換**である：「複製の防止」（技術の問題であり、守る側は必敗）から「無用化」（アーキテクチャの問題であり、正しく設計すればもう守らなくてよい）へ。
- **帰結**：「コードを守る」ことに大量の労力を注いでいる自分に気づいたら、それは価値が間違った場所に置かれている信号である。**正しい動作は防御を強めることではなく、価値を引っ越させることである。**

しかしこの濠は一つの前提の上に建っている——**技術的障壁が十分に高く、他人は短期間では作れない、という前提である。** その前提がもはや成り立たなくなったら？ 第 11 章へ。
