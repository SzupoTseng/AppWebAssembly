# 第2章：バイナリの物理学——マジックナンバーのあとの一バイトずつ

> どんな `.wasm` ファイルを開いても、冒頭は必ずこの八バイトである：`00 61 73 6D 01 00 00 00`。前半四つはマジックナンバー `\0asm`、後半四つはバージョン番号 `1`。**この八バイトより後のすべては、あなたを信用していない機械が、読み終える前にあなたが悪事を働かないと証明できるようにするためにある。**

## シナリオ 1　それは機械語ではなく、証明できる契約書である

**背景**：多くの人が Wasm に抱く第一印象は「コンパイル済みの機械語」である。この印象は誤りであり、しかも肝心なところで誤っている。**Wasm はいかなる物理 CPU の命令セットでもない**——x86 でもなく、ARM でもなく、RISC-V でもない。それは**仕様の上で定義された抽象スタックマシン**であり、この機械の性質は一つ残らず「検証可能性」に奉仕している。

**モジュールの物理構造**：一つの `.wasm` ファイルは複数の**セクション**が線形に並んだものである。各セクションは 1 バイトの ID で始まり、続いて LEB128 符号化された長さ、そして内容が来る。順序は仕様で強制されている。

| ID | セクション | 内容 |
|---|---|---|
| 1 | Type | すべての関数シグネチャ（`(i32, i32) -> i32` のような） |
| 2 | Import | ホスト環境から受け取るもの：関数、メモリ、テーブル、グローバル変数 |
| 3 | Function | 各関数が Type セクションのどのシグネチャに対応するか |
| 4 | Table | 関数参照テーブル（間接呼び出しのジャンプ先） |
| 5 | Memory | 線形メモリの初期ページ数と上限 |
| 6 | Global | グローバル変数 |
| 7 | Export | 外部へ公開する関数／メモリ／テーブル／グローバル |
| 8 | Start | インスタンス化後に自動実行される関数 |
| 9 | Element | テーブルの初期内容 |
| 10 | Code | 各関数の実際の命令とローカル変数 |
| 11 | Data | 線形メモリの初期データ |
| 12 | DataCount | データセグメント数（bulk memory 提案が導入。単一パス検証のため） |
| 0 | Custom | 任意のカスタムデータ（デバッグシンボル `name`、ソースマップへのリンク、言語固有のメタデータ） |

**この順序は美学ではなく工学である**：型は関数宣言に先立ち、関数宣言は関数本体に先立つ。これにより検証器は**頭から末尾まで一度走査するだけでよい**——命令を一つ読むたびに、必要な型情報はすべてすでに前方に現れている。だから Wasm の検証は **O(n) の単一パス線形時間**であり、だから**ダウンロードしながらコンパイル**できる。

**命令はどう動くか**：Wasm はスタックマシンである。`local.get 0` は 0 番のローカル変数をスタックへ積み、`i32.add` は二つを取り出して一つを積み戻す。二つの数を足す関数は、テキスト形式（WAT）ではこうなる。

```wat
(module
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a        ;; スタック: [a]
    local.get $b        ;; スタック: [a, b]
    i32.add)            ;; スタック: [a+b]
  (export "add" (func $add)))
```

対応する命令列は `20 00 20 01 6A`——五バイトである。`0x20` が `local.get`、`0x6A` が `i32.add`。**レジスタ割り当てもアドレッシングモードも命令プレフィックスもない**。だからきわめて緊密であり、同時にどんな実在の CPU 命令へも機械的に翻訳しやすい。

> **より正確に言えば**：この五バイトは**命令**であって、Code セクション内の完全な「関数本体」には、前にローカル変数宣言（この例では `00`、ローカル変数のグループがゼロという意味）を、末尾に `0x0B`（`end`）を加える必要がある——**この二バイトは仕様で強制されている**。モジュール全体のバイト単位の完全な解体（LEB128 符号化、型符号化表、常用オペコード早見を含む）は**付録 M 第 1 節**にある。

**検証器はロード時に何を検査しているのか**：これは Wasm のセキュリティモデルの核心であり、多くの人が思っているより検査項目は多い。

1. **スタック型の一貫性**：各命令の実行前後で、オペランドスタックの型列が静的に導出できなければならない。`i32.add` の直前、スタック頂上は**必ず** `i32` 二つでなければならず、`f64` でも空でもいけない。
2. **制御フローの構造化**：Wasm には**任意ジャンプ（goto）がない**。制御フローは `block` / `loop` / `if` の三種類のブロックと、`br` / `br_if` / `br_table` という**自分を囲むブロックのラベルへ外向きにしか跳べない**分岐だけである。これにより制御フローグラフは生まれつき簡約可能（reducible）であり、コンパイラは高価な非簡約ループ解析をしなくてよい。
3. **分岐地点でスタックの高さが一致すること**：同じラベルへ跳ぶすべての経路で、スタック上の型は同一でなければならない。
4. **ローカル変数の添字が範囲内**、**関数の添字が範囲内**、**間接呼び出しのシグネチャは実行時に照合される**（`call_indirect` の四つの検査と C++ 仮想関数の実装のされ方は付録 M 第 3 節）。
5. **メモリとテーブルへのアクセスは一律に境界検査される**（次節で詳述）。

**もう一つ、単独で挙げる価値のある巧妙な技がある**：`unreachable` のあとの死んだコードはどう検証するのか。仕様は「**多相スタック（polymorphic stack）**」を使う——unreachable 状態に入ったあと、検証器はスタックを「任意個数・任意型の値を供給できる」とみなす。こうすればどんな死んだコードも検証を通り、**しかも検証器は到達可能性解析をしなくてよい**。**特例のように見えるこの規則こそ、「単一パス O(n)」というより根本的な性質を守るためのものである**（詳しくは付録 M 第 2 節）。

**検証を通ったモジュールにはきわめて強い性質がある**：それは線形メモリの外のバイトを読み書きすることが**不可能**であり、任意のアドレスへ跳ぶことも、関数ポインタを偽造することも、呼び出しスタックを破壊することも（return address はエンジン自身のスタック上にあり、Wasm のコードは触れない）不可能である。**バッファオーバーフロー攻撃は Wasm ではサンドボックスを貫けない**——せいぜいこのモジュール自身の線形メモリ内のデータを壊せるだけだ。

> ⚠️ 真偽の注意（広く流布した誤解）
> 「Wasm はメモリ安全だ」という言い方は、**サンドボックスの境界という意味においてのみ成り立つ**。保証しているのは「Wasm モジュールがホストを害せない」ことであって、**あなたが C で書いたプログラムが Wasm の中でメモリエラーを起こさないことは保証していない**。実のところ事情はもっと微妙である。線形メモリは一枚の平坦な `ArrayBuffer` なので、**スタック保護（stack canary）、アドレス空間配置のランダム化（ASLR）、実行不可ページ（NX）といったネイティブプラットフォームの緩和策の多くが Wasm には存在しない**。x86 なら ASLR に阻まれるバッファオーバーフローが、Wasm では安定して悪用可能かもしれない——ただし破壊の範囲は当該モジュールの線形メモリ内に限られる。学術界にも明確な議論がある（"Everything Old is New Again: Binary Security of WebAssembly"、USENIX Security 2020 など）。**サンドボックスの安全 ≠ アプリケーションの安全。**

> 💡 座右の一言
> **セキュリティの最も安い実装は、守りを足すことではなく、能力を削ることである。** Wasm には `goto` がなく、レジスタがなく、生ポインタがなく、実行可能なスタックがなく、システムコールがない——これらの攻撃面を「守った」のではなく、**仕様のレベルでそもそも存在しない**のだ。守衛には金がかかる（実行時検査、CPU サイクル、複雑さ、そして守衛自身が抱えうるバグ）。存在しないことは無料であり、バグも生まない。この原理はシステム設計でもっと一般的な名前を持つ——**不正な状態を表現不能にする（make illegal states unrepresentable）。** セキュリティ設計をしていて「ユーザが X をしていないか検査する」と書いている自分に気づいたら、一歩下がって問うてほしい：**X を、型で、プロトコルで、データ構造で、そもそも書けなくできないか？** 削れるものは、守れるものより、つねに信頼できる。

> 🔍 踏み込んだ論評──構造化制御フローの代価と、誰も語らないコンパイルの難問
> 「goto がない」はセキュリティ設計に聞こえるが、コンパイラ作者にとっては災難であり、その解法が面白い。**問題はこうだ：現実のコードには goto がある。** C には `goto` があり、LLVM IR の制御フローグラフは任意の有向グラフであるのに対し、Wasm は入れ子ブロックからなる木構造しか受け付けない。任意の CFG を構造化制御フローへ還元することは、コンパイラ理論の古い問題（Relooper アルゴリズム）である。Emscripten は初期にこれに頼り、のちに Binaryen がより強力な **Stackify** アルゴリズムを加えた。代価は何か。**一部の非簡約ループ（irreducible loops）では、追加の状態変数と大きな `br_table` を導入して制御フローを「模倣」しなければならない**——これは元のコードより遅い命令列を生む。手書きアセンブリの多いプロジェクト（動画デコーダなど）を Wasm へ移植すると、性能の低下が予想より大きいのはこのためだ。**Wasm の命令が遅いのではなく、制御フローの表現力が足りず、コンパイラに迂回を強いているのである。** のちの **funclets / multi-loop 提案**はこの制約の緩和を議論したが、核心仕様はいまも構造化制御フローを手放していない——それが、検証器が単一パス線形時間で完了できる前提だからだ。**これは非常に典型的なトレードオフの事例である：あらゆる端末で検査が無視できるほど安く済むように、仕様はごく一握りの極端な場面の性能を犠牲にすることを選んだ。** どんな「安全な実行環境」を評価するときも、このトレードオフ点を探すべきだ——それは必ず存在し、必ずどこかであなたに噛みつく。

## シナリオ 2　線形メモリ：あの平坦で、伸びるだけで縮まない荒野

**背景**：Wasm のメモリモデルは原始的なほど単純である——**一続きの、アドレス可能なバイト配列**、これを線形メモリ（linear memory）と呼ぶ。**64 KiB を 1 ページ**とし、`memory.grow` 命令でページ単位に伸ばし、`memory.size` で現在のページ数を問い合わせる。

**JavaScript 側から見れば、それはただの `ArrayBuffer` である**：

```javascript
const { instance } = await WebAssembly.instantiateStreaming(fetch("app.wasm"), imports);
const mem = instance.exports.memory;                 // WebAssembly.Memory
const bytes = new Uint8Array(mem.buffer);            // Wasm のメモリ全体が直接見える
const ints  = new Int32Array(mem.buffer);            // 同じメモリの別の見え方
```

**この一点が、あらゆる Wasm 性能テクニックの根である**：JS と Wasm のあいだで**データを複製する必要はない**。両者は同じバイト列を見ているからだ。いわゆる「ゼロコピー」とは、このバッファの上に `TypedArray` でビューを開くことであって、データを運び回すことではない。

**その四つの物理的性質は、どれも後の章で噛みついてくる**：

1. **伸びるだけで、縮まない**。`memory.grow` はあるが `memory.shrink` はない。かつて 3 GB まで使った Wasm アプリケーションは、内部のデータ構造をすべて解放しても、**その 3 GB の `ArrayBuffer` はオペレーティングシステムの帳簿に残ったまま**であり、インスタンス全体が捨てられるまで消えない。長時間動く Wasm アプリケーションが「使い終わったらインスタンスごと捨てる」設計にするか、内部に自前のメモリプールを持つかのどちらかになるのは、このためである。
2. **伸長は `ArrayBuffer` の detach を招きうる**。`growable ArrayBuffer` を使わない従来の挙動では、`memory.grow` のあと**既存の `TypedArray` ビューはすべて無効になる**（buffer が detach される）。初心者が最も踏む地雷である。

```javascript
let view = new Uint8Array(mem.buffer);
instance.exports.allocate_lots();   // 内部で memory.grow が起きた
view[0] = 42;                       // ❌ TypeError／detach 済み buffer への書き込み
// 正解：grow を起こしうる呼び出しのあとは、毎回ビューを取り直す
view = new Uint8Array(mem.buffer);
```

3. **アドレスは添字であり、`0` は合法なアドレスである**。Wasm に「ヌルポインタ」の概念はない——アドレス 0 は線形メモリの最初のバイトであり、完全に読み書きできる。したがって C の「NULL 参照解決で segfault する」という保護は Wasm では**既定で存在しない**（Emscripten は `--low-memory-unused` のようなオプションで低位アドレスをトラップ領域として予約できるが、それはツールチェーンの当て木であって仕様の保証ではない）。
4. **境界外アクセスは必ずトラップする**。これは仕様の硬い保証である。現在のメモリサイズを超えたアドレスへ `i32.load` すれば、**捕捉不能なトラップ**が発生し、JS 側では `WebAssembly.RuntimeError` の送出として現れる。

**境界検査をどうやって遅くせずに行うか**：素朴な実装はすべての `load`/`store` の前に比較と分岐を挿入するが、それは受け入れがたいオーバーヘッドである。現代のエンジンは 64 ビットホスト上で美しい手を使う——**ガードページ（guard page）**。

> エンジンは仮想アドレス空間の中で、32 ビット線形メモリ一つにつき **8 GiB**（4 GiB のアドレス可能空間に、前後の保護領域を加えたもの）を予約するが、実際に使うページだけを読み書き可能として**コミット**する。アドレス計算は 32 ビットのオフセットで行うため、**数学的にその 4 GiB の予約領域を超えることは不可能**である。未コミットの領域へ触れた瞬間、OS のページング機構が SIGSEGV を発生させ、エンジンのシグナルハンドラがそれを受け止めて Wasm のトラップへ翻訳する。
> **結果：ホットパス上の境界検査命令数はゼロ。代価は MMU ハードウェアが無料で負担する。**

これは一つのことも説明する。なぜ Wasm は 32 ビットホストや一部の組み込み実行環境で目に見えて遅くなるのか——**そこには予約に足る仮想アドレス空間がなく、逐次の明示的比較へ戻るしかないからだ。**

> 💡 座右の一言
> **最も冴えた性能最適化は、たいてい最適化に見えず、もともと無料の何かに仕事を押しつけたように見える。** ガードページのこの手は何一つ「高速化」していない。ただ「アドレスが範囲外かを検査する」ことを、ソフトウェアから、**メモリアクセスのたびにどうせ回っている**ハードウェアである MMU へ移しただけだ——言い換えれば、その代価はすでに誰かが払っているので、境界検査の限界費用がゼロになった。この筋は系統工学のいたるところにある。mmap はファイル読み込みをページングに相乗りさせ、copy-on-write は fork を MMU に相乗りさせ、DMA は I/O をバスに相乗りさせる。**何かのオーバーヘッドに悩んだとき、最も価値のある問いは「どうすればもっと速くなるか」ではなく、「これは、すでに走っている何かの機構の副産物にできないか」である。**

> 🔍 踏み込んだ論評──4 GB という数字の三段階の進化と、その本当の障害物
> 線形メモリの 4 GiB 上限は `i32` アドレス（2³² バイト）から来る。この数字には実務上三層の天井があり、**互いを覆い隠す**ため、自分がどの層に当たったのか多くの人が分からなくなる。**第一層、仕様層：wasm32 は 4 GiB に固定されている。** これは数学であり、回避できない。**第二層、エンジン層：ブラウザはたいてい 4 GiB まで持たない。** V8 は単一の Wasm メモリに独自の上限を持ち（歴史的に 2 GiB〜4 GiB のあいだで変動し、プラットフォーム依存）、実務では 2〜3 GiB で先に OOM する場面が多い。**第三層、ページング層：`ArrayBuffer` は連続した仮想アドレス空間を必要とする。** 32 ビットブラウザや、アドレス空間が断片化した長時間稼働のタブでは、理論上の枠が残っていても、`memory.grow` は単に十分な連続領域が見つからずに失敗しうる。**局面を打開するのが Memory64（`i64` アドレス。Wasm 3.0 で核心仕様入り）**であり、理論上限は 2⁶⁴ へ上がる。しかし見落とされがちな代価がある：**アドレスが 64 ビットになった瞬間、先の「8 GiB の仮想空間を予約 + ガードページ」という無料の境界検査は成立しなくなる**——メモリごとに 2⁶⁴ の仮想アドレスを予約することはできない。したがって memory64 は多くの実装で**明示的境界検査へ戻らざるをえず**、相応の性能低下（ベンチマークにより数パーセントから二桁パーセントまで）を伴う。だから正しい心的モデルは「memory64 が出れば問題は消える」ではなく——**4 GiB 以下で享受しているのはハードウェアに補助された無料の安全であり、その線を越えた瞬間、安全は課金され始める**、である。アーキテクチャ判断への含意は直截だ：**分割ストリーミングや複数メモリ（第 8 章）で 4 GiB 以内に収まるなら、Memory64 へ急いで跳ぶ必要はない。**

## シナリオ 3　バイナリから機械語へ：階層型コンパイルと、見えないウォームアップ曲線

**背景**：ユーザが Enter を押したあと、あの 20 MB の `.wasm` にはいったい何が起きているのか。答えは「解析が終われば走り出す」ではなく、**同時に競走している二本のパイプライン**である。

**現代のエンジン（V8 を例に）の階層戦略**：

| 層 | コンパイラ | 特性 | 用途 |
|---|---|---|---|
| Tier 1 | **Liftoff** | 単一パス、最適化なし、ほぼ命令の逐次翻訳 | **実行可能コードを極めて速く出す**（数百 MB/s 級のコンパイルスループット）。プログラムがすぐ走り出せる |
| Tier 2 | **TurboFan** | 完全な SSA 中間表現、インライン展開、ループ最適化、レジスタ割り当て | 高品質な機械語を出す。**バックグラウンドスレッドでコンパイル**し、できたらホットスワップ |

SpiderMonkey には対応する **BaseLine → Ion** の二層があり、JavaScriptCore には **BBQ → OMG** がある。**三つのエンジンが示し合わせたように同じ形を選んだのは、問題が同じだからである**：ユーザが欲しいのは「すぐに走り出す」ことで、長期の性能が欲しいのは「十分によくコンパイルされている」ことであり、この二つは同時には満たせない——二度やるのでなければ。

**ストリーミングコンパイル**：これは JS に対する Wasm の優位のうち、最も過小評価されているものである。

```javascript
// ✅ 正しい：ダウンロードしながらコンパイル。最初のバイトが届いた時点で Liftoff が働き始める
const { instance } = await WebAssembly.instantiateStreaming(
  fetch("app.wasm"), importObject);

// ❌ よくある誤り：先に全部を ArrayBuffer へ落としてからコンパイルする（ダウンロード一往復を無駄に待つ）
const buf = await (await fetch("app.wasm")).arrayBuffer();
const { instance } = await WebAssembly.instantiate(buf, importObject);
```

`instantiateStreaming` はサーバが返す `Content-Type` が `application/wasm` であることを要求し、そうでなければ拒否する。**GitHub Pages は `.wasm` 拡張子に対してこの MIME を正しく返す**。それが Wasm を走らせるのに意外なほど適している理由の一つである。

**コードキャッシュ**：Chrome は TurboFan のコンパイル結果をディスクキャッシュへ書き込み、同じ URL への二度目の訪問ではコンパイル結果を直接読み込んでコンパイル段階を丸ごと飛ばす。これにより**大きな Wasm アプリケーションの二度目のロードは、一度目より一桁速いことが多い**——「Pyodide は 30 MB もダウンロードする」という不満が、再訪ユーザではまったく違う体感になるのはこのためだ。

**コールドスタートの完全なコスト分解**（「Wasm を使う価値があるか」を評価するとき、本当に計算すべき勘定である）：

```
総コールドスタート時間 =
    ネットワーク転送（gzip/brotli 圧縮後のサイズと RTT に支配される）
  + Liftoff コンパイル（≒ バイト数に線形。通常はネットワーク時間よりはるかに小さい）
  + インスタンス化（線形メモリの確保、Data セグメントの初期化、start 関数の実行）
  + 実行時初期化（C++ のグローバルコンストラクタ、Rust の lazy static、言語 runtime のブートストラップ）
  ─────────────────────────────────────────────
  ⚠️ 最後の一項が最も過小評価される：Pyodide の CPython ブートストラップも、
     Emscripten のファイルシステムのマウントも、「コンパイル完了後」に起きる。
```

**最適化の順序もこれで決まる**：まずサイズを削り（`wasm-opt -Oz`、`--strip-debug`、必要に応じたモジュール分割）、次に実行時初期化を削り（遅延初期化、スナップショット）、最後にようやく命令レベルの最適化の番が来る。**あの 30 MB のダウンロードを放置して命令レベルに力を注ぐのは、最もよくある配分ミスである。**

**第四段については、名前だけ先に覚えておく価値のある専用の武器がある**：**Wizer**（Bytecode Alliance）は**ビルド時に**初期化を走らせきり、「初期化後のメモリ状態」を新しい `.wasm` へスナップショットできる——実行時に受け取るモジュールは、Data セクションがすでに初期化済みのイメージになっている。公式ベンチマークは**インスタンス化と初期化が 1.35 倍から 6.00 倍速くなる**と主張している。**代価は Data セクションが大きくなること、つまりサイズと引き換えに起動速度を買うこと**——これはまさに本節の「四段のコストはそれぞれ独立している」からの直接の帰結である。

> **サイズと速度は互いに牽制しあう一揃いの技術であり、単独で解体する価値がある。** 「自分のバイトはどこへ消えたか」の解剖法から、`wasm-opt` の各パスが実際に何をしているか、Rust の `panic!` に潜む書式化機構、圧縮辞書転送で改版時に数十 KB だけを送る方法、Wizer とバックエンド AOT、SIMD 自動ベクトル化の三つの現実、そして数字を測り間違えさせるタイマ精度の罠まで——**すべて付録 N に収めてある。**

> 💡 座右の一言
> **一つのシステムが互いに矛盾する二つの指標を同時に満たさねばならないとき、正しい答えはたいてい折衷ではなく階層化である。** Liftoff と TurboFan の関係は「中間値を取る」ではない——そうすれば、起動も十分速くなく実行も十分速くない凡庸なコンパイラができるだけだ。それは**まず、極端に粗いが極端に速い案でシステムを生かし、背後で静かに良いものへ差し替える**やり方である。このパターンの名は**漸進的最適化（progressive optimization）**であり、思いつくあらゆる場所に現れる。画像のプログレッシブ読み込み、データベースの LSM ツリー（速く書き、背後で良い形へマージする）、CDN の stale-while-revalidate、さらには CPU の分岐予測（まず一つ当てて、外れたら巻き戻す）。**「速い応答」と「高品質な結果」のあいだで悩んだら、まず問うてほしい：この二つを同じ時間軸で競わせないで済ませられないか？**

> 🔍 踏み込んだ論評──「Wasm はネイティブの 60〜80% の性能」がほとんど無意味である理由
> これは本書が早めに突いておかねばならない一文である。付録の百一の事例の中で百一回現れるからだ。**この数字の成立は、ワークロードの形に強く依存する。** 分解しよう。**（一）整数と浮動小数点の演算が密で、データが L1/L2 キャッシュに収まり、制御フローが単純なループ**——Wasm はネイティブの 90%+ に迫れる。TurboFan の出す機械語は Clang -O2 とさして変わらないからだ。**（二）手書き SIMD やプラットフォーム特化アセンブリが要る場面**——Wasm の SIMD は 128 ビット固定幅（`v128`）しかなく、現代の x86 には AVX2（256 ビット）と AVX-512 が、ARM には SVE がある。AVX2 向けに手で最適化された動画デコーダを Wasm へ移せば、**ネイティブの 40〜50% まで落ちるのが常態**である。ベクトル幅がそのまま半減し、relaxed SIMD 提案が一部の意味論を緩めてマッピングを改善しても、幅の差までは埋められない。**（三）JS/Wasm 境界をまたぐ細かい呼び出しが大量にある場合**——境界越えには固定オーバーヘッドがあり、関数本体が数命令しかなければオーバーヘッドが大半を占める。このとき Wasm は純粋な JS**より遅い**こともある。**（四）文字列とオブジェクトの操作が大量にある場合**——Wasm に文字列型はなく、文字列のやり取りのたびにエンコード・コピー・デコードの三段が要る。ここでは純粋な JS が圧倒する。**（五）メモリアクセスパターンが悪く、キャッシュミスが支配的な場合**——ボトルネックはメモリバスにあり、Wasm とネイティブの差はほぼゼロへ収束する（どちらも DRAM を待っているからだ）。だから正しい言い方は「Wasm はネイティブの N% の性能だ」ではなく——**Wasm は JavaScript の動的型検査、ガベージコレクションの停止、オブジェクト割り当てのオーバーヘッドを消し去った。残る差は、あなたのワークロードが Wasm 仕様にないものにどれだけ依存しているかで決まる**、である。Wasm の性能主張を読むとき、最初に問うべきはつねに：**このベンチマークの形は、私が走らせたいものに似ているか？**

## シナリオ 4　境界を越える：`wasm-bindgen`、グルーコード、そして本当の料金所

**背景**：Wasm が知っている型は四つの数値型（`i32`、`i64`、`f32`、`f64`、それに SIMD の `v128` と参照型）だけである。**文字列を知らず、配列を知らず、オブジェクトを知らず、`null` を知らない。** では `wasm-pack` が出力した JS の中で、`greet("GitHub Pages")` はどうやって動いているのか。

**答えは：あれは一回の呼び出しではなく、一揃いのプロトコルである。** Rust + `wasm-bindgen` を例に、文字列を一つ渡す完全な流れを見よう。

```rust
#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", name)
}
```

下で実際に起きていること：

```
JS 側                                    Wasm 側
─────────────────────────────────────────────────────────
1. TextEncoder が "GitHub Pages" を
   UTF-8 バイト列へ符号化
2. wasm.__wbindgen_malloc(len) を呼ぶ →   線形メモリを確保し、アドレス ptr を返す
3. memory.buffer の ptr 位置へ
   バイト列を書き込む（メモリコピー一回）
4. wasm.greet(ptr, len) を呼ぶ       →   Rust が ptr/len から &str を構築
                                         （この一段はゼロコピー。線形メモリを直接指す）
                                         format! を実行し、結果を新たに確保した領域へ書く
                                    ←    戻り領域を通じて (ptr2, len2) を返す
5. memory.buffer の ptr2 からバイト列を読む
6. TextDecoder が JS 文字列へ復号（またコピー一回）
7. wasm.__wbindgen_free(ptr2) を呼ぶ  →   解放
```

**「文字列を一つ渡す」だけで、符号化・復号が二回、メモリコピーが少なくとも二回、境界越えの呼び出しが三回。** だから、あらゆる Wasm 性能助言の中で最も重要な一条はこれである：**境界は粗く作れ。細かく作るな。**

**具体的な最適化手法**：

- **バッチ化**：`process_pixel()` を百万回呼ぶより、`process_image(ptr, width, height)` を一回呼ぶ。
- **コピーではなくビュー**：Rust 側で `js_sys::Uint8Array::view(&data)` を使い、スライスを直接 JS のビューへ写像する（これは `unsafe` である点に注意。Wasm 側で `memory.grow` が起きた瞬間、このビューは無効になる）。
- **共有バッファ**：JS が大きなバッファを一つ確保し、双方でオフセットによる約束事を決めれば、処理の全過程で境界を越えない。
- **フレームごとのコールバックを避ける**：物理エンジンやゲームループでは、オブジェクトごとに一回コールバックすることは絶対に避ける。「Wasm が結果バッファへ書き、JS がフレームごとに一度読む」というリングキュー方式へ変える。

**二つの主要ツールチェーンの分業**：

| | Emscripten | `wasm-bindgen` / `wasm-pack` |
|---|---|---|
| 言語 | C / C++（他の LLVM フロントエンドも） | Rust |
| 出力 | `.wasm` + 大量の JS グルー（libc、ファイルシステム、SDL/OpenGL 変換層を含む） | `.wasm` + 簡潔な JS バインディング（使った型変換だけ） |
| 哲学 | **POSIX 環境を丸ごと模倣し**、既存の C プログラムをほぼ無改変でコンパイルできるようにする | **型の橋渡しだけ**を行い、あとは Web API に任せる |
| 向き | 既存の大規模 C/C++ プロジェクトの移植（FFmpeg、SQLite、OpenCV） | ゼロから書く新規プロジェクト、サイズに敏感なライブラリ |
| 典型的なサイズ負担 | 大きめ（runtime と shim を含む） | 小さめ（数 KB〜数十 KB のグルー） |

**Emscripten のグルーは何をしているのか**：それは型変換どころではない。**MEMFS**（メモリ上の仮想ファイルシステム。`fopen("video.mp4","rb")` のような呼び出しに行き先を与える）を一式実装し、SDL2 の描画命令を WebGL へ変換し、`pthread` を Web Worker + `SharedArrayBuffer` へ写像し、`printf` を `console.log` へ繋ぐ。**OpenTTD や VLC のような数十万行の C++ ゲームやプレイヤーが「核心ロジックをほぼ無改変で」ウェブへ移せるのは、このためである**——Wasm が魔法なのではなく、Emscripten が下に偽のオペレーティングシステムを一層敷いているのだ。

> 💡 座右の一言
> **異質な二つのシステムのあいだの界面において、コストは「転送」ではなく「翻訳」に宿る。** JS と Wasm のあいだで `i32` を一つ渡すのはほぼ無料だが、文字列を一つ渡すには符号化・復号が二回とコピーが二回かかる——差はデータ量ではなく、**両者の「値とは何か」という定義が違うこと**にある。この法則の適用範囲は Wasm をはるかに超える。ORM のオブジェクト・リレーショナルのインピーダンスミスマッチ、マイクロサービス間の JSON シリアライズ、Python と C 拡張のあいだの GIL の境界、GPU と CPU のあいだのデータ転送——**どれも同じ病であり、治し方も同じである：界面を粗く、往復を少なく、データを同じ側に長く留めよ。** 界面の転送速度を最適化している自分に気づいたら、まず、そもそもそんなに何度もやるべきでないことを最適化していないか確かめてほしい。

## 本章のまとめ

- Wasm は**機械語ではなく、抽象スタックマシンの命令符号化である**。セクション順序、構造化制御フロー、スタック型の一貫性——設計の一条一条が、検証を **O(n) の単一パス線形時間**で完了させるためにある。これこそが「ダウンロードしながらコンパイル」の前提である。
- 検証を通ったモジュールは、境界外の読み書き、任意ジャンプ、呼び出しスタックの破壊が**不可能**である。しかし**サンドボックスの安全 ≠ アプリケーションの安全**：線形メモリの内側に ASLR/NX/stack canary はなく、C プログラムのメモリエラーはむしろ Wasm のほうが安定して悪用可能でありうる（シナリオ 1 の ⚠️ 参照）。
- **線形メモリは伸びるだけで縮まない**。`memory.grow` は既存の `TypedArray` ビューを無効にし、アドレス 0 は合法で書き込め、境界外は必ずトラップする。境界検査は**8 GiB の仮想アドレス予約 + ガードページ**でホットパス命令ゼロを実現する——代価は MMU が無料で負担する。
- 検証器は `unreachable` のあとの死んだコードを**多相スタック**で扱う——特例に見えるこの規則は、実は「単一パス O(n)」というより根本的な性質を守るためのものである（付録 M §2）。
- **階層型コンパイル（Liftoff → TurboFan）** は「すぐ走る」と「十分速く走る」を同じ時間軸で競わせずに済ませる。`instantiateStreaming` + 正しい `application/wasm` MIME は無料の起動最適化であり、コードキャッシュは再訪コストを一桁下げる。
- **起動は四つの独立したコストである**（転送／コンパイル／インスタンス化／実行時初期化）。そして**第四段が最も過小評価される**。それ専用の武器が **Wizer** であり、ビルド時に初期化を走らせきってメモリ状態をモジュールへスナップショットできる（付録 N §10-2）。
- 「Wasm はネイティブの 60〜80% の性能」は**ほとんど情報量のない一文**である——SIMD の幅、境界越えの頻度、文字列の比重、キャッシュの挙動、どれか一つでこの数字は倍以上動く（シナリオ 3 の 🔍 参照）。
- **境界は料金所である**：文字列一往復 = 符号化・復号二回 + コピー二回 + 境界越え三回。**界面を粗く、往復を少なく**——これが Wasm の性能最適化で最も見返りの大きい一条である。

物理法則の棚卸しは終わった。次章はこれらの法則を人の言葉へ翻訳する——**Wasm が見事にこなすこと、できないこと、そしてできるがやらせるべきでないこと。** 第 3 章へ。
