# 第8章：4 GB の天井——ファイルサイズ、アプリサイズ、そして四つの突破アーキテクチャ

> **「Wasm の file size limit は？ app size limit は？」**
> この二つの問いは同じことに聞こえるが、実際にはまったく独立した二つの天井である：**一方は「エンジンがどれだけ大きなモジュールをコンパイルできるか」が決め、もう一方は「仮想機械がどれだけのメモリをアドレスできるか」が決める。** 両者を混同することが、大規模な Wasm プロジェクトがアーキテクチャレビューで転ぶ出発点になる。

## シナリオ 1　二つの天井、四つの数字

**背景**：まず四つの数字をはっきりさせよう。以降のアーキテクチャ判断はすべてこの表から導かれる。

### 天井その一：`.wasm` ファイル自体はどれだけ大きくできるか

| 環境 | 硬い限界 | 実務上の天井 | 制約の本質 |
|---|---|---|---|
| **ブラウザ** | 通常 1 GB〜2 GB 級 | **10 MB〜30 MB 以内を強く推奨** | ストリーミングコンパイル時に巨大なコンパイル状態をメモリ上に構築する。しかもダウンロード時間が初回描画をそのまま食う |
| **バックエンドの実行環境**（Wasmtime / WasmEdge） | 明確な上限なし。物理メモリに支配される | 数百 MB から 1 GB+ まで可 | メモリさえ足りれば、ニューラルネットの重みをモジュールへ直接同梱できる |

**なぜブラウザの実務上の天井は硬い限界よりはるかに低いのか**：ファイルが大きすぎると三重の代価が重なる——ネットワークのダウンロード時間が伸び、数百 MB の Wasm の解析でモバイル端末の CPU が瞬時に振り切れて発熱し、初回描画が遅延する（そして Core Web Vitals が軒並み悪化する）。**これは能力の問題ではなく体験の問題である**が、能力の問題より回避しにくい。

### 天井その二：実行時の線形メモリはどれだけ大きくできるか

| アドレスモード | 硬い限界 | ブラウザの現実的な遮断 | 状態 |
|---|---|---|---|
| **wasm32**（現在の絶対的主力） | **4 GiB に固定**（2³² バイト） | Chrome は通常 **2 GiB〜3 GiB** で保護機構により OOM を投げ、タブをクラッシュさせる | 全面対応 |
| **wasm64**（Memory64、**Wasm 3.0 の核心仕様入り**） | 理論上 2⁶⁴（16 EiB 級） | ホスト OS と cgroup の割当に支配される | 標準化済み。**ただし性能上の代価がある** |

**wasm32 の 4 GiB は数学であって実装の選択ではない**：アドレスは 32 ビットのポインタであり、`2³² = 4,294,967,296` バイトである。この線は回避できない。

**産業事例への直接の帰結**：**FFmpeg.wasm の動画処理も v86 の Linux 起動も、既定では 2〜3 GB を超える単一ファイルを絶対に扱えない／読み込めない**——ファイルはまずその線形メモリへ全量読み込まれねばならないからだ（第 7 章の MEMFS 参照）。

**memory64 の隠れたコスト**（マーケティング資料が決して語らない一節であり、第 2 章で伏線を張っておいた）：

```
wasm32 の無料の境界検査：
  エンジンは 8 GiB の仮想アドレス空間を予約する（4 GiB のアドレス可能域 + 前後の保護領域）
  → 32 ビットのオフセットは数学的に予約域を超えられない
  → 境界外では MMU が SIGSEGV を発生させ、エンジンが受け止めてトラップへ翻訳する
  → ホットパス上の境界検査命令数：0

wasm64 では？
  メモリごとに 2⁶⁴ の仮想アドレス空間を予約することはできない
  → ガードページの技が失効する
  → 「アクセスのたびに明示的な比較 + 分岐」へ戻らねばならない
  → 性能低下：ベンチマークにより数パーセントから二桁パーセントまで
```

**したがって正しい心的モデルはこうだ**：**4 GiB 以下で享受しているのはハードウェアに補助された無料の安全である。その線を越えれば、安全は課金され始める。** ここから直接、一つのアーキテクチャ原則が出る——**分割ストリーミング（シナリオ 2）や複数メモリ（シナリオ 4）で 4 GiB 以内に収まるなら、wasm64 へ急いで跳ぶ必要はない。**

> ⚠️ 真偽の注意
> 「wasm64 の硬い限界は 16 EB に達する」は数学的には正しいが、実務ではまったく意味がない——この桁のメモリを提供できるホストは存在しない。より覚えるべき数字は二つ：**（一）** ブラウザの単一 Wasm メモリの実際の上限は、歴史的にバージョンとプラットフォームによって 2 GiB〜4 GiB のあいだで動いている。**4 GiB を使える枠だと思ってはいけない**。**（二）** Memory64 は **Wasm 3.0** の核心仕様へ入ったが、**性能はエンジン間で顕著に差があり、採用前に必ず対象環境で実測すること**。
>
> **もう一つ、混同しやすい意味論に注意**：`memory.grow` は**失敗してもトラップせず、`-1` を返す**（成功時は成長前のページ数を返す）。これは**メモリ枯渇があなたが能動的に検査せねばならない戻り値であって、勝手に爆発してくれる例外ではない**ことを意味する——そして `malloc` の失敗を「起きない」と扱う多くの C コードは、ここで存在しないメモリへ静かに書き込み、次のアクセスで初めてトラップする。**あなたが見た境界外エラーは、しばしば数百行前の、検査されなかった grow の失敗である。**

> 💡 座右の一言
> **「無料」のシステム特性の背後にはどれも、あなたが気づいていない物理的な前提がある。その前提を越えた瞬間、請求書が現れる。** Wasm の境界検査は 4 GiB 以下では無料である。64 ビットホストの仮想アドレス空間が、一面を無駄にできるほど安いからだ。ひとたび 64 ビットのアドレスを要求すれば、その前提は消え、無料だったものが課金され始める。このパターンはシステム工学で繰り返し現れる。小さなオブジェクトの確保は無料である（slab allocator があるから）——オブジェクトが大きくなるまでは。キャッシュは無料である（ワーキングセットが L3 より小さいから）——データが大きくなるまでは。同期は無料である（スレッドが一本だから）——二本目を足すまでは。**だから工学的直感で最も価値のある一つは、「どうせ速い」ものが何の前提のおかげで速いのかを知っていることである**——拡張はつねに、まず前提を破り、それからコストを露わにするからだ。

## シナリオ 2　突破アーキテクチャ一：OPFS の分割ストリーミング（スライディングウィンドウ）

**背景**：四つの突破アーキテクチャのうち最も重要で、最も過小評価されているものである。その核心の思想は**ファイル全体をメモリへ読み込むことを拒否する**ことにある。

**やり方**：10 GB のファイルを一度にすべて Wasm のメモリへ読み込まない。OPFS の `FileSystemSyncAccessHandle` で `read(buffer, { at: offset })` を行う——Wasm 内部には 50 MB の**スライディングウィンドウキャッシュ**だけを開き、磁気テープを見るように、必要な区間だけをポインタ直操作でディスクから取る。

**結果：メモリはわずか 50 MB でありながら、100 GB の巨大ファイルを滑らかに処理できる。**

```rust
// 概念の骨格：Worker の中で、同期ハンドルによるランダム読み取りを行う
const WINDOW: usize = 50 * 1024 * 1024;   // 50 MB のスライディングウィンドウ

struct ChunkedReader {
    handle: FileSystemSyncAccessHandle,   // OPFS から
    window: Vec<u8>,                      // 常駐する唯一のメモリ
    window_start: u64,                    // 現在のウィンドウに対応するファイルオフセット
    window_len: usize,
    file_size: u64,
}

impl ChunkedReader {
    /// 任意の位置のバイトを読む。現在のウィンドウを出るときだけディスク I/O が起きる
    fn read_at(&mut self, offset: u64, len: usize) -> &[u8] {
        let in_window = offset >= self.window_start
            && offset + len as u64 <= self.window_start + self.window_len as u64;
        if !in_window {
            // ウィンドウの再配置：ブロック境界へ整列させ、頻繁な小口読み取りを避ける
            self.window_start = (offset / CHUNK) * CHUNK;
            self.window_len = self.handle
                .read_at(&mut self.window, self.window_start);   // ← 同期 pread
        }
        let local = (offset - self.window_start) as usize;
        &self.window[local .. local + len]
    }
}
```

**四つの実装要点**（これらが使えるか非常に遅いかを分ける）：

1. **ウィンドウを整列させること**。オフセットを 1 MB か 4 MB の境界へ整列してから読み、一バイト読むためにウィンドウ全体を再読み込みする事態を避ける。
2. **アクセスパターンを考慮すること**。順次走査（動画のデコードなど）は大きなウィンドウ + 先読み。ランダムな飛び回り（データベースの索引など）は小さなウィンドウ + 複数ウィンドウの LRU キャッシュ。
3. **Worker の中でなければならない**（`createSyncAccessHandle` の仕様上の制約。第 7 章参照）。
4. **リモートファイルは HTTP Range Request で同じロジックを使う**——`handle.read_at()` を `fetch(url, {headers: {Range: 'bytes=...'}})` に置き換えるだけで、アーキテクチャはまったく同じである。**DuckDB-Wasm がリモートの Parquet を照会するのはこのやり方だ**（第 6 章参照）。

**この一手の威力は、「メモリ上限」の問題を「I/O 帯域」の問題へ変換することにある**——後者は先読み、キャッシュ、圧縮で緩和できるが、前者は壁である。

## シナリオ 3　突破アーキテクチャ二：複数モジュールによるメモリ隔離（4 GB × N）

**背景**：単一の Wasm インスタンスが最大 4 GiB なら、たくさん開けばよい。

**やり方**：ページ側で独立した Web Worker を複数起動し、**各 Worker の内部にそれぞれ独立した Wasm 実行インスタンスを読み込む**。仮想機械ごとに独自の 4 GiB 線形メモリを持つので、メインスレッドをデータバスとして複数の Worker へタスクを配れば、**アプリ全体の計算力とメモリ上限を 4 GiB × N へ倍増できる。**

```
                メインスレッド（調停だけ。計算はしない）
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Worker 1         Worker 2        Worker 3
   Wasm インスタンス A  Wasm インスタンス B  Wasm インスタンス C
   線形メモリ 4 GiB    線形メモリ 4 GiB    線形メモリ 4 GiB
   （第 1 区間を処理）  （第 2 区間を処理）  （第 3 区間を処理）
        │               │               │
        └───────────────┴───────────────┘
              結果は Transferable で返す。ゼロコピー
```

**これは「Wasm のマルチスレッド」とはまったく別のものである**（最も混同されやすいところだ）：

| | 複数インスタンス隔離（本節） | Wasm threads（`SharedArrayBuffer`） |
|---|---|---|
| メモリ | インスタンスごとに独立した 4 GiB | **一枚を共有**。総量は依然として 4 GiB に制限される |
| 通信 | `postMessage` + Transferable（複製または所有権の移転） | 同じメモリを直接読み書き + アトミック操作 |
| クロスオリジン隔離が要るか | **❌ 要らない** | **✅ COOP/COEP が要る** |
| 向く用途 | データを分割できるタスク（分割処理、並列レンダリング、独立したクエリ） | 細粒度の共有状態を要するアルゴリズム（物理シミュレーション、グラフ探索） |
| GitHub Pages では | **そのまま使える** | `coi-serviceworker` が要る |

**この表には非常に実用的な帰結がある**：**あなたのタスクが「データを切り分けられる」ものなら（大多数のバッチ処理はそうだ）、複数インスタンス隔離で済む——クロスオリジン隔離が要らず、サードパーティのリソースを壊さず、ついでに 4 GiB も突破する。** 多くのチームが COOP/COEP と二週間格闘したあとで、そもそも共有メモリが要らなかったと気づく。

## シナリオ 4　突破アーキテクチャ三：複数メモリ（Wasm 3.0 の新機能）

**背景**：2025 年 9 月に核心仕様へ入ったばかりの新しい道であり、しかもちょうど 4 GiB の問題に正面から取り組んでいる。

**やり方**：**Wasm 3.0 の multiple memories により、一つのモジュールが複数の線形メモリを宣言してアクセスでき、しかもそれらのあいだで直接データを運べる。**

```wat
(module
  (memory $code 16)          ;; 第 0 のメモリ：コードの作業領域
  (memory $assets 1024)      ;; 第 1 のメモリ：アセット／大きなデータ
  (memory $scratch 64)       ;; 第 2 のメモリ：一時領域

  (func $copy_in
    ;; memory.copy はメモリをまたげる：宛先メモリの添字、元メモリの添字
    (memory.copy $scratch $assets
      (i32.const 0) (i32.const 4096) (i32.const 65536)))
  ;; load/store もメモリの添字を指定できる
  (func $peek (result i32)
    (i32.load $assets (i32.const 1024))))
```

**前の二つの道との関係は、はっきり描いておく価値がある**：

| | 複数メモリ（本節） | 複数モジュール隔離（シナリオ 3） | Memory64 |
|---|---|---|---|
| Wasm インスタンスの数 | **一つ** | N 個 | 一つ |
| メモリの枚数 | **複数** | インスタンスごとに一枚 | 一枚（超大） |
| データ移動のコスト | **`memory.copy` がメモリをまたぐ。エンジン層で完結** | `postMessage` でスレッドをまたぐ | 移動不要 |
| ガードページの無料境界検査 | **✅ 各枚が依然 wasm32 なので、すべて保たれる** | ✅ | **❌ 失われる** |
| Worker が要るか | ❌ | ✅ | ❌ |
| クロスオリジン隔離が要るか | ❌ | ❌ | ❌ |
| 向く用途 | **シングルスレッドで、データを区分できる大規模アプリ** | タスクを切り分けられるバッチ処理 | 本当に単一の超大アドレス空間が要る場合 |

**最も美しいのは第四行である**：メモリの一枚一枚が**それぞれ依然として 32 ビットアドレス**なので、「仮想アドレス空間を予約 + ガードページ = 無料の境界検査」という機構が**完全に保たれる**。言い換えれば——

> **複数メモリは、無料の境界検査を手放さずに、単一 4 GiB の制限を突破させてくれる。**
> これこそ Memory64 にはできない取捨であり、「データが自然に区分できる」場面（コード領域／アセット領域／一時領域、テナントごとに一枚、ホットとコールドの分離）では、**複数メモリがほぼつねに Memory64 より割に合う理由でもある。**

**現実の但し書き**：**ツールチェーンの対応は仕様に遅れている。** 多くの C/C++/Rust ツールチェーンは既定でいまも「メモリは一枚」と想定しており、使うには手書きの WAT か、複数メモリに対応した新しめのツールチェーンと属性注釈が要ることが多い。**仕様が先に来て、ツールチェーンが後から来る——これはどの新機能でも常態であり、「仕様の状態」と「あなたが今日使えるか」を分けて問わねばならない理由でもある。**

## シナリオ 5　突破アーキテクチャ四：Wasm GC を有効にして、実行環境をブラウザへ返す

**背景**：前の三手はどれも**メモリの天井**に対処するものだった。この一手が対処するのは、シナリオ 1 で立てた**もう一つの天井——ファイルサイズ**である。

**問題**：Java、Kotlin、Dart、C# のような高水準言語を Wasm へコンパイルする場合、従来のやり方では言語のガベージコレクタと標準ライブラリを丸ごと `.wasm` へ同梱せねばならず、ファイルサイズが数 MB あるいはそれ以上へ膨れ上がる。

**やり方**：**Wasm GC**（2025 年 9 月に Wasm 3.0 とともに核心仕様入り）を直接有効にし、自前で一式を持ち込む代わりに、ブラウザ本来の極度に最適化されたガベージコレクションエンジン（V8 の Orinoco、SpiderMonkey の GC）を Wasm に使わせる。

**Wasm GC が仕様レベルで加えたもの**（本章で最も新しい部分なので、技術的詳細を挙げる）：

- **ヒープ型（heap types）**：`struct`、`array`、そして `i31`（ポインタの中に詰められる小整数の最適化）。
- **型付き参照（typed references）**：`(ref $MyStruct)`、`(ref null $MyArray)`——Wasm が初めて「構造を持つオブジェクトを指す」能力を得た。`i32` のオフセットだけではなくなったのである。
- **部分型（subtyping）と `br_on_cast`**：オブジェクト指向言語の継承と動的なキャストを表現できるようにする。

```wat
;; Wasm GC：本物のオブジェクト。ホストの GC が管理し、線形メモリを占めない
(type $Point (struct (field $x f64) (field $y f64)))
(func $make (result (ref $Point))
  (struct.new $Point (f64.const 1.0) (f64.const 2.0)))
```

**利得と代価**：

| | 利得 | 代価 |
|---|---|---|
| サイズ | **大幅に縮められる**（GC と実行環境の一部を同梱しなくてよい） | — |
| 性能 | 高度に最適化されたホストの GC を使うので、自前の簡易 GC より通常は良い | 回収の時機に対する制御を失う。**GC 停止が戻ってくる** |
| 適用 | Kotlin/Wasm、Dart（Flutter Web）、Java、Scheme など | **Rust/C/C++ にはほぼ無用**——それらのデータはもともと線形メモリにある |
| 対応 | **Wasm 3.0 の核心仕様入り**。主要ブラウザは対応済み | バックエンドの実行環境とツールチェーンの対応はブラウザに遅れている |

> ⚠️ 真偽の注意
> 「Wasm GC を有効にすれば `.wasm` のサイズが 80% 以上そのまま縮む」という主張をよく見る。**方向は正しいが、この数字は「もともと言語の実行環境をまるごと同梱していた」言語にしか成り立たない**（Java、Kotlin、Dart など）し、実際の縮小幅はもともと何をどれだけ同梱していたかに依存する。**Rust、C、C++ にとって、Wasm GC を有効にしてもサイズの恩恵はほぼない**——それらのオブジェクトはもともと線形メモリに確保されており、節約できる GC が存在しない。この助言をすべての言語へ無差別に適用するのは、非常によくある誤読である。

**しかしどのコンパイラフラグをいじるより先に、第 0 条をやること**——その投資対効果は他のすべてを圧倒することが多い。

> **★ 第 0 条：コードを削る前に、データを削れ。**
> 大規模な C/C++ プロジェクトの Wasm 成果物では、半分以上が引きずり込んだ**データテーブル**であることが多く、そのテーブルの 90% はあなたがまったく使わない。
> **実例**（付録 L）：FluffOS の Wasm ビルドは ICU の break-iterator 規則だけを残し、**データを約 30 MB から約 780 KB へ削った（−97%）。一方ドライバのコード本体はわずか 3.6 MB である。**
> **だから最初の動作はフラグを立てることではなく、`wasm-objdump -h` でセクションの予算を見ることである**——Data が半分を占めているなら、Code をさらに 10% 圧縮しても総サイズは 5% しか変わらない。

**セクションの予算を確認して初めて、あのツールチェーンの出番になる**：`wasm-opt -Oz` → コンパイル時の設定（`lto` / `codegen-units=1` / `panic="abort"` / `strip`）→ `twiggy` による診断 → 死コード削除 → Brotli 転送 → モジュール分割。

> **これは一覧にすぎない。各項が実際に何を削り、代価が何で、そして一覧にないもの——Rust の `panic!` に潜む書式化機構、単相化爆発への「ジェネリックの薄い殻」という解法、`wasm-opt` の各パスの働き、圧縮辞書転送で改版時に数十 KB だけを送る方法——はすべて付録 N 第一部に収めてあり、項目ごとの投資対効果の総表も付いている。**

> 🔍 踏み込んだ論評──四つの突破アーキテクチャは、実は同じ思想の四つの投影である
> この四手を並べると、解いているのが同じ問題であることが分かる：**「一度に全部」があらゆる資源上限の共通の病根である。** 分割ストリーミングは「データを一度に全部持ち込むな」と言い、複数モジュール隔離は「一つのインスタンスで全部を抱えるな」と言い、複数メモリは「全部を同じアドレス空間へ詰め込むな」と言い、モジュール分割と遅延読み込みは「コードを一度に全部ダウンロードするな」と言う。**四つとも「総量の問題」を「時間軸あるいは空間軸上の区分の問題」へ分解している**——そして流量の問題はつねに総量の問題より解きやすい。先読み、キャッシュ、優先度、バックグラウンド読み込みで均せるからだ。この原理の一般性はきわめて高い。データベースのページングクエリ、動画の適応的ストリーミング（HLS/DASH）、フロントエンドの仮想スクロールリスト、LLM の KV キャッシュのページング（PagedAttention）、オペレーティングシステムの仮想メモリ——**すべて同じ着想である：「どれだけ持っているか」ではなく、「いまどの区間が必要か」を問え。** 次にどんな「容量上限」にぶつかっても、最初に問うべきは「どうすれば上限を上げられるか」ではなく——**本当に同じ瞬間に全部を持っている必要があるのか**、である。十回のうち九回は必要ないし、その十回目こそ、より大きなマシンを買う価値がある。

## 本章のまとめ

- **二つの独立した天井**：`.wasm` の**ファイルサイズ**（ブラウザの硬い限界は 1〜2 GB 級、**実務推奨は 10〜30 MB**。バックエンドはほぼ無限）と**線形メモリのサイズ**（wasm32 は **4 GiB に固定**、ブラウザは 2〜3 GiB で OOM することが多い）。
- **wasm64 は無料ではない**：アドレスが 64 ビットになった瞬間、「8 GiB の仮想アドレス予約 + ガードページ」の無料境界検査が失効し、明示的比較へ戻らざるをえず、実質的な性能低下を伴う。**4 GiB 以下で享受しているのはハードウェアに補助された安全である。**
- **突破一：OPFS の分割ストリーミング（スライディングウィンドウ）**——`createSyncAccessHandle` の `read(buffer, {at})` でランダム読み取りを行えば、メモリ 50 MB で 100 GB のファイルを扱える。リモートファイルは HTTP Range Request で同じロジックを使う。
- **突破二：複数モジュールによるメモリ隔離**——N 個の Worker × N 個の Wasm インスタンス = 4 GiB × N。**これは Wasm threads とはまったく別のものである**：複数インスタンスは **COOP/COEP を必要とせず**、GitHub Pages でそのまま使える。**タスクを切り分けられるなら、まずこれを選べ。**
- **突破三：複数メモリ**（Wasm 3.0 の新機能）——一つのモジュールに複数の線形メモリを持ち、`memory.copy` がメモリをまたいでデータを運べる。**最大の利点は各枚が依然 wasm32 であり、したがってガードページの無料境界検査が完全に保たれること**——これこそ Memory64 にはできない取捨である。ただし**ツールチェーンの対応は仕様に遅れている**（シナリオ 4 参照）。
- **突破四：Wasm GC**（Wasm 3.0 の核心仕様入り）——ガベージコレクションをホストエンジンへ返す。サイズの利得は顕著だが、**「もともと実行環境を同梱していた」言語（Java/Kotlin/Dart）にしか効かず、Rust/C/C++ にはほぼ無用である**（シナリオ 5 の ⚠️ 参照）。
- `memory.grow` は**失敗時にトラップせず `-1` を返す**——メモリ枯渇はあなたが能動的に検査せねばならない戻り値であり、**あなたが見た境界外エラーは、しばしば数百行前の検査されなかった grow の失敗である。**
- サイズ削減の**第 0 条は「コードを削る前にデータを削れ」**——まず `wasm-objdump -h` でセクションの予算を見ること。Data が半分を占めているなら Code を圧縮しても意味がない。実例は付録 L（ICU 30 MB → 780 KB）。**完全な武器庫と投資対効果の総表は付録 N 第一部にある。**
- 四つの突破アーキテクチャは同じ思想の四つの投影である：**「総量の問題」を「時間軸あるいは空間軸上の区分の問題」へ分解すること**——どんな容量上限にぶつかっても、まず「本当に同じ瞬間に全部を持っている必要があるのか」を問え（シナリオ 5 の 🔍 参照）。

第二部はここで終わる。機械は建ち、走り、ものを覚え、容量の制限も突破した。**さて、最初から頭上に吊るされていたあの問いに向き合おう：この機械は、見知らぬ一台一台のコンピュータへ完全にダウンロードされてしまった。** 第 9 章へ。
