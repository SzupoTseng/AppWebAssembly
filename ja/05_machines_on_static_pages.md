# 第二部：静的ページの上に機械を建てる

# 第5章：静的ページで機械を走らせる——COOP/COEP という関門と、天才的な迂回路

> **「GitHub Pages のページは静止しているのか？ server は動かせるのか？」**
> これが調査全体の転回点だった。答えはこうだ：ページ自体はまったく静止していないが、その上で従来型のサーバを動かすことは確かにできない。**そして Wasm が第三の答えを可能にした——サーバをユーザのブラウザの中へ移せばいい。**

## シナリオ 1　まず三つを区別する：GitHub のサイト、GitHub Pages、そして「server を動かす」こと

**背景**：この三語はしばしば混同され、「GitHub は静的だ」というよくある誤解を生む。

**GitHub のサイト自体：まったく静的ではない。** リポジトリを閲覧し、Issue を立て、Pull Request を送るとき目にしているのは高度に動的なページである。フロントには大量の JavaScript（React コンポーネント）がリアルタイムの対話を処理し、バックエンドは GitHub 自身の巨大なサーバ群（主に Ruby on Rails で構築）がリクエスト処理、データベースとファイルシステムへのアクセスを担っている。

**GitHub Pages：静的ファイルをホストするだけ。** リポジトリ内の HTML、CSS、JS、画像、`.wasm` をそのまま CDN 経由で配る。

- ❌ **できないこと**：Node.js / Django / Go のバックエンドプロセスを動かす、ポートを待ち受ける、データベースへ繋ぐ、スケジューラを回す。
- ⭕ **できること**：シングルページアプリケーション（React / Vue / Svelte）のホスティング、そして**WebAssembly が駆動する任意に複雑なフロントエンド計算**。

**GitHub が提供する「何かを動かせる」場所は他に二つある**（境界を明確にするのは重要だ。多くの人がそれらを代替案とみなすからである）：

| サービス | 何を動かせるか | 硬い制約 |
|---|---|---|
| **GitHub Pages** | 静的ファイル + ブラウザ側のすべて（Wasm を含む） | 独自 HTTP ヘッダなし、バックエンドなし、データベースなし |
| **GitHub Actions** | 仮想機械（Linux/Windows/macOS）内で任意のプロセスを起動できる。データベースもサーバも含む | **テスト／ビルドのために存在する**：一回の実行に時間上限があり（公開リポジトリでは通常ジョブあたり 6 時間）、終われば VM は破棄される。**常駐サイトのホストにはできない** |
| **GitHub Codespaces** | 完全なクラウド開発コンテナ。`npm start` や `python manage.py runserver` ができ、一時的なポート転送 URL が自動生成される | 開発用途。アイドルで休眠する。**本番ホストではない** |

**核心となる繋がり**：「静的ウェブ環境」の中でバックエンドのように見えるサービスを動かしたいなら、**Wasm はその答えの一つである**。すでに（StackBlitz の **WebContainers** のような）プロジェクトが Wasm を使い、Node.js の実行環境と OS カーネルのかなりの部分をブラウザ内部で直接コンパイル・実行することに成功している——ユーザがページを開けば、ブラウザは Wasm でフロントに「バックエンドサーバ」を模倣し、本物のクラウドホストはまったく要らない。

**そしてこれを底までやり切った例を見たいなら**：**FluffOS**——いまも維持されている LPMud ドライバ（MudOS の現代的なフォーク、C++ 製）——はすでに **WebAssembly を公式のビルドターゲットの一つに挙げている**。公式 README の原文はこうだ：「**ドライバ全体が一つのブラウザページの中で動く：コンパイラ、仮想機械、efuns、telnet**」。その mudlib（つまりゲーム世界のソースコード全体）は Emscripten の `file_packager` で静的バンドルへ固められ、**サーバは要らない**。これは、ハートビートを持ち、タイマを持ち、持続する世界状態を持ち、しかも実行時にユーザのコードをコンパイルするマルチプレイヤーのゲームサーバが、CDN へ放り込める三つの静的ファイルになったということである。**完全な解体は付録 L にある。**

> ⚠️ 真偽の注意
> 「WebContainers が Node.js をブラウザで動かしている」は本当であり検証可能である（StackBlitz の公開技術記事に詳細がある）。しかしその境界を正確に理解すること：**それは Node.js の C++ ソースをそのまま Wasm へコンパイルしたのではなく**、Wasm 上で動く Node.js API 互換の実行環境を作り直し、Service Worker でネットワークリクエストを横取りしてサーバの挙動を模倣したものである。**「ブラウザの中で本物のサーバを動かす」の正確な版はこうだ：ブラウザの中で、このページに対しては挙動の一致するサーバを模倣している。** 外部インターネットにいる他の人は、URL でこの「サーバ」へ**接続できない**——P2P の穴あけを追加しない限り。

> 💡 座右の一言
> **「静的」と「動的」はページの属性であったことは一度もない。「計算がどちら側で起きるか」の属性である。** 同じ HTML ファイルは、CDN に置けば静的だが、それが引き上げる Wasm モジュールはクライアント側で動画のトランスコードを終え、SQL クエリを走らせ、ニューラルネットワークを一巡させられる。計算は減っていない。**支払う人が替わっただけである**——あなたのサーバ請求書から、ユーザの CPU サイクルとバッテリーへ。この件の商業的含意は技術的含意よりはるかに大きい：**高価なコストが痛みなくユーザへ転嫁でき、しかもユーザが痛みを感じないなら、そのコストは必ず転嫁される。** 広告 SDK はそうしてきたし、暗号通貨のマイニングスクリプトもそうしてきた。そして Wasm は、正当な重い計算にもそれを可能にした。だから次に「サーバコストゼロ」の五文字を見たら、後半を補う習慣をつけてほしい：**コストは消えていない。誰かの電気代になったのだ。**

## シナリオ 2　九割の人がぶつかる関門：COOP / COEP

**背景**：ローカルの `python -m http.server` では快調に動いていた FFmpeg.wasm が、GitHub Pages へ上げた途端にこう吐く。

```
ReferenceError: SharedArrayBuffer is not defined
```

あるいは

```
Uncaught DOMException: Failed to construct 'Worker': ... blocked by cross-origin isolation
```

**問題の完全な因果連鎖**（すべてを理解する鍵であり、第 3 章の伏線がここで爆発する）：

```
Spectre（2018、CPU の投機的実行によるサイドチャネル脆弱性）
   ↓ 攻撃にはキャッシュのタイミングを測る高精度タイマが要る
SharedArrayBuffer は Atomics と組み合わせてナノ秒級のタイマを作れる
   ↓ そこでブラウザは SharedArrayBuffer を全面的に既定無効化した
   ↓ のちに戻されたが、条件が付いた：ページは「クロスオリジン隔離」されねばならない
クロスオリジン隔離はサーバが二つの HTTP ヘッダを返すことを要求する
   ↓
Cross-Origin-Opener-Policy: same-origin      ← 他オリジンのウィンドウとの window 参照を断つ
Cross-Origin-Embedder-Policy: require-corp   ← すべてのクロスオリジン子リソースが明示的に許諾せねばならない
   ↓ 両方が満たされたとき self.crossOriginIsolated === true
   ↓ このとき初めて SharedArrayBuffer が存在する
   ↓ そして Wasm のマルチスレッドは SharedArrayBuffer に依存する
   ↓
❌ GitHub Pages は独自 HTTP ヘッダを許さない
   ↓
マルチスレッドを使う Wasm プロジェクト（FFmpeg.wasm のマルチスレッド版、
OpenCV の並列、Emscripten の pthread、Rust の rayon-wasm……）は
GitHub Pages 上で単純に動かない
```

**二つのヘッダはそれぞれ何を防いでいるのか**：

- `Cross-Origin-Opener-Policy: same-origin`（COOP）：`window.opener` というクロスオリジンの参照鎖を断ち、他オリジンのウィンドウがあなたと同じ OS プロセスに同居することを防ぐ（同一プロセスは同一アドレス空間を意味し、Spectre があなたのメモリを読む機会を得るからだ）。
- `Cross-Origin-Embedder-Policy: require-corp`（COEP）：ページ内に読み込まれる**すべての**クロスオリジンリソース（画像、スクリプト、iframe、フォント）が、埋め込まれることへの同意を明示的に表明することを要求する——`Cross-Origin-Resource-Policy: cross-origin` レスポンスヘッダか、CORS を通じて。**表明のないものは一律に遮断される。**

**COEP の巻き添え被害が、この件で最も痛いところである**：クロスオリジン隔離を有効にした瞬間、**CORP/CORS ヘッダを返さないサードパーティリソースがすべて壊れる**——Google Fonts、CDN 上の画像、YouTube の埋め込み、広告、解析スクリプト。だからこそ、ヘッダを設定できる立場にあっても（自前の Nginx や Cloudflare Pages の `_headers` を使えても）、隔離の有効化は代価を伴う決定なのである。

> 💡 **解決策：`coi-serviceworker`**
> オープンソースコミュニティは天才的な迂回路を作った。**`coi-serviceworker`** というスクリプトを導入すると、ブラウザの **Service Worker** 技術を使い、**フロントエンド**でページ自身が発したすべてのリクエストを横取りし、レスポンスにこの二つのヘッダを「足して」くれる。
> やり方：`coi-serviceworker.js` を GitHub Pages のルートに置き、`index.html` の `<head>` の最上部で読み込む。
> ```html
> <script src="coi-serviceworker.js"></script>
> ```
> 初回ロード時には Service Worker がまだ引き継いでいないので、スクリプトは自動でページを一度リロードする。二度目のロードからはすべてのレスポンスに COOP/COEP が乗り、`crossOriginIsolated` が `true` になり、`SharedArrayBuffer` が現れる。

**なぜ合法で、なぜ安全なのか**：Service Worker は**同一オリジンのページ自身が登録する**プロキシ層であり、自分のスコープ内のリクエストしか横取りできない。ブラウザのセキュリティモデルを迂回してはいない——**ページ自身の権限の範囲内で「私は自ら隔離状態に入る」と宣言している**のだ。ブラウザがこの宣言を受け入れるのは、隔離の代価（クロスオリジンリソースを失うこと）もまたこのページ自身が負うからである。

**その四つの代価**（必ず知っておくこと。さもないと本番で地雷を踏む）：

1. **ページをもう一度読み込む必要がある**（Service Worker の登録後に有効になるため）。初回の体験が一瞬ちらつく。
2. **HTTPS が要る**（GitHub Pages は既定で対応。ローカルの `localhost` も安全なオリジンとみなされる）。
3. **CORP のないクロスオリジンリソースは依然として遮断される**——この点は本物のヘッダ設定とまったく同じである。Service Worker は自分が触れるレスポンスしか変えられない。
4. **Service Worker には独自のキャッシュと更新の意味論がある**。新版の配備時にユーザが旧版を受け取る問題が起きうるので、`skipWaiting` / `clients.claim` を扱う必要がある。

**そもそもこの一式が要らないのはどんなときか**：**あなたの Wasm がシングルスレッドなら、COOP/COEP はまったく要らない。** ほとんどのプロジェクト（`wasm-pack` の既定出力、たいていのパーサやコンパイラ）はシングルスレッドであり、そのまま GitHub Pages へ上げれば動く。**本当にマルチスレッドが要るのかを先に確かめてから、この代価を払うこと。**

### 代価を減らせる二つの選択肢

**選択肢その一：`require-corp` の代わりに `COEP: credentialless`。**

`require-corp` はすべてのクロスオリジン子リソースが埋め込みへの同意を**能動的に表明する**（`Cross-Origin-Resource-Policy` を返す）ことを求める——しかしサードパーティが表明するかどうかは、あなたには制御できない。`credentialless` は発想を変える：**表明していないクロスオリジンリソースの読み込みを許すが、「資格情報なし」（cookie もクライアント証明書も送らない）でリクエストする。**

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: credentialless    ← require-corp よりずっと穏やか
```

**これでも `crossOriginIsolated` は `true` になり**、しかも「CORP を設定していないだけの公開画像やフォント」をまとめて殺さずに済む。代価は：**cookie を伴わなければ取得できないクロスオリジンリソースは取れなくなる**（リクエストが資格情報を運ばないため）こと、そしてブラウザの対応が `require-corp` ほど揃っていないことである。**まず `credentialless` を試し、駄目なら `require-corp` へ戻ること。**

**選択肢その二：`SharedArrayBuffer` を必要としないバックエンドへ替える。**

この一条の価値はしばしば過小評価される。永続化 SQLite を例に取ろう。公式の SQLite-Wasm は **二種類**の OPFS VFS を提供する。第一世代の `opfs` は `SharedArrayBuffer` を必要とする（したがって隔離が要る）が、**`opfs-sahpool` は COOP/COEP をまったく必要とせず、しかも公式ドキュメントで最速の選択肢として挙げられている**（詳しくは第 7 章）。

> 💡 **多くのチームが `SharedArrayBuffer` と隔離のために二週間格闘したが、彼らが欲しかったものには、それを必要としない道があった。手を動かす前に十分だけ、依存するライブラリに第二のバックエンドがないか読んでほしい。**

### まだぶつかっていないかもしれないが、いずれぶつかる壁：CSP

**サイトに Content-Security-Policy が設定されていると、Wasm のコンパイルは直接遮断される。**

理由は、`WebAssembly.compile()` / `instantiate()` / `compileStreaming()` が CSP の目には**動的コード生成**——`eval()` と同類——だからである。初期には `'unsafe-eval'` を開けるしか解法がなかった——**それは XSS の防衛線をまるごと明け渡すに等しい。**

**いまの正解は専用のキーワードである**：

```http
Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'
```

`'wasm-unsafe-eval'` は **WebAssembly のコンパイルだけを許し、`eval()` や `new Function()` は許さない**。対応状況：**Chrome 97+、Firefox 102+、Safari 16+**（Chrome 拡張では v103 以降、manifest の `content_security_policy` で使える）。

**この一条は三つの場面でとりわけ噛みつきやすい**：**（一）** あなたの Wasm が他人の iframe に埋め込まれ、相手の CSP が許可していない場合。**（二）** ブラウザ拡張。**（三）** 統一 CSP ポリシーを持つ企業内ポータル。**症状は CSP violation であって Wasm のエラーではないので、調べる方向を間違えやすい。**

> 🔍 踏み込んだ論評──`coi-serviceworker` は「合法な仕様の隙間」であり、この種のものの寿命には警戒すべきである
> この迂回路が成立するのは、セキュリティモデルの微妙な前提のおかげである：**ブラウザは「ページが自ら隔離状態に入る」ことと「サーバがページに隔離状態を要求する」ことを、安全上等価とみなしている。** 隔離が守る対象はこのページ自身だからだ。この推論は厳密であり、だから `coi-serviceworker` は脆弱性の悪用ではなく、**仕様の正しい使い方**である。しかしここには長期的に警戒すべき二つのことがある。**第一に、それが依拠しているのは明示的に約束されたことのない組み合わせの挙動である。** 「Service Worker が合成した COOP/COEP ヘッダは、サーバが発したものと等価とみなされねばならない」と書いた条文はどこにもない——各実装が仕様から引いた自然な推論にすぎない。「複数の仕様の交差点における推論的な挙動」に依拠する技はどれも、将来の版で締められる危険を抱えている。**第二に、そしてより根本的なこと：それは構造的な事実を露わにする——無料の静的ホスティングは CDN をくれ、HTTPS をくれ、バージョン管理をくれるが、「レスポンスヘッダ」という制御権だけはくれない。そして現代 Web の高度な能力（クロスオリジン隔離、CSP、Permissions Policy、Trusted Types、さらには一部の Origin Trials）は、すべてレスポンスヘッダに繋がれている。** だから本当の教訓は「coi-serviceworker の使い方を覚えよ」ではなく——**無料のプラットフォームを選ぶとき、あなたが手放すのはたいてい、いま必要なものではなく、二年後に必要になる制御権である**、ということだ。無料プラットフォームの天井は、あなたがある大きさまで育ったときに初めてぶつかるものであり、そのときには移行コストがすでに高い。この件は第 11 章、第 12 章で濠を語るときに別の形で再び現れる：**制御権こそ、唯一本当に希少なものである。**

## シナリオ 3　完全な配備経路：`cargo` からあの `github.io` の URL まで

**背景**：理論を、そのまま真似できる一本の経路へ収束させる。最も主流の **Rust + WebAssembly** を例に取る。

**ステップ 1：ローカルでコンパイル**

`wasm-pack` で Rust を Web 専用の Wasm と JS グルーコードへコンパイルする。

```bash
wasm-pack build --target web
```

これで `pkg/` フォルダが生成され、中に `.wasm` ファイルと `.js` グルーファイルが入る。

**`--target` の四つの選択肢を正しく選ぶこと**（初心者が最も設定を間違えるところである）：

| target | 出力の形 | 適用 |
|---|---|---|
| `web` | ES module。`<script type="module">` で直接読み込める | **GitHub Pages の静的配備の正解** |
| `bundler` | webpack/rollup/vite が食うモジュール（`import` 構文を含む） | バンドラのあるプロジェクト |
| `nodejs` | CommonJS。Node.js 用 | サーバサイド |
| `no-modules` | グローバル変数にぶら下がる従来型スクリプト | 旧環境、あるいは Worker で `importScripts` を使いたい場合 |

**ステップ 2：フロントエンドの HTML を書く**

```html
<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="UTF-8">
  <!-- マルチスレッドを使うときだけ必要。しかも必ず最前に置く -->
  <script src="coi-serviceworker.js"></script>
  <title>Wasm on GitHub Pages</title>
</head>
<body>
  <script type="module">
    import init, { greet } from './pkg/your_project.js';
    async function run() {
      await init();              // Wasm モジュールの初期化（内部で instantiateStreaming を使う）
      greet("GitHub Pages");     // Wasm 内部の関数を呼ぶ
    }
    run();
  </script>
</body>
</html>
```

**ステップ 3：push して Pages を有効にする**

1. プロジェクト（`index.html` と `pkg/` を含む）を GitHub リポジトリへ push する。
2. **Settings → Pages** へ入る。
3. **Build and deployment** で、公開するブランチ（`main` や `gh-pages` など）を選ぶ。
4. 数分待って `https://<アカウント>.github.io/<プロジェクト名>/` を訪れる。

**必ず踏む四つの落とし穴**（踏まれる頻度の順）：

1. **`.gitignore` が `pkg/` を無視している**。`wasm-pack` が生成する `pkg/` は多くの Rust テンプレートで既定的に無視されるため、push したのは `.wasm` のないサイトになる。**解法**：`pkg/` をバージョン管理へ入れるか、GitHub Actions の CI でコンパイルする（後述）。
2. **パスが相対で、プロジェクトページにはサブパスがある**。`https://user.github.io/repo/` というサブパスのせいで、`/pkg/xxx.js` のような絶対パスは 404 になる。**解法**：すべて相対パス `./pkg/xxx.js` にする。
3. **Jekyll がアンダースコア始まりのフォルダを食う**。GitHub Pages は既定で Jekyll を走らせ、`_` で始まるファイルとフォルダを無視する。**解法**：ルートに空の `.nojekyll` ファイルを置く。
4. **`await init()` を忘れる**。Wasm のロードは非同期であり、初期化が終わる前にエクスポートされた関数を呼べば必ず爆発する。

**GitHub Actions で自動コンパイル・配備する**（`pkg/` を手で commit するよりずっと清潔である）：

```yaml
name: Deploy Wasm to Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: wasm32-unknown-unknown
      - name: Install wasm-pack
        run: curl https://rustwasm.github.io/wasm-pack/installer/init.sh -sSf | sh
      - name: Build
        run: wasm-pack build --target web --release
      - name: Optimize
        run: |
          npm install -g binaryen
          wasm-opt -Oz --strip-debug pkg/*_bg.wasm -o pkg/tmp.wasm
          mv pkg/tmp.wasm pkg/$(ls pkg | grep _bg.wasm)
      - name: Assemble site
        run: |
          mkdir -p dist && cp index.html dist/
          cp -r pkg dist/ && touch dist/.nojekyll
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4
```

> 💡 座右の一言
> **配備経路の難しさは手順が何段あるかではなく、失敗したときのエラーメッセージが本当の原因からどれだけ離れているかで決まる。** 上の四つの落とし穴は、どれもエラーメッセージがあなたを騙す。`pkg/` を push していなければ 404 が見える。パスを絶対で書いても、やはり 404 が見える。Jekyll がファイルを食っても、**やはり** 404 が見える。まったく異なる三つの病因に、同じ症状。だから「チュートリアルどおりにやったのに動かない」が初心者の最もよくある挫折なのだ——**チュートリアルが書くのは幸福な経路であり、現実では時間の九割が、間違った方向を指すエラーメッセージの解読に費やされる。** だから本当に価値のあるドキュメントは手順一覧ではなく、**症状-病因の対照表**である。この点は、あなた自身がツールを書き、ライブラリを書き、エラーメッセージを書くときにも同じく成り立つ：**良いエラーメッセージ一本は、チュートリアル十ページに匹敵する。**

## シナリオ 4　最も古典的な「他の人がその上で何を走らせているか」三つ

**背景**：百一の事例へ踏み込む前に、最も典型的で「なぜそうするのか」を最もよく示す形を三つ見ておこう。

**形その一：サーバの仕事をユーザへ転嫁する——ウェブ版の動画編集（FFmpeg.wasm）**

C 言語で書かれた映像音声ツール FFmpeg を Wasm へコンパイルする。ユーザが動画を GitHub Pages のページへドラッグすると、**変換はユーザ自身の CPU で完結し**、サーバの帯域はまったく消費されない。

- **価値は速さではなく「金を払わなくていい」ことにある**：クラウドのトランスコードサービス（AWS MediaConvert の類）は分単位の課金であり、大量のアップロード帯域を食う。FFmpeg.wasm の限界費用はゼロである。
- **付随するプライバシーの配当**：ユーザの動画ファイルは最初から最後まで彼のコンピュータを離れない。個人の動画、医療画像、社内素材を扱うとき、これは性能より説得力のある売り文句になる。

**形その二：死んだものを甦らせる——ウェブ版レトロゲームエミュレータ**

C++ や Rust で書かれた Game Boy、NES、PS1 のエミュレータが多数 Wasm へコンパイルされ、GitHub Pages にホストされ、ページを開けば遊べる。

- **なぜ Wasm が鍵なのか**：エミュレータは CPU サイクルを**クロック精度で**模倣する必要がある。JavaScript のタイマは不正確で、ガベージコレクションがランダムに止まるため、音と映像がずれ、ポップノイズが出る。Wasm の性能曲線は平らであり、それこそエミュレータが欲しいものだ。

**形その三：AI を端末へ押し出す——ブラウザ側推論（ONNX Runtime Web）**

GitHub Pages 上で軽量化されたモデル（物体検出、顔認識）を読み込み、Wasm でリアルタイムに計算し、**サーバの AI チップ代さえ節約する**。

- **ここでの Wasm の役割は「最後の砦」である**：WebGPU/WebGL バックエンドのほうが速いが、ドライバとハードウェアに依存する。Wasm の CPU バックエンドはどんな端末でも動く。**これは性能ではなく可用性の選択である。**

**形その四：サーバをまるごと持ち込む——ブラウザの中の MUD ドライバ（FluffOS × Wasm）**

前の三つはどれも「**関数**を一つ持ち込む」ものだった——入力を与え、出力を取る。**第四の形は違う。持ち込むのは、ハートビートを持ち、状態を持ち、生き続けるサーバである。**

- **なぜ前の三つより難しいのか**：MUD ドライバはリクエストハンドラではない。heartbeat があり、`call_out` タイマがあり、持続する世界状態があり、複数の並行接続があり、**しかも実行時に mudlib の LPC ソースをバイトコードへコンパイルして実行しなければならない**——コンパイラと仮想機械が丸ごとブラウザへ入る必要がある。
- **「ブラウザはブロックできない」をどう解決したか**：ネイティブのドライバは libevent のイベントループでブロックするが、これはブラウザでは死路である。解法は**ループの所有権をホストへ渡すこと**——ページが `setInterval` でエクスポートされた `fluffos_tick(now_ms)` を呼び、毎回スケジューラを一歩進め、期限の来たイベントを処理して即座に戻る。**スケジューリングの中核はネイティブと共有で、違いは誰が鐘を鳴らすかだけ**なので、mudlib は一行も変えなくてよい。
- **その代価**：ソケットなし（DNS はスタブ化されて `127.0.0.1` を返す）、スレッドなし、TLS なし（ブラウザの管轄）、**書き込みは現状タブのセッション内でのみ有効**（MEMFS。IDBFS/OPFS のオーバーレイはロードマップ上）。

**この形は「静的ホスティング + Wasm」をその論理的終点まで押し進めた**：持続するマルチプレイヤーの世界まるごとが、三つの静的ファイルになる。**詳しくは付録 L。**

**四つの形に共通する構造**（これが第二部全体の骨格である）：

```
    もともとサーバがやるはずだったこと
          ↓
    ┌─────────────────┐
    │  重く、高く、公開 │  ← アルゴリズム自体は公開されている
    │  できる密な計算   │     （FFmpeg、エミュレータ、ONNX 推論）
    │                  │     商業機密はなく、あるのは計算コストだけ
    └─────────────────┘
          ↓ Wasm へコンパイル
    ┌─────────────────┐
    │  ユーザのブラウザ │  ← コストはゼロへ、プライバシーは向上、並行数は無限
    │  へ押し出して実行 │     代価：初回のダウンロードサイズ、端末の発熱、電池の消耗
    └─────────────────┘
```

**逆に、押し出せないものは何か**：鍵、認証、課金、そして「漏れたら会社が終わる」中核アルゴリズムに関わるすべて。**この線こそ、第三部の四章がまるごと描く線である。**

## 本章のまとめ

- **GitHub のサイトは静的ではなく、GitHub Pages が静的である**。Pages はファイルをホストするだけ。Actions は時間上限があり終われば破棄される CI 環境。Codespaces は休眠する開発コンテナ。**三つとも常駐ホストではなく、そして Wasm が第四の道を提供した：サーバをブラウザへ移すこと。**
- **COOP/COEP は静的ホスティングで Wasm を走らせるときの筆頭の障害である**。その完全な因果連鎖は：Spectre → `SharedArrayBuffer` の無効化 → 復活したが要クロスオリジン隔離 → 隔離は二つの HTTP ヘッダを要求 → **GitHub Pages はヘッダを設定させない** → マルチスレッド Wasm が動かない。
- **`coi-serviceworker`** は Service Worker でこの二つのヘッダをフロントで合成する。脆弱性の悪用ではなく仕様の正しい使い方である。代価は：ロードが一度余分に要る、HTTPS が要る、**CORP のないクロスオリジンリソースは依然として遮断される**、そして Service Worker の更新の意味論の問題。
- **代価を減らせる二つの選択肢**：**`COEP: credentialless`**（表明のないクロスオリジンリソースを許すが資格情報なしで要求する。`require-corp` よりずっと穏やか）、そして**`SharedArrayBuffer` を必要としないバックエンドへ替えること**（たとえば SQLite-Wasm の `opfs-sahpool` VFS。**隔離不要でしかも最速**。第 7 章参照）。
- **本当にマルチスレッドが要るのかを先に確かめること**——ほとんどの Wasm プロジェクトはシングルスレッドであり、そのまま上げれば動く。この一式に触れる必要すらない。
- **CSP はいずれぶつかるもう一つの壁である**：Wasm のコンパイルは CSP の目には動的コード生成であり、**正解は `script-src 'wasm-unsafe-eval'`**（Chrome 97+／Firefox 102+／Safari 16+）。Wasm のコンパイルだけを許し、`eval()` は許さない。**症状は CSP violation であって Wasm のエラーではないので、調べる方向を間違えやすい。**
- 配備経路の四つの落とし穴（`pkg/` が gitignore される、絶対パスで 404、Jekyll がアンダースコアのフォルダを食う、`await init()` を忘れる）は**症状がすべて 404 で、病因はまったく異なる**——これこそ「チュートリアルどおりにやったのに動かない」の根源である。
- 四つの古典的な形に共通する構造は：**「重く、高く、アルゴリズムが公開されている」密な計算を、ユーザのブラウザへ押し出すこと**である。第四の形（FluffOS が MUD ドライバまるごとをタブへ持ち込み、`fluffos_tick` でホストにイベントループを引き取らせる）はこれを論理的終点まで押し進めた——**持続するマルチプレイヤーの世界まるごと＝三つの静的ファイル**（付録 L 参照）。押し出せないものが何かは第三部の主題である。
- **「サーバコストゼロ」の後半はつねに：コストは消えていない。誰かの電気代になったのだ。**

関門は越え、機械も走り出した。では——**人々はこの上でいったい何を走らせているのか。** 百二十件まで転がったあのリストを、次章から解体する。第 6 章へ。
