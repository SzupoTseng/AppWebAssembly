## I. 映像音声と信号処理

### 1.（元 1）FFmpeg.wasm — 純粋フロントエンドの映像音声トランスコードと編集　🟢

**痛点**：従来のトランスコードはサーバ側（AWS MediaConvert か自前の FFmpeg クラスタ）に依存し、三つの痛点がある。帯域と計算のコストが極めて高い、プライベートなファイルをアップロードせねばならない、オフラインで使えない。

**原理**：Emscripten で数百万行の C 言語の FFmpeg 中核を `ffmpeg.wasm` へコンパイルする。「メインスレッド（UI）+ Web Worker（計算）」モデルを採る。JS が動画を `ArrayBuffer` として Wasm の仮想ファイルシステム **MEMFS** へ書き込み、エクスポートされたコマンドラインインタフェース（`ffmpeg -i input.mp4 output.avi`）を呼ぶと、Wasm の内部がメモリ上のビットストリームを直接デコード・エンコードする。完了したら MEMFS から読み出し、Blob URL に変えてダウンロードさせる。

**性能**：SIMD とマルチスレッド（`SharedArrayBuffer`）でネイティブ C の **60%〜80%** に達すると主張されている。

**長所**：極限のプライバシー（データが端末を出ない）、ホスティングコストがゼロ、ほぼすべての主流形式に対応。
**短所**：ブラウザのメモリ制限（通常 2〜4 GB）に縛られ、数十 GB の 4K の大きなファイルは扱えない。初回ロードで約 20〜30 MB のモジュールをダウンロードする必要がある。マルチスレッド版は**必ず COOP/COEP の設定が要り**、GitHub Pages では `coi-serviceworker` に頼る必要がある。

**競合**：クラウドのトランスコード（計算力に上限がなく、費用が高く、プライバシーの危険がある）。純粋な JS の映像音声ライブラリ（video.js/jsmpeg。簡単な再生とコンテナ処理しかできず、H.264/H.265 の中核の符号復号は担えない）。

### 2.（元 2）Rust-uBlock — Wasm の広告ブロック照合エンジン　🟡

**痛点**：現代の広告ブロッカーは数万のネットワークリクエストを数十万のフィルタ規則（EasyList）とリアルタイムに照合せねばならない。純粋な JS で大量の文字列比較と正規表現照合をすると CPU を大量に消費し、タブ切り替え時に微小な引っかかり（jank）を生む。

**原理**：中核の照合ロジックを Rust で書き、`wasm-bindgen` で Wasm へコンパイルする。**規則ツリー**の構造を採り、線形メモリ内に高度に最適化されたトライ（Trie）とブルームフィルタを構築する。リクエストを捕捉したら URL を Wasm へ渡し、マイクロ秒のうちに数十万の規則をバイナリ検索して、許可／遮断のブール値を返す。

**性能**：文字列比較と規則検索が純粋な JS より **3〜5 倍速い**と主張されている。メモリ使用は安定し、JS が文字列オブジェクトを頻繁に生成することで起きる GC 停止を完全に避けられる。

**長所**：低性能な端末（スマートフォンのブラウザ）の CPU 負荷と消費電力を顕著に下げる。規則のデータベースが線形メモリに緊密に並び、断片化が少ない。
**短所**：JS↔Wasm で URL 文字列を頻繁に受け渡すと境界変換のオーバーヘッド（文字列の符号化・復号）が生じるため、精緻なバッファ共有の仕組みを設計せねばならない。

**競合**：純粋な JS のブロックエンジン（開発が容易でエコシステムが成熟しているが、50 万を超える規則ではメモリと CPU のピークが明らかに高い）。ブラウザ標準の宣言的ブロック（Manifest V3 の `declarativeNetRequest`。性能は最高だが規則数に制限があり、複雑なロジックを自作できない）。

### 3.（元 3）v86 — ブラウザ側の x86 ハードウェアエミュレータ　🟢

**痛点**：ウェブページで Linux や Windows 95 を動かすには、従来はバックエンドで仮想機械（KVM）を走らせ VNC で画面をストリーミングした——サーバコストが高く、遅延が大きく、対話性が悪い。

**原理**：CPU エミュレーション、メモリ管理、ディスクコントローラ（IDE）の中核を Wasm へコンパイルする。Wasm は線形メモリ内で x86 のレジスタ、物理メモリ、割り込みベクタテーブルを模倣し、さらに **x86 の機械語を即座に Wasm 命令へ翻訳して実行する JIT コンパイラ**を内蔵している（第 6 章シナリオ 4 に詳述）。画面の出力時には VRAM のデータをコピーし、JS が Canvas/WebGL で描画する。キーボードとマウスのイベントは JS が捕捉して Wasm の割り込みハンドラへ渡す。

**性能**：ブラウザ内での Linux の実行速度は往年の Pentium 級に近く、数秒で起動して端末に入り、Doom などの古典的な 3D ゲームも滑らかに動くと主張されている。

**長所**：完全に非中央集権であり、GitHub Pages はイメージファイル（10 MB の Linux ISO など）をホストするだけでよい。起動状態をシリアライズしてファイルへ書き出し、いつでもセーブできる。
**短所**：ホストのハードウェア仮想化（Intel VT-x）を使えず純粋なソフトウェア模倣なので、**現代の 64 ビットの重いオペレーティングシステムは動かせない。**

**競合**：バックエンドの Docker/VNC（性能がよく互換性も高いが、コストが利用者数に比例して跳ね上がり、オフラインで使えない）。純粋な JS のエミュレータ（初期の jor1k など。精密なビット演算と緊密なメモリを欠くため 10 倍以上遅く、画面のティアリングと音声の途切れが起きる）。

### 4.（元 4）ONNX Runtime Web (Wasm) — フロントエンドの AI 推論エンジン　🟢

**痛点**：ウェブで顔認識、背景ぼかし、音声のテキスト化を行うとき、従来はデータをバックエンドの GPU へ送り返した——プライバシーの問題、GPU のコスト、ネットワークの遅延を伴う。

**原理**：Microsoft がオープンソースの ONNX Runtime の C++ 中核を Wasm へコンパイルした。開発者は `.onnx` モデルを GitHub Pages に置く。JS がモデルとマルチメディア入力（ウェブカメラの映像など）を読み込み、画像行列を Wasm へ渡す。Wasm はニューラルネットワークの行列積と活性化関数を実装する。中核の最適化は **Wasm SIMD** によるハードウェア加速と **Web Worker** によるマルチコア並列である。

**性能**：SIMD とマルチスレッドを有効にすると、推論速度が純粋な JS のニューラルネットワークより **10〜20 倍速い**と主張されている。軽量モデル（MobileNet、YOLOv8-nano）は一回の推論を 30 ミリ秒以内へ縮められ、30 FPS のリアルタイム解析に達する。

**長所**：計算力をユーザのブラウザが分担するので、静的ホスティングだけで大規模並行の AI サービスを持てる。オフラインで使え、データが安全である。
**短所**：大型モデル（数百 MB の LLM や Stable Diffusion）はダウンロード時間が長すぎる。CPU 推論の性能は WebGPU の加速に及ばない。

**競合**：TensorFlow.js（WebGL/WebGPU モードは GPU の活用で優位だが、ONNX Runtime Wasm のほうがクロスプラットフォーム互換性が堅牢で、よい GPU ドライバのない端末での最後の砦である）。バックエンドの Python API（巨大なモデルに対応するが、高並行時のコストが高い）。

### 5.（元 5）DuckDB-Wasm — ブラウザ側の分析型 SQL データベース　🟢

**痛点**：ウェブで数百万件の大規模データ（CSV、Parquet、ログ）を処理・分析・フィルタするとき、すべてを JS のメモリへ読み込めばオブジェクトが多すぎて OOM か長い GC 停止を招く。表示用のダッシュボードのためにバックエンドのデータベースを立てるのは重すぎる。

**原理**：組み込みの**列指向 SQL データベース**である DuckDB の C++ 中核を丸ごと Wasm へコンパイルする。**ベクトル化実行エンジン**を採り、大規模データをストリームで読み込み、線形メモリ内に緊密な Arrow の列形式で保存する。ユーザが標準 SQL を打つと、Wasm 内部のクエリオプティマイザがメモリを高速に並列走査する。**最も美しいのはリモート読み取りである**：リモートの Parquet/CSV に **HTTP Range Request** を発し、必要なバイト区間だけを取ることをネイティブに対応している（第 6 章シナリオ 4 に詳述）。

**性能**：1000 万行の集計クエリが **100〜200 ミリ秒**で完了し、JS の配列走査（`Array.filter.reduce`）より **60 倍以上速い**と主張されている。

**長所**：静的ページに強力な BI ダッシュボードを直接立てられる。ファイル全体をダウンロードせずにリモートのデータを照会できる。
**短所**：データは既定でメモリ上にあり、タブを閉じれば消える（OPFS/IndexedDB へ永続化できるが、容量の制限を受ける）。

**競合**：SQLite-Wasm（トランザクション型の OLTP が得意だが、百万件規模の OLAP 統計分析では列指向の DuckDB が圧勝する）。純粋な JS のデータ処理ライブラリ（Lodash、Crossfilter。百万件を超えると力不足である）。

### 6.（元 6）SQLite-Wasm — ウェブ側の完全な ACID リレーショナルデータベース　🟢

**痛点**：複雑なフロントエンドアプリケーション（オフラインのノート、家計簿、PWA のメールクライアント）は IndexedDB に頼るしかなかった——非同期のイベント駆動 API は書き方が煩雑で、複数表の JOIN もプリペアドステートメントも強い ACID トランザクションもない。

**原理**：SQLite の公式が標準の C ソースを Emscripten で `sqlite3.wasm` へコンパイルした。**最も精妙なのは永続化層（VFS）である**：公式が専用の仮想ファイルシステムを開発し、**OPFS（Origin Private File System）** か IndexedDB を下層のストレージ媒体として使う（仕組みは第 7 章に詳述）。実行のアーキテクチャは Web Worker で隔離する：メインスレッドが `postMessage` で SQL を送り、Worker 内の Wasm エンジンがメモリ上の B-Tree の索引とデータページを操作し、VFS を通じて同期的に書き戻す。

**性能**：OPFS の下では単一の挿入も複雑な JOIN もローカルのネイティブとほぼ変わらず、読み書きのスループットが JS でラップした IndexedDB より **2〜4 倍速く**、クラッシュ安全性も保証されると主張されている。

**長所**：フロントエンドが完全な標準 SQL とトランザクションの支援を得る。`.db` ファイルをそのまま固めてダウンロードでき、バックアップと移動が極めて容易である。
**短所**：Wasm とグルーで数百 KB になる。ブラウザが OPFS に対応していない場合、IndexedDB で VFS を模倣する退路へ落ちると書き込み性能が大きく下がる。

**競合**：ネイティブの IndexedDB（ダウンロード不要でサイズのコストもないが、関連クエリとトランザクションの能力を欠く）。バックエンドのデータベース（膨大なデータとマルチテナントに対応するが、サーバコストがあり、徹底したオフライン能力がない）。

### 7.（元 7）Pyodide — ブラウザ側の Python 科学計算実行環境　🟢

**痛点**：Python はデータサイエンスの覇者である（NumPy、Pandas、Matplotlib）が、ウェブで Python を実行したり対話的な教育プラットフォームを作ったりするには、以前はバックエンドに Jupyter カーネルを立てるしかなかった——コストが高く、並行数が多いとバックエンドが容易に崩れる。

**原理**：CPython の中核と、C 拡張を大量に含む科学計算ライブラリ（NumPy、Pandas、SciPy、scikit-learn）を丸ごと Wasm へコンパイルする。**双方向の型の橋渡し**：JS の `Array` を Python が `list`/`dict` として読め、その逆もできる。Matplotlib が描いた図をバイナリストリームへ変えて JS が `<canvas>` へ描ける。

**性能**：純粋な Python のコードはネイティブの約 **1/3〜1/5**（仮想機械の中でインタプリタを走らせる二層の抽象）。しかし NumPy/Pandas の C カーネルを呼べば、行列演算はネイティブの **70%** に迫る。

**長所**：真にバックエンドコストがゼロで、完全なデータサイエンス環境がクライアントで走る。対話的な教育とデータ可視化のダッシュボードに極めて向く。
**短所**：**初回のロードは壊滅的である**——CPython と基礎ライブラリで容易に 30〜50 MB になる。緩和手段：パッケージの必要時読み込み（`micropip`）、Service Worker による永続キャッシュ、あるいは MicroPython/Wasm への切り替え。

**競合**：Google Colab / バックエンドの JupyterHub（性能が強く GPU にも対応するが、運用と拡張のコストが高い）。Brython/Skulpt（純粋な JS の Python インタプリタ。ファイルは極小だが構文の模倣にすぎず、**C 拡張を含む科学計算ライブラリを実行できない**）。

### 8.（元 8）Canvas-GIMP / wasm-img — 高性能な画像とフィルタの処理　🟡

**痛点**：フロントエンドで高解像度写真のピクセル単位の処理（ぼかし、シャープ化、色行列、エッジ検出）をするとき、JS で数千万の RGBA ピクセルを走査すれば深刻な GC の引っかかりを招き、シングルスレッドの計算はページに「応答なし」を出させる。

**原理**：GIMP の中核アルゴリズム（あるいは OpenCV の C++ 画像モジュール）を Wasm へコンパイルする。**共有メモリのアーキテクチャ**：Canvas が画像の `ImageData` を読んだあと、ピクセルのポインタを直接 Wasm の線形メモリへ書き、JS↔Wasm の大量のデータコピーを避ける。**並列ピクセル計算**：内部で SIMD を有効にし（一命令で 4 つのピクセルチャネルの浮動小数点演算を同時に処理）、画像をタイルへ切って複数の Worker 内の Wasm スレッドへ配る。

**性能**：4K（約 1200 万ピクセル）の写真を処理するとき、ガウシアンぼかしなどの高度なフィルタの処理時間はたいてい **50 ミリ秒未満**であり、純粋な JS の配列走査より **15〜30 倍速い**と主張されている。

**長所**：極限の演算性能でマルチコア CPU を絞り切る。写真をどのサーバへもアップロードする必要がなく、医療級のプライバシー要求を満たす。
**短所**：アルゴリズムがコンパイル済みのモジュールに固定されており、JS からフィルタのアルゴリズムを動的に注入・改変しにくく、柔軟性に劣る。

**競合**：純粋な CSS フィルタ / Canvas 2D API（ブラウザがハードウェア加速するので極めて速いが、基本的な操作しか対応せず、中核の複雑な行列演算や高度な背景除去を自作できない）。クラウドの画像 API（Cloudinary の類。強力だが課金され、遅延とプライバシーの危険がある）。

### 9.（元 9）OpenTTD-Wasm — 大型の経営シミュレーションゲームの移植　🟢

**痛点**：《トランスポートタイクーン》（OpenTTD）は数万行の C++、大量の経路探索（A*）、車両の AI、動的な地図描画を含む。コミュニティは「開けばすぐ遊べる」ことを望みつつ、クロスプラットフォームの音声・入力・グラフィックの互換性を克服せねばならなかった。

**原理**：Emscripten と **SDL2** で C++ のゲーム全体を Wasm へコンパイルする。SDL2 の低水準な描画命令は自動で WebGL へ翻訳される。マウス、キーボード、音声は Web Audio API と DOM のイベントで橋渡しする。セーブデータと MOD のリソースは Emscripten の **IDBFS**（IndexedDB ベースの仮想ファイルシステム）でブラウザのストレージと同期する。

**性能**：地図上で数千の列車と航空機が同時に経路を計算する重い負荷でも、**60 FPS** を安定して保てると主張されている。

**長所**：移植の利便性が極めて高く、C++ の中核ロジックをほぼ変えずに二十年前のゲームを甦らせられる。完全に無料でバックエンドも要らない。
**短所**：初回の起動でやや大きな素材（スプライトと効果音）をダウンロードする必要がある。サンドボックスの制約により、ウェブ版はローカルのネイティブ版と LAN でマルチプレイしにくい。

**競合**：JS/HTML5 での書き直し（工事が巨大であり、しかも JS の動的型付けと GC は数千のゲームオブジェクトのリアルタイム経路探索でフレームを落としやすい）。

### 10.（元 10）swc-wasm — 超高速な JS/TS のトランスパイルとバンドル　🟢

**痛点**：現代のフロントエンドは新しい構文の JS/TS を互換版へトランスパイルせねばならない（Babel の仕事である）。プロジェクトが大きくなると、Node.js で書かれた Babel は数万の AST ノードの解析で牛歩となり、ビルドが容易に数分かかる。

**原理**：`swc` は **Rust** で書かれた高性能な JS/TS トランスパイラである。Wasm へコンパイルすれば静的ページへ直接配備でき、オンラインのリアルタイムトランスパイラ（Playground）や極小のバンドラとして使える。ユーザが現代的な TS を入力すると、JS が文字列を Wasm のメモリへ渡し、Rust のパーサが極度に最適化されたメモリ配置で AST を構築し、圧縮（minification）とトランスパイルを行う。文字列の解析とトークン化はすべて Wasm の内部で行われ、JS エンジンの頻繁なオブジェクト回収を避ける。

**性能**：トランスパイルの速度が純粋な JS の Babel より **20〜40 倍速い**と主張されている。シングルスレッドのブラウザ環境でも、一万行の複雑な TypeScript のトランスパイルに十数ミリ秒しかかからない。

**長所**：バックエンドのないオンライン IDE、コードフォーマッタ、静的検査プラットフォームの構築に極めて向く。
**短所**：ローカルのネイティブバイナリ版に比べ、Wasm 版はサンドボックスと文字列の境界越えの制約で約 2 倍遅い（それでも Babel よりはるかに速い）。

**競合**：Babel（エコシステムとプラグインが極めて豊富だが、JS 言語の制約を受け、大規模なトランスパイルでは次元を落として打ちのめされる）。

## II. 検索、解析、ツールチェーン

### 11.（元 11）Sonic-Wasm — 純粋フロントエンドの全文検索エンジン　🟡

**痛点**：GitHub Pages に静的ブログ（Hexo、Hugo、Jekyll）や大型のドキュメントサイトを立てるとき、全文検索が要る。バックエンドの方式（Elasticsearch、Algolia）は課金か運用が要る。純粋な JS の方式（Lunr.js）は数 MB の JSON 索引をメモリへ読み込み、あいまい検索と並べ替えで遅くなり GC を招き、入力の遅延を起こす。

**原理**：Rust で書かれた軽量な検索エンジン Sonic の中核を Wasm へコンパイルする。線形メモリ内に高度に緊密な**転置索引とブルームフィルタ**を構築し、データをバイナリのバイト列として並べる。クエリ時に JS が共有バッファでキーワードを渡すと、Wasm がビットマスク演算と N-gram の語頻度分析を行い、マイクロ秒級で文書 ID を返す。

**性能**：数万件の記事（約 50 MB のテキスト）の索引を検索するとき、複雑なあいまい照合が **2〜5 ミリ秒**で完了し、Lunr.js より **10 倍以上速く**、メモリは JS 版の 1/4 だと主張されている。

**長所**：静的ページにミリ秒級でバックエンド不要の全文検索をもたらす。運用コストがゼロ。
**短所**：内容の更新が頻繁な場合、フロントエンドは定期的に大きなバイナリ索引を再生成してダウンロードせねばならない。

**競合**：Algolia/Elasticsearch（膨大なデータと動的な重みに対応するが、課金か運用が要る）。Lunr.js/Fuse.js（学習コストはないが、数万字を超える長文の検索で CPU のピークが高すぎる）。

### 12.（元 12）Web-Wireshark (Wasm-Pcap) — ネットワークパケットの解析　🟡

**痛点**：ネットワーク障害の分析には `.pcap` のパケットファイルを開く必要がある。従来はバックエンドへアップロードして C のプログラム（libpcap）に解析させた——しかし pcap にはたいてい企業の機微なネットワーク位相とパケットの内容が含まれ、クラウドへ上げるのは大きな危険である。

**原理**：C/C++ のネットワーク解析ライブラリ（libpcap か Rust の pcap-parser）を Wasm へコンパイルする。**ストリーミングのバイナリ解析**：ユーザが数百 MB の `.pcap` をドロップすると、JS が File API でストリームとして読み Wasm のメモリへ書く。Wasm がビット単位で分解し、Ethernet、IP、TCP、UDP、さらにアプリケーション層（HTTP/DNS）のプロトコルツリーを再構成し、構造化データを JS へ返して対話的な折りたたみツリーとして描画する。

**性能**：100 MB、数十万フレームの pcap の解析に約 **200 ミリ秒**しかかからず、純粋な JS より **15〜20 倍速い**と主張されている。

**長所**：100% プライバシー安全であり、企業のパケットは決して端末を出ない。静的ホスティングだけで、世界中のエンジニアが無料で使える診断ツールを提供できる。
**短所**：サンドボックスの制約により、Wasm はローカルの NIC を直接呼んで**ライブキャプチャ**を行えず、静的なパケットファイルの解析しかできない。

**競合**：ローカルの Wireshark（機能が最も完全でライブキャプチャに対応するが、インストールが要り、ページに埋め込んで共有できない）。純粋な JS のパケット解析ライブラリ（効率的なバイナリのポインタ操作と構造体の整列を欠き、大きなファイルの解析で OOM を起こしやすい）。

### 13.（元 13）OpenCascade-Wasm — 産業級の 3D CAD モデリングエンジン　🟢

**痛点**：産業用 3D モデリングの中核（AutoCAD や SolidWorks の類）はたいてい数百万行の極度に最適化された C++ である。ウェブで複雑な工業部品（`.STEP`、`.IGES`）を編集しようとしても、純粋な JS のライブラリ（Three.js）は表面メッシュしか扱えず、**正確な境界表現（B-Rep）、ブール演算、曲面の当てはめをまったく計算できない。**

**原理**：オープンソースの産業幾何カーネル **OpenCascade (OCCT)** を丸ごと Wasm へコンパイルする。線形メモリ内に正確な幾何の数学モデル（三次元曲線、NURBS 曲面）を保存し、ブール位相演算、面取り、シェル化のアルゴリズムをすべて Wasm 内で行う。計算後に動的なテッセレーションで三角面を生成し、頂点バッファをそのまま WebGL/WebGPU のハードウェア加速描画へ渡す。

**性能**：複雑な 3D ソリッドのブール切削の効率がネイティブ C++ の **75%** に達し、数百ミリ秒でマウス操作に応答できると主張されている。

**長所**：「ウェブでは 3D を見られても作れない」という制約をひっくり返し、静的ページの上でローカルソフトと同等に正確な幾何代数の演算を実行できる。
**短所**：モジュールが巨大である（圧縮後でも **10〜15 MB**）ため、初回のロードに時間がかかる。

**競合**：Three.js/Babylon.js（可視化の展示には向くが、産業級の幾何位相とソリッドモデリングの数学的能力を持たない）。Onshape（商用のクラウド CAD。強力だが演算はバックエンドの GPU クラスタで行われ、購読料が高い）。

### 14.（元 14）FontForge-Wasm — フォントの編集と変換　🟡

**痛点**：ウェブフォントを最適化するとき、大きなフォント（15 MB の `.TTF`/`.OTF`）をサブセット化（よく使う字だけを残す）したり、圧縮（`.WOFF2` へ変換）したり、輪郭を編集したりする必要がしばしば生じる。ウェブサービスにすると大きなフォントのアップロードが帯域を食い、バックエンドで大量のベジェ曲線を処理するコストも高い。

**原理**：FontForge の C 言語の中核フォント処理・組版エンジンを Wasm へコンパイルする。**ベクタ輪郭の解析**：Wasm 内の TrueType パーサがバイナリの構造テーブル（`glyf`、`head`、`cmap`）を読み、各文字の二次／三次ベジェ曲線の輪郭をメモリへ読み込む。**動的なサブセット化**：ユーザが必要な文字を選ぶと、Wasm がメモリ上で選ばれなかったグリフのデータを直接取り除き、内部のポインタとオフセットをすべて再計算し、Brotli 圧縮を呼んで即座に固める。

**性能**：2 万の漢字を含む巨大なフォントを切り詰めて `.WOFF2` を書き出すのに **1〜2 秒**しかかからず、純粋な JS より **25 倍近く速い**と主張されている。

**長所**：フォントを完全にローカルで処理し、開発者の帯域を消費しない。
**短所**：フォントの設計は複雑な OpenType の機能組版（カーニングなど）に関わり、こうした C 言語のレンダリング版面をフロントエンドで模倣するとき、UI の応答には高度に最適化されたグルーコードが要る。

**競合**：バックエンドの Python（fontTools。エコシステムは成熟しているがサーバが要る）。opentype.js（基本的な読み取りと描画はできるが、高度な WOFF2 圧縮と全面的なサブセット再構成の性能と完全性が足りない）。

### 15.（元 15）WebXm-Tracker — チップチューン（Chiptune / MOD）の合成と再生　🟡

**痛点**：80/90 年代のチップチューン（`.XM`、`.MOD`、`.IT`）は数十 KB しかない。波形ではなく譜面の命令とサンプル楽器を保存しているからだ。MP3 へ変換すればそのサイズの利点が壊れる。純粋な JS でリアルタイムに復号・ミキシングすると、メインスレッドの干渉で「パチパチ」というノイズが出やすい。

**原理**：C 言語のチップチューン復号エンジン（libmodplug か Rust のトラッカーエンジン）を Wasm へコンパイルする。**AudioWorklet のアーキテクチャを採る**：Wasm は高優先度の音声レンダリングスレッドへ読み込まれ、メインの UI スレッドと完全に隔離される。Wasm は毎秒 44100 のサンプル点を計算し、音符、音量、ポルタメントなどのエフェクト命令をリアルタイムに解析し、楽器の波形の周波数を動的に変え、計算し終えた浮動小数点の音声バッファをそのまま出力へ渡す。

**性能**：Wasm の音声スレッドでの計算時間はたいてい **0.1 ミリ秒未満**（128 サンプル点の 2.9 ミリ秒という硬い締切をはるかに下回る）であり、メインのページが大きな画像を読み込んでいても音楽は絶対に滑らかだと主張されている。

**長所**：CPU とメモリのオーバーヘッドが極めて低く、ハードウェア級のレトロ音楽を完璧に再現する。音楽ファイルは数十 KB で再生を始められる。
**短所**：音声のポインタ操作はメモリ安全への要求が極めて高く、配列が一度でも境界を越えれば音声スレッド全体が無音のまま落ち、デバッグが難しい。

**競合**：従来の MP3/AAC の再生（サイズが 100 倍以上大きく、しかもトラックのリアルタイムな動的制御や譜面の可視化ができない）。純粋な JS の音声デコーダ（GC の不定期な停止に妨げられ、ページにアニメーションやスクロールがあると音割れや途切れを起こしやすい）。

### 16.（元 16）Web-GnuPG (Wasm-GPG) — フロントエンドの PGP 暗号化と電子署名　🟡

**痛点**：PGP はメールとファイルを暗号化する黄金標準だが、従来の GnuPG はローカルに CLI をインストールする必要があり、障壁が高い。ウェブサービスにする際、秘密鍵か平文をバックエンドへ上げれば「エンドツーエンド暗号」の中核原則を完全に破壊してしまう。純粋な JS の暗号ライブラリは 4096 ビットの RSA 鍵ペアの生成が極めて遅く、しばしばタブを固まらせる。

**原理**：C 言語の GnuPG（あるいは Rust の Sequoia-PGP）を Wasm へコンパイルする。**多倍長演算の最適化**：暗号の中核はきわめて密な巨大整数の冪剰余演算を伴い、Wasm は `i64` 命令で線形メモリ上のレジスタ級のビット操作を直接行う。**乱数の安全性**：Wasm はハードウェアの乱数源へ直接アクセスできないので、アーキテクチャ上は JS のグルーからブラウザ標準の `crypto.getRandomValues()` を呼び、エントロピーを Wasm エンジンへ注入する。

**性能**：4096 ビットの RSA の生成や数百 MB の AES-256 の処理でネイティブ C の **85%** に達し、鍵の生成は 1〜2 秒、初期の openpgp.js より **8〜10 倍速く**、UI も固まらないと主張されている。

**長所**：真のゼロ知識アーキテクチャであり、鍵と平文は決して端末を出ない。静的ホスティングにより、攻撃者がバックエンドの脆弱性を通じてフロントの暗号ロジックを改竄することが極めて難しくなる。
**短所**：サンドボックスの制約でローカルの GPG キーリングを読めず、使うたびに手で鍵をインポートするかブラウザ内に保存するしかない（後者には危険がある）。

**競合**：ローカルの Gpg4win / GnuPG CLI（最も安全で統合度も最高だが、インストールが要る）。純粋な JS の暗号ライブラリ（SJCL、forge。低水準のメモリ整列とビット演算の最適化を欠き、大きなファイルの暗号化で CPU のピークが高すぎる）。

### 17.（元 17）esbuild-wasm — 高速なフロントエンドのコンパイル・バンドル Playground　🟢

**痛点**：静的ページにコードの練習場を作るとき、Webpack や Babel の JS 版を使うと、ユーザが一行変えるたびに数秒待たされ、即時のフィードバック体験が壊れる。

**原理**：`esbuild` は **Go** で書かれた超高速なバンドラである。このプロジェクトは Go の Wasm ターゲット（`GOOS=js GOARCH=wasm`）で esbuild の中核全体を `.wasm` へコンパイルする。内部でメモリ上のファイルシステムを模倣し、JS が複数ファイルのコードを文字列で渡すと、esbuild が瞬時に分解して単一の JS/CSS へ固めて返す。

**性能**：ブラウザ内で 50 モジュール、約一万行の React プロジェクトのバンドルに **30〜50 ミリ秒**しかかからず、純粋な JS の Rollup/Babel より **30 倍以上速い**と主張されている。

**長所**：オンライン IDE と技術ドキュメントにリアルタイムのトランスパイル能力を与え、バックエンドの Node.js コンパイルサービスをまったく必要としない。
**短所**：**Go からコンパイルされた Wasm モジュールはおおむね大きく（通常 8〜12 MB）**、しかも Go 自身の実行環境を含むので初回ロードに厳しい（これこそ第 3 章の「言語の実行環境の負担」の典型例である）。

**競合**：Babel-Standalone（サイズは小さいが、JS の動的型付けと GC の制約を受け、大量のコードの解析では次元を落として打ちのめされる）。ローカルの esbuild ネイティブバイナリ（マルチコア並列を使えて Wasm 版より 3〜5 倍速いが、ブラウザ内では実行できない）。

### 18.（元 18）Tesseract.wasm — 多言語対応の純粋フロントエンド OCR　🟢

**痛点**：OCR は従来クラウドの API（Google Cloud Vision など）へアップロードする必要があり、課金とプライバシーの問題（身分証や領収書の写真が漏れる危険）を伴った。純粋な JS の文字照合アルゴリズムは精度が極めて低く、複雑な背景や手書きに対処できない。

**原理**：C++ のオープンソース OCR エンジン Tesseract を Emscripten で Wasm へコンパイルする。Tesseract 4.0 以降は **LSTM** ベースのエンジンを導入しており、Wasm モジュールは訓練済みの言語パック（`.traineddata`）を直接読み込み、線形メモリ上で行列積を実行する。**言語パックの動的読み込み**：エンジン自体は軽量に保ち、ユーザが言語を選んだときに初めて JS が対応するバイナリの特徴パックをダウンロードして Wasm へ渡す。

**性能**：SIMD を有効にすると、文字で埋まった A4 の画像の認識に約 **0.5〜1.5 秒**、精度は 95% 以上で、ネイティブ C++ の **70%** に達すると主張されている。

**長所**：100% オフラインで使え、データは完全にブラウザに留まる。静的ホスティングだけで、無限に並行し運用ゼロの無料テキスト抽出ツールを作れる。
**短所**：言語の訓練パックが大きい（中国語のパックはしばしば **10〜40 MB** に達する）ため、モバイルや回線が悪いときの待ち時間が長い。

**競合**：クラウドの商用 OCR API（精度は最高だが従量課金でプライバシーを守れない）。純粋な JS の基本的な画像認識（機械学習モデルの支えがなく、傾いた画像やノイズのある画像で認識能力を失う）。

### 19.（元 19）WebManiac-GameBoy — ハードウェア級の Game Boy エミュレータ　🟡

**痛点**：初期の純粋な JS のエミュレータは、ハードウェアのクロックと正確な割り込みの模倣で巨大な障害にぶつかった——JS の `setInterval` は不正確であり、ページのスクロールやバックグラウンドのタスクで音と映像が大きくずれ、コマ落ちと耳障りなノイズを生んだ。

**原理**：Rust で書かれた精密な Game Boy エミュレータの中核を Wasm へコンパイルする。**クロック精度の模倣**：Game Boy の LR35902 CPU は毎秒約 419 万のクロックサイクルを実行する。Wasm は厳密なループでレジスタの状態、メモリマップド I/O（MMIO）、画像処理ユニット（PPU）の走査線を精確に模倣する。**ダブルバッファ描画**：Wasm は線形メモリ内に 160×144 の生のピクセルバッファを保持し、毎フレームの V-Blank 割り込みで素早く JS の Canvas `ImageData` へコピーし、`requestAnimationFrame` で 60 Hz のリフレッシュレートと同期する。

**性能**：ハードウェアのクロックの模倣に **CPU の 2% 未満**しか使わず、画面はしっかり 60 FPS に固定され、8 ビットの効果音も完璧に滑らかだと主張されている。

**長所**：完璧なハードウェアの再現度で、音と映像の同期が極めて滑らかである。ゲームの状態をワンクリックでバイナリのスナップショットへ書き出し、ミリ秒で復元できる。
**短所**：サンドボックスの制約により、一部の USB コントローラの高度な振動フィードバックや特殊なハードウェア周辺機器に対応できない。

**競合**：純粋な JS のエミュレータ（動的な型変換と不定期な GC 停止で微小な画面のティアリングと音の途切れが生じる）。ローカルの RetroArch（機能は最も揃っているが、インストールと設定が要る）。

### 20.（元 20）Libzen-Wasm (MediaInfo) — マルチメディアのメタデータの深い解析　🟡

**痛点**：映像音声の実務者はしばしばメディアファイルの詳細なパラメータ（コーデック、ビットレート、フレームレート、色空間、音声トラック、字幕のコンテナ）を確認する必要がある。現代のコンテナ（`.MKV`、`.MP4`）のメタデータはファイルの先頭か末尾に散らばっていることがあり、数 GB の動画をアップロードしたり頻繁に分割転送したりすれば帯域を大きく食う。

**原理**：C++ の MediaInfo（下層は libzen と libmediainfo）を Wasm へコンパイルする。**範囲読み取り**：ユーザが 4 GB の動画をドロップすると、JS が HTML5 File API で**ファイル構造の先頭と末尾だけを精確に取る**（MP4 の `moov` atom など）。**バイナリ構造の分解**：JS がその断片を Wasm へ渡し、Wasm 内部のパーサがマイクロ秒でコンテナのバイナリのテーブル構造を分解し、数百項目の構造化パラメータを JSON で返す。

**性能**：5 GB でマルチチャンネルと埋め込み字幕を含む 4K 動画の解析が **10 ミリ秒**を超えず、メモリ使用は 5 MB 未満だと主張されている。

**長所**：極めて低い資源で、任意のサイズの動画をフロントエンドで秒単位に解析できる。サーバの帯域を 100% 節約する。
**短所**：コンテナが壊れていたり形式が珍しかったりするファイルに対し、コンパイル時に例外処理を十分に最適化していないと、モジュールがそのまま落ちることがある。

### 31.（元 40）Z-Music (libgme-wasm) — レトロゲーム機の音声チップのエミュレーション　🟡

**痛点**：初期のゲーム機のネイティブな音楽（ファミコンの Ricoh 2A03、スーパーファミコンの SPC700、メガドライブの YM2612。形式は `.nsf`、`.spc`、`.vgm` など）の再生は非常に魅力的である——これらのファイルは数 KB しかない。ハードウェアを直接制御する命令だからだ。しかし純粋な JS でこれらのチップのフィルタと波形発生器を模倣すると、不正確なタイマと動的型付けで頻繁に音割れが起き、CPU 使用率も不合理に高い。

**原理**：C++ の音声チップエミュレーションライブラリ **Game Music Emulator (GME)** を Wasm へコンパイルし、**AudioWorklet** と組み合わせて配備する。**スレッドの隔離**：Wasm は最高優先度の独立した音声スレッドへ読み込まれ、UI の描画、スクロール、メインスレッドのブロックの干渉をまったく受けない。**レジスタ級のハードウェアエミュレーション**：Wasm は線形メモリ内でこれら旧世代チップの内部レジスタの状態を模倣し、44.1 kHz で毎秒 44100 回の波形の浮動小数点を計算し、矩形波、三角波、ノイズチャネル、PCM サンプルのミキシングを動的に模倣する。

**性能**：複雑なスーパーファミコンの 16 ビット音声チップのエミュレーションに **CPU の 0.5% 未満**しか使わず、音声バッファの計算時間は 0.05 ミリ秒未満だと主張されている。

**長所**：極めて低いオーバーヘッドでレトロハードウェアの音声を完璧に甦らせる。数 KB の音声ファイルでゲーム音楽を一曲まるごと再生できる。
**短所**：壊れた非標準の ROM に当たると容易にメモリの境界越えを引き起こすので、厳格なサンドボックスの境界検査が要る。

**競合**：従来の MP3/OGG の再生（サイズが 1000 倍以上大きく、しかもトラックのリアルタイムな切り替えやピッチを保った変速というハードウェア級の対話の楽しみを失う）。純粋な JS の音声エミュレータ（GC の停止に妨げられ、ユーザがページをスクロールした途端に音が途切れ割れる）。

### 32.（元 41）Stockfish.wasm — 世界最高峰のチェス AI エンジン　🟢

**痛点**：Stockfish の中核的な競争力は、密なアルファベータ枝刈り探索、NNUE ニューラルネットワークの評価、膨大なビットボード演算にある。以前はウェブで強力な解析を提供するには、バックエンドの CPU サーバ群へ送るしかなかった——維持コストが巨大であり、数万のプレイヤーが同時に解析すれば計算力が瞬時に振り切れる。

**原理**：C++17 の Stockfish のソースを Emscripten で Wasm へコンパイルし、主流のチェスサイト（Lichess など）のフロントエンド解析エンジンとする。**マルチスレッドと SIMD のアーキテクチャ**：Web Workers + `SharedArrayBuffer` で大規模な並列探索を実現し、内部で SIMD を有効にして NNUE の重み行列積を加速する。**ビットボードの直通**：線形メモリ内で盤面の状態を `i64` で表し、ビットマスクとビットスキャンの命令で数百万の合法手を瞬時に列挙する。

**性能**：SIMD と 4 コアを有効にすると、探索速度（NPS）がローカルのネイティブ C++ の **75%〜85%** に達し、フロントエンドで毎秒数百万から千万手を計算でき、深さは 20 手以上に達すると主張されている。

**長所**：真に非中央集権であり、静的ホスティングだけで世界最高峰の AI 解析を提供でき、サーバの計算コストはゼロである。オフラインで使え、ネットワークの遅延もない。
**短所**：NNUE の重みファイルはたいてい数 MB から十数 MB ある。強力な探索はユーザの CPU を振り切らせ、端末の発熱と電池の消耗を招く。**しかもこれは `SharedArrayBuffer` を要する典型的な事例であり——GitHub Pages では必ず `coi-serviceworker` と組み合わせねばならない。**

**競合**：純粋な JS のチェスエンジン（初歩的な計算しかできず、複雑な終盤では完全に次元を落として打ちのめされる）。バックエンドのクラウド解析（計算力に制限はないが、数百万のプレイヤーの無料の並行需要には応えられない）。

### 33.（元 42）Web-GnuTLS (Wasm-TLS) — フロントエンドの TLS 極小ネットワークスタック　🟡

**痛点**：バックエンドのない非中央集権のウェブアプリケーション（P2P ネットワーク、ブラウザ側の MQTT コンソール）を構築するとき、フロントエンドが外部の TCP/UDP サーバと（WebSocket の中継を通じて）安全な TLS 接続を直接張る必要が生じることがある。しかしブラウザ標準の `fetch` のセキュリティ機構は非常に厳格で、**TLS ハンドシェイク段階の証明書検証、暗号スイートの折衝、私設 CA の登録を開発者が自作することを許さない。**

**原理**：C 言語の GnuTLS を丸ごと Wasm へコンパイルし、静的ページ上に完全にフロントエンドの制御下にある「極小の暗号ネットワークスタック」を構築する。**メモリバッファのネットワーク I/O（BIO モード）**：Wasm はシステムのネットワーク API を直接呼ばず、TLS のハンドシェイクのパケットをメモリ上のリングバッファへ書き、外部の JS が取り出して WebSocket か WebRTC のデータチャネルで送る。**暗号演算子の加速**：TLS のハンドシェイクは大量の非対称（ECDHE、RSA）と対称（AES-GCM、ChaCha20-Poly1305）の演算を伴い、Wasm は 64 ビット整数演算と緊密な配置でサンドボックス内の多倍長乗算を高速に実行する。

**性能**：完全な TLS 1.3 のハンドシェイクと鍵交換が **5〜10 ミリ秒**を超えず、スループットはローカルの C 版とほぼ同等で、純粋な JS の暗号ライブラリより **10 倍以上速い**と主張されている。

**長所**：ネットワークセキュリティのプロトコル層に対するブラウザのブラックボックスの制約を破り、静的ページで独自の証明書検証や双方向 TLS（mTLS）を実現できる。鍵は端末を出ない。
**短所**：TLS のネットワークスタックは極度に複雑で Wasm のモジュールも大きい。しかもソケットを直接操作できないため、パケットの転送と再結合のための複雑な JS のグルーを書かねばならない。

**競合**：純粋な JS の暗号プロトコルライブラリ（forge の類。TLS の流れの一部を模倣できるが、高頻度の暗号化パケットのスループットで GC の引っかかりを起こし、TLS 1.3 への対応と安全性も十分ではない）。

### 34.（元 43）QuickJS-Wasm — 安全なサンドボックス級の「JS の中の JS」実行環境　🟢

**痛点**：オンラインの Playground、ローコードのプラットフォーム、ユーザ製プラグインを要するアプリケーションでは、フロントエンドが「ユーザの入力した JavaScript を実行する」必要がある。`eval()` や `new Function()` を直接使えば、ユーザのコードが `window`、`document`、`cookie` へ直接アクセスでき、致命的な XSS の危険を生む。iframe で隔離しても、攻撃者は `while(true)` でメインスレッドを完全に固められる。

**原理**：Fabrice Bellard が書いた軽量で効率的な C 言語の JS エンジン **QuickJS** を丸ごと Wasm へコンパイルし、「JavaScript の中でもう一つの JavaScript を走らせる」という精妙なことを実現する。**二重のサンドボックス**：ユーザのスクリプトはブラウザ標準の V8 では実行されず、文字列として QuickJS-Wasm へ渡され、Wasm の閉じた線形メモリのサンドボックス内で解釈実行される。**外側のページのいかなる DOM や機微な情報へもまったくアクセスできない。** **時間とメモリの割当**：Wasm モジュールの内部に割り込みハンドラを設け、ユーザのコードが割当（500 ミリ秒など）を超えるかメモリを超過して要求すれば即座に強制終了する——無限ループがページを固めることを完璧に防ぐ。

**性能**：解釈実行ではあるが QuickJS は極めて軽量で、Wasm 内で標準の JS を毎秒数百万命令で実行でき、複雑な業務ロジック、単体テスト、データ変換を滑らかに動かすのに十分である。

**長所**：静的ページに軍需級の安全なコード実行環境をもたらし、XSS と無限ループを根絶する。圧縮後は数百 KB しかなく、読み込みが極めて速い。
**短所**：「インタプリタのインタプリタ」であるため、JIT で最適化されたネイティブの V8 には性能で及ばず（通常 10〜20 倍遅い）、重いグラフィックや行列演算には向かない。

**競合**：ネイティブの `eval()` / iframe のサンドボックス（性能は最高だが、安全の境界が脆く、高度な脆弱性の悪用や悪意の無限ループを防ぐのが極めて難しい）。JS で書かれた JS インタプリタ（サイズは同程度だが、構文の対応度とメモリ割当の制御の完全性で QuickJS にはるかに劣る）。

### 35.（元 44）Web-GSL — GNU の科学計算・数値解析の行列ライブラリ　🟡

**痛点**：工学、物理、金融の計量の領域ではしばしば複雑な数値計算が要る：高次の行列の固有値の求解、常微分方程式（ODE）の数値解、最小二乗の当てはめ、高速フーリエ変換（FFT）、複雑な統計分布からの標本抽出。従来は C 言語の権威あるライブラリ **GSL** に頼ってきた。フロントエンドで JS の浮動小数点配列にこれらの式を手書きすると、演算子の多重定義、緊密なメモリ整列、高速なポインタ算術を欠くために遅いだけでなく、浮動小数点の精度の喪失で科学的な結果が誤りやすい。

**原理**：巨大で厳密な C 言語の GNU 科学ライブラリの中核を丸ごと Wasm へコンパイルし、オンラインの科学数値計算の作業台を作る。**正確なメモリ配置（BLAS の統合）**：効率的な基本線形代数サブプログラム（CBLAS）を内部に統合し、多次元行列を連続した倍精度浮動小数点（`f64`）で厳密に整列させ、L1/L2 のキャッシュヒット率を最大化する。**GC の干渉ゼロ**：微分方程式の近似も非線形の最小二乗の反復も、すべて Wasm 内部のメモリプールで実行する。

**性能**：500×500 の行列の固有値の求解や百万点の FFT の実行で、効率がネイティブ C の **80%〜90%** に達し、純粋な JS の数値ライブラリより **20〜40 倍速い**と主張されている。

**長所**：教育、研究、金融工学に、インストール不要で完全に無料の産業級の数値計算プラットフォームをもたらす。精度は GNU の国際的な科学標準に適合する。
**短所**：GSL の API 設計は極度に学究的かつ低水準であり、現代のフロントエンドが慣れたチェーン呼び出しや JSON の受け渡しを欠くので、やや厚い JS のラッパ層を書く必要がある。

**競合**：math.js（日常的な代数演算と通常の作図には向くが、硬派な産業級の微分方程式の求解、大きな疎行列、高精度の数値の当てはめではまったく比較にならない）。

> **本巻（1–35）のまとめ**：最初の 35 案は**映像音声の信号、データの照会、パーサとツールチェーン**の三領域に集中しており、Wasm エコシステムのなかで**最も検証可能性の高い**一段である——FFmpeg.wasm、v86、Pyodide、DuckDB-Wasm、SQLite-Wasm、esbuild、swc、OpenCV.js、Tesseract.js、solc、Stockfish、HarfBuzz、QuickJS、Viz.js は、いずれも実在し広く使われているプロジェクトである。
> 共有する形はきわめて一致している：**成熟した C/C++/Rust の中核を線形メモリへ移し、ゼロコピーのビューで JS と受け渡し、必要なら SIMD と Worker を足す**。違いは、それぞれがどの壁にぶつかったかだけである——**FFmpeg はメモリ上限に、Pyodide はダウンロードサイズに、Stockfish は `SharedArrayBuffer` に、OpenCascade はモジュールの大きさにぶつかった。**
> 次巻（36–70）は**圧縮、地理、暗号、グラフ代数、リバースエンジニアリング**へ入り、🟡 の等級の比重が上がりはじめる。
