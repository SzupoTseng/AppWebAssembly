# 付録L　深水の事例：FluffOS × Wasm——MUD のサーバをまるごと静的ページへ

> **これは本書で唯一、単独の一篇に値する事例である。同時に三つのことを兼ねているからだ：**
> **一つ、それは付録 E にある二つの 🔴 例示的な構成（事例 58 Minestom-Wasm、事例 60 Micro-Apache-Wasm）の現実の版である**——しかも、その二つの構想よりも徹底している。
> **二つ、それは本書の十二章が語ったすべての壁に、一度でぶつかり切っている**。しかも、それぞれの壁の扱い方が公開の工学の記録として残っている。
> **三つ、それは本書の中核の命題の、最も清潔な生きた標本である**：**コードは 100% ダウンロードでき、自前で立てられ、改変できる。それでいてその価値は三十年のあいだ一分たりとも失われていない。**
>
> **真偽の等級：🟢 確かめられる。** 本付録の技術の細部はすべて FluffOS 公式リポジトリの `README.md` と `src/wasm/README.md`、および `fluffos/mudlibs` リポジトリから引いている。**時とともに動くのは収録の数と「WASM 化された」割合だけである**——リポジトリのその時点の状態を基準にしてほしい。

## 1. それが何であるか

### FluffOS：いまも保守されている LPMud のドライバ

**FluffOS** は **MudOS の現代の分岐**——C++ で書かれ、いまも積極的に保守されている **LPMUD driver**（LPC のインタプリタ + ゲームエンジン）である。その職責は「一つのゲーム」ではなく、**ゲームサーバの完全な実行環境が一台**であることだ：

```
FluffOS driver（C++）
├── LPC コンパイラ  ← mudlib の .c のソースを実行時にバイトコードへ
├── 仮想機械（VM）  ← そのバイトコードを走らせる
├── efun            ← 組み込みの関数群（文字列、配列、ファイル、ネットワーク、時刻…）
├── スケジューラ核  ← heartbeat（心拍）、call_out（タイマ）、reset（再設定）
└── ネットワーク層  ← telnet / WebSocket / TLS
```

既存の MudOS の mudlib と後方互換であり、十数年ぶんの性能の最適化を積み上げている。加えて **WebSocket、TLS、MySQL/PostgreSQL/SQLite3 の統合**、および **UTF-8 の EGS を意識した LPC の文字列演算**（範囲演算子が emoji やその他の Unicode 文字を支える）を備える。

**ビルドの目標**：CMake で、Ubuntu、macOS、Windows（MSYS2/MinGW64）、**そして WebAssembly**。

### mudlibs：ひとつの時代のソースコードの典蔵

`github.com/fluffos/mudlibs` は**中国語圏の MUD の場面のソースコードの考古学的な典蔵**である——一九九〇年代半ばから二〇一五年前後までの作品にわたり、《侠客行》《笑傲江湖》《金庸群侠伝》《西遊記》といった武侠・仙侠を題材にした LPC のゲームと、その各種の分岐を収めている。

リポジトリの組み方そのものが、一つの修復の工学の記録になっている：

```
archives/                       元の封存ファイル
libs/<slug>/raw/                手を触れずに解凍した中身（元の符号化を保つ）
libs/<slug>/work/               遊べる版（UTF-8 へ変換し、修復を当てたもの）
libs/<slug>/config.fluffos      実行時の設定
libs/<slug>/README.md           遊ぶ人への説明
libs/<slug>/NOTES.md            修復の記録
scripts/                        変換と試験の道具
lib_numbering.json              機械が読める対照の表
```

**収録の状態**（リポジトリの README の記載による。数字は修復の進みとともに動く）：

| 状態 | 数 |
|---|---|
| 修復された mudlib | **200 本**（**158 個**の重複しない codebase にわたる） |
| **ブラウザ（WASM）で遊べると検証済み** | **79 個** |
| native での起動は検証済み、WASM の同梱は未着手 | 117 個 |
| 方針として native 限定 | 1 個 |
| 起動できないと確認 | 4 個 |

**ライセンス**：多くは歴史的な共同体の典蔵として、正式なライセンス条項を持たない（うち《重生的世界》は明確に GPLv2）。プロジェクトの立ち位置は「**それらを文化資産として保存する**」ことであり、原作者の署名を保っている。

> ⚠️ **数は動く**：オンラインの典蔵サイト `mudlibs.fluffos.info` が本書の執筆当時に挙げていた遊べるゲームの数と、リポジトリの README の統計は完全には一致していない（前者はおよそ九十余り、後者は 79 個が WASM で遊べると検証済みと記す）。**この種の数字は修復が進むたびに変わる**——あなたが訪れたその時点のリポジトリとサイトを基準にしてほしい。本書が引くのは絶対の値ではなく相対の関係である。

## 2. なぜそれが単独の一篇に値するのか

**それが、他の者はスライドの上でしか越えなかった線を、実際に越えたからである。**

付録 E の二つの 🔴 の項目を思い出そう：

- **事例 60「Micro-Apache-Wasm」**：ブラウザの中で微小な HTTP サーバを走らせ、Service Worker で要求を横取りして Wasm へ食わせるという構想。**この構想は成り立つが、それが模すのは「要求—応答」という状態のないものである。**
- **事例 58「Minestom-Wasm」**：ブラウザの中で Minecraft のサーバを走らせるという構想。**こちらのほうが近いが、他人が入ってくるには WebRTC が要る。**

**FluffOS の Wasm の目標が成し遂げたことは、この二つよりも硬い**——MUD のドライバは要求の処理器ではなく、**心拍があり、タイマがあり、持続する世界の状態があり、複数の同時接続があり、しかも実行時に利用者のコードをコンパイルする**ものだからだ：

> 公式 README の言葉はこうだ：**「The whole driver runs in a browser page (or node) — compiler, VM, efuns, telnet.」**
> コンパイラ、仮想機械、組み込みの関数群、telnet のプロトコル——**すべて**が一つのブラウザのタブの中にある。

そして mudlib の配り方はこうだ：**「Mudlibs ship as static bundles via `tools/wasm/pack-mudlib.sh`; no server required.」**——**静的な bundle にまとめられ、サーバは要らない。**

これはまさに、第 5 章のあの一文の極致の版である：**計算は消えていない。金を払う人が替わっただけだ。**

## 3. アーキテクチャの深掘り：解かねばならなかった五つの難題

この節が本付録の技術の核である。**FluffOS の Wasm への移植は「もう一度コンパイルすれば済む」というものではなかった**——Wasm とブラウザの物理的な制約を一つずつ処理せねばならず、そのそれぞれの解き方が書き留めるに値する。

### 難題一：ブラウザは詰まってはならない。しかしサーバの本質は「待つ」ことである

**native のドライバは libevent のイベントループの中で詰まっている**——`while(true) { wait_for_events(); dispatch(); }`。**これはブラウザでは死路である**：メインスレッドがひとたび詰まれば、タブ全体が凍る。

**解き方：イベントループの所有権をホストへ渡す（host-driven tick）。**

```javascript
// ページが setInterval / requestAnimationFrame でドライバを駆動する
setInterval(() => {
  Module._fluffos_tick(Date.now());   // ← 一度スケジュールを進め、期限の来た事象を処理して即座に戻る
}, 50);
```

**要となる設計**：スケジューラの核（gametick の待ち行列、保守の事象）は **native と Wasm のあいだで共有されている**。両者の違いは**「誰がループを進めるか」だけ**にある。ゆえに **heartbeat、call_out、reset といった LPC の層の仕組みはまったく変えなくてよい**——mudlib のコードは一行たりとも、自分がブラウザの中で生きていることを知らない。

> 💡 **これは移植の全体で最も美しい一手である**：それは「時間がどう流れるか」を変えず、「誰が鐘を打つか」だけを変えた。

> 🔧 **注目に値する未来の選択肢**：この「ループをホストへ渡す」解き方が解いたのは**能動的なスケジュール**であって、**受動的な待ち**ではない——LPC のコードが非同期のもの（たとえば OPFS の非同期の API や、一度のネットワーク要求）を読もうとしたとき、ドライバには依然として待つ場所がない。**JSPI**（第 3 章の壁七、付録 M §5）はまさにこの部分に効く：エンジンが Wasm のスタックを丸ごと中断し、Promise が解決したら再開させるのだ。
> このプロジェクトにとっての意味は具体的である：**roadmap にあるあの「IDBFS/OPFS の層を被せる」永続化の計画は、JSPI のあとなら、ストレージの層をまるごと非同期へ書き換えずに済む。** 代価は再入の問題を招くことだ——**中断のあいだに `fluffos_tick` がもう一度呼ばれうる**が、ドライバは「同時に走る tick は一つだけ」という仮定を非常に強く置いている。**これは「新しい能力が新しい制約を連れてくる」典型の例である。**

### 難題二：socket がない。しかし遊ぶ人はそれぞれ一本の接続である

**解き方：「接続」をバイト列の管（Transport）として抽象する。**

利用者の接続はそれぞれ `Transport` を持つ——抽象的なバイト列の管で、`write` / `flush` / `schedule_command` / `close` の四つの操作しかない。その下には三つの実装がある：

| 実装 | 目標 | 下層 |
|---|---|---|
| `SocketTransport` | native | libevent |
| `WebsocketTransport` | native | libevent |
| **`WasmConsoleTransport`** | **ブラウザ** | **JS の橋渡し** |

`WasmConsoleTransport` の二つの向き：

```
外向き：ドライバの吐くバイト列 → Module.fluffos.onOutput(id, bytes) → ページの端末
内向き：利用者の打つ命令       → 輸出関数 fluffos_input(id, bytes, count) → ドライバ
```

**そして最も面白い細部はこれだ：ドライバは依然として本物の telnet のプロトコルを吐く。** ゆえにウェブページの側が telnet のクライアントを用意せねばならない——公式に付属する画面は **ECHO、SGA、NAWS（窓の大きさ）、TTYPE** を交渉し、**xterm.js** で端末を描画する。

> **この部分は付録 E の事例 29（xterm の Wasm 解析プラグイン）のちょうど裏返しの対照である**：あちらは ANSI の解析を Wasm へ移したのに対し、こちらは**プロトコルのもう一方の端**をまるごと Wasm へ移し、xterm.js を外側の表示器として使っている。

### 難題三：輸出の面は十分に狭くなければならない

**ドライバ全体が外へ晒すのは七つの関数だけである**——これはまさに、第 2 章の「Export セクションは攻撃者につねに見えるもの」と、第 12 章の「境界は狭く」の教科書級の実演である：

| 輸出関数 | 用途 |
|---|---|
| `fluffos_boot(config_path)` | ドライバを初期化する |
| `fluffos_tick(now_ms)` | 実際の時刻に従ってスケジュールを進める |
| `fluffos_connect()` | 新しい仮想の接続を作る |
| `fluffos_input(id, bytes, count)` | クライアントの命令のバイト列を送り込む |
| `fluffos_disconnect(id)` | 接続を閉じる |
| `fluffos_shutdown()` | ドライバを閉じる |
| `fluffos_flag(flag)` | 実行時の旗を立てる（`'test'` など） |

モジュールの実体化：

```javascript
const M = await createFluffOS({ print, printErr, locateFile });
```

**七つの関数で、サーバが一台。** 第 2 章のシナリオ 4 のあの一文——**境界は粗く、往復は少なく**——に照らせば、これは見つけられる限り最も極端な例である。

### 難題四：mudlib は数万のファイルであり、Wasm にはファイルシステムがない

**解き方：MEMFS + Emscripten の `file_packager`。**

Emscripten はファイル I/O を透明にメモリのファイルシステム（MEMFS、第 7 章参照）へ写す。mudlib は `file_packager` で**単一の `mudlib.data` の映像 + `mudlib.js` の読み込み器**にまとめられ、実行環境の起動前に指定の経路へマウントされる。

```bash
# 任意の mudlib をまとめる
MUDLIB=/path/to/lib tools/wasm/build.sh
# あるいは
tools/wasm/pack-mudlib.sh --mudlib <dir> --config <path>
```

**こうして配布の形はこうなる**：一つの `.wasm`、一つの `.js` の糊、一つの `.data` の映像——**三つの静的なファイルが、そのままゲームの世界まるごとである。**

**だがここには正直な現況が一つあり**、それはちょうど第 7 章のあの四段のストレージの階段の生きた教材になっている：

> **いまのところ書き込みはタブのセッションの内でしか有効でない（MEMFS は揮発する）。**
> 公式の roadmap の Phase 2 の計画はこうだ：**mudlib の書き込みの経路（`/data`、セーブ、ログ）に IDBFS（あるいは OPFS）の層を被せ、タイマと `visibilitychange` のときに `FS.syncfs()` を呼ぶ**——データがタブの再読み込みをまたいで生き延びられるように。**まだ実装されていない。**

**言い換えれば：このプロジェクトはいま第 7 章の第一段（MEMFS）で止まっており、自分が第二段・第三段（IDBFS/OPFS）へ進むべきだと分かっている。** 本書のどこにも、これ以上によい現場の検証はない。

### 難題五：能力は削り落とされねばならない

第 2 章はこう言った——「安全性の最も安い実現の仕方は、防護を足すことではなく、能力を削ることである」。**FluffOS の Wasm のビルドは、それを一枚の表にしている**：

| 機能 | 状態 | 理由 |
|---|---|---|
| libevent | **除去** | tick の待ち行列が取って代わる |
| OpenSSL / TLS | **除去** | **TLS はブラウザの担当**。`sys_reload_tls` は存在しない |
| zlib | **除去** | MCCP と compress のパッケージを停止 |
| POSIX の eval-limit のタイマ | 自動で停止 | `__linux__` でしか使えない。代替は計画中 |
| BSD socket | 閉鎖 | 外向きの socket の efun がない |
| DNS | **スタブ化** | 次の tick で `127.0.0.1` を合成して返す |
| 外部のプロセス | 閉鎖 | `posix_spawn` を支えない |
| Worker のスレッド | 閉鎖 | async のパッケージがない |
| データベースのクライアント | 閉鎖 | MySQL/SQLite/PG のライブラリが使えない |

**この表こそ、能力ベースの安全の具体的な姿である**（第 1、7 章）。それは「これらの攻撃面を防いだ」ではなく、「**これらの攻撃面は、このビルドにはそもそも存在しない**」である。

同時にそれは、第 3 章の四つのシステムの壁——**native のシステムへの入り口がない、メモリは増やすだけで縮められない、複数スレッドがない、同期のコードが非同期の世界にぶつかる**——にきれいに対応している。

## 4. 具体的な数字

**これは本書で最も価値のある実測の数字の組である。ベンチマークの玩具ではなく、現実の、複雑な、いまも保守されているプロジェクトから来ているからだ。**

| 項目 | 数値 | 本書の対応 |
|---|---|---|
| 初期の線形メモリ | **64 MB**（必要に応じて **2 GB** まで伸びる） | 第 8 章：上限が 4 GiB ではなく 2 GB に置かれていることに注目——**これがまさに「ブラウザの現実による遮り」である** |
| スタック | 16 MB | 第 2 章 |
| コードの大きさ（PCRE 込み） | **〜3.6 MB 生** | 第 3、8 章：「30 MB という実務上の天井」をはるかに下回る |
| コードの大きさ（Brotli 圧縮後） | **〜0.8 MB** | 第 8 章：**圧縮率およそ 4.5 倍。「Wasm の Brotli の圧縮率はたいてい良い」を裏づける** |
| ICU のデータ | **〜780 KB**（もとはおよそ 30 MB） | 第 8 章：**break-iterator の規則だけを残し、97% を削った**——「体積を削る投資対効果が最も高い一歩はコンパイルの旗ではなく、使わないデータを削ることだ」 |
| DWARF のデバッグ情報 | リンク時に剥ぐ | 第 9 章 |
| 関数名 | **残す**（読めるスタックトレースのため） | 第 3 章：**これは意図した引き換えである**——難読化の強さを少し犠牲にして、デバッグ可能性を買っている |

> 🔍 **あの ICU の数字は、三秒立ち止まって見る値打ちがある。**
> 30 MB → 780 KB、97.4% を削った。**これは `wasm-opt` によるものでも LTO によるものでもなく、「私は ICU に何をさせたいのかを、はっきり考えた」ことによる**——このプロジェクトが要るのは break-iterator（分かち書き）の規則だけなので、残りの地域設定、時間帯、照合の規則、翻字の表はすべて同梱しない。
> **第 8 章のあの「体積を削る投資対効果の順序」には、第 0 条を足すべきである：まずデータを削り、それからコードを削れ。** 大きな C/C++ のプロジェクトの Wasm の産物には、それが引きずり込んだデータの表が半ば以上を占めることがよくあり、そしてその表のたいてい 90% は、あなたにはまったく要らないものだからだ。

## 5. 自分の手元で動かす

### 経路 A：native（いちばん早く何かが見える）

```bash
# 1. mudlib を取る
git clone https://github.com/fluffos/mudlibs
cd mudlibs/libs/<選んだ slug>

# 2. ビルド済みの driver で起動する（work/ は UTF-8 へ変換し修復を当てた遊べる版）
~/src/fluffos/build-debug/src/driver config.fluffos

# 3. telnet で入る
```

### 経路 B：WebAssembly（静的なサイトに仕立てる）

```bash
# 一度きり：wasm32 向けに ICU をクロスビルドする
tools/wasm/build-deps.sh

# ビルド：native の codegen の道具 + wasm のドライバ + demo の bundle
tools/wasm/build.sh

# 手元で静的なサーバを立てて結果を見る
python3 -m http.server -d build-wasm/dist 8080
# http://localhost:8080/ を開く
```

**自分の mudlib に差し替える**：

```bash
tools/wasm/pack-mudlib.sh --mudlib <mudlib のディレクトリ> --config <config の経路>
# あるいは
MUDLIB=/path/to/lib tools/wasm/build.sh
```

**産物は純粋な静的のディレクトリである**——GitHub Pages でも、どの CDN でも、どの S3 バケットへ置いても、そのまま遊べるゲームになる。**これはまさに第 5 章「静的なページの上に機械を造る」の完全な閉じた輪である。**

### 公開の前に、第 5 章と付録 C に照らす

| 確認の項目 | この事例の状況 |
|---|---|
| COOP/COEP が要るか？ | **要らない**——複数スレッドがない（async のパッケージは閉じている）ので、**そのまま配備できる** |
| `.wasm` の MIME | 静的ホスティングは `application/wasm` を正しく返す必要がある |
| 相対の経路 | プロジェクトのページは下位の経路に置かれるので、`locateFile` の解決に注意 |
| `.nojekyll` | 要る（`_` で始まる資源が食われるのを避ける） |
| Brotli | **強く勧める**——3.6 MB → 0.8 MB |

## 6. ぶつかった壁を、一つずつ本書へ戻す

| 壁 | 現れ方 | 本書の章 |
|---|---|---|
| **詰まるイベントループがない** | `fluffos_tick(now_ms)` に直し、ホストに駆動させる | 第 3 章（システムの壁）、第 5 章 |
| **socket がない** | Transport の抽象 + JS の橋渡し。DNS はスタブで `127.0.0.1` を返す | 第 3、7 章 |
| **スレッドがない** | async のパッケージを丸ごと閉じ、同期の代替を計画中 | 第 3、5 章 |
| **eval limit がない** | **無限の LPC のループがタブ全体を固まらせる**（native は POSIX のタイマに頼るが、Wasm にはまだ代替がない） | 第 3 章（サンドボックスはあなた自身を守らない） |
| **MEMFS は揮発する** | 書き込みはセッションの内でしか有効でない。IDBFS/OPFS の被せ層は roadmap にある | **第 7 章（四段のストレージ）** |
| **タブが背景で止められる** | タイマが止まり、前面へ戻ると gametick が追いつく（**上限は 100 回**） | 第 5 章（ホスト環境の拍子はあなたが決めるのではない） |
| **文字集合の表に対応しない** | アルゴリズム型（UTF-8/16/32、Latin-1、ASCII）のみ支え、表型には対応しない | 第 8 章（体積の大半はデータである） |
| **メモリの上限 2 GB** | 4 GiB ではない——**これはブラウザの現実による遮りである** | 第 8 章 |
| **ブラウザの環境に足りない能力** | 典蔵サイトは一部のゲームを「遊べるがログインに制限あり」と注記している。`query_ip_number()` のような能力が欠けているからだ | 第 3、7 章（能力はホストが手渡すもので、渡せないなら、それは無いということだ） |

> **最後の一行は、とりわけ味わう値打ちがある**：一九九〇年代に書かれた mudlib が、ログインの流れで `query_ip_number()` を呼び、遊ぶ人の IP を記録していた——**ところがブラウザには、それへ渡せる IP という概念がない。** 三十年前に書かれた一行が、今日、移植の行く手を塞ぐ石になっている。
> **これこそ第 12 章の「保守のエントロピー」の最も具体的な姿である：あなたのコードが壊れたのではない。その足もとの世界が入れ替わったのだ。**

## 7. jsbridge：開かれたその双方向の扉

FluffOS の Wasm のビルドは、**WASM の目標にのみ存在する** `jsbridge` の efun を一組そなえ、LPC とページの JavaScript が双方向に呼び合えるようにしている：

```
LPC → JS：  js_eval()、js_call()      → fetch、canvas/WebGL、audio、storage…
JS  → LPC： js_export() + fluffos.callLPC()
```

**このことの意味は見た目より大きい**：一九九〇年代の文字のゲームが、**ゲームのロジックに手を触れないまま、canvas の地図、WebGL の効果、Web Audio の音楽、そしてブラウザ側のストレージを生やせる**ということだからだ——その橋は双方向であり、ゲームの側は efun を一つ余分に呼べばよいだけである。

> これはちょうど第 12 章の四層の地形と響き合う：**Wasm の核（LPC のドライバ）は資産であり、十年動かさないことを設計の目標とする。ページの層（xterm.js、canvas、UI）は消耗品であり、三年ごとに書き直されることを許す。** そして jsbridge が、その「誤りようがないほど狭い境界」である。

## 8. なぜそれが本書の命題の、生きた標本なのか

**ここで技術を置いて、この件のもう一方の面を見よう。**

一つの MUD の**すべてのソースコード**——世界の地図、NPC の台詞、武芸の体系、経済の規則、部屋一つひとつの描写——それがその mudlib である。**それはつねに丸ごとダウンロードできるものだった**：一九九〇年代にはまとめてファイルを送ることで、今日は `git clone` で、そして今ではブラウザの中で直に読み込んで走らせることさえできる。

**秘密のコードは一行もない。**

「コードは資産である」という古い論理に従えば、こんなものに価値があるはずがない。ところが：

- これらのゲームは**三十年生きてきた**。原作者がとうに去ったあとも、繰り返し分岐され、改変され、開き直されてきた。
- **多大な労力をかけてそれらを修復した人々がいる**——符号化を変え、bug を直し、`NOTES.md` に一つひとつの改変を記録し、起動できるかを一本ずつ検証して。
- そして今日、**ドライバをまるごと Wasm へコンパイルした人がいる**。ただ、それらがもう一度開けるようにするために。

**その堀は、はじめからコードの中にはなかった。**

それはあの人たちの側にある——自分が十七歳のとき、ある部屋で三日詰まったことを覚えている人たちの側に。三十年前の壊れた封存ファイルを一つずつ直して戻した人の側に。**これこそ第 12 章の五つの防衛線のうち、最も複製しにくい二つである：データの引力（世界の状態と、あの記憶）と、エコシステム（共同体）**であり、それらはコードが見えるかどうかとまったく関わりがない。

> 💡 座右の一言
> **あるものの原始のコードが三十年にわたって丸ごと複製できたのに、それでもなお取って代わられていないなら、あなたは価値についての清潔な証拠を一つ手にしたことになる。** これらの mudlib はソフトウェアの歴史でも珍しい対照実験である——**秘匿の度合いは零、複製の費用は零、改変の敷居は極めて低い**。理屈のうえでは、もっとよい複製品に埋め尽くされていて当然だった。だが、そうならなかった。利用者が欲しかったのは初めから「動くコード一式」ではなく、「**あの世界と、その世界にいる人たち**」だったからだ。そしてその二つは、`git clone` では持ち去れない。
> これを第 12 章の枠へ置けば、答えは実に澄む：**LLM がコードを書く限界費用を零にしたとき、私たちは実のところ、MUD がずっと置かれてきた境遇へ戻っただけである——コードははじめから値打ちがなく、値打ちがあるのはその周りに生えたものたちだった。** 変わったのはただ一つ、いまやすべてのソフトウェアがこの境遇に向き合わねばならなくなったことだ。
> だから「AI が私の製品を複製するのではないか」と気を揉むより、もっと役に立つ問いを一つ立てるほうがよい：**私のソースコードが明日すべて公開されたとして、三十年後もそれを使っている人はいるだろうか？** これらの mudlib の答えは「いる」だ。**あなたのは？**

> 🔍 踏み込んだ論評──保存の技術的負債と、誰も語らない長期の問題
> この事例はもう一つ、デジタル保存の領域ではますます鋭くなっているのに、ソフトウェア業界がおおむねまだ向き合いはじめていないことを照らし出している。**三十年前の mudlib を修復するとき、難しいのはコードではなく、その足もとにあった、消えてしまった世界のほうである。** リポジトリのあの `NOTES.md` が記録しているものの多くは論理の誤りではなく、こういうことだ——元の符号化は GB2312 だったか BIG5 だったか、当時のドライバにあって今はもう無い efun はどれか、`query_ip_number()` のように「ネットワークがあり、IP があり、オペレーティングシステムがある」を前提した呼び出しをどうするか。**コードそのものはほとんど壊れていない——壊れているのは、それが環境について置いていた前提の一つひとつである。**
> **そしてここにこそ、文化の保存における Wasm の本当の価値があり、仮想機械やエミュレータとの違いがある。** エミュレータ（付録 D 事例 3 の v86）が保存するのは「ハードウェア」であり、コンテナの映像が保存するのは「オペレーティングシステムと依存」である。**ドライバを Wasm へコンパイルして保存されるのは「実行の意味論」である**——一九九六年の Linux を一台まるごと保存する必要はなく、3.6 MB のモジュールと、仕様の安定したホストの境界を一つ保存すればよい。**ゆえに Wasm は思いがけず、いま最良のソフトウェアの保存形式の一つになった**：仕様が公開され、独立した実装が複数あり、後方互換の約束が極めて強く、しかもホスト環境（ブラウザ）そのものが、人類が最も真面目に保守している互換性の層である。
> 裏返せば、これはいまコードを書いているすべての人へ、かなり居心地の悪い注意を与える：**あなたが今日書き下ろす、環境についてのあらゆる前提——この API はあるだろう、このサービスはあるだろう、この形式は支えられているだろう——は、三十年後の誰かへ出す試験問題である。** そして第 12 章のあの「三年後にこれが真夜中に壊れたとき誰が直すのか」という問いは、ここでその最終形をとる：**三十年後、あなたがなぜそう書いたのかを、まだ読み解ける人がいるだろうか？** あの `NOTES.md` こそが、その問いへの唯一有効な答えである。

## 9. 図鑑へ戻す：それは誰の代わりになったか

| 付録 E の 🔴 の構想 | 現実の対照 | どこが違うか |
|---|---|---|
| 事例 58 Minestom-Wasm（ブラウザ内のゲームサーバ） | **FluffOS × Wasm** | FluffOS は本物であり、しかもより硬い——実行時に利用者のコードまでコンパイルする |
| 事例 60 Micro-Apache-Wasm（ブラウザ内のサーバのエンジン） | **FluffOS × Wasm** | Micro-Apache は状態のない要求しか扱わない。FluffOS には心拍とタイマと持続する世界の状態がある |
| 事例 92 OpenLISP-Wasm（記号計算のインタプリタ） | **FluffOS の LPC コンパイラ + VM** | 同じ形である：**ある言語の完全な実行環境を Wasm へ移す** |
| 事例 34 QuickJS-Wasm（JS inside JS） | **FluffOS の LPC inside Wasm** | 同じ形だが、FluffOS はゲームの実行環境を一式、余分に連れている |

**付録 D〜F のあの図鑑が「この道は通じるか」の地図だとすれば、この一篇は、その道の果てに本当に人が住んでいる場所である。**
