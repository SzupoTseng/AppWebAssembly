## III. フォント、映像音声の符号化、圧縮

### 36.（元 45）Web-Graphite (Graphite2-Wasm) — 少数民族言語のスマート組版　🟡

**痛点**：世界には多くの特殊な文字（ビルマ文字、クメール文字、北米先住民の文字、そして複雑な文脈依存の変形規則を持つ非ラテン書体）があり、**Graphite 組版システム**——OpenType より柔軟で、規則記述言語を書けるスマートフォント技術——を使っている。Firefox は Graphite を標準で内蔵するが、**Chrome と Safari はまったく非対応**であり、少数民族の文化を扱うページはブラウザによって文字が完全に崩れる。

**原理**：C++ の Graphite2 スマートフォント組版の中核を Wasm へコンパイルし、静的な環境で全ブラウザ互換の組版を提供する。JS が複雑な Unicode の文字と Graphite 対応の `.ttf` を Wasm のメモリへ渡す。Wasm 内部の Graphite2 エンジンがフォントに埋め込まれた複雑な状態機械の規則を実行し、グリフの連結を動的に再構成し、文字の重なりの座標とベースラインのオフセットを調整する。計算後に正確なグリフ輪郭の添字とピクセルの幾何行列を出力し、フロントエンドが Canvas API でピクセル単位に描画して、ブラウザ標準の組版エンジンの欠陥を迂回する。

**性能**：数万字を含むクメール語の文献一篇の組版で、全文のシェーピングと境界の計算が **10〜15 ミリ秒**で完了し、純粋な JS の模倣より **35 倍以上速い**と主張されている。

**長所**：完璧な文化保護の技術であり、Chrome/Safari が Graphite スマートフォントを正しく描画できないという歴史的な痛点を根本から解決する。静的ホスティングだけで世界の少数民族の文献の展示サイトを作れる。
**短所**：高度に専門的な垂直ツールであり、組版のデバッグとフォント埋め込みの規則を理解するコストが極めて高い。

**競合**：ネイティブの OpenType / HarfBuzz（ウェブ組版の主流標準だが、極度に柔軟な文脈規則を要する特殊な歴史文献の書体では、表現力が Graphite に及ばない）。

### 37.（元 46）Web-libvpx / dav1d-wasm — 新世代の映像デコードエンジン　🟡

**痛点**：現代のウェブは VP9、AV1 などの高品質な圧縮形式に強く依存するが、多くの古いオペレーティングシステム、モバイル端末、特定のブラウザは**これらの形式のデコーダをハードウェア層に内蔵していない**。JS で AV1 の複雑なビットストリームを直接解析しピクセルの予測を計算すれば速度は異様に遅く、深刻なコマ落ちやメインスレッドの固まりを招く。

**原理**：Google のオープンソースのコーデックの中核 **libvpx**（あるいは AV1 の **dav1d**。C とアセンブリで書かれている）を Emscripten で Wasm へコンパイルし、ブラウザの MSE（Media Source Extensions）の予備のデコードエンジンとする。**マルチスレッドのピクセルデコード**：Web Worker + `SharedArrayBuffer` でデコードのタスク（フレーム内予測、逆離散コサイン変換 IDCT）をブロックに切って並列に計算する。**SIMD のベクトル最適化**：一つの CPU 命令で 4 つか 8 つのピクセル群のデブロッキングフィルタ演算を同時に処理し、デコード後の YUV の生ピクセルをそのままメモリへ書く。

**性能**：SIMD とマルチスレッドを有効にすると、ハードウェア加速がまったくない低性能なコンピュータでも 1080p の VP9/AV1 を **30〜45 FPS** でソフトウェアデコードでき、ネイティブ C の **70%** に達すると主張されている。

**長所**：静的な映像プラットフォームに「クロスブラウザ、100% 形式互換」の再生能力を与え、ホストのハードウェアチップに縛られない。完全にオフラインで使える。
**短所**：ソフトウェアデコードは CPU を大きく食い、1080p を長時間ソフトウェアデコードすれば端末が大きく発熱し、消費電力もハードウェアデコードより顕著に高い。

**競合**：ネイティブの `<video>`（性能は最高で消費電力も極めて少ないが、端末が対応しない AV1 や特定のコーデックでは黒画面かエラーになる）。

### 38.（元 47）Hjson-Wasm — 人にやさしい設定ファイル構文の変換　🟡

**痛点**：標準の JSON の構文は厳格である（コメントを書けず、文字列は二重引用符が必須で、末尾にコンマを置けない）ため人にきわめて不親切であり、コミュニティは **Hjson（Human JSON）** を出した。静的ページで Hjson をリアルタイムに標準 JSON へ変えるとき、純粋な JS のパーサは数万行の巨大な設定（複雑なゲームのステージデータ、企業のアーキテクチャ定義）に対して、頻繁な文字列の切り出しと GC でエディタの入力の遅延を招く。

**原理**：Rust（あるいは C）で書かれた `hjson` の中核を Wasm へコンパイルする。**ゼロコピーの字句走査**：ユーザが入力した Hjson のテキストを JS がメモリのポインタで渡し、Wasm 内部の Rust のパーサは**中間の文字列オブジェクトを一切生成せず**、ポインタのオフセットで生のバイト列の上を直接字句解析する。**AST のメモリプール**：線形メモリ内に高度に緊密な構文木を作り、コメントと空白をすべて取り除いたあと標準の JSON 文字列を直接整形して出力する。

**性能**：10 MB で階層とコメントを多く含む巨大な Hjson の変換に **8〜12 ミリ秒**しかかからず、純粋な JS 版より **20 倍以上速く**、メインスレッドの GC 停止は完全にゼロになると主張されている。

**長所**：フロントエンドのエディタ（Monaco Editor のプラグインなど）に、遅延のないリアルタイムの設定構文の検証と変換をもたらす。
**短所**：比較的垂直な構文ツールであり、**設定ファイル自体が数 KB しかないなら、Wasm の初回ロードのオーバーヘッドがもたらす性能の利得を上回る**（これは第 3 章の「性能の優位には計算量の閾値がある」の典型的な反例である）。

**競合**：純粋な JS の Hjson パーサ（書き方が柔軟で統合も容易だが、大規模に自動生成された設定や膨大なデータの洗浄ではメモリと CPU のピークが指数的に跳ね上がる）。

### 39.（元 48）Web-Proj (PROJ-Wasm) — 地図投影と地理座標の変換　🟡

**痛点**：GIS の開発では、全球の地理座標（WGS84 の緯度経度）を特定の国の工学的な投影座標（台湾の TWD97 二度分帯など）へ変えるのに、複雑な測地学と高度な球面三角の演算が要り、たいてい C/C++ の権威あるライブラリ **PROJ** に頼る。以前は静的ページで膨大な GIS の点群や地籍図を扱うにはバックエンドの地理サーバ（GeoServer）へ送り返すしかなく、さもなければ純粋な JS の座標変換では精度が足りず遅かった。

**原理**：PROJ を丸ごと Wasm へコンパイルし、非中央集権の座標の精密変換の作業台を提供する。**高精度の浮動小数点行列**：内部に連続した `f64` のメモリを確保し、数百万の点の座標（X, Y, Z）を `TypedArray` で直接書き込む。**基準面の動的変換**：Wasm 内部で複雑な三次元アフィン変換、モロデンスキーモデル、グリッドの歪み補正を実行し、すべてバイナリのレベルで操作する。

**性能**：100 万点を含む地理データセットの処理で、全量の座標系の投影変換が **40 ミリ秒**以内に完了し、純粋な JS の地理ライブラリより **25 倍以上速い**と主張されている。

**長所**：静的な地図解析ツールに、デスクトップ級の GIS（QGIS）と同等の精度と効率をもたらす。政府の地籍や商用の点群データが決して端末を出ない。
**短所**：PROJ は巨大な測地グリッドのデータベース（grid files。特定の地域の重力の歪みを補正するためのもの）に依存し、これらのファイルはやや大きく、フロントエンドが Range Request で動的にダウンロードせねばならない。

**競合**：proj4js（軽量で通常のウェブ地図の表示には向くが、数百万規模の点群や全球の高精度グリッド補正を要する産業級の製図では、性能も精度もまったく比較にならない）。

### 40.（元 49）Brotli-Wasm — 極限の圧縮率を持つ Brotli の符号復号　🟢

**痛点**：Brotli は Google が開発した現代的な可逆圧縮アルゴリズムで、圧縮率は Gzip を大きく上回る。ブラウザは **HTTP 転送層**では Brotli の解凍をネイティブに対応しているが、**フロントエンドの JavaScript にネイティブの Brotli API を公開していない**。つまりページ内でユーザのデータを極小のファイルへ圧縮して IndexedDB へ入れたり、独自の `.br` ファイルを手で解凍したりしたくても、純粋な JS ではブラウザ内蔵のエンジンを呼べない。

**原理**：Google 公式の C 言語の Brotli 符号復号の中核を Wasm へコンパイルし、低水準の圧縮 API をフロントエンドへ直接開放する。**スライディングウィンドウのメモリ最適化**：Brotli は文脈のモデリングのために巨大なスライディングウィンドウ（最大 16 MB）へ強く依存する。Wasm は線形メモリ内にこの連続した空間を直接確保し、高速なハフマン符号化とバイナリのバイト列の照合を実行する。**オブジェクトを作らないストリーミング圧縮**：データをバイナリのバイトブロックとしてストリームで渡し、Wasm が圧縮し終えたら `Uint8Array` を直接吐き出す。全過程で JS のゴミオブジェクトを生成しない。

**性能**：20 MB のプレーンテキストや JSON の圧縮・解凍でネイティブ C の **85%** に達し、**30〜50 ミリ秒**しかかからず、純粋な JS の Brotli 模倣ライブラリより **15 倍近く速い**と主張されている。

**長所**：ブラウザの API の封鎖を突破し、静的なアプリケーションにブラウザ内部で最高水準の可逆圧縮を行う能力を与える。PWA のオフラインキャッシュの容量の最適化にきわめて向く。
**短所**：Brotli の最高圧縮レベル（Quality 11）は計算が極度に複雑であり、フロントエンドで闇雲に最高レベルを使えばメインスレッドが一瞬固まるので、**たいてい Web Worker の中で実行せねばならない**。

**競合**：純粋な JS の Brotli 実装（効率的なビット演算と緊密なメモリの利点を欠き、大きなファイルの圧縮で CPU のピークが高すぎる）。

### 41.（元 50）libFLAC-Wasm — 高忠実度の可逆音声のリアルタイム符号化　🟡

**痛点**：ユーザがウェブでマイク録音するとき（オンラインのポッドキャストツール、音楽制作のサンドボックス）、ブラウザは標準では非可逆の Opus/WebM か、まったく未圧縮で巨大な WAV しか対応しない。純粋なフロントエンドで音を世界の主流の可逆形式 **FLAC** へ保存しようとしても、純粋な JS のアルゴリズムでは録音しながら密な線形予測符号化（LPC）とハフマンの残差符号化をリアルタイムに計算できず、深刻なフレーム落ちと途切れを招く。

**原理**：公式の C 言語の **libFLAC** の中核を Wasm へコンパイルし、**AudioWorklet**（高優先度の音声スレッド）と深く統合する。**リアルタイムのストリーミング音声スタック**：マイクが捕らえた生の PCM データを AudioWorklet 内の JS が遅延なく Wasm のメモリのポインタへ書く。**密な数学の予算**：Wasm 内の libFLAC の符号化器がただちに格子解析、チャネル間の相関（ミッドサイドカップリング）の計算、残差の圧縮を実行し、マイクロ秒で FLAC のビットストリームへ圧縮する。

**性能**：Wasm の音声スレッドでの符号化時間が **0.1 ミリ秒未満**で、**CPU の 1% 未満**しか使わず、録音しながら 24 bit/96 kHz の高忠実度 FLAC を生成できると主張されている。

**長所**：静的な録音・音楽のプラットフォームに、放送級の可逆音声を収録する能力をもたらす。バックエンドの音声処理サーバをまったく要さない。
**短所**：FLAC の符号化はメモリの安定性への要求が極めて高く、線形メモリの精密な設定が要る。入力のチャネル数やサンプリングレートが急変してグルーが適切に処理しなければ、容易にメモリの破壊を招く。

**競合**：純粋な JS の FLAC 符号化器（不定期な GC の停止に妨げられ、ページにアニメーションやクリックがあると計算が間に合わず、録れた音声に深刻な途切れと音割れが出る）。

## IV. グラフ代数、文書変換、リバースエンジニアリング

### 42.（元 51）Web-Biconical — 大規模グラフの二重連結成分の平面化レイアウト　🔴

**痛点**：ネットワークセキュリティ（攻撃経路の追跡）、バイオインフォマティクス（タンパク質相互作用ネットワーク）、ブロックチェーンの取引の追跡において、エンジニアはしばしば数万のノードと複雑な循環構造を含む「巨大グラフ」の平面化レイアウトを行う必要がある。純粋な JS のグラフライブラリ（Cytoscape.js）は二重連結成分、強連結成分、重心のバネモデルの計算で密なポインタの飛び回りと配列のアドレス指定を要し、深刻な動的メモリ確保と GC を招き、ページを凍らせるかメモリを使い切ってクラッシュさせる。

**原理**：学術界の C++ の高性能グラフアルゴリズムの中核を Wasm へコンパイルする。**メモリ連続のグラフ配置**：線形メモリ内で、グラフのノードと辺はもはや JS オブジェクトとして離散して保存されず、キャッシュに優しい連続配列（**CSR、Compressed Sparse Row** 形式など）へ圧縮され、L1/L2 のヒット率を限界まで高める。**並列の位相分割統治**：マルチスレッドで巨大グラフを複数の独立した二重連結部分グラフへ分解し、異なる Worker が同期して交差最小化の計算を行う。

**性能**：50,000 ノードと 150,000 辺の超大型の攻撃連鎖の位相図の処理で、レイアウトが **180〜250 ミリ秒**で完了し、純粋な JS で最速のグラフアルゴリズムより **40 倍以上速い**と主張されている。

**長所**：静的なダッシュボードで百万規模の大規模データのグラフを直接探索できる。政府や大企業のネットワーク位相のデータが外へ漏れない。
**短所**：メモリの配置が極度に抽象的かつ低水準であり、**フロントエンドが個別のノードを頻繁に動的に追加・削除する必要があるなら、メモリの再整列の代価が高い**——したがって一度きりの分析や大きなバッチ更新の場面により向く。

**競合**：d3-force / vis.js（1000 ノード以内の小さな対話的グラフには向くが、数万ノードの産業級の位相を扱うとページがそのまま固まる）。

### 43.（元 52）pulldown-cmark-wasm — 百万字級の Markdown 解析　🟢

**痛点**：現代の技術ドキュメントのプラットフォームは極端に長い Markdown をリアルタイムに描画せねばならない。純粋な JS のパーサ（markdown-it、marked）は人気があるが、ユーザが数万字で入れ子の表、コードブロック、数式を大量に含む「百万字の仕様書」を貼り付けると、正規表現の照合と頻繁な文字列のスライスが CPU を振り切らせ、入力を引っかからせる。

**原理**：Rust で書かれた産業級の Markdown 解析の中核 **pulldown-cmark** を Wasm へコンパイルする。**ストリーミングのイベント解析**：Wasm 内部は重い AST のオブジェクトツリーを捨て、プル型のイベントストリームを採る——生のバイト列を読み込むとき線形メモリ内でポインタを進めるだけで、トークンのイベントを動的に吐き出す。**ゼロコピーの HTML 生成**：解析の過程で中間の JS 文字列オブジェクトを一切生成せず、Wasm が Markdown を直接 HTML のバイナリのバイト配列へ変換し、最後に一度だけ大きな文字列へ変えて DOM へ注入する。

**性能**：100 万字の技術マニュアル一冊の解析に **15〜25 ミリ秒**しかかからず、純粋な JS 版より **25〜35 倍速く**、遅延のないリアルタイムの同期プレビューを実現すると主張されている。

**長所**：静的な技術ドキュメントサイトに遅延のないリアルタイムの変換と検索の体験をもたらし、極限の量のテキストファイルにも余裕で対処する。
**短所**：コンパイル済みのバイナリモジュールであるため、開発者が Markdown へ非標準の構文拡張プラグインを動的に加えたい場合、拡張の難度が純粋な JS のパーサより高い。

**競合**：純粋な JS の Markdown パーサ（エコシステムが豊かでプラグインもすぐ手に入るが、数万行を超える巨大な文献を扱うと明らかな性能のボトルネックがある）。

### 44.（元 53）Zstd-Wasm — 大規模データの高速な圧縮と解凍　🟢

**痛点**：Zstandard（Zstd）は Facebook が開発したリアルタイムの可逆圧縮アルゴリズムであり、Gzip と同等かそれ以上の圧縮率を提供しながら驚異的な解凍速度を持ち、バックエンドと大規模データの領域（Hadoop、Kafka、Parquet）の標準装備となった。しかし**ブラウザはいまだに Zstd のフロントエンド API をネイティブに公開していない**。フロントエンドが静的サイトから数百 MB の構造化された大規模データ、テレメトリのログ、ゲームの 3D アセットをダウンロードして解凍する必要があるとき、JS で模倣した Zstd ではこのアルゴリズムの物理的な限界をまったく引き出せない。

**原理**：Facebook 公式の C 言語の Zstd の符号復号の中核を丸ごと Wasm へコンパイルする。**有限状態エントロピー（FSE）の復号**：Zstd の中核は Jarek Duda の有限状態エントロピー符号化に基づいており、Wasm は線形メモリ内で極度に密なビットシフトと表引きを直接実行する。**ストリーミングのブロック処理**：ユーザが大きな `.zst` をドロップするかフロントエンドがダウンロードすると、JS が Streams API でデータをブロックに切って渡し、Wasm が数マイクロ秒で解凍して `Uint8Array` を吐き出す。全過程で JS のゴミオブジェクトを生成しない。

**性能**：100 MB の Zstd のログファイルの解凍で **毎秒 400〜600 MB** に達し、ネイティブ C の **85%** に近く、純粋な JS の従来の解凍ライブラリより **20 倍以上速い**と主張されている。

**長所**：ブラウザのプロトコルの制約を突破し、静的ホスティングの大規模データのダッシュボードが極めて高い圧縮率で大きなファイルを転送し、フロントエンドで瞬時に解凍できるようにする。ダウンロードの待ち時間とサーバの帯域を大きく節約する。
**短所**：Zstd が高強度の圧縮モードを使うときは辞書のバッファとしてやや大きな線形メモリが要るので、アーキテクチャ上は仮想機械のメモリ上限を精密に制限せねばならない。

**競合**：pako / zlib.js（古い DEFLATE/Gzip しか対応せず、圧縮率でも解凍スループットでも全方位に凌駕される）。

**痛点**：音声エンジニアと音声 AI の開発者がフロントエンドで音声を扱うとき、専門的で珍しい形式（`.wav`、`.aiff`、`.flac`、`.ogg`、`.voc`、`.sf`）を読む必要がしばしば生じる。ブラウザの Web Audio API は標準ではごく少数の民生向け形式（MP3、AAC）しか対応しない。ウェブで専門的な音声のトラックチャネル、量子化ビットレート、生の PCM サンプルを分析・編集・抽出しようにも、純粋な JS のパーサは極度に乏しく、大きなファイルの解析で容易に OOM を起こす。

**性能**：200 MB の産業級の可逆マルチトラック WAV を解析して全サンプルを抽出するのに **15 ミリ秒**を超えず、メモリ使用も極めて低いと主張されている。

**長所**：静的なプラットフォームに数十の専門的な音声形式の深い解析と直接制御の再生能力をもたらす。音楽制作者の未発表のマスタが決して端末を出ない。
**短所**：libsndfile は極限の性能を追うため、例外処理と壊れたファイルへの防御がコンパイル時の境界検査に強く依存する。悪意を持って作られた音声ファイルに当たったとき、仮想機械が落ちるのを防ぐ必要がある。

**競合**：ネイティブの `decodeAudioData`（性能はよいが対応形式が非常に狭く、AIFF や VOC などの専門形式をまったく読めない）。バックエンドの SoX/FFmpeg（強力だがサーバコストと長いアップロードがある）。

### 46.（元 55）libxslt-Wasm — XML の XSLT スタイルシート変換エンジン　🟡

**性能**：数万ノードを含む医療の XML データセットの高度な XSLT 変換で、全量の変換が **8〜12 ミリ秒**で完了し、ネイティブ C の **80%** に達し、純粋な JS の模倣より **30 倍以上速い**と主張されている。

**長所**：現代のブラウザの XSLT 2.0/3.0 への対応が欠けているという痛点を完璧に解決し、企業が既存の XML/XSLT のアーキテクチャを変えずに純粋なフロントエンドへ移れるようにする。サーバコストはゼロ。
**短所**：XML の解析は大きなコードベースであり、コンパイルされた Wasm は圧縮後で約 **2〜3 MB** ある。しかも API が低水準寄りで、文字列とバッファを繋ぐグルーの層が要る。

**競合**：ネイティブの `XSLTProcessor`（ダウンロード不要でサイズの負担もないが、**XSLT 2.0 以降の高度な構文にまったく非対応**であり、機能が大きく乖離している）。バックエンドの Saxon サービス（機能は最も揃っているが、サーバコスト、ネットワークの遅延、プライバシーの危険がある）。

### 47.（元 56）VLC.wasm (libvlc) — 万能のマルチメディア再生とストリーミング復号の中核　🟡

**痛点**：ブラウザ内蔵の `<video>` は形式への対応が厳しい（たいてい MP4、WebM、Ogg のみ）。ユーザが `.mkv`（複数の字幕トラックを含む）、`.avi`、`.flv`、あるいは専門的な RTSP/RTMP のリアルタイム監視ストリームを再生しようとすると、ブラウザは端的に拒否する。従来の解法はバックエンドに高価なリアルタイムのトランスコードサーバを立てること（MKV を HLS へ変える）であり、数万のユーザが同時に接続すればコストが破滅的に跳ね上がる。

**原理**：数百万行の C 言語の **VLC (libvlc)** の中核を Emscripten で丸ごと Wasm へコンパイルする。**ソフトウェア復号のネットワークスタック**：ユーザが動画をドロップするかストリームの URL を入力すると、JS が WebSocket か fetch でバイナリのブロックを取り、**ブラウザのマルチメディアのパーサを飛ばして**、直接 Wasm の MEMFS へ書く。Wasm 内部のデマルチプレクサとデコーダがサンドボックス内で映像と音声のビットストリームをソフトウェア復号する。**YUV から RGB へのハードウェア直通**：復号された YUV420p の生ピクセルは JS の変換を経ず、メモリのポインタを直接公開し、JS が WebGL/WebGPU のシェーダで GPU 内の色空間変換と描画を行う。

**性能**：SIMD とマルチスレッドを有効にすると、ハードウェア加速のない環境でも 1080p/30 FPS の MKV や H.264 を滑らかにソフトウェア復号でき、再生の遅延は **30 ミリ秒**未満で、ネイティブの VLC の **70%〜75%** に達すると主張されている。

**長所**：静的サイトに真に「万能な形式互換」の再生能力をもたらす。バックエンドコストはゼロで、動画は端末を出ない。
**短所**：密なソフトウェア復号は CPU の負荷が極めて大きく、低性能なスマートフォンやタブレットで高解像度の動画を再生すれば顕著に発熱し電池を食う。

**競合**：hls.js / flv.js（フロントエンドで人気のストリーミングライブラリだが、本質的にはリマルチプレクスをするだけであり、**下層では依然としてブラウザ内蔵の対応する復号チップに強く依存している**）。

### 48.（元 57）SuiteSparse:GraphBLAS-Wasm — 疎行列によるグラフ代数の超計算　🟡

**痛点**：大規模データの分析、ソーシャルネットワークの発掘（数億の人間関係の PageRank）、金融のリスク管理では、グラフはたいてい膨大な「疎行列」へ変換されて代数演算にかけられ、産業級の C 言語の権威あるライブラリ **SuiteSparse:GraphBLAS** に頼る。フロントエンドで JS の配列にこの高度に疎な（99% がゼロの）巨大行列の積を手書きすると、オブジェクトの確保の仕組みが大量のメモリの断片を生み、しかもバイナリのポインタの飛び回りの最適化を欠くため、ブラウザが数十秒にわたり無応答になる。

**原理**：SuiteSparse:GraphBLAS の中核を丸ごと Wasm へコンパイルする。**圧縮疎列の配置**：行列を線形メモリ内で **CSC（Compressed Sparse Column）** のバイナリ形式に厳密に並べ、ゼロ要素を一切保存せず、キャッシュヒット率を最大化し JS のオブジェクト生成を完全に迂回する。**半環代数の演算**：あらゆるグラフの位相の走査と最短経路の計算を、Wasm 内部のビットマスクとバイナリの高速な積和演算へ変換し、複数の Worker が線形メモリを並列に走査する。

**性能**：100,000 ノードと 2,000,000 辺の巨大なソーシャルグラフの PageRank の反復が **80〜120 ミリ秒**で完了し、純粋な JS のグラフ行列ライブラリより **50 倍以上速い**と主張されている。

**長所**：無料の静的なダッシュボードに、百万規模の大きなネットワークのグラフへ硬派なグラフ代数を行う能力を与える。100% データの機密が保たれる。
**短所**：GraphBLAS の API は極度に学究的かつ高度に抽象的であり、フロントエンドの開発者が直感的にノードを追加削除できないので、厚いデータ変換のグルー層を書かねばならない。

**競合**：math.js（通常の密行列の代数には向くが、数万次を超え膨大なゼロ要素を持つ産業級の疎行列のグラフ計算では数桁遅れる）。

### 49.（元 58）HTML Tidy-Wasm — 汚れた HTML/XML の産業級の洗浄と修復　🟡

**痛点**：ウェブのクローラ、オンラインの HTML エディタ、コードレビューのツールでは、フロントエンドがしばしば構文が欠け、タグが閉じておらず、属性が乱れた「汚れた HTML/XML」を受け取る。純粋な JS の正規表現の照合は精度が極めて低く、しかも数百万行の巨大なページのソースを扱うと文字列のスライスと DOM ツリーの再構築が CPU を振り切らせる。

**長所**：静的なオンラインのコードサンドボックスに遅延のないリアルタイムの構文洗浄と自動修復をもたらす。バックエンドコストはゼロ。
**短所**：比較的垂直なツールであり、**コード量が極めて小さいときは、Wasm モジュール自体のロード時間が性能の優位を打ち消す**。

**競合**：htmlparser2（互換性がよくエコシステムも成熟しているが、数十万行を超える企業級のページデータの洗浄では明らかな性能のボトルネックがある）。

### 50.（元 59）Web-Fontfuzz — フォントファイルのセキュリティのファジング　🔴

**痛点**：フォントファイル（`.ttf`、`.otf`、`.woff2`）は構造が複雑で、微小なハードウェア命令（TrueType バイトコードのインタプリタ）を含む。歴史上、オペレーティングシステムとブラウザの重大なリモートコード実行（RCE）の脆弱性の多くが、悪意を持って作られたフォントの解析に由来した。セキュリティの研究者がフォントのファジングをするには、ローカルに複雑な Linux の環境とクラスタを組まねばならない。ウェブでいつでも開ける検査プラットフォームを作ろうにも、従来のフロントエンドの技術ではバイナリのフォントの内部のテーブル構造に高頻度のランダムな変異とクラッシュの分析をまったく行えない。

**原理**：Rust/C++ のフォントのセキュリティのファジングの中核（libFuzzer ベースのフォント解析の演算子など）を Wasm へコンパイルし、静的な環境へ配備する。**変異の状態機械**：ユーザがフォントをドロップすると、Wasm が線形メモリ内でそのバイナリ構造（`glyf`、`loca` のテーブル）に毎秒数万回のランダムなビット反転と構造の改竄を行う。**サンドボックスのメモリ隔離**：変異した悪意あるフォントを Wasm 内部の仮想パーサへ直接渡す。メモリの境界越えを引き起こしても、**Wasm のサンドボックスがその RuntimeError を精確に捕らえ、ユーザの本物のオペレーティングシステムとブラウザの安全へは絶対に波及しない**（これこそ第 2 章の「サンドボックスが守るのはホストである」の前向きな応用である）。

**性能**：シングルスレッドで毎秒 **5,000〜8,000 回**のフォント構造の変異と深い解析のテストを実行でき、ネイティブの C++ の中核の **80%** に達すると主張されている。

**長所**：セキュリティのエンジニアに 100% 隔離され非中央集権のウェブ版フォント脆弱性診断ツールを提供する。
**短所**：ウェブ環境の制約により、Wasm の仮想機械がクラッシュしてもローカルの Linux のように完全なコアダンプを直接書き出せず、精密なグルーでメモリのログをリアルタイムに書き出す必要がある。

**競合**：ローカルの AFL++ / libFuzzer（計算力に上限がなくデバッグも最も充実しているが、インストールが煩雑で、ウェブのようにいつでも開ける手軽さがない）。

### 51.（元 60）Web-Gidra（Ghidra の逆コンパイル中核）— バイナリのリバースエンジニアリング　🔴

**痛点**：リバースエンジニアがマルウェアやバイナリの実行ファイル（x86/ARM の `.exe`、`.bin`）を分析するとき、機械語を読める高水準の C へ逆コンパイルする必要がある。中核は極めて巨大な逆コンパイルの意味論エンジン（NSA がオープンソース化した Ghidra など）である。以前はウェブで高速なバイナリ分析の Playground を提供するには、悪意あるバイナリをバックエンドへアップロードするしかなかった——これは極めて大きなセキュリティの懸念を生み（マルウェアがバックエンドを汚染しうる）、しかも制御フローグラフ（CFG）の構築の CPU コストも高い。

**原理**：Ghidra の C++ の中核の逆コンパイルエンジン（Sleigh のデコーダと定数伝播のオプティマイザ）を Wasm へコンパイルし、オンラインのリバースエンジニアリングの演習場を作る。**中間言語（P-code）の変換ツリー**：ユーザがバイナリの実行ファイルをドロップすると、Wasm 内部のデコーダが機械語を高速に読み、アーキテクチャ非依存の中間表現（P-code）へ変換し、線形メモリ内に高度に緊密な制御フローグラフを構築する。**構造化された意味論の再構成**：内部のオプティマイザが死コードの削除と変数の型推論を行い、線形メモリ内で逆コンパイルされた C 言語の文字列を直接組み立てる。

**性能**：約 2 MB の x86 のライブラリの逆コンパイルに **200〜400 ミリ秒**しかかからず、高品質な C のコードを生成でき、ローカルのデスクトップ版 Ghidra の **75%** に達すると主張されている。

**長所**：**100% 絶対的な安全の隔離**——悪意あるバイナリは Wasm の密閉されたサンドボックス内で完全に逆コンパイルされ、ローカルのシステムに感染できない。静的サイトの運営コストはゼロ。
**短所**：Ghidra の C++ の逆コンパイルの中核は巨大であり、コンパイルされた Wasm は圧縮後でも **5〜8 MB** あり、初回のロードに時間がかかる。

**競合**：純粋な JS のバイナリのパーサ（たいてい十六進の閲覧か単純な逆アセンブルしかできず、複雑な制御フローの最適化と意味論の再構成を要する逆コンパイルにはまったく手も足も出ない）。

> **注目に値する自己言及**：この事例は第 9 章と面白い閉じた輪を作る——**Wasm で逆コンパイラを走らせ、他人の Wasm を分析する。** 実際、Ghidra のコミュニティには `.wasm` を分析対象にできる Wasm のローダプラグインがあり、WABT の `wasm-decompile` も C 風の疑似コードを出力する。**逆解析のツールと逆解析の対象が同じサンドボックスで動く——この事実自体が、「バイナリは不可逆である」が成り立たない主張であることを示している。**

### 52.（元 71）Circom-Witness-Wasm — フロントエンドのゼロ知識証明の生成　🟢

**痛点**：ゼロ知識証明（ZKP）は、パスワードや身元を漏らさずに権限を持つことをサーバへ証明させる（プライバシー投票、zk-Rollups）。しかし ZK の証明の生成には巨大な算術回路の構築と、極度に密な暗号の多項式（MSM と NTT）の計算が要る。ウェブの DApp にすると、純粋な JS のライブラリは数万の回路ゲートの処理で性能が低すぎ、ブラウザに「ページが応答しません」を出させる。

**原理**：ZK 回路のコンパイラ `circom` が生成する証人（witness）の計算コードを、そのまま Wasm モジュールへコンパイルして静的な環境にホストする。**大きな体の演算の最適化**：ZKP は特定の有限体（BN254 楕円曲線など）上の巨大整数の演算を伴い、Wasm は `i64` 命令でサンドボックス内に連続したメモリプールを確保し、極度に最適化された剰余乗算と剰余加算を実行する。**ゼロコピーの証明の流れ**：JS がプライベートな入力を `TypedArray` で Wasm のメモリへ直接渡し、Wasm がサンドボックス内で数千の制約を高速に解いてバイナリの証人ファイルを生成する。

**性能**：50,000 ゲートを含むプライバシーの身元回路の証明の生成に、フロントエンドで **300〜500 ミリ秒**しかかからず、初期の純粋な JS 版（snarkjs の JS モード）より **25 倍以上速い**と主張されている。

**長所**：ユーザの本物のパスワードとプライベートな入力が **100% 端末を出ない**。暗号の最高の安全原則に適合し、バックエンドの運用コストを完全になくす。
**短所**：**回路の規模が極度に巨大な場合（数百万ゲートを含む zk-EVM の証明など）、Wasm は 4 GB の線形メモリの上限を超えて実行できず**、バックエンドの計算力の支援が要る（第 8 章の天井のもう一つの具体例である）。

**競合**：純粋な JS の暗号計算（独自の有限体と多倍長演算への低水準の命令の最適化を欠き、大規模な回路の求解でそのまま固まる）。

### 53.（元 72）Qiskit-Wasm — 量子計算の状態ベクトルのシミュレーション　🟡

**痛点**：量子計算の研究者と学生が量子アルゴリズム（Shor、Grover）を設計するとき、量子ビットの重ね合わせと絡み合いをシミュレートする必要がある。IBM の Qiskit がこの領域の覇者だが、中核は C++/Python で書かれている。ウェブで対話的な量子プログラミングの教育プラットフォームを提供するには、回路をバックエンドへ送って順番待ちさせるしかなく、多数の学生が同時に実行すればバックエンドの行列積の計算力が瞬時に飲み込まれる。

**原理**：軽量な量子シミュレーションの中核（C++/Rust の状態ベクトル計算器）を Wasm へコンパイルし、静的ページへ配備する。**複素行列のテンソル積**：量子ビットのシミュレーションは本質的に密な複素ベクトルとクロネッカー積の演算であり、Wasm は線形メモリ内に緊密な `f64` の実部と虚部の配列を構築する。**確率振幅のストリーミング標本抽出**：ユーザが量子測定を実行すると、Wasm 内部のモンテカルロの状態機械がメモリ上で高速に標本を抽出し、統計のヒストグラムを JSON で返して Canvas に描かせる。

**性能**：16 量子ビットの任意の論理ゲート（Hadamard、CNOT など）の複合回路のシミュレーションで、全量の状態ベクトルの発展が **10〜20 ミリ秒**で完了し、ネイティブ C++ の **80%** に達すると主張されている。

**長所**：量子計算の教育プラットフォームに、バックエンドの遅延がまったくないリアルタイムのシミュレーション体験をもたらし、学術機関が計算サーバを立てる費用を大きく下げる。
**短所**：**量子状態ベクトルの次元は量子ビット数に対して指数的に爆発する（2ⁿ）**。つまりフロントエンドは最大でも約 **20〜24 量子ビット**にしか対処できず、それを超えれば OOM でクラッシュする。**これは 4 GB 上限の最も清潔な現れである：24 量子ビットの複素状態ベクトルはちょうど数百 MB から数 GB の桁に迫る。**

**競合**：純粋な JS の複素行列の計算（メモリの連続整列を保証できず、大規模な行列積で L1/L2 のキャッシュミスが頻発し、15 倍以上遅い）。

### 54.（元 73）libp2p-Wasm — 分散 P2P ネットワークの多重化プロトコルスタック　🟢

**痛点**：非中央集権のネットワークアプリケーション（IPFS、ウェブの P2P チャットルーム、WebTorrent）を構築するとき、フロントエンドは世界の他のノードと複雑な P2P 接続を張る必要がある。しかしブラウザは高水準の WebRTC API しか提供せず、低水準のストリームの多重化、ノードのルーティング（DHT）、安全な暗号のハンドシェイクの折衝を欠く。従来は厚い JS 版の libp2p に頼るが、数百の P2P の仮想チャネルを保ちバイナリのパケットヘッダを解析するとき、動的型付けが大量の CPU を消費して UI を断続的に引っかからせる。

**原理**：Go か Rust の産業級の libp2p の中核ネットワークスタック（`mplex` の多重化、`yamux`、`noise` の暗号層を含む）を丸ごと Wasm へコンパイルする。**バイナリのパケットのパイプライン**：WebRTC のデータチャネルが受け取った生の P2P のバイト列を `Uint8Array` として直接 Wasm のメモリへ書き、内部のパーサが極めて速い整数の状態機械でパケットのヘッダを分解し各仮想サブチャネルへ自動で振り分ける。**メモリ上のネットワークバッファ**：Wasm 内部が効率的なスライディングウィンドウとリングキューを保持し、流量制御と暗号の防御を実行し、全過程で JS のゴミオブジェクトを生成しない。

**性能**：200 の P2P ノードの接続を同時に保ち毎秒 50 MB のスループットを出す極限のテストで、プロトコルの解析速度が純粋な JS 版より **12〜18 倍速く**、CPU 使用率が 65% 下がると主張されている。

**長所**：静的ホスティングの DApp に産業標準に適う「サーバなしの P2P 接続能力」をもたらし、ウェブ側の IPFS ノードの転送の安定性を大きく高める。
**短所**：サンドボックスの制約により、**依然として従来の TCP/UDP の待ち受けを直接開始できず**、外部の JS が WebRTC か WebSocket を物理 NIC の踏み台として使うことに頼らねばならない（第 11 章の P2P の「サーバ不要」に対する四つの留保に呼応する）。

**競合**：js-libp2p（機能の完全性は高いが、極めて高頻度のバイナリのパケットの分解と Noise のハンドシェイクで深刻な GC の引っかかりを招く）。

### 55.（元 74）minimap2-Wasm — 遺伝子配列の高速アライメント　🟡

**痛点**：現代の生物医学では、科学者はシーケンサが生む DNA の膨大な塩基配列（reads）を既知の標準ゲノムとアライメントし、遺伝子の変異や感染症の特徴を捉えねばならず、たいてい C 言語の権威あるライブラリ **minimap2**（精密な動的計画法と seed-and-extend のアルゴリズムを採る）に頼る。以前は生物学者が Linux の端末をインストールするか、機微な個人の遺伝子データを病院のクラウドへ上げるしかなかった——巨大なプライバシーの危険があるうえ、バックエンドのクラスタの維持コストも極めて高い。

**原理**：数万行の極度に最適化された C 言語の遺伝子アライメントのエンジンを Emscripten で Wasm へコンパイルし、ウェブ版の遺伝子診断の作業台を作る。**バイナリの索引の表引き**：標準ゲノムの巨大な索引テーブル（数百 MB）をバイナリのバイト列として一度に Wasm の線形メモリへ読み込む。**SIMD で加速した動的計画法**：遺伝子アライメントの中核はスミス・ウォーターマン行列の求解であり、Wasm 内部で SIMD を有効にし、一命令で 4 つか 8 つの塩基のスコア行列とペナルティの重みを並列に計算する。

**性能**：10,000 塩基対を含む未知のウイルスの DNA 配列のアライメントに **80〜150 ミリ秒**しかかからず、ネイティブ C の **75%** に達すると主張されている。

**長所**：**100% 医療級のプライバシーの安全**。個人の DNA データが完全にローカルのサンドボックスに留まる。研究者が野外の調査でスマートフォンからページを開くだけでリアルタイムにアライメントできる。
**短所**：ヒトの標準ゲノムの索引ファイル（`.mmi`）はしばしば数百 MB から数 GB に達し、フロントエンドの初回ロードとメモリの割当の制御には極めて精密なストリーミングのアーキテクチャ設計が要る（まさに第 8 章の「突破アーキテクチャ一」が必要になる場面である）。

**競合**：純粋な JS の文字列照合のアルゴリズム（バイナリのポインタ操作と SIMD のベクトル加速を欠き、大規模な遺伝子データの処理で数桁遅く、産業的な実用の可能性がまったくない）。

### 56.（元 75）Orekit-Wasm — 天体力学と衛星軌道の予測　🟡

**痛点**：航空宇宙のエンジニアや天文の愛好家が人工衛星（ISS、Starlink）の正確な軌道位置を予測するとき、極めて精密な天体力学の数値計算が要る：地球の重力場の不均一性（球面調和関数のモデル）、太陽輻射圧、大気の抵抗、多体の重力摂動。権威あるオープンソースの下層ライブラリは **Orekit** である。ウェブで純粋な JS の通常の浮動小数点にこれらの軌道摂動の微分方程式を手書きすると、正確な 64 ビットの整列と高速な行列の反復を欠くために、予測した軌道が数日後には数キロメートルの累積誤差を生む。

**原理**：厳密な天体力学の中核を Wasm へコンパイルし、非中央集権の衛星追跡のダッシュボードを提供する。**正確な数値積分器**：Wasm 内部に高次のルンゲ・クッタ（Dormand-Prince）の常微分方程式のソルバを実装し、軌道要素と地心座標を厳密に連続した `f64` として線形メモリ上で進める。**時刻系と座標系の変換の状態機械**：IERS 標準の時刻系（TAI、UTC）と慣性座標系（EME2000、ITRF）の複雑な行列変換をバイナリのレベルで高速に実行し、全過程で JS の GC の干渉を迂回する。

**性能**：衛星の今後 30 日の正確な位置の予測（刻み 1 秒の連続積分）に **40〜60 ミリ秒**しかかからず、精度は航空宇宙産業の標準に適合し、純粋な JS より **30 倍以上速い**と主張されている。

**長所**：まったくインストール不要で、バックエンドコストがゼロで、航空宇宙級の高精度のオンライン軌道推算ツールをもたらす。Three.js と組み合わせればリアルタイムの 3D 地球の軌道の可視化ができる。
**短所**：全球の重力場モデル（EGM96）と正確な閏秒の観測データを読み込む必要があり、これらの静的な特徴ファイルはフロントエンドが動的に要求して注入せねばならない。

**競合**：satellite.js（より単純な SGP4 モデルに基づき速いが、物理の単純化の度合いが極めて高く、高次の重力場の不均一性や大気の抵抗の摂動を計算する能力を持たない）。

### 57.（元 76）WireGuard-Wasm — フロントエンドの VPN ネットワークプロトコルスタック　🟡

**痛点**：リモートワークとゼロトラストのアーキテクチャにおいて、WireGuard は高性能で軽量な暗号 VPN のプロトコルである。しかし従来の VPN はオペレーティングシステムの下層に仮想 NIC のドライバをインストールせねばならず、極めて高いシステム権限が要る。従業員がインストールなしでページを開くだけで社内ネットワークの資源へ安全に接続できるようにしたくても、純粋な JS の暗号ライブラリでは毎秒数十 MB の高頻度な ChaCha20-Poly1305 のパケットの再構成と Noise のハンドシェイクの状態機械にまったく対処できない。

**原理**：WireGuard 公式の Go か Rust のユーザ空間のネットワークスタックの中核を Wasm へコンパイルする。**トンネルのパケットの分解**：Wasm がサンドボックスの線形メモリ内で仮想 NIC を一枚模倣する。外部の JS が WebRTC か WebSocket（物理的な中継として）で暗号化された UDP のパケットを受け取ると、そのまま Wasm のメモリへ渡し、内部の状態機械が高速に復号・検証し、元の内部ネットワークの IP パケットを取り出す。**メモリのバッファの流れ**：復号後のデータは Wasm 内部でフロントエンドが読める `ArrayBuffer` へ再び包まれ、ページ内の極小のクライアント（ウェブ版の SSH など）と直接通信する。全過程でオペレーティングシステムのネットワークスタックを通らない。

**性能**：パケットの処理と復号のスループットが純粋な JS の暗号の模倣より **12〜20 倍速く**、ブラウザ側で **毎秒 30〜50 MB** の暗号化された転送に達し、CPU 使用率も安定していると主張されている。

**長所**：静的ページにインストール不要の「ネイティブ級の安全な VPN トンネルの接続能力」をもたらす。暗号の秘密鍵は永久にユーザのブラウザ内に留まる。
**短所**：サンドボックスの境界の制約により、**このトンネルは現在のタブか現在のアプリケーションのネットワーク要求にしか使えず、オペレーティングシステム上の他のソフトウェア全体へ全域の VPN 暗号化を提供できない。**

**競合**：純粋な JS の暗号ネットワークライブラリ（効率的なバイナリのビットシフト演算と緊密なメモリの整列を欠き、大量の VPN のパケットのスループットで深刻な GC の引っかかりと切断を招く）。

### 58.（元 77）Minestom-Wasm — ブラウザ内の Minecraft サーバエンジン　🔴

**痛点**：Minecraft の世界は数百億のブロックからなり、マルチプレイは従来、高価な Java のサーバを借りてブロックの生成、プレイヤーの同期、物理の衝突を処理してきた。コミュニティは静的ページで「開けばすぐ遊べる、ホスト不要」のマルチプレイ体験を望んでいる——それは**ブラウザのフロントエンド自体がサーバにならねばならない**ことを意味する。純粋な JS で書いたゲームサーバは、3D のブロック世界の衝突体積の計算と膨大なパケットの直列化に対して性能が低すぎ、ページを固めてしまう。

**原理**：オープンソースの高性能な Minecraft サーバの中核 **Minestom**（あるいは Rust 実装のサーバの下層）を Wasm へコンパイルし、ウェブのフロントエンドで直接実行する。**メモリのサンドボックスのサーバ**：Wasm が線形メモリ内に高度に緊密な 3D 世界のブロックのデータベースを構築し、プレイヤーの位置、ブロックの破壊と生成、モブの AI をすべて Wasm 内部で計算する。**P2P のネットワーク転送**：WebRTC のデータチャネルを使い、他のプレイヤーがホストのプレイヤーの Wasm サーバと直接 P2P 接続を張る。Wasm はメモリ上で生成した 3D のチャンクをバイナリのバイト列へ直列化して高速に配る。

**性能**：このブラウザ内蔵のサーバが **10〜15 名のプレイヤー**のオンライン接続、物理の衝突、3D 世界の同期を同時に処理でき、サーバ側の毎秒の tick 時間を **2 ミリ秒**以内に収められる（ゲームの上限である 50 ミリ秒をはるかに下回る）と主張されている。

**長所**：真に非中央集権であり、プレイヤーはクラウドのホストを一切借りずに、無料の静的ホスティングでマルチプレイの 3D ゲームサーバを立てられる。ステージのセーブはバイナリファイルへ書き出せる。
**短所**：4 GB のメモリ上限の制約により、大きな描画距離（render distance）や 20 人を超える接続には対応できない。

> ★ **この構想の本物の版が存在し、しかももっと硬派である**：**FluffOS × Wasm** は LPMud のドライバまるごと（LPC のコンパイラ、仮想機械、efuns、telnet プロトコルを含む）をブラウザのタブへコンパイルし、mudlib は `file_packager` で静的なバンドルへ固める。この構想より二つ多く難題を解いている：**実行時にユーザのコードをコンパイルすること**、そして**ホストが駆動する `fluffos_tick()` でブロッキングのイベントループを置き換えること**である。**付録 L 参照。**

**競合**：従来の Java/C++ の独立サーバ（機能は完全で万人規模の接続に対応するが、VPS を購入し複雑なポート転送の設定を扱わねばならない）。

### 59.（元 78）GnuCash-Wasm — 企業級の複式簿記と ERP の中核　🟡

**痛点**：中小企業が財務を管理し、請求書を発行し、貸借対照表を作るには ERP か複式簿記のシステムが要り、オープンソースの権威あるツールは GnuCash である。クラウドサービスにすれば、企業の機微な財務の流れ、利益、給与を第三者へ上げねばならず、危険が巨大である。純粋な JS で会計の中核を手書きすれば、数万件の取引、通貨をまたぐ複利の計算、勘定科目の残高表のリアルタイムの再計算において、**JS は正確な 64 ビットの固定小数点の演算を欠き、浮動小数点の精度の喪失で帳尻が合わなくなりやすい。**

**原理**：C 言語のオープンソースの会計の中核 **GnuCash (libgnucash)** を丸ごと Wasm へコンパイルする。**高精度の固定小数点のメモリ**：会計の帳簿は浮動小数点の誤差を最も嫌うので、Wasm 内部で厳密に `i64` を使って高精度の会計の固定小数点を模倣し、あらゆる貸借の均衡の演算を連続したバイナリの構造の上で直接進め、GC を完全に避ける。**XML/SQL のセーブの同期**：取引のデータをそのまま `.gnucash`（gzip した XML）か SQLite のファイルへ圧縮でき、仮想ファイルシステムを通じてローカルと同期する。財務データは 100% 端末を出ない。

**性能**：5 万件の国際取引を含み 5 種類の外貨の自動レート換算を伴う一年分の総勘定元帳の再計算に、フロントエンドで **20〜40 ミリ秒**しかかからず損益計算書と貸借対照表を生成でき、純粋な JS より **30 倍速い**と主張されている。

**長所**：静的な企業の管理画面に産業級の高精度の財務会計の計算能力をもたらす。100% データの機密が保たれ、財務監査の ACID のトランザクションの安全基準に適合する。

### 60.（元 79）Micro-Apache-Wasm — ブラウザ内の極小のウェブサーバ　🟡

**痛点**：フロントエンドの教育、静的な演習、オフラインの PWA ツールの構築において、ブラウザの内部に「本物のウェブサーバ」を仮想化し、標準の HTTP リクエストを解析したり、独自のルートの書き換え（`.htaccess`）をしたり、仮想の POST フォームを処理したりする必要が生じることがある。以前はこれに Node.js、Apache、Nginx のインストールが要った。純粋な JS で極めて高頻度の HTTP ヘッダの文字列の力任せの解析とステータスコードのリダイレクトを行うと CPU のピークが高すぎ、しかも本物のサーバの下層のアーキテクチャを再現しにくい。

**性能**：高頻度の仮想 API のリクエストの処理で、**1 ミリ秒未満**で標準の HTTP リクエストの解析、ルートの照合、レスポンスの生成を完了でき、QPS が純粋な JS の正規表現で書いたモックサーバより **15 倍以上高い**と主張されている。

**長所**：無料の静的ホスティングの上に、完全で標準的でルートの書き換えの能力を持つサーバエンジンを再現する。オンラインでインストール不要のバックエンド開発とネットワークプロトコルの教育プラットフォームを作るのにきわめて向く。
**短所**：**これは「ブラウザのメモリの中で動く」仮想サーバにすぎず、外部インターネットの本物のユーザがこれを通じてそのユーザのコンピュータへ接続することはできない**（P2P の穴あけトンネルと組み合わせない限り）——これこそ第 5 章の WebContainers に対する真偽の注意と同じことである。

**競合**：Mock.js / MSW（通常のフロントエンドの API データの模擬には向くが、本物の Web サーバの下層の C の状態機械、独自の書き換え規則、本物の HTTP のバイト列の分解の能力をまったく持たない）。

### 61.（元 80）GNU-Tar-Wasm — 産業級のアーカイブと検査のエンジン　🟡

**性能**：5,000 個の微小なファイル（合計 50 MB）のプロジェクト構造のアーカイブとチェックサムの計算に **8〜15 ミリ秒**しかかからず、純粋な JS のアーカイブライブラリより **25 倍以上速い**と主張されている。

**長所**：GNU 公式が数十年積み上げた高い互換性のアーカイブのアルゴリズムを 100% 複製し、フロントエンドが固めた書庫が決して壊れないことを保証する。開発者のサーバの帯域も CPU もまったく消費しない。
**短所**：アーカイブの形式と検査の互換性に高度に特化した低水準のツールであり、**ユーザが単純な一ファイルしか扱わないなら、Wasm の初回ロードのサイズが性能の利得を上回る**。

**競合**：純粋な JS のアーカイブライブラリ（書き方は簡単だが、数千ファイルの密な梱包、POSIX 標準のヘッダのバイトの精密な整列、八進のチェックサムの計算では、効率も形式の互換性も正統な移植版にはるかに及ばない）。

**長所**：静的な 3D プリントのコミュニティにバックエンドコストゼロのデスクトップ級のスライス能力をもたらす。工業デザイナーの試作品が 100% ローカルに留まり、知財の流出の危険をなくす。
**短所**：モデルの幾何が深刻に壊れている場合（非多様体の幾何など）、C++ の中核が Wasm 内で例外を投げるとき、デバッグと異常時のメモリの後始末のグルーの設計が極度に複雑になる。

**競合**：純粋な JS の幾何スライスのライブラリ（厳格な型と効率的な多次元の空間木のアドレス指定を欠き、5 万を超える三角面を扱うとページがそのまま OOM を起こすか長い GC で固まる）。

**長所**：ウェブが「高周波のハードウェアのデジタル信号」を扱えないという禁域を破る——USB の受信機を挿せばブラウザが全機能の無線受信機になる。サーバコストはゼロ。
**短所**：Wasm 内部の求解のアルゴリズムが固定されているので、フロントエンドがまったく新しい独自の変調の式を動的に注入したい場合、柔軟性が低い。

**競合**：純粋な JS の DSP ライブラリ（64 ビットの複素ベクトルのメモリの連続整列を保証できず、大量の IQ サンプルが流れ込むと頻繁な GC の引っかかりを招き、復号された音声に耳障りな音割れと歪みが出る）。

**競合**：Cannon.js / Oimo.js（サイズが小さく習得も速いが、多数の物体の高密度な積み重ね、複雑な関節の拘束、連続衝突検出（CCD）では、計算力も数値の精度も産業や高度なゲームの場面にまったく対処できない）。

### 67.（元 86）NimBLE-Wasm — 低消費電力 Bluetooth（BLE）のプロトコルスタック　🟡

**痛点**：ウェブの IoT のコンソールや医療ウェアラブルの監視ステーションを開発するとき、フロントエンドは Web Bluetooth API でハードウェアと通信する。しかしブラウザ標準の Bluetooth API は高水準の GATT の読み書きのインタフェースしか公開せず、低水準のパケットの分解、多デバイスの再試行と流量制御の状態機械、特殊な暗号のハンドシェイクへの対応を欠く。純粋な JS で高頻度の Bluetooth の特性値のバイナリの解析と独自プロトコルの再構成を手書きすると、動的なメモリの確保が断続的な GC の引っかかりを招き、高頻度のデータの流れ（毎秒 100 回のリアルタイム心電図）に対してパケットを失いやすい。

**原理**：C 言語の産業級の BLE の中核プロトコルスタック **NimBLE**（ESP32 や Apache Mynewt でよく見られる）を Wasm へコンパイルする。**バイト列のプロトコル解析のパイプライン（L2CAP/ATT 層）**：ブラウザが受け取った生の `ArrayBuffer` は JS の解析を飛ばし、メモリのポインタで直接 Wasm のリングキューへ書かれる。内部の NimBLE の状態機械がバイナリのレベルでプロトコルのヘッダを極めて速く分解し、検証を行い、パケットの再構成を終える。**メモリの隔離による防御**：あらゆるタイムアウトの再試行、スライディングウィンドウの流量制御を、Wasm のサンドボックス内で極めて低いオーバーヘッドで実行する。

**性能**：4 台の Bluetooth の医療機器を同時に保ち、毎秒数万の特性値のバイトを流す負荷試験で、プロトコルの解析速度が純粋な JS より **15〜22 倍速く**、CPU 使用率が 70% 下がると主張されている。

**長所**：静的な IoT の管理画面に、産業級で干渉に強く流量制御の能力を持つ Bluetooth のプロトコルスタックをもたらす。デバイスのデータは完全にローカルで解析される。
**短所**：**ブラウザの下層のセキュリティのサンドボックスを迂回できず**、依然として外部の JS が Web Bluetooth API をハードウェアの橋として使うことに頼らねばならないので、精密な安全のイベントのコールバック層を設計する必要がある。

**競合**：純粋な JS の独自の Bluetooth のパーサ（開発の難度は低いが、多デバイスの並行、高頻度のビットシフトの解析、精密な流量制御の状態機械では効率が低く、データの遅延や切断を招きやすい）。

### 68.（元 87）Espace3D-Wasm — 3D の室内音響のレイトレーシングのシミュレーション　🔴

**痛点**：建築工学、コンサートホールの設計、高度な音響空間の計画では、エンジニアが 3D 空間における音の反射、吸収、回折を評価し、残響時間（RT60）と音場の分布を計算せねばならない。これには密な**音響のレイトレーシング**の実行が要る。フロントエンドで純粋な JS に 3D の幾何モデルを走査させ数百万の音響のレイのメッシュとの交差と材質の吸収率の反復を実行させると、正確な 64 ビットの空間木（BVH）のアドレス指定の最適化を欠くために、メインスレッドを長時間そのまま固まらせる。

**原理**：C++ の高性能な室内音響のシミュレーションの中核を Emscripten で Wasm へコンパイルし、デスクトップ級の音響設計の機能を提供する。**空間の境界表現のメモリ（BVH の配置）**：3D の建築モデルの幾何の頂点と材料の音響吸収係数の表（125 Hz〜8 kHz の八つのオクターブ帯）を厳密にバイナリのバイト列として線形メモリへ書き、メモリ上に緊密な空間分割の木を構築する。**マルチコアの音線の並列発展**：Web Workers + `SharedArrayBuffer` を使い、数百万の仮想の音響のレイの射出と反射の軌跡を複数の CPU コアへ並列に配り、バイナリのレベルでインパルス応答を高速に解く。

**性能**：10,000 の多角形を含む複雑なコンサートホールのモデルへ 100,000 本の音響のレイを射出し全帯域の残響を計算するのに、フロントエンドで **400〜600 ミリ秒**しかかからず、ネイティブ C++ の **80%** に達すると主張されている。

**長所**：静的な建築設計のダッシュボードに産業級の音響シミュレーションの能力をもたらす。**Web Audio API と完璧に組み合わさる——シミュレートしたインパルス応答（IR）をフロントエンドで直接音楽と畳み込んでミックスし、3D 空間音響のリアルタイムのバイノーラルのモニタリングのプレビューを実現できる。**
**短所**：密な幾何と音線の追跡が短時間で CPU を振り切らせるので、モバイルでの利用ではレイの総数を精密に制限して過負荷を防ぐ必要がある。

**競合**：純粋な JS の幾何シミュレーションのライブラリ（効率的なベクトル演算とキャッシュに優しい多次元の空間木のアドレス指定を欠き、高精度の空間音響の境界の処理で 25 倍以上遅く、まったく実用にならない）。

### 69.（元 88）Telemetry-Wasm — ストリーミングのテレメトリの時系列の高速解析　🔴

**痛点**：大規模なサーバのクラスタ、自動運転の車両群、産業のセンサネットワークを監視するとき、フロントエンドは絶え間なく流れてくるテレメトリのデータ（タイムスタンプ、指標のラベル、数値）を受け取らねばならない。静的な監視のダッシュボードで数百万点を含む時系列のグラフをリアルタイムに描画しようとすると、JS に解析させた場合、突発的な「データの嵐」に対してバイナリを高水準のオブジェクトへ頻繁に変えることで深刻な GC の崩壊を招き、グラフの更新率が一桁まで落ちる。

**原理**：Rust（あるいは C）で書かれた新世代の時系列の圧縮と解析の中核（Facebook の **Gorilla** に似た圧縮アルゴリズムを採る）を Wasm へコンパイルする。**Delta-of-Delta の時刻圧縮の状態機械**：データをストリームとして線形メモリへ読み込み、Wasm がポインタで生のバイト列の上を直接 Delta-of-Delta のタイムスタンプの圧縮と XOR の浮動小数点の値の圧縮の走査を行う（**JS のオブジェクトを生成しない**）。**平坦なグラフのバッファ**：解析し終えたデータを Wasm 内部で直接 WebGL/Canvas の描画形式に適う緊密な頂点行列へ組み直し、全過程で JavaScript のヒープの確保を迂回する。

**性能**：2,000,000 件の高頻度のテレメトリのログを含むバイナリの大きなファイルの解析と洗浄に **15〜25 ミリ秒**しかかからず、純粋な JS 版より **30 倍以上速く**、メインスレッドの GC 停止は完全にゼロになると主張されている。

**長所**：無料の静的な監視のダッシュボードに産業級の時系列の大規模データの洗浄とリアルタイムの描画の能力をもたらす。100% バックエンドコストゼロで、ログが端末を出ないという企業のプライバシーの要求を満たす。
**短所**：内部の解析のアルゴリズムが特定の時系列の形式に高度に最適化されているので、入力の形式や標準のプロトコル（Prometheus か独自の形式）が変われば Wasm モジュールを再コンパイルせねばならない。

**競合**：純粋な JS の JSON/CSV のパーサ（十万件を超えるストリーミングのテレメトリの大規模データには力不足で、UI を凍らせやすい）。

### 70.（元 89）FeatureOCR-Wasm — エッジ AI の光学文字の特徴抽出（HOG）　🔴

**痛点**：ウェブで身分証の認識、ナンバープレートの読み取り、手書きの認識をするとき、前段の処理として画像に複雑な**特徴抽出**と幾何の補正（勾配方向ヒストグラム HOG、局所二値パターン LBP、テクスチャ解析）が要る。この密な計算を純粋な JS に任せると、4K の写真の処理で配列の走査と浮動小数点の演算の効率が極めて低い。大きな画像をまるごとクラウドの API へ送れば、高価な帯域の課金と機微な証明書の流出の危険に直面する。

**原理**：産業級のコンピュータビジョンの特徴工学の C++ の中核の演算子を Emscripten で Wasm へコンパイルし、非中央集権のフロントエンド AI の最後の砦の計算エンジンとする。**行列のスライディングウィンドウの加速**：Canvas が取り込んだ高精細な画像のバイトのポインタを直接 Wasm の線形メモリへ書き、内部でポインタの直接制御による高速な表引きで畳み込みの核とピクセル行列のスライディングウィンドウの演算を実行する。**SIMD の演算子のベクトル化**：一つの CPU 命令で 4 つか 8 つのピクセルの勾配の方向と強度を並列に計算し、サンドボックス内で高度に緊密なバイナリの特徴ベクトルを高速に作る。

**性能**：1000 万ピクセル（4K）の高精細な証明書の写真の処理で、フロントエンドは **35〜50 ミリ秒**で全画像の HOG の特徴抽出と幾何の補正を完了し、純粋な JS より **25 倍以上速い**と主張されている。

**長所**：静的ページに無限に並行し運用ゼロの無料の AI の特徴の前処理の能力をもたらす。100% プライバシー安全であり、機微なファイルが完全にローカルのサンドボックスに留まる。
**短所**：特徴抽出のアルゴリズムがコンパイル済みのバイナリモジュールに固定されているので、特徴の重みを動的に替えたり畳み込みの式を変えたりしたければ再コンパイルが要る。

**競合**：純粋な JS の画像処理ライブラリ（低水準のメモリの整列とビット演算の最適化を欠き、大きな写真のピクセル単位の走査で CPU のピークが高すぎる）。**注意：OpenCV.js（事例 27）はこの構想のより完全で検証可能な上位集合である。**
