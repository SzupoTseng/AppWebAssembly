# 第9章：全部見られている——バイナリの天然の難読化、二つの物理的禁域、そして混成アーキテクチャ

> **「GitHub Pages でプログラムを走らせたら、全部見られてしまうのでは？」**
> そのとおり、完全に見られている。これは欠陥ではなく、静的ホスティングの定義である。ユーザがあなたのサイトを閲覧するとき、ブラウザは HTML も JavaScript も `.wasm` バイナリも**すべて彼のコンピュータへダウンロードして**実行する。誰でも F12 を押せば、あなたのファイルをまるごと持ち去れる。
> **この章が問うのは「どう防ぐか」ではなく、「防げないという前提で、どう設計するか」である。**

## シナリオ 1　バイナリの「天然の難読化」はどれだけ強いのか

**背景**：`.wasm` はダウンロードできるが、JavaScript とは本質的に違う。

**JavaScript は圧縮（minify）してもロジックは読める**：変数名は消えても、制御フロー、文字列定数、API 呼び出し、業務ロジックの形はすべてそこに晒されている。経験のある者なら三十分で、圧縮された JS が何をしているか読み取れる。

**Wasm は C++、Rust、Go からコンパイルされた低水準のバイナリ命令形式である**。あなたの `.wasm` を手に入れた者が見るのはソースコードではなく、こういうものだ。

```wat
(func (;42;) (param i32 i32 i32) (result i32)
  (local i32 i32 i32 f64)
  local.get 0
  i32.load offset=12
  local.tee 3
  i32.const 3
  i32.shl
  local.get 1
  i32.add
  f64.load
  local.set 6
  ...
  br_if 2 (;@1;)
  ...)
```

**ここには決定的な情報の喪失がある**：C++ のクラス、継承関係、テンプレートの実体化、Rust の trait ディスパッチ、そしてすべての変数名と関数名——**コンパイルの過程でまるごと消し去られている**。残るのは数百万の平坦なスタック命令だけである。

**産業級の防御的コンパイル設定**：

```toml
# Cargo.toml —— これが「リリース版」で必ず入れるべき四つのスイッチである
[profile.release]
opt-level = 3        # あるいは "z"（サイズ優先）
strip = true         # ★ 関数名と変数名（name セクション）を強制的に取り除く
lto = true           # ★ リンク時全体最適化——クレートを越えてインライン展開し、元の関数境界を掻き乱す
codegen-units = 1    # LTO に完全な視野を与え、インライン展開を徹底させる
panic = "abort"      # ついでに unwinding テーブルを削る（同時にサイズも浮く）
```

```bash
# C/C++ (Emscripten)
emcc -O3 -flto --closure 1 -s ASSERTIONS=0 ...
# もう一段：Binaryen でもう一度剥がす
wasm-opt -O3 --strip-debug --strip-producers --strip-target-features in.wasm -o out.wasm
```

**こうしてコンパイルすれば、攻撃者がリバースエンジニアリングツール（`wasm2wat`、`wasm-decompile`、Ghidra の Wasm ローダ）で逆アセンブルしても、見えるのは意味を欠いた `func_1`、`func_2` の山だけである。核心アルゴリズムのロジックを逆算して復元する難度は、商用のシングルプレイヤーゲームを逆解析するのに近い。**

**しかし「難しい」の層を正確に理解すること**。ここには明言せねばならない技術的現実がある。

| 層 | 攻撃者が手に入れられるもの | 難度 |
|---|---|---|
| 1. 平文の文字列をすべて読む | `strings app.wasm`、あるいは Data セクションを走査する | **秒級**——誰でもできる |
| 2. モジュールのインタフェースを見る | Import/Export セクションは仕様で強制され、**永遠に剥がせない**。関数シグネチャは一目瞭然 | **秒級** |
| 3. WAT へ逆アセンブルする | `wasm2wat` / `wasm-objdump -d` で、読める命令列が得られる | **分級**。ツールは出来合いである |
| 4. 制御フローとデータフローを大まかに復元する | `wasm-decompile`（WABT 内蔵）、Ghidra + Wasm プラグインで、C 風の疑似コードが得られる | **時間級** |
| 5. 「これが何のアルゴリズムか」を復元する | 領域知識と大量の突き合わせが要る | **日〜週級** |
| 6. 保守でき再開発できるソースへ復元する | そうする経済的理由がほぼない | **月級以上。たいてい割に合わない** |

**第 2 層に注意**：Wasm の Export セクションは仕様が要求するものであり、**剥がすことはできない**——攻撃者はつねに「このモジュールは `compute_risk_score(i32, i32) -> f64` をエクスポートしている」といった情報を見られる。シンボルの除去が防げるのは第 5・6 層だけであり、前の四層は防げない。

> ⚠️ 真偽の注意
> 「Wasm は不可逆なバイナリ変換だ」という一文は**成り立たない**。Wasm のバイナリ形式は**完全に公開され構造化されて**おり、WAT への逆アセンブルは可逆で、機械的で、出来合いのツールがある——これは x86 機械語の逆解析より**はるかに容易である**（x86 には可変長命令、コードとデータの混在、間接ジャンプテーブルといった難題があるが、Wasm にはどれもない）。正確な言い方はこうだ：**Wasm が隠すのは「ソースの意味論の層」（型、命名、抽象）であって、「プログラムの振る舞いの層」ではない。** 決意と領域知識のある分析者は、Wasm モジュールが何をしているかを完全に理解できる——**難読化が押し上げるのはコストであって、可能性ではない。**

> 💡 座右の一言
> **あらゆるコード保護技術が売っているのは「不可能」ではなく「割に合わない」である。** どんな難読化も、パッキングも、ホワイトボックス暗号も、バイナリと時間と決意を持つ者を数学的に阻むことはできない。それらがしているのはすべて同じこと——**攻撃コストを攻撃の見返りより高く押し上げること**である。つまり保護の強度を測る正しい単位は「破るのがどれだけ難しいか」ではなく、「破ったらいくら儲かるか」である。一週間のキャンペーンの抽選ロジックを守る難読化は弱くてもかまわない。中核の価格モデルを守る難読化は、どれだけ強くても足りないかもしれない——相手の見返りがあなたの市場全体でありうるからだ。**だから「これで十分安全か」を議論するときにまず問うべきは：破ることに成功した者は、いくら持ち去れるのか、である。** その数字があなたに必要な保護の等級を定義し、同時に、いつ保護への投資をやめて資産を別の場所へ移すべきかも定義する。

## シナリオ 2　二つの物理的禁域：入れたら一秒で終わる

**背景**：Wasm のバイナリは完全な復元が難しい。**しかしあなたのコードが以下の二つを含んでいるなら、一秒で終わりである。**

### 禁域その一：ハードコードされた鍵（API キー／秘密鍵）

**絶対に**、Wasm のコード内に AWS のシークレット、OpenAI の API キー、データベースのパスワード、署名用の秘密鍵を書き込んではならない。

**攻撃者はあなたのアルゴリズムを読み解く必要がない**——バイナリの文字列走査ツール（Linux の `strings` コマンド）で `.wasm` を走査すれば、一秒であなたの平文文字列がすべて出てくる。

```bash
$ strings app.wasm | grep -Ei 'sk-|AKIA|BEGIN.*PRIVATE|password|secret'
sk-proj-aBcD1234...
AKIAIOSFODNN7EXAMPLE
-----BEGIN RSA PRIVATE KEY-----
```

**なぜシンボルの除去では救えないのか**：`strip` が剥がすのは **name カスタムセクション**（関数名、変数名）である。**文字列定数は Data セクションにあり**、それはプログラムの実行に必要なデータであって、**剥がすことは不可能である**。それはそこにある。平文で、grep されるのを待って。

**よくある誤った対処と、それがなぜ効かないか**：

| 誤った対処 | なぜ効かないか |
|---|---|
| 鍵を Base64 で符号化する | `strings` には引っかからないが、`base64 -d` で一秒で戻る。しかも復号関数はすぐ隣にある |
| 鍵を数片に切って連結する | 連結のコードがバイナリの中にある。一度動的に実行すれば吐き出される |
| 鍵を XOR で暗号化する | 鍵の鍵もバイナリの中にある（これがホワイトボックス暗号の根本的な袋小路である） |
| 「どうせ私の小さなプロジェクトを逆解析する者などいない」 | 自動走査機が毎日 GitHub Pages と npm を這い回っており、相手を選ばない |

**唯一の正解**：**鍵はクライアントへ決して入れない。** フロントエンドは自分のバックエンドへ**短命で範囲を限定した**トークンを要求し、本物の鍵はバックエンドだけが持つ。この規則は Wasm でも JS でもモバイルアプリでもまったく同じである——**Wasm は、もともと間違っていたアーキテクチャを正しくしてはくれない。**

### 禁域その二：中核の商業機密

もしあなたの会社が特許化された「独自の中核予測アルゴリズム」で稼いでおり、そのアルゴリズムが漏れれば会社が破産するのなら、**その業務は絶対に GitHub Pages の Wasm で走らせてはならない。**

**判断基準は単純である**——自分に一言問え：**もし競合が明日このロジックを完全に手に入れたら、私には何が残るのか。**

- 「データ、ユーザ、チャネル、ブランド、コンプライアンス上の資格が残る」→ フロントに置いてよい。
- 「何も残らない」→ それはサーバ上に、しかもあなたが制御するサーバ上になければならない。

## シナリオ 3　産業界の標準解：混成アーキテクチャ

**背景**：「静的ホスティングのゼロコストと無限の並行性」と「商業機密の安全」を同時に手に入れるため、成熟したチームの標準的なやり方が**混成アーキテクチャ（Hybrid Architecture）**である。

**この分界線の引き方**：

```
┌──────────────────── クライアント（完全にダウンロードされうる）────────────────────┐
│                                                                              │
│  フロントの Wasm が「密な計算とピクセルの描画」を担う                             │
│  ─────────────────────────────────────────                                   │
│  · 3D 幾何の行列演算、有限要素の求解                                            │
│  · 高頻度フィルタ、映像のストリーミング分割、符号復号                              │
│  · 大規模データのローカル分析、SQL クエリ、索引検索                               │
│  · 標準アルゴリズム（畳み込み、FFT、A*、ニュートン法……業界に公開されている）        │
│                                                                              │
│  特徴：コードサイズが大きく、計算力を食うが、アルゴリズム自体は公開されている        │
│  利得：大量のバックエンド計算費用を節約、データが端末を出ない、無限の並行性          │
└──────────────────────────────────────────────────────────────────────────────┘
                              ↕  最小化され、暗号化され、認証のあるインタフェース
┌──────────────────── サーバ側（あなたが完全に制御する）────────────────────────┐
│                                                                              │
│  バックエンド API が「認証、安全検証、機密の中核」を担う                          │
│  ─────────────────────────────────────────                                   │
│  · ユーザのログイン、セッション、権限の判定                                       │
│  · 課金、割当、計量、監査ログ                                                   │
│  · 鍵の保管、署名、暗号化・復号                                                 │
│  · データベースの読み書き、多人数協調の衝突解決                                   │
│  · 本物の商業機密アルゴリズム（もしあれば）                                       │
│                                                                              │
│  特徴：計算量は小さいが、ひとたび漏れれば災難である                               │
│  形態：極めて軽量でよい（AWS Lambda、Cloudflare Workers で十分）                 │
└──────────────────────────────────────────────────────────────────────────────┘
```

**このアーキテクチャの経済学は美しい**：**計算量の大きい部分（高いが機密ではない）は無料でクライアントへ渡して走らせ、機密の部分（価値があるが計算量は小さい）は安いサーバ一台に留める。** 両側のコスト構造がちょうど補完的である——これは偶然ではなく、これが標準解になれた理由そのものである。

**実用的な線引きの問い**（どんなアーキテクチャ図よりも役に立つ）：

> どの機能モジュールにも問え：**「このロジックが一字一句ブログに公開されたら、私の商売は影響を受けるか？」**
> - 受けない → フロントの Wasm へ。金が浮く。
> - 受ける → バックエンドへ。そして第二の問いを：**「それが必要とする計算量は、そのためにサーバを一台養う価値があるか？」**
>   - ある → 標準的なバックエンドサービス。
>   - ない → 設計し直し、「フロントで計算し、バックエンドで検証する」へ分割する。

**第三の問いが最も価値がある**：バックエンドに置かねばならないように見える重い計算の多くは、実は**フロントで結果を計算し + バックエンドで結果を検証する**へ分割できる。検証は計算より数桁安いのがふつうである（プルーフ・オブ・ワークを思い出し、ゼロ知識証明を思い出し、「ソートは高いが、ソート済みかの検査は安い」を思い出せ）。**これが混成アーキテクチャの最も精妙な一層である。**

> 💡 座右の一言
> **アーキテクチャ設計の本質は、性質の異なるコストを、それを負うのに最も適した場所へ置くことである。** 計算力は安いが量が多い——なら無限に無料のコンピュータがある場所（ユーザのブラウザ）へ置け。機密は高価だが量は少ない——なら鍵をかけられる場所（あなたのサーバ）へ置け。本当のアーキテクチャの力量はフレームワークを正しく選ぶことではなく、**各コストの「性質」を見抜き、そのコスト曲線が最も平らな位置を見つけること**にある。この原理はあらゆる工学的判断へ広げられる。キャッシュは読みが多く書きが少ない場所へ、索引はカーディナリティの高い列へ、非同期は待ち時間の長い場所へ、レート制限は攻撃源に最も近い場所へ。**「これはどこへ置くべきか」と迷ったら、「どこなら技術的に可能か」ではなく、「これのコストはどんな性質で、どこで負うのが最も安いか」を問え。**

## シナリオ 4　逆から考える：見られていることが究極の武器になることもある

**背景**：ある領域では、「見られていること」は欠陥ではなく、**信頼を築く唯一の方法**である。

### エンドツーエンド暗号（E2EE）の信頼の礎

暗号とゼロ知識証明（ZKP）の領域で、ユーザはなぜ高度に機微な秘密鍵をあなたのページ上で計算させる気になるのか。

**それはまさに、あなたのページが GitHub Pages に配備され、コードが完全にオープンで透明だからである。** ユーザは開発者ツール（F12）で Wasm のコードを一行ずつ検証し、あなたが**彼のデータをこっそり第三者サーバへ送っていないことを百パーセント**確認できる。これこそ分散型アプリケーション（DApp）の中核的な優位である。

**技術的にこの信頼の鎖がどう成立しているのか**（「オープンソース」の一語よりずっと精確である）：

1. **監査可能なネットワーク挙動**：ユーザが DevTools の Network タブを開き、あなたの PGP ツールがユーザの「暗号化」ボタンのあとに**外部リクエストを一本も発していない**なら、それは誰にでも検証できる事実である。
2. **監査可能なバイナリ**：`.wasm` のハッシュ値は計算でき、記録でき、突き合わせられる。再現可能ビルド（reproducible build）と組み合わせれば、コミュニティは「この `.wasm` は確かにそのソースからコンパイルされた」ことを検証できる。
3. **侵入されるサーバが存在しない**：静的ホスティングにはアプリケーション層のバックエンドがなく、したがって SQL インジェクションもなく、SSRF もなく、侵入後にレスポンスをこっそり差し替えられる可能性もない。
4. **変更に記録が残る**：コードと `.wasm` ファイルはあなたの Git コミット履歴に閉じ込められており、誰かがあなたのコードを動かすには Git の署名を通らねばならない。**攻撃者はユーザに気づかれずにあるレスポンスだけを差し替えることができない**——全員に見えるコミットを押さねばならないのだ。

### 改竄防止のもう一面

もしあなたのサービスにバックエンドがあれば、**バックエンドが侵入された瞬間、フロントのページにフィッシングスクリプトを注入されうる**。しかも静かに、特定のユーザだけを狙って、事後には追えない形で。静的ホスティングはこの攻撃面を丸ごと取り除く。

> ⚠️ 真偽の注意
> 「GitHub Pages のコードは Git のコミット記録に固定されており、安全性が極めて高い」という一文には三つの但し書きが要る。**（一）** 攻撃者があなたの GitHub アカウントか Personal Access Token を取れば、同じくコミットを押せる——**アカウントのセキュリティこそ本当の境界である**（必要な二要素認証とブランチ保護を有効にすること）。**（二）** サプライチェーンのリスクは依然として残る：ビルドの過程で毒を仕込まれた npm パッケージや crate を取り込めば、出力される `.wasm` 自体が悪意あるものになり、しかも同じく美しいコミット履歴を持つ。**Wasm 固有の検査を二つ覚える価値がある：`wasm-objdump -x` で import 一覧を見ること（モジュールがどんな能力を要求したか、その一覧こそ攻撃面である）、そして再現可能ビルド（「このバイナリは確かにそのソースからコンパイルされた」ことをコミュニティが検証できるようにすること）——付録 O §7-2 参照。****（三）** 「ユーザは Wasm を一行ずつ検証できる」は理論上は成り立つが、**実務ではほとんど誰もやらない**——第三者のセキュリティ監査かコミュニティの継続的な監視がないかぎり。**透明性が提供するのは「監査可能」であって、「監査済み」ではない。** この二つの差こそ、大半のセキュリティ事故が起きる場所である。

> 🔍 踏み込んだ論評──同じ性質でも、二つのビジネスモデルの下では価値の符号が正反対になる
> この章から持ち帰る価値が最も高いのは、どの技術でもなく、一つの構造的な観察である：**「コードが完全に見られうる」という性質そのものに善悪はなく、その価値の符号はビジネスモデルが決める。** **アルゴリズムそのもの**を売る会社（独自の圧縮アルゴリズムのライセンスで稼ぐベンダなど）にとって、透明性は純粋な負債である——価値のすべてがそのコードにあり、見られた瞬間ゼロになる。**信頼**を売る製品（暗号ツール、DApp、プライバシーウォレット、医療データ処理）にとって、透明性は中核の資産である——価値のすべてが「私が悪事を働いていないことをあなた自身が検証できる」ことにあり、隠せば逆に一文の値打ちもない。そしてこの二極のあいだに、大多数のソフトウェア企業がいる：**その価値はアルゴリズムにも透明性にもなく、データに、ユーザとの関係に、コンプライアンス上の資格に、エコシステムにある**——彼らにとってコードの可視性は実のところ**どうでもよく**、そこに拘泥することは高価な気の散らしである。**だからコード保護の予算を投じる前に、正直に一つ答えてほしい：私の濠は、そもそもコードの中にあるのか。** 多くの人はこの問いに答えたがらない。答えがたいてい「ない」だからだ——そしてそれを認めることは、より難しい問いに向き合うことを意味する：**では、どこにあるのか。** それこそが、続く三章の全内容である。

## 本章のまとめ

- 静的ホスティング上のすべては完全にダウンロードされる。**これは定義であって欠陥ではない。** 議論の出発点は「防げないという前提でどう設計するか」であるべきだ。
- Wasm の「天然の難読化」は本物だが、層を正確に理解すること：**平文文字列（秒級）、Export インタフェース（秒級。しかも仕様で強制され剥がせない）、WAT への逆アセンブル（分級）、疑似コードの復元（時間級）、アルゴリズムの理解（日〜週級）、保守可能なソースへの復元（月級。たいてい割に合わない）。** `strip`/`lto` が防げるのは後ろの二層だけである。
- **「Wasm は不可逆」は誤りである**——その形式は完全に公開され構造化されており、逆アセンブルは x86 の逆解析より**はるかに容易である**。難読化が押し上げるのはコストであって可能性ではない（シナリオ 1 の ⚠️ 参照）。
- **二つの物理的禁域**：**ハードコードされた鍵**（`strings` で一秒。Data セクションは剥がせず、符号化／分割／XOR の対処はすべて無効）と**中核の商業機密**（判定：相手が明日このロジックを完全に手に入れたら、私に何が残るか）。
- **混成アーキテクチャが標準解である**：計算量が大きくアルゴリズムが公開されているものはクライアントへ押し出し（金が浮く）、計算量は小さいが漏れれば災難のものはサーバに閉じ込める（安全）。最も精妙な一層は——**多くの重い計算は「フロントで計算し、バックエンドで検証する」へ分割でき、検証は計算より数桁安いのがふつうである。**
- **透明性はある領域では中核の資産である**（E2EE、DApp、プライバシーツール）。「監査可能なネットワーク挙動 + 監査可能なバイナリ + 侵入されうるバックエンドの不在 + 記録の残る変更」を提供するからだ。ただし覚えておくこと：**透明性が提供するのは「監査可能」であって「監査済み」ではない**（シナリオ 4 の ⚠️ 参照）。
- 最終的な問いは「どうコードを隠すか」ではなく——**私の濠は、そもそもコードの中にあるのか**、である。

理論は語り終えた。次章では、このアーキテクチャを極限まで突き詰めた実例を見る：**`figma.wasm` は毎日世界中の数億台のコンピュータへダウンロードされているのに、なぜ今日まで使い物になる模倣品が一つも現れないのか。** 第 10 章へ。
