## シナリオ 2　十の類別：Wasm はどの領域を占めたのか

**背景**：101 件を「それが何を置き換えたか」で分類すると、非常に整った図が見える。

**この表で最も注目すべきは、第 8 類がなぜ最大なのか**（約三割を占める）である。科学計算の領域には特殊な構造がある。

- **アルゴリズムが完全に公開されている**（有限要素法、モンテカルロ、ニュートン・ラフソン、FFT——どれも教科書の内容であり、商業機密がない）。
- **既存の実装が成熟した C/C++ ライブラリである**（GSL、EPANET、OpenVDB、pagmo——移植コストが低い）。
- **本来の利用障壁が法外に高い**（Linux ワークステーションを立てるか、数万ドルの商用ライセンスを買うか、HPC クラスタの順番待ちをするか）。

**この四条件が重なると、Wasm の価値は速さではなく「領域全体の参入障壁をゼロまで打ち下げること」になる。** 大学院生がページを開けば遺伝子配列のアライメントを走らせられ、電力エンジニアが現場のノートパソコンで全網の潮流を計算できる——しかもデータは一バイトも彼のマシンを出ない。

**逆に、どの領域が「表にないか」も同じくらい情報がある**：CRUD の管理画面がなく、EC がなく、コンテンツ管理がなく、ソーシャル機能がない。**それらの場面のボトルネックが計算力であったことは一度もなく、データと状態にあるからだ**——そしてそれこそが第三部の主題である。

> 🔍 踏み込んだ論評──この十類の並びは、明快な価値の選別ルールを示唆している
> 101 件の動機欄を並べてみると、それらがすべて四つの理由に落ちること、そして**その四つの重みの高低が、そのまま実務的な判断ルールになる**ことが分かる。**理由その一：計算コストの転嫁（ほぼ全件に現れる）。** アルゴリズムが公開され、計算量が大きく、商業機密がない——これは Wasm の最も異論の余地ない甘い場所である。**理由その二：データ主権（約七割に現れる）。** 医療、金融、防衛、個人のプライバシー——「データは決して端末を出ない」はこれらの領域では加点項目ではなく、参入条件である。**理由その三：能力の欠落（約三割に現れる）。** ブラウザが XSLT 2.0 に対応せず、Graphite フォントに対応せず、Brotli API を公開せず、AV1 のハードウェアデコードに対応しない——Wasm が唯一の埋め方である。**理由その四：資産の復活（約二割に現れる）。** 数十万行の C++ 幾何カーネル、二十年もののゲーム、GNU が数十年積み上げたツールチェーン——書き直しは不可能でも、コンパイルは可能だ。**この理由の極致の形が文化の保存である**：`fluffos/mudlibs` は一九九〇年代半ばから二〇一五年前後までの中国語圏 MUD のソースを二百件修復し（一五八の重複しない codebase を網羅）、FluffOS ドライバをまるごと Wasm へコンパイルして、そのうち数十件をブラウザで開けば遊べるようにした——**それらのコード自体はほとんど壊れておらず、壊れていたのは環境に対する前提の一つひとつだった**（付録 L 参照）。**したがって判断ルールはこうなる：あなたの場面が当てはまる理由が多いほど、Wasm の投資対効果は高い。理由一だけしか当てはまらないなら、ダウンロードサイズと境界越えオーバーヘッドの勘定を丁寧にすること。一つも当てはまらないなら、Wasm を使うな。** とりわけ注意すべきは——**理由二（データ主権）は唯一「純粋な JS でもできるが、誰も信じてくれない」理由である**という点だ。技術的には、純粋な JavaScript でもデータを送らないことは同じくできる。しかし弁護士を、コンプライアンス担当を、病院の情報セキュリティ部門を説得するとき、「アルゴリズム一式が検証可能なバイナリへコンパイルされ、ユーザ自身のブラウザのサンドボックス内で走り、ネットワークタブに外部リクエストが一つも出ない」という語りの説得力は、「信じてください、私の JS はこっそり送っていません」よりはるかに高い。**これは技術の外にある価値である——売っているのは性能ではなく、監査可能性なのだ。**

## シナリオ 3　五つの汎用アーキテクチャパターン：101 の事例には五つの形しかない

**背景**：101 件を読み終えると一つのことに気づく——アーキテクチャの記述が驚くほど似ているのだ。これは記述の手抜きではない。**Wasm の物理法則のもとでは、実行可能なアーキテクチャが本当にこれだけしかない**からである。

### パターン一：平坦メモリ + ゼロコピービュー（Flat Memory / Zero-copy View）

**出現頻度：101/101。** これはあらゆる Wasm 性能物語の地盤である。

```
JS 側：データを Wasm の線形メモリへ書くか、TypedArray でビューを開く
                    ↓ ポインタと長さだけを渡し、中身は渡さない
Wasm 側：連続したバイト配列で処理する（Structure-of-Arrays、CSR 疎行列、
        Roaring Bitmap、メモリプール、B+ 木……）
                    ↓ 結果を同じメモリへ書き戻す
JS 側：ポインタの位置から結果を読む（あるいは WebGL の VertexBuffer へ直接渡す）
```

**その本当の優位はしばしば誤って語られる**。多くの記述は「JS のガベージコレクションを避けられるから」と言うが、これは半分しか正しくない。**より重要なのは CPU キャッシュである。** JavaScript のオブジェクトはヒープ上に離散して確保されており、百万個の `{x, y, z}` オブジェクトを走査することは百万回のキャッシュミスの可能性を意味する。Wasm では同じデータが三本の連続した `Float64Array` であり、CPU のプリフェッチャが完璧に働ける。**現代の CPU の L1 ヒットは約 4 サイクル、DRAM アクセスは約 200 サイクル——この 50 倍の差こそ、あの「30 倍速い」という数字の本当の出所であり、GC ではない。**

### パターン二：Worker 隔離 + 転送可能オブジェクト（Worker Isolation / Transferable）

**出現頻度：約 60%。** 計算が 16 ミリ秒を超えるなら、メインスレッドを離れねばならない。

```javascript
// メインスレッド：postMessage の第二引数が鍵である
const buf = new ArrayBuffer(50 * 1024 * 1024);
worker.postMessage({ cmd: "process", buf }, [buf]);
// ↑ 第二引数 [buf] がこれを Transferable と宣言する：
//   50 MB を複製せず、メモリの所有権を Worker へ移す（マイクロ秒級）
//   代価：移したあとメインスレッド側の buf は即座に長さ 0 になり、二度と使えない
```

**二つのデータ受け渡し方式を区別すること**：

| 方式 | コスト | 適用 |
|---|---|---|
| 構造化複製（既定） | O(n)。大きなデータでは痛い | 小さなメッセージ、双方がデータを保持する必要がある場合 |
| **Transferable**（`postMessage(x, [x])`） | O(1)。所有権を移すだけ | 大きな buffer の一方向の受け渡し |
| **`SharedArrayBuffer`** | O(1)。双方から同時に見える | 本当のマルチスレッド共有（**クロスオリジン隔離が要る**。第 5 章参照） |

### パターン三：SIMD ベクトル化（`v128`）

**出現頻度：約 40%。** 仕事が「大量のデータに同じことをする」ものなら使える。

Wasm SIMD は固定 128 ビットの `v128` 型と一組のレーン操作を提供し、一命令で `f32` を 4 つ、`f64` を 2 つ、`i8` を 16 個同時に処理できる。典型的な加速比は 2〜4 倍（4〜16 倍ではない——メモリ帯域とデータの並べ替えが一部を食うからだ）。

```bash
# SIMD を有効にする（Rust）
RUSTFLAGS="-C target-feature=+simd128" cargo build --target wasm32-unknown-unknown --release
# SIMD を有効にする（Emscripten）
emcc -msimd128 -O3 ...
```

**実務上の落とし穴が二つ**：**その一、SIMD は検出可能な機能である**——古いブラウザにはないので、非 SIMD の予備ビルドを用意し実行時に検出する必要がある。**その二、Wasm SIMD は 128 ビットしかない**——ネイティブの AVX2 は 256、AVX-512 は 512 である。第 2 章で述べたとおり、AVX2 向けに手で最適化されたコードを移せば、ベクトル幅はそのまま半減する。

### パターン四：ストリーミングと分割処理（Streaming / Sliding Window）

**出現頻度：約 30%。ただし「大きなファイル」の場面では 100%。** これは 4 GB 上限を回避する唯一の実用解である（詳しくは第 8 章）。

```
やってはいけない：10 GB のファイルを丸ごと線形メモリへ read する  ❌ 即 OOM
やるべきこと　　：Wasm 内に 50 MB のスライディングウィンドウを開き、
                OPFS の FileSystemSyncAccessHandle で read(buffer, {at: offset}) を行う
                磁気テープを見るように、必要な区間だけをディスクから取る  ✅
```

MediaInfo が MP4 の `moov` atom だけを読み、DuckDB-Wasm が HTTP Range Request で Parquet の必要な列ブロックだけを取り、Tantivy が索引のヒットしたブロックだけをダウンロードする——**すべて同じ手である。**

### パターン五：AudioWorklet / 高優先度スレッドの隔離

**出現頻度：すべての音声事例（約 6 件）。** 音声スレッドには残酷な硬い締切がある。

```
44.1 kHz のサンプリングレートで、128 サンプルのブロック = 2.9 ミリ秒
→ 処理関数は 2.9 ミリ秒以内に戻らねばならない。さもなくば聞こえるポップノイズになる
→ ここに GC 停止の入る余地は一度もない
→ だから AudioWorklet + Wasm がほぼ業界の慣例になった
```

FLAC の符号化、チップチューンの合成（libmodplug/GME）、SDR の復調——すべてこの道を行く。

> 💡 座右の一言
> **ある領域のすべての成功事例のアーキテクチャがそっくり同じなら、それは創意の欠如ではなく、物理法則が喋っているのである。** 101 の事例は映像音声、データベース、遺伝子、電網、天文、金融をまたぎ、領域間にまったく関連がない。それでもアーキテクチャ図はほぼ互いに差し替え可能だ——同じ制約の組に向き合っているからである：**一枚の平坦なメモリ、一本の高価な境界、16 ミリ秒のフレーム予算、2.9 ミリ秒の音声予算、4 GB の上限。** ここから非常に実用的な帰結が出る：**新しい領域へ入るときは、まずその領域の成功事例三つのアーキテクチャ図を探すこと。よく似ていれば、その形はその領域の物理法則であり、革新しようとしてはいけない。まったく違っていれば、その領域はまだ自分の形を見つけていないということであり、そこにこそ革新の機会がある。** この二つを見分ける能力は、どんな具体的な技術よりも価値がある。

## シナリオ 4　代表的な三事例の深水域

**背景**：付録では一件 500 字だが、ここでは三つを底まで踏む——それぞれが「Wasm が不可能を可能にする」機構の一種を代表しているからだ。

### DuckDB-Wasm：静的ページ上の OLAP エンジンと、HTTP Range という奥の手

**何をしたか**：C++ で書かれた列指向の分析型データベース DuckDB を丸ごと Wasm へコンパイルした。ユーザはページ上で標準 SQL を打ち、ブラウザの中で数百万行のデータに集計クエリをかける。

**なぜ純粋な JS に 60 倍以上の差をつけられるのか**（元のリストは 1000 万行の集計クエリが 100〜200 ミリ秒で完了すると主張している）：

1. **ベクトル化実行**：行ごとに処理せず、一度に列ベクトルのバッチ（通常 1024〜2048 個の値）を処理する。分岐予測に優しく、SIMD に優しく、キャッシュに優しい。
2. **Apache Arrow の列指向メモリレイアウト**：データは線形メモリの中で列ごとに連続して並び、`SELECT SUM(price)` は price の連続配列を走査するだけで、他の列にはまったく触れない。
3. **ゼロコピーの受け渡し**：クエリ結果は Arrow 形式のまま線形メモリに留まり、JS 側は `TypedArray` ビューで直接読む。直列化しない。

**最も美しい一手は、リモートファイルの読み方である**：

```sql
-- この一行は Parquet ファイル全体をダウンロードしない
SELECT region, SUM(revenue) FROM 'https://example.com/sales.parquet' GROUP BY region;
```

Parquet のファイル構造は「データブロック + 末尾のメタデータ（footer）」である。DuckDB-Wasm はこうする。

```
1. HTTP Range Request を一本発して末尾の数 KB だけ取る → footer を読み、
   各列・各 row group がどのバイトオフセットにあるかを知る
2. SQL からどの列・どの row group が要るかを判断する
   （footer の min/max 統計で predicate pushdown による枝刈りをする）
3. さらに数本の Range Request を発し、その数区間のバイトだけを取る
   → 2 GB の Parquet に対して、ダウンロードは 8 MB で済むこともある
```

**これこそ「静的ホスティング + Wasm」という組み合わせの完全な威力である**：CDN が Range Request（無料でどこにでもある能力）を提供し、Wasm がファイル形式を理解する知能を提供する。**あなたはサーバのないデータウェアハウスを手に入れた。**

### Pyodide：CPython まるごとをサンドボックスへ、そしてあの 30 MB の代価

**何をしたか**：CPython インタプリタ本体に、NumPy、Pandas、SciPy、scikit-learn といった**大量の C 拡張を含む**科学計算ライブラリを加え、まとめて Wasm へコンパイルした。

**技術的に最も難しかったのは CPython のコンパイルではなく、それらの C 拡張である**。NumPy の中核は数十万行の C コードであり、自分が `dlopen` があり POSIX ファイルシステムがあり CPU 特化経路がある世界に生きていると想定している。Pyodide は以下をせねばならなかった。

- Emscripten の **MEMFS/IDBFS** でファイルシステム一式を偽造する。
- Wasm に初期には動的リンクがなかった問題を処理する（Emscripten の `SIDE_MODULE`/`MAIN_MODULE` の動的リンク機構を使うか、すべて静的にコンパイルして入れる）。
- **双方向の型の橋渡し**を実装する：JS の `Array` を Python が `list` として読め、Python のオブジェクトを JS が触れ、Matplotlib が描いた図をバイナリストリームへ変えて JS が `<canvas>` へ描ける。

**性能の二層の現実**（この対比はきわめて示唆的である）：

| 何を実行するか | ネイティブに対する性能 | なぜか |
|---|---|---|
| 純粋な Python ループ | **約 1/3 〜 1/5** | 仮想機械の中でインタプリタを走らせている——抽象が二層重なる |
| NumPy / Pandas の C カーネルの呼び出し | **約 70%** | ホットループが C にあり、Wasm はコンパイル済みの機械語を直接実行する |

**この 3〜5 倍の落差は一つのことを語っている**：Pyodide の価値は「Python を速く走らせる」ことではなく、「**Python エコシステムの C カーネルをブラウザの中から呼べるようにした**」ことにある。これで密な純 Python ループを書くのは誤用であり、`df.groupby().agg()` を走らせるのが正解である。

**あの 30〜50 MB のダウンロード**が最大の痛点であり、現実的な緩和手段は三つある。パッケージの必要時読み込み（Pyodide は実行時の `micropip.install` に対応）、Service Worker による永続キャッシュ（二度目の訪問はほぼ瞬時に開く）、そして言語本体だけが必要な場面では **MicroPython/Wasm** への切り替え（サイズが二桁小さい）。

### v86：ブラウザの中で完全な x86 コンピュータを走らせる

**何をしたか**：純粋な静的ページの中で完全な x86 仮想ハードウェアを模倣する——CPU、メモリ管理ユニット、IDE ディスクコントローラ、VGA、キーボード割り込み。Linux が動き、Windows 95 が動き、DOOM が動く。

**その中核技術は非常に直感に反するもの——動的再コンパイル（JIT）である**：

```
素朴なエミュレータ：ループ{ x86 命令を一つ読む → switch(opcode) → 実行 }
                  → 命令ごとにデコードとディスパッチのコストを払い、100 倍遅い

v86 のやり方：x86 の基本ブロック一段 → 動的に Wasm 命令列へ翻訳
             → WebAssembly.instantiate でその Wasm を即時コンパイル
             → 以後そのコードは毎回ネイティブ速度で走る
             → つまり：JIT が Wasm を生成し、ブラウザがその Wasm を機械語へ JIT する
```

**これは「JIT が JIT の入力を生成する」二層構造である**。これが成立するのは、Wasm のほとんど議論されない特性のおかげだ：**`WebAssembly.Module` は実行時にバイト配列から動的に構築できる。** 言い換えれば、**Wasm はプログラムによって生成できるターゲット形式である**——これが、あらゆるエミュレータ、動的言語の実行環境、さらには将来の JIT コンパイラにとって、Wasm を天然のバックエンドにしている。

**ぶつかる壁も明快である**：ホストのハードウェア仮想化（Intel VT-x / AMD-V）は使えない。ring 0 権限を要するからだ。メモリアドレスの変換はすべてソフトウェアで模倣したページテーブルに頼る。したがって Pentium 級の 32 ビットシステムは動かせるが、**現代の 64 ビットの重いオペレーティングシステムは動かせない。**

> 💡 座右の一言
> **技術プラットフォームに長期の生命力があるかを判断するには、一つ見れば足りる——それが「他のものにとってのコンパイル先」になれるかどうかである。** 人が手で書くしかない形式の天井は人類の生産力である。プログラムが生成できる形式の天井は、自分をそこへ移したいと考えるすべてのシステムの総和である。v86 は Wasm を動的に生成し、Pyodide は CPython をそこへコンパイルし、Cranelift は Wasm を機械語へコンパイルし、さらには Wasm 自身が C へコンパイルされてネイティブへ戻される（wasm2c）——**この「誰もが自分をそれへ翻訳できる」性質こそ、中間表現の本当の濠である。** JVM が三十年生き、LLVM IR がコンパイラのバックエンドを制し、Wasm が次になる目があるのはこのためだ。逆に、これは実用的な判定基準も与える：**新しい形式、新しいプロトコル、新しいプラットフォームを評価するときは、一言問え——「第三者がそれを自動生成しているか？」 答えが否なら、それはたいてい道具であってプラットフォームではない。**

## 本章のまとめ

- あの「120 の事例」は実際には **101 件しか重複していない**。19 件は番号を振り直した再述である。これは長い対話における生成の具体的な失敗モードを露わにする：**外部で維持された産出済みリストがないとき、重複排除は文脈に頼るしかなく、文脈は失効する**——そして有効な解法は**探索空間を制約すること（新しい類別を指定すること）であり、記憶を求めることではない**。
- 101 件は三つの真偽等級に分かれる：**🟢 検証可能（約四割）、🟡 上流は本物だが Wasm 移植は要検証（約四割）、🔴 示唆的な構成（約二割）**。正しい読み方はこれを**実現可能性の地図**として扱うことであり、プロジェクト索引ではない。
- 十の類別のうち**科学と工学の計算が三割を占める**。理由は四つの条件を同時に満たすからである：アルゴリズムが公開されている、既存の C 実装が成熟している、本来の参入障壁が極度に高い、データが極度に機微である。**ここでの Wasm の価値は速さではなく、領域全体の障壁をゼロまで打ち下げることである。**
- 101 の事例には**五つのアーキテクチャの形**しかない：平坦メモリのゼロコピー、Worker 隔離と Transferable、SIMD ベクトル化、ストリーミングのスライディングウィンドウ、AudioWorklet の硬い締切の隔離。**すべての成功事例のアーキテクチャが同じなら、それは物理法則が喋っているのである。**
- 「N 倍速い」の本当の出所はたいてい誤って語られている——**ガベージコレクションではなく、CPU キャッシュである**（L1 ヒット約 4 サイクル vs. DRAM 約 200 サイクル）。
- 深水域の三事例はそれぞれ一つの機構を代表する：**DuckDB-Wasm** = CDN の Range Request + Wasm の形式知 = サーバのないデータウェアハウス。**Pyodide** = 純 Python は 3〜5 倍遅いが C カーネルは 70% であり、価値は「エコシステムの C カーネルを呼べるようにした」ことにある。**v86** = Wasm を動的生成する二層 JIT であり、**Wasm がプログラムによって生成できるコンパイル先である**ことを証明している。

機械は走り出し、十分に速くも走った。しかしこれらの機械には共通の致命傷がある——**タブを一度リロードすれば、覚えていたことがすべて蒸発する。** 次章はこれを扱う。第 7 章へ。
