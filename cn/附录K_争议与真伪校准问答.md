# 附录K　争议与真伪校准问答

> 本书横跨可查证的规范事实与未经查证的社群说法。这一份附录把全书所有「⚠️ 真伪提醒」集中起来，并补上几个常见但没在正文出现的争议。
> **格式**：问题 → 流行说法 → 校准后的答案 → 出处在本书哪一章。

## 一、关于历史与定位

### Q1. WebAssembly 是要取代 JavaScript 吗？

**流行说法**：「W3C 钦定的第四种语言，将取代 JavaScript。」

**校准**：**不是。** 规范文档从未把 Wasm 定位为 JS 的替代品，而是明确定位为**互补（complement）**。技术上，Wasm 至今无法独立操作 DOM、无法独立加载自己——**它的每一次启动都需要 JavaScript（或宿主环境）递给它第一把钥匙。** 正确的分工是「Wasm 算、JS 画」。

「2019 年 W3C 定为推荐标准、与 HTML/CSS/JS 并列为第四种内核语言」这件事本身**是真的**，被加料的是「取代」二字。 → 第 1 章、第 4 章

### Q2. 「如果 2008 年有 WASI，就不需要发明 Docker」——所以容器要死了？

**校准**：这句话**确实存在**（Docker 创办人 Solomon Hykes，2019），但常被断章取义。原推文的下一句是「Wasm 是服务器运算的未来」，而非声明容器过时；作者本人后续也澄清这是对「轻量、可携、跨平台」这组性质的称赞。

**现实**：两者**互补**。容器隔离整个操作系统用户空间，**能跑任何既有二进位**；Wasm 只隔离单一应用，换来冷启动与体积的量级优势，但**只能跑重新编译过的东西**。实务上最常见的部署形态是 **Wasm 模块跑在容器化的运行期里**。 → 第 1 章、第 4 章

### Q3. NaCl 是因为技术不行才失败的吗？

**校准**：**不是。** NaCl 技术上是成功的（静态验证 x86 机器码 + 分段沙盒确实安全且快）。它失败于**政治**：只有 Chrome 支持、它是「寄生在网页里的原生程序」而非网页的一部分、且要求其他厂商为每种 CPU 架构各写一套机器码验证器（安全工程上极昂贵的承诺）。 → 第 1 章

## 二、关于性能

### Q4. 「Wasm 有 60–80% 的原生性能」这句话对吗？

**校准**：**这句话几乎没有信息量**，因为它高度依赖工作负载形状：

| 工作负载 | 相对原生 | 原因 |
|---|---|---|
| 纯数值密集循环、数据在缓存内 | **90%+** | TurboFan 产码接近 Clang -O2 |
| 手写 AVX2 优化的代码移植 | **40–50%** | **Wasm SIMD 只有 128 比特，矢量宽度直接砍半** |
| 大量细碎跨界调用 | **可能比纯 JS 还慢** | 跨界固定开销占绝大部分 |
| 大量字符串与对象操作 | 纯 JS 碾压 | Wasm 要付编解码税 |
| 内存受限（缓存未命中主导） | 接近 100% | 两边都在等 DRAM |

**读任何性能宣称时，第一个问题永远是：这个基准的形状跟我要跑的东西像不像？** → 第 2 章

### Q5. 「Wasm 比 JavaScript 快 10–30 倍」？

**校准**：只在特定基准成立（无 GC 压力的密集数值循环，对照组是未优化的 JS）。**V8 充分预热、类型稳定的 monomorphic 热循环下，JavaScript 可以逼近 Wasm，差距常在 1–2 倍以内。**

但有一件事是 Wasm 稳赢的，而且它比平均性能更值钱——**性能可预测性**。JS 会偶尔因 GC 或去优化卡住 30 毫秒；Wasm 的曲线是平的。**这在音频（2.9 毫秒硬时限）与游戏循环（16.6 毫秒预算）里是决定性的。** → 第 4 章

### Q6. 「Wasm 比 Docker 快 100 倍」？

**校准**：**指冷启动时可信**（微秒 vs. 数十毫秒到数秒）。**指稳态运行性能则是错的**——容器里跑的是真正的原生二进位，Wasm 是编译过的中介表示，**运行性能低于容器内的原生代码**。 → 第 4 章

### Q7. 附录 D–F 那些「快 N 倍」的数字可信吗？

**校准**：**信其方向，疑其倍率。** 这些全部是原始对话的宣称值，本书未独立验证。方向（Wasm 在密集运算上胜过纯 JS）是可信的；具体倍数（15 倍、40 倍、55 倍）应视为量级提示而非量测结果。 → 附录 D、E、F 开头说明

## 三、关于安全

### Q8. 「Wasm 是内存安全的」——所以我的 C 程序在里面就安全了？

**校准**：**这是本书最重要的一次澄清。** 「Wasm 内存安全」只在**沙盒边界**的意义上成立——它保证「Wasm 模块伤不到宿主」，**不保证你用 C 写的程序在里面没有内存错误**。

而且情况更微妙：因为线性内存是一整块平坦的 `ArrayBuffer`，**传统原生平台的缓解措施（ASLR、NX、stack canary）在 Wasm 里多半不存在**。一个在 x86 上会被 ASLR 挡下的缓冲区溢出，在 Wasm 里可能稳定可利用——只是破坏范围被限制在该模块的线性内存内。学术界对此有明确讨论（"Everything Old is New Again: Binary Security of WebAssembly", USENIX Security 2020）。

**沙盒安全 ≠ 应用安全。** 实务对策：用 `-fsanitize=address` / `-fsanitize=undefined` 建置测试版本。 → 第 2 章、第 3 章

### Q9. 「Wasm 是不可逆的二进位转译」？

**校准**：**错误。** Wasm 的二进位格式**完全公开且结构化**，反汇编回 WAT 是无损的、机械的、有现成工具的（`wasm2wat`、`wasm-objdump -d`、`wasm-decompile`、Ghidra 的 Wasm 加载器）——这比逆向 x86 机器码**容易得多**（x86 还有变长指令、数据与代码混杂、间接跳转表，Wasm 全都没有）。

准确的说法是：**Wasm 隐藏的是「原代码的语义层」（类型、命名、抽象），不是「程序的行为层」。混淆擡高的是成本，不是可能性。**

**还有一个常被忽略的点**：Export 段是**规范强制**的，永远无法剥离——攻击者一定看得到你导出了哪些函数、签章是什么。 → 第 9 章

### Q10. 加密 / 编码 / 切段能保护硬编码的密钥吗？

**校准**：**全部无效。**

| 手法 | 为什么没用 |
|---|---|
| Base64 编码 | `strings` 抓不到，但 `base64 -d` 一秒还原，解码函数就在旁边 |
| 切成几段拼接 | 拼接代码就在二进位里，动态运行一次就吐出来 |
| XOR 加密 | 密钥的密钥也在二进位里（白盒密码学的根本困境） |
| 「没人会逆向我的小项目」 | 自动化扫描仪每天在爬公开托管，不挑对象 |

**唯一正解：密钥永远不进客户端。** 前端向自己的后端要短期、限定范围的 token。**Wasm 不会让一个本来就错的架构变对。** → 第 9 章

### Q11. 「用 Wasm 所以是恒定时间（constant-time），可防侧信道」？

**校准**：**错误。** Wasm 规范本身**不保证**恒定时间。它保证的是「不会有 JS 引擎那种依数据类型动态切换内部表示（V8 的 Smi → HeapNumber）的行为」，但**编译器仍可能引入分支、CPU 仍可能有数据相关的缓存行为**。

恒定时间是由**原代码的写法**保证的（避免依私钥分支、避免依私钥索引查表），Wasm 只是提供了一个比 JS 更可控的运行基底。 → 附录 F 案例 73

### Q12. 静态托管 + Git 签章 = 高安全性？

**校准**：方向对，但有三个但书：

1. **帐号安全才是真正的边界**——攻击者若取得你的 GitHub 帐号或 PAT，一样可以推 commit。请开双因素验证与分支保护。
2. **供应链风险依然存在**——建置流程若引入被投毒的套件，产出的 `.wasm` 本身就是恶意的，而它同样有漂亮的 commit 纪录。
3. **「用户可以检验每一行 Wasm」在实务上几乎没人做**——**透明性提供的是「可被稽核」，不是「已被稽核」**。这两者的差距，就是大多数安全事故发生的地方。 → 第 9 章

### Q13. 客户端做内存哈希校验能防破解吗？

**校准**：**技术上站不住。** 客户端的任何自我校验都可以被本地修改绕过——这是「客户端不可信」这条资安铁律的直接推论。真正有效的是**服务器端的授权判断**（这个 token 属于哪个帐号、有没有付费、有没有这份文件的权限），而不是客户端的自证清白。 → 第 10 章

## 三之二、关于规范版本（本书修订时添加）

### Q13b. Wasm 3.0 之后，哪些常见说法过时了？

**校准**：**2025 年 9 月，WebAssembly 3.0 宣布完成并成为现行标准**，一次把九项特性收进内核规范：**WasmGC、Memory64、例外处理、尾调用、128 比特 SIMD、多重内存、具类型的函数参考、扩充常数表达式、分支提示**。

**于是这几句话都过时了**：

| 过时说法 | 现况 |
|---|---|
| 「Wasm GC 还是提案／实验性」 | **已是内核规范**（Wasm 3.0） |
| 「memory64 提案还没定案」 | **已是内核规范**；但**性能代价依然存在**（失去保护页的免费界检查） |
| 「C++ 例外只能靠 JS 蹦床」 | **已有原生例外处理**：Tag 区段（id 13）+ `try_table` / `exnref` |
| 「函数式语言在 Wasm 上一定爆栈」 | **已有 `return_call` 尾调用** |
| 「一个模块只能有一块线性内存」 | **多重内存已标准化**——这是绕开 4GiB 的第四条路，且**保留了保护页的免费界检查**（附录 M §8） |

**但要区分两件事**：**规范标准化 ≠ 你今天就能用。** 引擎支持大致跟上了，**工具链往往落后**——多数 C/C++/Rust 工具链默认仍假设「只有一块内存」。**「规范状态」与「我今天能不能用」必须分开问。** → 附录 A、附录 M

### Q13c. 同步的 C 代码真的可以等一个 Promise 了吗？

**校准**：**可以，这就是 JSPI（JavaScript Promise Integration）。** 它在 **2025 年 4 月进入 Phase 4（标准化）**，并已于 **Chrome 137、Firefox 139** 出货。机制是**引擎把整条 Wasm 运行堆栈挂起**，Promise 解决后再从挂起处恢复——从 Wasm 那一侧看就是一次普通的同步调用。

**但三个代价必须知道**：**（一）** 挂起／恢复的成本与堆栈深度相关，**不能放进热循环**；**（二）** **它解决的是「等待」不是「并行」**——你依然只有一条线程；**（三）** **重入问题**：挂起期间 JS 可能再次调用同一个实例的导出函数，而绝大多数 C 代码假设「同时只有一个调用在跑」，这会造成状态损坏，需要自己加重入锁。

**它取代的是 Asyncify**（Binaryen 对整个模块做二进位改写来仿真挂起）——后者体积膨胀显著、需要手动标注会 unwind 的函数。**迁移策略：侦测 `typeof WebAssembly.Suspending === "function"`，有就用 JSPI，没有就退回 Asyncify 建置。** → 第 3 章墙七、附录 M §5

### Q13d. 在 GitHub Pages 上跑持久化 SQLite，一定要处理 COOP/COEP 吗？

**校准**：**不一定，而这是本书修订时最有实务价值的一次更正。**

官方 SQLite-Wasm 提供**两种** OPFS VFS：

- **`opfs`（第一代）**：主线程与 OPFS 之间用异步代理，靠 `Atomics.wait` 把异步变同步 → **需要 `SharedArrayBuffer`，因此需要跨来源隔离**。
- **`opfs-sahpool`**：直接持有一组预先开好的 sync access handle，在 Worker 内同步读写 → **不需要 COOP/COEP，而且是官方文档里最快的选项**；代价是**不支持同时多个连接**。主流浏览器自 2023 年 3 月起大致可用。

**官方建议也正是如此**：重视性能胜于并发、或无法设置 COOP/COEP 的客户端，应该用 `opfs-sahpool`。

> **通用教训**：当你正要为某个平台限制付出高昂的架构代价时，**先确认你依赖的函数库有没有一条不需要那个限制的路径。** 很多团队为了 `SharedArrayBuffer` 跟隔离搏斗了两周，而他们要的东西其实有第二个后端。 → 第 5 章、第 7 章

## 四、关于限制

### Q14. wasm64 出来就没有 4GB 问题了？

**校准**：**要付代价。** wasm32 的界检查之所以在热路径上是零指令，靠的是「引擎保留 8GiB 虚拟地址空间 + 保护页，由 MMU 免费完成检查」。**一旦地址变成 64 比特，你不可能为每块内存保留 2⁶⁴ 的虚拟空间**，保护页技巧失效，必须退回显式比较与分支，带来实质的性能回退。

**正确的心智模型**：4GiB 以下享受的是硬件补贴的免费安全，越过那条线之后安全就要开始收费了。**能靠分块串流在 4GiB 以内解决的，就别急着跳 wasm64。** → 第 2 章、第 8 章

### Q15. 「打开 Wasm GC 能让文件体积砍 80%」？

**校准**：**方向正确，但只对「原本要打包整个语言运行期」的语言成立**（Java、Kotlin、Dart 等）。**对 Rust、C、C++ 而言，打开 Wasm GC 几乎没有体积效益**——它们的对象本来就配置在线性内存里，根本没有 GC 可以省。把这条建议无差别套用到所有语言，是很常见的误读。 → 第 8 章

### Q16. `coi-serviceworker` 是不是在钻安全漏洞？

**校准**：**不是。** 它是对规范的**正确使用**——Service Worker 是由同源页面自己注册的代理层，只能拦截自己 scope 内的请求。它没有绕过浏览器的安全模型，而是**在页面自己的权限范围内声明「我自愿进入隔离状态」**，而隔离的代价（失去跨来源资源）也由这个页面自己承担。

**但有两点值得长期警惕**：（一）规范没有明文承诺「Service Worker 合成的 COOP/COEP 必须与服务器发出的等效」——这是各家实作对规范的自然推论，而依赖「多规范交集处的推论行为」存在被收紧的风险。（二）它揭示了一个结构性事实：**免费托管不给你的往往不是你当下需要的东西，而是你两年后才会需要的那个控制权**。 → 第 5 章

### Q17. WebContainers 真的在浏览器里跑了一台服务器？

**校准**：**技术上是真的，但边界要说清楚。** 它不是把 Node.js 的 C++ 原代码原封不动编译成 Wasm，而是**重新实作了一套运行在 Wasm 上、与 Node.js API 兼容的运行期**，并用 Service Worker 拦截网络请求来仿真服务器行为。

**精确版本**：「在浏览器里仿真出一个对本页面而言行为一致的服务器」。**外部互联网上的其他人无法通过网址连进这台『服务器』**——除非再配上 P2P 穿透。 → 第 5 章、附录 E 案例 60

## 五、关于那份「120 个案例」

### Q18. 那 120 个案例都是真的项目吗？

**校准**：**不是，而且要分三层看。**

- **首先，120 条里有 19 条是重复的**（26–30 重述 21–25；32–35 重述 21–24；61–65 重述 46–50；66–70 重述 36–40）。**实际不重复者为 101 条。**
- **其次，101 条分三个真伪等级**：🟢 可查证（约四成）、🟡 上游真实但 Wasm 移植待考（约四成）、🔴 示意性构造（约两成）。
- **最后，正确的读法是把它当「可行性地图」而不是「项目索引」。** 🔴 条目描述的技术路径几乎都成立，只是还没有人做，或做了但不叫这个名字（案例 66 之于 DuckDB-Wasm、案例 70 之于 OpenCV.js 就是最好的例子）。 → 第 6 章、附录 D–F

### Q19. 为什么会重复？这说明了什么？

**校准**：这是长对话生成的一个具体失效模式——**当生成端没有一份外部维护的「已产出清单」时，去重只能依赖对话上下文，而上下文一旦超出有效注意范围，去重就会失效。**

有趣的是原始对话里用户的应对演化：先是「请给我跟前面不重复的」（无效）→「你重复了」（无效）→ 最后改成指定新的类别维度（「应用类别：网络、游戏、ERP、server、开源 port」「软件引擎、物理引擎、世界引擎、LLM 引擎、图形引擎」）**——这一招有效。**

**教训：约束搜索空间，比要求记忆更有效。** → 第 6 章

### Q19b. FluffOS 真的把一整台 MUD 服务器跑进浏览器了吗？

**校准**：**是，而且这是本书少数几个可以逐条查证的重量级案例。** FluffOS 官方 README 明列 WebAssembly 为建置目标之一，`src/wasm/README.md` 完整记载了架构（宿主驱动的 `fluffos_tick()` 事件循环、Transport 抽象与 JS 桥接、七个导出入口、MEMFS + `file_packager` 打包）。官方原话是「整个驱动器跑在一个浏览器分页里：编译器、虚拟机、efuns、telnet」。

**但要准确理解三个边界**：**（一）** 它是**单机**的——没有 BSD socket、DNS 桩化回传 `127.0.0.1`，**别人无法通过网络连进你浏览器里的那台服务器**（与 Q17 的 WebContainers 是同一件事）。**（二）** **目前写入只在分页 session 内有效**（MEMFS 挥发），IDBFS/OPFS 覆盖层仍在 roadmap。**（三）** 没有 eval limit，**无穷的 LPC 循环会卡死整个分页**。

**收录数量会移动**：仓库 README 记载 200 份 mudlib／158 个 codebase／79 个已验证 WASM 可玩，而在线典藏站当时列出的数字与此不完全一致。**这类统计每次修复推进都会变，请以你造访当下的状态为准。** → 附录 L

### Q20. Penpot 是基于 Wasm 的吗？

**校准**：**Penpot 确实存在且是真实的开源设计协作工具**，可以合理地当作「开源替代品正在成熟」的证据。但把它描述为「基于 Wasm」**并不准确**——它的技术栈以 ClojureScript/SVG 为主。

**这类细节上的滑移在技术叙事里很常见，而它会误导架构决策。** 准确的说法是：开源替代品确实存在且在成熟，但它们的技术路径未必与商业产品相同。 → 第 11 章

## 六、关于商业与护城河

### Q21. Figma 的架构描述有多可信？

**校准**：**部分基于 Figma 公开的工程博客**（Wasm 迁移、多人协作、渲染管线等主题确有官方文章），**部分属于依技术逻辑的合理推论**（例如「所有 UI 文本都动态串流」「后端会做二进位特征匹配」这类具体实作细节，Figma 未公开证实）。

「矢量网格（Vector Networks）」确为 Figma 公开宣传的内核技术特色，但其具体算法未公开。

**请把第 10 章读成一个架构模式的范例，而不是 Figma 内部设计的权威描述。** → 第 10 章

### Q22. 「数据引力」是自然形成的吗？

**校准**：**很大一部分是设计选择的结果，不是数据量的自然结果。** 数据引力的强度**与数据的可携性成反比**：

- 格式开放、有完整导出 API、有第三方能导入 → 引力弱。
- 专有格式、导出有损、没有第二个目的地 → 引力强。

**所以「数据引力」在实务上，很大程度是「格式与 API 的设计选择」的产物。** 这一点对创建者与采购者同样重要——创建者知道怎么造，采购者也就知道怎么不掉进去。 → 第 12 章

### Q23. P2P 真的能让协作「免服务器」吗？

**校准**：**「大部分时候免服务器」。** 四个工程现实常被跳过：

1. **NAT 穿透成功率不是 100%**——对称型 NAT 下必须退回 **TURN 中继**，而 TURN 服务器要付钱、要带宽、要维运。
2. **脱机与异步协作**——「我周五改完，你周一才打开」需要一个永远在线的节点，那就是服务器，只是换了名字。
3. **谁是真实来源**——企业要的是权威版本、稽核纪录、访问控制、离职员工权限撤销。**P2P 天生弱于权限撤销**（数据已经在对方机器上了）。
4. **合规**——「数据分散在每个员工的浏览器里」不是一个能通过审计的答案。 → 第 11 章

### Q24. 「Token 便宜了，自己造轮子只是需要时间」——这个推论对吗？

**校准**：**推论本身是对的，但漏算了两笔帐。**

- **时间陷阱**：软件工程的定律是「写代码占 20%，Debug 与边界条件占 80%」，而 **AI 只让前者归零**。你省下的是那 20%。
- **维护熵增**：两年后 W3C 废弃了一个你依赖的 API，而**没有人真正读懂过那十万行**。你必须重新请 AI 理解这堆「旧轮子」，甚至打掉重练。

**更精确的形变描述**：AI 让「产出代码的速度远超过理解代码的速度」，于是**「没有人真正读懂的代码」以前所未有的速度累积**——而系统的可维护性取决于后者，不是前者。 → 第 12 章

### Q25. 那到底该不该自己造？

**校准**：分两种人。**独立个体与小团队**造微型轮子是划算的（规模小、需求稳定、坏了自己修）；**现代工业与大企业**付钱给供应商是划算的（把技术熵增外包出去，时间花在内核业务上）。

**中间那一层——平庸、功能单一的轻量级 SaaS——会被消灭。**

而判断自己该不该造，只需要一条检验：**「三年后这东西坏在半夜，谁会修它，他还在不在公司？」** 这个问题没有清晰答案之前，**你造的不是轮子，是债。** → 第 12 章
