# 第4章　竞品全景：JavaScript、Docker、V8 Isolates、EVM、WebGPU 与原生

> 「Wasm 的竞争对手是谁？」这个问题没有单一答案，因为 **Wasm 在六个完全不同的战场上，面对六个完全不同的对手**。在浏览器里它跟 JavaScript 分工；在云原生它跟容器争夺隔离边界；在边缘它跟 V8 Isolates 抢冷启动；在区块链它跟 EVM 争虚拟机的话语权；在密集运算上它跟 **WebGPU** 分工；而在所有这些之外，还有一个最根本的对手——**干脆别做网页**。**赢法不一样，输法也不一样。**

## 情境 1　浏览器战场：Wasm vs. 纯 JavaScript

**背景**：这是最常被误解的一组对比，因为它根本不是对立关系。

**分工的物理基础**：

| 面向 | JavaScript | WebAssembly |
|---|---|---|
| 类型 | 动态，运行期推断 | 静态，加载时验证 |
| 内存 | 垃圾回收的对象堆 | 手动管理的线性内存 |
| 启动 | 解析 → 解译 → JIT 预热（性能随运行次数爬升） | 解析 → 直接编译（性能从第一次调用就稳定） |
| 性能可预测性 | 差（去优化、GC 暂停、隐藏类别转换都会造成尖峰） | **好**（无 GC 暂停、无去优化，适合即时场景） |
| DOM / 浏览器 API | 原生、零成本 | 必须经 JS 桥接 |
| 字符串与对象 | 极强 | 极弱（要手动编解码） |
| 适合的工作 | UI 交互、事件处理、业务逻辑、数据拼装 | 3D 渲染、影音编解码、加解密、大矩阵运算、解析器 |

**「性能可预测性」比「平均性能」更值钱**：这一点在游戏、音频与即时交互场景是决定性的。JavaScript 的平均性能其实很好，但它会**偶尔**因为 GC 暂停或去优化而卡住 30 毫秒——对一个要求每帧 16.6 毫秒的游戏循环，这就是一次可见的掉帧。Wasm 的性能曲线是平的。**AudioWorklet 里跑 Wasm 几乎成了业界惯例，正是因为音频线程容不下任何一次不可预测的暂停。**

**什么时候「纯 JS 反而更快」**：

- 工作负载小于跨界开销（例如每次只算一个像素、只比对一个字符串）。
- 大量字符串处理——V8 的字符串实作（rope、内部化、slice 共享）极度优化，而 Wasm 要付编解码税。
- 大量 DOM 操作——每一次都要绕 JS，Wasm 纯亏。
- 冷启动极度敏感、且计算量不大的场景——那 500KB 模块的下载与编译永远赚不回来。

> ⚠️ 真伪提醒
> 常见宣称「Wasm 比 JavaScript 快 10~30 倍」。这种倍数**只在特定形状的基准上成立**（无 GC 压力的密集数值循环、对照组是未优化的 JS 实作）。在 V8 充分预热、且代码是类型稳定的 monomorphic 热循环时，**JavaScript 可以逼近 Wasm 的性能，差距常在 1~2 倍以内**。附录 D–F 的一百零一个案例里出现的所有「快 N 倍」数字，都应以此标准阅读：**信其方向，疑其倍率。**

> 💡 君之一席话
> 与君一席话：**在工程里，「平均值更好」常常输给「最坏情况更好」。** JavaScript 的平均性能不输 Wasm 多少，但它的 P99 会被 GC 打穿；Wasm 的平均性能未必碾压，但它的 P99 是平的。用户感受到的从来不是平均值——**他们感受到的是那一次卡顿、那一次爆音、那一次掉帧。** 这条原理在系统设计里叫「尾延迟（tail latency）」，而它解释了一大堆看似不理性的技术选择：为什么交易系统宁可用没有 GC 的语言、为什么数据库愿意牺牲吞吐去换 P99、为什么即时音频宁可用 Wasm 也不用已经够快的 JS。**当你在做选型时，先问清楚这个系统是被平均值评价的，还是被最坏情况评价的——这两者要的技术完全不同。**

## 情境 2　云原生战场：Wasm + WASI vs. Docker / 容器

**背景**：这一组对比最常被夸张成「Wasm 将取代 Docker」，而真相要有趣得多——**它们隔离的根本不是同一层东西。**

**隔离边界的层级差异**（这是理解一切差异的钥匙）：

```
容器（OCI / Docker）：
  ┌───────────────────────────────────────┐
  │ 你的程序 + 完整的用户空间             │  ← 隔离的是「一整个操作系统发行版」
  │ (glibc, coreutils, /etc, 套件管理…)    │
  ├───────────────────────────────────────┤
  │ namespace + cgroup + seccomp + capabilities │  ← 靠 Linux 内核提供隔离
  ├───────────────────────────────────────┤
  │           共用的宿主内核                │  ← 攻击面：整个 syscall 接口
  └───────────────────────────────────────┘

Wasm + WASI：
  ┌───────────────────────────────────────┐
  │ 你的程序（编译成 Wasm）                 │  ← 隔离的是「单一应用」
  ├───────────────────────────────────────┤
  │ Wasm 运行期（内存安全的虚拟机）        │  ← 靠类型系统与验证器提供隔离
  ├───────────────────────────────────────┤
  │ WASI 能力接口（宿主明确授予的那几样）     │  ← 攻击面：你 import 的那几个函数
  └───────────────────────────────────────┘
```

**逐项对照**：

| 面向 | 容器 | Wasm + WASI | 谁赢 |
|---|---|---|---|
| 冷启动 | 数十毫秒 ~ 数秒 | 微秒 ~ 数毫秒 | **Wasm，且是量级差距** |
| 映像/模块体积 | 数十 ~ 数百 MB | 数十 KB ~ 数 MB | **Wasm** |
| 内存足迹 | 每实例数十 MB 起 | 每实例数百 KB ~ 数 MB | **Wasm** |
| 跨 CPU 架构 | 每架构各出一版 | 单一 `.wasm` 通吃 | **Wasm** |
| 攻击面 | 整个 syscall 接口 | 显式 import 的那几个函数 | **Wasm**（但运行期本身也可能有洞） |
| 能跑既有软件 | **任何 Linux 二进位** | 只有重新编译过的 | **容器，且是决定性的** |
| 生态成熟度 | 十年以上，工具链完备 | 仍在演进（WASI 0.2 迁移中） | **容器** |
| 多线程 / 网络 | 完整 | 逐步补齐中 | **容器** |
| 可观测性 | 完整（strace、perf、eBPF…） | 相对贫乏 | **容器** |

**「速度快 100 倍」这句话该怎么读**：如果指的是**冷启动**，这个量级是可信的（微秒 vs. 数十毫秒）。如果指的是**运行性能**，那是错的——**Wasm 的运行性能低于容器内的原生代码**，因为容器里跑的是真正的原生二进位，而 Wasm 是编译过的中介表示。

> ⚠️ 真伪提醒
> 「Wasm 比 Docker 快 100 倍且极轻量」这类说法在市场材料里很常见。**准确的说法是：Wasm 的冷启动与内存足迹比容器好一到数个量级，但稳态运行性能通常不如容器内的原生代码。** 这个差异决定了适用场景：**Wasm 赢在「大量、短命、突发」的函数（Serverless、边缘、多租户插件），容器赢在「长期运行、依赖既有生态」的服务。** 把两者当成非此即彼的替代关系，是对这项技术最常见的误用。

**Wasm 在后端真正的杀手级场景**，是那些容器**做不到**的事：

1. **多租户插件系统**：让客户上传自己的代码跑在你的服务里。用容器你要为每个客户起一个容器（重、慢、贵）；用 Wasm 你可以在同一个进程里跑上千个互不信任的模块，每个都有独立的线性内存与能力边界。Envoy、Istio、Shopify Functions、Redpanda 的数据转换都走这条路。
2. **边缘运算的极端冷启动要求**：边缘节点没有本地流量，几乎每次请求都是冷启动。容器的数十毫秒在这里是不可接受的。
3. **一次编译到处部署**：同一个 `.wasm` 跑在 x86 服务器、ARM 边缘设备与浏览器上。

> 🔍 进阶点评──「不能跑既有二进位」这一条，才是胜负手
> 表格里 Wasm 赢了七项、输了四项，看起来优势明显。但那四项里有一项的权重压过其他全部：**Wasm 只能跑重新编译过的东西。** 这句话的实际含义是——**你的公司过去十年累积的所有 Python 脚本、Java 服务、Node.js 应用、以及那个没人敢动的祖传 PHP，一个都搬不过去，除非有人重写或至少重新编译它们。** 容器的历史性胜利从来不是因为技术优雅（cgroup + namespace 称不上优雅），而是因为它提供了一条**零重写的迁移路径**：`FROM ubuntu:22.04`，把你的烂摊子原封不动装进去，明天就能上 Kubernetes。这就是为什么「Wasm 取代 Docker」的叙事在 2019 年喊到 2026 年，市占率依然悬殊。**技术的采用曲线由迁移成本决定，不由技术优越性决定。** 而这也预告了 Wasm 在后端真正的成长路径：它不会从既有服务手上抢市场，它会在**那些容器天生不适合的新场景**（多租户插件、极致冷启动、跨架构边缘）长出自己的地盘，然后慢慢往中间扩。**看一项基础设施技术的未来，别看它能不能赢过在位者，看它有没有一块在位者结构上进不去的地方。**

## 情境 3　边缘战场：Wasm vs. V8 Isolates

**背景**：这是六场竞争里最贴身的一场，因为对手用的是同一颗引擎。

**V8 Isolate 是什么**：Cloudflare Workers 的内核思路——不为每个租户起一个进程或容器，而是在**同一个 V8 进程里**开一个个 `Isolate`（V8 的隔离运行环境，各有独立的堆积与全域对象）。冷启动可以压到 5 毫秒以下，内存足迹只有几 MB。

**两者的对比**：

| 面向 | V8 Isolates | Wasm 模块 |
|---|---|---|
| 冷启动 | 极快（~5ms 或更低） | 极快（微秒 ~ 毫秒级） |
| 支持语言 | **只有 JS / TypeScript** | 几十种可编译到 Wasm 的语言 |
| 内存足迹 | 较低（共用 V8 的内置对象与代码） | 每实例要自己的线性内存 |
| 隔离强度 | 依赖 V8 自身的安全性（历史上 V8 有大量 CVE） | 额外一层规范级的类型与内存隔离 |
| 生态 | npm，极其庞大 | 各语言自己的生态，跨语言集成仍在发展 |

**现实是它们已经合流了**：Cloudflare Workers **同时支持**在 Isolate 里运行 Wasm 模块。Fastly 的 Compute@Edge 则直接以 Wasm（Lucet/Wasmtime 系）为内核。**所以正确的问题不是「选哪个」，而是「你的逻辑用什么语言写」**——JS/TS 就走 Isolate，Rust/Go/C++ 就编成 Wasm 塞进去。

> 💡 君之一席话
> 与君一席话：**当两项首席技术官期并存且互相嵌套时，说明它们解决的不是同一个问题——只是市场一开始把它们放在同一个货架上。** Isolate 解决的是「如何在同一个 JS 引擎里安全地多租户」，Wasm 解决的是「如何让非 JS 语言安全地跑在任何地方」。它们看起来竞争，是因为在「边缘 Serverless」这个具体产品形态上恰好撞在一起。**每当你看到两项技术被拿来对比，先去找它们各自最擅长、对方完全做不到的那件事——那件事才是它们真正的定义。** 用同一组指针比较两个定义不同的东西，是技术评估里最常见的逻辑错误。

## 情境 4　区块链战场：eWasm vs. EVM

**背景**：这是六场里最「政治」的一场，因为它牵涉的不只是技术，还有已经锁在链上的数千亿美元资产。

**EVM（以太坊虚拟机）的问题**：

- **256 比特字长**。EVM 的原生字长是 256 比特，因为它为密码学哈希而设计。但这意味着**每一次加法都要在 64 比特的实体 CPU 上仿真成多次运算**，对非密码学的一般计算是巨大的浪费。
- **工具链封闭**。你基本上只能用 Solidity 或 Vyper，编译器、调试器、分析器都得从零打造。
- **运行性能低**。它是为「可验证的确定性」而不是为速度设计的。

**Wasm 作为智能合约虚拟机的优势**：

- **成熟的多语言工具链**：Rust、C++、AssemblyScript 都能写合约，且能直接复用既有的编译器优化、调试器、fuzzing 工具。
- **运行效率高一到数个量级**（对非密码学运算而言）。
- **规格已由四大浏览器实作验证过**，不必自己维护一台虚拟机的规范。

**Wasm 在链上的致命难题**（这是市场材料通常不讲的）：

1. **确定性（determinism）**。区块链要求所有节点对同一笔交易算出**完全相同**的结果。而 Wasm 规范里有若干**非确定性**的角落：浮点数的 NaN 比特模式在不同实作上可能不同、SIMD 的某些操作、`memory.grow` 失败的时机取决于宿主资源。**链上 Wasm 必须先定义一个「确定性子集」**（通常直接禁用浮点数），这是所有 Wasm 链的第一项工程。
2. **计量（metering / gas）**。EVM 的每条指令都有明码标价的 gas 成本。Wasm 没有这个概念，必须靠**指令插桩（instrumentation）**——在编译后的模块里自动插入计数代码——来实现，而这会带来 10~50% 不等的性能损失，直接吃掉一部分速度优势。
3. **生态惯性**。以太坊主网上锁着的资产、部署的合约、审计过的程序库，全部是 EVM 比特码。**迁移的协调成本是天文数字。**

**现实走向**：eWasm 作为以太坊 1.x 的运行层替代方案已实质搁置（以太坊的路线图转向了 EOF 与其他方向）；但 Wasm 在**其他链**上大获成功——Polkadot 的 runtime 本身就是 Wasm（可热升级）、NEAR、Cosmos 的 CosmWasm、Internet Computer 全都以 Wasm 为运行环境。

> 🔍 进阶点评──「计量」这件事，暴露了通用虚拟机做特化用途的根本张力
> Gas 计量的实作困难不是工程细节，它是一个范式冲突的征状，值得单独拆开。**EVM 从第一天就把「每条指令要收多少钱」写进了规范**，因为它的存在目的就是在不信任的环境里运行不信任的代码，并且要能停下来收钱。**Wasm 从第一天就把计量排除在规范之外**，因为它的存在目的是「尽可能快地运行已被验证安全的代码」，而任何计量都是纯开销。于是把 Wasm 拿去当合约虚拟机的人，必须在编译后的模块里插桩——这件事有三个连锁后果：**其一**，插桩后的模块跟原始模块不是同一个东西，你的优化器可能把插桩指令优化掉，于是计量与优化互相打架；**其二**，插桩的粒度决定了计量的精确度与开销的权衡（每条指令都计太贵，每个基本区块计一次又可能被无限循环钻空子）；**其三**，不同链的插桩策略不同，于是「同一份 Wasm 在不同链上的 gas 消耗不同」，可携性的承诺被打了折。**这个案例的通用启示是：当你把一个为「速度」设计的通用底层，拿去解决一个需要「可计量、可中断、可审计」的问题时，你补上去的那一层，往往会吃掉你当初选择它的理由。** 选型时要问的不是「这个底层够不够快」，而是——**我要加上去的那些东西，会不会把它变回一个平庸的方案？**

## 情境 5　密集运算战场：Wasm vs. WebGPU

**背景**：这是六个对手里最新、也最容易被误判的一个——因为它在 2026 年才真正成为「所有人都能用」的选项。

**WebGPU 的状态变了**：它在 **2026 年 1 月达成主流浏览器全面出货**（Chrome 自 113 起、Firefox 141 起于 Windows、145 扩及 Apple Silicon 的 macOS、Safari 26.0 涵盖 macOS/iOS/iPadOS/visionOS）。**这意味着「浏览器里的密集运算」第一次有了两个都可以认真考虑的选项，而不是一个。**

**它们的本质差异，不在快慢，在平行度的形状**：

| | **Wasm（+SIMD +threads）** | **WebGPU（compute shader）** |
|---|---|---|
| 硬件 | CPU | **GPU** |
| 平行模型 | 少量粗粒度线程（≈ 内核数） | **数千条细粒度线程**（SIMT） |
| 矢量宽度 | **固定 128 比特** | 由硬件决定，远宽 |
| 分支发散 | 便宜 | **昂贵**（同一个 warp 走不同分支 = 串行化） |
| 随机内存访问 | 便宜（有大缓存） | **昂贵**（要 coalesced 访问才快） |
| 递归 / 复杂控制流 | 自然 | **WGSL 不支持递归**，动态控制流受限 |
| 精度 | `f32`/`f64` 完整 | `f32` 为主，`f64` 支持有限或没有 |
| 启动延迟 | 毫秒级 | **需要取得 adapter/device、编译 shader、建 pipeline** |
| 数据回读 | 零拷贝（同一块内存） | **必须 `mapAsync` 回读，有可观延迟** |
| 可用性 | **几乎 100%** | ~70%（且行动端与驱动差异大） |
| 调试 | 难 | **更难** |

**于是分工的判准很清楚**：

```
你的运算是「同一个运算套用到几百万个独立元素」吗？
├─ 是，而且数据能留在 GPU 上连续处理好几步
│    → WebGPU（矩阵乘法、卷积、影像滤波、粒子、光线追踪）
│
├─ 是，但算完立刻要把结果拿回 CPU 做别的事
│    → ⚠️ 先量测回读延迟——它常常吃掉 GPU 省下的时间
│
└─ 否：有复杂分支、递归、随机访问、或需要 f64 精度
     → Wasm（解析器、压缩、数据库、仿真器、几何求解）
```

**真实世界的答案通常是「两个都要」**——而附录 D 的案例 4（ONNX Runtime Web）就是最好的例子：**它同时维护 WebGPU 后端与 Wasm 后端**，前者快，后者「在任何设备上都能跑」。**Wasm 在这里扮演的角色不是竞争者，是保底层（fallback）。**

> ⚠️ 真伪提醒
> 常见宣称「WebGPU 比 Wasm 快 10–100 倍」。**在合适的工作负载上这个量级可信**（大矩阵乘法、卷积），**但它省略了三笔帐**：**（一）** 启动成本——取得 device、编译 WGSL、建 pipeline，对短任务可能占绝大部分；**（二）** 回读成本——`mapAsync` 把结果搬回 CPU 的延迟；**（三）** 可用性成本——你必须为没有 WebGPU 的设备准备一条 Wasm 路径，于是你维护了两份实作。**「快 N 倍」讲的是稳态吞吐，而你的用户体验到的是端到端时间。**

> 💡 君之一席话
> 与君一席话：**当两项技术被放在同一张比较表上时，先确认它们平行的「颗粒」是不是同一种。** CPU 的平行是「几个聪明的工人各做各的」，GPU 的平行是「几千个工人同时做完全一样的动作」——**前者擅长判断，后者擅长重复。** 把需要判断的工作丢给 GPU，你会得到分支发散；把纯粹重复的工作留在 CPU，你会浪费掉几千倍的算力。这条原理远不只适用于 Wasm 与 WebGPU：线程池 vs. SIMD、批量处理 vs. 串流、微服务 vs. 单体——**每一组对比的真正差异，都在「工作被切开的方式」，而不在「谁比较快」。** 选错的代价不是慢一点，是你的工作形状跟工具的形状对不上，于是怎么优化都不对。

## 情境 6　最根本的对手：干脆别做网页

**背景**：这一节问一个整本书都默认了答案、却从没问出口的问题——**这件事真的该在浏览器里做吗？**

**因为如果不用浏览器，前面十几道墙有一半会直接消失**：没有 4GiB 上限、没有 COOP/COEP、没有跨界收费站、没有下载体积焦虑、可以开线程、可以直接碰文件系统与硬件、性能是 100% 而不是 60–90%。

**三个「不做网页」的具体形态**：

| 形态 | 是什么 | 相对 Wasm 的取舍 |
|---|---|---|
| **直接发原生二进位** | 就是一般的桌面程序 | 最快、无任何限制；**但零安装的优势完全消失**，且要为每个平台各出一版、签章、处理更新 |
| **Electron** | 打包一整个 Chromium + Node.js | 拿到完整的 Node 能力与文件系统；**代价是每个 App 一百多 MB 与可观的内存足迹** |
| **Tauri** | 用**系统内置的 WebView** 显示前端，后端是原生 Rust | 产物仅数 MB；前端仍是 Web 技术，**但重运算改由原生 Rust 跑——不需要编译成 Wasm，因此没有 4GiB 上限、没有跨界税、可以开线程** |

**Tauri 这一列特别值得停下来看**，因为它揭示了一件事：**很多人用 Wasm，其实是为了「用 Web 技术写 UI」，而不是为了「在浏览器里跑」。** 如果你的用户本来就要装一个 App，那把重运算编成 Wasm 是**纯亏**——你付了 Wasm 的所有代价，却没有换到它唯一的好处（零安装、免更新、跨平台单一产物）。

**于是判准只有一条**：

> **问「零安装」对这个产品值多少钱？**
>
> - **值很多**（一次性工具、分享链接就能用、企业不准装软件、需要被搜索引擎索引、要跑在别人的网站里）→ **浏览器 + Wasm，前面所有的墙都是必要之恶。**
> - **值不多**（用户本来就会装、要长时间使用、要碰本机大量文件、需要背景运行）→ **Tauri 或原生。你会省下这本书第二篇整整四章的麻烦。**

**两个常见的误判**：

1. **「反正都要写 Rust，那就编成 Wasm 一次搞定两边。」** 听起来漂亮，实际上 Wasm 版会被 4GiB、跨界税、缺线程拖着，而原生版一项都不会。**共用内核逻辑是对的，但要接受两边的能力边界不同。**
2. **「Electron 太肥，所以我用 Wasm。」** 这两件事不对位——Electron 的替代品是 Tauri，不是 Wasm。**如果你比较的是「App 体积」，Tauri 才是那个答案。**

> 🔍 进阶点评──六个对手排在一起，会浮现一条清楚的定位线
> 把这一章的六场竞争摊开，Wasm 的位置其实非常明确，而它跟大多数人的直觉不同。**Wasm 不是「更快的运行方式」，它是「在别人的地盘上，安全地运行你的代码」这件事的通用解。** 每一场竞争的胜负都印证这一点：**对 JavaScript** 它赢在「你可以带着既有的 C++ 资产进来」，不是赢在快；**对容器**它赢在「一个进程里跑上千个互不信任的租户」，不是赢在性能；**对 V8 Isolates** 它赢在「不限于 JS」；**对 EVM** 它赢在「工具链是现成的」；**对 WebGPU** 它根本不竞争，它是那个「任何设备都跑得动」的保底层；**对原生**它赢在「零安装」，而输掉其他一切。
> **六条连起来，Wasm 的定义就浮出来了：它是一种「可携的信任边界」。** 它的所有优势都来自「宿主可以放心运行它」，它的所有限制也都来自同一个原因。所以选型时真正该问的不是「Wasm 快不快」，而是——**我这段代码要跑在谁的地盘上，那个地主凭什么相信我？** 如果答案是「跑在我自己的机器上」，那你多半不需要 Wasm；如果答案是「跑在几百万个陌生人的浏览器里」「跑在同一个进程里的其他租户旁边」「跑在一条所有节点都必须算出同样结果的链上」——**那没有第二个选项。**

## 本章小结

- **六个战场，六种赢法**：浏览器里与 JS **分工**（Wasm 算、JS 画）；云原生与容器**错位竞争**（赢在冷启动与多租户，输在既有生态）；边缘与 V8 Isolates **已经合流**（Isolate 跑 JS，Wasm 跑其他语言）；区块链上**赢了性能、卡在确定性与生态惯性**；密集运算上与 **WebGPU 分工而非竞争**；而面对**原生**，它只赢一件事——**零安装**。
- 对 JS：**「性能可预测性」比「平均性能」更值钱**——Wasm 的曲线是平的，这在音频与游戏循环里是决定性的。但小工作负载、字符串密集、DOM 密集的场景，**纯 JS 反而更快**。
- 对容器：**Wasm 的冷启动与足迹赢一到数个量级，但稳态运行性能不如容器内的原生码**。而「不能跑既有二进位」这一条的权重压过其他所有优势——**技术的采用曲线由迁移成本决定，不由技术优越性决定**（见情境 2 🔍）。
- 对 EVM：Wasm 的速度与工具链优势是真的，但**gas 计量必须靠插桩补上，而插桩会吃掉一部分速度优势**——这是「通用底层做特化用途」的根本张力（见情境 4 🔍）。
- 对 WebGPU：**它们平行的「颗粒」不同**——CPU 是「几个聪明的工人各做各的」，GPU 是「几千个工人做完全一样的动作」。**Wasm 在浏览器 AI 推理里的角色是保底层而不是竞争者**（ONNX Runtime Web 同时维护两个后端就是证据）。注意「快 10–100 倍」省略了启动、回读与可用性三笔帐（见情境 5 ⚠️）。
- 对原生：**判准只有一条——「零安装」对这个产品值多少钱。** 值不多的话，Tauri 或原生会让你省下第二篇整整四章的麻烦。**注意 Electron 的替代品是 Tauri，不是 Wasm。**
- 所有「快 N 倍」的宣称都应以**对照组的形状**来读，包括本书附录里那一百零一个案例（见情境 1 ⚠️）。
- **六条连起来，Wasm 的定义就浮出来了：它是一种「可携的信任边界」。** 所有优势都来自「宿主可以放心运行它」，所有限制也来自同一个原因。选型时该问的不是「Wasm 快不快」，而是——**我这段代码要跑在谁的地盘上，那个地主凭什么相信我？**（见情境 6 🔍）
