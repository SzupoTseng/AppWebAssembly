## 一、影音与信号处理

### 1.（原 1）FFmpeg.wasm — 纯前端影音转码与剪辑　🟢

**痛点**：传统转码依赖服务器端（AWS MediaConvert 或自建 FFmpeg 集群），三大痛点：带宽与算力成本极高、隐私文件必须上传、无法脱机。

**原理**：以 Emscripten 将数百万行 C 语言的 FFmpeg 内核编译为 `ffmpeg.wasm`。采「主线程（UI）+ Web Worker（计算）」模型。JS 将视频以 `ArrayBuffer` 写入 Wasm 的虚拟文件系统 **MEMFS**；JS 调用导出的命令行接口（`ffmpeg -i input.mp4 output.avi`），Wasm 内部直接对内存中的比特流解码与编码；完成后从 MEMFS 读出，转为 Blob URL 供下载。

**性能**：宣称藉 SIMD 与多线程（`SharedArrayBuffer`）达到原生 C 的 **60%–80%**。

**优点**：极致隐私（数据不离端）、托管成本为零、支持几乎所有主流格式。
**缺点**：受浏览器内存限制（通常 2–4GB），无法处理数十 GB 的 4K 大档；首次加载需下载约 20–30MB 模块；多线程版**必须配置 COOP/COEP**，在 GitHub Pages 上需依赖 `coi-serviceworker`。

**竞品**：云端转码（算力无上限、费用高、有隐私风险）；纯 JS 影音库（video.js/jsmpeg，只能做简单播放与封装，无法承担 H.264/H.265 内核编解码）。

### 2.（原 2）Rust-uBlock — Wasm 广告拦截比对引擎　🟡

**痛点**：现代广告拦截器需对数万条网络请求即时比对数十万条过滤规则（EasyList）。纯 JS 做大量字符串比对与正则匹配会消耗大量 CPU，导致分页切换时的微小卡顿（jank）。

**原理**：内核比对逻辑以 Rust 撰写，经 `wasm-bindgen` 编译为 Wasm。采**规则树**结构：在线性内存中建构高度优化的字典树（Trie）与布隆过滤器（Bloom Filter）。拦截到请求时将 URL 传入 Wasm，于微秒内完成数十万条规则的二进位检索，回传允许/拦截的布尔值。

**性能**：宣称字符串比对与规则检索比纯 JS **快 3–5 倍**，内存占用稳定，完全避开 JS 频繁创建字符串对象引发的 GC 停顿。

**优点**：显著降低低配设备（手机浏览器）的 CPU 负载与耗电；规则库在线性内存中紧凑排列，碎片少。
**缺点**：JS↔Wasm 频繁传递 URL 字符串会产生边界转换开销（字符串编解码），必须设计精密的缓冲区共享机制。

**竞品**：纯 JS 拦截引擎（开发容易、生态成熟，但面对 50 万条以上规则时内存与 CPU 峰值明显较高）；浏览器原生声明式拦截（Manifest V3 的 `declarativeNetRequest`，性能最高但规则数受限、无法自订复杂逻辑）。

### 3.（原 3）v86 — 浏览器端 x86 硬件仿真器　🟢

**痛点**：要在网页上跑 Linux 或 Windows 95，传统做法是后端跑虚拟机（KVM）再以 VNC 串流画面——服务器成本高、延迟大、交互性差。

**原理**：CPU 仿真、内存管理与磁盘控制器（IDE）内核编译为 Wasm。Wasm 在线性内存中仿真 x86 的寄存器、物理内存与中断矢量表，并内含一个 **JIT 编译器，把 x86 机器码即时翻译成 Wasm 指令运行**（详见第 6 章情境 4）。画面输出时将 VRAM 数据拷出，由 JS 通过 Canvas/WebGL 渲染；键鼠事件由 JS 捕获后传入 Wasm 的中断处理进程。

**性能**：宣称在浏览器中运行 Linux 的速度接近早年 Pentium 等级，数秒内开机进入终端机，可流畅运行 Doom 等经典 3D 游戏。

**优点**：完全去中心化，GitHub Pages 只需托管映像档（如 10MB 的 Linux ISO）；开机状态可串行化导出为文件，随时存盘。
**缺点**：无法利用宿主的硬件虚拟化（Intel VT-x），纯软件仿真，因此**跑不动现代 64 比特重度操作系统**。

**竞品**：后端 Docker/VNC（性能好、兼容性佳，但成本随用户量线性暴涨，无法脱机）；纯 JS 仿真器（如早期 jor1k，因缺乏精确比特运算与紧凑内存，慢 10 倍以上，画面撕裂与音频卡顿）。

### 4.（原 4）ONNX Runtime Web (Wasm) — 前端 AI 推理引擎　🟢

**痛点**：网页端做人脸辨识、背景虚化、语音转文本时，传统作法是把数据传回后端 GPU——伴随隐私问题、GPU 成本与网络延迟。

**原理**：微软将开源的 ONNX Runtime 内核 C++ 编译为 Wasm。开发者把 `.onnx` 模型放在 GitHub Pages 上；JS 负责加载模型与多媒体输入（如 WebCam 影像），将影像矩阵传入 Wasm；Wasm 内部实作神经网络的矩阵乘法与激活函数。内核优化为 **Wasm SIMD** 硬件加速与 **Web Worker** 多核并行。

**性能**：宣称打开 SIMD 与多线程后，推理速度比纯 JS 神经网络**快 10–20 倍**；轻量模型（MobileNet、YOLOv8-nano）单次推理可缩至 30 毫秒内，达 30 FPS 即时分析。

**优点**：算力由用户浏览器分摊，静态托管即可拥有大规模并发的 AI 服务；脱机可用、数据安全。
**缺点**：大型模型（数百 MB 的 LLM 或 Stable Diffusion）下载时间过长；CPU 推理性能仍不如 WebGPU 加速。

**竞品**：TensorFlow.js（WebGL/WebGPU 模式在利用 GPU 上更有优势，但 ONNX Runtime Wasm 跨平台兼容性更稳健，是无良好 GPU 驱动设备上的保底方案）；后端 Python API（支持巨大模型，但高并发时成本高昂）。

### 5.（原 5）DuckDB-Wasm — 浏览器端分析型 SQL 数据库　🟢

**痛点**：网页要处理、分析、过滤数百万条大数据（CSV、Parquet、日志）时，全部加载 JS 内存会导致对象数量过多，引发 OOM 或长时间 GC 停顿。架设后端数据库对展示型 Dashboard 又过于沉重。

**原理**：把 DuckDB 这款嵌入式**字段式（columnar）SQL 数据库**的 C++ 内核完整编译为 Wasm。采**矢量化运行引擎**，大数据以串流方式读取，直接在线性内存中以紧凑的 Arrow 字段格式保存。用户输入标准 SQL，Wasm 内部的查找优化器在内存中高速并行扫描。**最漂亮的是远程读取**：原生支持对远程 Parquet/CSV 发 **HTTP Range Request**，只抓需要的字节区段（详见第 6 章情境 4）。

**性能**：宣称 1000 万行的聚合查找可在 **100–200 毫秒**内完成，比 JS 数组遍历（`Array.filter.reduce`）**快 60 倍以上**。

**优点**：让静态页直接创建强大的 BI 看板；无须下载整份文件即可查找远程数据。
**缺点**：数据默认在内存中，分页关闭即消失（可持久化到 OPFS/IndexedDB，但受配额限制）。

**竞品**：SQLite-Wasm（擅长事务型 OLTP，但百万级 OLAP 统计分析上字段式的 DuckDB 完胜）；纯 JS 数据处理库（Lodash、Crossfilter，百万级以上力不从心）。

### 6.（原 6）SQLite-Wasm — 网页端完整 ACID 关系型数据库　🟢

**痛点**：复杂前端应用（脱机笔记、记帐、PWA 邮件客户端）只能依赖 IndexedDB——异步事件驱动 API 写法繁琐，不支持多表 JOIN、预编译语句与强 ACID 事务。

**原理**：SQLite 官方将标准 C 原代码经 Emscripten 编译为 `sqlite3.wasm`。**最精妙的是持久化层（VFS）**：官方开发了专属的虚拟文件系统，利用 **OPFS（Origin Private File System）** 或 IndexedDB 作为底层保存媒介（机制详见第 7 章）。运行架构采 Web Worker 隔离：主线程通过 `postMessage` 发送 SQL，Worker 内的 Wasm 引擎操作内存中的 B-Tree 索引与数据页，并通过 VFS 同步写回。

**性能**：宣称在 OPFS 下单条插入与复杂 JOIN 几乎与本机原生无异，读写吞吐比 JS 封装的 IndexedDB **快 2–4 倍**，且保证崩溃安全（crash safety）。

**优点**：前端拥有完整标准 SQL 与事务支持；`.db` 档可直接打包下载，极易备份与搬移。
**缺点**：Wasm 加胶水约数百 KB；若浏览器不支持 OPFS，退回 IndexedDB 仿真 VFS 时写入性能大幅下滑。

**竞品**：原生 IndexedDB（免下载、无体积成本，但缺乏关联查找与事务能力）；后端数据库（支持海量数据与多租户，但有服务器成本，无极致脱机能力）。

### 7.（原 7）Pyodide — 浏览器端 Python 科学计算运行期　🟢

**痛点**：Python 是数据科学霸主（NumPy、Pandas、Matplotlib），但要在网页运行 Python 或创建交互教学平台，过去必须在后端架设 Jupyter Kernel——成本高昂，且大量并发时后端极易崩溃。

**原理**：将 CPython 内核与大量含 C 扩充的科学计算库（NumPy、Pandas、SciPy、scikit-learn）完整编译为 Wasm。**双向类型桥接**：JS 的 `Array` 可被 Python 当 `list`/`dict` 读取，反之亦然；Matplotlib 画出的图表能转成二进位流由 JS 渲染到 `<canvas>`。

**性能**：纯 Python 代码约为原生的 **1/3–1/5**（虚拟机里跑解译器，两层抽象）；但一旦调用 NumPy/Pandas 的 C 算子，矩阵运算逼近原生的 **70%**。

**优点**：真正零后端成本，完整数据科学环境跑在客户端；极适合交互式教学与数据可视化 Dashboard。
**缺点**：**初始加载是灾难性的**——CPython 加基础库动辄 30–50MB。缓解手段：按需加载套件（`micropip`）、Service Worker 持久缓存、或改用 MicroPython/Wasm。

**竞品**：Google Colab / 后端 JupyterHub（性能强、支持 GPU，但维运与扩展成本高）；Brython/Skulpt（纯 JS 的 Python 解译器，文件极小但只是语法仿真，**无法运行含 C 扩充的科学计算库**）。

### 8.（原 8）Canvas-GIMP / wasm-img — 高性能影像与滤镜处理　🟡

**痛点**：前端做高分辨率照片的像素级处理（模糊、锐化、色彩矩阵、边缘检测）时，用 JS 遍历数千万个 RGBA 像素会导致严重 GC 卡顿，单线程计算会让网页跳出「页面无回应」。

**原理**：将 GIMP 的内核算法（或 OpenCV 的 C++ 影像模块）编译为 Wasm。**共享内存架构**：Canvas 读取图片的 `ImageData` 后，将像素指针直接写入 Wasm 线性内存，避免 JS↔Wasm 的大量数据拷贝。**并行像素计算**：内部打开 SIMD（一条指令同时处理 4 个像素信道的浮点运算），并将图片切成区块（tiles）分发给多个 Worker 内的 Wasm 线程。

**性能**：宣称处理 4K（约 1200 万像素）照片时，高斯模糊等高级滤镜处理时间通常小于 **50 毫秒**，比纯 JS 数组遍历**快 15–30 倍**。

**优点**：极致运算性能，完全压榨多核 CPU；照片不需上传任何服务器，满足医疗级隐私需求。
**缺点**：算法固定在编译好的模块中，JS 难以动态注入或修改滤镜算法，灵活性较差。

**竞品**：纯 CSS 滤镜 / Canvas 2D API（由浏览器硬件加速，速度极快，但仅支持基本操作，无法自订内核的复杂矩阵运算或高级去背）；云端影像 API（Cloudinary 一类，功能强大但需计费、有延迟与隐私风险）。

### 9.（原 9）OpenTTD-Wasm — 大型仿真经营游戏移植　🟢

**痛点**：《运输大亨》（OpenTTD）包含数万行 C++、大量路径规划（A*）、车辆 AI 与动态地图渲染。社群希望「点开即玩」，同时要克服跨平台音频、输入与图形兼容性。

**原理**：以 Emscripten 搭配 **SDL2** 将整款 C++ 游戏编译为 Wasm。SDL2 的底层绘图指令被自动转译为 WebGL；鼠标、键盘与音频通过 Web Audio API 与 DOM 事件桥接。存盘与 MOD 资源通过 Emscripten 的 **IDBFS**（基于 IndexedDB 的虚拟文件系统）与浏览器保存同步。

**性能**：宣称在地图上数千辆火车、飞机同时运算路径规划的重度负载下，仍能稳定维持 **60 FPS**。

**优点**：极高的移植便利性，几乎不用修改 C++ 内核逻辑就能让二十年前的游戏复活；完全免费且无须后端。
**缺点**：初次进入需下载较大的素材包（Sprites 与音效）；沙盒限制使网页版难以与本机原生版进行区网多人连接。

**竞品**：用 JS/HTML5 重写（工程浩大，且 JS 的动态类型与 GC 在处理成千上万游戏对象的即时寻路时极易掉帧）。

### 10.（原 10）swc-wasm — 超高速 JS/TS 转译与打包　🟢

**痛点**：现代前端需把新语法的 JS/TS 转译为兼容版本（Babel 的工作）。项目规模扩大后，Node.js 写成的 Babel 在解析数万个 AST 节点时慢如牛步，建构动辄数分钟。

**原理**：`swc` 是用 **Rust** 写成的高性能 JS/TS 转译器。将其编译为 Wasm 后可直接部署在静态页上，作为在线即时转译器（Playground）或微型打包工具。用户输入现代 TS，JS 将字符串传入 Wasm 内存；Rust 解析器以极致优化的内存布局建构 AST，运行压缩（minification）与转译。所有字符串分析与标记化完全在 Wasm 内部进行，避免 JS 引擎的频繁对象回收。

**性能**：宣称转译速度比纯 JS 的 Babel **快 20–40 倍**；即使在单线程浏览器环境，转译一万行复杂 TypeScript 也仅需十几毫秒。

**优点**：极适合创建无后端的在线 IDE、代码格式化工具或静态检查平台。
**缺点**：相较于本机原生二进位版，Wasm 版受沙盒与字符串跨界传参限制，速度约慢 2 倍（但仍远快于 Babel）。

**竞品**：Babel（生态与插件极其丰富，但受 JS 语言限制，大规模转译上被降维打击）。

## 二、检索、解析与工具链

### 11.（原 11）Sonic-Wasm — 纯前端全文检索引擎　🟡

**痛点**：在 GitHub Pages 上创建静态博客（Hexo、Hugo、Jekyll）或大型文档站时需要全文搜索。后端方案（Elasticsearch、Algolia）需付费或维运；纯 JS 方案（Lunr.js）会将数 MB 的 JSON 索引加载内存，模糊搜索与重排序时速度慢且易触发 GC，导致打字延迟。

**原理**：将 Rust 写成的轻量搜索引擎 Sonic 内核编译为 Wasm。在线性内存中建构高度紧凑的**倒排索引与布隆过滤器**，数据以二进位字节流排列。查找时 JS 通过共享缓冲区传入关键字，Wasm 内部运行比特遮罩运算与 N-gram 词频分析，于微秒级返回文档 ID。

**性能**：宣称检索数万篇文章（约 50MB 文本）的索引时，复杂模糊匹配可在 **2–5 毫秒**内完成，比 Lunr.js **快 10 倍以上**，内存仅为 JS 版的 1/4。

**优点**：为静态页带来毫秒级、无后端的全文检索；零成本维运。
**缺点**：内容频繁更新时，前端必须定期重新生成并下载大体积的二进位索引。

**竞品**：Algolia/Elasticsearch（支持海量数据与动态权重，但需付费或维运）；Lunr.js/Fuse.js（免学习成本，但数万字以上长文本检索时 CPU 峰值过高）。

### 12.（原 12）Web-Wireshark (Wasm-Pcap) — 网络封包分析　🟡

**痛点**：分析网络故障需打开 `.pcap` 封包档。传统作法是上传到后端由 C 程序（libpcap）解析——但 pcap 通常包含企业敏感的网络拓扑与封包内容，上传云端有极大风险。

**原理**：将 C/C++ 网络分析库（libpcap 或 Rust 的 pcap-parser）编译为 Wasm。**串流二进位解析**：用户拖入数百 MB 的 `.pcap`，JS 通过 File API 以串流形式读取并写入 Wasm 内存；Wasm 内部逐比特拆解，重构出 Ethernet、IP、TCP、UDP 乃至应用层（HTTP/DNS）的协定树，将结构化数据传回 JS 渲染成交互式折叠树。

**性能**：宣称解析 100MB、数十万条网络讯框的 pcap 仅需约 **200 毫秒**，比纯 JS **快 15–20 倍**。

**优点**：100% 隐私安全，企业封包绝不离端；静态托管即可提供全球工程师免费使用的诊断工具。
**缺点**：受沙盒限制，Wasm 无法直接调用本机网卡进行**即时抓包（live capture）**，只能分析静态封包档。

**竞品**：本机 Wireshark（功能最完整、支持即时抓包，但需安装且无法嵌入网页分享）；纯 JS 封包解析库（缺乏高效二进位指针操作与结构体对齐，解析大文件时易 OOM）。

### 13.（原 13）OpenCascade-Wasm — 工业级 3D CAD 建模引擎　🟢

**缺点**：AST 存在 Wasm 内存中，若前端 JS 想频繁深度遍历这棵树，跨界的串行化/反串行化会产生额外耗损。

**竞品**：Babel Parser（功能最强大、插件最丰富，但纯前端处理大规模原代码时内存消耗与解析速度远远落后）。

### 26.（原 31）Web-Jq (jq-wasm) — JSON 高速过滤与转换　🟢

**痛点**：`jq` 是命令行 JSON 处理神器，能用强大的 DSL 对复杂 JSON 做切片、过滤、映射。但在网页端提供在线 JSON Playground 时，纯 JS 方案面对数百 MB 的巨大 JSON 日志会因创建数百万个 JS 对象而引发长达数秒的 GC 卡顿甚至分页崩溃。

**原理**：将 C 语言的 jq 内核经 Emscripten 编译为 Wasm。**串流内存解构**：用户贴入巨大 JSON 或上传文件时，JS 通过共享缓冲区将字节流直接写入 Wasm 的连续内存。**DSL 引擎解析**：Wasm 内部即时解析过滤表达式（如 `.items[] | select(.status == "active")`），在内存中高速遍历紧凑排列的二进位 JSON 树（**不产生 JS 对象**），将结果以字符串返回。

**性能**：宣称 100MB 级的复杂 JSON 文件，解析、过滤与转换通常在 **80–150 毫秒**内完成，比纯 JS **快 15–25 倍**。

**优点**：完全去中心化、零后端成本、秒级处理大体积 JSON；满足高敏感日志绝不离端的需求。
**缺点**：JS↔Wasm 的字符串边界传参在处理极高频率的微小查找时会产生开销，必须以大块批处理优化。

**竞品**：原生 `JSON.parse` + 自订过滤（小文件轻量，但数十万行以上的大型日志结构会使内存与 CPU 峰值指数暴涨）。

### 27.（原 36）OpenCV.js (Wasm) — 工业级电脑视觉与矩阵运算　🟢

**痛点**：网页端要做即时影像处理（如识别手持信用卡轮廓），纯 JS 图形库（tracking.js）极度缺乏优化；JS 缺乏多维矩阵的紧凑布局与直控指针，遍历 1080P 的数百万像素会引发严重 GC 卡顿，无法达到即时交互要求。

**原理**：将数百万行 C++ 的 OpenCV 内核经 Emscripten 交叉编译为 `opencv.wasm`，并把底层的 `cv::Mat` 矩阵结构映射至前端。**零拷贝影像流**：HTML5 Video 每帧截取的 `ImageData` 指针直接写入 Wasm 线性内存，杜绝拷贝开销。**硬件级算子加速**：内部激活 SIMD，一条 CPU 指令内同时处理 4 个像素点的灰阶化（Canny）、高斯滤波或索贝尔算子运算。

**性能**：宣称处理 720P 即时视频流时，运行 ORB 特征点检测仅需 **12–15 毫秒**，轻松维持 60 FPS，是纯 JS 版的 **20 倍以上**。

**优点**：完美隐私保护（身分证扫描等不离端）；静态托管即可布建大规模并发的 CV 应用。
**缺点**：OpenCV 功能庞大，编译出的 Wasm 加胶水压缩后仍有 **6–9MB**，通常需采动态延迟加载。

**竞品**：tracking.js（体积小但功能简陋，缺乏高级矩阵变换、特征匹配与光流法）；云端视觉 API（准确度高，但有延迟、计费与隐私风险）。

### 28.（原 37）solc-wasm — 以太坊智能合约编译器　🟢

**痛点**：区块链开发者需把 Solidity 转为 EVM 比特码。传统要安装 `solc` 二进位，或由前端送到远程服务器编译——对 Remix IDE 这类网页环境，依赖后端编译服务器带来运维成本，且高并发或受攻击时极易崩溃。

**原理**：以太坊基金会将 C++ 的官方 Solidity 编译器编译为 `soljson.wasm`。用户点击编译时，JS 将 Solidity 原代码字符串传入 Wasm 内存；Wasm 内部进行词法分析、语法分析、建构 AST 并运行类型检查，直接在线性内存中输出 EVM 兼容比特码、ABI 接口定义与 Source Maps。

**性能**：宣称编译标准 ERC-20 合约仅需 **100–300 毫秒**，达本机原生二进位版的 **80%**。

**优点**：为 DApp 的在线 IDE（如 Remix）提供完全无后端、零维运的编译能力；代码在本地编译，防止未公开的合约被第三方截获。
**缺点**：因包含大量优化器与密码学组件，`soljson.wasm` 体积非常巨大（通常 **10–15MB**），首次加载缓慢。

**竞品**：后端编译 API（网页加载快，但存在死机、服务中断与合约外泄风险）。

### 29.（原 38）xterm 的 Wasm 解析插件 — 百万级日志终端渲染　🟡

**痛点**：在网页端（Kubernetes 控制台、云端 Shell）查看即时滚动的容器日志时，后端每秒送来数百 KB 的 ANSI 转义串行。主流的 xterm.js 在做大量字符串解析、UTF-8 解码与屏幕缓冲区管理时，会引发严重 GC，直接导致 UI 冻结。

**原理**：将终端机最内核的 **ANSI 串行解析器与状态机**用 C++/Rust 重写并编译为 Wasm，作为 xterm.js 的性能插件。**二进位字节流直通**：WebSocket 收到后端的原始字节后，跳过 JS 字符串转换，直接把 `Uint8Array` 写入 Wasm 内存。**高效状态机**：Wasm 以静态类型的整数状态机极速识别 `\x1b[31m` 等控制符，在线性内存中维护二进位形式的虚拟屏幕二维数组，仅在每帧渲染时将改变通知 JS 的 WebGL 渲染层。

**性能**：宣称在极限「日志暴风雨」测试中吞吐量比纯 JS 正则解析**快 10–15 倍**；每秒处理 50 万行 ANSI 字符时仍稳定 60 FPS，CPU 占用下降 70%。

**优点**：彻底解决网页终端在大流量日志下卡死的痛点；大幅提升低配笔电运行云端控制台的续航与流畅度。
**缺点**：把原本灵活的 JS 解析逻辑固化到 Wasm 中，未来若有新的非标准转义扩充协定，升级灵活性较低。

**竞品**：纯 JS 版的 xterm.js 解析器（兼容性完美、扩展方便，但处理数百万行 CI/CD 建构日志时会 OOM 崩溃）。

### 30.（原 39）HarfBuzz.js (Wasm) — 复杂文本塑形排版引擎　🟢

**痛点**：「文本塑形（text shaping）」负责把 Unicode 字符转为字体中的字形（glyphs）与精确几何座标，在处理阿拉伯文、印度文、泰文等具复杂连字与动态变形的语系时不可或缺。浏览器原生排版虽强，但在 Canvas 2D/WebGL、网页游戏引擎或在线 PDF 生成中，开发者无法直接调用浏览器的排版细节，导致复杂语系文本错位、断字或连字失效。

**原理**：将全球最顶级的开源文本塑形内核 **HarfBuzz**（C++ 编写，也是 Chrome 与 Android 的底层依赖）编译为 Wasm。JS 将待排版的 Unicode 字符串与 OpenType 字体的二进位指针传给 Wasm；Wasm 在线性内存中深度解析字体内的 `GSUB`（字形替换表）与 `GPOS`（字形位置表），精确计算每个文本的 X/Y 偏移量与前进量，回传结构化的字形 ID 与座标数组，由 WebGL 直接绘制。

**性能**：宣称大规模阿拉伯文或泰文排版时，连字数学计算效率几乎与本机系统无异，每秒可处理数十万字，比纯 JS 仿真的排版引擎**快 30 倍以上**。

**优点**：确保复杂文本在所有浏览器、Canvas 与导出的 PDF 中有 100% 像素级一致且正确的排版，填补网页图形领域的重大空白。
**缺点**：属极度垂直的分支工具，API 设计非常低级，前端工程师需具备深厚的字体排版知识才能顺利对接。

**竞品**：opentype.js 的自建排版（仅支持简单拉丁字母，面对需要上下文感知的阿拉伯语、印度诸语时结果完全错误）。

### 31.（原 40）Z-Music (libgme-wasm) — 复古主机音频芯片仿真　🟡

**痛点**：播放早期游戏主机的原生音乐（FC 的 Ricoh 2A03、SFC 的 SPC700、MD 的 YM2612；格式如 `.nsf`、`.spc`、`.vgm`）非常迷人——这些文件只有几 KB，因为它们是直接控制硬件的指令。但用纯 JS 仿真这些芯片的滤波器与波形发生器，会因不精确的定时器与动态类型引发频繁爆音，且 CPU 占用不合理地高。

**原理**：将 C++ 的音频芯片仿真库 **Game Music Emulator (GME)** 编译为 Wasm，结合 **AudioWorklet** 部署。**线程隔离**：Wasm 被加载到最高优先级的独立音频线程，完全不受 UI 渲染、滚动或主线程阻塞干扰。**寄存器级硬件仿真**：Wasm 在线性内存中仿真这些老芯片的内部寄存器状态，以 44.1kHz 每秒计算 44100 次波形浮点数，动态仿真方波、三角波、杂音声道与 PCM 采样的混音。

**性能**：宣称仿真一颗复杂的 SFC 16 比特音频芯片仅消耗不到 **0.5% 的 CPU**，音频缓冲区计算耗时小于 0.05 毫秒。

**优点**：以极低开销完美复活复古硬件音频；音频档仅数 KB 即可开播整首游戏音乐。
**缺点**：若遇到损坏的非标准 ROM，容易引发内存越界，需要严格的沙盒边界检查。

**竞品**：传统 MP3/OGG 播放（体积大 1000 倍以上，且丧失即时动态开关音轨、变速不变调的硬件级交互乐趣）；纯 JS 音频仿真器（受 GC 停顿干扰，用户滚动网页时立刻断音爆音）。

### 32.（原 41）Stockfish.wasm — 世界顶级国际象棋 AI 引擎　🟢

**痛点**：Stockfish 的内核竞争力在高密集的 alpha-beta 剪枝搜索、NNUE 神经网络评估与海量比特棋盘（bitboard）运算。过去要在网页提供高强度分析，必须送到后端 CPU 服务器群——维护成本巨大，且数万玩家同时分析时算力瞬间被拉满。

**原理**：将 C++17 的 Stockfish 原代码经 Emscripten 编译为 Wasm，作为主流象棋网站（如 Lichess）的前端分析引擎。**多线程与 SIMD 架构**：以 Web Workers + `SharedArrayBuffer` 实现大规模并行搜索，内部激活 SIMD 加速 NNUE 的权重矩阵乘法。**比特棋盘直通**：线性内存中以 `i64` 表示棋盘状态，利用比特遮罩与比特扫描指令瞬间枚举数百万种合法着法。

**性能**：宣称打开 SIMD 与 4 内核后，搜索速度（NPS）可达本机原生 C++ 的 **75%–85%**，每秒可在前端计算数百万到上千万步棋局，深度可达 20 层以上。

**优点**：真正去中心化，静态托管即可提供世界顶级的 AI 分析，服务器算力成本为零；可脱机使用、无网络延迟。
**缺点**：NNUE 权重档通常有数 MB 到十几 MB；高强度搜索会把用户的 CPU 拉满，引发设备发热与耗电。**且它是需要 `SharedArrayBuffer` 的典型案例——在 GitHub Pages 上必须配 `coi-serviceworker`。**

**竞品**：纯 JS 象棋引擎（只能做初阶计算，面对复杂残局时被彻底降维打击）；后端云端分析（算力不受限，但无法应对数百万玩家的免费并发需求）。

### 33.（原 42）Web-GnuTLS (Wasm-TLS) — 前端 TLS 微型网络栈　🟡

**痛点**：构建无后端、去中心化的网页应用（P2P 网络、浏览器端 MQTT 控制台）时，前端有时需直接与外部 TCP/UDP 服务器（通过 WebSocket 转发器）创建安全的 TLS 连接。但浏览器自带的 `fetch` 安全机制非常严格，**不允许开发者自订 TLS 握手阶段的凭证验证、密码套件协商或私有 CA 注册**。

**原理**：将 C 语言的 GnuTLS 完整编译为 Wasm，在静态页上构建一个完全由前端控制的「微型加密网络栈」。**内存缓冲区网络 I/O（BIO 模式）**：Wasm 不直接调用系统网络 API，而是将 TLS 握手包写入内存中的环形缓冲区，由外部 JS 提取并通过 WebSocket 或 WebRTC Data Channel 送出。**密码学算子加速**：TLS 握手涉及大量非对称（ECDHE、RSA）与对称（AES-GCM、ChaCha20-Poly1305）运算，Wasm 利用 64 比特整数运算与紧凑布局在沙盒内高速运行大数乘法。

**性能**：宣称完整的 TLS 1.3 握手与密钥交换耗时不超过 **5–10 毫秒**，吞吐与本机 C 版几乎同级，比纯 JS 加密库**快 10 倍以上**。

**优点**：打破浏览器对网络安全协定层的黑盒限制，允许在静态页实现自订凭证验证、双向 TLS（mTLS）；密钥不离端。
**缺点**：TLS 网络栈极其复杂，Wasm 模块体积较大；且因无法直接操作 Socket，必须编写复杂的 JS 胶水做封包转发与拼接。

**竞品**：纯 JS 密码学协定库（forge 一类，能仿真部分 TLS 流程，但高频加密封包吞吐时 GC 卡顿，且对 TLS 1.3 的支持与安全性不够完备）。

### 34.（原 43）QuickJS-Wasm — 安全沙盒级「JS inside JS」运行期　🟢

**痛点**：在线 Playground、低代码平台或需要用户自订插件的应用，前端需要「运行用户输入的 JavaScript」。直接用 `eval()` 或 `new Function()`，用户代码可直接访问 `window`、`document`、`cookie`，带来致命的 XSS 风险。即使用 iframe 隔离，攻击者依然可以用 `while(true)` 把主线程彻底卡死。

**原理**：将 Fabrice Bellard 写成的轻量高效 C 语言 JS 引擎 **QuickJS** 完整编译为 Wasm，实现精妙的「在 JavaScript 里跑另一个 JavaScript」。**双重沙盒**：用户的脚本不在浏览器原生 V8 中运行，而是被当作字符串传入 QuickJS-Wasm，在 Wasm 封闭的线性内存沙盒内解译运行，**完全无法访问外部网页的任何 DOM 或敏感信息**。**时间与内存配额**：Wasm 模块内部设置中断处理器，若用户代码运行超过配额（例如 500 毫秒）或申请内存超限，会立刻强制终止——完美防止无限循环卡死网页。

**性能**：虽是解译运行，但 QuickJS 极轻量，在 Wasm 中运行标准 JS 的速度可达每秒数百万条指令，足以流畅运行复杂商业逻辑、单元测试或数据转换。

**优点**：为静态页带来军工级的安全代码运行环境，彻底杜绝 XSS 与无限循环；压缩后仅数百 KB，加载极快。
**缺点**：作为「解译器的解译器」，性能无法与经 JIT 优化的原生 V8 相比（通常慢 10–20 倍），不适合运行重度图形或矩阵运算。

**竞品**：原生 `eval()` / iframe 沙盒（性能最高，但安全边界脆弱，极难防御高级漏洞利用与恶意无限循环）；纯 JS 写的 JS 解译器（体积相仿，但语法支持度与内存配额控制的完整度远不如 QuickJS）。

### 35.（原 44）Web-GSL — GNU 科学计算与数值分析矩阵库　🟡

**痛点**：工程、物理与金融计量领域常需运行复杂数值计算：高级矩阵特征值求解、常微分方程（ODE）数值解、最小二乘拟合、快速傅里叶变换（FFT）、复杂统计分布抽样。传统依赖 C 语言的权威库 **GSL**。在前端若用 JS 的浮点数组手写这些公式，因缺乏操作符重载、内存紧凑对齐与高速指针算术，不仅慢，且极易因浮点精度损失导致科学结果出错。

**原理**：将庞大严谨的 C 语言 GNU 科学库内核完整编译为 Wasm，创建在线科学数值计算工作台。**精确内存布局（BLAS 集成）**：内部集成高效的基础线性代数子进程（CBLAS），多维矩阵以连续的双精度浮点（`f64`）严格对齐排列，极大化 L1/L2 缓存命中率。**零 GC 干扰**：所有微分方程逼近、非线性最小二乘迭代完全在 Wasm 内部的内存池中运行。

**性能**：宣称求解 500×500 矩阵的特征值或运行百万点 FFT 时，效率达原生 C 的 **80%–90%**，比纯 JS 数值库**快 20–40 倍**。

**优点**：为教育、科研与金融工程带来无需安装、完全免费的工业级数值计算平台；精度符合 GNU 国际科学标准。
**缺点**：GSL 的 API 设计高度学院派且极其低级，缺乏现代前端习惯的链式调用或 JSON 对接，需要编写较厚重的 JS 包装层。

**竞品**：math.js（适合日常代数运算与常规绘图，但面对硬核工业级微分方程求解、大型稀疏矩阵与高精度数值拟合时完全无法相比）。
