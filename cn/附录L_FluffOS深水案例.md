# 附录L　深水案例：FluffOS × Wasm——把一整台 MUD 服务器搬进静态页

> **这是全书唯一一个值得单独成篇的案例，因为它同时是三件事：**
> **一，它是附录 E 里两个 🔴 示意性构造（案例 58 Minestom-Wasm、案例 60 Micro-Apache-Wasm）的真实版本**——而且做得比那两个构想更彻底。
> **二，它把本书十二章讲过的每一道墙，一次撞了个遍**，且每一道墙的处理方式都留下了公开的工程纪录。
> **三，它是全书内核命题最干净的活体标本**：**代码 100% 可下载、可自架、可修改，而它的价值三十年来从未因此消失一分。**
>
> **真伪等级：🟢 可查证。** 本附录所有技术细节均引自 FluffOS 官方仓库的 `README.md` 与 `src/wasm/README.md`，以及 `fluffos/mudlibs` 仓库。**唯一会随时间变动的是收录数量与「已 WASM 化」的比例**——请以仓库当下状态为准。

## 一、它是什么

### FluffOS：一台还在维护的 LPMud 驱动

**FluffOS** 是 **MudOS 的现代分支**——一个用 C++ 写成、仍在积极维护的 **LPMUD driver**（LPC 解释器 + 游戏引擎）。它的职责不是「一个游戏」，而是**一台完整的游戏服务器运行期**：

```
FluffOS driver（C++）
├── LPC 编译器      ← 把 mudlib 的 .c 原代码在运行期编译成字节码
├── 虚拟机（VM）    ← 运行那些字节码
├── efuns           ← 内置函数库（字符串、数组、文件、网络、时间…）
├── 调度内核        ← heartbeat（心跳）、call_out（定时器）、reset（重置）
└── 网络层          ← telnet / WebSocket / TLS
```

它向下兼容既有的 MudOS mudlib，并累积了十多年的性能优化，另外支持 **WebSocket、TLS、MySQL/PostgreSQL/SQLite3 集成**，以及 **UTF-8 EGS 感知的 LPC 字符串运算**（范围操作符支持 emoji 与其他 Unicode 字符）。

**建置目标**：CMake，支持 Ubuntu、macOS、Windows（MSYS2/MinGW64），**以及 WebAssembly**。

### mudlibs：一整个时代的原代码典藏

`github.com/fluffos/mudlibs` 是一份**中文 MUD 场景的原代码考古典藏**——涵盖一九九〇年代中期到二〇一五年前后的作品，收录的是《侠客行》《笑傲江湖》《金庸群侠传》《西游记》这一类武侠、仙侠题材的 LPC 游戏及其各种分支。

仓库的组织方式本身就是一份修复工程纪录：

```
archives/                       原始封存盘
libs/<slug>/raw/                原封不动的解压内容（保留原始编码）
libs/<slug>/work/               可玩版本（转成 UTF-8、套用修复）
libs/<slug>/config.fluffos      运行期设置
libs/<slug>/README.md           玩家说明
libs/<slug>/NOTES.md            修复纪录
scripts/                        转换与测试工具
lib_numbering.json              机器可读的对照表
```

**收录状态**（依仓库 README 记载，数字会随修复进度变动）：

| 状态 | 数量 |
|---|---|
| 已修复的 mudlib | **200 份**（涵盖 **158 个**不重复的 codebase） |
| **已验证可在浏览器（WASM）中游玩** | **79 个** |
| 原生开机验证通过、WASM 打包待办 | 117 个 |
| 政策上仅限原生 | 1 个 |
| 确认无法开机 | 4 个 |

**授权**：多数作为历史社群典藏，并无正式授权条款（其中《重生的世界》明确为 GPLv2）。项目的定位是「**把它们当成文化资产保存下来**」，并保留原作者署名。

> ⚠️ **数量会移动**：在线典藏站 `mudlibs.fluffos.info` 在本书写作当时列出的可玩游戏数与仓库 README 的统计并不完全一致（前者约九十余个，后者记载 79 个已验证 WASM 可玩）。**这类数字每次修复推进都会变**——请以你造访当下的仓库与站台为准，本书引用的是相对关系而非快照。

## 二、它为什么值得单独一篇

**因为它跨过了一道别人只在投视频上跨过的线。**

回想附录 E 的两个 🔴 条目：

- **案例 60「Micro-Apache-Wasm」**：构想是在浏览器里跑一台微型 HTTP 服务器，用 Service Worker 拦截请求喂给 Wasm。**这个构想成立，但它仿真的是「请求—回应」这种无状态的东西。**
- **案例 58「Minestom-Wasm」**：构想是在浏览器里跑一台 Minecraft 服务器。**这个构想更接近，但它需要 WebRTC 才能让别人连进来。**

**FluffOS 的 Wasm 目标做到的，比这两个都硬**——因为一台 MUD driver 不是一个请求处理器，它是一个**有心跳、有定时器、有持久世界状态、有多个并发连接、还要在运行期编译用户代码**的东西：

> 官方 README 的原话是：**「The whole driver runs in a browser page (or node) — compiler, VM, efuns, telnet.」**
> 编译器、虚拟机、内置函数库、telnet 协定——**全部**在一个浏览器分页里。

而 mudlib 的分发方式是：**「Mudlibs ship as static bundles via `tools/wasm/pack-mudlib.sh`; no server required.」**——**打包成静态 bundle，不需要服务器。**

这正是第 5 章那句话的极致版本：**运算没有消失，它只是换了付钱的人。**

## 三、架构深拆：五个必须被解决的难题

这一节是本附录的技术内核。**FluffOS 的 Wasm 移植不是「重编一次就好」**——它必须逐条处理 Wasm 与浏览器的物理限制，而每一条的解法都值得记下来。

### 难题一：浏览器不能阻塞，可是服务器的本质就是「等」

**原生驱动阻塞在 libevent 的事件循环里**——`while(true) { wait_for_events(); dispatch(); }`。**这在浏览器里是死路**：主线程一旦阻塞，整个分页冻结。

**解法：把事件循环的所有权交给宿主（host-driven tick）。**

```javascript
// 页面用 setInterval / requestAnimationFrame 驱动驱动器
setInterval(() => {
  Module._fluffos_tick(Date.now());   // ← 推进一次调度，处理到期事件后立刻返回
}, 50);
```

**关键设计**：调度内核（gametick 队列、维护事件）**在原生与 Wasm 之间是共用的**，两者的差异**只在「谁来推进循环」**。因此 **heartbeat、call_out、reset 这些 LPC 层的机制完全不用改**——mudlib 的代码一行都不知道自己活在浏览器里。

> 💡 **这是整个移植里最漂亮的一手**：它没有去改「时间怎么流动」，只改了「谁负责敲钟」。

> 🔧 **一个值得注意的未来选项**：这套「把循环交给宿主」的解法解决的是**主动的调度**，但它没有解决**被动的等待**——当 LPC 代码想读一个异步的东西（例如 OPFS 的异步 API、或一次网络请求）时，驱动器依然无处可等。**JSPI**（第 3 章墙七、附录 M §5）正好对付这一段：它让引擎把整条 Wasm 堆栈挂起，等 Promise 解决后再恢复。
> 对这个项目的意义很具体：**roadmap 上那个「挂一层 IDBFS/OPFS 覆盖」的持久化计划，在 JSPI 之后可以不必把整个保存层改写成异步。** 代价是它引入了重入问题——**挂起期间 `fluffos_tick` 可能又被调用一次**，而一台驱动器对「同时只有一个 tick 在跑」的假设非常强。**这是一个典型的「新能力带来新约束」的例子。**

### 难题二：没有 socket，可是每个玩家都是一条连接

**解法：把「连接」抽象成一根字节管道（Transport）。**

每个用户连接拥有一个 `Transport`——一个抽象的字节管道，只有 `write` / `flush` / `schedule_command` / `close` 四个操作。底下有三种实作：

| 实作 | 目标 | 底层 |
|---|---|---|
| `SocketTransport` | 原生 | libevent |
| `WebsocketTransport` | 原生 | libevent |
| **`WasmConsoleTransport`** | **浏览器** | **JS 桥接** |

`WasmConsoleTransport` 的两个方向：

```
出站：驱动器写出的字节 → Module.fluffos.onOutput(id, bytes) → 页面的终端机
入站：用户敲的指令     → 导出函数 fluffos_input(id, bytes, count) → 驱动器
```

**而最有趣的细节是：驱动器依然吐出真正的 telnet 协定。** 所以网页必须自己提供一个 telnet 客户端——官方附的接口会协商 **ECHO、SGA、NAWS（窗口大小）、TTYPE**，并用 **xterm.js** 做终端机渲染。

> **这一段是附录 E 案例 29（xterm 的 Wasm 解析插件）的真实对照组**：那里是把 ANSI 解析搬进 Wasm，这里是把**协定的另一端**整个搬进 Wasm，然后让 xterm.js 在外面当显示器。

### 难题三：导出面必须够窄

**整个驱动器对外只曝露七个函数**——这正是第 2 章「Export 段是攻击者永远看得到的东西」与第 12 章「接口要窄」的教科书级示范：

| 导出函数 | 用途 |
|---|---|
| `fluffos_boot(config_path)` | 初始化驱动器 |
| `fluffos_tick(now_ms)` | 依实际时间推进调度 |
| `fluffos_connect()` | 创建一条新的虚拟连接 |
| `fluffos_input(id, bytes, count)` | 送入客户端的指令字节 |
| `fluffos_disconnect(id)` | 关闭连接 |
| `fluffos_shutdown()` | 关闭驱动器 |
| `fluffos_flag(flag)` | 设置运行期旗标（如 `'test'`） |

模块实例化：

```javascript
const M = await createFluffOS({ print, printErr, locateFile });
```

**七个函数，一整台服务器。** 对照第 2 章情境 4 的那句话——**把边界做粗、把往返做少**——这是能找到的最极端例子。

### 难题四：mudlib 是几万个文件，而 Wasm 没有文件系统

**解法：MEMFS + Emscripten 的 `file_packager`。**

Emscripten 把文件 I/O 透明地映射到内存文件系统（MEMFS，见第 7 章）。mudlib 用 `file_packager` 打包成**单一的 `mudlib.data` 映像档 + `mudlib.js` 加载器**，在运行期启动前挂载到指定路径。

```bash
# 打包任意 mudlib
MUDLIB=/path/to/lib tools/wasm/build.sh
# 或
tools/wasm/pack-mudlib.sh --mudlib <dir> --config <path>
```

**于是分发形态变成**：一个 `.wasm`、一个 `.js` 胶水、一个 `.data` 映像——**三个静态文件，就是一整个游戏世界。**

**但这里有一个诚实的现况**，而它恰好是第 7 章那条四层保存阶梯的活教材：

> **目前的写入只在分页 session 内有效（MEMFS 是挥发的）。**
> 官方 roadmap 的 Phase 2 计划是：**在 mudlib 的写入路径（`/data`、存盘、日志）上挂一层 IDBFS（或 OPFS）覆盖，并在计时器与 `visibilitychange` 时调用 `FS.syncfs()`**——让数据能跨分页重载存活。**尚未实作。**

**换句话说：这个项目此刻正卡在第 7 章的第一层（MEMFS），而它知道自己要往第二、三层（IDBFS/OPFS）走。** 全书没有比这更好的一次现场验证。

### 难题五：能力必须被砍掉

第 2 章说过「安全性最便宜的实现方式不是加防护，是砍能力」。**FluffOS 的 Wasm 建置把这件事做成了一张表**：

| 功能 | 状态 | 原因 |
|---|---|---|
| libevent | **移除** | 由 tick 队列取代 |
| OpenSSL / TLS | **移除** | **TLS 归浏览器管**，`sys_reload_tls` 不存在 |
| zlib | **移除** | MCCP 与 compress 套件停用 |
| POSIX eval-limit 计时器 | 自动停用 | 仅 `__linux__` 可用，替代方案规划中 |
| BSD sockets | 关闭 | 没有对外 socket efun |
| DNS | **桩化** | 下一个 tick 合成回传 `127.0.0.1` |
| 外部进程 | 关闭 | 不支持 `posix_spawn` |
| Worker threads | 关闭 | 无 async 套件 |
| 数据库客户端 | 关闭 | MySQL/SQLite/PG 函数库不可用 |

**这张表就是能力式安全的具体长相**（第 1、7 章）：它不是「我们防住了这些攻击面」，是「**这些攻击面在这个建置里根本不存在**」。

同时它也精准对应第 3 章的四道系统墙——**没有原生系统访问、内存只能长不能缩、没有多线程、同步代码碰上异步世界**。

## 四、那些具体的数字

**这是全书最有价值的一组实测数字，因为它们来自一个真实、复杂、还在维护的项目，而不是 benchmark 玩具。**

| 项目 | 数值 | 对应本书 |
|---|---|---|
| 初始线性内存 | **64 MB**（依需求成长至 **2 GB**） | 第 8 章：注意上限设在 2GB 而非 4GiB——**这正是「浏览器的现实拦截」** |
| 堆栈 | 16 MB | 第 2 章 |
| 代码大小（含 PCRE） | **~3.6 MB 原始** | 第 3、8 章：远低于「30MB 实务天花板」 |
| 代码大小（Brotli 压缩后） | **~0.8 MB** | 第 8 章：**压缩率约 4.5 倍，印证「Wasm 的 Brotli 压缩率通常很好」** |
| ICU 数据 | **~780 KB**（原始约 30 MB） | 第 8 章：**只保留 break-iterator 规则，砍掉 97%** ——这是「砍体积投报率最高的一步不是编译旗标，是砍掉你不用的数据」 |
| DWARF 调试信息 | 链接时剥离 | 第 9 章 |
| 函数名 | **保留**（为了可读的堆栈追踪） | 第 3 章：**这是一个刻意的取舍**——牺牲一点混淆强度，换取可调试性 |

> 🔍 **那个 ICU 的数字值得停下来看三秒。**
> 30 MB → 780 KB，砍掉了 97.4%。**这不是靠 `wasm-opt`，不是靠 LTO，是靠「想清楚我到底要 ICU 做什么」**——这个项目只需要 break-iterator（断词）规则，于是其余的地区设置、时区、校对规则、转写表全部不打包。
> **第 8 章那条「砍体积投报率排序」应该补上第 0 条：先砍数据，再砍代码。** 因为一个大型 C/C++ 项目的 Wasm 产物里，往往有一大半是它拖进来的数据表，而那些数据表通常有 90% 你根本用不到。

## 五、自己在本地跑起来

### 路线 A：原生（最快看到东西）

```bash
# 1. 取得 mudlib
git clone https://github.com/fluffos/mudlibs
cd mudlibs/libs/<你选的 slug>

# 2. 用建好的 driver 启动（work/ 是已转 UTF-8、套过修复的可玩版本）
~/src/fluffos/build-debug/src/driver config.fluffos

# 3. telnet 进去
```

### 路线 B：WebAssembly（做成静态站）

```bash
# 一次性：为 wasm32 交叉建置 ICU
tools/wasm/build-deps.sh

# 建置：原生 codegen 工具 + wasm 驱动器 + demo bundle
tools/wasm/build.sh

# 本地起一个静态服务器看结果
python3 -m http.server -d build-wasm/dist 8080
# 开 http://localhost:8080/
```

**换上自己的 mudlib**：

```bash
tools/wasm/pack-mudlib.sh --mudlib <mudlib 目录> --config <config 路径>
# 或
MUDLIB=/path/to/lib tools/wasm/build.sh
```

**产物就是一个纯静态目录**——丢到 GitHub Pages、任何 CDN、任何 S3 bucket 上就是一个能玩的游戏。**这正是第 5 章「在静态页上造机器」的完整闭环。**

### 上线前对照第 5 章与附录 C

| 检查项 | 这个案例的状况 |
|---|---|

## 六、它撞到的每一道墙（逐条对回本书）

| 墙 | 现象 | 本书章节 |
|---|---|---|
| **没有阻塞式事件循环** | 必须改成 `fluffos_tick(now_ms)` 由宿主驱动 | 第 3 章（系统墙）、第 5 章 |
| **没有 socket** | Transport 抽象 + JS 桥接；DNS 桩化回传 `127.0.0.1` | 第 3、7 章 |
| **没有线程** | async 套件整个关闭，规划同步替代 | 第 3、5 章 |
| **没有 eval limit** | **无穷 LPC 循环会卡死整个分页**（原生靠 POSIX 计时器，Wasm 上还没有替代） | 第 3 章（沙盒不保护你自己） |
| **MEMFS 是挥发的** | 写入只在 session 内有效；IDBFS/OPFS 覆盖层在 roadmap | **第 7 章（四层保存）** |
| **分页被背景暂停** | 计时器暂停；回到前景时 gametick 追赶（**上限 100 次**） | 第 5 章（宿主环境的节奏不由你决定） |
| **字符集表格不支持** | 只支持算法型（UTF-8/16/32、Latin-1、ASCII），表格型不支持 | 第 8 章（数据才是体积大宗） |
| **内存 2 GB 上限** | 不是 4 GiB——**这是浏览器的现实拦截** | 第 8 章 |
| **缺少浏览器环境能力** | 典藏站注记部分游戏「可玩但登录受限」，因为缺少 `query_ip_number()` 这类能力 | 第 3、7 章（能力必须由宿主递入，递不了就是没有） |

> **最后一条特别值得玩味**：一个一九九〇年代写的 mudlib，在登录流程里调用了 `query_ip_number()` 来记录玩家 IP——**而浏览器里没有 IP 这个概念可以给它。** 三十年前写下的一行代码，在今天成了移植的拦路石。
> **这就是第 12 章「维护熵增」最具体的样子：不是你的代码坏了，是它脚下的世界换了。**

## 七、jsbridge：那条被打开的双向门

FluffOS 的 Wasm 建置提供了一组**只在 WASM 目标存在**的 `jsbridge` efuns，让 LPC 与页面 JavaScript 双向调用：

```
LPC → JS：  js_eval()、js_call()      → fetch、canvas/WebGL、audio、storage…
JS  → LPC： js_export() + fluffos.callLPC()
```

**这件事的意义比它看起来大**：它意味着一个一九九〇年代的文本游戏，**可以在不改动游戏逻辑的前提下，长出 canvas 地图、WebGL 特效、Web Audio 配乐、以及浏览器端的保存**——因为那条桥是双向的，而游戏那一侧只需要多调用一个 efun。

> 这正好呼应第 12 章的四层拓扑：**Wasm 内核（LPC 驱动器）是资产，设计目标是十年不动；页面那一层（xterm.js、canvas、UI）是消耗品，允许每三年被重写一次。** 而 jsbridge 就是那个「窄到不可能出错的接口」。

## 八、为什么它是全书命题的活体标本

**现在把技术放下，看这件事的另一面。**

一个 MUD 的**全部原代码**——世界地图、NPC 对话、武功系统、经济规则、每一个房间的描述——就是那个 mudlib。**它从来都是可以被完整下载的**：在一九九〇年代靠打包传档，在今天靠 `git clone`，而现在甚至可以在浏览器里直接加载运行。

**没有任何一行代码是秘密。**

按照「代码是资产」的旧逻辑，这种东西不可能有价值。可是：

- 这些游戏**活了三十年**，在原作者早已离开之后仍被反复分支、修改、重开。
- 有人**花了大量心力去修复它们**——转编码、修 bug、写 `NOTES.md` 记录每一处改动、逐个验证能不能开机。
- 而今天有人**把整台驱动器编译成 Wasm**，只为了让它们能被再次打开。

**那个护城河从来就不在代码里。**

它在那些人身上——在那些记得自己十七岁时在某个房间里卡了三天的人身上，在那个把三十年前的破损封存盘一份一份修回来的人身上。**这正是第 12 章那五道防线里最难被拷贝的两道：数据引力（世界状态与那段记忆）与生态（社群）**，而它们与代码的可见性完全无关。

> 💡 君之一席话
> 与君一席话：**当一件东西的原代码可以被完整拷贝了三十年，而它依然没有被取代时，你就找到了一个关于价值的干净证据。** 这些 mudlib 是软件史上少见的对照实验——**保密程度为零、拷贝成本为零、修改门槛极低**，理论上它们早该被更好的拷贝品淹没。可是没有。因为用户要的从来不是「一份能跑的代码」，而是「**那个世界，以及那个世界里的人**」。而那两样东西，`git clone` 拿不走。
> 把这条放到第 12 章的框架里，答案就非常清楚了：**当 LLM 让写代码的边际成本归零时，我们其实只是回到了 MUD 一直以来的处境——代码从来就不值钱，值钱的是它周围长出来的那些东西。** 唯一改变的是，现在所有的软件都要面对这个处境了。
> 所以与其焦虑「AI 会不会拷贝我的产品」，不如问一句更有用的：**如果我的原代码明天全部公开，三十年后还会有人在用它吗？** 这些 mudlib 的答案是「会」。**你的呢？**

> 🔍 进阶点评──保存的技术债，与一个没人谈的长期问题
> 这个案例还揭示了一件在数字保存领域越来越尖锐、但软件业普遍还没开始面对的事。**修复一份三十年前的 mudlib，难的不是代码，是它脚下那个消失了的世界。** 仓库里那些 `NOTES.md` 记录的多半不是逻辑错误，而是：原始编码是 GB2312 还是 BIG5、当年的驱动器有哪些现在已经没有的 efun、`query_ip_number()` 这种假设了「有网络、有 IP、有操作系统」的调用要怎么办。**代码本身几乎没坏——坏掉的是它对环境的每一个假设。**
> **而这正是 Wasm 在文化保存上真正的价值所在，也是它与虚拟机、仿真器不同的地方。** 一台仿真器（附录 D 案例 3 的 v86）保存的是「硬件」；一个容器映像保存的是「操作系统与依赖」；**而把驱动器编译成 Wasm 保存的是「运行语意」**——它不需要你保存一整台一九九六年的 Linux，只需要保存一个 3.6 MB 的模块和一份规格稳定的宿主接口。**Wasm 因此意外地成为了目前最好的软件保存格式之一**：规范公开、有多家独立实作、向后兼容承诺极强、且宿主环境（浏览器）本身就是人类维护得最认真的兼容性层。
> 反过来说，这也给所有正在写代码的人一个很不舒服的提醒：**你今天写下的每一个对环境的假设——这个 API 会在、这个服务会在、这个格式会被支持——都是在给三十年后的某个人出考题。** 而第 12 章那个「三年后这东西坏在半夜谁会修」的问题，在这里变成了它的最终形态：**三十年后，还有人看得懂你当初为什么那样写吗？** 那些 `NOTES.md`，就是那个问题唯一有效的答案。

## 九、把它放回图鉴：它取代了谁

| 附录 E 的 🔴 构想 | 真实对照 | 差在哪 |
|---|---|---|
| 案例 58 Minestom-Wasm（浏览器内的游戏服务器） | **FluffOS × Wasm** | FluffOS 是真的，而且更硬——它还要在运行期编译用户代码 |
| 案例 60 Micro-Apache-Wasm（浏览器内的服务器引擎） | **FluffOS × Wasm** | Micro-Apache 只处理无状态请求；FluffOS 有心跳、定时器与持久世界状态 |
| 案例 92 OpenLISP-Wasm（符号计算解译器） | **FluffOS 的 LPC 编译器 + VM** | 同一种形状：**把一个语言的完整运行期搬进 Wasm** |
| 案例 34 QuickJS-Wasm（JS inside JS） | **FluffOS 的 LPC inside Wasm** | 同一种形状，但 FluffOS 额外带了一整套游戏运行期 |

**如果附录 D–F 那份图鉴是一张「这条路通不通」的地图，这一篇就是路的尽头那个真的有人住的地方。**
