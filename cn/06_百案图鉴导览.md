**看这张表最该注意的是第 8 类为什么最大**（约占三成）。科学计算领域有一个特殊结构：

- **算法完全公开**（有限元素法、蒙特卡罗、牛顿-拉夫森、FFT——全都是教科书内容，没有商业机密）；
- **既有实作是成熟的 C/C++ 函数库**（GSL、EPANET、OpenVDB、pagmo——移植成本低）；
- **原本的使用门槛高得离谱**（要嘛装 Linux 工作站，要嘛买数万美元的商业授权，要嘛排队等 HPC 集群）；

**这四个条件叠起来，Wasm 的价值不是快，是「把一整个领域的准入门槛打到零」。** 一个研究生打开网页就能跑基因串行比对，一个电力工程师在现场用笔电就能算全网潮流——而且数据一个字节都没有离开他的机器。

**反过来，看哪些领域「不在表上」也同样有消息量**：没有 CRUD 后台、没有电商、没有内容管理、没有社群功能。**因为那些场景的瓶颈从来不是算力，是数据与状态**——而那正是第三篇的主题。

> 🔍 进阶点评──这十类的排列，其实暗示了一条清晰的价值筛选规则
> 把 101 个案例的动机字段摊开来看，会发现它们全部落在四个理由上，而且**这四个理由的权重高低，可以当成一条可操作的决策规则**。**理由一：算力成本转嫁（出现在几乎每一条）。** 算法公开、运算量大、无商业机密——这是 Wasm 最无争议的甜蜜点。**理由二：数据主权（出现在约七成）。** 医疗、金融、国防、个人隐私——「数据绝不离端」在这些领域不是加分项，是准入条件。**理由三：能力缺口（出现在约三成）。** 浏览器不支持 XSLT 2.0、不支持 Graphite 字体、不曝露 Brotli API、不支持 AV1 硬解——Wasm 是唯一的填补方式。**理由四：资产复活（出现在约两成）。** 几十万行的 C++ 几何内核、二十年的游戏、GNU 累积数十年的工具链——重写不可能，编译可行。**这条理由的极致形态是文化保存**：`fluffos/mudlibs` 把一九九〇年代中期到二〇一五年前后的中文 MUD 原代码修复了两百份（涵盖一百五十八个不重复的 codebase），并把 FluffOS 驱动器整台编译成 Wasm，让其中数十个在浏览器里点开即玩——**那些代码本身几乎没坏，坏掉的是它对环境的每一个假设**（见附录 L）。**于是决策规则长这样：你的场景命中的理由越多，Wasm 的投资回报越高；只命中理由一的，要仔细算下载体积与跨界开销的帐；一个都没命中的，别用 Wasm。** 特别要注意的是——**理由二（数据主权）是唯一一个「纯 JS 也能做到，但没人信」的理由。** 技术上，纯 JavaScript 同样可以做到数据不上传；但当你要说服一个律师、一个合规官、一个医院资安部门时，「整套算法编译成一个可被检验的二进位、跑在用户自己的浏览器沙盒里、网络分页上一个外连请求都没有」这个叙事的说服力，远高于「相信我，我的 JS 没有偷传」。**这是一个技术之外的价值——它出售的是可稽核性，而不是性能。**

## 情境 3　五种通用架构模式：101 个案例其实只有五个形状

**背景**：读完 101 条之后你会发现一件事——它们的架构描述长得惊人地像。这不是叙述偷懒，是因为**在 Wasm 的物理定律底下，可行的架构真的只有这几种**。

### 模式一：平坦内存 + 零拷贝视图（Flat Memory / Zero-copy View）

**出现频率：101/101。** 这是所有 Wasm 性能故事的地基。

```
JS 侧：把数据写进 Wasm 的线性内存，或用 TypedArray 开一个视图
                    ↓ 只传指针与长度，不传内容
Wasm 侧：用连续的字节数组处理（Struct-of-Arrays、CSR 稀疏矩阵、
        Roaring Bitmap、内存池、B+ 树……）
                    ↓ 结果写回同一块内存
JS 侧：从指针处读出结果（或直接喂给 WebGL VertexBuffer）
```

**它的真正优势常被说错**。大多数叙述说「因为避开了 JS 的垃圾回收」，这只对了一半。**更重要的是 CPU 缓存。** JavaScript 的对象是离散分配在堆上的，遍历一百万个 `{x, y, z}` 对象意味着一百万次可能的缓存未命中；Wasm 里同样的数据是三条连续的 `Float64Array`，CPU 的预取器（prefetcher）能完美工作。**现代 CPU 的一次 L1 命中约 4 个周期，一次 DRAM 访问约 200 个周期——这 50 倍的差距，才是那些「快 30 倍」数字的真正来源，而不是 GC。**

### 模式二：Worker 隔离 + 可转移对象（Worker Isolation / Transferable）

**出现频率：约 60%。** 只要运算超过 16 毫秒，就必须离开主线程。

```javascript
// 主线程：postMessage 的第二个参数是关键
const buf = new ArrayBuffer(50 * 1024 * 1024);
worker.postMessage({ cmd: "process", buf }, [buf]);
// ↑ 第二参数 [buf] 声明这是 Transferable：
//   不拷贝 50MB，而是把内存所有权转移给 Worker（微秒级）
//   代价：转移后主线程这一侧的 buf 立刻变成长度 0，不能再用
```

**两种数据传递方式要分清楚**：

| 方式 | 成本 | 适用 |
|---|---|---|
| 结构化拷贝（默认） | O(n)，大数据很痛 | 小消息、需要双方都保有数据 |
| **Transferable**（`postMessage(x, [x])`） | O(1)，只转移所有权 | 大 buffer 单向传递 |
| **`SharedArrayBuffer`** | O(1)，双方同时可见 | 真正的多线程共用（**需要跨来源隔离**，见第 5 章） |

### 模式三：SIMD 矢量化（`v128`）

**出现频率：约 40%。** 只要工作是「对一大堆数据做同一件事」，就用得上。

Wasm SIMD 提供固定 128 比特的 `v128` 类型与一组信道操作，一条指令能同时处理 4 个 `f32`、2 个 `f64`、16 个 `i8`。典型加速比在 2~4 倍（不是 4~16 倍——因为内存带宽与数据重排会吃掉一部分）。

```bash
# 打开 SIMD（Rust）
RUSTFLAGS="-C target-feature=+simd128" cargo build --target wasm32-unknown-unknown --release
# 打开 SIMD（Emscripten）
emcc -msimd128 -O3 ...
```

**两个实务陷阱**：**其一，SIMD 是可侦测特性**，老旧浏览器没有，需要准备非 SIMD 的备援建置并在运行期侦测。**其二，Wasm SIMD 只有 128 比特**——原生 AVX2 是 256、AVX-512 是 512。这就是第 2 章说过的：为 AVX2 手写优化的代码移植过来，矢量宽度直接砍半。

### 模式四：串流分块处理（Streaming / Sliding Window）

**出现频率：约 30%，但在「大文件」场景是 100%。** 这是绕开 4GB 上限的唯一实用解（详见第 8 章）。

```
不要：把 10GB 文件整个 read 进线性内存  ❌ 立刻 OOM
要　：在 Wasm 内开一个 50MB 的滑动窗口，
      用 OPFS 的 FileSystemSyncAccessHandle 做 read(buffer, {at: offset})
      像看磁带一样，需要哪一段就去磁盘抓哪一段  ✅
```

MediaInfo 只读 MP4 的 `moov` atom、DuckDB-Wasm 用 HTTP Range Request 只抓 Parquet 需要的字段区块、Tantivy 只下载索引中命中的 block——**全都是同一招。**

### 模式五：AudioWorklet / 高优先线程隔离

**出现频率：所有音频案例（约 6 条）。** 音频线程有一个残酷的硬时限：

```
在 44.1kHz 采样率下，一个 128 采样点的区块 = 2.9 毫秒
→ 你的处理函数必须在 2.9 毫秒内回传，否则就是可听见的爆音
→ 这里容不下任何一次 GC 暂停
→ 所以 AudioWorklet + Wasm 几乎成了业界惯例
```

FLAC 编码、chiptune 合成（libmodplug/GME）、SDR 解调——全部走这条路。

> 💡 君之一席话
> 与君一席话：**当一个领域里所有成功案例的架构长得一模一样时，那不是缺乏创意，那是物理定律在说话。** 101 个案例横跨影音、数据库、基因、电网、天文、金融，领域之间毫无关联，可是它们的架构图几乎可以互相替换——因为它们面对的是同一组限制：**一块平坦内存、一条昂贵的边界、一个 16 毫秒的画格预算、一个 2.9 毫秒的音频预算、一个 4GB 的上限。** 这带来一个非常实用的推论：**当你进入一个新领域时，先去找那个领域里三个成功案例的架构图，如果它们长得很像，那个形状就是这个领域的物理定律，不要试图创新它；如果它们长得完全不同，说明这个领域还没有找到自己的形状，那才是创新的机会所在。** 分辨这两种情况的能力，比任何具体技术都值钱。

## 情境 4　三个代表案例的深水区

**背景**：附录里每案 500 字，这里挑三个把水踩到底——因为它们各自代表一种「Wasm 让不可能变可能」的机制。

### DuckDB-Wasm：静态页上的 OLAP 引擎，以及 HTTP Range 这个大绝

**它做了什么**：把 C++ 写成的字段式分析型数据库 DuckDB 完整编译成 Wasm。用户在网页上输入标准 SQL，在浏览器里对数百万行数据做聚合查找。

**它为什么能赢纯 JS 60 倍以上**（源清单宣称 1000 万行聚合查找 100~200 毫秒完成）：

1. **矢量化运行**：不逐列处理，一次处理一整个 batch（通常 1024~2048 个值）的字段矢量。分支预测友善、SIMD 友善、缓存友善。
2. **Apache Arrow 的字段式内存布局**：数据在线性内存里按栏连续排列，`SELECT SUM(price)` 只需扫过 price 那一条连续数组，完全不碰其他字段。
3. **零拷贝交接**：查找结果以 Arrow 格式停留在线性内存里，JS 端用 `TypedArray` 视图直接读，不做串行化。

**最漂亮的一招是它怎么读远程文件**：

```sql
-- 这一行不会下载整个 Parquet 文件
SELECT region, SUM(revenue) FROM 'https://example.com/sales.parquet' GROUP BY region;
```

Parquet 的文件结构是「数据区块 + 尾端的中继数据（footer）」。DuckDB-Wasm 会：

```
1. 发一个 HTTP Range Request 只抓最后几 KB → 读到 footer，知道每个字段每个 row group 在哪个字节偏移
2. 根据 SQL 判断需要哪些字段、哪些 row group（用 footer 里的 min/max 统计做 predicate pushdown 剪枝）
3. 再发若干个 Range Request，只抓那几段字节
   → 一个 2GB 的 Parquet，可能只下载了 8MB
```

**这就是「静态托管 + Wasm」组合的完整威力**：CDN 提供 Range Request（一个免费且到处都有的能力），Wasm 提供理解文件格式的智能。**你得到了一个没有服务器的数据仓库。**

### Pyodide：把整个 CPython 搬进沙盒，以及那 30MB 的代价

**它做了什么**：把 CPython 解译器本体，加上 NumPy、Pandas、SciPy、scikit-learn 这些**含大量 C 扩充**的科学计算库，整包编译成 Wasm。

**技术上最难的部分不是编译 CPython，是那些 C 扩充**。NumPy 的内核是几十万行 C 代码，它假设自己活在一个有 `dlopen`、有 POSIX 文件系统、有 CPU 特化路径的世界。Pyodide 必须：

- 用 Emscripten 的 **MEMFS/IDBFS** 假造一整套文件系统；
- 处理 Wasm 早期没有动态链接的问题（Emscripten 的 `SIDE_MODULE`/`MAIN_MODULE` 动态链接机制，或全部静态编进去）；
- 实作 **双向类型桥接**：JS 的 `Array` 能被 Python 当 `list` 读，Python 的对象能被 JS 访问，Matplotlib 画的图能转成二进位流由 JS 渲染到 `<canvas>`。

**性能的两层现实**（这个对比极具启发性）：

| 运行什么 | 相对原生的性能 | 为什么 |
|---|---|---|
| 纯 Python 循环 | **约 1/3 ~ 1/5** | 你在虚拟机里跑一个解译器——两层抽象叠加 |
| 调用 NumPy / Pandas 的 C 算子 | **约 70%** | 热循环在 C 里，Wasm 直接运行编译过的机器码 |

**这个 3~5 倍的落差说明了一件事**：Pyodide 的价值不在「跑 Python 快」，在「**让 Python 生态的 C 内核可以在浏览器里被调用**」。用它写密集的纯 Python 循环是误用；用它跑 `df.groupby().agg()` 是正解。

**那 30~50MB 的下载**是它最大的痛点，而现实的缓解手段有三：按需加载套件（Pyodide 支持运行期 `micropip.install`）、用 Service Worker 做持久缓存（第二次造访近乎瞬开）、以及对只需要语言本身的场景改用 **MicroPython/Wasm**（体积小两个量级）。

### v86：在浏览器里跑一台完整的 x86 电脑

**它做了什么**：在纯静态网页里仿真出一台完整的 x86 虚拟硬件——CPU、内存管理单元、IDE 磁盘控制器、VGA、键盘中断。跑得起 Linux、跑得起 Windows 95、跑得起 DOOM。

**它的内核技术是一件很反直觉的事——动态重编译（JIT）**：

```
天真的仿真器：循环{ 读一条 x86 指令 → switch(opcode) → 运行 }
             → 每条指令都要付一次解码与分派成本，慢 100 倍

v86 的做法：把一段 x86 基本区块 → 动态翻译成一段 Wasm 指令
           → 用 WebAssembly.instantiate 即时编译这段 Wasm
           → 之后这段代码每次运行都是原生速度
           → 也就是：JIT 产生 Wasm，再让浏览器把 Wasm JIT 成机器码
```

**这是「JIT 产生 JIT 的输入」的双层结构**，而它能成立，靠的正是 Wasm 一个很少被讨论的特性：**`WebAssembly.Module` 可以在运行期由字节数组动态建构**。换句话说，**Wasm 是一个可以被程序生成的目标格式**，这让它成为所有仿真器、动态语言运行期、乃至于未来 JIT 编译器的天然后端。

**它撞得到的墙也很清楚**：无法使用宿主的硬件虚拟化（Intel VT-x / AMD-V），因为那需要 ring 0 权限；所有内存地址翻译都靠软件仿真的分页表。因此它跑得动 Pentium 级的 32 比特系统，**跑不动现代 64 比特重度操作系统**。

> 💡 君之一席话
> 与君一席话：**判断一个技术平台有没有长期生命力，看一件事就够了——它能不能成为「其他东西的编译目标」。** 一个只能被人手写的格式，天花板是人类的产能；一个能被程序生成的格式，天花板是所有想把自己搬过来的系统的总和。v86 动态产生 Wasm、Pyodide 把 CPython 编过来、Cranelift 把 Wasm 编成机器码、甚至 Wasm 自己也被编成 C 再编回原生（wasm2c）——**这种「人人都能把自己翻译成它」的性质，才是一个中介表示真正的护城河**。这就是为什么 JVM 活了三十年、LLVM IR 统治了编译器后端、而 Wasm 有机会成为下一个。反过来，这也给了一条实用的判准：**当你在评估一个新格式、新协定、新平台时，问一句「有没有第三方在自动生成它？」——如果答案是没有，它多半只是一个工具，不是一个平台。**

## 本章小结

- 那份「120 个案例」实际只有 **101 条不重复**，19 条是重新编号后的重述。这揭示了长对话生成的一个具体失效模式：**没有外部维护的已产出清单时，去重只能靠上下文，而上下文会失效**——而有效的解法是**约束搜索空间（指定新类别），不是要求记忆**。
- 101 条分三个真伪等级：**🟢 可查证（约四成）、🟡 上游真实但 Wasm 移植待考（约四成）、🔴 示意性构造（约两成）**。正确读法是把它当**可行性地图**，不是项目索引。
- 十个类别中**科学与工程计算占了三成**，原因是它同时满足四个条件：算法公开、既有 C 实作成熟、原本准入门槛极高、数据极度敏感。**Wasm 在这里的价值不是快，是把一整个领域的门槛打到零。**
- 101 个案例只有**五种架构形状**：平坦内存零拷贝、Worker 隔离与 Transferable、SIMD 矢量化、串流分块滑动窗口、AudioWorklet 硬时限隔离。**当所有成功案例的架构都一样时，那是物理定律在说话。**
- 「快 N 倍」的真正来源多半被说错了——**不是垃圾回收，是 CPU 缓存**（L1 命中约 4 个周期 vs. DRAM 约 200 个周期）。
- 三个深水案例各代表一种机制：**DuckDB-Wasm** = CDN 的 Range Request + Wasm 的格式智能 = 没有服务器的数据仓库；**Pyodide** = 纯 Python 慢 3~5 倍但 C 算子有 70%，价值在「让生态的 C 内核可被调用」；**v86** = 动态生成 Wasm 的双层 JIT，证明了**Wasm 是一个可被程序生成的编译目标**。
