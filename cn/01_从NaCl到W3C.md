# 第1章　从 NaCl 到 W3C：一个失败的插件，如何长成 Web 的第四种语言

> 二〇一一年，Google 在 Chrome 里塞进一个叫 **Native Client** 的东西，宣称可以在浏览器里跑原生 C/C++。它技术上是成功的，商业上是彻底的失败——因为除了 Chrome，没有任何一家浏览器愿意实作它。十四年后，同一件事被做成了，差别只有一个：**这次没有人自己先动手。**

## 情境 1　那个技术上成功、政治上失败的项目

**背景**：Web 的性能天花板不是新问题。JavaScript 是一门动态类型、垃圾回收、单线程的语言；它在 UI 逻辑上无可取代，但一旦碰上「密集计算」——视频转码、3D 渲染、影像滤波、大矩阵运算——它就撞墙。二〇一〇年前后，这个天花板下有两条路线在互相竞争。

**第一条路：Google 的 NaCl / PNaCl（Native Client / Portable Native Client）**。它的思路直白到近乎粗暴：既然要快，那就**直接跑原生机器码**。NaCl 用一套静态验证器（validator）扫描 x86 机器码，强制指令对齐到 32 字节边界、禁止不安全的跳转与系统调用，再把整段代码关进一个由分段寄存器（segment register）围出来的沙盒里。后来的 PNaCl 更进一步：不再分发 x86 机器码，改分发 **LLVM bitcode**，由浏览器端做最后一哩的翻译，借此摆脱 CPU 架构绑定。

**它为什么失败**：不是因为它慢——它一点都不慢。它失败于三件事：

- **它不是 Web**。NaCl 模块活在一个叫 `<embed>` 的插件容器里，跟 DOM、跟 JavaScript 之间隔着一层消息传递接口。它是**寄生在网页里的原生程序**，而不是网页的一部分。
- **它是一家公司的规格**。Mozilla 公开反对，Apple 与 Microsoft 从未表态要实作。一个只有 Chrome 支持的「Web 标准」，对开发者而言就是一个负债。
- **验证器的复杂度过高**。要在每一种 CPU 架构上写一套能证明其正确性的机器码验证器，是安全工程上极其昂贵的承诺。

**第二条路：Mozilla 的 asm.js**。它的思路完全相反，甚至有点狡猾——**根本不引入新东西**。asm.js 是 JavaScript 的一个**极度严格的子集**：所有数值运算都用比特运算标注类型（`x|0` 代表 32 比特整数，`+x` 代表双精度浮点数），所有内存访问都走一个巨大的 `ArrayBuffer` 类型化数组，禁止对象、禁止闭包、禁止垃圾回收。

```javascript
// asm.js 的典型长相：靠注解标记模块，靠比特运算把类型「写死」在语法里
function AsmModule(stdlib, foreign, heap) {
  "use asm";                          // ← 引擎看到这行，切换到 AOT 编译路径
  var HEAP32 = new stdlib.Int32Array(heap);
  function add(x, y) {
    x = x|0;                          // ← 声明：x 是 32 比特整数
    y = y|0;
    return (x + y)|0;                 // ← 声明：回传值也是 32 比特整数
  }
  return { add: add };
}
```

**这一招的精髓在于：它是合法的 JavaScript。** 在不认识 asm.js 的浏览器里，这段代码照样正确运行（只是慢）；在认识它的浏览器里，引擎看到 `"use asm"` 就跳过整套 JIT 预热流程，直接把它当成静态类型语言做 AOT（提前编译）。**Emscripten** 把 C/C++ 经由 LLVM 编译成这种 JavaScript，第一次让「把整个 Unreal Engine 搬进浏览器」变成可以在会场上演示的事。

**两条路各自证明了一件事**：NaCl 证明了**浏览器沙盒有能力安全地运行接近原生的代码**；asm.js 证明了**不需要插件，光靠引擎优化就能拿到 2 倍以内的原生性能，而且四家浏览器都能实作**。

> 💡 君之一席话
> 与君一席话：**一个技术方案能否活下来，取决于它让多少人「不需要同意」它。** NaCl 要求其他三家浏览器厂商全盘接受一套庞大的新运行环境与机器码验证器——那是要求别人下重注赌你的判断；asm.js 只要求「你什么都不用做，反正它是合法的 JS，只是我做了优化」——那是**把采纳成本降到零，把优化收益留给愿意跟进的人**。前者是政治提案，后者是技术事实。任何跨组织的标准之争里，这条规律都成立：**能在对方零成本的前提下先跑起来的方案，最后会赢；需要对方先付出代价才能开始的方案，通常连讨论的机会都没有。** 这也是为什么 Wasm 最后选择的路，是 asm.js 的政治智能加上 NaCl 的技术野心。

> 🔍 进阶点评──asm.js 的三个致命瓶颈，正是 Wasm 每一条设计的答案
> asm.js 赢得了政治，却输给了物理，而它输的那三处，恰好逐条对应 Wasm 的设计动机。**第一，解析成本。** asm.js 再怎么优化，它终究是**文本**。一个 40MB 的 asm.js 文件，浏览器必须先做完整的 JavaScript 词法与语法分析，才能发现「哦这是 asm.js」。纯解析就吃掉几百毫秒到数秒，而且这笔钱每次冷启动都要付一遍。Wasm 的二进位格式把这一步压缩到近乎为零——它可以**边下载边编译**（streaming compilation），第一个字节到达时编译器就开工了。**第二，类型是靠惯例而非规范保证的。** `x|0` 是一个「引擎请你相信我」的约定；一旦代码稍有偏差，引擎会静默地退回普通 JS 路径，性能断崖式下跌，而开发者往往看不到任何警告。Wasm 的类型是写在二进位里、由验证器在加载时强制检查的——**要嘛通过验证、要嘛拒绝加载，没有中间态。** 第三，**它永远拿不到 JS 没有的东西**。64 比特整数（`i64`）在 JavaScript 里没有原生类型，asm.js 只能用两个 32 比特数仿真；SIMD 矢量指令、原子操作、多线程共享内存，全都无法在 JS 语法里表达。Wasm 一开始就把 `i32/i64/f32/f64` 四种数值类型写进规范。所以真正的历史叙事不是「Wasm 取代了 asm.js」，而是——**asm.js 是一次成功的市场验证实验，它证明了需求真实存在、证明了四家厂商的引擎都能吃下静态类型的优化路径，然后它把自己烧成了 Wasm 的燃料。** 这种「用一个注定被取代的方案，去证明下一个方案值得被投资」的策略，在基础设施演进里反复出现。

## 情境 2　二〇一五：四家厂商为什么突然坐到同一张桌子

**背景**：二〇一五年六月，Google、Mozilla、Microsoft、Apple 共同宣布开发一个全新的二进位格式标准——**WebAssembly**。这在浏览器战争的历史上罕见到近乎反常：四家在几乎所有议题上都互相掣肘的公司，在这件事上一次到位。

**为什么这次能谈成**，关键在于**三个「都不吃亏」**：

| 厂商 | 已投入的资产 | Wasm 保住了什么 |
|---|---|---|
| Google | NaCl/PNaCl 的沙盒与验证器经验、V8 的 TurboFan 后端 | 沙盒技术有了标准化的出口，不必再独自维护一个没人跟进的规格 |
| Mozilla | asm.js、Emscripten 工具链、SpiderMonkey 的 OdinMonkey AOT 路径 | 现有的 Emscripten 生态可以无痛换后端；asm.js 的优化投资不算白费 |
| Microsoft | Edge 需要快速追上性能叙事 | 拿到一个规格明确、实作边界清楚的目标，不必逆向他人的 JS 引擎优化 |
| Apple | JavaScriptCore 的 FTL JIT | 一个「小而封闭」的规格，远比「支持任意 LLVM bitcode」在安全审查上便宜 |

**设计上的关键取舍——它刻意做小**。Wasm MVP（最小可行产品，2017 年落地）刻意**不做**很多事：没有垃圾回收、没有例外处理、没有多线程、不能碰 DOM、没有系统调用、连字符串类型都没有。它只有四种数值类型、一块连续内存、一组堆栈指令，以及一套能在加载时线性时间完成的验证算法。

**这种「刻意做小」是政治上的必要条件**：规格越小，四家独立实作出现行为分歧的几率就越低；验证器越简单，安全审查的成本就越低；能力越少，被拿去做坏事的攻击面就越窄。**Wasm 的 MVP 几乎是一份「我们保证不会吓到你」的协议书。**

**时间线**（可查证的规范里程碑）：

- **2015 年 6 月**：四方共同宣布 WebAssembly。
- **2017 年 3 月起**：Chrome、Firefox、Safari、Edge 陆续内置 Wasm 引擎，MVP 成为四大浏览器的共同能力。
- **2019 年 12 月**：W3C 正式将 WebAssembly Core Specification 1.0 定为推荐标准（Recommendation），Wasm 与 HTML、CSS、JavaScript 并列为 Web 的第四种内核语言。
- **2019 年起**：**WASI**（WebAssembly System Interface）提案面世，Wasm 开始脱离浏览器，进军服务器端、云原生与边缘计算。

> ⚠️ 真伪提醒
> 「四大巨头 2015 年联手」「2017 年四浏览器全面支持」「2019 年 W3C 定为标准」这三件事均为可查证的公开事实。但坊间常见的加料版本——例如把 Wasm 说成「W3C 钦定的第四种编程语言，将取代 JavaScript」——是叙事夸张。**规范文档从未把 Wasm 定位为 JavaScript 的替代品，而是明确定位为互补（complement）**：Wasm 至今无法独立操作 DOM、无法独立加载自己，它的每一次启动都需要 JavaScript（或宿主环境）递给它第一把钥匙。

> 🔍 进阶点评──「刻意做小」的复利，与它现在正在付的利息
> MVP 的极简主义在 2017 年是胜利的关键，但到了 2026 年，它的帐单也全部到期了。**帐单一：没有 GC，等于把整个 Java/Kotlin/Dart/C# 生态挡在门外。** 这些语言必须把自己的垃圾回收器整包编译进 `.wasm`，导致产出动辄数 MB 起跳——这正是后来 **Wasm GC**（让 Wasm 直接复用宿主引擎既有的 GC，**已于 Wasm 3.0 进入内核规范**）的直接动机，而 Wasm GC 落地后，Kotlin/Wasm、Dart（Flutter Web）这类语言的产出体积能大幅缩减。**帐单二：没有例外处理，等于 C++ 的 `try/catch` 只能靠 JavaScript 蹦床（trampoline）仿真**，每一次跨边界都是可观的开销——这是 **原生例外处理**（Wasm 3.0）的动机。**帐单三：没有尾调用，等于函数式语言（Scheme、OCaml、Haskell）的深层递归一定爆栈**——这是 **尾调用**（`return_call`，Wasm 3.0）的动机。**帐单四：只有数值类型，等于每一次字符串往返都要手动编码解码**——这是 **Reference Types**、**JS String Builtins** 一路演化的动机。所以看待 Wasm 提案清单（SIMD、threads、bulk memory、multi-value、reference types、GC、exception handling、tail call、memory64、multiple memories、relaxed SIMD、branch hinting……）的正确方式不是「功能越来越多」，而是——**每一条提案都在偿还 2015 年为了让四家坐上谈判桌而刻意欠下的一笔债。**
> **而这笔债，到 2025 年 9 月基本上还完了。** 那个月 **WebAssembly 3.0 宣布完成**，一次把 **GC、Memory64、例外处理、尾调用、多重内存、具类型的函数参考、扩充常数表达式、分支提示、128 比特 SIMD** 全部收进内核规范。**十年前为了达成共识砍掉的东西，用十年逐条加了回来，而内核模型一次都没有崩。**
>
> 这条规律值得所有做平台的人记住：**为了拿到共识而做的减法，会在你成功之后，变成你必须逐条加回来的技术债；而那笔债能不能还得起，取决于你当初砍掉的东西，有没有破坏内核模型的一致性。** Wasm 还得起，是因为它砍的是「能力」，没有砍「类型安全」与「线性内存」这两根柱子。**如果 2015 年他们为了性能而在类型系统上让步，这十年就不会是还债，会是重写。**

## 情境 3　破圈：WASI，以及那句被反复引用的话

**背景**：二〇一九年，Wasm 走出了浏览器。内核规范里的 Wasm 模块**本来就没有任何系统能力**——它不能开文件、不能创建连接、不能读时钟。所有能力都必须由宿主环境（host）以 **import** 的形式明确递进去。这个设计原本是为了浏览器沙盒，却意外地成了服务器端最想要的东西。

**WASI 做了什么**：它定义了一套**与操作系统无关的标准接口**——文件、时钟、随机数、环境变量、网络（在后续版本中）——让同一份 `.wasm` 可以在 Linux、Windows、macOS 上被同一套语意运行。更关键的是它的安全模型：

- **能力式安全（capability-based security）**：Wasm 模块默认「两手空空」。它没有 `open()` 的权限，只有宿主**预先打开并递给它**的目录句柄（pre-opened directories）。
- **路径逃逸在运行期被拦截**：模块若试图访问 `/sandbox/../etc/passwd`，会被运行期在能力边界上直接挡下，而不是靠文件系统权限碰运气。

```bash
# Wasmtime：把主机的 ./my_storage 映射为 Wasm 眼中的 /sandbox，且只有这一个目录
wasmtime run --dir=./my_storage::/sandbox my_server.wasm
```

**这跟传统服务器进程的差别是质变，不是量变**。一个被攻破的 Node.js 进程，拿到的是**运行它的那个用户的全部权限**；一个被攻破的 Wasm 模块，拿到的是**宿主明确递进去的那几样东西，一样都不会多**。这是「默认拒绝」与「默认允许」的差异。

**那句被反复引用的话**：Docker 创办人 Solomon Hykes 在 2019 年那则广为流传的推文里说——**「如果 2008 年就有 WASM+WASI，我们根本不需要发明 Docker。」**

> ⚠️ 真伪提醒
> 这句话确实存在，且经常被引用；但它常被断章取义成「Wasm 将取代 Docker」。**原推文的下一句是「Wasm 是服务器运算的未来」而非「容器已死」**，而 Hykes 本人也在后续讨论中澄清这是对「轻量、可携、跨平台」这一组性质的称赞，不是声明容器过时。现实里两者是**互补**的：Docker/OCI 隔离的是整个操作系统用户空间，能跑任何既有的二进位；Wasm 只隔离单一应用，换来启动时间与体积的量级优势，但**只能跑「重新编译过」的东西**。实务上最常见的部署形态是 **Wasm 模块跑在容器化的运行期里**（如 Kubernetes 上的 runwasi / Krustlet 一类方案），而不是二选一。

**Wasm 在后端的三个具体优势**（可量化、可验证）：

| 面向 | 容器（OCI / Docker） | Wasm + WASI |
|---|---|---|
| 冷启动 | 数十毫秒 ~ 数秒（拉映像、起 namespace、init 进程） | 微秒 ~ 数毫秒（模块实例化，权重可预先编译缓存） |
| 产物体积 | 数十 MB ~ 数百 MB（含基础映像与操作系统层） | 数十 KB ~ 数 MB（只有你的代码与必要 runtime） |
| 隔离边界 | Linux namespace + cgroup + seccomp（操作系统层） | 内存安全的虚拟机（语言层），加上能力式 API 授权 |
| 跨架构 | 需为每个 CPU 架构各出一版映像 | 单一 `.wasm` 到处跑（由运行期做最后一哩编译） |
| 能跑什么 | 任何既有 Linux 二进位 | **只有重新编译过的东西**（这是最大的现实限制） |

**主要运行期**：**Wasmtime**（Bytecode Alliance 主导，WASI 的参考实作与规范推进者）、**WasmEdge**（CNCF 沙盒项目，针对云原生、微服务与 AI 推理优化，支持在 Wasm 内调用 GPU）、**Wasmer**（强调可携与跨语言嵌入）、**Spin**（Fermyon 出品，用来建构与运行 Wasm 微服务的框架，让开发者用熟悉的语言写 Serverless Function）。

> 💡 君之一席话
> 与君一席话：**能力式安全的真正价值，不在于它更安全，而在于它让「安全」变成一件可以在部署脚本里读懂的事。** 传统的沙盒安全是**否定式**的——你要靠 seccomp 白名单、AppArmor 规则、capability drop 去一条一条剥夺权限，而你永远不确定自己有没有漏掉一条。能力式安全是**肯定式**的——那行 `--dir=./my_storage::/sandbox` 就是这个服务所拥有能力的**完整清单**，多一个字都没有。安全审查从「证明没有漏洞」变成「读懂一行参数」，这是审计成本的量级下降。把这条原理放大，你会在数据库权限、云端 IAM、OAuth scope、浏览器扩展权限里到处看见同一个挣扎：**所有默认全给、事后扣除的权限模型，最后都会演化成默认全无、逐项授予；而每一次这种迁移，都贵到让人拖延十年。**

## 情境 4　它在哪里真的落地了：四个不可辩驳的商业案例

**背景**：技术叙事再漂亮，也不如四个「你天天在用」的产品有说服力。以下四个是 Wasm 最常被引用、且有公开技术文章佐证的重量级落地：

- **Figma**：内核渲染引擎由 C++ 编写并编译为 Wasm。这是网页端能流畅编辑数万个矢量图层的关键。Figma 公开的工程文章记载了从 asm.js 迁移到 Wasm 后**加载时间显著缩短**的实测。
- **Adobe Photoshop Web**：Adobe 把数百万行的 C++ 历史代码通过 Wasm（配合 Emscripten 与后续的多线程、SIMD 支持）移植到浏览器，让用户无须安装就能做专业图层编辑。
- **Google Earth**：早期的 3D 地球需要专属插件（NPAPI 时代的产物），如今通过 Wasm 在浏览器内直接渲染全球 3D 地形。
- **AutoCAD Web**：把累积数十年的 C++ CAD 内核搬上浏览器，工程图档不必再绕路桌面软件。

**这四个案例的共同点，比它们的差异更重要**：它们全都是**「已经有数百万行成熟 C/C++ 资产」的公司**。Wasm 对它们的价值不是「跑得快」，而是**「不用重写」**——把二十年的几何内核、影像算法、字体排版引擎，用一条编译管线搬到一个全新的分发信道上，而不是叫三百个工程师用 TypeScript 重写一遍。

**反过来说，这也划出了 Wasm 不划算的边界**：如果你要做的是一个表单 CRUD、一个博客、一个电商前台，**Wasm 对你毫无价值**，甚至是纯负债（多一层编译、多一份体积、多一套调试困难）。这件事在第 3 章会用限制清单讲得更狠。

> 💡 君之一席话
> 与君一席话：**一项新技术真正的商业价值，往往不在「它能做什么新的事」，而在「它让多少既有的资产免于报废」。** Figma、Adobe、Autodesk 这几家采用 Wasm，图的从来不是性能报表上那几个百分点，而是**几十年 C++ 资产的残值被一次性盘活**——那是一笔帐面上看不见、却大到足以决定一家公司要不要押注新平台的数字。这就是为什么「颠覆式创新」的叙事常常误导人：**真正推动大型组织采用新技术的，往往是保守的动机（保住既有投资），而不是激进的动机（拥抱未来）。** 当你要说服一个组织采用某项技术时，讲「它能让你做到以前做不到的事」通常打动不了决策者；讲「它让你已经付过的那笔钱，在新的信道上再赚一次」才会。

## 本章小结

- Wasm 的前史是两条路线的合流：**NaCl 证明了浏览器沙盒能安全跑接近原生的代码，asm.js 证明了不需要插件就能拿到接近原生的性能且四家都能实作**——前者贡献技术野心，后者贡献政治智能。
- **2015 年四方共识、2017 年四浏览器落地、2019 年 W3C 定为标准**（皆可查证）。谈成的关键是「刻意做小」：没有 GC、没有例外、没有线程、不能碰 DOM——**规格越小，四家独立实作出现分歧的几率越低。**
- 今天的每一条 Wasm 特性（SIMD、threads、GC、exception handling、tail call、memory64、multiple memories……），本质上都是在**偿还 2015 年为了达成共识而刻意欠下的债**——而这笔债在 **2025 年 9 月的 WebAssembly 3.0** 基本还清。
- **WASI 让 Wasm 破圈**，其内核不是「能开文件了」，而是**能力式安全**：模块默认两手空空，所有能力必须由宿主明确递入，且完整清单就写在启动参数里。
- 「如果 2008 年有 WASI 就不需要发明 Docker」确有其言，但**不等于容器已死**——实务上最常见的是 Wasm 跑在容器化的运行期里（真伪待考处见情境 3 ⚠️）。
- Figma、Photoshop Web、Google Earth、AutoCAD Web 的共同点是：它们都握有数百万行成熟 C++ 资产。**Wasm 对它们的价值是「不用重写」，而不是「跑得快」。**

历史讲完了，该看机器本身。下一个问题很具体：**当浏览器拿到那串以 `\0asm` 开头的字节，它到底做了什么？为什么那串字节可以被证明是安全的？** 翻到第 2 章。
