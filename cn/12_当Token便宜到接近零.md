# 第12章　当 Token 便宜到接近零：造轮子的时间陷阱与终局架构

> **「当所有的 App 都可以用 LLM 自己打造／模仿，护城河如何持续？」**
> **「每个人都不想付钱，都自己重新打造轮子。但是 token 的费用如果够便宜，那其实自己打造时只是需要时间。」**
> 这两个问题直接切中了整个软件工程界与创投圈最内核的集体焦虑：**当「写代码」的边际成本归零，所有的软件功能在 LLM 面前都不再具备稀缺性。**
> 而第二句话的推论是对的——**只是它漏算了「时间」这个词里藏着的两笔帐。**

## 情境 1　五道在「代码免费」之后还站得住的防线

**背景**：如果传统的「技术护城河」与「产品功能护城河」将彻底瓦解，那么在一个「全自动软件拷贝」的时代，企业要如何构建新的护城河？以下五条是目前看得见的答案。

### 一、数据引力与状态垄断（Data Gravity & State Monopoly）

**LLM 可以瞬间拷贝代码（code），但它无法拷贝用户的历史数据与关系链（data state）。**

- **代码是流动的，数据是黏稠的**：AI 可以帮你打造一万个仿 Figma 的渲染引擎，但你的公司过去五年累积的数百万个 UI 组件、设计系统、每一次修改的版本历史、以及跨部门的审批评论，**全部保存在原版的云端数据库里**。
- **终局防线**：企业买的不是那段 Wasm 的绘图算力，买的是「**数据的连续性与单一真实来源（single source of truth）**」。数据越多，吸引周边应用的引力就越强——**这绝不是 AI 拷贝一段代码就能搬走的。**

**要补一句技术上的诚实话**：数据引力的强度**与数据的可携性成反比**。如果数据格式是开放的、有完整导出 API、且有第三方能导入，引力就弱；如果是专有格式、导出有损、且没有第二个目的地，引力就强。**所以「数据引力」在实务上，很大一部分是「格式与 API 的设计选择」的结果，而不是数据量本身的自然结果。** 这一点对创建者与采购者同样重要。

### 二、工作流锁定与组织协作网络

软件在现代企业中扮演的角色，本质上是「**组织内部沟通的协议（protocols）**」。

- **功能易拷贝，习惯难迁移**：一间万人规模的公司，从 PM、设计师到前端工程师、QA，所有人已经围绕着某套软件创建起紧密、直觉的跨部门工作流。
- **信任与协作边界**：更换软件不只是换个网址那么简单，它需要动员整个公司的管理成本、重新培训员工、重新通过资安审查。

> **LLM 可以帮你做出一把更完美的吉他，但它无法帮你凭空生出一个有默契的交响乐团。**

### 三、实体世界的硬件锚定与带宽成本

在 LLM 能自己打造所有软件的世界里，算力与带宽等「物理实体资源」将变得更加昂贵。

- 即使 AI 帮你写出了一套超强的去中心化 P2P 协作系统，但在处理**百万级并发、跨国数据中心低延迟同步、巨型文件保存与 DDoS 防御**时，背后都需要实实在在的云端硬件基础设施与庞大的电费、带宽成本。
- **这些实体资源的护城河，是纯软件 AI 无法用代码凭空变出来的。**

**这一条在 AI 时代的权重正在上升而非下降**——因为当软件变便宜，剩下的稀缺性就会全部往「不能被软件拷贝的东西」聚集：电力、土地、光纤、GPU 产能、以及取得它们的长期合约。

### 四、企业级合规、责任背书与信任溢价

这在 B2B 市场中是绝对的物理定律。大型企业（金融、医疗、跨国科技）采购软件时，第一要素从来不是「功能多便宜」，而是「**合规与风险承担**」。

- **谁来负责（accountability）**：一个由 LLM 自动生成的山寨版 App，如果因为一个边界条件漏洞发生数据外泄，或在半夜大死机导致企业损失百万美元，**该由谁来负责？**
- **工业级壁垒**：SOC 2 Type II 安全认证、ISO 27001、99.99% 的 SLA 保障、以及随叫随到的专业售后工程师团队——**这才是企业愿意支付高额订阅费的真正原因。企业买的是「出了事有人能背锅、能赔偿」的信任溢价。**

### 五、插件与 AI 代理人的双向生态系

当代码被看光、被任意拷贝时，护城河将从「软件本身」转移到「**围绕软件建构的动态生态系**」。

- **App Store 的翻版逻辑**：AI 即使拷贝了主程序，那个插件市场是空的。
- **AI 代理人锁定（agentic lock-in）**：在未来，各种自律 AI 代理人会被派去各个平台运行任务。**如果某个平台成为了全行业 AI 代理人默认对接的「标准 API 与数据格式」，那么其他用 LLM 模仿出来的软件，因为没有打通这些 AI 生态链的上下游，依然会沦为无人问津的数字孤岛。**

**第五条是最新、也最值得注意的一条**：它意味着在 AI 时代，「**你的 API 是不是 AI 代理人的默认选项**」会变成一个全新的竞争维度——就像 2010 年代「你的 App 有没有进 App Store」一样。

### 一个已经跑了三十年的对照实验

**这五道防线听起来都很有道理，但它们都缺一个东西：时间验证。** 我们怎么知道「代码免费之后价值会迁移到数据与社群」不只是一句安慰话？

**有一组样本可以回答这个问题，而且它已经跑了三十年。**

一九九〇年代的中文 MUD——那些用 LPC 写成的文本武侠世界——**它们的全部原代码从第一天起就是可以被完整下载的**。世界地图、NPC 对话、武功系统、经济规则、每一个房间的描述，全都在那个叫 mudlib 的目录里。当年靠打包传档，今天靠 `git clone`，而现在**整台驱动器被编译成了 WebAssembly，你可以在浏览器里直接点开它们**（见附录 L）。

**保密程度为零、拷贝成本为零、修改门槛极低。** 按照「代码是资产」的旧逻辑，这种东西早该被更好的拷贝品淹没。

**可是没有。** 它们活了三十年，在原作者离开之后仍被反复分支、修改、重开；而今天还有人花大量心力去修复两百份残破的封存盘，逐个转编码、修 bug、写下每一处改动的纪录——**只为了让它们能被再次打开。**

**这就是那五道防线的实测结果**：用户要的从来不是「一份能跑的代码」，而是**那个世界，以及那个世界里的人**。而那两样东西，`git clone` 拿不走，LLM 也生不出来。

> 💡 君之一席话
> 与君一席话：**当一种资源的生产成本归零时，价值不会消失，它会迁移到「与那种资源互补的稀缺品」上。** 印刷术让文本的拷贝成本归零，于是价值从「拥有书」迁移到了「作者的声誉」与「编辑的筛选」；串流让音乐的拷贝成本归零，于是价值从「唱片」迁移到了「演唱会」与「艺人本身」。现在 LLM 让代码的生产成本归零，于是价值正在从「软件」迁移到**数据、关系、责任与生态**——这四样东西的共同点是：**它们都无法被拷贝，因为它们根本不是信息，是关系。** 所以每当一项技术宣称「让 X 变得免费」时，最值钱的问题不是「那 X 的生意怎么办」，而是——**与 X 互补、而且没有跟着变便宜的那个东西是什么？** 答案所在之处，就是新的价值中心。

## 情境 2　时间陷阱：你需要的不是「打造时间」，是「Debug 的机会成本」

**背景**：那句追问说得很准——「token 的费用如果够便宜，那其实自己打造时只是需要时间」。**这个推论完全切中了 AI 时代软件商品化的内核物理本质。**

**LLM 写出十万行高性能代码（包含复杂的 Wasm 矩阵运算与数据库）可能只需要五分钟，token 费用只要一块钱。**

**但软件工程最硬核的定律是：写代码占 20% 的时间，Debug 和处理边界条件（edge cases）占 80% 的时间。**

**这条路会撞上两面高墙**：

### 第一面墙：那 5% 的极端场景

- **轮子转动时**：AI 帮你捏好的专属设计软件或 ERP，在 95% 的常规场景下跑得非常完美。
- **物理撞墙期**：到了第 96% 的极端场景——**例如浏览器因为操作系统更新，突发调整了 OPFS 的保存配额；或是多人连接时，网络突发产生了极罕见的分布式状态冲突**——你的专属轮子突然卡死了。
- **隐形代价**：此时，你必须亲自或叫 AI 去排查那十万行代码。这个过程消耗的**专注力、精力与时间机会成本**（你原本可以用这些时间去谈生意、陪家人或研发内核业务），会立刻远远超过你付给原厂每个月几十美元的「买断免烦恼」订阅费。

**这里值得补一段更精确的分析，因为它是本章最实用的部分**：

**AI 造轮子时，成本结构发生了一个关键的形变**——

```
传统开发：
  写代码成本  ████████░░  高（需要工程师）
  Debug 成本    ████████░░  高（需要工程师）
  → 两者同数量级，团队会自然地在「写」与「修」之间平衡

AI 辅助开发：
  写代码成本  ░░░░░░░░░░  趋近零
  Debug 成本    ████████░░  高（仍然需要理解系统的人）
  → 两者差距达到数个量级
  → 结果：产出代码的速度远超过「理解代码」的速度
  → 于是「没有人真正读懂的代码」以前所未有的速度累积
```

**这个形变的后果不是「开发变快了」，是「未被理解的代码库的增长率变快了」。** 而系统的可维护性，取决于后者而不是前者。

### 第二面墙：系统的维护熵增

**软件不是石头，它是活的有机体。** 操作系统会升级、浏览器会更新 API 规范（例如对 WebGPU 或 Wasm 多线程的安全性限制随时在变）。

- **造轮子的隔天**：你用极便宜的 token 造好了一个完美的 ERP。
- **两年后的灾难**：W3C 废弃了某个你的轮子高度依赖的底层 API。你的轮子突然在客户面前崩溃了。
- **熵增爆炸**：你当时是用 LLM 一键生成的，**你或你的员工根本没有人真正读懂这十万行代码的底层架构**。你必须重新请 LLM 来理解这堆「两年前的旧轮子」，甚至必须整个打掉重练。

**这种长期维护的技术债与生命周期成本，是自主造轮子者最容易忽略的巨大盲点。**

**用第 5~8 章的具体技术当例子，让这件事更具体**：

| 你的轮子依赖的东西 | 它在两年内可能怎么变 |
|---|---|
| `SharedArrayBuffer` + COOP/COEP | 隔离要求可能收紧；`coi-serviceworker` 依赖的行为推论可能被规范明确化或收窄（见第 5 章 🔍） |
| OPFS 的 `createSyncAccessHandle` | 配额政策、驱逐策略、跨分页锁语意都可能调整 |
| `wasi_snapshot_preview1` | **已经在被 WASI 0.2 取代**——这不是假设，是正在发生的事 |
| Emscripten 的 MEMFS/IDBFS | 官方方向已转向 WasmFS |
| 特定的 Wasm 提案（GC、EH、tail call） | 语意在标准化过程中曾多次调整 |

**一个没人读懂的十万行系统，撞上这五项中的任何一项，都会变成一次「请 AI 重新理解整个项目」的重型作业。** 而且每一次，你都是在赌 AI 这次能理解得跟上次一样好。

> 🔍 进阶点评──「造轮子变便宜」真正改变的，是规模的分布而不是总量
> 这一节值得再往前推一步，因为它预测了未来十年软件业的形状。**当造轮子的成本从「三个工程师六个月」降到「一个人一个下午」，改变的不是「有没有人造轮子」，而是「什么尺寸的轮子值得造」。** 过去，一个只有你自己会用的工具（个人记帐、私人 CRM、给你团队五个人用的排班系统）永远不值得开发——因为固定成本压过了收益。现在它值得了。**于是市场会裂成两半：一半是「小到不值得买、但现在值得自己造」的长尾，另一半是「大到自己造不起、必须买」的内核系统。而中间那一层——那些平庸的、功能单一的、轻量级的 SaaS 小工具——会被彻底消灭。** 这对从业者的意涵很具体：**如果你的产品可以被一个人在一个下午用 AI 拷贝出九成，你就在被消灭的那一层里。** 而唯一的出路不是把产品做得更复杂（复杂度也可以被 AI 拷贝），而是往两端走——**要嘛下沉到长尾里去做「帮别人造轮子的工具」，要嘛上升到那些需要规模、数据、责任与生态才能运作的内核系统。** 中间地带正在消失，而且消失的速度取决于 token 价格下降的速度。

## 情境 3　终局时代的两种护城河形态

**背景**：当「自己造轮子」变得如此廉价，商业模式必然会走向两种终极形态。

### 形态一：买保险与背书（The Insurance Model）

**这也是为什么科技巨头永远不缺自建软件的能力，却依然大量采购外部 SaaS。**

企业不想付钱买软件，但企业极度愿意**付钱买「出事有人赔、有人在十五分钟内通宵修好」的服务等级协议（SLA）**。

**在商业世界里，付钱给 Figma 或大型 ERP 厂商，本质上不是买功能，是买「风险外包」的保险。**

**这一条在 AI 时代反而会强化，理由很直接**：AI 生成的系统越多，「这东西出事谁负责」就越是一个没有答案的问题。**而没有答案的问题，会让有答案的供应商变得更值钱。**

### 形态二：标准协议与互通性（The Protocol Standard）

如果每家公司都用 LLM 为自己量身打造一套专属 ERP 或设计软件，那当两家公司需要合作、对接订单或共同设计同一个产品时，他们的「自建轮子」因为数据格式、API 接口完全不同，会面临严重的「**数字巴别塔**」危机。

**此时，谁能定义全球通用的「标准数据协议与生态总线」，谁就握有无法被 AI 拷贝的终极护城河。**

**这一条有一个很强的历史模拟**：当桌面出版工具百花齐放时，真正的赢家不是最好用的排版软件，是 **PDF**；当即时通信 App 遍地都是时，撑住企业互通的是 **SMTP/email**。**协议的价值来自「所有人都同意」，而「所有人都同意」是 AI 生成不出来的东西——它需要时间、需要协调、需要多方的既得利益绑定。**

### 未来会分化成两种人

| | 独立个体与小团队 | 现代工业与大企业 |
|---|---|---|
| 行为 | 全面利用极便宜的 token，疯狂打造完全属于自己的、高度客制化的「微型小轮子」（客制记帐、微型 CRM、专属工具） | 依然选择付钱给顶级供应商 |
| 理由 | 客制化的价值 > 维护成本（因为规模小、需求稳定、坏了自己修） | **把时间花在自己的内核印钞机业务上，把造轮子与修轮子的技术熵增外包出去，才是整体回报率（ROI）最高的黄金决策** |
| 后果 | **彻底消灭所有平庸、功能单一的轻量级小软件公司** | 顶级供应商的集中度上升 |

> 💡 君之一席话
> 与君一席话：**「我可以自己做」与「我应该自己做」之间，隔着一整个生命周期的成本。** 这句话在 AI 时代变得前所未有地重要，因为 AI 极大地缩短了「我可以」的距离，却几乎没有缩短「我应该」的距离——**维护、升级、调试、承担后果，这四件事的成本没有跟着 token 一起下降。** 于是会出现一个危险的认知落差：**造轮子的门槛塌了，养轮子的门槛没塌，而大多数人是在门槛塌掉的那一刻做决定的。** 判断自己该不该造，有一条很简单的检验：**问「三年后，这东西坏在半夜，谁会修它，他还在不在公司？」** 如果这个问题没有清晰的答案，那你造的不是轮子，是债。

## 情境 4　终局架构：一颗「免维护、零服务器成本、极致性能」的专属引擎

**背景**：既然结论是「小团队会造自己的轮子」，那就把这个轮子的架构规划出来——**一套在 token 边际成本归零的时代，最能打、最不易引发技术债的次世代微型高性能 Wasm 专属应用架构蓝图。**

**内核思想**：**将「高维护成本」的底层零件完全商品化、标准化，把「高算力、高隐私、高客制化」的业务内核，通过 Wasm 死死熔接在前端。**

### 三大防御性架构原则

为了防止你自己造的轮子在两年后因为浏览器更新或技术熵增而崩溃，必须遵守这三条死纪律：

**原则一：宿主环境零依赖（Host-Agnostic Isolation）**

不要让 Wasm 代码深度绑定任何特定的 JavaScript 前端框架（如 React/Vue 的特定版本）。Wasm 内部必须保持标准的 ANSI C++ 或纯粹的 Rust 逻辑，**只通过标准的二进位网页 API（Canvas 2D/WebGL、OPFS）与实体硬件对接。**

> **这样不论未来的 JavaScript 框架怎么改版，你的 Wasm 内核轮子永远不会坏。**

**这条原则的技术根据**：Web 平台的**标准 API 有极强的向后兼容承诺**（「不要破坏 Web」是浏览器厂商的首要工程原则），而**框架没有**。React 18 → 19 的 breaking change 比 Canvas API 十年来的变化还多。**把内核绑在标准上，把外壳绑在框架上，让外壳可以被便宜地重写。**

**原则二：定型化数据协议（Structured Protocol Buffers）**

Wasm 与外部通信，一律不使用灵活但容易格式崩溃的 JSON。全面采用 **Protocol Buffers 或 FlatBuffers** 作为数据串行化协议。

**这能确保不论你以后用 LLM 怎么修改前端或后端的零件，数据通信的「数字巴别塔」协议永远锁定，绝不相冲突。**

**补充两个技术理由**（除了稳定性之外）：

- **FlatBuffers 支持零拷贝读取**——不需要反串行化就能直接读字段，这正好对应第 2 章「边界是收费站」的优化方向。
- **schema 是机器可读的契约**——这在 AI 时代有一个新的价值：**当你叫 LLM 修改某一侧时，schema 是它唯一不能自由发挥的地方**，也就是你手上最有效的约束工具。

**原则三：无状态运算流（Stateless Compute Window）**

将 Wasm 虚拟机当作一个纯粹的「黑盒处理器」。数据从 OPFS 读进来，在 Wasm 内存内进行极速运算、渲染，完成后立刻把状态写回硬盘并清空内存。

**这能完美防范 wasm32 先天 4GB 的内存溢出（OOM）致命盲点**（见第 8 章）。而且因为 Wasm 实例化极便宜（微秒级），**「用完就丢掉整个实例」在 Wasm 里是一个可以常规使用的手段**，而不是最后的补救。

### 四层内核拓扑架构

```
┌─ 第 1 层：接口与事件调度（Pure HTML5 / JS）──────────────────┐
│  职责：只捕获鼠标点击、键盘输入，以及基础的 DOM 配置          │
│  硬纪律：此层不允许包含任何内核计算算法                     │
│         它只是一个「显示面板（Display Panel）」               │
│  → 这一层是消耗品，允许每三年被 LLM 用当红框架重写一次        │
└──────────────────────────┬───────────────────────────────────┘
                           │ postMessage + Transferable Objects
                           │ （内存所有权转移，零拷贝）
┌─ 第 2 层：独立线程异步总线（Web Worker）──────────────┐
│  职责：启动独立 Worker，将整套 Wasm 保存与运算内核加载其中    │
│        彻底与 UI 主线程隔离                                │
│  内核优化：postMessage(buffer, [buffer]) 显式打开 transfer   │
│           → 操作系统级的内存所有权转移，开销趋近零          │
│  附带收益：createSyncAccessHandle 只能在 Worker 里用          │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌─ 第 3 层：业务内核 Wasm 引擎（Rust / C++）───────────────────┐
│  职责：运行专属轮子的硬核功能                                 │
│        （财务 ERP 的聚合矩阵、3D 几何轨迹规划、全文检索…）     │
│  安全防御：opt-level = 3, lto = true, strip = true            │
│           即便被下载，也毫无被逆向的商业价值                   │
│  → 这一层是资产，设计目标是十年不动                           │
└──────────────────────────┬───────────────────────────────────┘
                           │ FileSystemSyncAccessHandle
┌─ 第 4 层：高性能持久化保存（OPFS Sync API）─────────────────┐
│  职责：利用 Worker 内专属的 createSyncAccessHandle()          │
│  架构优化：让 Wasm 能像本机 C 程序一样，用完全同步、           │
│           零 Promise 开销的极速磁盘 I/O                       │
│           进行分块滑动窗口的随机文件读写                       │
│           → 彻底打通 4GB 内存极限                           │
└──────────────────────────────────────────────────────────────┘
```

**这个架构最重要的性质，在图上看不出来**：它把系统分成了**「消耗品」与「资产」两层**。

- 第 1 层是消耗品：绑死在当红框架上，**设计目标就是「可以被便宜地丢弃重写」**。
- 第 3、4 层是资产：只依赖标准 API 与二进位协议，**设计目标是十年不动**。
- 第 2 层是防火墙：用 `postMessage` + 定型化协议把两者隔开，**确保消耗品的腐烂不会蔓延到资产**。

**这正是对抗「维护熵增」的唯一有效结构**——不是让所有东西都不腐烂（做不到），而是**让腐烂被限制在你愿意丢弃的那一层里**。

**给 AI 代理人的完整规格书范本**（可直接使用，见 **附录 H**）：本章的架构蓝图已整理成一份可以直接贴给 Claude Code 或其他编码代理人的系统规格书，包含依赖设置、内核实作、Worker 隔离与基准测试四个阶段的完整指令，以及三种保存机制（OPFS / IndexedDB / WASI）的专属调校指令。

> 💡 君之一席话
> 与君一席话：**对抗腐烂的正确方式，不是让每一部分都坚固，而是决定哪些部分「可以烂」。** 一个所有部件都设计成十年不变的系统，会在第三年因为无法适应变化而整体报废；一个所有部件都跟着潮流走的系统，会在第二年陷入无止尽的迁移。真正活得久的系统，都有一条清楚的分界线：**内核用最保守、最标准、最无聊的技术写，外壳用最方便、最当红、最容易找到人的技术写，然后在中间放一个窄到不可能出错的接口。** Unix 的文件描述符、浏览器的 DOM、数据库的 SQL、网络的 IP——每一个能活三十年以上的东西，都是这个形状。**当你设计任何要活很久的东西时，先画那条线，再开始写代码。**

## 本章小结

- **五道在「代码免费」之后还站得住的防线**：数据引力与状态垄断、工作流锁定与组织协作、实体硬件与带宽锚定、合规与责任背书、插件与 AI 代理人生态。
- 补充的诚实话：**数据引力的强度与数据可携性成反比**——它很大程度是「格式与 API 设计选择」的结果，不是数据量的自然结果。
- **「造轮子只是需要时间」的推论是对的，但漏算两笔帐**：**时间陷阱**（写 20%、Debug 80%，而 AI 只让前者归零）与**维护熵增**（W3C 废弃一个 API，而没有人真正读懂那十万行）。
- AI 辅助开发真正的形变不是「开发变快」，是——**产出代码的速度远超过理解代码的速度，于是「没有人真正读懂的代码」以前所未有的速度累积。**
- **市场会裂成两半**：长尾（小到不值得买、现在值得自己造）与内核（大到自己造不起、必须买），而**中间那层平庸的轻量级 SaaS 会被消灭**。出路是往两端走（见情境 2 🔍）。
- 终局的两种护城河形态：**买保险（SLA 与究责）** 与 **标准协议（PDF、SMTP 的位置）**——后者的价值来自「所有人都同意」，而那是 AI 生成不出来的。
- **终局架构的三条死纪律**：宿主环境零依赖（绑标准不绑框架）、定型化数据协议（Protobuf/FlatBuffers，schema 是你约束 LLM 最有效的工具）、无状态运算流（用完丢掉整个实例）。
- 四层拓扑最重要的性质在图上看不出来：**它把系统分成「消耗品」与「资产」两层，并用一个窄接口隔开**。对抗腐烂的方式不是让一切都坚固，而是**让腐烂被限制在你愿意丢弃的那一层里**。

## 全书终章：回到那个下午三点四十分

那条对话从「请细说 WebAssembly 的发展史」开始，在一个多小时后停在「请规划」两个字上。中间经过了一百二十个案例、四层保存架构、一个 4GB 的天花板、一次「不是被看光了吗」的追问，以及一场关于 AI 时代护城河的思辨。

**如果要把整趟旅程压成一句话，那句话是**：

> **能被下载的，迟早会被拷贝；不能被搬走的，才是护城河。**

而这句话最好的证据，不在硅谷，在一批一九九〇年代的中文文本游戏里——**它们的原代码被完整拷贝了三十年，而它们至今还在**（附录 L）。

Wasm 是一项极其优秀的技术——它把运算安全地、廉价地、无限地推到了世界上每一台电脑的边缘。**而正因为它太成功，它同时摧毁了「代码是资产」这个延续了半世纪的假设。**

所以这本书真正的结论，不是一份技术清单，是三个问题。**每次你要动手造东西之前，先问自己**：

1. **这段运算，是不是「重、公开、无机密」的？** 是的话，把它编译成 Wasm，推给客户端，省下的钱是纯利。
2. **这段东西被逐字公开之后，我还剩下什么？** 如果什么都不剩，它不该在客户端；如果还剩下数据、关系、责任与生态，那客户端随便看。
3. **三年后这东西坏在半夜，谁会修它？** 这个问题没有清晰答案之前，你造的不是轮子，是债。

**如果你想要一个更狠的版本的第二题**，把它换成那些 mudlib 已经回答过的形式：

> **如果我的原代码明天全部公开，三十年后还会有人在用它吗？**

车库的灯可以关了。**现在你知道那台机器怎么运转、能跑在哪里、以及它跑起来之后，价值到底留在了谁的手上。**
