## 一、三问决策流程

```
对每一个功能模块，依序问三个问题：

┌─────────────────────────────────────────────────────────┐
│ 问题一：这段逻辑如果被逐字公开在博客上，我的生意会受影响吗？ │
└─────────────────────────────────────────────────────────┘
        │
        ├─ 不会 ──→ 【放前端 Wasm】省钱、省带宽、提升隐私、无限并发
        │
        └─ 会 ──→ 继续问问题二
                  │
┌─────────────────────────────────────────────────────────┐
│ 问题二：它需要的运算量，值得我为它养一台服务器吗？             │
└─────────────────────────────────────────────────────────┘
        │
        ├─ 值得 ──→ 【标准后端服务】
        │
        └─ 不值得 ──→ 继续问问题三
                      │
┌─────────────────────────────────────────────────────────┐
│ 问题三：能不能拆成「前端算、后端验」？                        │
│（验证通常比计算便宜几个量级：排序很贵，检查是否已排序很便宜）    │
└─────────────────────────────────────────────────────────┘
        │
        ├─ 能 ──→ 【混合：Wasm 算 + 轻量后端验】★ 最优解
        │
        └─ 不能 ──→ 【必须放后端】并接受它的成本
```

## 二、分类对照表

### ✅ 放前端 Wasm（运算重、算法公开、无机密）

| 类别 | 例子 |
|---|---|
| 媒体处理 | 转码、滤波、去背、缩略图、格式转换、波形分析 |
| 几何与渲染 | 3D 矩阵、布尔运算、网格化、路径规划、物理仿真 |
| 数据处理 | 本地 SQL 查找、聚合、排序、全文检索、压缩解压 |
| 解析与转译 | 语法解析、AST、代码转译、格式转换、Markdown |
| 标准算法 | FFT、卷积、有限元素、蒙特卡罗、牛顿法、A* |
| 密码学运算 | 加解密、签章、哈希、ZKP 证明生成（**算法公开，密钥不进二进位**） |
| 边缘 AI 推理 | 影像分类、OCR、对象侦测、轻量 LLM |

### ❌ 必须放后端（泄漏即灾难，或需要单一权威）

| 类别 | 为什么 |
|---|---|
| **密钥、密码、签章私钥** | `strings` 一秒抓出（第 9 章禁区一） |
| **鉴权与授权判断** | 客户端不可信，任何自证都能被本地改掉 |
| **扣款、额度、计量** | 涉及金钱，必须有单一真实来源 |
| **稽核日志** | 必须不可窜改 |
| **多人协作的冲突解决** | 需要权威仲裁与单一状态（Figma 的 CRDT 引擎） |
| **数据所有权与访问控制** | 权限撤销必须在服务器端生效 |
| **内核商业机密算法** | 判准：对手明天拿到它，我还剩什么？ |
| **合规要求数据落地的处理** | 审计问的是「数据存在哪里、谁能访问」 |

### ⚖️ 可拆成「前端算、后端验」（最有价值的一类）

| 场景 | 前端做 | 后端做 |
|---|---|---|
| 文件上传 | 本地压缩、切块、算哈希 | 验证哈希、检查配额与权限 |
| 表单 | 即时验证、格式化 | **再验一次**（前端验证只是体验，不是安全） |
| 大文件处理 | 完整处理，只传结果摘要 | 验证摘要合理性 |
| ZKP | 生成证明（贵） | 验证证明（便宜几个量级） |
| 影像处理 | 滤镜、裁切、压缩 | 验证输出格式与大小 |
| 调度 / 优化 | 求解（NP-Hard，贵） | 验证解的可行性（便宜） |
| 搜索 | 本地索引检索 | 只在需要跨用户数据时介入 |

## 三、混合架构的接口设计原则

```
┌──────────── 客户端（可被完整下载）─────────────┐
│  Wasm 计算内核                                │
│  · 只依赖标准 Web API（Canvas/WebGL/OPFS）      │
│  · 不含任何密钥或明文机密                       │
│  · 以 strip/lto 编译                           │
└───────────────────┬───────────────────────────┘
                    │ ★ 这条线的四个设计原则：
                    │
                    │ 1. 接口要窄：能传摘要就不传全量
                    │ 2. 接口要粗：一次请求换一批结果，不要细碎往返
                    │ 3. 接口要有 schema：Protobuf/FlatBuffers，不要裸 JSON
                    │ 4. 接口要假设对面是敌人：所有输入都当成恶意的
                    │
┌───────────────────┴───────────────────────────┐
│  后端 API（你完全控制）                        │
│  · 短期、限定范围的 token（绝不下发长期密钥）    │
│  · 所有授权判断在这一侧，不信任何客户端声明       │
│  · 可以极轻量（Lambda / Workers 就够）          │
└───────────────────────────────────────────────┘
```

**四条反模式**（看到就要警觉）：

| 反模式 | 为什么错 |
|---|---|
| 前端计算一个「是否有权限」的布尔值传给后端 | 客户端可以直接改成 `true` |
| 后端信任前端传来的价格 / 折扣 / 数量 | 同上 |
| 用前端 Wasm 的哈希做完整性校验 | 客户端自我校验永远能被绕过 |
| 把「短期 token」设成半年有效 | 那就是长期密钥了 |

## 四、护城河自评表

> 对你的产品逐条打分（0 = 完全没有，3 = 极强）。

| # | 护城河类型 | 检验问题 | 时间常数 | 分数 |
|---|---|---|---|---|
| 1 | **技术领先** | 开源社群要多久才能做出等效的东西？ | **1–3 年** | ☐ |
| 2 | **数据引力** | 用户累积的数据，换平台后会损失多少？ | 5–15 年 | ☐ |
| 3 | **工作流锁定** | 换掉我，客户要重新培训多少人、改多少流程？ | 5–15 年 | ☐ |
| 4 | **网络效应** | 用户越多，对每个用户越有价值吗？ | 5–15 年 | ☐ |
| 5 | **生态系** | 有多少第三方为我做了沉没的专用投资？ | 5–15 年 | ☐ |
| 6 | **实体资源** | 我掌握了什么软件变不出来的东西（算力、带宽、产能、合约）？ | 长 | ☐ |
| 7 | **合规与究责** | 我能签下 SLA 并在出事时赔偿吗？竞争者能吗？ | **10 年+** | ☐ |
| 8 | **标准协议** | 别人是否必须导入到我的格式才能互通？ | 长 | ☐ |
| 9 | **AI 代理人生态** | AI 代理人运行任务时，会不会默认对接我的 API？ | 新兴 | ☐ |

**判读方式**：

- **只有第 1 项高分** → **危险**。三年内会被追平，而且你可能还没创建起任何别的东西。**正确动作：用技术领先换取时间，去创建 2–5 项。**
- **2–5 项有高分** → 稳固。这是大多数成功 SaaS 的位置。
- **6–8 项有高分** → 极稳固，**且不受 AI 侵蚀**。
- **第 9 项** → 新的竞争维度，2026 年才开始成形。

## 五、采购方的镜像清单（同一张表，反过来读）

> 供应商创建锁定是理所当然的；客户评估锁定也是理所当然的。**这不是道德问题，是对称的商业判断。**

```
□ 我的数据能不能完整导出？导出格式是开放的还是专有的？
□ 导出之后，有没有第二个地方能导入它？（有没有真的试过？）
□ 版本历史、评论、权限设置这些「周边数据」能不能一起带走？
□ 我的自动化流程绑死了多少专有 API？
□ 如果这家公司明天涨价三倍，我的最坏情况是什么？
□ 如果这家公司明天倒闭，我的数据还在吗？
□ 我有没有定期演练过「导出并在别处还原」？
□ 我付的钱里，有多少是买功能，有多少是买「出事有人赔」？
```

**最后一条最重要**：如果你付的钱**主要是买功能**，那在 AI 时代你有机会自建；如果**主要是买责任外包**，那自建反而是把风险扛回自己身上（第 12 章的时间陷阱）。

## 六、三年后的自我检查

> 第 12 章的内核问题，值得单独列出来，写进每一次架构评审的议程。

```
□ 这个东西三年后坏在半夜，谁会修它？他还在公司吗？
□ 有没有第二个人读懂过这段代码的底层架构？
□ 我依赖的标准 API，有哪几个在标准委员会里还在变？
□ 如果我依赖的某个浏览器行为明天被收紧（例如 OPFS 配额、
   跨来源隔离规则、某个 Wasm 提案的语意），我的降级路径是什么？
□ 我的「消耗品层」与「资产层」分开了吗？
   腐烂会被限制在我愿意丢弃的那一层里吗？
□ 我的 schema 稳定吗？它是我约束未来所有改动最有效的工具吗？
```

**如果第一个问题没有清晰的答案，你造的不是轮子，是债。**
