# 第3章　优点、缺点，与那些说不出口的限制

> 一份技术评估文档里最没用的东西，是那张「优点五条、缺点三条」的表。因为缺点永远写得比优点客气，而真正会杀死项目的，往往是第四条没写出来的那个。这一章把三个维度的限制摊开：**浏览器端、系统与架构、开发与生态**——并且逐条追问「它为什么是这样」。

## 情境 1　四个优点，以及它们各自的隐藏条款

**背景**：Wasm 的优点在任何一篇入门文里都能找到。但每一条优点底下都有一行小字，而那行小字才是工程决策要看的。

**优点一：接近原生的性能。**

- **它为什么快**：二进位格式解析成本极低、静态类型让编译器不必插入类型检查、没有垃圾回收器在背后随机暂停、线性内存布局紧凑因此 CPU 缓存命中率高。
- **隐藏条款**：这四项优势**全部只在「密集计算」的形状下成立**。如果你的代码大部分时间在等网络、在改 DOM、在拼字符串，Wasm 一项也帮不上，而且你还多付了模块下载与跨界开销。**Wasm 的性能优势是有门槛的，计算量不够大就是负收益。**

**优点二：沙盒安全性。**

- **它为什么安全**：默认在内存安全的隔离环境中运行，无法访问宿主资源，所有能力必须显式 import。
- **隐藏条款**：**「沙盒安全」保护的是宿主，不是你的程序。** 而且在后端场景，那个沙盒是不是真的密不透风，取决于运行期的实作品质——Wasm 运行期是一大坨含 JIT、信号处理器与内存映射管理的复杂软件，**而那正是历史上漏洞最密集的地方**。**「Wasm 所以安全」不是一个可以写进安全评估报告的句子**（三层攻击面的完整拆解与对策见附录 O §7）。

**优点三：语言无关性。**

- **它为什么行**：任何能编译到 LLVM（或有自己 Wasm 后端）的语言都能产出 `.wasm`。Rust、C/C++、Go、Zig、AssemblyScript、C#（Blazor）、Kotlin、Swift、Dart 都能用。
- **隐藏条款**：**「能编译」跟「编译出来能用」是两件事。** 分水岭是这门语言有没有一个必须跟着打包的运行期：

| 语言 | 运行期负担 | 典型 `.wasm` 体积（Hello World 级） | 现实评价 |
|---|---|---|---|
| Rust / C / C++ / Zig | 几乎没有（无 GC、无 runtime） | 数 KB ~ 数十 KB | **与 Wasm 天生一对** |
| AssemblyScript | 极小的 runtime + 简易 GC | 数 KB | 前端工程师的平滑入口 |
| Go | **完整 runtime + GC + scheduler** | 传统 `GOOS=js` 下 ~1.5MB+ 起跳 | 体积是主要痛点（TinyGo 可大幅缩减，但支持子集） |
| C# / Blazor | .NET runtime（或 AOT 裁剪） | 数 MB 级 | 生态强大，体积与冷启动是代价 |
| Java / Kotlin | 传统上要打包 JVM 语意层 | 极大 | **Wasm GC（已进 3.0 内核规范）落地后才真正可用** |
| Python | 整个 CPython 解译器 | Pyodide 全家桶 30~50MB | 只在「需要整个科学生态」时才划算 |

**优点四：极度轻量、启动极快。**

- **它为什么行**：相较于 Docker 映像动辄数百 MB、启动需要拉映像与起 namespace，`.wasm` 通常只有几 KB 到几 MB，实例化在微秒级。
- **隐藏条款**：**这个对比只在后端成立。** 在浏览器端，你的竞争对手不是 Docker，是「什么都不下载的纯 JavaScript」。一个 8MB 的 Wasm 模块相对于 200KB 的 JS bundle，是**四十倍**的重量。「轻量」是相对谁而言的问题，换个对照组结论就翻转。

> 💡 君之一席话
> 与君一席话：**任何技术优势都是一个比值，而比值的分母是可以被替换的。** 「Wasm 极度轻量」在跟 Docker 比的时候是真的，在跟 `<script>` 比的时候是假的；「Wasm 接近原生性能」在跟 JavaScript 比的时候是真的，在跟原生二进位比的时候是打折的。这不是谁在说谎，是**每一句性能宣称都默认了一个对照组，而那个对照组往往被省略了**。所以评估任何技术时最该做的动作，是把被省略的分母补回来，然后问：**在我的场景里，我真正的替代方案是谁？** 大多数失败的技术选型，都不是因为选错了技术，而是因为比错了对象。

## 情境 2　浏览器端的三道墙

**背景**：这三道墙是所有前端 Wasm 项目都会撞上的，顺序几乎固定。

**墙一：无法直接操作 DOM。**

Wasm 至今无法直接访问 HTML、CSS 或 DOM 元素。它必须通过 JavaScript 当中间人（胶水代码）传递数据。

- **技术上为什么**：DOM 是一套创建在 JavaScript 对象模型上的高级 API，涉及垃圾回收的对象图、字符串、原型链——而内核 Wasm 规范里**这些类型一个都没有**。要让 Wasm 直接碰 DOM，等于要先把整个 JS 对象模型搬进 Wasm 的类型系统。
- **现在的解法**：`wasm-bindgen` / `web-sys` 帮你生成绑定，让 Rust 看起来可以调用 `document.createElement()`——但底层每一次调用**都还是绕了一趟 JavaScript**。
- **未来的解法**：**Reference Types**（让 Wasm 能持有不透明的宿主参考，Wasm 2.0）与 **Wasm GC**（让 Wasm 能理解宿主的对象，Wasm 3.0）已经把这道缝缩小了不少，**JS String Builtins** 还在往前推。但「直接操作 DOM 且没有桥接开销」在可预见的未来仍不现实。
- **实务结论**：**不要用 Wasm 写 UI。** 用 Wasm 算，用 JS 画。Figma 就是这么干的——Wasm 算几何与排版，WebGL 画像素，DOM 只负责菜单和面板。

**墙二：与 JavaScript 的数据传输成本高。**

Wasm 内部只认得数字。字符串、对象、数组都必须串行化进线性内存，处理完再反串行化出来（机制细节见第 2 章情境 4）。

- **实测心智模型**：跨界调用本身的固定开销在奈秒级，但**一次字符串往返的编解码可以轻易到微秒级**。当你每秒做十万次细粒度调用，这笔帐就会出现在火焰图的正中央。
- **常见的灾难模式**：把 Wasm 当成「一个更快的函数库」逐函数替换 JS——结果是每个函数都变快了，整体却变慢了，因为边界穿越次数暴增。

**墙三：文件体积容易过大。**

- **主因**：带有庞大运行期的语言（Go、C#、Java）必须把整个 GC 与标准库打包进去。
- **次因**：静态链接。Wasm 传统上没有动态链接，用到 `libpng` 就要把 `libpng` 整包编进去，十个模块用同一个函数库就编十份。
- **可用的武器**：

```bash
# 1. Binaryen 的 wasm-opt：最重要的一步，体积与速度双收
wasm-opt -Oz --strip-debug --strip-producers input.wasm -o output.wasm

# 2. Rust 侧：把优化与剥离写进 Cargo.toml
#    [profile.release]
#    opt-level = "z"      # 或 3（速度优先）/ "s"（平衡）
#    lto = true           # 跨 crate 内联与死码消除
#    codegen-units = 1    # 让 LTO 有更完整的视野
#    panic = "abort"      # 砍掉 unwinding 表（Rust 特有，省下可观体积）
#    strip = true         # 剥离符号

# 3. 诊断：twiggy 告诉你哪个符号在吃体积
twiggy top -n 20 output.wasm

# 4. 传输层：一定要开 Brotli（Wasm 的压缩率通常很好，常见 3.5–5 倍）
```

> **这只是入口。** 体积优化的完整武器库——区段层级的解剖方法、`wasm-opt` 每个 pass 真正做什么、Rust 那个藏在 `panic!` 里的格式化机制（小模块可占 30% 以上）、单型化爆炸的「泛型薄壳」解法、`no_std`、数据裁剪、以及**压缩字典传输**（让改版只传几十 KB）——**见附录 N 第一部**。

> ⚠️ 真伪提醒
> 网络上流传的「Wasm 文件通常只有几 KB 到几 MB」是**对「纯运算内核」而言**。一旦牵涉到完整的语言运行期或大型 C++ 函数库，实际体积是另一个量级：OpenCV.js 约 6~9MB、Solidity 编译器 `soljson.wasm` 约 10~15MB、Pyodide 全家桶 30~50MB。**引用体积数字时务必确认它指的是哪一层。**

> 🔍 进阶点评──「无法操作 DOM」其实是一个祝福，只是没人愿意这样说
> 这是本章最反直觉的一段。所有入门文都把「不能碰 DOM」列为缺点，但如果 Wasm 真的能直接操作 DOM，会发生什么事？**首先，它会变慢。** DOM 操作的瓶颈从来不在「调用的语言是什么」，而在于样式重算（recalculate style）、版面重排（reflow）与绘制（paint）——这些发生在浏览器的渲染管线里，跟你用什么语言发起无关。一个能直接调用 `appendChild` 的 Wasm，**不会比 JS 快，只会让你更容易写出每帧触发一千次重排的代码**。**其次，它会撕裂生态。** 一旦 Wasm 能直接碰 DOM，就会出现一整套「Wasm 版 React」「Wasm 版 Vue」，而它们与 JS 生态的互通会变成永久的痛。**第三，也是最关键的：它会摧毁那条清晰的架构分界线。** 现在这条线逼着每个人做一个健康的决定——**把重运算放进 Wasm、把交互与画面留在 JS**。这正是 Figma、Photoshop Web、AutoCAD Web 不约而同采用的形状，而且它们是**被迫**采用的。所以真相是：**Wasm 对 DOM 的无能，是一道把架构师从自己的诱惑里救出来的护栏。** 这条原理值得推广——**一个平台最有价值的限制，往往是那些阻止你做「看起来很方便、但长期会烂掉」的事的限制。** gRPC 逼你先定义 schema、Rust 逼你想清楚所有权、Wasm 逼你划清运算与呈现的边界，这三件事的本质是同一件。

## 情境 3　系统与架构的四道墙

**墙四：严格的沙盒——没有原生系统访问权。**

Wasm 默认没有操作系统的概念。它不能读文件、不能创建 socket、不能访问硬件。在浏览器里它靠 JS 递数据，在后端它靠 WASI 拿能力，而 **WASI 规范至今仍在演进**：

- **`wasi_snapshot_preview1`**：事实上的第一代，以 POSIX 风格的文件描述符为模型。生态最广、工具支持最好，但语意上与 POSIX 绑太紧。
- **WASI 0.2（Preview 2）**：改建在 **Component Model** 之上，用 **WIT**（Wasm Interface Types）描述接口，把世界拆成 `wasi:io`、`wasi:filesystem`、`wasi:sockets`、`wasi:http` 等一组可组合的接口。这是方向正确、但生态迁移仍在进行的一代。
- **实务结论**：**你今天写的后端 Wasm，要准备好它会被迁移一次。** 这是采用成本的一部分，不该被忽略。

**墙五：内存管理受限。**

一整块连续的线性内存，只能扩大、无法缩小；一旦代码内部发生内存泄漏，Wasm 不会帮你回收（见第 2 章情境 2）。实务上的两个后果：

- **长时间运行的分页会单调地变胖**。解法是「用完丢掉整个实例、重新 instantiate」——这在 Wasm 里便宜到可以当成常规操作（微秒级）。
- **`ArrayBuffer` detach 的陷阱**会在你最忙的时候咬你（大量分配 → 触发 grow → 所有视图失效）。

**墙六：多线程支持不完美。**

Wasm 本身没有原生的线程创建能力。在浏览器里它必须依赖 **Web Workers + `SharedArrayBuffer`**（threads 特性提供 `memory` 的 `shared` 标记与一组原子指令 `i32.atomic.*`、`memory.atomic.wait/notify`，详见附录 M §6）。

**而 `SharedArrayBuffer` 有一段血淋淋的历史**：2018 年 **Spectre / Meltdown** 这类推测运行侧信道漏洞爆发后，`SharedArrayBuffer` 因为能提供高精度计时器而成为攻击工具的一环，**被所有主流浏览器紧急默认停用**。它后来被放回来，但附了一个严苛的条件——**跨来源隔离（cross-origin isolation）**：

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

必须由**服务器**回传这两个 HTTP Header，网页才会进入隔离状态，`self.crossOriginIsolated` 才会是 `true`，`SharedArrayBuffer` 才会存在。

**这一条会在第 5 章变成整本书最重要的一道坎**——因为 **GitHub Pages 不允许自订 HTTP Header**。

**墙七：同步的代码，碰上一个异步的世界。**

这是四道系统墙里最少被谈、却最常在移植途中把人绊倒的一道。

**问题的形状**：你要移植的 C/C++/Rust 代码是**同步**写的——`read(fd, buf, n)` 调用下去，它期待数据回来时就在 `buf` 里。可是**浏览器的世界几乎全是异步的**：`fetch()` 回 Promise、IndexedDB 回事件、OPFS 的异步 API 回 Promise。**而 Wasm 没有办法「等」一个 Promise**——它不能阻塞，一阻塞整个分页就冻结。

**历史上的三种解法，一种比一种好**：

| 解法 | 机制 | 代价 |
|---|---|---|
| **改写成异步** | 把整个调用链改成回呼/状态机 | 对几十万行的既有 C 代码**不可行** |
| **Asyncify**（Emscripten 的二进位变换） | 由 Binaryen 把整个模块改写，把调用堆栈手动存进线性内存再还原 | **能用，但很贵**：代码体积可能大幅膨胀、运行变慢，且要小心标注哪些函数会 unwind |
| **★ JSPI（JavaScript Promise Integration）** | **由引擎在 Wasm 的堆栈层面挂起与恢复** | **原生、几乎零改写**——这才是正解 |

**JSPI 的状态值得单独记住**：它在 **2025 年 4 月进入 Phase 4（标准化）**，并已于 **Chrome 137 与 Firefox 139** 出货。它的运作方式是：**当 Wasm 调用一个会回传 Promise 的导入函数时，引擎把整个 Wasm 运行堆栈挂起；Promise 解决后再从挂起处恢复，并把结果交回去**——从 Wasm 那一侧看，那就是一次普通的同步调用。

```javascript
// 概念示意：把一个回传 Promise 的 JS 函数，包成 Wasm 眼中的同步导入
const asyncImport = new WebAssembly.Suspending(async (url) => {
  const res = await fetch(url);           // 异步的世界
  return new Uint8Array(await res.arrayBuffer());
});
// 而导出的入口用 Promising 包起来，让它对 JS 呈现为 async
const run = WebAssembly.promising(instance.exports.main);
await run();
```

**它把第 5 章、第 7 章与附录 L 的一个共同困境打开了一个口**：OPFS 的异步 API、`fetch`、IndexedDB，**不再必须靠「搬进 Worker + 同步句柄」或「Asyncify 重写」才能被同步的 C 代码使用**。

**但别把它当万灵丹，三个但书**：**（一）** 挂起与恢复不是免费的，高频调用下开销可观——**它适合「偶尔等一次 I/O」，不适合把它放进热循环**。**（二）** 支持度仍需侦测与降级路径。**（三）** **它解决的是「等待」，不是「并行」**——你依然只有一条线程。

> 💡 君之一席话
> 与君一席话：**一个安全漏洞的真正成本，很少是修补它的工程量，而是它在整个生态上留下的永久税金。** Spectre 的修补在 CPU 微码与编译器层面早就完成了，但它留下的税——**每一个想用多线程的网页，都必须付出「跨来源隔离」这个沉重的部署代价，而隔离会连带打坏第三方 iframe、广告、嵌入式视频、CDN 资源**——会被整个 Web 生态缴上十几年。这条规律在资安里有一个残酷的推论：**当你评估一个漏洞的严重性时，该问的不是「它能造成多大损害」，而是「为了防住它，全世界要在接下来十年里付出多少不便」。** 前者是一次性的，后者是复利的。

## 情境 4　开发与生态的两道墙

**墙八：调试极度困难。**

当 Wasm 崩溃时，浏览器主控台通常只给你一个 `RuntimeError: memory access out of bounds` 加上一串 `wasm-function[1234]`。

- **为什么难**：编译已经把类型、变量名、原代码结构全部抹掉。堆栈只有函数索引，没有名字。
- **能做的事**（比多数人以为的多）：
  - **保留 `name` 自订区段**：这是 Wasm 规范里专门用来放函数名的 Custom Section。编译时不要无脑 `--strip-all`，保留它能让堆栈追踪变成人话。
  - **DWARF 调试信息**：Emscripten 与 Rust 都能在 Wasm 里嵌入 DWARF。搭配 Chrome DevTools 的 **C/C++ DevTools Support (DWARF)** 扩展，可以在浏览器里**看 C++ 原代码、下中断点、看变量值**。这是这几年最被低估的体验改善。
  - **`wasm2wat` / `wasm-objdump`**（WABT 工具集）：把二进位转回可读的文本格式，逐条检查指令。
  - **Emscripten 的 Sanitizer**：`-fsanitize=address`、`-fsanitize=undefined` 在 Wasm 上可用，能抓出线性内存内部的越界与未定义行为——**这是弥补「Wasm 沙盒内没有 ASLR/canary」的最实际手段**。
  - **`console.log` 派**：Emscripten 的 `EM_ASM` 与 Rust 的 `web_sys::console::log_1`，永远可用，永远有效。
- **但正式环境是另一回事**：发布时你会 `strip = true`（见第 9 章），而那正好把调试信息全部拿掉。**你必须保留一份带符号的建置产物，并用 Source Map 或符号服务器对应回去**——这件事在 Wasm 生态里远不如原生世界成熟。

**墙九：不是所有语言编译出来都划算。**

- **无 GC 语言（Rust、C/C++、Zig）**：与 Wasm 是完美绝配。
- **重运行期语言（Java、Python、JavaScript-in-Wasm）**：编译成 Wasm 后的运行性能往往**不如预期，甚至可能比在原生环境直接运行还慢**。原因很直接：你等于在一个虚拟机里跑另一个虚拟机（解译器的解译器），两层抽象叠加。QuickJS 编成 Wasm 之后运行 JS，比浏览器原生 V8 慢 10~20 倍，这是可预期的物理结果，不是实作缺陷。
- **Wasm GC 改变了什么**：让 Kotlin、Dart、Java、Scheme 这类语言可以**直接使用宿主引擎既有的、经过极致优化的垃圾回收器**，而不必把自己的 GC 打包进去。这对体积是量级的改善，对性能也有实质帮助——但它需要引擎支持，且对已经有大量 `i32` 指针式代码的既有项目帮助有限。

> 💡 君之一席话
> 与君一席话：**评估一项技术的成熟度，最准的指针不是它跑多快，是它坏掉的时候有多容易查。** 一项技术的性能可以在 benchmark 里量出来，写进投视频；但「凌晨三点在线崩了，你有多快能定位到那一行」这个指针，不会出现在任何一份技术选型比较表里，却是决定团队三年后过得好不好的那个变量。Wasm 的性能故事讲了十年，可观测性故事才刚开始讲——**这正是它今天适合「一个团队拥有的、边界清晰的计算内核」，而不适合「整个应用的主体」的真正原因。** 选型时多问一句：**这东西出事的时候，我手上有什么？**

## 本章小结

- 四大优点各有隐藏条款：**性能优势有计算量门槛**、**沙盒保护的是宿主不是你的程序**、**语言无关的分水岭是运行期负担**、**「轻量」的结论随对照组翻转**（跟 Docker 比是轻，跟 `<script>` 比是重）。
- 浏览器端三道墙（第一至三）：**不能碰 DOM**（因为内核规范里没有对象/字符串类型）、**跨界数据成本高**（一次字符串往返 = 两次编解码 + 两次拷贝）、**体积容易失控**（重运行期语言 + 静态链接）。
- **「不能碰 DOM」实质上是一道护栏**，它逼出了 Figma/Photoshop Web 那套「Wasm 算、JS 画」的健康架构（见情境 2 🔍）。
- 系统端四道墙：**WASI 仍在 preview1 → 0.2 的迁移中**（今天写的后端 Wasm 要准备被迁移一次）、**线性内存只能长不能缩**、**多线程必须靠 `SharedArrayBuffer`，而它被 Spectre 的余波绑上了跨来源隔离的枷锁**、**同步的代码碰上异步的世界**。
- 第四道墙的正解是 **JSPI**（2025-04 标准化，Chrome 137 / Firefox 139 出货）：**由引擎在堆栈层面挂起与恢复 Wasm**，让同步的 C 代码可以直接用回传 Promise 的 Web API，取代昂贵的 Asyncify 二进位变换。但它**解决的是「等待」不是「并行」**，且不该放进热循环。
- 开发端两道墙（第八、九）：**调试困难**（但 `name` section、DWARF + Chrome 扩充、`wasm2wat`、Sanitizer 是实际可用的解法，远比「只能 console.log」的印象好）、**重运行期语言编译成 Wasm 常常不划算**（虚拟机里跑虚拟机）。
- 那条跨来源隔离的限制，会在下一篇变成整本书最关键的一道坎——因为**免费的静态托管，恰恰不让你设 HTTP Header**。

限制清点完了，但只知道自己的限制还不够。下一个问题是：**在同一个场景里，我真正的替代方案是谁？它凭什么赢我、又输在哪？** 翻到第 4 章。
