# 第7章　无状态机器的记忆：MEMFS、IDBFS、OPFS 与 WASI

> WebAssembly 本身是一台**无状态（stateless）**的沙盒虚拟机。它既没有硬盘，也没有原生的数据库。它默认只有一块由宿主分配的平坦内存，**只要分页一重整，里面的所有数据就会像泡沫一样瞬间蒸发。**
> 它解决这件事的方式，本质上只有四个字：**权限外包。**

## 情境 1　第一层：MEMFS，那个活在内存里的假 Linux

**背景**：当你把一个 C/C++ 项目（FFmpeg、SQLite、GNU tar）编译成 Wasm，代码里到处都是这种东西：

```c
FILE *f = fopen("input.mp4", "rb");
fread(buf, 1, size, f);
fclose(f);
```

Wasm 没有 `fopen`。它甚至没有系统调用这个概念。那这行代码是怎么跑起来的？

**答案：Emscripten 在线性内存里假造了一整套 POSIX 文件系统。** 这套系统叫 **MEMFS**（In-Memory File System），它用类型化数组在 Wasm 的线性内存中仿真出标准的 Linux 目录结构（`/tmp`、`/home`、`/dev`），并把 libc 的文件函数全部重新导向过去。

```
C 代码:   fopen("/work/input.mp4", "rb")
                    ↓ Emscripten 的 libc 实作
JS 胶水:    FS.open("/work/input.mp4", "r")
                    ↓
MEMFS:      在线性内存里查一个 JS 对象建构的目录树，
            回传一个指向某块 Uint8Array 的文件描述符
```

**典型的数据流**（以 FFmpeg.wasm 为例）：

```javascript
// 1. 把用户拖进来的文件写进 Wasm 的虚拟文件系统
ffmpeg.FS('writeFile', 'input.mp4', await fetchFile(file));
// 2. 运行命令行——Wasm 内部真的以为自己在跑 CLI
await ffmpeg.run('-i', 'input.mp4', '-c:v', 'libx264', 'output.mp4');
// 3. 从虚拟文件系统读回结果
const data = ffmpeg.FS('readFile', 'output.mp4');
// 4. 转成 Blob URL 给用户下载
const url = URL.createObjectURL(new Blob([data.buffer], {type: 'video/mp4'}));
```

**MEMFS 的两个致命痛点**：

1. **它是暂存的**。分页关闭、重整、或内存耗尽（OOM），文件就消失了。
2. **它吃掉你的线性内存额度**。一个 500MB 的视频写进 MEMFS，就占掉了那 4GB 上限里的 500MB——而 FFmpeg 在转码过程中还要用掉更多。**这就是为什么 FFmpeg.wasm 处理不了大文件，跟 FFmpeg 本身的能力无关。**

**MEMFS 还有一个很少被提到的正面用途：整包分发。** Emscripten 的 `file_packager` 工具可以把成千上万个文件打包成**单一的 `.data` 映像档 + 一个 `.js` 加载器**，在运行期启动前挂载到指定路径。FluffOS 的 Wasm 建置就是这样分发整个 mudlib 的——**一个游戏世界的几万个 LPC 文件，变成一个静态 blob**。代价完全诚实地写在官方文档里：**「目前的写入只在分页 session 内有效」**，而它的 roadmap 下一步正是本节接下来要讲的两层——**在写入路径上挂一层 IDBFS 或 OPFS 覆盖**（见附录 L）。

> **这是本书能找到最好的一次现场验证**：一个真实、复杂、还在维护的项目，此刻正卡在这条四层阶梯的第一层，而且它清楚知道自己要往第二、三层走。

> 💡 君之一席话
> 与君一席话：**兼容性的本质，是在新环境里忠实地重建旧环境的谎言。** Emscripten 没有让 C 程序「适应」浏览器，它做的是反过来的事——**它让浏览器假装自己是 Linux**，假到 `fopen`、`ioctl`、`pthread_create`、`SDL_CreateWindow` 全都能骗过去。这就是为什么一个二十年前的 C++ 游戏可以几乎不改一行内核逻辑就跑在网页上。这条原理在系统迁移里有一个更普遍的形式：**当你要把大量既有资产搬到新平台上时，「改造资产去适应平台」的成本是 O(资产数量)，而「在平台上仿真旧环境」的成本是 O(1)。** WSL、Rosetta、Wine、Docker、JVM——全都是这一招。代价也一样：**你搬过去的是一整套旧世界的假设，包括那些在新环境里本来可以避开的低效。**

## 情境 2　第二层：IDBFS，把内存倒带进浏览器的数据库

**背景**：为了解决 MEMFS 的暂存问题，Emscripten 提供了 **IDBFS**——把虚拟文件系统与浏览器的 **IndexedDB** 数据库串接起来。

**运作原理**：

```javascript
// 挂载：把 /save 这个虚拟目录绑定到 IndexedDB
FS.mkdir('/save');
FS.mount(IDBFS, {}, '/save');

// 从 IndexedDB 加载到内存（开机时）
FS.syncfs(true, err => { /* true = 从 IDB 读进 MEMFS */ });

// C 程序照常写文件
// ... fopen("/save/game.sav", "wb") ...

// 把内存同步回 IndexedDB（存盘时）
FS.syncfs(false, err => { /* false = 从 MEMFS 写回 IDB */ });
```

**关键在于它是「整包倒带」，不是随机读写**。`syncfs` 会把整个挂载点的内容**全量**串行化进 IndexedDB（或反过来）。这决定了它的适用边界：

- ✅ **适合**：游戏存盘（几百 KB）、设置档、小型 JSON、用户偏好。**网页版复古游戏仿真器的存盘就是这么做的。**
- ❌ **不适合**：数据库文件、大型媒体、需要随机读写的任何东西。一个 500MB 的 SQLite 文件，每次 `syncfs` 都要整个搬一次。

**IndexedDB 本身的问题也一并继承过来**：异步的事件驱动 API、写入吞吐平庸、浏览器配额限制、以及在某些浏览器的隐私模式下会被限缩或清空。

## 情境 3　第三层：OPFS，这才是真正的解答

**背景**：**Origin Private File System（原生访问文件系统）** 是近年 Wasm 前端保存的黄金标准，也是 DuckDB-Wasm 与官方 SQLite-Wasm 能在浏览器里处理数 GB 数据库并保证 ACID 的原因。

**它是什么**：浏览器为每个来源（origin）开辟一个**高度隔离、极致优化的私有磁盘空间**。它不出现在用户的文件总管里、不需要授权对话框、不能被其他网站看到，而且——**它有一组专为性能设计的低级 API**。

**两种访问模式，差别是天壤之别**：

```javascript
// ── 模式 A：异步写入串流（主线程可用）────────────────
const root = await navigator.storage.getDirectory();
const fh = await root.getFileHandle('data.bin', { create: true });
const writable = await fh.createWritable();
await writable.write(uint8array);
await writable.close();        // 每一步都是 Promise，有 microtask 调度开销

// ── 模式 B：同步访问句柄（★ 只能在 Web Worker 里用）──
// 这是性能的分水岭
const root = await navigator.storage.getDirectory();
const fh = await root.getFileHandle('db.sqlite', { create: true });
const handle = await fh.createSyncAccessHandle();

handle.write(buffer, { at: offset });   // ← 完全同步，无 Promise
handle.read(buffer,  { at: offset });   // ← 随机访问，像本机 pread/pwrite
handle.flush();
handle.truncate(newSize);
handle.getSize();
handle.close();
```

**`createSyncAccessHandle()` 为什么是关键**：一个 C 语言写的数据库（SQLite、DuckDB）的保存层是**同步的**——它调用 `pread(fd, buf, len, offset)` 然后期待数据立刻在 buffer 里。你**无法**用一个回传 Promise 的 API 去实作它，除非你把整个程序改写成异步（那是不可能的，那是几十万行 C）。

**`createSyncAccessHandle` 给了 Wasm 一个真正的、同步的、可随机定位的文件句柄**——于是 SQLite 的 VFS（Virtual File System，SQLite 专门为了移植性设计的保存抽象层）只要实作几个函数，整个数据库就跑起来了：

```
SQLite 内核（未修改的 C 代码）
        ↓ 调用 VFS 接口：xOpen / xRead / xWrite / xTruncate / xSync / xLock
Emscripten 胶水层的 OPFS VFS 实作
        ↓
FileSystemSyncAccessHandle.read/write/flush
        ↓
浏览器的私有磁盘空间（真正落地）
```

**代价与限制**（这些是规范层面的，不是实作缺陷）：

1. **`createSyncAccessHandle` 只能在 Web Worker 里调用**。主线程禁止——因为同步 I/O 会阻塞 UI。这意味着**你的整个 Wasm 数据库引擎必须搬进 Worker**，主线程只能通过 `postMessage` 与它沟通。
2. **默认是独占锁**。同一个文件同时只能有一个 sync access handle。多分页同时打开同一个应用会互相抢锁——需要自己设计协调机制（例如 Web Locks API 或 `BroadcastChannel`）。
   **但这一条后来松绑了**：较新的浏览器支持 `createSyncAccessHandle({ mode: "readwrite-unsafe" })`，允许**同一文件同时开多个句柄**。名字里的 `unsafe` 是诚实的——**它把并行控制的责任整个交还给你**，浏览器不再帮你互斥。用它之前先问清楚：你的引擎自己有没有锁？
3. **配额**。浏览器对每个来源的保存有配额（通常与磁盘可用空间挂钩，可用 `navigator.storage.estimate()` 查找），并可能在磁盘压力下**驱逐**未标记为 persistent 的数据。要防止被清掉，需要 `navigator.storage.persist()`。
4. **用户看不见它**。这既是优点（不干扰用户）也是缺点（用户无法直接备份，你必须自己提供导出功能）。

**四层保存的完整对照**：

| | MEMFS | IDBFS | OPFS（async） | OPFS（sync handle） |
|---|---|---|---|---|
| 持久 | ❌ | ✅ | ✅ | ✅ |
| 随机访问 | ✅（在内存里） | ❌（整包倒带） | 有限 | **✅ 真正的 pread/pwrite** |
| 吃线性内存 | **✅（致命）** | 同步时吃 | ❌ | ❌ |
| 可在主线程 | ✅ | ✅ | ✅ | **❌ 只能在 Worker** |
| 性能 | 内存速度 | 差 | 中 | **接近本机磁盘** |
| 适用 | 暂存中间档 | 游戏存盘、设置 | 一般文件 | **数据库、大文件、串流** |

### ★ 一个会改变你部署决策的分岔：SQLite-Wasm 的两种 OPFS VFS

**这是本章最有实务价值的一段，而它几乎没有出现在任何入门文章里。** 官方 SQLite-Wasm 提供的不是一种 OPFS 后端，是**两种**，而它们的部署代价天差地别：

| | **`opfs` VFS**（第一代） | **`opfs-sahpool` VFS**（SAH = SyncAccessHandle） |
|---|---|---|
| 机制 | 主线程与 OPFS 之间用一个异步代理，靠 `Atomics.wait` 把异步变同步 | **直接持有一组预先开好的 sync access handle（一个「池」）**，在 Worker 内同步读写 |
| **需要 `SharedArrayBuffer`** | **✅ 需要** | **❌ 不需要** |
| **需要 COOP/COEP 跨来源隔离** | **✅ 需要** | **❌ 不需要** |
| 性能 | 可用 | **官方文档明列为所有 OPFS 选项中最高** |
| 多重连接 | 支持 | **不支持同时多个连接** |
| 可用性 | 较早 | 主流浏览器自 2023 年 3 月起大致可用 |

**这张表的意思，直接翻译成一句话**：

> **如果你要在 GitHub Pages 这种不能设 HTTP Header 的地方跑一个持久化的 SQLite，选 `opfs-sahpool`——它不需要跨来源隔离，而且还是最快的那个。**
> 官方的建议也正是如此：**重视性能胜于并发、或无法设置 COOP/COEP 响应标头的客户端，应该用 `opfs-sahpool`。**

**这件事把第 5 章那道「头号障碍」整个绕开了**，而代价只是「不支持多连接」——对绝大多数单用户的前端应用来说，那根本不是代价。

> 💡 **这里有一个更通用的教训**：当你发现自己正要为某个平台限制付出高昂的架构代价时（在这里是 COOP/COEP 带来的第三方资源全面损坏），**先确认一下你依赖的那个函数库，有没有提供一条不需要那个限制的路径。** 很多团队为了 `SharedArrayBuffer` 跟隔离搏斗了两周，而他们要的东西其实有一个不需要它的后端。

> ⚠️ 真伪提醒
> 「Sqlite-Wasm 读写吞吐比 IndexedDB 快 2~4 倍」「OPFS 让 Wasm 以接近本机硬盘的速度读写」这类说法方向正确，但**具体倍数高度依赖工作负载与浏览器版本**。可靠的定性结论只有三条：**（一）** `createSyncAccessHandle` 消除了异步调度开销，对「大量小型随机 I/O」（正是数据库的访问模式）改善最显著；**（二）** 对「一次写入一大块」的场景，async 与 sync 差距不大；**（三）** OPFS 的性能与浏览器实作强相关，Safari、Firefox、Chrome 的表现曾有明显差异。**做选型时请在目标浏览器上实测，不要照抄任何倍数。**

> 🔍 进阶点评──OPFS 的出现，才真正把 Wasm 从「函数库」变成「应用平台」
> 这一节值得单独拉出来说，因为它标志了一个分水岭。**在 OPFS 之前，Wasm 在浏览器里本质上是一个「纯函数加速器」**：你喂它输入、它吐出输出、然后它就该被遗忘。所有需要状态的东西——用户的项目档、数据库、缓存——都必须绕回 JavaScript，用 IndexedDB 那套异步 API 存起来。这道缝隙让「把桌面应用搬上浏览器」永远差最后一哩：**你可以把 SQLite 编译进来，但你没有一个能给它用的文件系统。** OPFS 的 `createSyncAccessHandle` 补上的正是这一哩，而它补的方式很有意思——**它不是给了 Wasm 一个新能力，而是给了 Wasm 一个「符合 C 语言世界期待的接口形状」。** 同步、可定位、有锁、有 flush。这四个性质不是因为它们最好，而是因为**过去五十年所有的保存软件都是照这个形状写的**。所以真正的洞见是：**一个新平台要接收既有的软件资产，关键不在于提供多强的能力，而在于提供对方期待的接口形状。** 这解释了为什么 OPFS 选择了一个看起来「不够现代」（同步、阻塞）的 API 设计——因为现代的异步设计会把整个 C/C++ 生态挡在门外。**当你设计一个平台的 API 时，最重要的问题不是「什么设计最优雅」，而是「我要接收的资产是照什么形状写的」。**

## 情境 4　第四层：后端的 WASI，以及能力外包的完整形态

**背景**：当 Wasm 破圈走向后端（Wasmtime、WasmEdge），它不再受限于浏览器沙盒，而是面临「操作系统级硬盘访问」的问题。而它的答案，和前端本质上是同一个。

**能力式安全（capability-based security）的完整含义**：

- 传统 Linux 上，一个被攻破的 Node.js 进程可以直接读 `/etc/passwd`——因为它有那个用户的**全部**权限。
- Wasm 运行期默认是「**绝对两手空空**」的：它没有 `open()` 系统调用的权限，因为 `open()` 这个 import 根本没有被提供。

```bash
# 启动时明确把主机的 ./my_storage 授权为 Wasm 眼中的 /sandbox
wasmtime run --dir=./my_storage::/sandbox my_server.wasm
```

模块内部若试图访问 `/sandbox/../etc/passwd`，会被运行期在能力边界上直接拦截并终止——**这不是靠文件系统权限碰运气，是靠「你手上那个目录句柄根本不能往上走」的结构性保证**（技术上这对应 POSIX 的 `openat` 语意与路径解析限制）。

**WASI 的两个世代**（做技术选型时务必分清）：

| | `wasi_snapshot_preview1` | WASI 0.2 (Preview 2) |
|---|---|---|
| 模型 | POSIX 风格的文件描述符 | **Component Model** + WIT 接口定义 |
| 接口 | 一大包扁平的函数 | 拆成 `wasi:filesystem`、`wasi:io`、`wasi:sockets`、`wasi:http`、`wasi:clocks`… |
| 生态 | **成熟**，Rust `wasm32-wasip1`、TinyGo、多数工具链都支持 | 演进中，工具链逐步跟上 |
| 可组合性 | 差（单体接口） | **好**（可以只给某个组件 `wasi:clocks`，不给文件） |

**Component Model 是这条路的终点**：它让 Wasm 模块之间能用**高级类型**（字符串、记录、变体、串流）互相沟通，而不是只能传 `i32` 指针——换句话说，它试图一次解决第 2 章那个「边界收费站」的问题。**WIT（Wasm Interface Type）** 是它的接口描述语言：

```wit
// 一份 WIT 接口定义：像 IDL，但编译期就能产生各语言的绑定
package example:storage@0.1.0;

interface kv {
  record entry { key: string, value: list<u8> }
  get: func(key: string) -> option<list<u8>>;
  put: func(key: string, value: list<u8>) -> result<_, string>;
  list-all: func() -> list<entry>;
}
```

**技术思维的总结**：Wasm 解决数据保存的本质，是 **内存映射（Memory Mapping）+ 权限外包（Capability Delegation）**。

- 在**前端**，它把硬盘操作外包给浏览器的 IndexedDB 或 OPFS API；
- 在**后端**，它把硬盘操作外包给 WASI 运行期的预先授权信道。

这套架构既完整保留了 Wasm 虚拟机的沙盒隔离特性，又赋予了它逼近原生 C 程序的 I/O 吞吐量。

> 💡 君之一席话
> 与君一席话：**一个系统最诚实的地方，是它列出自己需要什么的那张清单。** WASI 的 import 段落、浏览器扩展的 `permissions` 字段、Android 的 manifest、Kubernetes 的 ServiceAccount——这些清单的价值不在于「限制了坏人」（一个真正的恶意程序会直接要求它需要的一切），而在于**它让「这个东西能做什么」变成一个可以在五秒内读完的事实，而不是一个需要逆向工程才能回答的问题**。安全审计的成本，因此从「证明它不会做坏事」降到「看它要了什么」。这条原理的推论很实用：**当你评估任何第三方组件时，第一件事不是看它的代码，是看它的权限清单——如果那张清单不存在，或者长到读不完，你已经得到答案了。**

## 本章小结

- Wasm 本身**无状态**：只有一块线性内存，分页重整即蒸发。它的解法只有四个字——**权限外包**。
- **MEMFS**：Emscripten 在线性内存里假造的一整套 POSIX 文件系统，让 `fopen()` 有地方可去。**暂存，且吃掉你的 4GB 额度**——这才是 FFmpeg.wasm 处理不了大文件的真正原因。
- **IDBFS**：通过 `FS.syncfs()` 把整个挂载点**整包倒带**进 IndexedDB。适合游戏存盘与设置（几百 KB），**不适合数据库与任何需要随机读写的东西**。
- **OPFS 是真正的解答**，而分水岭是 **`createSyncAccessHandle()`**——它给了 Wasm 一个同步、可随机定位、有锁与 flush 的文件句柄，让 SQLite 的 VFS 只要实作几个函数就能整包跑起来。代价：**只能在 Worker 里用、默认独占锁（`{mode:"readwrite-unsafe"}` 可松绑但责任归你）、有配额、用户看不见**。
- **★ 最有实务价值的一条**：SQLite-Wasm 有**两种** OPFS VFS。第一代 `opfs` 需要 `SharedArrayBuffer`，因此**需要跨来源隔离**；而 **`opfs-sahpool` 不需要 COOP/COEP，且是官方文档里最快的选项**，代价只是不支持多重连接。**在 GitHub Pages 上要持久化 SQLite，选后者，第 5 章那道头号障碍就整个绕开了。**
- 通用教训：**当你正要为某个平台限制付出高昂的架构代价时，先确认你依赖的函数库有没有一条不需要那个限制的路径。**
- OPFS 的设计启示是：**新平台要接收既有软件资产，关键不是提供多强的能力，是提供对方期待的接口形状**——即使那个形状（同步、阻塞）看起来不够现代（见情境 3 🔍）。
- 后端的 **WASI** 是同一个哲学的另一面：**能力式安全**，模块默认两手空空，能力清单就写在启动参数里。注意 **preview1 与 0.2 是两个世代**，今天写的东西要准备被迁移一次。
- 前端外包给 OPFS/IndexedDB，后端外包给 WASI——**同一套心法，两个宿主。**
