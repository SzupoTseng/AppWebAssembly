# 第2章　二进位的物理学：魔数之后的每一个字节

> 打开任何一个 `.wasm` 文件，开头永远是这八个字节：`00 61 73 6D 01 00 00 00`。前四个是魔数 `\0asm`，后四个是版本号 `1`。**这八个字节之后的一切，都是为了让一台不信任你的机器，能在读完之前就证明你不会作恶。**

## 情境 1　它不是机器码，是一份可以被证明的合约

**背景**：多数人对 Wasm 的第一印象是「编译后的机器码」。这个印象是错的，而且错得很关键。**Wasm 不是任何一颗实体 CPU 的指令集**——没有 x86，没有 ARM，没有 RISC-V。它是一台**规格上定义出来的抽象堆栈机器**，而这台机器的每一条性质，都是为了「可验证性」服务的。

**模块的物理结构**：一个 `.wasm` 文件由若干个**区段（section）**线性排列而成，每个区段以一个字节的 ID 开头，接着是 LEB128 编码的长度，然后是内容。顺序是规范强制的：

| ID | 区段 | 内容 |
|---|---|---|
| 1 | Type | 所有函数签章（`(i32, i32) -> i32` 这种） |
| 2 | Import | 从宿主环境要进来的东西：函数、内存、表、全域变量 |
| 3 | Function | 每个函数对应到 Type 区段的哪一个签章 |
| 4 | Table | 函数参考表（间接调用的跳转目标） |
| 5 | Memory | 线性内存的初始页数与上限 |
| 6 | Global | 全域变量 |
| 7 | Export | 对外曝露的函数/内存/表/全域 |
| 8 | Start | 实例化后自动运行的函数 |
| 9 | Element | 表的初始内容 |
| 10 | Code | 每个函数的实际指令与区域变量 |
| 11 | Data | 线性内存的初始数据 |
| 12 | DataCount | 数据段数量（bulk memory 提案引入，供单趟验证用） |
| 0 | Custom | 任何自订数据（调试符号 `name`、Source Map 链接、语言专属中继数据） |

**这个顺序不是美学，是工程**：类型先于函数声明，函数声明先于函数本体。这保证了验证器**只需要从头到尾扫一遍**——每读到一条指令，它需要的所有类型信息都已经在前面出现过了。这就是为什么 Wasm 的验证是 **O(n) 单趟线性时间**，也是为什么它能**边下载边编译**。

**指令是怎么运作的**：Wasm 是堆栈机器。`local.get 0` 把第 0 号区域变量推上堆栈，`i32.add` 弹出两个值、推回一个。一个把两数相加的函数，在文本格式（WAT）里长这样：

```wat
(module
  (func $add (param $a i32) (param $b i32) (result i32)
    local.get $a        ;; 堆栈: [a]
    local.get $b        ;; 堆栈: [a, b]
    i32.add)            ;; 堆栈: [a+b]
  (export "add" (func $add)))
```

对应的指令串行是 `20 00 20 01 6A`——五个字节。`0x20` 是 `local.get`，`0x6A` 是 `i32.add`。**没有寄存器分配、没有寻址模式、没有指令前缀**，因此它极度紧凑，也极度容易被机械地翻译成任何真实 CPU 的指令。

> **精确一点说**：这五个字节是**指令**，而 Code 区段里完整的「函数本体」还要在前面加一个区域变量声明（此例为 `00`，代表零组区域变量），并在结尾加上 `0x0B`（`end`）——**这两个字节是规范强制的**。整个模块逐字节的完整拆解（含 LEB128 编码、类型编码表、常用脚本速查）见**附录 M 第一节**。

**验证器在加载时到底检查什么**：这是 Wasm 安全模型的内核，它检查的东西比大多数人以为的多：

1. **堆栈类型一致性**：每条指令运行前后，操作数堆栈的类型串行必须可被静态推导。`i32.add` 之前堆栈顶端**必须**是两个 `i32`，不能是 `f64`，也不能是空的。
2. **控制流结构化**：Wasm **没有任意跳转（goto）**。控制流只有 `block` / `loop` / `if` 三种区块，以及 `br` / `br_if` / `br_table` 三种**只能往外跳到某个包住自己的区块标签**的分支。这保证了控制流图天生是可归约的（reducible），编译器不需要做昂贵的不可归约循环分析。
3. **分支处的堆栈高度必须一致**：跳到同一个标签的所有路径，堆栈上的类型必须相同。
4. **区域变量索引在界内**、**函数索引在界内**、**间接调用的签章在运行期比对**（`call_indirect` 的四道检查与 C++ 虚拟函数的实作方式见附录 M 第三节）。
5. **内存与表的访问一律有界检查**（下一节详谈）。

**还有一个很聪明的技巧值得单独提**：`unreachable` 之后的死代码怎么验证？规范用「**多态堆栈（polymorphic stack）**」——进入 unreachable 状态后，验证器把堆栈视为「可提供任意数量、任意类型的值」，于是任何死代码都能通过验证，**而验证器不必做可达性分析**。**这个看起来像特例的规则，正是为了保住「单趟 O(n)」这个更根本的性质**（详见附录 M 第二节）。

**通过验证的模块有一个极强的性质**：它**不可能**读写线性内存之外的任何字节、不可能跳到任意地址、不可能伪造函数指针、不可能破坏调用堆栈（return address 存在引擎自己的堆栈上，Wasm 代码碰不到）。**缓冲区溢出攻击在 Wasm 里打不穿沙盒**——它最多只能弄坏这个模块自己线性内存里的数据。

> ⚠️ 真伪提醒（一个广为流传的误解）
> 「Wasm 内存安全」这句话**只在沙盒边界的意义上成立**。它保证的是「Wasm 模块伤不到宿主」，**不保证你用 C 写的程序在 Wasm 里就没有内存错误**。事实上情况更微妙：因为线性内存是一整块平坦的 `ArrayBuffer`，**传统的堆栈保护（stack canary）、地址空间随机化（ASLR）、不可运行页（NX）这些原生平台的缓解措施在 Wasm 里多半不存在**。一个在 x86 上会被 ASLR 挡下的缓冲区溢出，在 Wasm 里可能稳定可利用——只是它的破坏范围被限制在该模块的线性内存内。学术界对此有明确的讨论（如 "Everything Old is New Again: Binary Security of WebAssembly"，USENIX Security 2020）。**沙盒安全 ≠ 应用安全。**

> 💡 君之一席话
> 与君一席话：**安全性最便宜的实现方式，不是加防护，是砍能力。** Wasm 没有 `goto`、没有寄存器、没有裸指针、没有可运行的堆栈、没有系统调用——它不是「守住」了这些攻击面，是**这些攻击面在规格层面根本不存在**。守卫是要花钱的（运行期检查、CPU 周期、复杂度、以及每一个守卫自己可能的漏洞）；不存在是免费的，而且不会有 bug。这条原理在系统设计里有一个更常见的名字：**让非法状态无法被表示（make illegal states unrepresentable）。** 每当你在做安全设计时发现自己在写「检查用户有没有做 X」，先退一步问一句：**能不能让 X 在类型、在协定、在数据结构上根本无法被写出来？** 能砍掉的，永远比能守住的可靠。

> 🔍 进阶点评──结构化控制流的代价，以及那个没人提的编译难题
> 「没有 goto」听起来只是安全设计，但它对编译器作者是一场灾难，而这场灾难的解法很有意思。**问题在于：真实世界的代码有 goto。** C 有 `goto`，LLVM IR 的控制流图是任意的有向图，而 Wasm 只接受由嵌套区块组成的树状结构。把任意 CFG 还原成结构化控制流，是编译理论里的老问题（Relooper 算法），Emscripten 早期就是靠它，后来 Binaryen 加入了更强的 **Stackify** 算法。代价是什么？**对于某些不可归约的循环（irreducible loops），你必须引入一个额外的状态变量与一个大 `br_table`，把控制流「仿真」出来**——这会产生比原始代码更慢的指令串行。这就是为什么某些手写汇编密集的项目（如视频解码器）移植到 Wasm 后，性能损失比预期大：**不是 Wasm 指令慢，是它的控制流表达能力不够，逼编译器绕路。** 后来的 **funclets / multi-loop 提案**讨论过放宽这一点，但至今内核规范仍守着结构化控制流不放——因为那是验证器能在单趟线性时间内完成的前提。**这是一个非常典型的取舍案例：为了让每一台设备上的验证都便宜到可以忽略不计，规范愿意牺牲一小撮极端场景的性能。** 当你评估任何一个「安全的运行环境」时，都应该去找这个取舍点在哪——它一定存在，而且它一定会在某个角落咬你。

## 情境 2　线性内存：那块平坦的、只能长不能缩的荒原

**背景**：Wasm 的内存模型简单到近乎原始——**一整块连续的、可寻址的字节数组**，称为线性内存（linear memory）。它以 **64KiB 为一页**，用 `memory.grow` 指令按页增长，用 `memory.size` 查找当前页数。

**在 JavaScript 侧，它就是一个 `ArrayBuffer`**：

```javascript
const { instance } = await WebAssembly.instantiateStreaming(fetch("app.wasm"), imports);
const mem = instance.exports.memory;                 // WebAssembly.Memory
const bytes = new Uint8Array(mem.buffer);            // 直接看到 Wasm 的整块内存
const ints  = new Int32Array(mem.buffer);            // 同一块内存的另一种视角
```

**这一点是所有 Wasm 性能技巧的根**：JS 与 Wasm 之间**不需要拷贝数据**，因为它们看的是同一块字节。所谓「零拷贝」，指的就是用 `TypedArray` 在这块 buffer 上开一个视图，而不是把数据搬来搬去。

**它的四条物理性质，逐条都会在后面的章节咬人**：

1. **只能增长，不能缩小**。`memory.grow` 有，`memory.shrink` 没有。一个曾经吃到 3GB 的 Wasm 应用，即使释放了所有内部数据结构，**那 3GB 的 `ArrayBuffer` 依然被操作系统记在帐上**，直到整个实例被丢弃。这就是为什么长时间运行的 Wasm 应用要嘛设计成「用完就丢掉整个实例」，要嘛在内部自建内存池。
2. **增长可能导致 `ArrayBuffer` detach**。在不使用 `growable ArrayBuffer` 的旧行为下，`memory.grow` 之后**所有既有的 `TypedArray` 视图都会失效**（buffer 被 detach）。这是新手最常踩的雷：

```javascript
let view = new Uint8Array(mem.buffer);
instance.exports.allocate_lots();   // 内部触发了 memory.grow
view[0] = 42;                       // ❌ TypeError / 写进了已 detach 的 buffer
// 正解：每次可能触发 grow 的调用之后，重新取得视图
view = new Uint8Array(mem.buffer);
```

3. **地址就是索引，`0` 是合法地址**。Wasm 没有「空指针」的概念——地址 0 是线性内存的第一个字节，完全可读可写。所以 C 语言里「解参考 NULL 会 segfault」的保护在 Wasm 里**默认不存在**（Emscripten 可以用 `--low-memory-unused` 之类的选项把低地址保留起来当作陷阱区，但那是工具链的补丁，不是规范的保证）。
4. **越界访问一定会 trap**。这是规范的硬保证。`i32.load` 一个超出当前内存大小的地址，会产生一个**不可捕捉的陷阱（trap）**，在 JS 侧表现为抛出 `WebAssembly.RuntimeError`。

**界检查怎么做到不慢**：天真的实作会在每一次 `load`/`store` 前插入一条比较与分支，那是不可接受的开销。现代引擎在 64 比特宿主上用一招漂亮的技巧——**保护页（guard page）**：

> 引擎在虚拟地址空间里为每个 32 比特线性内存保留 **8GiB**（4GiB 的可寻址空间，加上前后的保护区），但只把实际用到的页面**提交**（commit）为可读写。地址计算用 32 比特的偏移量做，因此**在数学上不可能超出那 4GiB 的保留区**；一旦访问到尚未提交的区域，操作系统的分页机制会产生 SIGSEGV，引擎的信号处理器接住它，翻译成 Wasm trap。
> **结果：热路径上的界检查指令数是零，代价由 MMU 硬件免费承担。**

这也解释了一件事：为什么 Wasm 在 32 比特宿主或某些嵌入式运行期上会明显变慢——**那里没有足够的虚拟地址空间做保留，只能退回逐次显式比较。**

> 💡 君之一席话
> 与君一席话：**最高明的性能优化，通常长得不像优化，而像是把工作交给了某个本来就免费的东西。** 保护页这一招没有「加速」任何运算，它只是把「检查地址是否越界」这件事，从软件搬到了 MMU 这个**本来就在每一次内存访问时都会运转的硬件**上——换句话说，它让界检查的边际成本变成零，因为那个成本已经有人在付了。这条思路在系统工程里到处都是：mmap 让文件读取搭上分页的便车，copy-on-write 让 fork 搭上 MMU 的便车，DMA 让 I/O 搭上总线的便车。**当你为某件事的开销苦恼时，最有价值的问题不是「怎么让它更快」，而是「这件事有没有可能是某个已经在跑的机制的副产品」。**

> 🔍 进阶点评──4GB 这个数字的三段式演化，与它真正的拦路虎
> 线性内存的 4GiB 上限来自 `i32` 地址（2³² 字节）。这个数字在实务上有三层天花板，而**它们互相遮挡**，导致很多人搞不清楚自己是撞到哪一层。**第一层，规范层：wasm32 死锁在 4GiB。** 这是数学，绕不过。**第二层，引擎层：浏览器通常撑不到 4GiB。** V8 对单一 Wasm 内存有自己的上限（历来在 2GiB~4GiB 之间变动且与平台有关），实务上很多场景在 2~3GiB 就先 OOM 了。**第三层，分页层：`ArrayBuffer` 需要连续的虚拟地址空间。** 在 32 比特浏览器或地址空间碎片化严重的长时间运行分页上，即使理论额度还有，`memory.grow` 也可能单纯因为找不到一块够大的连续区间而失败。**破局的是 Memory64（`i64` 寻址，已于 Wasm 3.0 进入内核规范）**，理论上限提到 2⁶⁴，但这里有个常被忽略的代价：**一旦地址变成 64 比特，前面那套「保留 8GiB 虚拟空间 + 保护页」的免费界检查就不成立了**——你不可能为每块内存保留 2⁶⁴ 的虚拟地址。因此 memory64 在多数实作上**必须退回显式界检查**，带来可观的性能回退（不同基准下数个百分点到双位数不等）。所以正确的心智模型不是「memory64 出来就没问题了」，而是——**你在 4GiB 以下享受的是硬件补贴的免费安全，越过那条线之后，安全就要开始收费了。** 这对架构决策的意义很直接：**能靠分块串流或多重内存（第 8 章）在 4GiB 以内解决的，就别急着跳 Memory64。**

## 情境 3　从二进位到机器码：分层编译与那条看不见的预热曲线

**背景**：用户按下 Enter 之后，那个 20MB 的 `.wasm` 到底经历了什么？答案不是「解析完就开始跑」，而是一条**同时在赛跑的双轨流水线**。

**现代引擎（以 V8 为例）的分层策略**：

| 层 | 编译器 | 特性 | 用途 |
|---|---|---|---|
| Tier 1 | **Liftoff** | 单趟、不做优化、几乎是逐条指令翻译 | **极快产出可运行码**（数百 MB/s 级的编译吞吐），让程序立刻能跑 |
| Tier 2 | **TurboFan** | 完整的 SSA 中间表示、内联、循环优化、寄存器分配 | 产出高品质机器码，**在背景线程编译**，好了就热替换 |

SpiderMonkey 有对应的 **BaseLine → Ion** 双层，JavaScriptCore 则有 **BBQ → OMG**。**三家引擎不约而同选择了同一个形状，因为问题是同一个**：用户要的是「立刻开始跑」，长期性能要的是「编译得够好」，而这两件事无法同时满足——除非你做两次。

**串流编译（streaming compilation）**：这是 Wasm 相对 JS 最被低估的优势。

```javascript
// ✅ 正确：一边下载一边编译，第一个字节到达时 Liftoff 就开工了
const { instance } = await WebAssembly.instantiateStreaming(
  fetch("app.wasm"), importObject);

// ❌ 常见错误：先把整包下载成 ArrayBuffer，再开始编译（白白多等一整趟下载）
const buf = await (await fetch("app.wasm")).arrayBuffer();
const { instance } = await WebAssembly.instantiate(buf, importObject);
```

`instantiateStreaming` 要求服务器回传的 `Content-Type` 必须是 `application/wasm`，否则会拒绝。**GitHub Pages 对 `.wasm` 扩展名会正确回传这个 MIME**，这是它意外地适合跑 Wasm 的原因之一。

**代码缓存（code caching）**：Chrome 会把 TurboFan 编译的结果写进磁盘缓存，第二次造访同一个 URL 时可直接加载编译结果，跳过整个编译阶段。这使得**大型 Wasm 应用的第二次加载往往比第一次快一个量级**——也是为什么那些「Pyodide 要下载 30MB」的抱怨，在回访用户身上感受完全不同。

**冷启动的完整成本拆解**（这是评估「值不值得用 Wasm」时真正该算的帐）：

```
总冷启动时间 =
    网络传输（受 gzip/brotli 压缩后体积与 RTT 支配）
  + Liftoff 编译（≈ 与字节数线性相关，通常远小于网络时间）
  + 实例化（配置线性内存、跑 Data 段初始化、运行 start 函数）
  + 运行期初始化（C++ 的全域建构子、Rust 的 lazy static、语言 runtime 的自举）
  ─────────────────────────────────────────────
  ⚠️ 最后一项是最常被低估的：Pyodide 的 CPython 自举、
     Emscripten 的文件系统挂载，都发生在「编译完成之后」。
```

**优化顺序也因此被决定**：先砍体积（`wasm-opt -Oz`、`--strip-debug`、按需分割模块），再砍运行期初始化（延迟初始化、快照），最后才轮到指令层优化。**把力气花在指令层而不管那 30MB 的下载，是最常见的误配。**

**关于第四段，有一项专门的武器值得先记住名字**：**Wizer**（Bytecode Alliance）可以在**建置时**就把初始化跑完，并把「初始化之后的内存状态」快照回一个新的 `.wasm`——运行期拿到的模块，Data 区段里已经是初始化完成的映像。官方基准宣称**实例化与初始化快 1.35 到 6.00 倍**。**代价是 Data 区段变大，也就是拿体积换启动速度**——这正是本节那条「四段成本各自独立」的直接推论。

> **体积与速度是一整套互相牵制的技术，值得单独拆解。** 从「你的字节花在哪里」的解剖方法，到 `wasm-opt` 每个 pass 真正做什么、Rust 那个藏在 `panic!` 里的格式化机制、压缩字典传输如何让改版只传几十 KB、Wizer 与后端 AOT、SIMD 自动矢量化的三个现实、以及一个会让你量错数字的计时器精度陷阱——**全部收在附录 N。**

> 💡 君之一席话
> 与君一席话：**当一个系统必须同时满足两个互相矛盾的指针时，正确的答案往往不是折衷，而是分层。** Liftoff 与 TurboFan 的关系不是「取中间值」——那样会得到一个既不够快启动、也不够快运行的平庸编译器。它是**先用一个烂到极致但快到极致的方案让系统活起来，再在背景默默把它换成好的**。这个模式的名字叫**渐进式优化（progressive optimization）**，而它出现在所有你想得到的地方：图片的渐进式加载、数据库的 LSM tree（先写快的、背景合并成好的）、CDN 的 stale-while-revalidate、甚至 CPU 的分支预测（先猜一个，错了再回滚）。**每当你在「快速回应」与「高品质结果」之间纠结时，先问一句：这两者能不能不要在同一个时间轴上竞争？**

> 🔍 进阶点评──为什么「Wasm 有 60~80% 的原生性能」这句话几乎没有意义
> 这是本书必须早点戳破的一句话，因为它会在附录的一百零一个案例里出现一百零一次。**这个数字的成立高度依赖于工作负载的形状。** 拆开来看：**（一）纯整数与浮点运算密集、数据放得下 L1/L2 缓存、控制流简单的循环**——Wasm 可以逼近原生的 90%+，因为 TurboFan 产出的机器码和 Clang -O2 差不了多少。**（二）需要手写 SIMD 或平台特化汇编的场景**——Wasm SIMD 只有 128 比特固定宽度（`v128`），而现代 x86 有 AVX2（256 比特）与 AVX-512，ARM 有 SVE。一个为 AVX2 手写优化的视频解码器移植到 Wasm，**掉到原生的 40~50% 是常态**，因为它的矢量宽度直接减半，而且 relaxed SIMD 提案虽然放宽了部分语意以换取更好的映射，仍补不回宽度差。**（三）大量跨越 JS/Wasm 边界的细碎调用**——每次跨界都有固定开销，如果你的函数本体只做几条指令，那开销会占绝大部分，此时 Wasm 可能比纯 JS **还慢**。**（四）大量字符串与对象操作**——Wasm 没有字符串类型，每一次字符串往返都是编码、拷贝、解码三步，纯 JS 在这里是碾压性的。**（五）内存访问模式差、缓存未命中主导**——此时瓶颈在内存总线，Wasm 与原生的差距会收敛到接近零（因为两边都在等 DRAM）。所以正确的说法不是「Wasm 有 N% 的原生性能」，而是——**Wasm 消除了 JavaScript 的动态类型检查、垃圾回收暂停与对象分配开销，剩下的差距取决于你的工作负载有多依赖那些 Wasm 规格里没有的东西。** 读任何 Wasm 性能宣称时，第一个要问的问题永远是：**这个基准测试的形状，跟我要跑的东西像不像？**

## 情境 4　跨越边界：`wasm-bindgen`、胶水代码，与那条真正的收费站

**背景**：Wasm 只认得四种数值类型（`i32`、`i64`、`f32`、`f64`，加上 SIMD 的 `v128` 与参考类型）。**它不认得字符串、不认得数组、不认得对象、不认得 `null`。** 那 `wasm-pack` 产出的 JS 里，`greet("GitHub Pages")` 是怎么跑起来的？

**答案是：那不是一次调用，是一整套协定。** 以 Rust + `wasm-bindgen` 为例，一次传字符串的完整流程：

```rust
#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", name)
}
```

底下实际发生的事：

```
JS 侧                                    Wasm 侧
─────────────────────────────────────────────────────────
1. TextEncoder 把 "GitHub Pages"
   编码成 UTF-8 字节
2. 调用 wasm.__wbindgen_malloc(len)  →   分配线性内存，回传地址 ptr
3. 把字节写进 memory.buffer 的
   ptr 位置（一次内存拷贝）
4. 调用 wasm.greet(ptr, len)        →   Rust 用 ptr/len 建构 &str
                                         （这一步零拷贝，直接指向线性内存）
                                         运行 format!，结果写进新分配的区块
                                    ←    通过回传区把 (ptr2, len2) 传回
5. 从 memory.buffer 的 ptr2 读出字节
6. TextDecoder 解码成 JS 字符串（又一次拷贝）
7. 调用 wasm.__wbindgen_free(ptr2)  →   释放
```

**一次「传个字符串」，付出了两次编解码、至少两次内存拷贝、三次跨界调用。** 这就是为什么所有 Wasm 性能建议里最重要的一条是：**把边界做粗，不要做细。**

**具体的优化手法**：

- **批量化**：与其调用 `process_pixel()` 一百万次，不如调用 `process_image(ptr, width, height)` 一次。
- **视图而非拷贝**：Rust 侧用 `js_sys::Uint8Array::view(&data)` 直接把切片映射成 JS 视图（注意这是 `unsafe`，因为只要 Wasm 侧发生 `memory.grow`，这个视图就失效了）。
- **共享缓冲区**：由 JS 分配一块大 buffer，双方约定用偏移量沟通，整个处理过程不再跨界。
- **避免每帧回呼**：物理引擎、游戏循环千万不要每个对象一次回呼；改用「Wasm 写进一块结果缓冲区，JS 每帧读一次」的环形队列模式。

**两种主要工具链的分工**：

| | Emscripten | `wasm-bindgen` / `wasm-pack` |
|---|---|---|
| 语言 | C / C++（也支持其他 LLVM 前端） | Rust |
| 产出 | `.wasm` + 一大包 JS 胶水（含 libc、文件系统、SDL/OpenGL 转译层） | `.wasm` + 精简 JS 绑定（只含你用到的类型转换） |
| 哲学 | **仿真一整个 POSIX 环境**，让既有 C 程序几乎不改就能编 | **只做类型桥接**，其他交给 Web API |
| 适合 | 移植现成的大型 C/C++ 项目（FFmpeg、SQLite、OpenCV） | 从零写的新项目、对体积敏感的函数库 |
| 典型体积负担 | 较大（含 runtime 与 shim） | 较小（几 KB 到数十 KB 的胶水） |

**Emscripten 的胶水到底在做什么**：它远不只是类型转换。它实作了一整套 **MEMFS**（内存虚拟文件系统，让 `fopen("video.mp4","rb")` 这种调用有地方可去）、把 SDL2 的绘图指令转译成 WebGL、把 `pthread` 映射到 Web Worker + `SharedArrayBuffer`、把 `printf` 接到 `console.log`。**这就是为什么 OpenTTD、VLC 这种数十万行的 C++ 游戏与播放器可以「几乎不改内核逻辑」就搬上网页**——不是因为 Wasm 神奇，是因为 Emscripten 在下面垫了一整层假的操作系统。

> 💡 君之一席话
> 与君一席话：**任何两个异质系统之间的接口，成本都不在「传输」，而在「翻译」。** JS 与 Wasm 之间传一个 `i32` 几乎免费，传一个字符串却要付两次编解码与两次拷贝——差别不在数据量，在于**两边对「什么是一个值」的定义不同**。这条规律的适用范围远远超出 Wasm：ORM 的对象关联阻抗不匹配、微服务之间的 JSON 串行化、Python 与 C 扩充之间的 GIL 边界、GPU 与 CPU 之间的数据上传——**每一个都是同一个病，而每一个的解法也都一样：把接口做粗、把往返做少、让数据在同一侧待久一点。** 当你发现自己在优化一个接口的传输速度时，先确认你不是在优化一件本来就不该做那么多次的事。

## 本章小结

- Wasm **不是机器码，是一台抽象堆栈机器的指令编码**。区段顺序、结构化控制流、堆栈类型一致性——每一条设计都是为了让验证能在 **O(n) 单趟线性时间**完成，这才是「边下载边编译」的前提。
- 通过验证的模块**不可能**越界读写、任意跳转或破坏调用堆栈。但**沙盒安全 ≠ 应用安全**：线性内存内部没有 ASLR/NX/stack canary，C 程序的内存错误在 Wasm 里反而可能更稳定可利用（见情境 1 ⚠️）。
- **线性内存只能长不能缩**，`memory.grow` 会使既有的 `TypedArray` 视图失效，地址 0 合法可写，越界必 trap。界检查靠**保留 8GiB 虚拟地址 + 保护页**做到热路径零指令——代价由 MMU 免费承担。
- 验证器用**多态堆栈**处理 `unreachable` 之后的死代码——一个看起来像特例的规则，实际上是为了保住「单趟 O(n)」这个更根本的性质（附录 M §2）。
- **分层编译（Liftoff → TurboFan）** 让「立刻能跑」与「跑得够快」不必在同一个时间轴上竞争；`instantiateStreaming` + 正确的 `application/wasm` MIME 是免费的启动优化，代码缓存让回访成本降一个量级。
- **启动是四段独立的成本**（传输／编译／实例化／运行期初始化），而**第四段最常被低估**。针对它有专门的武器——**Wizer** 可在建置时跑完初始化并把内存状态快照回模块（附录 N §10-2）。
- 「Wasm 有 60~80% 原生性能」是一句**几乎没有信息量的话**——SIMD 宽度、跨界频率、字符串比重、缓存行为，每一项都能把这个数字挪动一倍以上（见情境 3 🔍）。
- **边界是收费站**：一次字符串往返 = 两次编解码 + 两次拷贝 + 三次跨界调用。**把接口做粗、把往返做少**，是所有 Wasm 性能优化里回报最高的一条。
