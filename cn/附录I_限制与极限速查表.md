# 附录I　限制与极限速查表

> 一页看完所有会撞到的墙。**每一条都标明「这是规范限制、引擎限制，还是实务建议」**——因为它们的可绕过性完全不同。

---

## 一、大小与内存

| 项目 | 数值 | 性质 | 绕法 |
|---|---|---|---|
| 线性内存页大小 | **64 KiB** | 规范 | — |
| wasm32 寻址上限 | **4 GiB**（2³²） | **规范，绕不过** | 串流分块；多实例隔离；**多重内存**；Memory64 |
| 浏览器实际内存上限 | 常在 **2–3 GiB** 就 OOM | 引擎（随版本/平台变动） | 降低初始内存、分块处理 |
| wasm64 寻址上限 | 2⁶⁴（理论） | 规范 | **代价：失去保护页的免费界检查** |
| `.wasm` 文件大小（浏览器） | 硬性 1–2 GB 级 | 引擎 | — |
| `.wasm` 文件大小（实务建议） | **10–30 MB 以内** | **实务建议** | **先砍数据**、`wasm-opt -Oz`、模块分割、Brotli |
| 真实参照（FluffOS 驱动器） | **3.6 MB 原始 / 0.8 MB Brotli**；ICU 数据 30MB→780KB | 实测 | 见附录 L |
| `.wasm` 文件大小（后端） | 无明确上限 | — | 受物理内存支配 |
| `memory.grow` 方向 | **只能增长，不能缩小** | 规范 | 用完丢掉整个实例（微秒级） |
| 地址 0 | **合法可读写**（无空指针保护） | 规范 | Emscripten 可保留低地址当陷阱区 |

## 二、线程与并行

| 项目 | 限制 | 性质 |
|---|---|---|
| Wasm 原生创建线程 | **不能**。必须靠宿主（Web Worker / OS thread） | 规范 |
| 共享内存 | 需要 `SharedArrayBuffer` + 多线程特性 | 规范 |
| `SharedArrayBuffer` 前提 | **跨来源隔离**（COOP + COEP 两个 HTTP Header） | 浏览器安全策略 |
| GitHub Pages 设 Header | **不允许** | 平台限制 |
| 绕法 | `coi-serviceworker`（前端合成 Header）；或改用多实例隔离 | — |
| 多实例隔离的内存 | **4 GiB × N**（各自独立） | — |
| 多实例隔离是否需要隔离 | **❌ 不需要** | — |

## 三、SIMD

| 项目 | 数值 | 对照 |
|---|---|---|
| Wasm SIMD 矢量宽度 | **固定 128 比特（`v128`）** | x86 AVX2 = 256、AVX-512 = 512；ARM SVE 可变 |
| 典型加速比 | **2–4 倍**（不是 4–16 倍） | 内存带宽与数据重排会吃掉一部分 |
| 是否需要侦测 | **是**，老浏览器没有 | 需准备非 SIMD 备援建置 |
| Relaxed SIMD | 放宽语意换性能，**结果可能因平台而异** | 链上/需确定性的场景必须禁用 |

## 四、跨界（JS ↔ Wasm）

| 项目 | 成本 |
|---|---|
| 传一个 `i32` | 几乎免费（奈秒级） |
| 传一个字符串（双向） | **两次编解码 + 两次拷贝 + 三次跨界调用**（可到微秒级） |
| `postMessage` 结构化拷贝 | O(n) |
| `postMessage` + Transferable | **O(1)**（转移所有权，来源侧立刻失效） |
| `SharedArrayBuffer` | O(1)（双方同时可见，需隔离） |
| 直接操作 DOM | **不能**，必须经 JS |
| **黄金法则** | **把边界做粗、把往返做少** |
| 同步代码等异步 API | **JSPI**（Chrome 137+／FF 139+）挂起整条 Wasm 堆栈；退路是 Asyncify（贵） |

## 五、保存

| 机制 | 持久 | 随机访问 | 吃线性内存 | 主线程可用 | 适用 |
|---|---|---|---|---|---|
| **MEMFS** | ❌ | ✅（在内存里） | **✅ 致命** | ✅ | 暂存中间档 |
| **IDBFS** | ✅ | ❌（整包倒带） | 同步时吃 | ✅ | 游戏存盘、设置（<几 MB） |
| **OPFS（async）** | ✅ | 有限 | ❌ | ✅ | 一般文件 |
| **OPFS（sync handle）** | ✅ | **✅ 真 pread/pwrite** | ❌ | **❌ 只能 Worker** | 数据库、大文件、串流 |
| **WASI（后端）** | ✅ | ✅ | ❌ | — | 服务器端 |

**额外限制**：OPFS 同一文件默认只能有**一个** sync access handle（独占锁；`{mode:"readwrite-unsafe"}` 可开多个，但并行控制责任归你）；未 `persist()` 的数据可能在磁盘压力下被驱逐；用户看不见 OPFS，必须自行提供导出功能。

## 六、语言与运行期负担

| 语言 | 典型 Hello World 体积 | 是否适合 |
|---|---|---|
| Rust / C / C++ / Zig | 数 KB – 数十 KB | **★ 天生一对** |
| AssemblyScript | 数 KB | ★ 前端平滑入口 |
| Go（标准工具链） | ~1.5 MB+ | ⚠️ 体积是主要痛点（TinyGo 可大幅缩减） |
| C# / Blazor | 数 MB 级 | ⚠️ 生态强，冷启动与体积是代价 |
| Java / Kotlin | 传统上极大 | **Wasm GC 落地后才真正可用** |
| Python (Pyodide) | 30–50 MB 全家桶 | 只在「需要整个科学生态」时划算 |

**运行性能的两层现实**（以 Pyodide 为例）：纯 Python 循环约原生的 **1/3–1/5**；调用 NumPy 的 C 算子约 **70%**。**在虚拟机里跑解译器，两层抽象叠加。**

## 七、规范层面「不存在」的东西

| 没有 | 后果 | 对应提案 |
|---|---|---|
| `goto` / 任意跳转 | 编译器必须把 CFG 结构化（Relooper/Stackify），少数不可归约循环会慢 | multi-loop（未落地） |
| 字符串类型 | 每次往返要编解码 | JS String Builtins |
| 对象 / 垃圾回收（MVP 没有） | 高级语言要自带 GC → 体积暴增 | **✅ 已进 Wasm 3.0** |
| 例外处理（MVP 没有） | C++ try/catch 靠 JS 蹦床 | **✅ 已进 Wasm 3.0**（Tag 区段 + `try_table`/`exnref`） |
| 尾调用（MVP 没有） | 函数式语言深层递归爆栈 | **✅ 已进 Wasm 3.0**（`return_call`） |
| 阻塞／等待异步 | 同步 C 代码无法等 Promise | **JSPI**（2025-04 标准化，Chrome 137+／FF 139+） |
| 系统调用 | 一切能力必须由宿主 import | **WASI** |
| ASLR / NX / stack canary | **线性内存内部的 C 内存错误可能更稳定可利用** | 无（用 ASan/UBSan 补） |
| 运行期反射 / 动态加载（内核） | 静态链接导致重复打包 | dynamic linking（Emscripten 有自己的方案） |

## 七之二、部署层必检

| 项目 | 要求 |
|---|---|
| MIME | `Content-Type: application/wasm`（否则 `instantiateStreaming` 直接拒绝） |
| 差分更新 | 压缩字典传输（RFC 9842，`dcb`/`dcz`）：改版只传增量（附录 N §7-2） |
| ⚠️ 计时器精度 | **未跨来源隔离时 `performance.now()` 被降精度**——微秒级操作量不准（附录 N §15） |
| CSP | `script-src 'wasm-unsafe-eval'`（Chrome 97+／FF 102+／Safari 16+） |
| 压缩 | `Content-Encoding: br`（Wasm 压缩率通常很好，常见 4 倍以上） |
| 完整性 | **`fetch()` 加载的 `.wasm` 没有内置 SRI**；自行验哈希会牺牲串流编译 |
| 代码缓存 | 给 `.wasm` 稳定 URL（内容哈希文件名最佳），回访可跳过编译 |
| 多 Worker | `WebAssembly.Module` 可结构化拷贝——**编译一次 postMessage 给 N 个 Worker** |

## 八、安全红线

| 红线 | 为什么 | 检查方式 |
|---|---|---|
| **硬编码密钥** | 字符串在 Data 段，**无法剥离** | `strings app.wasm \| grep -Ei 'sk-\|AKIA\|password\|secret'` |
| **内核商业机密算法** | 逆向擡高的是成本不是可能性 | 问：对手明天拿到它，我还剩什么？ |
| Export 段 | **规范强制，永远可见** | `wasm-objdump -x app.wasm` |
| 「客户端自我完整性校验」 | 客户端不可信，任何自证都能被本地改掉 | 把授权判断放服务器端 |

**逆向难度的六个层次**（见第 9 章）：读字符串（秒）→ 看 Export（秒）→ 反汇编 WAT（分）→ 伪码还原（时）→ 看懂算法（天–周）→ 还原可维护原代码（月+，通常不划算）。

## 九、性能宣称的阅读守则

| 常见宣称 | 真实情况 |
|---|---|
| 「Wasm 有 60–80% 原生性能」 | **视工作负载形状而定**：纯数值循环可达 90%+；手写 AVX2 移植过来可能只有 40–50%；细碎跨界调用可能比 JS 还慢 |
| 「比 JS 快 10–30 倍」 | 只在特定基准成立。V8 充分预热且类型稳定时，**JS 可逼近 Wasm，差距常在 1–2 倍内** |
| 「比 Docker 快 100 倍」 | **指冷启动时可信**；稳态运行性能**低于**容器内的原生二进位 |
| 「文件只有几 KB 到几 MB」 | 指纯运算内核。OpenCV.js 6–9MB、solc 10–15MB、Pyodide 30–50MB |
| 「Wasm 内存安全」 | 指**沙盒边界**安全（伤不到宿主），**不代表**你的 C 程序没有内存错误 |
| 「Wasm 不可逆」 | **错误**。格式公开且结构化，反汇编比逆向 x86 容易得多 |
| 「开 Wasm GC 体积砍 80%」 | 只对「原本要打包语言运行期」的语言成立（Java/Kotlin/Dart）；**对 Rust/C/C++ 几乎无效** |
| 「GC／memory64／尾调用是提案」 | **已过时**。这些在 **2025-09 的 Wasm 3.0** 就进了内核规范（见附录 A） |
| 「用了 Wasm 所以是恒定时间」 | **错误**。恒定时间由原代码写法保证，Wasm 只是提供更可控的基底 |
