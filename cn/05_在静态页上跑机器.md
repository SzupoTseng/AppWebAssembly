# 第二篇　在静态页上造机器

# 第5章　在静态页上跑机器：COOP/COEP 那道坎，与一个天才级的绕法

> **「GitHub Pages 的网页是静止的吗？可以跑 server？」**
> 这是整趟调查的转折点。答案是：网页本身一点都不静止，但你确实不能在上面跑一台传统服务器。**而 Wasm 让第三个答案成为可能——你可以把服务器搬进用户的浏览器里。**

## 情境 1　先把三件事分清楚：GitHub 网站、GitHub Pages、以及「跑 server」

**背景**：这三个词经常被混在一起，导致一个很常见的误解——「GitHub 是静态的」。

**GitHub 网站本身：一点都不静态。** 你浏览保存库、开 Issue、送 Pull Request 时看到的是高度动态的网页：前端有大量 JavaScript（React 组件）处理即时交互，后端则是 GitHub 自己庞大的服务器群（主要以 Ruby on Rails 构建），负责处理请求、访问数据库与文件系统。

**GitHub Pages：只托管静态文件。** 它把你 repo 里的 HTML、CSS、JS、图片、`.wasm` 原封不动地经由 CDN 送出去。

- ❌ **不能**：跑 Node.js / Django / Go 的后端进程、监听连接端口、连数据库、跑调度。
- ⭕ **可以**：托管单页应用（React / Vue / Svelte）、以及**由 WebAssembly 驱动的任意复杂前端运算**。

**GitHub 提供的另外两种「能跑东西」的地方**（厘清边界很重要，因为很多人拿它们当替代方案）：

| 服务 | 能跑什么 | 硬限制 |
|---|---|---|
| **GitHub Pages** | 静态文件 + 浏览器端的一切（含 Wasm） | 无自订 HTTP Header、无后端、无数据库 |
| **GitHub Actions** | 在虚拟机（Linux/Windows/macOS）里启动任何进程，包含数据库与服务器 | **为测试/打包而生**：单次运行有时间上限（公开保存库上限通常为 6 小时／工作），结束后 VM 销毁，**不能当常驻网站主机** |
| **GitHub Codespaces** | 完整的云端开发容器，可 `npm start`、`python manage.py runserver`，并自动产生临时的端口转发网址 | 开发用途，会闲置休眠，**不是生产主机** |

**内核联结**：如果你想在「静态网页环境」里跑一个看起来很像后端的服务，**Wasm 就是解答之一**。现在已经有项目（例如 StackBlitz 的 **WebContainers**）成功利用 Wasm 把 Node.js 运行期与操作系统内核的相当一部分直接编译并运行在浏览器内部——用户只要打开网页，浏览器就会用 Wasm 在前端「仿真」出一台后端服务器，完全不需要真正的云端主机。

**而如果你想看一个把这件事做到底的例子**：**FluffOS**——一台还在维护的 LPMud 驱动器（MudOS 的现代分支，C++ 撰写）——已经把 **WebAssembly 列为官方建置目标之一**，官方 README 的原话是「**整个驱动器跑在一个浏览器分页里：编译器、虚拟机、efuns、telnet**」。它的 mudlib（也就是整个游戏世界的原代码）用 Emscripten 的 `file_packager` 打包成静态 bundle，**不需要服务器**。这意味着一个有心跳、有定时器、有持久世界状态、还要在运行期编译用户代码的多人游戏服务器，变成了三个可以丢上 CDN 的静态文件。**完整拆解见附录 L。**

> ⚠️ 真伪提醒
> 「WebContainers 把 Node.js 跑在浏览器里」是真实且可验证的（StackBlitz 的公开技术文章有详细说明）。但要准确理解它的边界：**它不是把 Node.js 的 C++ 原代码原封不动编译成 Wasm**，而是重新实作了一套运行在 Wasm 上、与 Node.js API 兼容的运行期，并用 Service Worker 拦截网络请求来仿真服务器行为。**「在浏览器里跑一台真正的服务器」这句话的精确版本是：在浏览器里仿真出一个对本页面而言行为一致的服务器。** 外部互联网上的其他人，**无法**通过网址连进这台「服务器」——除非再配上 P2P 穿透。

> 💡 君之一席话
> 与君一席话：**「静态」与「动态」从来不是网页的属性，是「运算发生在哪一端」的属性。** 同一个 HTML 文件，放在 CDN 上是静态的，但它拉起的 Wasm 模块可以在客户端做完影音转码、跑完 SQL 查找、推完一轮神经网络。运算没有变少，**它只是换了付钱的人**——从你的服务器帐单，换成了用户的 CPU 周期与电池。这件事的商业意涵远大于技术意涵：**当一项昂贵的成本可以被无痛地转移给用户，且用户感受不到痛，那个成本就会被转移。** 广告 SDK 这样做、加密货币挖矿脚本这样做、而 Wasm 让正当的重运算也能这样做。所以下次看到「零服务器成本」这五个字，要习惯性地补上下半句：**成本没有消失，它变成了别人的电费。**

## 情境 2　那道 90% 的人会撞上的坎：COOP / COEP

**背景**：你在本机 `python -m http.server` 跑得好好的 FFmpeg.wasm，一推上 GitHub Pages 就喷错：

```
ReferenceError: SharedArrayBuffer is not defined
```

或者

```
Uncaught DOMException: Failed to construct 'Worker': ... blocked by cross-origin isolation
```

**问题的完整因果链**（这是理解一切的关键，第 3 章埋的伏笔在这里爆掉）：

```
Spectre（2018，CPU 推测运行侧信道漏洞）
   ↓ 攻击需要高精度计时器来测量缓存时序
SharedArrayBuffer 可以搭配 Atomics 做出奈秒级计时器
   ↓ 于是浏览器全面默认停用 SharedArrayBuffer
   ↓ 后来放回来，但附加条件：页面必须「跨来源隔离」
跨来源隔离要求服务器回传两个 HTTP Header
   ↓
Cross-Origin-Opener-Policy: same-origin      ← 切断与其他来源窗口的 window 参考
Cross-Origin-Embedder-Policy: require-corp   ← 所有跨来源子资源必须明确授权
   ↓ 两者同时满足时，self.crossOriginIsolated === true
   ↓ 此时 SharedArrayBuffer 才存在
   ↓ 而 Wasm 的多线程依赖 SharedArrayBuffer
   ↓
❌ GitHub Pages 不允许自订 HTTP Header
   ↓
凡是用到多线程的 Wasm 项目（FFmpeg.wasm 多线程版、
OpenCV 并行、Emscripten pthread、Rust rayon-wasm…）
在 GitHub Pages 上直接无法运行
```

**两个 Header 各自在防什么**：

- `Cross-Origin-Opener-Policy: same-origin`（COOP）：切断 `window.opener` 这条跨来源的参考链，防止其他来源的窗口与你共处同一个操作系统进程（因为同进程意味着同一个地址空间，Spectre 就有机会读到你的内存）。
- `Cross-Origin-Embedder-Policy: require-corp`（COEP）：要求页面内加载的**每一个**跨来源资源（图片、脚本、iframe、字体）都必须明确表态同意被嵌入——通过 `Cross-Origin-Resource-Policy: cross-origin` 回应标头，或走 CORS。**没表态的一律挡掉。**

**COEP 的连带伤害是这件事最痛的地方**：一旦你开了跨来源隔离，**所有没有回传 CORP/CORS 标头的第三方资源全部会坏掉**——Google Fonts、CDN 上的图片、YouTube 嵌入、广告、统计脚本。这就是为什么即使你有能力设 Header（例如自架 Nginx 或用 Cloudflare Pages 的 `_headers`），打开隔离仍然是一个要付出代价的决定。

> 💡 **解决方案：`coi-serviceworker`**
> 开源社群做出了一个天才级的绕法。你可以引入一个名为 **`coi-serviceworker`** 的脚本，它利用浏览器的 **Service Worker** 技术，在**前端**拦截页面自己发出的所有请求，并在回应上「补上」这两个 Header。
> 做法：把 `coi-serviceworker.js` 放到 GitHub Pages 根目录，并在 `index.html` 的 `<head>` 最上方引入：
> ```html
> <script src="coi-serviceworker.js"></script>
> ```
> 首次加载时 Service Worker 尚未接管，脚本会自动刷新一次页面；第二次加载时所有回应都会带上 COOP/COEP，`crossOriginIsolated` 变成 `true`，`SharedArrayBuffer` 出现。

**它为什么合法、又为什么安全**：Service Worker 是一个由**同源页面自己注册**的代理层，它只能拦截自己 scope 内的请求。它并没有绕过浏览器的安全模型——**它是在页面自己的权限范围内，声明「我自愿进入隔离状态」**。浏览器接受这个声明，因为隔离的代价（失去跨来源资源）也是由这个页面自己承担的。

**它的四个代价**（一定要知道，否则会在正式环境踩雷）：

1. **必须多加载一次页面**（Service Worker 注册后才生效），首次体验会闪一下。
2. **需要 HTTPS**（GitHub Pages 默认有，本机 `localhost` 也被视为安全来源）。
3. **依然会挡掉没有 CORP 的跨来源资源**——这一点跟真正设 Header 一模一样，Service Worker 只能改自己能碰到的回应。
4. **Service Worker 有自己的缓存与更新语意**，部署新版时可能遇到用户拿到旧版的问题，需要处理 `skipWaiting` / `clients.claim`。

**什么时候你根本不需要这一整套**：**如果你的 Wasm 是单线程的，就完全不需要 COOP/COEP。** 大多数项目（`wasm-pack` 的默认输出、多数解析器与编译器）都是单线程的，直接推上 GitHub Pages 就能跑。**先确认你真的需要多线程，再去付这个代价。**

### 两个能少付代价的选项

**选项一：`COEP: credentialless` 取代 `require-corp`。**

`require-corp` 要求每一个跨来源子资源都**主动表态同意**被嵌入（回传 `Cross-Origin-Resource-Policy`）——而你管不了第三方要不要表态。`credentialless` 换了一个思路：**允许加载没有表态的跨来源资源，但以「不带凭证」（不送 cookie、不送 client cert）的方式请求。**

```http
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: credentialless    ← 比 require-corp 温和得多
```

**它同样能让 `crossOriginIsolated` 变成 `true`**，却不会把那些「只是没设 CORP 的公开图片与字体」整批打死。代价是：**需要带 cookie 才能取得的跨来源资源会拿不到**（因为请求不带凭证），而且浏览器支持度不如 `require-corp` 齐。**先试 `credentialless`，不行再退回 `require-corp`。**

**选项二：换一个不需要 `SharedArrayBuffer` 的后端。**

这一条的价值往往被低估。以持久化 SQLite 为例：官方 SQLite-Wasm 提供**两种** OPFS VFS，第一代 `opfs` 需要 `SharedArrayBuffer`（因此需要隔离），而 **`opfs-sahpool` 完全不需要 COOP/COEP，而且是官方文档里最快的选项**（详见第 7 章）。

> 💡 **很多团队为了 `SharedArrayBuffer` 跟隔离搏斗了两周，而他们要的东西其实有一条不需要它的路。动手前先花十分钟读一下你依赖的函数库有没有第二个后端。**

### 还有一道你可能还没撞到、但迟早会撞到的墙：CSP

**如果你的站台设了 Content-Security-Policy，Wasm 的编译会被直接挡下来。**

原因是：`WebAssembly.compile()` / `instantiate()` / `compileStreaming()` 在 CSP 的眼里属于**动态代码产生**，跟 `eval()` 同一类。早期唯一的解法是开 `'unsafe-eval'`——**而那等于把整个 XSS 防线让出去**。

**现在的正解是一个专用关键字**：

```http
Content-Security-Policy: script-src 'self' 'wasm-unsafe-eval'
```

`'wasm-unsafe-eval'` **只允许 WebAssembly 编译，不放行 `eval()` 或 `new Function()`**。支持度：**Chrome 97+、Firefox 102+、Safari 16+**（Chrome 扩展则自 v103 起可在 manifest 的 `content_security_policy` 中使用）。

**这一条在三个场合特别容易咬人**：**（一）** 你的 Wasm 被嵌在别人的 iframe 里，而对方的 CSP 没放行；**（二）** 浏览器扩展；**（三）** 企业内部有统一 CSP 政策的门户网站。**症状是一个 CSP violation 错误，而不是 Wasm 错误——所以很容易查错方向。**

> 🔍 进阶点评──`coi-serviceworker` 是一个「合法的协定漏洞」，而这类东西的寿命值得警惕
> 这个绕法能成立，靠的是安全模型里的一个微妙前提：**浏览器认为「页面自愿进入隔离状态」与「服务器要求页面进入隔离状态」在安全意义上等价**，因为隔离的保护对象是这个页面自己。这个推理是严谨的，所以 `coi-serviceworker` 不是漏洞利用，是一个**对规范的正确使用**。但这里有两件事值得长期警惕。**第一，它依赖的是一个未曾被明确承诺的组合行为。** 规范没有一条文本说「Service Worker 合成的 COOP/COEP 标头必须被视为与服务器发出的等效」——它是各家实作对规范的自然推论。任何依赖「多个规范交集处的推论行为」的技巧，都存在被未来版本收紧的风险。**第二，也是更根本的：它揭示了一个结构性事实——免费的静态托管给了你 CDN、给了你 HTTPS、给了你版本控制，唯独不给你「回应标头」这个控制权，而现代 Web 的高级能力（跨来源隔离、CSP、Permissions Policy、Trusted Types、甚至部分 Origin Trials）全部系在回应标头上。** 所以真正的教训不是「学会用 coi-serviceworker」，而是——**当你选择一个免费平台时，你放弃的往往不是你当下需要的东西，而是你两年后才会需要的那个控制权。** 免费平台的天花板，总是在你长大到某个尺寸时才会被撞到，而那时迁移成本已经很高了。这件事在第 11、12 章谈护城河时会以另一种形式再出现：**控制权才是唯一真正稀缺的东西。**

## 情境 3　完整的部署路径：从 `cargo` 到那个 `github.io` 网址

**背景**：把理论收成一条可以照做的路径。以最主流的 **Rust + WebAssembly** 为例。

**步骤 1：本地编译**

用 `wasm-pack` 把 Rust 编译成 Web 专用的 Wasm 与 JS 胶水代码：

```bash
wasm-pack build --target web
```

这会产生一个 `pkg/` 文件夹，内含 `.wasm` 档与 `.js` 胶水档。

**`--target` 的四个选项要选对**（这是新手最常配错的地方）：

| target | 产出形态 | 适用 |
|---|---|---|
| `web` | ES module，可直接 `<script type="module">` 引入 | **GitHub Pages 静态部署的正解** |
| `bundler` | 给 webpack/rollup/vite 吃的模块（含 `import` 语法） | 有打包工具的项目 |
| `nodejs` | CommonJS，给 Node.js 用 | 服务器端 |
| `no-modules` | 挂在全域变量上的传统脚本 | 旧环境、或要在 Worker 里用 `importScripts` |

**步骤 2：撰写前端 HTML**

```html
<!DOCTYPE html>
<html lang="zh-TW">
<head>
  <meta charset="UTF-8">
  <!-- 只有用到多线程时才需要这一行，且必须放在最前面 -->
  <script src="coi-serviceworker.js"></script>
  <title>Wasm on GitHub Pages</title>
</head>
<body>
  <script type="module">
    import init, { greet } from './pkg/your_project.js';
    async function run() {
      await init();              // 初始化 Wasm 模块（内部走 instantiateStreaming）
      greet("GitHub Pages");     // 调用 Wasm 内部的函数
    }
    run();
  </script>
</body>
</html>
```

**步骤 3：推上去并打开 Pages**

1. 把项目（含 `index.html` 与 `pkg/`）推到 GitHub 保存库。
2. 进入 **Settings → Pages**。
3. 在 **Build and deployment** 下，选择从你的分支（例如 `main` 或 `gh-pages`）发布。
4. 等几分钟，通过 `https://<帐号>.github.io/<项目名>/` 造访。

**四个一定会踩的坑**（依踩到的频率排序）：

1. **`.gitignore` 把 `pkg/` 忽略掉了**。`wasm-pack` 产生的 `pkg/` 在很多 Rust 范本里默认被忽略，于是你推上去的是一个没有 `.wasm` 的网站。**解法**：要嘛把 `pkg/` 加进版控，要嘛用 GitHub Actions 在 CI 里编译（见下）。
2. **路径是相对的，而项目页面有子路径**。`https://user.github.io/repo/` 这个子路径会让 `/pkg/xxx.js` 这种绝对路径 404。**解法**：全部用相对路径 `./pkg/xxx.js`。
3. **Jekyll 吃掉了底线开头的文件夹**。GitHub Pages 默认跑 Jekyll，会忽略 `_` 开头的文件与文件夹。**解法**：在根目录放一个空的 `.nojekyll` 文件。
4. **忘了 `await init()`**。Wasm 的加载是异步的，在初始化完成前调用任何导出函数都会炸。

**用 GitHub Actions 自动编译与部署**（比手动 commit `pkg/` 干净得多）：

```yaml
name: Deploy Wasm to Pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: wasm32-unknown-unknown
      - name: Install wasm-pack
        run: curl https://rustwasm.github.io/wasm-pack/installer/init.sh -sSf | sh
      - name: Build
        run: wasm-pack build --target web --release
      - name: Optimize
        run: |
          npm install -g binaryen
          wasm-opt -Oz --strip-debug pkg/*_bg.wasm -o pkg/tmp.wasm
          mv pkg/tmp.wasm pkg/$(ls pkg | grep _bg.wasm)
      - name: Assemble site
        run: |
          mkdir -p dist && cp index.html dist/
          cp -r pkg dist/ && touch dist/.nojekyll
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist
      - uses: actions/deploy-pages@v4
```

> 💡 君之一席话
> 与君一席话：**一条部署路径的难度，不在于步骤有几步，而在于失败时错误消息离真正的原因有多远。** 上面那四个坑，每一个的错误消息都在骗你：`pkg/` 没推上去，你看到的是 404；路径写绝对，你看到的还是 404；Jekyll 吃掉文件，你看到的**仍然是** 404。三个完全不同的病因，同一个症状。这就是为什么「照着教学做却跑不起来」是新手最常见的挫折——**教学写的是快乐路径，而现实里你 90% 的时间花在解读一个指向错误方向的错误消息上。** 所以真正有价值的文档不是步骤清单，是**症状-病因对照表**。这一点在你自己写工具、写函数库、写错误消息时同样成立：**一个好的错误消息，价值抵得上十页教学。**

## 情境 4　那三个最经典的「别人在上面跑什么」

**背景**：在深入一百零一个案例之前，先看三个最典型、也最能说明「为什么要这样做」的形态。

**形态一：把服务器的活转嫁给用户——网页版影音剪辑（FFmpeg.wasm）**

把 C 语言写成的影音工具 FFmpeg 编译成 Wasm。用户把视频拖进 GitHub Pages 网页，**转档直接用用户自己的 CPU 完成**，完全不消耗服务器流量。

- **价值不在快，在「不用付钱」**：一个云端转码服务（AWS MediaConvert 一类）按分钟计费，且要吃掉大量上传带宽；FFmpeg.wasm 的边际成本是零。
- **附带的隐私红利**：用户的视频文件从头到尾没有离开他的电脑。这在处理个人视频、医疗影像、企业内部素材时，是一个比性能更有说服力的卖点。

**形态二：把死掉的东西复活——网页版复古游戏仿真器**

许多用 C++ 或 Rust 写的 Game Boy、NES、PS1 仿真器被编译成 Wasm，托管在 GitHub Pages 上，点开网页就能玩。

- **为什么 Wasm 是关键**：仿真器需要**时钟精确（clock-accurate）**地仿真 CPU 周期。JavaScript 的计时器不精确、垃圾回收会随机暂停，导致音画不同步与爆音。Wasm 的性能曲线是平的，这正是仿真器要的。

**形态三：把 AI 推到端上——浏览器端推理（ONNX Runtime Web）**

在 GitHub Pages 上加载轻量化的模型（对象侦测、人脸辨识），通过 Wasm 进行即时计算，**连服务器 AI 芯片的钱都省了**。

- **Wasm 在这里的角色是「保底方案」**：WebGPU/WebGL 后端更快，但依赖驱动与硬件；Wasm CPU 后端在任何设备上都能跑。**这是可用性而非性能的选择。**

**形态四：把整台服务器搬进来——浏览器里的 MUD 驱动器（FluffOS × Wasm）**

前三个形态都是「把一个**函数**搬过来」——喂它输入、拿它输出。**第四个形态不一样：它搬的是一台有心跳、有状态、会一直活着的服务器。**

- **它为什么比前三个都难**：一台 MUD driver 不是请求处理器，它有 heartbeat、有 `call_out` 定时器、有持久的世界状态、有多条并发连接，**而且它要在运行期把 mudlib 的 LPC 原代码编译成字节码再运行**——编译器与虚拟机全都得跟着进浏览器。
- **它怎么解决「浏览器不能阻塞」**：原生驱动器阻塞在 libevent 的事件循环里，这在浏览器里是死路。解法是**把循环的所有权交给宿主**——页面用 `setInterval` 调用导出的 `fluffos_tick(now_ms)`，每次推进调度、处理到期事件后立刻返回。**调度内核与原生共用，差别只在谁来敲钟**，所以 mudlib 一行都不用改。
- **它的代价**：没有 socket（DNS 桩化回传 `127.0.0.1`）、没有线程、没有 TLS（归浏览器管）、**写入目前只在分页 session 内有效**（MEMFS，IDBFS/OPFS 覆盖层仍在 roadmap）。

**这个形态把「静态托管 + Wasm」推到了它的逻辑终点**：一整个持久的多人世界，变成三个静态文件。**详见附录 L。**

**四个形态的共同结构**（这是整个第二篇的骨架）：

```
    服务器原本要做的事
          ↓
    ┌─────────────────┐
    │  重、贵、可公开  │  ← 算法本身是公开的（FFmpeg、仿真器、ONNX 推理）
    │  的密集运算      │     没有商业机密，只有算力成本
    └─────────────────┘
          ↓ 编译成 Wasm
    ┌─────────────────┐
    │  推给用户的     │  ← 成本归零、隐私提升、无限并发
    │  浏览器运行       │     代价：首次下载体积、设备发热、耗电
    └─────────────────┘
```

**反过来，什么东西不能推出去**：任何涉及密钥、鉴权、计费、以及「一旦外流公司就完蛋」的内核算法。**这条线，就是第三篇整整四章要画的那条线。**

## 本章小结

- **GitHub 网站不静态，GitHub Pages 才静态**。Pages 只托管文件；Actions 是有时间上限、结束即销毁的 CI 环境；Codespaces 是会休眠的开发容器。**三者都不是常驻主机，而 Wasm 提供了第四条路：把服务器搬进浏览器。**
- **COOP/COEP 是静态托管上跑 Wasm 的头号障碍**，而它的完整因果链是：Spectre → `SharedArrayBuffer` 被停用 → 恢复但要求跨来源隔离 → 隔离要求两个 HTTP Header → **GitHub Pages 不给你设 Header** → 多线程 Wasm 直接挂掉。
- **`coi-serviceworker`** 用 Service Worker 在前端合成这两个 Header，是一个对规范的正确使用而非漏洞利用。代价是：多一次加载、需要 HTTPS、**仍会挡掉没有 CORP 的跨来源资源**、以及 Service Worker 的更新语意问题。
- **两个能少付代价的选项**：**`COEP: credentialless`**（允许没表态的跨来源资源，但不带凭证请求，比 `require-corp` 温和得多）；以及**换一个不需要 `SharedArrayBuffer` 的后端**（例如 SQLite-Wasm 的 `opfs-sahpool` VFS，**不需要隔离而且最快**，见第 7 章）。
- **先确认你真的需要多线程**——大多数 Wasm 项目是单线程的，直接推上去就能跑，根本不用碰这一整套。
- **CSP 是另一道迟早会撞到的墙**：Wasm 编译在 CSP 眼中属于动态代码产生，**正解是 `script-src 'wasm-unsafe-eval'`**（Chrome 97+／Firefox 102+／Safari 16+），它只放行 Wasm 编译而不放行 `eval()`。**症状是 CSP violation 而不是 Wasm 错误，所以很容易查错方向。**
- 部署路径的四个坑（`pkg/` 被 gitignore、绝对路径 404、Jekyll 吃掉底线文件夹、忘了 `await init()`）**症状全是 404，病因完全不同**——这正是「照教学做却跑不起来」的根源。
- 四个经典形态的共同结构是：**把「重、贵、算法公开」的密集运算推给用户的浏览器**。第四个形态（FluffOS 把整台 MUD driver 搬进分页，靠 `fluffos_tick` 让宿主接管事件循环）把这件事推到了逻辑终点——**一整个持久的多人世界＝三个静态文件**（见附录 L）。哪些不能推，是第三篇的主题。
- **「零服务器成本」的下半句永远是：成本没有消失，它变成了别人的电费。**

坎跨过去了，机器也跑起来了。那么——**别人到底在这上面跑了什么？** 那份滚了一百二十条的清单，下一章开始拆。翻到第 6 章。
