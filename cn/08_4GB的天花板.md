# 第8章　4GB 的天花板：文件大小、App 大小，与四种破圈架构

> **「Wasm 的 file size limit？app size limit？」**
> 这两个问题听起来像同一件事，其实是两个完全独立的天花板：**一个由「引擎能编译多大的模块」决定，另一个由「虚拟机能寻址多少内存」决定。** 把它们混在一起，是所有大型 Wasm 项目在架构评审时翻车的起点。

## 情境 1　两个天花板，四个数字

**背景**：先把四个数字摆清楚，后面所有的架构决策都是从这张表推出来的。

### 天花板一：`.wasm` 文件本身有多大

| 环境 | 硬性极限 | 实务天花板 | 限制的本质 |
|---|---|---|---|
| **浏览器** | 通常 1GB ~ 2GB 级 | **强烈建议 10MB ~ 30MB 以内** | 串流编译时要在内存中建构庞大的编译状态；且下载时间直接吃掉首屏 |
| **后端运行期**（Wasmtime / WasmEdge） | 无明确上限，受物理内存支配 | 数百 MB 到 1GB+ 皆可 | 只要内存够，可以把神经网络权重直接打包进模块 |

**为什么浏览器的实务天花板远低于硬性极限**：文件过大会导致三重代价叠加——网络下载时间拉长、解析几百 MB 的 Wasm 让行动设备 CPU 瞬间拉满而发热、首字渲染延迟（以及 Core Web Vitals 全线恶化）。**这是体验问题，不是能力问题**，但它比能力问题更难绕过。

### 天花板二：运行期的线性内存有多大

| 寻址模式 | 硬性极限 | 浏览器的现实拦截 | 状态 |
|---|---|---|---|
| **wasm32**（目前的绝对主力） | **死死锁在 4GiB**（2³² 字节） | Chrome 通常在 **2GiB ~ 3GiB** 就因保护机制抛出 OOM 并使分页崩溃 | 全面支持 |
| **wasm64**（Memory64，**已进 Wasm 3.0 内核规范**） | 理论上 2⁶⁴（16 EiB 级） | 受宿主 OS 与 cgroup 配额支配 | 已标准化，**但有性能代价** |

**wasm32 的 4GiB 是数学，不是实作选择**：地址是 32 比特指针，`2³² = 4,294,967,296` 字节。这条线绕不过去。

**工业案例的直接后果**：**FFmpeg.wasm 处理视频、v86 跑 Linux，在默认情况下绝对无法处理或加载大于 2~3GB 的单一文件**——因为文件必须先全量读进那块线性内存（见第 7 章的 MEMFS）。

**memory64 的隐藏成本**（这是市场材料绝口不提的一段，第 2 章已埋下伏笔）：

```
wasm32 的免费界检查：
  引擎保留 8GiB 虚拟地址空间（4GiB 可寻址 + 前后保护区）
  → 32 比特偏移量在数学上不可能超出保留区
  → 越界时由 MMU 触发 SIGSEGV，引擎接住翻成 trap
  → 热路径上的界检查指令数：0

wasm64 呢？
  你不可能为每块内存保留 2⁶⁴ 的虚拟地址空间
  → 保护页技巧失效
  → 必须退回「每次访问前显式比较 + 分支」
  → 性能回退：不同基准下数个百分点到双位数不等
```

**所以正确的心智模型是**：**你在 4GiB 以下享受的是硬件补贴的免费安全；越过那条线，安全就要开始收费了。** 这直接推出一条架构原则——**能靠分块串流（情境 2）或多重内存（情境 5）在 4GiB 以内解决的，就别急着跳 wasm64。**

> ⚠️ 真伪提醒
> 「wasm64 硬性极限高达 16EB」在数学上正确，但实务上毫无意义——没有任何宿主能提供这个量级的内存。更该记住的两个数字是：**（一）** 浏览器对单一 Wasm 内存的实际上限历来在 2GiB~4GiB 之间随版本与平台变动，**不要把 4GiB 当成可用额度**；**（二）** Memory64 虽已进入 **Wasm 3.0** 内核规范，**性能表现在各引擎间差异显著，采用前务必在目标环境实测**。
>
> **另外要注意一个容易搞混的语意**：`memory.grow` **失败时不会 trap，它回传 `-1`**（成功时回传成长前的页数）。这意味着**内存耗尽是一个你必须主动检查的回传值，不是一个会自己炸出来的例外**——而多数把 `malloc` 失败当成「不会发生」的 C 代码，会在这里安静地写进一块不存在的内存，然后才在下一次访问时 trap。**你看到的越界错误，往往是几百行之前那次没被检查的 grow 失败。**

> 💡 君之一席话
> 与君一席话：**每一个「免费」的系统特性，背后都有一个你没注意到的物理前提；当你越过那个前提，帐单就会出现。** Wasm 的界检查在 4GiB 以下是免费的，因为 64 比特宿主的虚拟地址空间便宜到可以整片浪费；一旦你要求 64 比特寻址，那个前提消失，于是本来免费的东西开始收费。这个模式在系统工程里反复出现：小对象的分配是免费的（因为有 slab allocator），直到你的对象变大；缓存是免费的（因为工作集小于 L3），直到你的数据变大；同步是免费的（因为只有一个线程），直到你加了第二个。**所以工程直觉里最值钱的一项，是知道每个「反正很快」的东西，是靠什么前提才快的**——因为扩张总是先打破前提，才显现成本。

## 情境 2　破圈架构一：OPFS 分块串流（滑动窗口）

**背景**：这是四种破圈架构里最重要、也最被低估的一种。它的内核思想是**拒绝把整个文件读进内存**。

**做法**：不要将整个 10GB 的文件一次性读入 Wasm 内存。而是利用 OPFS 的 `FileSystemSyncAccessHandle` 运行 `read(buffer, { at: offset })`——让 Wasm 内部只开辟一个 50MB 的**滑动窗口缓存（Sliding Window Cache）**，像看磁带一样，需要哪段数据、就用直控指针去磁盘抓哪段。

**结果：内存仅 50MB，却能流畅处理 100GB 巨型文件。**

```rust
// 概念骨架：在 Worker 里，用同步句柄做随机读取
const WINDOW: usize = 50 * 1024 * 1024;   // 50MB 滑动窗口

struct ChunkedReader {
    handle: FileSystemSyncAccessHandle,   // 来自 OPFS
    window: Vec<u8>,                      // 唯一常驻的那块内存
    window_start: u64,                    // 当前窗口对应的文件偏移
    window_len: usize,
    file_size: u64,
}

impl ChunkedReader {
    /// 读取任意位置的字节；只有跨出当前窗口时才触发磁盘 I/O
    fn read_at(&mut self, offset: u64, len: usize) -> &[u8] {
        let in_window = offset >= self.window_start
            && offset + len as u64 <= self.window_start + self.window_len as u64;
        if !in_window {
            // 重新定位窗口：对齐到区块边界，避免频繁小量读取
            self.window_start = (offset / CHUNK) * CHUNK;
            self.window_len = self.handle
                .read_at(&mut self.window, self.window_start);   // ← 同步 pread
        }
        let local = (offset - self.window_start) as usize;
        &self.window[local .. local + len]
    }
}
```

**四个实作要点**（这些决定它是能用还是很慢）：

1. **窗口要对齐**。把 offset 对齐到 1MB 或 4MB 边界再读，避免因为读一个字节而触发整个窗口重载。
2. **考虑访问模式**。顺序扫描（如视频解码）用大窗口 + 预读；随机跳跃（如数据库索引）用小窗口 + 多窗口 LRU 缓存。
3. **必须在 Worker 里**（`createSyncAccessHandle` 的规范限制，见第 7 章）。
4. **远程文件用 HTTP Range Request 走同一套逻辑**——把 `handle.read_at()` 换成 `fetch(url, {headers: {Range: 'bytes=...'}})`，架构完全相同。**DuckDB-Wasm 查找远程 Parquet 就是这么干的**（见第 6 章）。

**这一招的威力在于它把「内存上限」问题转化成了「I/O 带宽」问题**——而后者可以用预读、缓存、压缩来缓解，前者是一堵墙。

## 情境 3　破圈架构二：多模块内存隔离（4GB × N）

**背景**：既然单一 Wasm 实例最多 4GiB，那就开很多个。

**做法**：在网页端启动多个独立的 Web Worker，**每个 Worker 内部各加载一个独立的 Wasm 运行期实例**。由于每个虚拟机都有自己独立的 4GiB 线性内存，你可以通过主线程作为数据总线（bus），在多个 Worker 之间分发任务，**将整个 App 的算力与内存上限倍增到 4GiB × N**。

```
                主线程（只做调度，不做运算）
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   Worker 1         Worker 2        Worker 3
   Wasm 实例 A      Wasm 实例 B      Wasm 实例 C
   线性内存 4GiB   线性内存 4GiB   线性内存 4GiB
   （处理第 1 段）   （处理第 2 段）   （处理第 3 段）
        │               │               │
        └───────────────┴───────────────┘
              结果用 Transferable 回传，零拷贝
```

**它跟「Wasm 多线程」是完全不同的两件事**（这是最容易混淆的地方）：

| | 多实例隔离（本节） | Wasm threads（`SharedArrayBuffer`） |
|---|---|---|
| 内存 | 每个实例各自独立的 4GiB | **共用一块**线性内存，总量仍受 4GiB 限制 |
| 通信 | `postMessage` + Transferable（拷贝或转移所有权） | 直接读写同一块内存 + 原子操作 |
| 需要跨来源隔离 | **❌ 不需要** | **✅ 需要 COOP/COEP** |
| 适合 | 数据可分割的任务（分块处理、平行渲染、独立查找） | 需要细粒度共享状态的算法（物理仿真、图遍历） |
| 在 GitHub Pages | **直接可用** | 需要 `coi-serviceworker` |

**这张表有一个非常实用的推论**：**如果你的任务是「数据可切分」的（绝大多数批量处理都是），用多实例隔离就好——它不需要跨来源隔离、不会打坏你的第三方资源、还顺便突破了 4GiB。** 很多团队在跟 COOP/COEP 搏斗了两周之后才发现自己根本不需要共享内存。

## 情境 4　破圈架构三：多重内存（Wasm 3.0 添加）

**背景**：这是 2025 年 9 月才进入内核规范的一条新路，而它恰好正面对付 4GiB 的问题。

**做法**：**Wasm 3.0 的 multiple memories 让一个模块可以声明并访问多块线性内存，而且能直接在它们之间搬数据。**

```wat
(module
  (memory $code 16)          ;; 第 0 块：代码工作区
  (memory $assets 1024)      ;; 第 1 块：资产／大数据
  (memory $scratch 64)       ;; 第 2 块：暂存区

  (func $copy_in
    ;; memory.copy 可以跨内存：目的地内存索引、来源内存索引
    (memory.copy $scratch $assets
      (i32.const 0) (i32.const 4096) (i32.const 65536)))
  ;; 加载/保存也可以指定内存索引
  (func $peek (result i32)
    (i32.load $assets (i32.const 1024))))
```

**它与前两条路的关系，值得画清楚**：

| | 多重内存（本节） | 多模块隔离（情境 3） | Memory64 |
|---|---|---|---|
| 几个 Wasm 实例 | **一个** | N 个 | 一个 |
| 几块内存 | **多块** | 每个实例一块 | 一块（超大） |
| 数据搬移成本 | **`memory.copy` 跨内存，引擎层完成** | `postMessage` 跨线程 | 不需搬 |
| 保护页免费界检查 | **✅ 每块仍是 wasm32，全部保留** | ✅ | **❌ 失去** |
| 需要 Worker | ❌ | ✅ | ❌ |
| 需要跨来源隔离 | ❌ | ❌ | ❌ |
| 适合 | **单线程、数据可分区的大型应用** | 任务可切分的批量处理 | 真的需要单一超大地址空间 |

**它最漂亮的地方在于第四列**：因为每一块内存**各自仍是 32 比特寻址**，那套「保留虚拟地址空间 + 保护页 = 免费界检查」的机制**完整保留**。换句话说——

> **多重内存让你在不放弃免费界检查的前提下，突破单块 4GiB 的限制。**
> 这正是 Memory64 做不到的取舍，也是为什么在「数据可以自然分区」的场景（代码区 / 资产区 / 暂存区、多租户各一块、冷热数据分离），**多重内存几乎总是比 Memory64 划算。**

**现实的但书**：**工具链的支持落后于规范。** 多数 C/C++/Rust 工具链默认仍假设「只有一块内存」，要用到它通常得手写 WAT、或用支持多内存的较新工具链与属性标注。**规范先到，工具链后到——这是每一条新特性的常态，也是「规范状态」与「你今天能不能用」必须分开问的原因。**

## 情境 5　破圈架构四：激活 Wasm GC，把运行期还给浏览器

**背景**：前三招都在对付**内存天花板**。这一招对付的是情境 1 立下的**另一个天花板——文件体积**。

**问题**：如果你使用 Java、Kotlin、Dart、C# 这类高级语言编译为 Wasm，传统做法必须把整个语言的垃圾回收器与标准库打包进 `.wasm` 文件里，这会让文件体积暴增到数 MB 甚至更多。

**做法**：直接打开 **Wasm GC**（2025 年 9 月已随 Wasm 3.0 进入内核规范），让 Wasm 使用浏览器原生的、经过极致优化的垃圾回收引擎（V8 的 Orinoco、SpiderMonkey 的 GC），而不是自己带一套。

**Wasm GC 在规范层面加了什么**（技术细节，因为这是本章最新的一块）：

- **堆积类型（heap types）**：`struct`、`array`、以及 `i31`（一种可以塞在指针里的小整数优化）。
- **类型化参考（typed references）**：`(ref $MyStruct)`、`(ref null $MyArray)`——Wasm 第一次有了「指向一个有结构的对象」的能力，而不只是 `i32` 偏移量。
- **子类型（subtyping）与 `br_on_cast`**：让面向对象语言的继承与动态转型能被表达。

```wat
;; Wasm GC：真正的对象，由宿主 GC 管理，不占线性内存
(type $Point (struct (field $x f64) (field $y f64)))
(func $make (result (ref $Point))
  (struct.new $Point (f64.const 1.0) (f64.const 2.0)))
```

**收益与代价**：

| | 收益 | 代价 |
|---|---|---|
| 体积 | **可大幅缩减**（不用打包 GC 与部分运行期） | — |
| 性能 | 使用高度优化的宿主 GC，通常优于自带的简易 GC | 失去对回收时机的控制，**GC 暂停回来了** |
| 适用 | Kotlin/Wasm、Dart（Flutter Web）、Java、Scheme 等 | **对 Rust/C/C++ 几乎无用**——它们的数据本来就在线性内存里 |
| 支持 | **已进 Wasm 3.0 内核规范**，主流浏览器已支持 | 后端运行期与工具链支持度落后于浏览器 |

> ⚠️ 真伪提醒
> 常见宣称「打开 Wasm GC 能让 `.wasm` 文件体积直接缩减 80% 以上」。**方向正确，但这个数字只对「原本要打包整个语言运行期」的语言成立**（Java、Kotlin、Dart 等），且实际缩减幅度取决于原本打包了多少东西。**对 Rust、C、C++ 而言，打开 Wasm GC 几乎没有体积效益**——它们的对象本来就配置在线性内存里，根本没有 GC 可以省。把这条建议无差别套用到所有语言，是一个很常见的误读。

**但在你去调任何编译旗标之前，先做第 0 条**——它的投报率往往压过其他全部：

> **★ 第 0 条：先砍数据，再砍代码。**
> 大型 C/C++ 项目的 Wasm 产物里，常有一半以上是它拖进来的**数据表**，而那些表通常有 90% 你根本用不到。
> **实例**（附录 L）：FluffOS 的 Wasm 建置只保留 ICU 的 break-iterator 规则，**数据从约 30MB 砍到约 780KB（−97%），而整个驱动器的代码本体才 3.6MB。**
> **所以第一个动作不是开旗标，是 `wasm-objdump -h` 看区段预算**——如果 Data 占了一半，把 Code 再压 10% 也只换来总体积 5%。

**确认完区段预算之后，才轮到那套工具链**：`wasm-opt -Oz` → 编译期设置（`lto` / `codegen-units=1` / `panic="abort"` / `strip`）→ `twiggy` 诊断 → 死码消除 → Brotli 传输 → 模块分割。

> **这只是清单。每一项真正砍掉什么、代价是什么、以及那些不在清单上的东西——Rust 藏在 `panic!` 里的格式化机制、单型化爆炸的「泛型薄壳」解法、`wasm-opt` 每个 pass 的作用、压缩字典传输如何让改版只传几十 KB——全部收在附录 N 第一部，含一张逐项的投报率总表。**

> 🔍 进阶点评──四种破圈架构，其实是同一种思想的四个投影
> 把这四招摆在一起看，会发现它们解的是同一个问题：**「一次要全部」是所有资源上限的共同病根。** 分块串流说的是「不要一次把数据全部装进来」，多模块隔离说的是「不要一次用一个实例装下全部」，多重内存说的是「不要把全部塞进同一块地址空间」，模块分割与延迟加载说的是「不要一次把代码全部下载」。**四者都是把一个「总量问题」拆解成「时间轴或空间轴上的分区问题」**——而流量问题永远比总量问题好解，因为你可以用预读、缓存、优先级、背景加载去摊平它。这条原理的推广性极强：数据库的分页查找、视频的自适应串流（HLS/DASH）、前端的虚拟滚动列表、LLM 的 KV cache 分页（PagedAttention）、操作系统的虚拟内存——**全部是同一个念头：不要问「我有多少」，要问「我此刻需要哪一段」。** 当你下次撞到任何一种「容量上限」时，第一个该问的问题不是「怎么把上限提高」，而是——**我是不是真的需要在同一个时刻拥有全部？** 十次里有九次，答案是不需要，而那第十次才值得去买更大的机器。

## 本章小结

- **两个独立的天花板**：`.wasm` **文件大小**（浏览器硬性 1~2GB 级，**实务建议 10~30MB**；后端几乎无限）与**线性内存大小**（wasm32 **死锁 4GiB**，浏览器常在 2~3GiB 就 OOM）。
- **wasm64 不是免费的**：一旦地址变成 64 比特，「保留 8GiB 虚拟地址 + 保护页」的免费界检查就失效，必须退回显式比较，带来实质性能回退。**4GiB 以下享受的是硬件补贴的安全。**
- **破圈一：OPFS 分块串流（滑动窗口）**——用 `createSyncAccessHandle` 的 `read(buffer, {at})` 做随机读取，内存 50MB 就能处理 100GB 文件。远程文件用 HTTP Range Request 走同一套逻辑。
- **破圈二：多模块内存隔离**——N 个 Worker × N 个 Wasm 实例 = 4GiB × N。**它跟 Wasm threads 是完全不同的两件事**：多实例**不需要 COOP/COEP**，在 GitHub Pages 上直接可用。**任务可切分时，优先选这个。**
- **破圈三：多重内存**（Wasm 3.0 添加）——一个模块多块线性内存，`memory.copy` 可跨内存搬数据。**最大优势是每块仍是 wasm32，因此保护页的免费界检查完整保留**——这正是 Memory64 做不到的取舍。但**工具链支持落后于规范**（见情境 4）。
- **破圈四：Wasm GC**（已进 Wasm 3.0 内核规范）——把垃圾回收还给宿主引擎，体积收益显著，**但只对「原本要打包运行期」的语言有效（Java/Kotlin/Dart），对 Rust/C/C++ 几乎无用**（见情境 5 ⚠️）。
- `memory.grow` **失败时回传 `-1` 而不是 trap**——内存耗尽是一个你必须主动检查的回传值，**你看到的越界错误往往是几百行之前那次没被检查的 grow 失败**。
- 砍体积的**第 0 条是「先砍数据，再砍代码」**——先用 `wasm-objdump -h` 看区段预算，Data 占一半时压 Code 没有意义。实例见附录 L（ICU 30MB → 780KB）。**完整武器库与投报率总表见附录 N 第一部。**
- 四种破圈架构是同一个思想的四个投影：**把「总量问题」拆成「时间轴或空间轴上的分区问题」**——当你撞到任何容量上限时，先问「我是不是真的需要在同一个时刻拥有全部？」（见情境 5 🔍）

第二篇到此结束。机器造好了、跑起来了、记得住东西了、也突破了容量限制。**现在来面对那个从一开始就悬在头上的问题：这台机器，被完整下载到了每一台陌生的电脑上。** 翻到第 9 章。
