# 第三篇　看光之后的护城河

# 第9章　都被看光了：二进位的天然混淆、两大物理禁区与混合架构

> **「在 GitHub Pages 跑程序，不是被看光了？」**
> 是的，完全被看光了。这不是缺陷，是静态托管的定义。用户浏览你的网站时，浏览器会把所有的 HTML、JavaScript 以及 `.wasm` 二进位文件**全部下载到他的电脑中**运行。任何人只要按下 F12，就能拿走你的全部文件。
> **这一章要问的不是「怎么防止」，而是「防不住的前提下，该怎么设计」。**

## 情境 1　二进位的「天然混淆」到底有多强

**背景**：`.wasm` 可以被下载，但它与 JavaScript 有本质差异。

**JavaScript 即使压缩（minify），逻辑依然可读**：变量名没了，但控制流、字符串常数、API 调用、业务逻辑的形状全都摊在那里。一个有经验的人花半小时就能看懂一段压缩过的 JS 在做什么。

**Wasm 则是由 C++、Rust 或 Go 编译出来的低级二进位指令格式**。当别人拿到你的 `.wasm`，他看到的不是原代码，而是这种东西：

```wat
(func (;42;) (param i32 i32 i32) (result i32)
  (local i32 i32 i32 f64)
  local.get 0
  i32.load offset=12
  local.tee 3
  i32.const 3
  i32.shl
  local.get 1
  i32.add
  f64.load
  local.set 6
  ...
  br_if 2 (;@1;)
  ...)
```

**这里有一个关键的信息丧失**：C++ 的类别、继承关系、模板实例化、Rust 的 trait dispatch、所有的变量名与函数名——**在编译过程中全部被抹掉了**。剩下的只有几百万条平坦的堆栈指令。

**工业级的防御编译设置**：

```toml
# Cargo.toml —— 这是「发布版」必须开的四个开关
[profile.release]
opt-level = 3        # 或 "z"（体积优先）
strip = true         # ★ 强行剔除所有函数名与变量名（name section）
lto = true           # ★ 全局链接时优化——跨 crate 内联，打乱原本的函数边界
codegen-units = 1    # 让 LTO 有完整视野，内联更彻底
panic = "abort"      # 顺便砍掉 unwinding 表（同时省体积）
```

```bash
# C/C++ (Emscripten)
emcc -O3 -flto --closure 1 -s ASSERTIONS=0 ...
# 额外一道：Binaryen 再剥一次
wasm-opt -O3 --strip-debug --strip-producers --strip-target-features in.wasm -o out.wasm
```

**这样编译出来后，攻击者即使使用逆向工程工具（`wasm2wat`、`wasm-decompile`、或 Ghidra 的 Wasm 加载器）反汇编，看到的也只是一堆毫无语义的 `func_1`、`func_2`。想要逆向还原出内核算法逻辑，难度逼近去逆向一款商业单机游戏。**

**但要精确理解「难」的层次**，这里有一段必须说清楚的技术现实：

| 层级 | 攻击者能拿到什么 | 难度 |
|---|---|---|
| 1. 读出所有明文本串 | `strings app.wasm` 或扫 Data 段 | **秒级**——任何人都能做 |
| 2. 看到模块接口 | Import/Export 段是规范强制的、**永远无法剥离**，函数签章一目了然 | **秒级** |
| 3. 反汇编成 WAT | `wasm2wat` / `wasm-objdump -d`，得到可读的指令串行 | **分钟级**，工具是现成的 |
| 4. 粗略还原控制流与数据流 | `wasm-decompile`（WABT 内置）、Ghidra + Wasm 插件，得到类 C 的伪码 | **小时级** |
| 5. 还原出「这是什么算法」 | 需要领域知识 + 大量交叉比对 | **天到周级** |
| 6. 还原成可维护、可再开发的原代码 | 几乎没有经济理由这么做 | **月级以上，通常不划算** |

**注意第 2 层**：Wasm 的 Export 段是规范要求的，你**不可能**把它剥掉——攻击者永远能看到「这个模块导出了 `compute_risk_score(i32, i32) -> f64`」这种信息。剥离符号只挡得住第 5、6 层，挡不住前四层。

> ⚠️ 真伪提醒
> 「Wasm 是不可逆的二进位转译」这句话**不成立**。Wasm 的二进位格式是**完全公开且结构化**的，反汇编回 WAT 是无损的、机械的、有现成工具的——这比逆向 x86 机器码**容易得多**（x86 还有变长指令、数据与代码混杂、间接跳转表等难题，Wasm 全都没有）。准确的说法是：**Wasm 隐藏的是「原代码的语义层」（类型、命名、抽象），而不是「程序的行为层」。** 一个有决心、有领域知识的分析者，可以完整理解一个 Wasm 模块在做什么——**混淆擡高的是成本，不是可能性。**

> 💡 君之一席话
> 与君一席话：**所有的代码保护技术，卖的都不是「不可能」，是「不划算」。** 没有任何混淆、加壳、白盒密码学能在数学上阻止一个握有二进位、握有时间、握有决心的人；它们做的全部是同一件事——**把攻击成本擡到高过攻击收益**。这意味着保护强度的正确衡量单位不是「有多难破」，而是「破了能赚多少」。一个保护一周活动抽奖逻辑的混淆，弱一点无所谓；一个保护内核定价模型的混淆，再强也可能不够——因为对手的收益可能是你的整个市场。**所以每次讨论「这样够不够安全」时，该先问的问题是：破解成功的人能拿走多少钱？** 那个数字定义了你需要的保护等级，也定义了什么时候该停止在保护上投资、改把资产搬到别的地方去。

## 情境 2　两大物理禁区：放进去就一秒破功

**背景**：Wasm 的二进位很难被完整还原，**但如果你的代码包含以下两样东西，一秒钟就会破功。**

### 禁区一：硬编码的密钥（API Keys / Private Keys）

**绝对不要**在 Wasm 代码内写死任何 AWS 密钥、OpenAI API Key、数据库密码、签章私钥。

**攻击者不需要读懂你的算法**——他们只要用二进位字符串扫描工具（Linux 的 `strings` 指令）扫描你的 `.wasm` 文件，一秒钟就能把你的明文本串全部抓出来：

```bash
$ strings app.wasm | grep -Ei 'sk-|AKIA|BEGIN.*PRIVATE|password|secret'
sk-proj-aBcD1234...
AKIAIOSFODNN7EXAMPLE
-----BEGIN RSA PRIVATE KEY-----
```

**为什么剥离符号救不了你**：`strip` 剥掉的是 **name 自订区段**（函数名、变量名）。**字符串常数在 Data 段里**，那是程序运行必需的数据，**不可能被剥离**。它就在那里，明文，等着被 grep。

**常见的错误补救与它们为什么没用**：

| 错误补救 | 为什么没用 |
|---|---|
| 把密钥做 Base64 编码 | `strings` 抓不到，但 `base64 -d` 一秒还原；且解码函数就在旁边 |
| 把密钥切成几段再拼接 | 拼接代码就在二进位里，动态运行一次就吐出来了 |
| 用 XOR 加密密钥 | 密钥的密钥也在二进位里（这是白盒密码学的根本困境） |
| 「反正没人会逆向我的小项目」 | 自动化扫描仪每天在爬 GitHub Pages 与 npm，不挑对象 |

**唯一正解**：**密钥永远不进客户端。** 前端向你自己的后端要一个**短期、限定范围**的 token，后端才持有真正的密钥。这条规则对 Wasm、对 JS、对行动 App 一模一样——**Wasm 不会让一个本来就错的架构变对。**

### 禁区二：内核商业绝对机密

如果你的公司靠着某个专利的「独家内核预测算法」赚钱，且这个算法一旦外泄公司就会破产，**那这项业务绝对不能放在 GitHub Pages 跑 Wasm。**

**判断准则很简单**——问自己一句：**如果竞争对手明天就完整拿到这段逻辑，我还剩下什么？**

- 「还剩下数据、用户、通路、品牌、合规资质」→ 可以放前端。
- 「什么都不剩」→ 那它必须在服务器上，而且必须是你控制的服务器。

## 情境 3　工业界的标准答案：混合架构

**背景**：为了同时拿到「静态托管的零成本与无限并发」与「商业机密的安全」，成熟团队的标准做法是**混合架构（Hybrid Architecture）**。

**这条分界线的画法**：

```
┌──────────────────────── 客户端（可被完整下载）────────────────────────┐
│                                                                     │
│  前端 Wasm 负责「密集运算与像素渲染」                                  │
│  ─────────────────────────────────────────                          │
│  · 3D 几何矩阵运算、有限元素求解                                       │
│  · 高频滤波、影音流式切块、编解码                                       │
│  · 大数据本地分析、SQL 查找、索引检索                                   │
│  · 标准算法（卷积、FFT、A*、牛顿法……业界公开）                        │
│                                                                     │
│  特征：代码体积大、消耗算力高、但算法本身是公开的                     │
│  收益：省下大量后端算力费用、数据不离端、无限并发                         │
└─────────────────────────────────────────────────────────────────────┘
                              ↕  最小化的、加密的、有鉴权的接口
┌──────────────────────── 服务器端（你完全控制）────────────────────────┐
│                                                                     │
│  后端 API 负责「鉴权、安全校验与机密内核」                              │
│  ─────────────────────────────────────────                          │
│  · 用户登录、工作阶段、权限判定                                       │
│  · 扣款、额度、计量、稽核日志                                          │
│  · 密钥保管、签章、加密解密                                            │
│  · 数据库读写、多人协作的冲突解决                                       │
│  · 真正的商业机密算法（如果有的话）                                    │
│                                                                     │
│  特征：运算量小、但一旦泄漏就是灾难                                     │
│  形态：可以极轻量（AWS Lambda、Cloudflare Workers 都够用）             │
└─────────────────────────────────────────────────────────────────────┘
```

**这个架构的经济学很漂亮**：**运算量大的部分（贵、但不机密）免费送给客户端跑；机密的部分（值钱、但运算量小）留在一台便宜的服务器上。** 两边的成本结构恰好互补——这不是巧合，这正是它能成为标准答案的原因。

**一条实用的划线问句**（比任何架构图都好用）：

> 对每一个功能模块问：**「这段逻辑如果被逐字公开在博客上，我的生意会受影响吗？」**
> - 不会 → 放前端 Wasm，省钱。
> - 会 → 放后端，而且要问第二句：**「它需要的运算量，值得我为它养一台服务器吗？」**
>   - 值得 → 标准后端服务。
>   - 不值得 → 重新设计，把它拆成「前端算、后端验」。

**第三句话是最有价值的**：很多看似必须放后端的重运算，其实可以拆成**前端算出结果 + 后端验证结果**。验证通常比计算便宜几个量级（想想工作量证明、想想零知识证明、想想「排序很贵、检查是否已排序很便宜」）。**这是混合架构最精妙的一层。**

> 💡 君之一席话
> 与君一席话：**架构设计的本质，是把不同性质的成本放到最适合承担它们的地方。** 算力便宜但量大——那就放到有无限台免费电脑的地方（用户的浏览器）；机密昂贵但量小——那就放到一台你能上锁的地方（你的服务器）。真正的架构功力不在于选对框架，在于**看出每一项成本的「性质」，然后为它找到成本曲线最平的那个位置**。这条原理可以推广到所有工程决策：缓存放在读多写少的地方、索引建在高基数的字段上、异步用在等待时间长的地方、限流放在最靠近攻击源的地方。**每当你犹豫「这段东西该放哪」时，不要问「哪里技术上可行」，要问「这段东西的成本是什么性质的，哪里承担它最便宜」。**

## 情境 4　逆向思考：被看光有时是终极武器

**背景**：在某些领域，「被看光」不是缺陷，是**唯一能创建信任的方式**。

### 端到端加密（E2EE）的信任基石

在密码学与零知识证明（ZKP）领域，用户为什么敢把高度敏感的私钥放在你的网页上计算？

**就是因为你的网页部署在 GitHub Pages 上，代码完全开源且透明。** 用户可以用开发者工具（F12）检验每一行 Wasm code，确保你**百分之百没有把他的数据偷偷上传到第三方服务器**。这正是去中心化应用（DApp）的内核优势。

**技术上这个信任链是怎么成立的**（比「开源」三个字精确得多）：

1. **可稽核的网络行为**：用户打开 DevTools 的 Network 分页，如果你的 PGP 工具在用户按下「加密」之后**一个外连请求都没有发出**，这是一个谁都能验证的事实。
2. **可稽核的二进位**：`.wasm` 的哈希值可以被计算、被记录、被比对。搭配可重现建置（reproducible build），社群可以验证「这个 `.wasm` 确实是那份原代码编出来的」。
3. **没有服务器可以被入侵**：静态托管没有应用层后端，也就没有 SQL injection、没有 SSRF、没有被入侵后偷偷替换回应的可能。
4. **变更是有纪录的**：代码与 `.wasm` 文件锁在你的 Git commit 历史里，任何人想动你的代码都必须通过你的 Git 签章。**攻击者无法在用户不知情的情况下悄悄替换某一次回应**——他必须推一个所有人都看得到的 commit。

### 防篡改的另一面

如果你的服务有后端，**后端一被入侵，前端网页就可能被注入钓鱼脚本**，而且是静默的、针对特定用户的、事后查不到的。静态托管把这个攻击面整个移除了。

> ⚠️ 真伪提醒
> 「GitHub Pages 的代码锁死在 Git commit 记录中，安全性极高」这句话要加三个但书：**（一）** 攻击者若取得你的 GitHub 帐号或 Personal Access Token，一样可以推 commit——**帐号安全才是真正的边界**（请打开必要的双因素验证与分支保护）。**（二）** 供应链风险依然存在：你的建置流程若引入了被投毒的 npm 套件或 crate，产出的 `.wasm` 本身就是恶意的，而它同样有一个漂亮的 commit 纪录。**两条 Wasm 特有的检查值得记住：用 `wasm-objdump -x` 看 import 清单（模块要了哪些能力，那张清单就是它的攻击面），以及可重现建置（让社群能验证「这个二进位确实是那份原代码编的」）——见附录 O §7-2。****（三）** 「用户可以检验每一行 Wasm code」在理论上成立，**在实务上几乎没人做**——除非有第三方安全审计或社群持续监控。**透明性提供的是「可被稽核」，不是「已被稽核」。** 这两者的差距，就是大多数安全事故发生的地方。

> 🔍 进阶点评──同一个性质，在两种商业模式下的价值符号完全相反
> 这一章最值得带走的东西不是任何一项技术，是一个结构性的观察：**「代码可被完整查看」这个性质本身没有好坏，它的价值符号由商业模式决定。** 对一个卖**算法本身**的公司（例如一个靠独家压缩算法授权赚钱的厂商），透明是纯负债——它的全部价值就在那段代码里，看光即归零。对一个卖**信任**的产品（密码学工具、DApp、隐私钱包、医疗数据处理），透明是内核资产——它的全部价值在于「你可以自己验证我没有作恶」，藏起来反而一文不值。而在这两极之间，是绝大多数的软件公司：**它们的价值既不在算法里，也不在透明性里，而在数据、在用户关系、在合规资质、在生态里**——对它们而言，代码的可见性其实**无关紧要**，纠结于此是一种昂贵的分心。**所以在投入任何代码保护预算之前，先诚实回答一个问题：我的护城河，到底在不在代码里？** 大多数人不敢回答这个问题，因为答案往往是「不在」——而承认这一点，意味着要去面对一个更难的问题：**那它在哪里？** 这正是接下来三章的全部内容。

## 本章小结

- 静态托管上的一切都会被完整下载，**这是定义，不是缺陷**。讨论的起点应该是「防不住的前提下怎么设计」。
- Wasm 的「天然混淆」是真的，但要精确理解层次：**明文本串（秒级）、Export 接口（秒级，且规范强制无法剥离）、反汇编 WAT（分钟级）、伪码还原（小时级）、看懂算法（天到周级）、还原成可维护原代码（月级，通常不划算）。** `strip`/`lto` 只挡得住后两层。
- **「Wasm 不可逆」是错的**——它的格式完全公开且结构化，反汇编比逆向 x86 **容易得多**。混淆擡高的是成本，不是可能性（见情境 1 ⚠️）。
- **两大物理禁区**：**硬编码密钥**（`strings` 一秒抓出，Data 段无法剥离，所有编码/切段/XOR 补救都无效）与**内核商业机密**（判准：如果对手明天完整拿到这段逻辑，我还剩下什么）。
- **混合架构是标准答案**：运算量大但算法公开的推给客户端（省钱），运算量小但一旦泄漏就是灾难的锁在服务器（安全）。最精妙的一层是——**很多重运算可以拆成「前端算、后端验」，而验证通常比计算便宜几个量级。**
- **透明性在某些领域是内核资产**（E2EE、DApp、隐私工具），因为它提供了「可稽核的网络行为 + 可稽核的二进位 + 没有可被入侵的后端 + 有纪录的变更」。但要记得：**透明提供的是「可被稽核」，不是「已被稽核」**（见情境 4 ⚠️）。
- 最终的问题不是「怎么藏代码」，而是——**我的护城河，到底在不在代码里？**

理论说完了。下一章看一个把这套架构做到极致的真实案例：**`figma.wasm` 每天被下载到全球数亿台电脑上，为什么至今没有人做出一个能用的山寨版？** 翻到第 10 章。
